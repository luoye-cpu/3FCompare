### What this adds

HDR10+ (SMPTE ST 2094-40) dynamic metadata, end to end: bitstream parsing, per-window
targeted tone curves applied inside the SDR tone-mapping path, per-frame DXGI HDR metadata,
and an injection API -- `FFF3FP_SetHdrDynamicMetadata`, `FFF3FP_ClearHdrDynamicMetadata`,
`FFF3FP_GetHdrMetadataSource` -- so a host can drive that same path from an external source,
multi-window tables included.

### Semantics that measurement settled

These six are the behaviours a caller cannot infer from the signatures, so they are written
into `FFF.Player.Api.h` as contracts.

- **Table entries are keyed by decoded frame index, not by `pts`.** With a 1/15360 time base
  at 60 fps, frame 4 carries `pts = 1024`; using `pts` as the index silently selected the
  wrong entry and, for a sparse table, kept holding the previous one. A frame the session
  does not index (cover art, still image, warm-up) leaves the last indexed entry in force; a
  `pts` is never written into the index space.
- **Installing or clearing a table re-presents the cached frame**, so the picture changes
  while paused and at end-of-stream instead of only the diagnostics moving. It goes through
  the normal render path (`Redraw` -> presentation pump -> `DrawWithShader`), where the curve
  constants and the LUT are refreshed from a dirty flag consumed on the presenting thread --
  there is no second writer of those shader inputs.
- **The injection owns the metadata in force, not the classification of the samples.** The
  decode transfer decision and the gamut switch keep reading the stream's own format. ST
  2094-40 curves are defined for signals carrying their own transfer characteristic, so on an
  SDR-transfer source a table stays installed but inert (measured: 10 sampled points moved by
  up to 0.29020 in code value before this was fixed; 0 of 10 move now, and
  `hdrProcessingPath` stays 0).
- **Peak ownership**: an injected entry's own signal peak wins, otherwise the stream-level
  baseline. A curve whose windows carry no peak is no longer overwritten by the static
  `maximum_maxrgb` / `max_luminance` reading.
- **A Vivid baseline signalled as HLG is not read through the PQ absolute domain**, because
  `maximum_maxrgb x 10000` is only meaningful for PQ. An HLG-baseline stream that read 10000
  now reads 4000, while a PQ baseline with `maximum_maxrgb = 2048/4095` still reads 5001 --
  the `x 10000` arm is intact.
- **Curve rows and unused window slots.** The LUT is `kHdrMaxProcessingWindows` rows tall and
  a window addresses its row as `(index + 0.5) / rows`; passing the raw index addressed the
  middle window onto the last row, handing it another window's curve (out by 0.65396 against
  its own curve, tolerance 0.012). Slots the table does not use are parked one at a time: a
  slot left holding the array's default rectangle `(0,0)-(1,1)` is not "no area", because the
  blend ramps are symmetric about each border, so with a two-window table the third slot kept
  weight 1 while its row had never been written (the row array is zero-initialised and only
  as many rows as windows built are filled) -- the normalised blend then halved the whole
  picture in the PQ code domain. With one probe binary and only the DLL swapped: worst
  `left 0.77126 / right 0.79863` before, `0.00000 / 0.00000` after. Single- and three-window
  tables are unaffected by that change, which is why the rest of the readings do not move.

### Compatibility

`PlayerApiVersion` goes **16 -> 17** and `FFF3FPSnapshot` gains five diagnostic fields at the
tail. `FFF3FP_GetSnapshot` rejects a caller whose declared size is smaller than its own
struct, and the version gate is exact equality, so out-of-tree hosts must bump their
constant and extend their mirror in the same change. `FFF.Native.rc` and the in-tree
`FFF.Player` host are moved here for that reason: landing the kernel alone would leave the
application shipped in this repository unable to create a session (`FFF3FP_Create` refused,
`GetSnapshot` returning 7).

### Review notes

- `Render/ShaderBytecode.h` is generated by `tools/generate_shader_bytecode.py` (fxc
  10.0.28000.0). One array grows, 134,752 -> 141,872 bytes; the other six are byte for byte
  what you have. Because the delta is not a multiple of the six-values-per-line layout,
  everything after the insertion point re-flows, so `--stat` overstates the change
  enormously. Re-running the generator reproduces the untouched programs.
- `Render/SdrShaderBytecode.h` is deliberately not in this PR. The SDR specialisations compile
  the dynamic branch away, and regenerating produced all three arrays identical to yours.
- The decode transfer decision was factored into `PlayerVideoRenderer::ResolveDecodeTransfer`
  so the per-frame path and the injection-refresh path cannot diverge. It reproduces the
  three-way decision that was inline (Dolby Vision compatibility layer, then the frame's own
  `color_trc`, then format fallback), which is why those lines appear as removals. Upstream's
  `av_frame_free` for the gamut-converted frame is kept.
- COM teardown follows upstream's `ReleaseCom(T*&)` helper rather than the older hand-written
  releases, so the five objects upstream added there are not dropped.
- **This commit adds no tests.** The numbers quoted above come from probes maintained outside
  this repository; the repo's own test projects (`FFF.Player.Tests`, `FFF.Recorder.Tests`)
  gain no case, and nothing in-tree drives the injection API yet. Treat the feature as
  kernel-level until a test lands with it.
- `FFF.Player` is reviewed by construction, not compiled: this machine cannot build it (the
  `LakeUI.*` dependency set is missing). Field order, widths and both version gates were
  checked item by item against `FFF.Player.Api.h`. Please build it once before merging.

### One deviation I left for your judgement, not silently changed

In a multi-window table, the normalisation denominator is taken from window 0 for the whole
frame (`settings.sourcePeak = clamp(metadata.windows[0].signalPeakNits, 1, 10000)`) and the
curve builder never reads a window's own `maxscl` -- so per-window signal peaks other than
window 0 currently have no effect. Measured: doubling window 1's own `maxscl` moves its region
by 0.00000. ST 2094-40 scopes `maxscl`, the bezier anchors and `tone_mapping_flag` "in the
processing window", which points at a per-window denominator, but I could not get the
normative sentence about the curve's input denominator, and the fix is not a one-liner: it
needs a per-window peak in `b2` (struct, HLSL declaration, two fill sites, regenerated
bytecode). I did not do it here because the reference I measured against pins its own peak to
window 0, so it would have judged the more conformant build red by 0.46945-0.48663 -- the
expectation has to be rebuilt first. Single-window streams are unaffected either way: there
window 0's own peak is the only frame peak. Happy to land it as a follow-up if you agree the
scope is per window.
