VFR: bare-stream fixture as the fifth arm, and two of my own attributions corrected

Implementing the plan the previous round ended with, and the review of that plan
found two of its own conclusions were wrong. Both are corrected here with the
measurements that overturned them.

* The bare-stream defect was not where I said twice. Three attributions fell in turn:
  the FlushAtEnd condition (harmless as written), then Seek() running
  DecodeUntilSeekTarget() after a failed DoSeek (real, and guarded now, but not this
  case), then rolling the reader back to its previous offset (rollback succeeded and it
  still decoded nothing, because avio_tell reports a buffered logical position that can
  sit inside an access unit). The measured mechanism is that a demuxer without
  read_seek scans forward for a timestamp pair while trying a timestamp seek, so a
  failed seek leaves the reader at end of file -- FFF_SEEK_TRACE=1 showed
  before=450560 after=1102103 on a 1102103-byte file. Kernel fix is in 8cdc22e: seek to
  position 0 needs no time-to-byte mapping, so it no longer hides behind
  timelineExtent > 0, which is exactly the test untimestamped sources fail.

* "Bare streams carry no timing information" was only half true. Per-packet PTS is
  genuinely absent (0/120), but the demuxer assigns a uniform per-packet duration at its
  guessed rate (120/120). So the correct reading for a bare stream is a synthesised
  constant clock, not ignorance. The fixture self-check and the docs are rewritten to
  assert what was measured, and this is again the self-check going red first that told
  me my premise was wrong.

* New fifth arm, vfr/12d_bare_20.264, generated by the [12] section and covered by a
  bare_selfcheck (packet count complete, PTS empty, durations present). Before the
  kernel fix it fails the "zero frames plus failed seek" precondition; after it: state
  Playing, 91 frames decoded, a single 20.0 Hz plateau, and frameRateMode turning from
  "variable" at open (the container comparison, which is wrong here because
  av_guess=20/1 differs from r_frame_rate=40/1) to "constant" after playback -- so this
  one fixture is simultaneously the seek regression gate and the control proving the
  measured verdict outranks the container comparison. Five arms now pass (9/9/7/7/7
  judged, none red) alongside eight fixture self-checks.

* present_pacing_probe gained the neverCompositedPresents readout and a qualification on
  the two timing judges: they now decline to judge (未判) when presented throughput is
  below 0.95x the bound, instead of reporting red for what is a scheduling shortfall.
  Measured effect on the same file: the three runs that read 66.5 / 48.7 / 91.3%
  within-band before the accumulate fix read 72.0 / 88.6 / 95.6% after, with worst
  deviations 10/11/3 falling to 8/3/2, and neverCompositedPresents measured at
  88/95/58 per eight seconds. It is a partial explanation, not a complete one: periods
  with no flip at all contribute no accumulated expectation, so the band is still too
  tight. Banding holds by the displayed frame's content duration needs media time
  inside the renderer and is deliberately left undone rather than half-claimed.

* docs/03 A12 is updated with the corrected mechanism, the three wrong turns, the
  five-arm readings, and the ABI pairing status: kernel header and the VB interop struct
  are committed and both hosts compile; the C# copy has the field added but stays in the
  worktree because that file carries someone else's 330+ lines of unpublished host work
  and my line sits in the same hunk as their new struct tail. It is declaration-only
  there today, so nothing breaks.
