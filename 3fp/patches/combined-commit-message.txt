Native: SDR scRGB presentation, P3 gamut, viewport geometry, three missing exports

One submission covering a single goal: the presented picture tells the truth about
its pixels, and the host can see how it got there. The two viewport behaviours are
exercised by the repository's own test entry point (tools/测试3FP内核.ps1); the rest are
gated so the untouched case is the pre-existing behaviour, and what this repository has
no fixture for is listed under "Not covered by an automated case".

1) 10-bit SDR sources can join the 16-bit scRGB chain (wide gamut already was there)

   - FFF3FPConfiguration gains `sdrScRgbMode` (0 = never, i.e. exactly today's
     behaviour; 1 = auto). FFF3FP_Create rejects values > 1. PlayerApiVersion
     15 -> 16; VER_API and the version resources follow.
   - One gate replaces three copies of "IsHdrSource() || IsWideGamutSource()":
     WantsScRgbPresentationPath(bitDepth) adds the term "an SDR source whose bit
     depth exceeds 8". The swap-chain gate (EnsureSwapChain) takes the depth as a
     parameter, because the member is still 0 before the first frame lands. The two
     earlier gates (SetWindow, SetColorMode) run before any frame exists and still
     pass the member, so they decide the HDR / wide-gamut terms and leave the depth
     term to the swap-chain gate. Known consequence: until the first frame lands,
     ActualColorMode() reports MapToSdr for a 10-bit SDR source that is about to be
     routed to scRGB, and the fallback text says so; the chain actually created is
     the one EnsureSwapChain picks, so this is a diagnostic gap, not a wrong chain.
   - Paper white is anchored to Windows' "SDR content brightness"
     (AdvancedColorInfo::SdrWhiteLevelInNits, with a
     DISPLAYCONFIG_DEVICE_INFO_GET_SDR_WHITE_LEVEL fallback for when the WinRT call
     briefly fails), so an SDR picture on the scRGB chain keeps the luminance DWM
     would have given the classic chain. When nothing reports it the anchor is 80
     nits (the scRGB reference white), not 200. A partial read keeps the last known
     value instead of jumping mid-playback.
   - An SDR source on that chain now declares DXGI_HDR_METADATA_TYPE_NONE instead of
     inheriting the fallback HDR10 block, which declared Rec.2020 primaries and a
     peak the source never claimed - the kind of hint that makes a display tone-map.
   - A chain that rejected scRGB no longer sticks for the lifetime of the monitor
     handle, so turning Windows HDR on during playback can recover without restarting
     the session. The two kinds of "no" get different clocks: a display that does not
     advertise Advanced Color is re-asked on the 750 ms probe cache, while a swap chain
     that refused the colour space backs off for 10 s - a refused retry destroys and
     re-creates the chain (subtitle atlas, forced re-render) on hardware that will keep
     refusing it, so sharing one timer between the two turned the rejection into a
     ~1.3 Hz chain rebuild. Every reset that forces a re-probe moves the probe timestamp
     to the epoch, which clears both clocks, so a real capability change still recovers
     immediately.
   - The fallback rung now comes from the caller's bit depth instead of the member.
     When a chain refuses scRGB the renderer falls back to the classic chain at the
     source's own precision (>8-bit -> R10G10B10A2, else BGRA8), but both rejection paths
     read `sourceBitDepth_`, which `EnsurePipeline` only assigns *after* `EnsureSwapChain`
     has run: on the first frame that is still 0, so a 10-bit source was demoted to BGRA8
     and corrected one frame later by a second reconfigure. `CreateSwapChain` and
     `ReconfigureSwapChain` now take the depth as a parameter - the same correction the
     colour gate above already makes. Not exercised on the test machine (no adapter there
     refuses scRGB); a synthetic mutant arm was built for it and its own positive control
     showed the branch was never entered, so this rests on call order, not on a reading.
   - The DISPLAYCONFIG reading compiles against both SDK shapes (newer headers move
     `size` into the device-info header and make the query single-argument) via a
     `requires` probe, and the three traps found while wiring it are recorded in
     comments next to the code.

2) Display P3 / DCI-P3 sources get their own conversion

   - The shader's gamut input stops being a boolean: the cbuffer field is `Gamut`
     (0 Rec.709 / 1 Rec.2020 / 2 P3) and FFF3FPColorTransform.source2020 accepts the
     same range. P3 -> linear Rec.709 is a pure matrix, applied identically in the
     HLSL and in the CPU reference path, with no clamping: P3 red legitimately
     produces negative components and the FP16 scRGB chain carries them.
   - P3 is tested BEFORE Rec.2020, because real P3 video is marked
     primaries=SMPTE432 with matrix_coeffs=2020_NCL (the VUI has no P3 matrix).
     Falling through the 2020 test would classify it as Rec.2020 and undo the fix.
   - Render/ShaderBytecode.h is regenerated. Of its seven arrays only the playback pixel
     shader's changed content (134,540 -> 134,752 bytes); the other six are byte-identical, as
     is every line from the next array to the end of the file, so the only structural delta is
     a two-line comment naming the generator. The remaining line churn is inherent to a hex
     array diff (six bytes per row, so one changed byte shifts every row after it): judge the
     change by the seven array lengths, not by the line count.
   - The generator that produces it from the HLSL embedded in
     VideoRenderer.cpp is added to the repository as
     tools/generate_shader_bytecode.py: a 24k-line generated header the kernel links
     directly has to be reproducible from a clean checkout. Running it against these sources
     reproduces the committed header byte for byte.

3) Viewport: signed destination origin, and zoom < 1 really downscales

   - The video destination origin was unsigned and clamped at 0, so half of the pan
     range - the half that brings the picture's right/bottom edge into view - did not
     exist (measured: sweeping pan from -1 to +1 kept reporting origin (0,0)).
     VideoDestination::x/y, RenderTargetInfo destX/destY and the recorded last
     destination are now signed; sizes stay unsigned.
   - The transform gate becomes |z - 1| > 1e-4 so z < 1 enters it, the origin
     interval is the min/max of the box's two ends (writing it as
     [x0 - (transformed - fitted), x0] inverts for z < 1 and std::clamp with lo > hi
     is undefined behaviour), the travel range is an absolute value (the old
     max(maxPan, 0) form swallowed it to zero, killing panning while downscaled), the
     origin rounds with lround, and the zoomed size keeps a 1 px floor.
   - FFF3FPRenderTargetInfo version 1 is rejected outright. v1 and v2 have identical
     field widths, so `size` cannot tell them apart and a v1 caller would read a
     negative origin as a huge unsigned value: wrong content, no error. The version
     number is the only honest discriminator.
   - FFF3FP_SetFitLimitToNative (new, additive): cap the fitted box at the source's
     native size, which turns zoom into an absolute screen:video pixel ratio - 1.00
     becomes pixel-exact 1:1 instead of fit-to-window, and a larger window letterboxes
     the whole frame. It is separate from Render()'s per-frame limit argument on
     purpose (that one is refreshed by the decode thread, so a paused session would
     keep the old geometry); it applies on the next present, re-presents immediately so
     a host reading Dest* right after the call sees the new box, and returns
     NotSupported while a disc is open because that renderer owns its own geometry.

4) Three exports hosts already call, and the kernel did not provide

   - FFF3FP_SetLogCallback installs a process-wide UTF-8 log sink; the kernel calls it
     from its decode/present threads. Failures reported through PlayerSession::Fail and
     the adapter-selection diagnostic now reach the host's log instead of only a
     debugger. The invoker (FFF3FP_KernelLogImpl) is deliberately a plain C++ symbol,
     not FFF3FP_API, so it never enters the export table that ABI checks walk. A host
     whose callback is managed code must keep the delegate reachable until the kernel's
     threads have stopped, and must not let an exception escape into the kernel - the
     header says so.
   - FFF3FP_Redraw re-presents the cached frame on the presenter thread, for a host
     that resized a child HWND and needs flips to keep issuing while ResizeBuffers
     stays on the presenter.
   - FFF3FP_SetPresentConfig selects presentation pacing. The request is stored apart
     from the swap chain's tearing capability: Present(0, ALLOW_TEARING) is used only
     when the host asked and the chain was actually created with the flag, ResizeBuffers
     keeps mirroring the flag the chain was created with, and the request survives
     device and chain re-creation. Where the OS reports no support the renderer stays
     on the vsync-locked path.

5) FFF.Player (the sample host in this repository) follows API 16

   The version gate, the struct `version` written for FFF3FP_Create, and the
   interop configuration struct all still said 15 / 80 bytes; with a 16 kernel the
   repository's own test entry point could not create a session at all. The struct
   gains the trailing sdrScRgbMode field (Marshal.SizeOf -> 84) and binds
   FFF3FP_SetFitLimitToNative as 设置原生尺寸封顶.

6) Recorder defects

   - IAudioCaptureClient::GetNextPacketSize failure was hidden in a loop condition, so
     a dying endpoint (unplug / invalidation) left the capture thread parked forever
     with no failure callback, a silently silent audio track and no diagnostic. It is
     now handled the way GetBuffer failure already was.
   - VideoMuxer refuses mixed audio at a sample rate other than 48 kHz. AudioMixer's
     timeline semantics are 48 k-based while the session feeds absolute positions
     scaled by the configured rate, so the combination desynchronised audio by the
     rate ratio (~8.8% at 44.1 k) and grew the mixer's buffers without bound.

7) Concurrency and lifetime fixes found while reading the paths above

   - ~PlayerSession released the primaries carrier filter *before* joining the worker;
     the worker's still-image path is still using that graph, so it was a
     use-after-free window on every session teardown. The release now runs after the
     join.
   - fallbackReason_ was a plain std::string assigned under the device lock on the
     render path and copied from any thread through FallbackReason(); it now has its
     own leaf mutex, matching the errorMutex_ / lastError_ pattern in the same class.
   - ConfigureHdrStream cleared the Dolby-Vision extension flags unlocked while
     EnsurePipeline does a check-then-act on them under deviceMutex_; the flag is now
     written only under that lock, so a concurrent pipeline build cannot re-enter the
     extension-shader creation block and overwrite the live shader.

Tests

- This commit carries no regression case, and that is a consequence of the upstream
  state rather than an oversight: the VB test project (`FFF.Player.Tests`, including
  `KernelTimelineTests`) and the suite entry point `tools/测试3FP内核.ps1` were removed
  upstream after the commit this branch sits on. The viewport case written against them
  is therefore not included - re-adding a test project the maintainer just deleted is
  worse than arriving without one, so this says so explicitly instead.
- What the two viewport behaviours were measured with: a downstream host driving this
  kernel over real media, whose checks are geometric and rate-based. At 1280x720 the
  native-size cap gives Dest 1280x720 at zoom=1 (ratio 1.000) and exactly 2.000 at
  zoom=2; z=0.6 downscales to 1197x673; the drag anchor moves <= 0.5 px across five
  zoom steps; same readouts at 4K. Each behaviour has its own mutation arm: dropping
  the cap term fails "the cap did not apply", and restoring the old `zoom > 1.0001f`
  gate passes the cap assertions while failing "z < 1 was treated as a no-op".
- Why those numbers are not a frame count: on a box with a global present hook (RTSS),
  "presented frames == expected frames" is not reproducible. Twelve consecutive runs on
  this kernel and eight on a fresh checkout of its parent both failed it at similar
  rates, with a different fixture each time and deficits of 1-10 frames on both sides.
  That is a property of the assertion, not of this change, and it is why the evidence
  above is geometry and rate rather than a present count.

Not covered by an automated case in this repository: the 10-bit SDR-on-scRGB route
end-to-end, the scRGB rejection -> classic-chain fallback (no adapter on the test bench
refuses the colour space, and the synthetic arm built to force it did not reach the
branch), P3 rendering of a real clip, actual tearing cadence on a VRR display, the
log sink, and the WASAPI endpoint-removal path - there is no fixture or display path
for them here. Each is gated so the untouched case is the old behaviour: policy 0, a
non-Advanced-Color display, a chain created without the tearing flag, no installed
sink, a live endpoint.

Breaking

- FFF3FPRenderTargetInfo v1 callers now get InvalidArgument. FFF.Player does not bind
  GetRenderTargetInfo, so nothing in this repository is affected.
- PlayerApiVersion 16: hosts validating the version with strict equality must bump in
  lockstep (item 5 above).
- Mixed audio at any rate other than 48 kHz is refused instead of recorded drifted.

Known, deliberately not changed here

- The two pre-frame colour gates cannot see the bit depth (see item 1), so a host
  reading ActualColorMode() before the first frame still sees the classic chain for a
  10-bit SDR source. Fixing it means making the depth available at session setup or
  deferring the diagnostic, which is a separate change from the routing fix.
- swapAllowTearing_ remains a plain bool. It is written on the chain-creation path and
  read by PresentCurrentFrame, and the two never overlap because both hold
  presentMutex_, but that is a property of the current call graph rather than of the
  type. Changing it to std::atomic<bool> is a one-line follow-up; it was left alone so
  this commit carries no unrelated concurrency churn.
