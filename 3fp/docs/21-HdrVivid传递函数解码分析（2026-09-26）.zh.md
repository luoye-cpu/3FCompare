# HdrVivid 恒按 PQ 解码的问题分析（2026-09-26）

- 触发：用户「官方 Vivid 样本是 HLG 传递函数；内核对 HdrVivid 恒按 PQ 解码亮度（只对纯 HLG 格式选 HLG 解码），这个问题需要分析一下」
- 结论先行：**对规范内的 Vivid 内容（PQ 基线），内核现状正确**；FATE 官方样本的 HLG trc 是合成测试向量的构造痕迹（只用于验证 SEI 提取）。但内核存在一个真实的防御性缺口：**「HLG trc + Vivid 元数据」的规范外组合会被按 PQ 解码**，中高信号段亮度高估数倍，且首帧（HLG）与后续帧（PQ）色调跳变。建议给上游提独立 issue（与图片模式 PR 无关）。

---

## 1. 事实链

### 1.1 规范层：HDR Vivid 的基线就是 PQ

- HDR Vivid（CUVA 005.1-2021，UWA/世界超高清视频产业联盟）规范基线 = **SMPTE ST 2084（PQ）EOTF + BT.2020 色域，峰值 10000 nits**（UWA 标准解读与技术介绍多处一致；UWA 官网标准 PDF 为扫描/压缩件无法直接抓取条文，置信度：高——多方公开资料一致，且与内核 `maximum_maxrgb × 10000 nits` 的元数据语义自洽）。
- ⇒ **HLG 不是 Vivid 的规范基线**。「HLG + Vivid 元数据」是规范外组合。

### 1.2 FATE 样本性质：合成测试向量，只测 SEI 提取

- 两个样本在 FFmpeg 官方 `tests/fate/hevc.mak` 中的测试：`fate-hevc-hdr10-plus-metadata` / `fate-hevc-hdr-vivid-metadata`，命令均为 `probeframes -show_entries frame=side_data_list` —— **只验证「T.35 SEI → frame side data」这一步**，不涉及显示正确性。
- Vivid 样本内部是混搭构造：trc=HLG（arib-std-b67）+ mastering display 元数据（max_luminance=4000 nits）+ CLL=0 + Vivid SEI（targeted≈676 nits）——不是真实 Vivid 内容形态（真实内容恒 PQ，CLL 应有效）。

### 1.3 内核行为（代码证据）

| 环节 | 位置 | 行为 |
|---|---|---|
| 流级分类 | `HdrProcessor.cpp:180-204` `ConfigureStream` | 按容器 side data / `color_trc` 先验：HDR10+ 侧数据→Hdr10Plus；**trc=HLG→Hlg(3)**；trc=PQ→Hdr10(1) |
| 帧级翻转 | `HdrProcessor.cpp:248-262` `ProcessFrame` | 首帧带 Vivid side data → format=**HdrVivid(5)**、path=**HdrVividDynamic(6)**、sourcePeak=maximum_maxrgb×10000 |
| 解码传递函数 | `VideoRenderer.cpp:4121-4124` | `settings.transfer = (format==Hlg ‖ (DV 且 HLG 兼容位)) ? 2 : (非 SDR ? 1(PQ) : 0)` ⇒ **HdrVivid(5) → PQ**，与流 trc 无关 |

⇒ HLG trc 的 Vivid 流：首帧按 HLG（[open] 阶段，format 尚为 Hlg）呈现，翻转后按 PQ 解码；同一文件两种传递函数混用。

## 2. 影响分析

### 2.1 对规范内容（PQ 基线 Vivid）：✅ 正确

真实 Vivid 内容恒 PQ ⇒ 「HdrVivid → PQ 解码」恰好正确。元数据驱动的逐场景峰值（maximum_maxrgb×10000）也只在 PQ 绝对亮度域语义下成立（CUVA 005.1 的 maxRGB 是 12bit 归一的绝对亮度统计）。

### 2.2 对 HLG 基线的 Vivid（规范外）：❌ 色调错

HLG 信号被按 PQ EOTF 解释的近似量级（PQ⁻¹ 的已知锚点 vs HLG 逆 OETF，按 1000 nits 参考对齐）：

| 信号码值 | HLG 场景光（意图） | 按 PQ 解出的绝对亮度 | 误差 |
|---|---|---|---|
| 0.35 | ≈ 41 nits | ≈ 27 nits | 低估 ~35% |
| 0.50 | ≈ 83 nits | ≈ 92 nits | 接近 |
| 0.75 | ≈ 241 nits | **≈ 1846 nits** | **高估 ~7.7×** |
| 0.90 | ≈ 548 nits | **≈ 9860 nits** | **高估 ~18×** |

规律：中间调大体接近，**0.6 以上急剧高估**（PQ 曲线高段陡升）——HLG 内容的高光被按 PQ 解出天文数字亮度，再经 BT.2390 从 10000 nits 元数据峰值压缩 ⇒ 高光过曝/灰化/褪色。

### 2.3 翻转时序跳变

`[open]` 阶段（ProcessFrame 未跑）首帧按 Hlg 路径（transfer=2）呈现；Play 后首帧元数据到达 → 后续全部按 PQ ⇒ 同一文件第 1 帧与第 2 帧起色调不一致（实测 sourcePeak 首帧即 10000，outBits=16，无崩溃）。

### 2.4 同根因的延伸面

`transfer` 由 `hdrState.format` 推断的写法对**一切「元数据分类 ≠ 像素 trc」的组合**都会错：HDR10+/HLG 怪流（ST 2094-40 规范上也只定义于 PQ）同理。DolbyVision 是唯一被正确处理的例外（4122-4123 显式看 HLG 兼容位）。

## 3. 修复建议（供上游 issue / 后续 PR，与本次图片模式 PR 无关）

**方案 A（推荐，最小正确）**：`settings.transfer` 改由**像素级 trc** 决定，元数据分类只负责峰值与处理路径——ST 2094 系列元数据本来就定义在「不改变像素编码」的前提下，元数据到达不应改变像素解码方式。
- 落点：`VideoRenderer.cpp:4121` 的判定改为优先读 `frame->color_trc`（解码帧自带，翻转前后每帧一致）：`trc==ARIB_STD_B67 → 2`；DV 保留现有 HLG 兼容位判定**且优先级高于帧 trc**（DV RPU 重映射语义特殊）。
- 验证：FATE Vivid 样本修复前后读像素/色调锚点对比（应从 PQ 解码值回到 HLG 值），`dynamicMeta=1`、`path=6`、峰值 10000 均不变。
- 附带收益：消除首帧/后续帧的传递函数跳变。

**方案 B（保守）**：维持现状，仅在 issue 里声明「HLG 基线 Vivid 不支持、按 PQ 解码」。
