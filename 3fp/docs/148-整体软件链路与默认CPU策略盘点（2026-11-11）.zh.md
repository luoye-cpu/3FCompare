# 148 · 整体软件链路与默认 CPU 策略盘点（2026-11-11）

> **状态：草稿（交接版）**。已写的结论与默认值矩阵都来自代码阅读，可以直接引用；但 §一/§二的**完整线程清单**原计划并入两份并行静态审查（内核侧 CPU 策略盘点、宿主侧 CPU 策略盘点）的报告，交接时报告尚未回收 ⇒ 并入后再定稿。两份审查都是只读任务，无写风险。

> **问题**：把 3FP 从"双击启动 → 打开 → 播放 → 空闲"的整条链路按层拆开，说清**默认设置**下每一层的 CPU 策略（进程优先级/线程优先级/CPU Set/线程数/唤醒节奏），并给建议。
>
> **结论（先看这 8 条）**：
> 1. **默认策略是"三套旋钮各管一段、互不通信"**：宿主启动期把整进程拉到 HIGH 再 1.5 s 后恢复；内核 `PlacementPolicy` 在播放开始后按拓扑给**整个进程**设软 CPU Set、并在压力下把进程抬到 ABOVE_NORMAL + present 线程 HIGHEST；运行期预取又在自己起线程/进程。没有单一所有者，也没有统一状态机。
> 2. **唯一"真 CPU 策略"（CPU Sets）至今零收益账**：播放期 tier0 从未用 `FFF_PLACEMENT=off` 做过 A/B；新增的启动期放置（docs/147）默认关、同样未测。它还是**进程级**软亲和，会把宿主 UI、计时器、预取线程一起约束。
> 3. **启动期 HIGH 是纯负担**：两次实测没有收益（docs/120 混合臂、docs/124 单独臂 Δ+4.4 ms/p=0.78；docs/145 复核），且它埋了一个真缺陷——若"启动即播放"落在 `Shown+1500 ms` 之前，内核会把 HIGH 记成基线，之后 Boost 释放时恢复成 HIGH（docs/124 §4.1，本机未复现但代码路径成立）。
> 4. **默认开的"未量化项"在叠加**：多适配器解码回退默认 on（docs/144 ST-11 未做 A/B）、运行期预取引擎默认 on（`FFF3FP_PREFETCH` 默认 true，mode=2 连 helper 一起）、自适应解码线程默认 on（floor 4/ceiling 32，受 CPU 数-4 封顶）。出问题时无法归因到单一旋钮。
> 5. **预取侧车是默认 CPU 策略里最大的漏洞**（docs/144 PF-1）：静图侧车解码 `avcodec_alloc_context3` 后**不设 `thread_count`**，FFmpeg 取 `av_cpu_count()`（本机 20）⇒ 首次打开静图会连发 6 次解码、可拉起约 20 个 worker，且 `worker_` 线程未降优先级，完全绕过主链路的"预留 3+1 线程"预算，正压在开图动画/缩放上。
> 6. **常驻 CPU 税分散在多处**：session pump 有三处 `Sleep(1)/Sleep(2)` 每毫秒唤醒（docs/144 KR-13，0.3–1% 单核 + ~1000 次/s 上下文切换）；`PrecisionTimer` 只要还挂着就持有进程级 `timeBeginPeriod(1)`（docs/144 HS-7）；宿主常驻 100/200/67/1000 ms 等计时器链。
> 7. **线程预算只看逻辑核数**：`ReservedPlaybackThreads=3 + SchedulerHeadroomThreads=1`（`PlayerSession.cpp:161-162`）不知道 P/E 拓扑，也不知道宿主线程、helper 进程、AI 字幕进程的存在；hybrid 上"P 线程 12"与"20 逻辑核"是两个数。
> 8. **建议**：先做 3 件"卫生"（删启动 HIGH、预览期 CPU Set 补 A/B、给关键线程补 `SetThreadDescription`），再收 3 处常驻税（KR-13 等待、timeBeginPeriod、计时器链），最后才谈把 CPU 拓扑策略产品化（单状态机 + 快照导出）。**不建议**再加任何进程级默认旋钮，除非先有 A/B。

## 一、链路分层：谁在哪个进程/线程跑

```
L0 进程启动（apphost→CLR→R2R/JIT→Main，~116.7 ms，docs/136）
   └ 应用无法干预；进程此时 NORMAL
L1 宿主 Startup→Form1_Load（UI 线程）
   ├ 进程优先级 = HIGH（默认开，FF_NO_STARTUP_PRIORITY=1 可关）
   ├ GPU 预热线程（后台；进程此刻 HIGH ⇒ 它继承线程优先级也是"HIGH 类"）
   ├ 启动期预取大件（默认关）；启动期 CPU 放置（默认关，docs/147）
   └ InitializeComponent / 设置加载 / LakeUI Attach（294.5 ms，其中 258.5 ms 必须付）
L2 内核创建 FFF3FP_Create（在 UI 线程上同步，~398 ms 含 WarmDevice 150–170 ms）
   └ 无 CPU Set（启动放置关）；进程仍 HIGH
L3 打开 → 首帧（session worker 线程 + FFmpeg 解码线程 + present）
   ├ 播放开始：PlacementPolicy.OnPlaybackStart 采样基线 → 设进程默认 CPU Set
   ├ present/worker 线程：SetThreadSelectedCpuSets 固定 tier0
   └ 首帧 Present(1,0) 等 vblank；DWM/GPU 等待与 CPU 策略无关
L4 稳态播放（worker + 解码线程池 + WASAPI 线程 + cover backdrop 线程）
   ├ 压力升级：Spill → 解码 ladder(4→32) → Boost(进程 ABOVE_NORMAL + present HIGHEST)
   ├ Prioritize overlay：线程预算耗尽时长期抬到 ABOVE_NORMAL + present HIGHEST
   ├ 音频：WASAPI event 线程（普通 std::thread，无 MMCSS/无优先级设置）
   └ cover backdrop：BELOW_NORMAL（VideoRenderer.cpp:8332）
L5 后台/辅助（默认开）
   ├ 内核预取 worker + guard 线程（NORMAL，不降优先级；mode=2 默认）
   ├ FFF.PrefetchHost.exe（BACKGROUND 模式 + LOWEST 线程 + Job 25% CPU 上限——公民性好）
   └ AI 字幕（用户启用后）：子进程 BelowNormal + 宿主 3 条 NORMAL 管道线程
L6 空闲（未打开媒体 / 播放暂停）
   ├ 进程回 NORMAL（宿主已恢复），无 CPU Set
   ├ UI 计时器链仍在跑（100 ms 界面呈现、200 ms 信息图层等）
   └ PrecisionTimer 只要挂着一个就持有 timeBeginPeriod(1)
```

## 三、结构性问题（按严重度）

**A. 优先级有三个写者，生命周期不对齐（最高风险）**
- 宿主只在启动期写（HIGH→恢复），内核在播放期写（ABOVE_NORMAL/present HIGHEST）并用**播放开始时的进程 class 当基线**（`PlacementPolicy.cpp:476-480`）。两者重叠时基线可能是 HIGH（docs/124 已判"真缺陷、边界未复现"）。
- 宿主恢复是**固定 1500 ms**，与真实打开时长无关：低负载下白付一段 HIGH，重负载/大文件下还没打开完就降回。
- 内核 `Prioritize` overlay 一旦触发就常驻到 `Release()`，健康窗口的 `Recover()` 只降 tier 不清 overlay ⇒ "一次压力 = 整段会话 ABOVE_NORMAL"。

**B. 启动期 HIGH 已被实测否定**
- docs/120：优先级+预取混合臂 Δ−111.7 ms（归因未拆）；docs/124：优先级单独 Δ+4.4 ms、U=92、p=0.783；docs/145 复核结论"建议删除或改事件驱动"。默认继续开着只有成本。

**C. CPU Set 是唯一"拓扑感知"的机制，却没验证过**
- 播放期 tier0 与 docs/147 启动期放置都是复用同一套发现逻辑，但整套只有"设计正确性"审查，没有性能读数。它的软亲和还会覆盖**宿主**所有未显式选择的线程（UI、计时器、预取 worker），效果不是"只约束播放线程"。

**D. 线程预算没有拓扑概念**
- `DecoderThreadBudget = 逻辑核数 − 4`（本机 16），而 tier0（P 组）只有 12 ⇒ 解码 ladder 升到 13+ 就会把 worker 放到 E 核（docs/144 注释承认"不跨物理边界一步"，但预算本身不分层）。hybrid 上"预算"应该写成"P 线程数 + 允许 spill 的 E 线程数"两段。

**E. 常驻税分散**
- KR-13 的 `Sleep(1)/Sleep(2)` 三处（4K 稳态队列饱和是常态，每毫秒跑完整 tick 前导）；KR-8/KR-15 每帧/每包查环境变量；HS-7 的 timeBeginPeriod(1)；6 条以上常驻计时器（播放/暂停/最小化都不分）。

**F. 默认开项缺少"出生账"**
- 多适配器回退、运行期预取、自适应解码线程三项默认 on，叠加在同一个启动/打开窗口里；任何一次"某机器变慢"都要先拆三层才能定位。docs/143 已要求"4 个默认开关各跑一遍 A/B"，多适配器那条仍未做。

**G. 诊断缺口**
- 没有线程名 ⇒ `thread_census.ps1` 只能按序号猜（此前实测启动后 127–136 个线程，未入库）；placement 也只有事件行，没有"当前 CPU 策略"快照（tier/CPU Set/优先级/解码线程数一次导出）。

## 四、建议（按性价比排序）

### P0 · 策略卫生（低风险，先做）
1. **删掉启动期 HIGH 默认**（docs/145）：保留 `FFF_NO_STARTUP_PRIORITY` 的反向语义（或改成显式 opt-in），宿主不再直接写 `PriorityClass`。附带收益：内核基线采样乱序缺陷从"真缺陷"降级为"不可能发生"。
2. **写明一条规则**：进程优先级只能由内核按测量升级，宿主只负责"启动/空闲"两个状态。落到代码注释 + 本文档，防止以后再出现第三个写者。
3. **补线程名**：UI、session worker、present、WASAPI、decoder 编排、prefetch worker/guard、cover backdrop、图层泵统一 `SetThreadDescription`。零行为变化，之后 thread_census 能按名对账。

### P1 · 先测再动（一次安静窗即可，20 轮交替）
4. **播放期 CPU Set 首个 A/B**：`FFF_PLACEMENT=off`（负控）vs 默认 on。这是整条 CPU 策略里"机制最强、账最空"的项；顺带用日志确认 AMD 分支在本机是否 `PLACEMENT_NONE`（本机 Intel，只验证 hybrid 分支）。
5. **启动期 CPU 放置 A/B**：`FFF_STARTUP_PLACEMENT=1` vs 关，与 4 同窗做。
6. **结论中性时的收敛**：启动期放置与 HIGH 一起"默认关 + 日志"，不再扩散；把"CPU 策略"收成诊断能力而不是默认行为。

### P2 · 常驻税（小但确定，稳态功耗/唤醒）
7. **KR-13**：三处 `Sleep(1)/Sleep(2)` 换成 `commandCondition_.wait_for`（先改一处），收益 0.3–1% 单核 + ~1000 次/s 上下文切换；验收要对齐 `pumpIterations_` 等按 tick 计的窗口口径。
8. **HS-7/ST-2**：暂停/最小化/图片静止/无播放时停 UI 计时器并释放 `timeBeginPeriod`；功耗项，不是吞吐项。
9. **计时器链合并**：媒体信息三条链（67/200/1000 ms）在窗口不可见时停；180 ms 布局 tick 改事件驱动；8 ms 图片缩放 tick 按显示节拍（docs/144 HS-6）。

### P3 · 结构与产品化（改动面大，需测量）
10. **线程预算两段化**：`P 线程数 + 允许 spill 的 E 线程数`；ladder ceiling 不再直接用 `hardware_concurrency−4`，hybrid 上让 spill 成为显式决策。
11. **预取侧车补预算**（docs/144 PF-1/PF-2/PF-9）：`thread_count=min(4,budget)` + `thread_type=SLICE` + worker `BELOW_NORMAL`；静图浏览时跳过 helper 死重；`PeekNamedPipe+Sleep(2)` 换阻塞读。这是默认 on 且真正抢 CPU 的项，优先级应高于"再加启动旋钮"。
12. **CPU 策略快照导出**：内核暴露一次可选导出（tier/CPU Set 数/进程 class/present 线程优先级/解码线程数），宿主设置页或诊断面板显示；以后所有 CPU 相关 A/B 都能自证当前状态。
13. **默认开项收敛**：多适配器回退、运行期预取、自适应解码线程各补一账（ST-11 / PF-1 / 9b82322），不达标就默认关。

### 不建议做的事（与既有判死对齐）
- 再加进程级 HIGH/ABOVE_NORMAL 默认值（docs/145 两次实测否定）。
- 硬亲和 `SetThreadAffinityMask` / 进程静态绑核（软亲和都还没有收益证据）。
- ServerGC / TieredPGO=0 / NativeAOT / 单文件压缩（docs/144 §五已判死）。
- 用优先级替代 I/O/GPU/DWM/vblank 等待（启动大头是同步等待，docs/145）。
- 在"启动期 CPU 时间/墙钟比 <30%"没有量出来之前，继续投入启动 CPU 放置产品化（docs/146 阶段 0 判据）。
- 音频线程未测 glitch 前不要加 MMCSS/最高优先级（可能引入新的优先级反转）。
