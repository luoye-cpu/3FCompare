# 148 · 整体软件链路与默认 CPU 策略盘点（2026-11-11）

> **状态：定稿**。两份并行只读静态审查（内核侧 / 宿主侧 CPU 策略）已回收，主 Agent 对其主张**逐条独立复核后**采纳或驳回（处置见 §〇）；§一/§二的线程清单与默认值矩阵按内核仓 `3fp/kernel` HEAD `49d1500` 逐条代码核验。所有「收益量级」仍是推断或既有 E1 记录，**本轮未跑任何测量**。
>
> **问题**：把 3FP 从「双击启动 → 打开 → 播放 → 空闲」的整条链路按层拆开，说清**默认设置**下每一层的 CPU 策略（进程优先级/线程优先级/CPU Set/线程数/唤醒节奏），并给建议。
>
> **结论（先看这 8 条）**：
> 1. **默认策略是「三套旋钮各管一段、互不通信」**：宿主启动期把整进程拉到 HIGH 再 1.5 s 后恢复；内核 `PlacementPolicy` 在播放开始后按拓扑给**整个进程**设软 CPU Set、压力下把进程抬到 ABOVE_NORMAL + session worker 抬到 HIGHEST；运行期预取又自己起线程/进程。进程 class 有三个写者，线程优先级另有一个来源（LakeUI `PrecisionTimer` 调度线程固定 `AboveNormal`），没有统一状态机。
> 2. **唯一「真 CPU 策略」（CPU Sets）至今零收益账**：播放期 tier0 从未用 `FFF_PLACEMENT=off` 做过 A/B；启动期放置（docs/147）默认关、同样未测。它还是**进程级**软亲和，会覆盖宿主 UI、计时器、预取线程。且被钉核/提权的是 **session worker**，不是执行 `Present` 的呈现线程（§〇 A1）。
> 3. **启动期 HIGH 是纯负担**：两次实测没有收益（docs/120 混合臂、docs/124 单独臂 Δ+4.4 ms/p=0.78；docs/145 复核），且埋了一个真缺陷——若「启动即播放」落在 `Shown+1500 ms` 之前，内核会把 HIGH 记成基线，之后 Boost 释放时恢复成 HIGH（docs/124 §4.1，本机未复现但代码路径成立）。
> 4. **默认开的「未量化项」在叠加**：多适配器解码回退默认 on（ST-11 未做 A/B）、运行期预取两条 lane 默认 on（helper 与进程内静图各有独立开关/条件）、自适应解码线程由**宿主显式打开**（内核 ABI 默认关）。出问题时无法归因到单一旋钮。
> 5. **预取侧车「绕过预算」属实，但草稿的收益论证被推翻**：侧车 `avcodec_alloc_context3` 后确实不设 `thread_count`/`thread_type`（`PrefetchService.cpp:221-231`），但 FFmpeg `AVCodecContext.thread_count` **默认是 1**（`options_table.h:216`），`av_cpu_count()` 只在显式 `threads=auto`/`thread_count=0` 时生效 ⇒ docs/144 PF-1 与草稿的「拉起约 20 个 worker、正压在开图动画上」**因果链不成立**。真实缺口是「侧车完全不受 `DecoderThreadBudget()` 约束 + worker 未降优先级」；实际线程数需 E1 复核，标 U。
> 6. **常驻税要按当前代码重数**：播放泵仍有 ≥12 处 `Sleep(1)/Sleep(2)`（含直通/光盘路径），但饱和背压已在 `PlayerSession.cpp:6436-6442` 改成 `commandCondition_.wait_for` ⇒ KR-13「三处忙轮询」口径过时；`timeBeginPeriod(1)` 有**两个持有者**（LakeUI 引用计数的空闲常驻份 + 内核播放期份）；**15 个计时器对象、默认持续跑 4 条**；`FFF3FP_UPLOAD_FORCE_*` 每帧读两次环境变量，而 `FFF_SEEK_PREVIEW` 已改为每次 seek 读一次。
> 7. **线程预算本身不看拓扑，但 ladder 与 CPU Set 已看**：`DecoderThreadBudget() = hardware_concurrency()−4`（本机 16，`PlayerSession.cpp:4798-4804`）；ladder 用 `PreferredDomainThreads()` 作物理边界（`:5095`），软解打开时 `EnsurePreferredCapacity(budget)` 会把 tier0 从 12 P 线程扩到 ≥16（`:3652`、`PlacementPolicy.cpp:274-294`）。⇒ 不能笼统说「完全不知道 P/E」，问题是**预算没有两段化**。
> 8. **建议**：先做 3 件「卫生」（删启动 HIGH、CPU Set 补 A/B、给原生线程补 `SetThreadDescription`），再收 3 处常驻税（短 Sleep、timeBeginPeriod、计时器 idle 全停），最后才谈产品化。**不建议**再加任何进程级默认旋钮，除非先有 A/B；PF-1 的优先级需按 §结论 5 重估。

## 三、结构性问题（按严重度）

**A. 优先级有三个写者，生命周期不对齐（最高风险）**
- 宿主只在启动期写进程 class（HIGH→恢复保存值），内核在播放期写（ABOVE_NORMAL/worker HIGHEST）并用**播放开始时的进程 class 当基线**（`PlacementPolicy.cpp:489-493`）。两者重叠时基线可能是 HIGH（docs/124 已判「真缺陷、边界未复现」）。
- 宿主恢复是**固定 1500 ms**，与真实打开时长无关；当前降回按保存值且有「仅当仍是 HIGH」守卫（`Form1.vb:617-620`），docs/124 的「600 ms 常量 NORMAL」是旧版事实。
- 内核 `Prioritize` overlay 常驻到 `Release()`：`ApplyTier` 降 tier 分支受 `if (!overlayPriority_)` 门控（`:606`），`Recover():640-645` 只降 tier、不碰 overlay ⇒ 「一次压力 = 整段会话 ABOVE_NORMAL」。
- 另有一层**线程优先级写者**：LakeUI `PrecisionTimer` 调度线程固定 `AboveNormal`（`PrecisionTimer.vb:339`），每个在跑的计时器一条。层级不同、不与进程 class 冲突，但对账时要分开数。

**B. 启动期 HIGH 已被实测否定**
- docs/120 混合臂 Δ−111.7 ms（归因未拆）；docs/124 单独臂 Δ+4.4 ms、U=92、p=0.783；docs/145 复核「建议删除或改事件驱动」。默认继续开着只有成本。

**C. CPU Set 是唯一「拓扑感知」的机制，却没验证过，且钉错了对象**
- 播放期 tier0 与 docs/147 启动期放置复用同一套发现逻辑，整套只有「设计正确性」审查，没有性能读数；软亲和会覆盖宿主所有未显式选择的线程。
- 被钉 tier0 / 提权的是 **session worker**，真正按 vblank 执行 `Present` 的 `TimedTextThread` **没有**被钉核或提权（A1）。⇒ 即便 A/B 证明 CPU Set 有效，也要先说清「钉的是谁」。

**D. 预算不分层，但 ladder 与 CPU Set 已分层**
- `DecoderThreadBudget() = hardware_concurrency()−4`（本机 16）不知道 P/E；但 ladder 用 `PreferredDomainThreads()` 阻止一步跨物理边界（`PlayerSession.cpp:5089-5097`），软解打开时 `EnsurePreferredCapacity(budget)` 把 tier0 扩到 ≥16（`:3652`）。⇒ 问题应表述为「预算应写成 `P 线程数 + 允许 spill 的 E 线程数` 两段」，**不是**「完全不感知拓扑」。

**E. 常驻税分散（按当前代码重数）**
- 播放泵 ≥12 处短 `Sleep(1)/Sleep(2)`（B2），但 `:6436-6442` 饱和背压已改 `wait_for` ⇒ KR-13「三处」口径过时；预取 worker/guard 是纯事件驱动，**不属于**轮询税。
- 每帧 2 次 `_dupenv_s`（`FFF3FP_UPLOAD_FORCE_*`，B6）；`FFF_SEEK_PREVIEW` 已改每次 seek 一次 ⇒ KR-8/KR-15「每帧/每包读环境变量」需分项目重述。**宿主 VB 侧无此盲区**：9 处 `Environment.GetEnvironmentVariable` 全在启动期/会话构造/模块探测，`FFF_CT_LOAD_TRACE` 是 `Private Shared ReadOnly` 类型初始化读一次（`播放器会话.vb:167`）；内核其余 5 个 `_dupenv_s`（`VideoRenderer.cpp:1559/1582/1602/1730/3058`）各有 `static` 缓存或按需调用。
- **两套** `timeBeginPeriod(1)`（A3）；15 个计时器对象、默认持续跑 4 条、三泵只降频不全停、无 idle 全停（§二·B）。docs/133:10 记录的三泵 `SpinWait` 常驻 51 ms/s 已修（8eaa472），不要重复立项。

**F. 默认开项缺少「出生账」**
- 多适配器回退、运行期预取（两条 lane 各有开关）、宿主显式打开的自适应解码线程叠加在同一窗口；docs/143 要求的「4 个默认开关各跑一遍 A/B」中多适配器仍未做。九旋钮里 4 项效力存疑（B8）也属同类。

**G. 诊断缺口**
- **C++ 原生线程无名**，VB/LakeUI 的 CLR 线程名对跨进程 `GetThreadDescription` 无效；`thread_census.ps1` 只能按模块/状态/CPU 时间粗分类（A11），docs/133:99 的按名归因工具已因权限 + 命名率 0 止损。启动后线程总量 127–136，docs/133:85 已判**线程池膨胀后回收、不是泄漏**，不要重新立项。
- placement 只有事件行，没有「当前 CPU 策略」快照；`thread_census.ps1` 未入库（A12）。

## 四、建议（按性价比排序）

### P0 · 策略卫生（低风险，先做）
1. **删掉启动期 HIGH 默认**（docs/145）：保留 `FFF_NO_STARTUP_PRIORITY` 的反向语义（或改显式 opt-in），宿主不再直接写 `PriorityClass`。附带收益：基线采样乱序缺陷降级为「不可能发生」。
2. **写明一条规则**：进程优先级只能由内核按测量升级，宿主只管「启动/空闲」两态；LakeUI 的线程级 `AboveNormal` 属另一层，规则里要点名区分。
3. **补线程名**：给 C++ 侧 session worker / `TimedTextThread` / WASAPI / 软解编排 / 预取 worker+guard / 扫描 / cover backdrop 统一 `SetThreadDescription`；宿主已有 CLR `Thread.Name` 的保持。零行为变化。

### P1 · 先测再动（一次安静窗，20 轮交替）
4. **播放期 CPU Set 首个 A/B**：`FFF_PLACEMENT=off` vs 默认 on；顺带用日志核对被钉的是 worker 还是呈现线程、tier0 是否被 `EnsurePreferredCapacity` 扩容。
5. **启动期 CPU 放置 A/B**：`FFF_STARTUP_PLACEMENT=1` vs 关，与 4 同窗做。
6. **结论中性时的收敛**：两项一起「默认关 + 日志」，把 CPU 策略收成诊断能力而非默认行为。

### P2 · 常驻税（按修正后的对象收）
7. **短 Sleep 统一**：先把剩余 ≥12 处按用途分组（背压、直通、光盘、预取），优先改仍每毫秒唤醒的；验收对齐 `pumpIterations_` 口径。**不要**再引用 KR-13 的「三处」和「0.3–1% 单核」旧量级。
8. **HS-7/ST-2（必须双侧同改）**：宿主侧在暂停/最小化/图片静止/无播放时停 **100 ms 界面呈现 + 三台 16 ms 图层泵**（补 `WindowState`/`Visible` 判断，三泵当前只降频）；**内核侧同步处理 `PresenterTimerResolution`** —— `TimedTextThread` 只在设备重建 / `ResetMedia` / `Close` 时停（`VideoRenderer.cpp:9540/9555/9640`），暂停态仍持有 `timeBeginPeriod(1)`。⇒ 单靠宿主停计时器**无法**让进程时基归零，草稿与上一版 P2 的写法不成立；空闲态该线程是否仍实际存活需 E1 确认（U）。
9. **环境变量与计时器链**：把 `ForceStagingUploadCached`/`ForceDynamicUploadCached` 改成真 `static` 缓存（B6）；媒体信息三条链与信息图层 200 ms **已按需启停，不必再改**；180 ms 布局已是单次 debounce，**删掉原「改事件驱动」项**；8 ms 图片缩放 tick 按显示节拍（HS-6）仍可做。

### P3 · 结构与产品化（改动面大，需测量）
10. **线程预算两段化**：`P 线程数 + 允许 spill 的 E 线程数`；ladder ceiling 不再直接用 `hardware_concurrency−4`。
11. **预取侧车补预算（优先级需重估）**：`PrefetchService.cpp:221-231` 显式给 `thread_count`/`thread_type`、`worker_` 降 `BELOW_NORMAL`；**但 PF-1 的「≈20 worker 抢 CPU」收益论证不成立（B1）**，先用 E1 量线程峰值与开图帧率，再决定相对其它项的优先级。`TakeProbe` 零消费者、静图浏览时 helper 白付 WARM/PROBE（docs/144 PF-2）与 `PeekNamedPipe+Sleep(2)` 换阻塞读（PF-9）不受此影响。
12. **CPU 策略快照导出**：内核暴露可选导出（tier/CPU Set 数/进程 class/**worker 线程**优先级/解码线程数/呈现线程是否已被钉），供以后所有 A/B 自证当前状态。
