> **背景**：docs/146 判定"启动期 CPU 放置（Intel P-core / AMD 同 L3 域）机制可行但收益待实测"。本轮按用户指令**只执行实现、暂不测试**（"系统比较繁忙，测试以后再说"）。

> - 内核 `FFF.Native` Release x64 与宿主 `FFF.Player` Release **编译通过**（内核 exit 0 无警告；宿主 0 警告 0 错误）；

## 一、实现内容

### 内核（FFF.Native）
| 改动 | 位置 | 说明 |
|---|---|---|
| 启动放置 API | `FFF.Native/3FP/Core/PlacementPolicy.h/.cpp` | 新增 `BeginProcessStartupPlacement()` / `EndProcessStartupPlacement(reason)` / `BuildStartupCpuSetIds()` + `groupCount_`；复用现有 `Discover()` 与域分组 |
| 域选择 | 同上 | **Intel**：`EfficiencyClass` 最高的组（P-core）；**AMD 多 CCD**：调用线程（host Startup 的 UI 线程）当前所在的 `LastLevelCacheIndex` 域（不猜"主 CCD"，只保 L3 局部性）；**多 processor group**：拒绝并记日志（CPU Set 跨 group 赋值会被 OS 忽略） |
| 施加范围 | 同上 | 只写**进程默认 CPU Set**（不写线程级选择）：旧线程与新线程都覆盖，且任意线程都能在 End 时清掉 |
| 与会话共存 | `PlacementPolicy::ApplyTier` | 会话一旦写进程默认集合，置 `g_sessionOwnsProcessDefaultCpuSets`；启动期 End 不会清掉会话的集合 |
| 负控一致 | 同上 | `FFF_PLACEMENT=off` 时启动放置同样不做（与播放期负控同一口径） |
| 首帧释放 | `FFF.Native/3FP/Core/PlayerSession.cpp` | `PresentVideoFrame` 的 `firstFrameForMedia && !seekPreview` 处分调 `EndProcessStartupPlacement("first-frame")`（幂等） |
| 新导出头 | `FFF.Native/3FP/Api/FFF.Player.CpuPlacement.h`（新增） | `FFF3FP_BeginStartupCpuPlacement() -> int`、`FFF3FP_EndStartupCpuPlacement()`；不抬 `PlayerApiVersion(20)`/`SnapshotVersion(23)`、不动 608 B 快照布局（与 prefetch/audio-tap 同纪律） |
| 导出实现 | `FFF.Native/3FP/Api/PlayerApi.cpp` | 两个薄包装，全部逻辑在 `PlacementPolicy` |
| 日志 | 同上 | `PLACEMENT_STARTUP begin kind=Hybrid\|CacheDomain ids=N groups=1`、`... end reason=first-frame\|host session-owned=0`、`skip reason=no-preferred-domain groups=N`、`fail api=SetProcessDefaultCpuSets`（走 `FFF3FP_KernelLogImpl`，另在 `FFF_PLACEMENT_TRACE` 之外也有） |

### 宿主（FFF.Player）
| 改动 | 位置 | 说明 |
|---|---|---|
| 启动钩子 | `ApplicationEvents.vb`（`MyApplication_Startup` 第一行） | **先查 `FFF_STARTUP_PLACEMENT=1`，再碰内核导出**——没开时绝不把 `FFF.Native` 提前加载，不污染所有人的启动时序；旧内核缺导出 ⇒ 静默不启用 |

## 二、开启方式

- **默认关**。要试用/A/B：`set FFF_STARTUP_PLACEMENT=1` 再启动 `FFF.Player.exe`。
- 受 `FFF_PLACEMENT` 约束：`FFF_PLACEMENT=off` 时启动放置也不做（负控一致）。
- 诊断：看内核日志里的 `PLACEMENT_STARTUP ...` 行；`FFF_PLACEMENT_TRACE=1` 下与播放期 `PLACEMENT transition=...` 行同流。

## 四、已知缺口与退路（都是实现阶段的取舍，不是新发现的 bug）

1. `FFF_STARTUP_PLACEMENT` 只在进程启动时读一次，运行期改无效果（与其它启动开关一致）。
2. 启动放置用**进程默认集合**，会覆盖所有未显式选择的线程（GC / 线程池 / 预取侧车 / 图层泵都在内）。这正是 docs/146 里"不要进程级"的争议点；如果 A/B 证明反效果，退路是改成只钉 UI + 内核 create 线程的**线程级**版本（`SetThreadSelectedCpuSets`）。
3. AMD 的"当前 L3 域"取调用线程在 `Begin` 时刻的 processor；若 Windows 在此之前已迁移过它，锁到的域是"此刻"的局部性最优而非"最初落点"——两者通常一致，但记录在案。
4. 多 group 机型（Threadripper 等）直接 no-op（日志 `groups=N`），未实现 group-aware 版本（docs/146 §四 的顾虑）。
5. 与启动期 HIGH 优先级**正交**；若后续按 docs/145 删除 HIGH，两者不耦合。
6. 没有做 `SetThreadIdealProcessorEx` 的轻量分支（docs/146 C0），当前只有 CPU Sets 一条路。
