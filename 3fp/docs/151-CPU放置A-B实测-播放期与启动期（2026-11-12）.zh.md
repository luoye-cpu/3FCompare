# 151 · CPU 放置两笔 A/B 实测：播放期 CPU Set 与启动期 CPU 放置（2026-11-12）

> **一句话结论**：按 docs/148 §四 P1 的口径做完了两笔首次 A/B（各 20 轮逐轮交替、臂顺序翻转、同轮配对检验）。**播放期 CPU Set 对用户可感知指标（呈现帧数/丢帧/呈现间隔）没有任何可测收益**；唯一的实读收益是**软件解码时进程 CPU 时间 −4.3%（配对 Δ −476.6 ms/6 s，Wilcoxon p=0.0005，MWU p=0.0002）**，而产品默认的硬件解码臂连 CPU 时间都完全一致（p=0.80）。**启动期 CPU 放置对 T2 无收益**（+33 ms，p=0.15，方向还略偏慢；另一次非交替复跑方向相反 −19 ms，p=0.20 ⇒ 差异在噪声内），CPU/墙钟比 −3.3%（p=0.077，不显著）。两份自证都成立：播放期被钉的是 **worker（12/16 个 CPU Set）**、**呈现线程 0 个显式集合**；启动期 on 臂 **22/22** 轮都在启动窗口持有 12 个进程默认 CPU Set，off 臂 0/22。**本轮零 commit / 零 push；未改任何产品默认值**（是否收敛成「默认关 + 日志」见 §五，等用户拍板）。

## 二、实验 1：播放期 CPU Set A/B —— 产品默认（硬件解码）

臂 A = `FFF_PLACEMENT=off`（负控，策略整体停用）；臂 B = 默认（CPU Set 生效）。两者同 exe、同媒体、同窗口；公共 env 另设 `FFF_PLACEMENT_TRACE=1`、`FFF3FP_PREFETCH=0`。20 轮 × 2 臂（+每臂 1 预热）。

| 指标 | A=off | B=默认 | 同轮配对 Δ 中位 | 变化 | Wilcoxon p |
|---|---|---|---|---|---|
| presented frames / 6 s | 359.00 | 359.00 | 0.00 | 0.0% | 0.32 |
| decoded frames | 362.00 | 362.00 | 0.00 | 0.0% | —（全相等） |
| dropped frames | 0（0 轮） | 0（0 轮） | — | — | — |
| 进程 CPU ms / 6 s | 765.62 | 765.62 | +15.62 | +2.0% | 0.77（MWU 0.80） |
| 呈现间隔 p50 ms | 16.62 | 16.66 | +0.03 | +0.2% | 0.099 |
| 呈现间隔 p99 ms | 19.63 | 19.64 | −0.10 | −0.5% | 0.43 |
| 呈现间隔 max ms | 21.08 | 21.27 | −0.38 | −1.8% | 0.73 |

**结论：完全中性。** 60 fps 满帧、0 丢帧、呈现节拍与 CPU 时间都在噪声内；连"CPU Set 会省 CPU"都测不出来。

**自证（P3-12 的验收场景，全部成立）**：
- A 臂：`tier=0 flags=0x3(DISABLED|AVAILABLE)`、`procdefault=0`、`workerSets=UNKNOWN`；内核账 `PLACEMENT_DISABLED reason=FFF_PLACEMENT=off`。
- B 臂：`tier=1(Preferred)`、`domain=1(Hybrid)`、`workerSets` 全 20 轮 `=12`（P-core 12 个逻辑处理器的 12 个 CPU Set）；**`presentSets=0` 全 20 轮** ⇒ 运行时实证了 docs/148 §〇 A1「被钉的是 session worker，不是执行 Present 的呈现线程」。
- 20/20 轮 B 臂都捕获到内核自己发的 `PLACEMENT_SNAPSHOT` 行（P3-12 的追踪行在真实播放路径上工作）。

## 三、实验 2：播放期 CPU Set A/B —— 软件解码敏感臂

同一素材加 `--decode cpu`（`--adaptive 1` 镜像产品配置：内核自适应解码线程=1、floor 4 / ceiling 32 / grow 10 / shrink 2）。这是"放置"理论上最该起作用的臂。

| 指标 | A=off | B=默认 | 同轮配对 Δ 中位 | 变化 | Wilcoxon p (MWU) |
|---|---|---|---|---|---|
| presented frames / 6 s | 355.00 | 355.00 | 0.00 | 0.0% | 1.00 (0.82) |
| decoded frames | 358.00 | 358.00 | 0.00 | 0.0% | 0.58 (0.92) |
| dropped frames | 0 | 0 | — | — | — |
| **进程 CPU ms / 6 s** | **10007.81** | **9578.12** | **−476.56** | **−4.8%** | **0.0005 (0.0002)** |
| 呈现间隔 p50 ms | 16.62 | 16.61 | −0.02 | −0.1% | 0.66 |
| 呈现间隔 p99 ms | 20.66 | 20.64 | −0.08 | −0.4% | 0.60 |

**结论：CPU 时间有真实且显著的节省（约 −4.3%~−4.8%，2/17 正负比），但吞吐/呈现/丢帧完全不变。** 也就是说：把软解线程拢到 P-core 上少烧了点 CPU，却没换来任何用户可感知的帧率或流畅度提升。

> 口径注：这里比的是"进程 CPU 秒数"。两臂解码线程数相同（4K 420 10-bit 走 `workers=min(logical,8)=8`，自适应阶梯在无饥饿时不下探，快照 `decoders=0` 是"阶梯尚未选档"的既有语义，不是 0 线程），所以差异来自**同一份工作落在哪类核上**——同样的解码在 E 核上要付更多周期。该读数对功耗/散热有意义，但不是"少做了工作"。

**自证**：B 臂 `workerSets=16`（20/20）——**tier0 被 `EnsurePreferredCapacity(DecoderThreadBudget()=16)` 从 12 个 P 核扩到 16 个**，直接回答了 docs/148 P1-4 的"tier0 是否被扩容"；`presentSets=0` 依旧（呈现线程未被钉）；20/20 轮有 `PLACEMENT_SNAPSHOT`。

## 四、实验 3：启动期 CPU 放置 A/B（GUI 冷启动 + 1080p 静图）

臂 A = 默认（启动放置关）；臂 B = `FFF_STARTUP_PLACEMENT=1`。`quiet_ab.ps1` 逐轮交替 + `-AltOrder`（偶数轮 B 先跑）+ 2 预热轮；T1/T2 口径沿用 `startup_image_time.ps1`（标题窗口 / 客户端像素内容），并新增 OS 侧自证与 CPU 时间列。

| 指标 | A=off | B=on | 同轮配对 Δ 中位 | 变化 | Wilcoxon p (MWU) |
|---|---|---|---|---|---|
| T1 标题窗口 ms | 930.1 | 963.9 | +31.65 | +3.4% | 0.123 (0.354) |
| T2 画面可见 ms | 1020.1 | 1049.4 | +33.25 | +3.3% | 0.147 (0.342) |
| CPU / 墙钟比 | 117.9% | 115.5% | −3.30 | −2.8% | 0.077 (0.146) |
| T2 时子进程 CPU ms | 1218.8 | 1250.0 | +0.00 | 0.0% | 0.88 |
| Process.Start ms | 85.0 | 84.8 | −0.20 | −0.2% | 0.82 |

**结论：T2 无收益，方向还略偏慢（+33 ms，p=0.15），CPU 占比小幅下降（p=0.077，不显著）。** 第一次（未开 `-AltOrder` 的早期跑）给出相反方向的 T2 Δ −18.8 ms（p=0.204）⇒ 两次同窗结论都落在噪声内，**没有证据支持启动期放置能缩短启动/开图**。

**自证**：on 臂 `StartupSetMax`（`GetProcessDefaultCpuSets` 在 OS 侧读数）**22/22 轮 = 12**；off 臂 0/22 ⇒ env→宿主→内核整条链路确实生效，本轮不是"注入失败读成无差异"。

**边界**：本轮 44/44 轮都是 `SpawnMs 60–700 ms`（"slow 档"，本机进程启动拦截），T2 ~1.0–1.3 s，明显慢于历史 600–900 ms；绝对读数受窗口负载影响大（中位 51.5%、峰值 100%）。配对设计保住了相对结论，但**若要为默认值决策，应在真正空闲的窗口复跑一次**。

## 五、结论与建议（产品默认值：本轮不改，等用户拍板）

1. **播放期 CPU Set**：对用户可感知指标 = **零收益**（硬解臂连 CPU 都无差；软解臂只有 CPU −4.3%）。与 docs/148「唯一真 CPU 策略（CPU Sets）至今零收益账」一致。若按 docs/148 P1-6 的"中性则收敛"，方向应是 **`FFF_PLACEMENT` 默认关 + 保留诊断/强制臂**（`FFF_PLACEMENT=prefer|spill|boost` 与 trace 仍在），把 CPU 策略收成诊断能力而不是默认行为。
2. **启动期 CPU 放置**：已默认关（docs/147），本轮也没有测出 T2 收益 ⇒ **维持默认关**，仅保留 `FFF_STARTUP_PLACEMENT=1` 作诊断/实验开关。
3. **我没有改任何默认值**：默认值变更属于产品口径，需要用户明确点头（红线：不给 A/B/C 菜单推决策）。若要落实第 1 条，是一处小改动 + 更新 docs/150/本节。
4. 如果用户更看重"软解时省 4.3% CPU"，也可以保留默认开；本轮数据支持"可见体验不变、CPU 略省"两种表述，取舍是产品决策。

## 八、证据分级与 U

- **E1**（本轮实机）：§二~§四 全部数字（同窗、逐轮交替、同轮配对；负载已逐轮记录）。
- **E2**（代码/OS 可核验）：§二/§三 的 `tier/flags/workerSets/presentSets` 来自内核 `FFF3FP_GetCpuPlacementSnapshot`（P3-12）；§四 的 `StartupSetMax` 来自 `GetProcessDefaultCpuSets`；`PLACEMENT_SNAPSHOT` 20/20 来自内核日志槽。
