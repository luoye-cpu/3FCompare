## 四、`avdevice-63.dll` 判断

### 结论：**不拷入**（不入 `runtime/`，也不入任何镜像）

### 理由（三类独立证据，同向）

1. **[VERIFIED·高] 内核不引用它。**
   对 `FFF.Native.dll`（`3fp/build/` 现役版）做二进制字符串搜索：
   `avcodec-63=True`、`avformat-63=True`、`avutil-61=True`、`avfilter-12=True`、
   `swscale-10=True`、`swresample-7=True`，而 **`avdevice-63=False`**。
   对 `3fp/kernel/FFF.Native/x64/Release/FFF.Native.dll` 及 `3fp/build/` 下
   21 个历史 `FFF.Native*.dll` 变体**全部** `avdevice_ref=False`。

2. **[VERIFIED·高] 源码面零引用。**
   全仓库 `*.cs / *.cpp / *.h / *.vcxproj / *.csproj / *.props / *.targets` 搜 `avdevice`，
   命中的**全部**是 FFmpeg SDK 头文件里的**注释与前置声明**
   （`libavformat/demux.h`、`mux.h` 的 `AVDeviceInfoList` 前置声明，`libavutil/avutil.h` 的文档注释）。
   **没有任何一处** `LoadLibrary`/`DllImport`/链接项指向 `avdevice-63.dll`。

3. **[VERIFIED·高] 谁在用它 —— 是 `ffmpeg.exe`，不是我们。**
   `publish/PLAN/ffmpeg-full/ffmpeg.exe` 确实引用 `avdevice-63`（True），
   因为 ffmpeg 命令行工具支持 `dshow`/`gdigrab` 等采集设备。
   **但 `ffmpeg.exe` 不在本项目的运行时依赖里**（内核走 `FFF.Native.dll` + C API，不 shell out）。
   这也解释了「publish 比 runtime 多一个 `avdevice-63.dll`」的由来：
   它是**命令行工具集**的伴生件，不是**库运行时**的必需件。

4. **[VERIFIED·中] 现役 `runtime/` 本来就没有它，且工作正常。**
   `runtime/`、`3fp/build/`、`3fp/kernel/runtime/`、`3fp/publish/Release-win-x64/`
   四处 `avdevice_present=False`，而 `docs/64` 记录的 4/5 JXR 成功正是**没有它**的情况下取得的。

### 风险与反悔成本

- 不加的代价：**零**。无任何加载路径会找它。
- 若将来要加（例如引入采集设备功能）：单文件 112,128 字节，从
  `publish/PLAN/ffmpeg-full/avdevice-63.dll`（`9E80C116F5ED62B5`）直接拷入即可，**成本可忽略**。
- ⇒ 遵循「**最小改动面**」原则：不在本任务中扩大运行时文件集。
