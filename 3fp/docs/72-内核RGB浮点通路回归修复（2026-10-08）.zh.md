layout 3 走 `:5338 UpdateSubresource(..., uploadPlanes[0], uploadLines[0], 0)`，

### 2.5 方法学教训

1. **诊断必须解释症状的"精确形状"。** 症状是"**恰好只剩 R 通道**"——这是"**格式被当成单通道**"的独有特征。
   Lead 的诊断解释了"数据会错"，却**没解释为何恰好是一个通道**，这正是漏掉 `:4037` 的信号。
2. **"症状消失了" ≠ "我修对了"。** Lead 改了两处后 G/B 确实恢复，但那是因为
   `:4037` 已由 vivid-impl 同时修好 —— **修复被"搭便车"归因**。只有**逐处受控变异**能区分必要与冗余。
3. **对抗复核的价值正在于此**：它没有接受"症状消失"，而是逐处还原给出判定。

### 2.6 保留 Lead 改动的理由（归因上非修复，工程上是加固）

Lead 的两处改动**予以保留**：
- `directYuv` 显式排除 layout 3 —— layout 3 不是平面 YUV 是**事实**，应显式表达；
- `floatRgb` 分支把"浮点逐字节上传"写成**显式意图**，不再依赖 `uploadPlanes` 初值的隐式巧合；
- 若将来 `uploadPlanes` 初值语义变化（如自适应缩放路径），显式分支更不易被破坏。

> ⇒ **归因上承认它们不是修复；工程上保留它们作为显式化加固。** 二者不矛盾。

### 3.0 唯一真修复：`:4037`（vivid-impl）
```cpp
// layout 3 is interleaved half-float RGBA: it has the same channel count as
// layout 0, so it must use the same 4-channel float format. Without this the
// `else` arm below degrades it to R16_FLOAT and only the red channel survives.
const auto format = layout == 0 || layout == 3 ? DXGI_FORMAT_R16G16B16A16_FLOAT :
    (layout == 2 && plane == 1 ? DXGI_FORMAT_R16G16B16_FLOAT :
        DXGI_FORMAT_R16_FLOAT);
```

### 3.1 等价改写一：`directYuv` 排除 layout 3（Lead，保留作加固）
```cpp
// Layout 3 is interleaved half-float RGBA (JPEG XR's rgbaf16le): like layout 0 it
// is sampled directly as RGB, so it must NOT take the planar/semi-planar upload
// path. Unlike layout 0 it needs no CPU conversion at all -- the decoded buffer is
// already half-float, which is bit-compatible with DXGI_FORMAT_R16G16B16A16_FLOAT,
// so sws_scale would only re-quantise it into an integer range that cannot hold the
// negatives and super-whites float RGB legitimately carries (see docs/65, docs/70).
const auto floatRgb = input.layout == 3;
const auto directYuv = input.layout != 0 && !floatRgb;
if (!directYuv && !floatRgb) {
```

### 3.2 等价改写二：浮点上传分支（Lead，保留作加固）
```cpp
} else if (floatRgb) {
    // Half-float RGBA is interleaved, one plane, 8 bytes per pixel -- the same
    // shape as the RGBA64LE path below, so it reuses the same single-plane upload.
    // The bytes are copied verbatim: no quantisation, so components outside [0,1]
    // survive into the FP16 texture.
    context_->UpdateSubresource(sourceTextures_[0], 0, nullptr, frame->data[0],
        frame->linesize[0], 0);
}
```

### 3.3 `planeCount` 无需改动（该"缺陷"从未存在）
`:5286` 的守卫是 `input.layout == 1 || input.layout == 2` —— `directYuv` 修正后 layout 3 自然不进入该分支。
（**二次确认**：仅修 `directYuv` 不足以修好，因为上传点是独立的 `else` 分支；两者都要改。）

## 五、改动 4（transfer/gamut 语义）—— **已由 Lead 实施**

### 5.1 为什么必须做（问题定位）

数据虽然**正确送达**且是真浮点，但**语义仍错**，Lead 定位：

1. JXR 帧 `color_trc = UNSPECIFIED` ⇒ `frameDeclaresTrc == false`（`VideoRenderer.cpp` 的 transfer 判定处）
2. ⇒ `settings.transfer` 落回 `hdrState.format == Sdr ? 0 : ...` ⇒ **transfer = 0**
3. ⇒ 着色器执行 `ToLinear709(rgb)`，即 `LinearOne(v)`：
   ```hlsl
   float LinearOne(float v) { v=saturate(v); return v<0.081 ? v/4.5 : pow((v+0.099)/1.099,1.0/0.45); }
   ```
4. **但 `docs/70` 已用一手证据确立：`rgbaf16le` 是 scRGB 线性光**（`JXRGlue.h:136`「scRGB formats. Gamma is 1.0」）：
   - **曲线错**：对已线性数据再做 **sRGB→线性解码**
   - **钳位回潮**：`saturate(v)` **把刚保留的负值与超白又夹掉**

⇒ **V1（饱和→0）与 V2（负值/超白存活）在改动 4 落地前不可能通过。**

### 5.2 改动 4 的实现（Lead）

**着色器侧**：新增 `Transfer==3` = "已是线性，不要解码"，插在 `ColorMode==0&&Transfer==0` 分支**之前**：
```hlsl
if(Transfer==3){
    float3 alreadyLinear=rgb;
    if(ColorMode==0){
        if(Gamut==1)alreadyLinear=ToBt709(To709(alreadyLinear));
        // No saturate() here on purpose: an SDR swap chain cannot represent >1.0 or
        // <0.0 anyway, and clamping here would silently destroy the wide-range data
        // this path exists to preserve. Let the 8-bit surface's own conversion do it.
        return float4(alreadyLinear,1);
    }
}
```
且 `nits` 选择改为：
```hlsl
float3 nits=Transfer==1?PqToNits(rgb):(Transfer==2?HlgToNits(rgb):(Transfer==3?rgb:ToLinear709(rgb)*PaperWhite));
```

**宿主侧**（keyed on 像素格式，**不是**值域启发式）：
```cpp
if (floatRgb) { settings.transfer = 3u; settings.gamut = 0u; }
```

### 5.3 实施中修正的两个自身缺陷
1. **`linear` 是 HLSL 保留字** ⇒ 首次编译 `error X3000: unexpected token 'linear'`；改名 `alreadyLinear` 后通过。
2. **`settings.gamut = 0u` 曾是死写**（vivid-impl 指出）：原放在 `settings.gamut = gamut;` **之前**，
   被后者无条件覆盖 ⇒ 已把 `if (floatRgb)` 整块**移到其后**，现真正生效。
3. **`saturate()` 移除**（vivid-impl 建议）：`ColorMode==0` 分支原带 `saturate()`，
   会把本任务要保留的负值/超白夹掉。~~该分支当前**不可达**（JXR 实测走 `ColorMode==2`）~~
   但作为 8-bit/强制 SDR 的未来路径，已移除并由注释说明理由。
