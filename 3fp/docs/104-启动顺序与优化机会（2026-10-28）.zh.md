## 二、本轮新增实测

1. **带窗 Create ≈ 398 ms**（新数据）：`image_load_probe.cpp` 加 Create 计时后 n=7，**中位 398.4 ms（385.6–459.2）**——Create 传真窗口时内核同步建全套渲染管线；而宿主 headless 创建+后绑窗的整段 T1→T2 才 89 ms ⇒ 宿主现路径已避开这 400 ms。该数字同时是内核侧「Create 急切初始化可懒化」的直接证据（对 API 使用者有益，上游 PR 素材）。
2. **headless 完成语义缺口**：探针 `--headless`（无窗，模拟更早的并行打开）等待 `OpenCompleted` **40 s+ 未触发**（带窗 ~86 ms）；宿主能跑通是因为它不等待该事件、由绑窗/呈现驱动完成链。⇒ **「解码先于窗口」的重叠设计在 main 上缺内核前提**，`task/image-open-perf` 分支保留的 `2867d8a`（无窗打开→绑窗链路修复）正是这一族工作。这是并行化方案 O5 的硬前提。
3. **LakeUI Debug 产物 = JIT 关优化（实锤）**：宿主 `FFF.Player.vbproj:241-245` HintPath 钉死 `..\..\LakeUI\LakeUI\bin\Debug\...`，本机 LakeUI 只有 Debug 产物（bin 下无 Release）；读元数据 `DebuggableAttribute = 263`（含 **DisableOptimizations**）⇒ **整个 UI 框架的托管代码 JIT 无优化**（对照 `FFF.Player.dll` = 2，正常优化）。
4. **A/B（重载窗口，结论受限）**：
   - LakeUI Release 换入（10 v 10）：T2 中位 2092.9 → 2035.9（**−57 ms**），Mann-Whitney **U=51/100** ⇒ 本机噪声下不可判定，方向有利；需安静机器 ≥20 轮（见 §六）。
   - R2R 发布（7 v 7）：快四分位 1593–1680 vs 基线 1641–1743（**−60~90 ms**），中位不可判；docs/17 干净窗口已证 **−141.4 ms（11/11 胜）**——方向一致。
   - 换入/换回核验：LakeUI.dll 还原后哈希与原件一致（`DA156AA5…`）✓。

## 四、JIT 专题结论

- .NET 10 运行时默认（TieredCompilation + TieredPGO + QuickJitForLoops）已是合理默认，**宿主无需动运行时开关**。
- 可做的 JIT 项就是两件：**R2R（O1）**——把 ETW 里 ~1.25 s 的三段托管 JIT gap 压掉热路径部分；**LakeUI MinOpts 修复（O2）**——本轮唯一的"代码正确性级"JIT 发现（Debug IL 让整个 UI 框架跑在无优化 JIT 下，比 R2R 更基本）。
- R2R 不能全消 JIT：冷路径/跨程序集泛型仍会现编译；docs/17 的 −141 ms 是实测上限参考而非理论上限。
- 注意 R2R 会把**当前 Debug 的 LakeUI IL** 一起预编译（MinOpts 原生码）——O1 与 O2 独立有效，叠加时先 O2 后 O1 才能拿到优化 IL 的 R2R。

## 七、陷阱追加（本轮新踩）

1. **`Sleep(1)` 受 15.6 ms 定时器分辨率影响**：探针事件等待循环每至多 30000×15.6 ms ≈ 8 分钟——headless 判定用短超时会得出假"无事件"结论；正确做法是等待前先 spin（`Sleep(0)`/`Yield`）或用可等待计时器。（本轮 headless 40 s 强杀的结论已按此保守表述。）
2. **Mann-Whitney U 在满载噪声下对 <100 ms 效应无判定力**（10 v 10 的 U=51/100）——docs/57 的"重载环境绝对值仅横向可比"警示继续有效。
3. **publish 臂与 bin 臂的 FFmpeg 不同源**（publish 走 `..\runtime\` 的 DevelopmentRuntime，bin 用手工拷的 3fp/build 套件，avcodec 75.06 vs 76.62 MB）——跨臂对比前必须统一 DLL 集（本轮已先换齐再测）。
4. `printf("%s", L"...")` 宽窄不匹配 MSVC 会给 C4471 note，用 `%ls` 或窄串。

## 九、R2R 体积账（2026-10-29 补测：R2R 比纯 IL 大多少）

同源四份发布对比（framework-dependent、非单文件；`pub_il`/`pub_r2r` = Debug-LakeUI 输入，`pub_il_rel`/`pub_r2r_rel` = LakeUI-Release 输入；脚本 `r2r_size.py`）：

| 程序集 | 纯 IL | R2R | 增量 | 倍率 |
|---|---:|---:|---:|---:|
| LakeUI.dll | 2,375,168 | 5,345,280 | **+2,970,112** | 2.25× |
| FFF.Player.dll | 1,084,928 | 2,338,816 | +1,253,888 | 2.16× |
| Svg.dll | 705,536 | 1,769,472 | +1,063,936 | 2.51× |
| ExCSS.dll | 344,064 | 1,085,440 | +741,376 | 3.15× |
| Vortice.Direct2D1.dll | 535,040 | 1,327,104 | +792,064 | 2.48× |
| 其余 Vortice/SharpGen 7 件 | 1,215,864 | 2,495,744 | +1,279,880 | ~2.05× |
| **托管合计** | **6,297,600** | **14,159,872** | **+7,862,272（+125%）** | **2.25×** |

要点：
1. **R2R 只长在托管面：净增 ≈ +7.9 MB（2.25×）；LakeUI 一件就占 +3.0 MB。** 原生件（FFmpeg/libass/FFF.Native）零影响（avcodec 逐字节一致校验通过）；apphost exe 不变。
2. ~~`Microsoft.Windows.SDK.NET.dll`（27.2 MB，最大托管件）零增量——它随包分发时已内置 R2R 代码~~ **更正（2026-10-29，docs/105 §六）**：该 dll 为**纯 IL**（RTR 魔数扫描阴性），R2R publish 时 crossgen2 根本未编译它（四目录零增量）；且整个交付面无任何托管件引用它（docs/105 §六实测）——它在本轮所有口径里都是死重。
3. **R2R 尺寸与输入 IL 的 Debug/Release 无关**：Debug-IL 与 Release-IL 输入的 R2R LakeUI 尺寸逐字节同大（5,345,280）——crossgen2 用自己的代码生成策略，不吃 `DebuggableAttribute`。⇒ 先做 O2（LakeUI Release）**不会**让 R2R 更小（IL 6.30→5.99 MB，R2R 恒为 14.16 MB），O2 的体积收益只在纯 IL 口径存在；O2 的价值在运行时 MinOpts 修复与稳态性能，不在 R2R 体积。
4. 整个发布目录总账：150.47 MB → 158.34 MB（+7.9 MB，≈5%）；与 docs/17 单文件口径 +7.5 MB 交叉一致（单文件差值即托管面 R2R 增量）。
5. 若另开 `PublishReadyToRunEmitSymbols`（vbproj 注释里有）还会更大——docs/17 当时因与 `-p:DebugType=None` 冲突未开，体积上默认不开是对的。

## 十、单 EXE 实机交付体积账（2026-10-29 补测）

上游发布事实（GitHub Releases 实查）：`2026.10.28 V2`（commit `021ee4e`）资产 = **FFF.Player.exe 38.1 MB（单文件、框架依赖、不含 FFmpeg 六件套）** + FFF.Recorder.exe 35.8 MB。

| 交付变体（同源发布） | 体积 | 相对纯 IL |
|---|---:|---|
| sf_il（单文件纯 IL，本地复现） | 34,488,845 B（32.9 MB） | — |
| **sf_r2r（单文件 R2R）** | **42,325,005 B（40.4 MB）** | **+7,836,160 B（+7.84 MB，+22.7%）** |
| 上游 38.1 MB 同款 + R2R | ≈ **46 MB**（38.1 + 7.84） | — |

结论与事实：
1. **单文件口径的 R2R 增量 = +7.84 MB**，与散装口径 +7.86 MB 一致（增量就是托管面 R2R，与捆包方式无关）⇒ 上游若发 R2R 版，38.1 → ≈46 MB。
2. **压缩降体积对上游交付形态不可行（NETSDK1176 实证）**：`EnableCompressionInSingleFile` 仅自包含支持；自包含要捆整个 .NET 运行时反而大几十 MB，而自包含+trimming 因 WinForms 不支持走不通。
3. 包内构成（估算）：FFmpeg 六件套不在包内（用户侧放置，~110 MB 另算）；`Microsoft.Windows.SDK.NET.dll` 27.2 MB 自带 R2R（两种臂均引用到）；FFF.Native（5.6 MB）+ libass 族（~5.5 MB）作为原生件捆入（首跑解压到 %TEMP%\.net，已被预热轮吸收）。上游 38.1 与本地 32.9 的 5.2 MB 差是组件版本演进（LakeUI/SDK.NET 等），未逐件解析，不下断言。
4. ~~启动 spot-check~~ **作废更正（2026-10-29）**：事后发现本地 SDK 11-rc2 发布的 sf 单文件**未捆绑原生库**（详proof见 §十一.3），两臂的 T2 实为「FFF.Native 缺失错误框」（TitleAtT2 恒为 FFF.Player、进程模块表无 FFF.Native），不能与散装全路径比较；此前写的「单文件比散装快 ~400 ms」**作废**。R2R 体积差（+7,836,160 B）不受影响（两臂同为同一形态）。docs/17 干净窗口的单文件 R2R 收益仍是 −74.1 ms（缺 FFmpeg 早退路径）。
5. **降体积总结**：38.1 MB 框架依赖单 EXE 已接近该形态下限——结构性大刀（NativeAOT / trimming / 压缩）全部不可行或不适用；可行小刀只有发布侧排除 pdb/XML 伴随件（<0.5 MB）。若上游接受 R2R，+7.9 MB 是干净、可预期的代价。

## 十一、单 EXE「运行后吐 DLL」机制分析（2026-10-29）

用户观察：上游单 EXE 运行后会在磁盘上吐出部分 DLL。定性 + 判定如下（全部实测证据）。

### 11.1 机制事实

- **上游 38.1 MB exe 捆绑了 15 件原生库**（下载官方 `2026.10.28 V2` 资产，sha256 与发布页逐字符一致后二进制扫描）：FFF.Native.dll（上游内核 1.02 MB，非 3FC 侧 5.6 MB 构建）+ libass 全家（ass-9/freetype/harfbuzz/fribidi/brotli×2/bz2/z/libpng/iconv/charset/libxml2）+ bluray-3/udfread，合计 ≈6.3 MB。FFmpeg 六件套**不在包内**（用户侧放置）。
- **运行时 .NET 单文件宿主把它们解压到 `%TEMP%\.net\FFF.Player\<bundle-hash>\`**：本机留有 2026-10-24 的同构解压集（15 件逐件对应）；本次运行上游 exe 时 apphost 也直接走了解压代码路径（`Failed to create directory ...\FFF.Player\c3f4, Error code: 5`，见下）。「吐 DLL」= 这个标准解压机制。
- **为什么必须吐**：Windows 无法从 bundle 内直接 `LoadLibrary` 原生 DLL（导入表/TLS 需真实文件路径）；.NET 单文件只对托管程序集做内存加载，原生库落盘是官方标准行为，目录按 bundle hash 命名（同版本复用、升级换目录）。
- **内核侧加载姿势正确（能工作的原因）**：`FfmpegRuntime.cpp:54,90` 用 `GetModuleFileNameW(自身模块)` + `LoadLibraryExW(…, LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS)` 双锚点——同时覆盖「解压目录（自身所在）」与「exe 目录（FFmpeg 用户侧放置）」；FFmpeg 探测/加载不依赖 PATH。

### 11.2 判定：机制正确，但有四个真实代价/风险

1. **首跑解压 + AV/MotW 摩擦（本轮实测复现）**：刚下载（带 Mark-of-the-Web）的上游 exe 首次启动直接**解压失败退出**（`Error code: 5`），`Unblock-File` 后不再复现；手动在同一位置建目录则成功。即：%TEMP% 写可执行 DLL 是 AV/策略高敏行为，真实用户可能偶发「启动即闪退」。
2. **版本残留**：每个版本一个 hash 目录（≈6.3 MB），旧目录残留到 temp 清理（本机已现一例）。
3. **🔴 SDK 版本敏感性（上游级发现，与 .NET 11 迁移直接相关）**：同一份 vbproj——上游（SDK 10）publish 出捆原生库的单文件；本机 SDK **11.0.100-rc.2** 默认 publish 出的单文件**不含任何原生库**（二进制扫描 ass-9/harfbuzz 0 命中，只剩 deps.json 引用串），交付即「FFF.Native 缺失」错误框；显式 `-p:IncludeNativeLibrariesForSelfExtract=true` 后恢复捆绑（43.5 MB，命中模式与上游 exe 完全一致）。⇒ **上游升 SDK 11 时若不在发布路径钉死该参数，单文件交付会静默变砖**。建议做成发布自检（解包校验 FFF.Native+libass 闭包，形如现有 VerifyPlayerApiVersion target）。
4. **FFmpeg 二阶依赖闭包无校验**：内核对六件套有探测，但 libplacebo→libshaderc 这类二阶依赖曾实证落到 PATH 命中（docs/103 的 `C:\PLAN\FFmpeg\libshaderc_shared.dll`）；干净机器上 avfilter 加载会失败且报因模糊。

### 11.3 结论与建议

**机制本身正确且标准**（.NET 官方行为、hash 缓存自洽、内核双锚点加载姿势正确；FFmpeg 不捆是体积+非 free 再分发的合理取舍）。建议上游：① 发布门禁加单文件 bundle 自检（防 SDK 11 行为变化，见 11.2.3）；② 文档化 `DOTNET_BUNDLE_EXTRACT_BASE_DIR`（企业/清理敏感场景可指到稳定目录）；③ FFmpeg 依赖闭包探测补二阶依赖与明确报错；④ 散装形态保留为官方备选。

本轮证据：`upstream_FFF.Player_2026.10.28V2.exe`（sha256 校验通过）、`sf_il_incl\`（显式 flag 对照发布）、`sf_up\`（上游 exe 运行试验目录）；扫描命令与计数见 §八 目录内 `r2r_size.py` 同级（本轮为 rg 静态扫描，无新增脚本）。
