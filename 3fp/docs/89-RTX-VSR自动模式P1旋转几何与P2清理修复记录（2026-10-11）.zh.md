## 2. P1：VSR 不感知视图旋转

### 2.1 根因

`DrawCachedVideo` 里，旋转奇数圈（90/270°）时**只交换了适配盒的轴长**：

```cpp
// VideoRenderer.cpp（改动前）
const auto swapAxes = (rotation & 1u) != 0;
const auto layoutWidth  = swapAxes ? sourceHeight_ : sourceWidth_;
const auto layoutHeight = swapAxes ? sourceWidth_  : sourceHeight_;
destination = CalculateVideoDestination(..., layoutWidth, layoutHeight, ...);
...
if (ApplySuperResolution(destination.width, destination.height) == Success ...) { ... }
```

于是传到 `ApplySuperResolution` 的 `targetWidth/targetHeight` 是**视图坐标轴**下的目的盒（竖构图）。而函数内部：

- 「是否在放大」的门比较的是 `targetWidth/targetHeight` 与**未旋转**的 `sourceWidth_/sourceHeight_`；
- VP 的输入几何用未旋转的 `sourceWidth_/sourceHeight_`，输出面尺寸却由这个视图目的盒决定。

两项都拿视图轴去比画面轴，旋转 90° 时会把一个**本来在缩小**的画面判成「在放大」，让 NVIDIA VSR 以错误的宽高比上采样，最终被着色器再旋转后表现为约 `(h/w)²` 的拉伸。`docs/88` P1 条目（证据行 `5893-5896`→`5956`、`3326-3327`）即指此。

### 2.2 改法：把目的盒换算回画面自身坐标轴

新增一个 `constexpr` 转换与判定（`VideoRenderer.cpp:3218-3240`），运行门与断言共用同一实现：

```cpp
struct SourceAxisTarget { std::uint32_t width; std::uint32_t height; };

constexpr SourceAxisTarget ToSourceAxisTarget(std::uint32_t targetWidth,
    std::uint32_t targetHeight, std::uint32_t rotation) noexcept {
    return (rotation & 1u) != 0
        ? SourceAxisTarget{ targetHeight, targetWidth }   // 90/270°：交换
        : SourceAxisTarget{ targetWidth,  targetHeight };  // 0/180°：不变
}
constexpr bool IsUpscaleTarget(std::uint32_t sourceWidth, std::uint32_t sourceHeight,
    SourceAxisTarget target) noexcept {
    return target.width > sourceWidth || target.height > sourceHeight;
}
```

运行路径（`VideoRenderer.cpp:3318-3331`）：

```cpp
const auto rotation = viewRotation_.load(std::memory_order_acquire);
const auto targetSource = ToSourceAxisTarget(targetWidth, targetHeight, rotation);
if (!IsUpscaleTarget(sourceWidth_, sourceHeight_, targetSource)) return skip(NotUpscaling);
...
const auto surfaceWidth  = (targetSource.width  + 1u) & ~1u;   // 偶数化的是画面轴尺寸
const auto surfaceHeight = (targetSource.height + 1u) & ~1u;
```

VP 的 `InputWidth/InputHeight` 仍是 `sourceWidth_/sourceHeight_`（未变），`OutputWidth/OutputHeight` 现在等于画面轴下的偶数面 —— 因为 `surfaceWidth/Height` 已由 `targetSource` 得出。

### 2.3 为什么不再动 `PrepareScaledVideo`

`PrepareScaledVideo` 在 VSR `active` 时把 `outputWidth/Height` 当作「已等于目标」的平面尺寸（`4031-4032`），据此算出的 `targetWidth = min(planeWidth, outputWidth)` **恒等于** `planeWidth` ⇒ 该平面**零次缩放 pass**，原样返回 `superResolutionViews_`。既然零 pass，这里面尺寸数字只用于建一张不会跑的临时链，不参与成像。着色器对采样纹理做的是**归一化 uv** 采样，真正决定成像的是 §2.4 的旋转采样坐标，与面尺寸无关。

> 待复核的边角：`docs/88` P2「奇数目的盒取偶后 `(w+1)/w` 轻度拉伸」仍在（见 §5）。

### 2.4 旋转方向的依据（着色器源码实读）

`docs/88` 把此点列为「实机无法验证」的阻断项。本次把内嵌的像素着色器源码逐行读了出来（`VideoRenderer.cpp:718-732` 的 HLSL 字符串，非仅有字节码）：

```hlsl
float2 sampleUv = uv;
if (ViewRotation > 0.5) {
    if (ViewRotation < 1.5)      sampleUv = float2(1.0-uv.y, uv.x);      // 90 cw
    else if (ViewRotation < 2.5) sampleUv = float2(1.0-uv.x, 1.0-uv.y);  // 180
    else                         sampleUv = float2(uv.y, 1.0-uv.x);      // 270 cw
}
```

**旋转只作用在采样坐标上，不改目的矩形、也不改纹理的宽高比解释。** 由此推出：向 VP 提供的上采样面只要落在**画面自身轴**上，着色器旋转采样后就是正确的；这正是 §2.2 的做法。⇒ 阻断解除，`(a) 旋转感知` 方案成立且**比** `docs/88` 备选的 `(b) 奇数圈直接跳过 VSR` 更好（保留了旋转视图下的 VSR）。

## 3. P2 清理

### 3.1 死双门：`ShouldEnableNvidiaSuperResolution`

`docs/88` P2：该函数**全仓零调用者**，是 `ApplySuperResolution` 内联门的漂移副本（两套判定已不同步）。处理：**删除**（`.h:369-372` 声明、`.cpp:3160-3175` 定义），不改成「让 `ApplySuperResolution` 调它」——因为内联门要用 `skip(reason)` 携带**具体原因**，而该函数只返回 `bool`，无法承载原因。删除后删除漂移风险最小，且树内无引用（`grep ShouldEnableNvidiaSuperResolution` = 0）。

### 3.2 `skip()` 无日志

`docs/88` P2：`skip()` 只写状态不写日志，静默失效不可见（典型：自适应降采样后源纹理无 `D3D11_BIND_DECODER`，静默拒绝）。处理：`skip()` 内补一行进程日志，并按**状态变迁去重**（新增 `std::atomic<std::uint32_t> videoSuperResolutionLoggedReason_`，哨兵 `0xFFFFFFFF`），避免稳态每帧刷屏；成功路径复位该标记，使「跳过→成功→再跳过」仍会重新记录。

> ⚠ **刻意记下的一处可见副作用**：`Off`（默认）时第一帧会新增**一行** `FFF.Native: RTX Super Resolution skipped: not requested`。它不进渲染、不改像素，但属宿主可见的新日志，故明写于此。若要绝对零日志，可在 `NotRequested` 分支不记（未做，因为「为什么没生效」正是这条 P2 要解决的）。

新增原因文案函数 `VideoSuperResolutionReasonText`（`VideoRenderer.cpp:3163`）。

### 3.3 闩锁语义：注释与实现对齐

`docs/88` P2：`Set(Auto)` 清闩锁（`6610-6611`）与注释「latch off permanently」（`3219-3221`）、以及 API 头注释「for the lifetime of this device」矛盾。**保留行为**（清闩锁是有意的：用户可能刚在 NVIDIA 面板开启 VSR，需要复探），**改注释**描述真实语义「闩锁保持到下一次 `Auto` 请求」：

- `.cpp` `ApplySuperResolution` 顶部注释；
- `.h` 成员注释 `videoSuperResolutionRejected_`；
- `FFF.Player.Api.h` 结构体 `driverRejected` 注释（**仅注释，无 ABI 变化**）。

### 3.4 跨线程无锁读：改原子

`docs/88` P2：「呈现线程写、API 线程无锁读」。把这些成员改为 `std::atomic`（presentation 写 / status 读）：

- `nvidiaAdapter_`（`bool` → `std::atomic<bool>`）；设备创建时写一次，status 可能并发读；
- `videoSuperResolutionRejected_`（`bool` → `std::atomic<bool>`）；
- `videoSuperResolutionSourceWidth_/Height_`、`videoSuperResolutionTargetWidth_/Height_`（`uint32_t` → `std::atomic<uint32_t>`）。

读写点均改为显式 `load/store`（`FillVideoSuperResolutionStatus`、`SetVideoSuperResolution`、`reject`/`rejectAt`/`ApplySuperResolution`）。**结构体布局、导出签名不变**。

## 5. 刻意没修 / 未闭环（先量再推迟，不是顺口搁置）

| 项 | 为何不动 |
|---|---|
| `active=1` 仅证 `VideoProcessorBlt` 成功，**无能力查询** → 状态可能谎报 | 扩展本身无 capability query，属 `docs/88` P2，**不可修**，只能靠文档/UI 措辞（仍是休眠而非故障） |
| **每帧重建** `VideoProcessorEnumerator/Processor/输入输出视图` | 真实开销项，但正确修法是新增一套按几何缓存的 VP 资源（枚举器+处理器+两视图），会动到设备生命周期，本机既不能构建也不能跑像素判据，盲改风险大于收益。**登记待夹具** |
| 奇数目的盒取偶面后 `(w+1)/w` 轻度拉伸（P2） | 与 §2.3 同源；修法需让 VSR 生效时按真实偶数面再走一次缩放到奇数目标（多一次 pass/帧），收益极小、代价是每帧额外 pass。暂留 |
| 自适应降采样启用时 VSR 被静默拒绝（P2） | §3.2 的日志已让「为什么没生效」**可见**；根因是降采样纹理无 `BIND_DECODER` + `sourceWidth_/Height_` 被折成窗口尺寸，属源尺寸语义（`docs/88` lane7），改动面大，**登记** |
| 实机闭环：本机 NVIDIA App VSR `isEnabled:false` | 环境阻断（`docs/88` §4）。`active` 位不构成增强证据，需用户侧开启 + 硬解 + `--sr-window` 大于源分辨率，方可跑 `vsr_*_probe` 判像素差 |
