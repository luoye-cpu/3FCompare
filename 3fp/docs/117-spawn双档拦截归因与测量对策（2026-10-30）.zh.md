# spawn 双档拦截：归因与测量对策（2026-10-30）

- 起因：docs/116 §六发现 `SpawnMs` 双档（7–9 ms / 240–250 ms），且该开销**完整传导到 T2**（约 +300 ms），污染所有 A/B 绝对值。
- 结论：**系统级、与产品无关的随机拦截**，归因 360 安全卫士的进程启动扫描；对策是测量协议层面规避，不改产品。

## 一、归因证据

| 证据 | 读数 | 判定 |
|---|---|---|
| Defender 实时保护 | `RealTimeProtectionEnabled=False` | 不是 Defender |
| 运行中的 AV | `360安全卫士`（productState=331776，启用） | 360 是唯一在跑的实时防护 |
| 360 组件 | `360Safe`、`360tray`、`360QuickPreview`、`360DesktopLite64` 等 | 具备进程扫描能力 |
| 被扫描对象签名 | 我们的 exe `NotSigned` | 无信誉背书 |
| 已签名对照（notepad） | 每次 59–73 ms，**稳定中位 62.9** | 360 对它**每次都做固定检查**（非偶发） |
| 我们的 exe | 多数 4–7 ms，偶发 240–250 ms | **间歇性**拦截 |
| 同一 exe 对照（参数有无） | 有参 3/8 slow、无参 2/8 slow | 与启动参数无关 |
| 两个不同体积的臂（combo / a2） | 3/9 与 4/9 slow | **与产品版本/体积无关** |
| 文件副本预热 / 垫付进程 | 无效（仍 ~240 ms） | 不是"首次扫描"或"首进程"效应 |

## 二、特征

- **比例稳定在约 1/3**，但**无严格周期**：24 次采样中 SLOW 出现在 t≈0.3/8.1/13.4/21.3/26.6/37/47.3/57.7 s，间隔 7.8/5.3/7.9/5.3/10.4/10.3/10.4 s。
- 单次开销 **240–250 ms**（偶见 300+、最高 1672），与 exe 体积、参数、路径无关。
- **完整传导**：同一 exe fast 档 T2 = 1012/1048/1075；slow 档 T2 = 1357/1364/1370；ΔT2 ≈ 290–330 ms。

## 三、为什么之前没发现

docs/103/104 时代的窗口加载普遍 ~68–70% CPU、且 spawn 中位 9.4 ms（当时处于 fast 状态），偶尔的离群轮被 `SpawnMs>50` 判据当作噪声丢掉了——**判废机制一直有效，但掩盖了"约 1/3 的轮次会被系统拦截"这个事实**。

## 四、测量对策（写进协议，不改产品）

1. **同档配对**：两臂必须取同一 spawn 档比较。当前 `quiet_ab.ps1` 的 1 轮/臂交替天然满足（同批相邻），但要**在分析时按档分组**，不能混算。
2. **判废规则修订**：`SpawnMs>50` 全窗判废 → 改为**分档统计**：
   - fast 档（<60 ms）：作绝对基线（真实交付读数）
   - slow 档（200–700 ms）：可作相对比较，绝对值标注 +~245 ms 系统噪声
   - 超长（>700 ms）：真判废
3. **`quiet_ab.ps1` 应输出分档汇总**（待改）：每组同时给 fast/slow 两个子集的 n 与中位。
4. **扩大样本**：fast 档命中率约 2/3，要拿到 n≥15 的 fast 样本，轮数建议 ≥25。
5. **可选（不改系统设置）**：把 360 对测试目录加白名单——属用户环境的系统设置，**不建议由我代劳**，需要用户自行决定。

## 五、一个重要的正面推论

**fast 档 T2 = 1012–1075 ms**（负载 13–22%、真实无拦截）。此前所有"安静窗"读数（1645–1687 @53%）都被这层拦截污染。

⇒ **3FP 当前交付形态的真实冷启动已进入 ~1.0–1.1 s 档**（TFM 正常化 + 携带 IAMF + JIT，20.95 MB 的 A2 臂在 fast 档应更低）。这个数字比台账里所有历史值都好，应作为新的真实基线候选——前提是用 fast 档同口径复测。
