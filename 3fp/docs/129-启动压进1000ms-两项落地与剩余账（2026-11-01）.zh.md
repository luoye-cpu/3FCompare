# 129-启动压进 1000ms：两项落地 −174.6 ms 与剩余账（2026-11-01）

> 目标：**`Process.Start → 首帧上屏` ≤ 1000 ms**。
> 承接 `128-启动压进1000ms-分账与执行计划`，本文给**已落地**的两项与剩余缺口。
> 判据一律：同臂/同 exe **逐轮交替配对**，两臂 spawn 全落 `fast<60ms` 档（绝对基线可用）。

## 0. 三条判词

1. **两项落地，T2 实测 1500.0 → 1325.4（−174.6 ms，U=31，p<0.001，n=32）**，像素闸门
   跨臂 **0/1,139,795**（阴性对照 0）⇒ 画面完全不变。已提交 `e478ee5`。
2. **两项之和（−206）大于实测（−174.6）⇒ 有重叠，不做加法声称。**
   实测是唯一可信的数。
3. **距 1000 还差 325 ms。剩下的钱几乎全在两个"非本仓"的地方**：
   **Attach 414.6 ms（LakeUI，外部商业兄弟仓）** 与**框架起窗 251.1 ms（WinForms 内部）**。
   这两块占了 666 ms —— 想进 1000，绕不过它们。

## 1. 已落地的两项（都有配对证据）

### 1.1 图层呈现器延后到首帧之后（−110.0 ms，U=36，p=0.004）

**做了什么**：`字幕/弹幕/歌词/信息` 四个呈现器原在 `Form1_Load` 里同步构造，实测吃掉
`24_streamsel_done → 25_layers_done` 段 **177.5 ms**，且各自 ctor 内就 `Start()` 了
60 Hz 计时器（三条泵 = 6 条线程）。改为在 `Form1_Shown` 里由 `创建图层呈现器()` 构造。

**为什么安全**：这四个字段在 `Form1.vb` 之外的全部引用点都已带 `?.` 或 `IsNot Nothing`
（docs/125 §2-B 逐条核对，本轮复核）；**唯一的裸调用**是
`信息图层呈现器.应用全局字体(设置.实例对象.字体)`，已随构造一起搬进新方法。

**踩到的关键细节（第一版只拿到 −107.9，顺序错了）**：
`BeginInvoke` 只是**把委托排进消息队列**，`Form1_Shown` 本次调用返回后才轮到它。
所以若把 `创建图层呈现器()` 写成**同步调用**，它会**抢在开图前面**跑 —— 等于没延后。
正解：**开图与图层构造都排队**，且开图排在前。

```vb
If Not String.IsNullOrEmpty(请求文件) Then
    BeginInvoke(Sub() 打开外部文件(请求文件))
    BeginInvoke(Sub() 创建图层呈现器())
Else
    创建图层呈现器()
End If
```

### 1.2 启动预取默认关闭（−96.4 ms，U=41，p=0.009）

**做了什么**：`启动期预取大件` 默认直接 return；`FFF_PREFETCH=1` 可重新开启做 A/B。

**依据**：同 exe 只切 `FFF_NO_PREFETCH`，14 轮配对，**关掉后 T2 快 96.4 ms**
（28/28 全 fast 档）。机制：它把 FFmpeg 六件 + libshaderc 共 ~113 MB 读进文件缓存，
**与 UI 线程争磁盘/内存带宽**；而内核真正映射这批大件时，缓存往往已经太晚。

**这是 PR #48 第 4 项的一半，本机判为负收益**（另半"启动期 HIGH 优先级"124 已测不显著）。
PR 自己写过"预取贡献应接近 0、增量主要来自优先级"——本机连那半个也不成立。

## 2. 已试并否决（全部有配对数据，别再重复投入）

| 项 | 结论 | 判据 |
|---|---|---|
| 字体 17→2 组 + 字体改直赋/共享 | **判死** | **天花板实验**：整段短路仅 **−0.2 ms**（126）。诊断计数：73 控件里 66 个族名已同、只实际赋值 7 个、造字体 2 个；Designer 17 个 `New Font` 中 11 个是菜单对象的 `MenuFont`/`DescriptionFont`，字体控制遍历不到 |
| 量宽接 `TextFormatCache` | **有代码无收益** | 各段 −3…+3 ms（126） |
| 跳过重复 `PerformLayout` | **无收益** | +21.4 ms，p=0.38（本轮；与 docs/123 §12.2"重复是真的但不要钱"一致） |
| 预热线程降 `BelowNormal` | **无收益** | Attach +47.9 ms，p10–p90 跨零、符号不一致（127） |
| 零引用占位 23 个 | **不可删** | 全是可见分隔线（886×1/2×40 等），删了改外观（126） |

**教训（写进方法，不只写进脚注）**：
- 判"值不值得投入"要问**天花板**（整段不做能省多少），不是只做 A/B。
  只做 A/B 会把"我的实现不够快"误读成"这件事有潜力"。
- **按里程碑算出来的段，先问"这段里还有别的语句吗"**：`13_settings_done→14_font_done`
  之间夹着 `文件关联管理器.启动后台同步(...)`，那 22–58 ms 的主体不是字体。
- **跨批比较中位在本机等于随机**：同一对戳、同一台机器，`32_load_end→40_shown` 在三批里
  给出 993.9 / 309.6 / 281.2（3.4 倍漂移）。125 曾据此误判"预热把钱挪进这段"，127 已更正。

**结论**：可动的宿主项加起来也就 ~100 ms 量级，**325 ms 的缺口靠宿主微优化补不上**。
要到 1000 必须动下面两件之一（或都动）：

1. **Attach 414.6 ms（第一优先）**：PR 自测分解是"样式/DWM/拦截器/Chrome 覆盖层 282 +
   首次渲染 328（设备创建 266 已由第 5 项预热吃掉）+ 尾部 31"。
   本轮实测 Attach 剩 **379.3–414.6**，与"282 + 62 + 31 ≈ 375"吻合 ⇒ **钱在
   "样式/DWM/拦截器/Chrome 覆盖层创建"那 282 ms**，不在设备创建。
   **已为此准备并撤销了一次插桩**：`attach_subs.py` 可在 `Attach` 内插 7 枚子戳
   （`at_attach_begin` / `step1_opacity` / `step2_style` / `step3_dwm` / `step4_interceptor` /
   `step5_setwindowpos` / `step5_chrome`）。**关键约束（本轮撞到）**：LakeUI 是外部仓
   （`git ls-files` 计数 0），宿主以 `HintPath` 引用其 `bin\Debug\...\LakeUI.dll`，
   而**臂是单文件包、LakeUI 嵌在 exe 里** ⇒ 直接替换目录里的 `LakeUI.dll` 不生效，
   **必须用带子戳的 LakeUI 重新编译宿主**。本轮已备份并完整还原（两处 SHA256 校验通过）。
2. **框架起窗 251.1 ms**：属 WinForms 内部，唯一可影响的杠杆是交付形态
   （R2R/AOT）；docs/115 已测 A2 口径 R2R −187.8 ms / +4.23 MB，是现成的。
