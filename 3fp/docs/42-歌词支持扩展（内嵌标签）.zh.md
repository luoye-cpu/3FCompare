# 42 · 歌词支持扩展：内嵌标签读取（歌词承载测试包）

> 需求：「扩展歌词支持分析一下，测试包 `C:\PLAN\kit\kit` 里有很多歌词实现办法，添加好支持」
> **结论：16 件素材 + BOM 边界共 17 项断言全部通过。** 缺口在**宿主侧**，内核无需改动。

---

## 0. 测试包是什么

16 件同一首歌的素材，**只差歌词的承载方式**；歌词 12 行、时间戳 0.5/4.0/7.5…（每 3.5 s），
因此"同步对不对"可肉眼判读。MANIFEST 还点名了**三处"各家不一致"**，正是本次要吸收的。

---

## 1. 分析：缺口到底在哪一层

### 1.1 3FP 原本只认**边车 `.lrc`**

```
第三方歌词加载：LRC歌词自动加载器.尝试加载同名歌词Async(媒体路径)
                → Path.ChangeExtension(媒体路径, ".lrc")
```

**完全没有读取内嵌标签的路径** ⇒ 歌词写在容器里的文件**静默无词**。

### 1.2 但内核**早就把全部载体暴露出来了**

实测 A–P 全扫描（`tools/lyrics_probe.cpp`）：内核的 `GetMediaInfo` JSON 里
**每一个歌词载体都在**——

| 素材 | 内核 JSON 里的键 | 层级 |
|---|---|---|
| A/B/C/E/H/I/L/O | `LYRICS` | 流级（opus）/ 容器级（mka/flac） |
| D | `LYRICS`（**纯文本，无时间轴**） | 流级 |
| F/J/K/M | `lyrics`（**小写**） | 流级/容器级 |
| G | `COMMENT` | 流级 |
| N | `syncedlyrics`（TXXX） | 容器级 |
| P | **无**（标签整批丢失，设计如此） | — |

⇒ **这是纯宿主侧缺口**，不需要新增任何内核导出。这一点很关键：
避免了又一次 ABI 变更。

---

## 2. 需要吸收的三根轴（MANIFEST 四）

### 2.1 键名与大小写

`LYRICS` / `lyrics` / `SYNCEDLYRICS` / `UNSYNCEDLYRICS` / `syncedlyrics` / `USLT` / `©lyr` / `COMMENT`

⇒ 大小写不敏感、按优先级逐个尝试。

### 2.2 挂载层级

- **`.opus` 在流级**（`ffprobe -show_format` 为空）
- **`.mka/.flac/.mp3/.m4a` 在容器级**

⇒ 两级都查，**容器级优先**（它通常是被主流工具正式写出的那份）。

### 2.3 有无时间轴

`SYNCEDLYRICS` 有，`UNSYNCEDLYRICS` 是纯文本。
**纯文本绝不能当同步词用**——否则 12 行会全挤在同一时刻。

⇒ 有轴才解析；纯文本保留为"有词但不可同步"，并**如实提示用户**，而不是静默丢弃。

## 3. 实现

### 3.1 新增 `TimedText/内嵌歌词提取器.vb`

- 复用了既有 `LRC歌词解析器.解析(TextReader)` —— 它本来就接收流，直接喂内嵌文本；
- 优先级：**边车 `.lrc` > 内嵌标签**（用户放边车是明确意图）；
- 键搜索：同步键 → 兜底键（`COMMENT` 需含时间轴或长度 ≥ 24 才认，
  否则会把"Cover (front)"这种说明当歌词——O 件实测就有这个陷阱）。

### 3.2 接线：`播放器控制器.自动加载同名歌词Async`

```
① 同名 .lrc 优先
② 没有边车 → 内嵌歌词提取器.提取(媒体信息)
③ 纯文本载体 → 提示"没有时间轴，无法同步显示"
```

### 3.3 ⚠️ 修掉一个我自己引入的**诊断错误**

第一版跑出 16/16，但我核对时发现：**F/J/M 报告键名是 `LYRICS`，而文件里实际是小写 `lyrics`**。

原因：`取键` 返回的是**我们搜索用的规范键**，而不是字典里**实际出现的拼写**。
这会让看日志的人以为文件里写的是大写 —— 诊断信息失真。

**已修**：返回实际键名。修正后测试期望也随之校正（F/J/K/M → `lyrics`）。

> 教训：**测试全绿不等于证据正确**。我逐个核对报告值才发现这个报告层缺陷——
> 如果只看"16/16 PASS"就收工，会把一个错的诊断字段当成对的。
> 这也是为什么测试用例里**断言了具体键名**，而不只是断言"能读到"。

### 4.1 BOM 这一条单独验（MANIFEST 四之三）

实测复现了 MANIFEST 的说法：

```
E_opus_lrc_with_BOM.lrc     BOM=True   吞BOM后=12行   不吞BOM=11行
C_opus_three_keys_plus_lrc.lrc  BOM=False            12行
```

⇒ **不剥 BOM 会丢首行（12→11）**，正是 ffmpeg 系的已知行为。
3FP 边车路径有**双重保护**：`StreamReader(detectEncodingFromByteOrderMarks:=True)`
+ `line.TrimStart(ChrW(&HFEFF))` ⇒ 12 条完整。

内嵌路径由提取器自己在解析前 `TrimStart(&HFEFF)`，且只剥行首那一个。

### 4.2 测试走**真实链路**

`--lyrics-kit-regression` 不重新实现一套逻辑，而是
**内核 MediaInfo JSON → 宿主模型 → 真实提取器**，否则测的是"我以为的逻辑"。

## 5. H 件（.mka：标签 + ASS 字幕轨）—— 两条路都通

MANIFEST 说 H 的"同步走字幕"。实测该文件**同时**有：

```
LYRICS 标签（12 条，本次新增路径读到）
Stream #0:1: Subtitle: ass
```

而 3FP **原本就会自动加载内嵌字幕轨**（`播放器控制器:1464`）⇒
**两条同步来源都可用**，无需额外改动。

## 7. 已知边界 / 未做

| 项 | 说明 |
|---|---|
| **P 件无词** | MANIFEST 明确"标签整批丢失是本件的设计目的"⇒ **不是缺陷**，是预期 |
| **tx3g / mov_text 同步轨** | J/K 的 `tx3g` 轨走**内嵌字幕**路径（已有能力），未与标签歌词做"谁优先"的仲裁——两者都能显示，未定义冲突规则 |
| **`.m4a` 的 `©lyr` 只读标签** | ffmpeg 把它映射成小写 `lyrics`，故走标签路径；**未解析 tx3g 轨道内的逐句时间码当作歌词** |
| **纯文本歌词的显示** | 只提示"无时间轴"，**未做静态展示**（如整页显示） |
| **字符编码** | 内嵌标签由 ffmpeg 解码为 UTF-8；非 UTF-8 的 ID3 编码由 ffmpeg 处理，未单独验证 GBK 等 |
| **UI 提示文案** | "内嵌歌词「XXX」没有时间轴"已实现，但**未在实机 UI 上目视确认** |
