> **一句话结论**：docs/148 §四 item 8 的**代码前提全部成立**——宿主 4 台常驻 `PrecisionTimer`（100ms 界面呈现 + 字幕/弹幕/歌词三泵）从 `Form1_Load` 起不释放，各持一份**进程级 `timeBeginPeriod(1)`**；内核 `FFF.Player.Present` 渲染过一帧就永不退出（暂停/最小化/静图都 alive），再持第二份 1ms。**但实测可测的 CPU 常驻税比预期小**：暂停/最小化 ≈ **0–0.5% 单核**、可见空闲 ≈ **1.25–4.7% 单核**（窗口噪声大）；"播放中最小化" 14.6% 单核是播放本身还在跑（设计如此）。⇒ P2-8 真正要治的是**"进程时基不归零"这一功耗事实**，不是可测 CPU 税；而本机 CPU 时间量具**看不见** 1ms 时基对深睡/C-state 的影响。建议按 §五 的内核最小面先做（低风险、零可见行为），宿主侧因"100ms 兼作双耳跟随心跳"需先答一个 U；若用户无功耗/续航诉求，此项目前**收益低，可降优先级**。

关键结论（host-vb 原文要点，均已核）：
1. **全树没有 `WindowState`/`Visible` 门控**：Form1 只挂 `Shown/FormClosed/DpiChanged`；最小化时 100ms 与三泵全部照跑。
2. **4 台常驻 timer ≈ 7 条线程、4 份 1ms 引用**：每台 `PrecisionTimer.Start` 即 `timeBeginPeriod(1)` 引用 +1（`PrecisionTimer.vb:77-89,306`），每刻度末 0.5ms `SpinWait`（`:527-531`）；从 `Form1_Load` 起，即便无媒体/暂停/最小化也不释放。
3. 暂停只发 `FFF3FP_Pause`（`播放器会话.vb:368`），不改任何计时器/间隔；暂停图标是 WinForms chrome 按钮（`Form1.Designer.vb:879-897`），**不提交原生图层**；最小化也不清层。⇒ 暂停/最小化不会**拉起**内核 Present 线程，但也**不会停止**它。
4. 播放中最小化时三泵仍 16ms tick 且位置前进 ⇒ 签名变化 ⇒ 每拍提交图层（主要浪费场景）。

## 三、内核侧事实（E2，来自 `kernel-cpp` 只读调查；行号为当前工作树）

- 唯一图层入口：`FFF3FP_SetTimedTextLayer`（`PlayerApi.cpp:258`）→ `PlayerSession::SetTimedTextLayer`（`PlayerSession.cpp:2937`，仅 Ready/Playing/Paused/Ended 接受 `:2952-2955`）→ `PlayerVideoRenderer::SetTimedTextLayer`（`VideoRenderer.cpp:5880`）。
- 可见性 = 四槽任一 `commands` 非空（`:5940-5956`），非空才起线程（`:5957-5962`）。
- **线程有 3 个启动点**：图层非空 `:5957` / `Render` 有帧 `:8065` / `Redraw` `:8122` ⇒ **静态图也会拉起 Present 线程**（与图层无关）。
- **唯一退出条件**是 `StopTimedTextThread`（`:6077-6087`）置 `timedTextThreadStop_` 并 join，调用者仅设备重建/`ResetMedia`/`Close`（`:9554/:9569/:9654`）；`timedTextThreadRunning_=false` 只在 join 之后（`:6086`）⇒ **不存在"线程存活但不干活"的路径**：暂停/最小化/Ended/图片静止均 alive。
- 时基：`PresenterTimerResolution` RAII（`:108-114`）在 `TimedTextThread` 开头构造（`:5981`），随线程析构释放；**内核全树只有这 1 处 `timeBeginPeriod`**。⇒ 与宿主 4 台 timer 叠加，进程在"暂停/最小化/静图"时同时持 2 类 1ms 引用。
- 只诊断结论：**无需新增内核代码/导出/日志**——`FFF.Player.Present` 已命名（P0-3，`VideoRenderer.cpp:5977`），外部枚举线程名 + 存活即证明 1ms RAII 还在；实际产品里 GUI 宿主没有内核日志槽（`注册内核日志()` 零调用点），加 trace 反而读不到。

## 四、E1 实测（本机，2026-11-12）

### 4.1 状态 × 线程 / CPU

| 状态 | 线程总数 | 有名线程 | `FFF.*` 线程 | `FFF.Player.Present` | Present 线程 CPU Δ（3 s） | 进程 CPU（% 单核） |
|---|---|---|---|---|---|---|

| 无媒体 idle（最小化） | — | — | — | — | — | 3.44（2.5–3.75） |

补充：
- 静态图比无媒体 idle 多 47 条线程：`av:png:df0-3` ×4、`FFF.*` ×5、.NET TP 等——图片解码后线程池/线程不回收，与 P2-8 无关（docs/133 已判线程池膨胀）。
- 暂停验证：`PostMessage` 空格会被前台锁定吞掉（`SetForegroundWindow` 返回 False 时第一次常见无效）；改用 `AttachThreadInput + keybd_event` 后，**playing 42.7% → paused 0.52% → resumed 40.1%**，判据成立。
- 无媒体 idle 时 `FFF.Player.Present` 不存在（未渲染过），但**宿主 4 台 timer 仍持 1ms**：所以纯 idle 的 1ms 来自宿主，不是内核。
- 命名验收（P0-3）：Release 产物可枚举到 `FFF.Player.Present` / `SessionWorker` / `Prefetch` / `PrefetchGuard` / `CoverBackdrop` 五条；宿主侧可枚举到 `LakeUI.PrecisionTimer.Scheduler` ×4–5 + `Worker#0` ×3，与 host-vb 的"4 timer ≈ 7 线程"一致。

### 4.2 解读

1. **暂停/最小化/静图时 CPU 税接近 0**；可见空闲窗口的 1.25–4.7% 单核波动无法稳定归因（timer 回调刷新 vs WinForms 重绘 vs 采样噪声），保守可说法是"可见空闲常驻税 ≲4% 单核 ≈ 0.2% 整机"。
2. **真正没被测到的是 1ms 时基对系统空闲的代价**：进程 CPU 为 0 时，持有 1ms 时基仍会让 CPU 无法进深 C-state、抬高整机空闲功耗/温度——这是 P2-8 想治的对象，需要功耗计或 `powercfg /energy` 级量具，不是 CPU 时间。
3. "播放中最小化" 14.6% 单核是解码/呈现仍在跑（音频继续的设计），不是计时器门控问题；要省它属于"最小化暂停播放"的产品决定，不在 P2-8 范围。
4. 暂停态回退到 0.52% 说明：**暂停本身很便宜**；P2-8 的收益仅在"让进程时基归零"（功耗），不在 CPU 税。

## 五、结论与范围建议

- **只诊断结论（本项完）**：宿主 4 timer 无窗口/播放态门控 + 内核 Present 线程永不退出，**代码层面成立**，且已用外部采样确认"暂停/最小化/静图时 Present 线程仍 alive、持有 1ms"。无需新增内核诊断代码。
- **要不要修**：按 docs/148 的原意图（`P2-8 双侧同改`），修法是：
  1. **内核最小面**（`kernel-cpp` 方案，只改 `VideoRenderer.cpp`，约 +15/−2）：`PresenterTimerResolution`（`:108-114`）加幂等 `Raise()/Release()`，线程循环里"本拍有 present → Raise；纯 `devicePollOnly`（`:6049-6052`）→ Release"；暂停/Ended/静图首个 500ms 空轮询即释放（滞后 ≤~0.5 s），generation 自增/notify 唤醒即重取。0 ABI/导出/契约变化。**注意：宿主 timer 仍持 1ms 时单项看不出收益**（进程级引用计数），所以必须先有宿主侧或同时改。
  2. **宿主最小面**（`host-vb` 方案）：Form1 补 `Resize/Minimized` 状态源（当前无）；字幕/歌词泵间隔判据并入播放状态（弹幕已是此型）；`界面呈现器` 最小化时 Interval 500–1000ms；恢复用现有"使图层失效/强制提交"立即补帧。**风险**：100ms 兼作双耳跟随设备心跳（`Form1.vb:339-342`），**播放中最小化不能停**；要宿主时基归零必须 4 台常驻 timer 全停（任一在跑即持 1ms），只停三泵不够；**不建议改 LakeUI third_party**。
- **我的建议**：由于实测 CPU 税很小、内核/宿主都必须改才有时基收益，且"最小化+播放中"因双耳心跳存在 U，**本轮建议只做内核最小面**（零可见行为、低风险、让"播放中持有的 1ms"变成"只在本拍有 present 时持有"——这是语义正确性修复），宿主侧等 U（双耳心跳是否必须播放中也跑、功耗收益是否值得）再定；若用户无功耗/续航诉求，P2-8 整体可**降优先级/仅记录方案**。内核最小面已于同日落 docs/153（新 DLL `EC3B89A550B3BD0E`，构建 0 警告/0 错误，探针与 GUI 无回归）。
- **不做的**：空闲停掉 `TimedTextThread`（会带走设备丢失轮询，需在 3 个启动点重接，风险大）；改 LakeUI `PrecisionTimer` 实现（third_party 红线）；把 "最小化时暂停播放" 塞进 P2-8。
