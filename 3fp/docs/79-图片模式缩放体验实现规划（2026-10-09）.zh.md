**由此定的三条硬结论**

- **C（链缓存键）是 B（平滑阻尼）的前置**，不是可选优化：平滑＝每 tick 换一个 zoom＝每 tick 一次整链重建。**且 C 不能塞进"超大图"门槛里**，否则 8K 图（≤16384）永远不受益，而 8K 图正是付费区间最宽的。
- **B 的锚点解法用现成的 `ZoomViewAt` 链式调用**，零新导出、零几何复制（见 §4-B2）。
- **D（超大图）在给定门槛下 = 分块 deep-zoom 一条路**，它是新渲染模式而非补丁；`降级预览` 那一档算能力降级，**要授权**。

## 2. 轨道划分与依赖

```
P0 牙齿（门禁/夹具）
   └─→ A 缩放语义对齐 PixelPictureBox          （纯宿主，可独立先行）
   └─→ C 降采样链缓存键（图片门控，内核）        │
          └─→ B 平滑缩放 + 阻尼体感（宿主）◀─────┘  ← C 不做，B 每 tick 拆一次链
                 └─→ E 中途插值滤镜决策（看图再定，可能整条撤）
P0 ──→ D 超大图 max(w,h)>16384 分块 deep-zoom（内核，最后做，破坏面最大）
```

**为什么 C 与 D 分家**：C 的收益对象是"任何 `源尺寸 > 缩放盒` 的图"（8K 图就在此列，远小于 16k 门槛）；D 的收益对象按用户口径严格限定为 `max(w,h) > 16384`。**若把 C 写成 D 的子项并按门槛激活，8K 图的平滑缩放仍然是每 tick 重建——等于没修。**

## 3. 轨道 A · 缩放语义对齐（宿主 `UI/播放器图片浏览控制器.vb`）

| 步 | 办法 | 落点 |
|---|---|---|
| A1 | **钳位收成一套**：删宿主 `最小缩放 0.1F / 最大缩放 32.0F`，宿主不再持有第二套界；数值上限改由"每图片像素的屏幕像素数"表达（默认 64，对齐 `PixelPictureBox.vb:290,569`），内核 `0.05–64`（`VideoRenderer.cpp:2120`）保留为最后防线 | `:20-21` → 改为属性 + 从 A2/A3 推导 |
| A2 | **最小缩放 = 适应比**（对齐 `PixelPictureBox.vb:566`），不再固定 0.1：`min(视口宽/源宽, 视口高/源高)`，图小于视口时取 1（对齐 `:554-562`）。视口与源尺寸宿主都拿得到 | `:20` 常量 → 函数 |
| A3 | **进/出图片模式开/关 `FFF3FP_SetFitLimitToNative`**：进（`设置模式` `:92-98`）置 1，出（含出错/关文件）必须置 0。这是"zoom 1 = 像素级 1:1"的底座，也是 A1 的"屏幕像素/图片像素"语义成立的前提。**该导出的盘上存在性尚未验证（§8-U1），实施第一步就是查它** | `:92-98`；Interop `播放器原生接口.vb` 加解析（照 `:712-717` 的 `GetExport` 可选解析写法，缺失即回退不崩） |
| A4 | **补双击：适应窗口 ↔ 1:1**（`docs/00 §6.4` 写了、控制器 0 命中、STATUS P4 挂着） | `播放器画面控件.vb` 的 `MouseWheel` 同级加 `MouseDoubleClick` 转发；控制器加一个"切到目标档"的过程 |
| A5 | **步进律与量化保持不动**（×1.25/×0.8、120 像素一刻度、`:1128` 式的"到界即空转"早退） | `:22-23,116-127` 不动 |

**判据**

- A-1 一次放大 N 格再一次缩小 N 格，`缩放值` 回到初值（×1.25 与 ×0.8 互逆，往返 20 格逐位等）。
- A-2 图小于视口时"适应"档读数为 1.00，不是 <1。
- A-3 `zoom=1` 时 `ReadVideoPixel`/`ReadPixelRegion` 采到相邻像素值相同（像素级 1:1 的**产物**证据，不看声明）；**并且退出图片模式回视频后，视频侧行为逐字节不变**（`ab_baseline_vs_patched.sh` 那条既有对照链）。
- A-4 双击两次回到原档；且 A3 的复位判据 = 关闭图片模式后 `SetFitLimitToNative` 读回 0（若无读回通道，就在宿主侧记一笔并由 A-5 的对话框断言覆盖）。

**⚠ A2 会撞上一个硬瓶颈，必须同批处理**：内核下钳 `0.05f`（`VideoRenderer.cpp:2120`）意味着**适应比低于 0.05 的图永远到不了"整图入窗"**，谓词是 `源边长 > 20 × 该边视口长`。16384px 图在 ≲819px 的视口里就落到这个区间——而这恰好是 D 轨那批图。处置：**图片门控地**放宽内核下钳（不放宽视频侧），并给放宽后的下限一个显式常数与理由；不能靠"把适应比钳到 0.05"糊过去，那会把"适应窗口"变成"看不全"。

## 4. 轨道 B · 平滑缩放 + 阻尼体感（宿主，**前置 = C**）

**选型定死**：用本仓已有的**临界阻尼弹簧**（`播放器360视角控制器.vb:290-299`，`阻尼时间秒=0.25F`），**不**用 LakeUI `D3D_AnimationHelper.AnimateTo` 的定长补间。
理由：滚轮是**连续改目标**的输入，定长补间每来一格就重启、必然抖；弹簧只换目标、状态（当前值＋速度）连续。LakeUI 该借的是**约定不是实现**——`AllowSmoothScroll` 默认 False 这条（`D3D_AnimationHelper.vb:12-13`），照搬成一个开关。

| 步 | 办法 | 关键点 |
|---|---|---|
| B1 | 状态三元组：`目标缩放`、`当前缩放`、`缩放角速度`；再加`锚点`(ax,ay)与`动画中`标志 | 全部宿主私有，不动内核 |
| B2 | **每 tick 用 `ZoomViewAt(本 tick 的比值, ax, ay)` 链式推进**：`factor_step = 新当前 / 旧当前`。这样**每一帧都满足"光标下的点不动"**，且钳位/几何全由内核权威计算，宿主不复制一行几何 | 这是不用 `SetViewTransform(绝对值)` 的原因：`ZoomViewAt` 只出参回 `resultingZoom`、**不回 pan**（`Api.h:644-645`），走绝对值就得宿主自己镜像 `VideoRenderer.cpp:2189-2216` 的锚定解，那是会漂移的第二份真相 |
| B3 | tick 驱动照 360 的先例：`Timer.Interval` 取常数（默认 **8ms**，与 `播放器360视角控制器.vb:23` 同值，因为 `阻尼时间秒/0.01 静止阈值` 是在那个 dt 下调的）；**步长必须用实测经过秒**，不能假定就是 8ms（WinForms Timer 不精确，且这里假定就是"两条异步命令间睡固定时长=赌"） | 静止判据照 `:251-255`：`|目标−当前|<ε` 且 `|速度|<ε` ⇒ 写死终值、停表。**不停表＝空转 present** |
| B4 | 连续滚轮：**合并进目标**（`目标缩放 *= 1.25`），**不重启动画、不清速度**；`滚轮余量` 量化（`:116-119`）保持在输入侧 | 体感核心：快速连滚应越滚越快而非一顿一顿 |
| B5 | 弹簧共享：把 `平滑阻尼` 从 360 控制器提出为 `Friend Shared` 的公共模块（或直接引用现签名的等价复制）。**先测两条链路是否要同一组常数**——缩放不需要过冲，360 需要，若常数不同就不要强行合并成一个文件 | 判据在下面 B-4 |
| B6 | 动画期间**禁止** A4 的双击/平移与动画打架：新输入进来时要么改写目标、要么 `SetImmediate` 式收尾。LakeUI 有现成范式（`D3D_AnimationHelper.SetImmediate :227`） | 否则出现"双击后还在飘" |

**判据**（全部要是**可数的状态**，不是形容词）

- B-1 单次滚轮一格 ⇒ 从输入到静止，present 次数落在 **[6, 30]**，且**末值 == 目标值**（钳位后），不是"接近"。取数点：`presentationGeneration_` 或宿主 tick 计数打印到日志。
- B-2 停止滚轮后 **present 计数归零**（证明停表真的发生了）。这条必须在"未修复构建"上跑一次并要求它**红**——否则它是恒绿的。
- B-3 连滚 5 格：总放大倍数 = 1.25^5，且光标下那一点全程不动 —— 用现成的 `zoom_anchor_probe.cpp` 的漂移读数法（`:126-137` 三步进量漂移、阈值 0.08），但**先按 P0 把 verdict 接进退出码**。
- B-4 弹簧稳定性：tick 抖动到 30ms（人为拖慢 UI 线程制造）后，缩放不发散、不越过目标 >2%。
- B-5 视频模式与 360 度回归不变（360 是被 B5 抽取动作碰到的那条链，必须有它自己的回归：`docs/06 §267` 提到过 360 的阻尼回归测项）。

## 5. 轨道 C · 降采样链缓存键（内核 `VideoRenderer.cpp`，图片门控）

**现状（已逐跳读到）**：链按 `(srcW,srcH,tgtW,tgtH,format)` 全等才复用（`:3778-3782`），否则释放**全部 pass** 再重建（`:3784-3793`）；`tgtW = min(planeWidth, destination.width)`（`:4037`），而 `destination.width = zoomedWidth`（`:5938`）。
⇒ **`zoomedWidth < 源宽` 区间内，每格滚轮 = 一次全图多级重降采样 + 一批 RT 释放/新建**；越过 1:1 后链为 0 pass，才不付费。

| 步 | 办法 | 副作用 |
|---|---|---|

## 6. 轨道 D · 超大图（激活谓词 `max(w,h) > 16384`，图片 + 动图）

### D0 门槛本身要先建成一件东西

- **谓词**：`max(源宽, 源高) > 16384`。**放置点**：`PlayerSession.cpp:2445` 现在把尺寸判定关在 `if (staticImage_)` 里；动图走不到那里（判词 6）。所以门槛必须是 **`staticImage_ || animatedImage_`** 两支共用的一个谓词，且**在 `OpenFormat` 之后、`OpenDecoder` 之前**取尺寸（现有取数点 `:2446-2448` 用的就是 `codecpar`）。
- **动图额外账**：动图今天可硬件解码（`:2465` `D3D11 && !staticImage_` ⇒ 动图**走 D3D11VA**），而静帧被强制 CPU。分块上传若假设"CPU 帧在手"，动图这条就得先 `av_hwframe_transfer_data`（`:3657`）或把动图也拉回 CPU 路——**前者是拷贝，后者是降级**，二者都要写明，不能默认。
- **动图的帧维数**：APNG/WebP 的帧可以带独立尺寸与偏移（不是统一画布），谓词必须按**画布/组合尺寸**判，而不是第一帧。多页 TIFF（`edge/08a_multipage.tiff`）同理。

### D1 为什么不是"金字塔"也不是"降尺度"

16384 是 FL 11_0+ 的 `TEXTURE2D` 规格上限：**任何一张纹理都装不下 >16k 的那条边**。而金字塔/降尺度的**第 0 级就是原图**——它在上传那一步就失败，后面的级根本没机会存在。所以在此门槛下只有两种收场：**(a) 分块，让任何单张纹理都不超限；(b) 降级预览，把第 0 级换成一张放得下的缩小图。**

### D2 分块 deep-zoom（唯一非降级解）

| 面 | 要改什么 | 证据 |
|---|---|---|
| 资源形态 | 单张全尺寸纹理 → **tile 网格**（`Texture2D` 数组或 `Texture2DArray`/slab）。今天 SRV 全是 `TEXTURE2D`，无一处 array SRV | `PlayerSession.cpp:2441-2444`；`VideoRenderer.cpp:3056/3112/3186` 【lane】 |
| 采样 | `Load(int3(uv*dimensions, 0))` 假设**单一全局 dimensions**；分块后必须先算 (tile 索引, tile 内坐标)，`ImageMode` 分支整块重写 | `:557-558, :626-629, :814` 【读】 |
| 视口/裁剪 | 今天没有 `srcRect`（只在 VP 路径存在 `:4127-4129`），也没设 scissor（`RSSetScissorRects` 命中 **0**），靠"视口∩RT 边界"天然不画屏外。分块必须显式**只上传/只画可见 tile** | 【读】 |
| 色度栅格 | 8-bit JPEG 是 `yuvj420p` 平面上传（`:3093-3095`），**tile 边界必须对齐 4:2:0 栅格**（tile 尺寸取 2 的幂、色度平面按 `(w+1)/2` 切），否则每块 tile 接缝处色度错位 | 【读】 |
| 低层常驻 | 高层（1/2、1/4、1/8…）小、可常驻，用现成的 sws **保格式**降尺度（模板 `PrepareAdaptiveDownscale:3962-3972`：`sws_getCachedContext` 且**保持同一 `pixelFormat` 与 range/colorspace/primaries**）；第 0 级 tile 按需上传、按需淘汰 | 【读】 |
| 回读要改道 | `ReadVideoPixel` / `ReadPixelRegion` 是这一路所有像素判据的**唯一取数口**，分块后它们必须能从 tile 读；否则 P0/B/C 的全部判据同时失明 | `Api.h:669+` 【读】 |
| 旁路消费者 | cover art / backdrop（`:2458`、`DrawCoverBackdrop :5968`）、`EnsurePipeline` 的单尺寸缓存（`:3031-3035`） | 【读/lane】 |
| 上限派生 | 16384 别再抄第二遍：tile 尺寸与"是否超限"都要从 `CheckFormatSupport(D3D11_FORMAT_SUPPORT2…)`/适配器实测派生（今天全树没有任何尺寸查询） | 【读】 |

**代价定性**：这不是补丁量级，是**新增一条渲染模式**。它和 §5 的 C 共用同一套 pass/tile 语义，**所以 D 必须排在 C 之后**——先把链的缓存与级选择做对，分块只是在同一套级选择上换存储布局。

### D3 解码峰值不因分块而下降（诚实账）

分块省的是 **GPU 常驻**，不是**解码峰值**：png/tiff/jxl/jxr/avif/heic/bmp/exr **必须先全解码**（`-lowres` 对这些解码器返回 "maximum value for lowres supported by the decoder is 0"，**【测】**）；只有 **mjpeg** 能白拿 1/2、1/4、1/8（**【测】** 960×540 / 480×270 / 240×135）。
⇒ 一张 20000×20000 的 PNG，分块方案下 CPU 侧仍要过一遍全尺寸帧；`16384²`×4B ≈ 1 GB 这一档的**峰值内存**问题，分块不解决。要解决它得另开一路（`D4`）。

### D4 真要把峰值压下来只有两档（都要授权）

- **D4-a 分块解码**：JPEG 用扫段/多遍、PNG 用 IDAT 行带流式解码——**FFmpeg 现有解码器不直接暴露行带接口**，要做等于自写或改解码器。成本级别：远超本规划其它所有项之和。**建议只做登记，不进本轮。**
- **D4-b 降级预览**：>16k 时以 `lowres`（仅 mjpeg 免费）或"全解码→保格式降尺度→**立刻释放原帧**"产出一个放得下的第 0 级，明确告诉用户"当前为预览分辨率"。**属能力降级，按规矩要授权**。峰值仍包含一次全解码，只降常驻，不降峰值。

### D5 面向用户的失败契约不能被改坏

今天 >16k 的文案是英文原文经 `ExOverlayMsgBox` 弹严重对话框（`播放器会话.vb:723-728` → `Form1.vb:570-574`，【lane】）。D 无论走到哪一档，**必须保留 `operation` 字符串这一层可断言的通道**（现有 `open-image-size` / `open-image` / `open-animation` `:2454, :2550`），并且给动图补上它今天缺的那一支（现在动图超限只会以不透明失败收场）。

### D 的判据

- D-1 谓词命中表：`>16384 静图 / >16384 动图 / ==16384 边界 / <16384` 四例，各自的状态与文案，**逐例指到日志行**。
- D-2 `20000×20000` 样张：可开、可放大到像素级 1:1 且 tile 接缝处**无**色度/几何错位（接缝处逐像素比对，取数走 D2 改道后的 `ReadPixelRegion`）。
- D-3 ≤16384 的一切**行为与今天逐字节相同**（门槛外不许有任何变化——这是这条口径的直接验收）。
- D-4 动图回归：既有 17/17 样例矩阵（`verify_all_samples.sh`）不新增失败；动图 >16k 从"不透明失败"变成"确定的、有 operation 的结局"。

### 11.12 S10 真鼠标拖动档：又换到一条既有缺陷（2026-10-10）

并发写者当天 10:10–10:14 又动了 `PlayerSession.cpp/.h` ⇒ 内核侧一律不碰，改动合并状态
重新封存到 `3fp/build/dirty_snapshot_20261010_1041/`（`tracked.patch` reverse-check 通过 + 14 件原件）。

把"拖动手感"从"只能靠眼"变成可算的依据是内核那条公式（读自源码）：
`offsetX = panX * |zoomedWidth − fittedWidth| / 2`（`:5933`），`zoomedWidth = fittedWidth * zoom`（`:5913`）
⇒ 一格 pan 换成屏幕位移的分母是**适配盒宽**，而 `fittedWidth` 只在**限制轴**上等于控件尺寸。

**读数**（真 `WM_LBUTTONDOWN/MOUSEMOVE/LBUTTONUP` 投到输出面 Panel 的 HWND，z=13.2159 即 1:1）：

| | 修前 | 修后 |
|---|---|---|
| 宿主实发 pan | `0.015543` | `0.021637` |
| 换算成屏幕位移 | `86.2 px`（请求 120px） | **`120.0 px`** |
| 跟手比值 | **`0.7184`** ＝ 908/1264 | **`1.0000`** |

⇒ **既有缺陷（非本轮引入）**：拖动分母一直用控件宽高。非限制轴上画面只走手指位移的
`适配盒/控件` 比例——12000×9000 在 1264×681 下就是**拖 120px 只走 86px，不跟手**；
限制轴（这里是高）恰好相等，所以一直看不出来。
⇒ **修法**：`图片缩放几何` 加 `适配盒宽/高`，控制器拖动改用它们当分母；顺带删掉因此失效的
`宽度/高度` 两个局部变量。**只动图片模式的拖动路径**，视频侧无关。

顺带三条自证：修前那条红是**代码错**（比值精确等于 908/1264，且我手算 pan 0.015542
与实发 0.015543 相符 ⇒ 模型对）；后来那条红是**我的断言算术写错**（`681×12000/9000` 写成了
`1264×12000/9000`）——两种红要分清楚，前者值得修代码，后者只该修测试。
