## 2 改了什么（按语义，行号已复核）

1. **静图一律先试硬解**：`DoOpen` [:2662](../kernel/FFF.Native/3FP/Core/PlayerSession.cpp) 的门控去掉 `&& !staticImage_`，
   失败后仍走既有的"显式关硬件重试" [:2668](../kernel/FFF.Native/3FP/Core/PlayerSession.cpp)；
   `RecoverVideoDevice` [:1730](../kernel/FFF.Native/3FP/Core/PlayerSession.cpp) 同步；
   原来无条件把静图读数压成 `Cpu` 的两行与 `"Still images use CPU decoding…"` 事件一并删除。
2. **静图后端只允许 D3D11VA**：[:2560](../kernel/FFF.Native/3FP/Core/PlayerSession.cpp)
   `backendCount = staticImage_ ? 1u : std::size(Backends)`。理由见 §5 的呈现缺陷。
3. **静图不再下载**：[:3794](../kernel/FFF.Native/3FP/Core/PlayerSession.cpp) 保持 `format != AV_PIX_FMT_D3D11` 才做
   `av_hwframe_transfer_data`，于是 D3D11 静图纹理直接进渲染器（与动图同一条通路）。
4. **设备重建后重解而非复用旧帧**：[:1750](../kernel/FFF.Native/3FP/Core/PlayerSession.cpp) 若保留帧是硬件帧就
   `av_frame_unref` 丢掉，倒带回流首再 `DecodeInitialFrame()`。这条替代了原实现"强制软解"所要满足的
   device-independent 语义。
5. **CPU 色域转换只用于 CPU 平面帧**：[:3827](../kernel/FFF.Native/3FP/Core/PlayerSession.cpp) 加 `!IsHardwareFrame(renderFrame)`；
   硬件帧交给渲染器自身的宽色域通路。
6. **软件回退对静图真的能续上**：两处必要件——
   `FallbackToSoftwareVideoDecoder` [:2994](../kernel/FFF.Native/3FP/Core/PlayerSession.cpp) 里静图倒带（`DoSeek` 对静图是刻意 no-op，不补就会打开失败）；
   `DecodeInitialFrame` [:2787](../kernel/FFF.Native/3FP/Core/PlayerSession.cpp) 缓存那一帧的包（新成员 `stillImagePacket_`），
   回退后 `avcodec_flush_buffers` + 重投 + drain [:2805](../kernel/FFF.Native/3FP/Core/PlayerSession.cpp)。
   因为 `image2`/`*_pipe` 没有时间轴，包一旦被硬解吃掉就无法重读。

ABI/头文件对外契约未动（无新导出、无结构体增字段；`PlayerSession.h` 只加了一个私有成员）。

## 3 现在的行为

| 格式 | 静图硬解 | 通路 | 依据 |
|---|---|---|---|
| HEIC | **是** | `hevc` + D3D11VA | 两卡 `mode=Gpu` 且 `max\|d\|=0.000000` |
| AVIF（8bit / 10bit PQ） | **是** | `av1` + D3D11VA | 同上，含 PQ 10bit |
| JPEG/MJPEG | **否**（留 CPU） | 唯一硬件后端是 CUDA，呈现缺陷挡路 | `-h decoder=mjpeg` 的 Supported hardware devices 只列 `cuda` |
| PNG / WebP / GIF / TIFF / JXL / JXR / BMP | **否** | FFmpeg 无硬件通路 | 打开期即在建设备之前被拒，代价实测 ≈0 |

尺寸收益（交错两臂中位数，同一 DLL）：**≥8K 赚 30–150ms**（四次独立读数 −148.7/−61.5/−33.6/−30.6ms），
普通尺寸付 0–60ms。定形后静图不再下载（纹理直接呈现），所以这笔代价纯粹是**每次开图付一次硬件解码器建立**
（后端探测 + decoder/GUID 枚举 + 表面池），一帧图摊薄不掉；图越大越划算，拐点在本机约 8K。

## 5 本轮定位到、但没修的缺陷（下一手的入口）

**渲染器/着色器把"从 GPU 下载到 CPU 的半平面帧（NV12/P010）"呈现错了。** 因果链（证据包 §6）：

1. 外部真值：`ffmpeg -hwaccel d3d11va … -vf hwdownload,format=nv12` 与软解对同一 HEIC 取中心均色**完全相同 (244,245,225)** ⇒ 硬解与下载都没错。
2. 内核里两臂各落盘一帧（`av_image_copy_to_buffer`）逐平面比：**Y/U/V max diff 全 0**；
   `cs/rng/prf/trc/chroma_site/sar/ICC/nb_side_data` 全同。唯一差别是 `yuv420p`(3 平面) vs `nv12`(2 平面)。
3. 呈现却 mean≈0.21、色调级偏差，且 **Intel 与 NVIDIA 的差值小数点后四位一致** ⇒ 不是硬件差异、不是时序。
4. 把静图改成直接用 D3D11 纹理呈现后，先前错的 4 张全部 `max|d|=0.000000`；
   只有 JPEG 仍错——它只能走 CUDA，而 CUDA 帧必须下载成半平面内存。

⇒ 静图这条只是把该缺陷变成常态可达；**视频走 CUDA 后端时同样会踩**，这条要单独判一次（本轮未判）。
修好它之后：删掉 §2-2 的 `staticImage_ ? 1u : …` 限制，JPEG 才有硬解可言，并复跑同一逐位等价判据。

## 7 已知回归（已测量）与未测项

- **`GetImageInfo` 把硬件像素格式当源格式报出**（本轮改动引入，**未修**，判据 `probe-pixfmt-regression.txt`）：
  `BuildImageInfo` [:4165](../kernel/FFF.Native/3FP/Core/PlayerSession.cpp) 优先取 `frame->format`，
  而静图现在保留的是 D3D11 帧，于是
  `01d_heic`：cpu 臂 `srcpixfmt=0 (yuv420p) bitdepth=8` → gpu 臂 **`srcpixfmt=171 (D3D11) bitdepth=8`**；
  `04_pq_10bit.avif`：cpu 臂 `srcpixfmt=62 (yuv420p10le) bitdepth=10` → gpu 臂 **`srcpixfmt=171` 且 `bitdepth=8`**
  —— **10bit 源被报成 8bit**，比格式号错更危险（宿主会据此判 scRGB/位深链）。
  PNG / JPEG（无硬解通路）两臂同值 `26` / `12`，未受影响。
  修法方向：硬件帧时回落到 `parameters->format`（或映射回等价软件格式），注意 :4163-4164 那条注释说的
  "不能读已被重置的 format"是另一头的约束，改完要用同一判据回归两臂同值。

- 渲染器半平面呈现缺陷**未修**；CUDA 后端在视频上是否同样错色——未判。
- Intel 上 `16384x8192`（134MP）静图：GPU 拒包后的重试路径 `open=0`（NVIDIA 同张能回退成功），未定位。
- HEIC 的 4:4:4 / 单色 / 带 irot 旋转样本；带 ICC 的 HEIC/AVIF 在硬解下的呈现（本轮采样文件 ICC side data 均为 0）。
- 应用级 `--selftest` 未跑（见 §9 归因问题）。
- `DoSelectStream` [:4480](../kernel/FFF.Native/3FP/Core/PlayerSession.cpp) 仍不看尺寸也不看 `staticImage_`；
  撤掉分档后它与 `DoOpen` 条件重新同源，剩下的问题是切流后 `stillImageFrame_` 不刷新 ⇒ 读数翻成 Gpu 而显示像素仍是旧帧。独立欠账。
- C# 宿主把 `DeviceChanged` 当"显卡/显示器变更"处理并设 `surface.ErrorText = "…请右键该路重试"`
  （`src/3FCompare/Services/PlaybackCoordinator.cs:972-985`）。本改动让事件数**只减不增**
  （改前每张静图都发一条，现在硬解成功就不发），但"解码回退"与"显卡变更"共用一个事件本身是欠账。

## 11.1 §5 半平面呈现缺陷 —— 已修（根因在一行算术，不是着色器）

第一轮 §10 猜的入口（`DescribeInput` / 着色器取样）**全部排除**。真正的根因在上传这一步：

```
3fp/kernel/FFF.Native/3FP/Render/VideoRenderer.cpp:5898-5912   (PlayerVideoRenderer::Render)
修复前: rowBytes = ceil(W >> xShift) * (bitDepth > 8 ? 2 : 1)          <- 缺"每 texel 分量数"
修复后: rowBytes = ceil(W >> xShift) * samplesPerTexel * (bitDepth > 8 ? 2 : 1)
        samplesPerTexel = (input.layout == 2 && plane != 0) ? 2u : 1u
```

- 半平面 chroma 的目标纹理是 `DXGI_FORMAT_R8G8_UNORM` / `R16G16_UNORM`（`:3421-3422`），**每 texel 2 个分量**；
  平面格式与 luma 是 `R8_UNORM` / `R16_UNORM`，每 texel 1 个分量 ⇒ 老表达式只对平面格式碰巧成立，这是它被长期漏掉的原因。
- 缺这个 2 ⇒ **每行只拷一半字节**，剩下的是新建纹理的零页 ⇒ 源图右半画面 chroma 读成 (U=0, V=0) ⇒ 强绿偏色。
- 这解释了第一轮全部现象，一条不剩：
  - **尺寸二分**：`>= 3840x2160` 走 `:5886-5889` 的 `UpdateSubresource`（用真实 `linesize`），天然躲过 ⇒ 第一轮"8K/4K 对、720p 错"不是内容差异而是开关差异；
  - **两卡差值小数点后 4–6 位一致**：未写的字节是零页，与厂商无关；
  - **改成 D3D11 直呈即愈**：那条路只有一次 `CopySubresourceRegion`，不进这段；
  - **只有 JPEG/CUDA 不愈**：只有它会先 `av_hwframe_transfer_data` 成 CPU 半平面帧。

⚠ **更正第一轮台账**：`_3fc_tmp/hw-image-analysis/00-合并结论.md:300` 说"先前错的 4 个"。按同一批原始读数
（`diag-sidedata.txt:19-24`、`diag-linesize.txt:15-18`、`probe-localize.txt:15-22`），8K HEVC 与 4K AVIF 一直是
`max|d|=0.000000`，**真正错的只有 2 个**（720p HEIC、1080p10 AVIF，都是小尺寸）。这个更正把"按内容"改成"按 4K 阈值二分"，
缺陷行因此被唯一定位。

**没动**：着色器 / `SdrShaderBytecode.h` / `EnsurePipeline` 的纹理几何（它们都对，被 ≥4K 样本的 `max|d|=0` 证明）。

## 11.3 §7 `GetImageInfo` 源格式/位深回归 —— 已修

`BuildImageInfo`（`PlayerSession.cpp:4134` 起）把"硬件帧的 format"和"已被 `av_frame_unref` 重置的 format"
同等对待，一起落进既有的 `parameters->format` 兜底链，末级再兜 `AVHWFramesContext::sw_format`。
顺手把位深那两行的判据与同文件 `:563-566` 的 `PixelFormatBitDepth()` 对齐（补 `descriptor->nb_components > 0`）。

为什么这么修而不是"映射回等价软件格式"：硬件 pixel format 的 descriptor **没有分量**（`nb_components == 0`），
所以 `comp[0].depth` 覆盖不生效，位深退化到 `bits_per_raw_sample ? … : 8` —— 这就是 10bit 被报成 8bit 的算术来源。
而 `parameters->format` 由 `avformat_find_stream_info` 用**软件**解码器填 ⇒ **与解码路径无关，天然满足"两臂同值"判据**。

## 14.1 §13 的 AVIF 条纹 —— 根因与修法（已修，两卡复验）

根因**在两条呈现路的色度位置约定不一致**，不在解码、也不在 §11.1 那条 `rowBytes`：
`VideoRenderer.cpp:6039-6041` 对 **d3d11 帧**把 `AVCHROMA_LOC_UNSPECIFIED` 替换成 `AVCHROMA_LOC_LEFT`
再喂 `ResolveChromaOffset`，而 CPU 平面路不替换 ⇒ 两臂差半个色度 texel 的水平位移（§13.3 的竖直条纹正是它的形状）。

修法取"让静图回到平面路"而不是"动纹理路的替换规则"：
`PlayerSession.cpp` 的硬件帧下载条件恢复为
`frame->format != AV_PIX_FMT_D3D11 || (staticImage_ && owner == format_)`。
理由：平面路是图片一直以来的基准，且它已被 §11.1 修好（MJPEG 视频两卡 `max|d|=0`）；
改动替换规则会波及**所有**硬件解码视频的色度对齐，风险面大得多，且"哪个才是对的"本轮无判据。
代价：静图每次多一次 GPU→CPU 拷贝（实测 1.6–6.4ms，8K 60.9ms），换来硬解仍在工作。

复验（`--pixels 200`，reps=1）：**两卡 8/8 全 `max|d|=0.000000`**，含原本条纹的三个夹具
（`s_640x480`、`a_960x540`、`a_1280x720`）；`mode=Gpu` 6 行、`xfer` 非零 ⇒ 仍在硬解。

## 14.2 新查出并修掉的一条元数据回归（§11.3 只修了一半）

改回平面路后，下载出的帧是 **NV12/P010**，而 `BuildImageInfo` 以"帧的格式"优先 ⇒ 同一张图
CPU 臂报 `0`、硬解臂报 `23`（实测 8K HEVC，两卡一致；像素仍 `0.000`）。
即：**10 bit 被报成 10 bit（对），但格式号按解码路线漂移**，§11.3 只挡了 `AV_PIX_FMT_D3D11` 这一种。

修法：`PlanarEquivalent()`（`PlayerSession.cpp` 匿名命名空间，紧邻 `IsHardwareFrame`）

## 14.4 Intel 大图：两条账分开

- **108MP（12000x9000）单臂失败**：`--reps 4` 让两臂次序交替后，失败从 Gpu 臂翻到 **CPU 臂**，两臂 `mode` 又都是 `Cpu`

- **134MP（16384x8192）**：Gpu 配置臂 **4/4 稳定失败**、CPU 配置臂稳定成功 ⇒ 与上面不是同一个病，
  是"试过硬解并回退之后"留下的状态让 CPU 重解呈现不出来。诊断读数（临时插桩，已删）：
  `still retry: result=0 now=0` ⇒ `DecodePacket` 返回成功但**一帧都没出**，于是末尾
