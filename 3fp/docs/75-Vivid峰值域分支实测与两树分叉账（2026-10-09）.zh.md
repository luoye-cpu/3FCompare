## 三、机制事实：HEVC 里 SEI type **4** 才是 registered T.35，**5** 是 x265 信息串（与 H.264 相反）

`laneC-vivid/vivid-sei-hexdump.txt` 对源样本的 NAL 清点：

```
NAL@87   nal_type=39 sei_payload_type=144 size=4      ← Content light level
NAL@101  nal_type=39 sei_payload_type=137 size=24     ← Mastering display
NAL@135  nal_type=39 sei_payload_type=5   size=2169   ← x265 编码器信息串（NOT Vivid）
NAL@2321 nal_type=39 sei_payload_type=4   size=47     ← CUVA T.35，ffprobe/内核真正当 Vivid 解析的唯一一条
```

**HEVC (H.265) Annex E.3.2：payload type 4 = `user_data_registered_itu_t_t35`，type 5 = `user_data_unregistered` —— 与 H.264 的对应关系相反。**
该判别**不是靠读规范下的结论，而是靠「删消息看 ffprobe 的 Vivid 掉不掉」的实验立住的**（副产物 `drop4.hevc` / `drop5.hevc` / `drop45.hevc` 在同目录）。lane C 自述「我一度搞反，再用删除-判别法纠正」—— 本账把它作为**结论级机制事实**登记，因为传染成本很高：任何按 H.264 直觉写 SEI 抽取代码的人都会去解析那条 2169 B 的非 Vivid 消息。

47 B T.35 载荷的字段布局（同日志）：`header bytes 0..5 = 26 00 04 00 05 | 01`（`system_start_code=1`）；stats 在 bit 48（bytes 6..11）`minimum=0 average=3046 variance=1535 maximum=4095`；**`maximum_maxrgb` 占 bits 84..95** = byte10 低半字节（`0xF`）+ byte11（`0xFF`）。

### 4.2 机制（本轮实读两树同一函数）
