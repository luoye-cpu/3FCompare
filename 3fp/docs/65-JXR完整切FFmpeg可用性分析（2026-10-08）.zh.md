# 65 · JXR 管线完整切 FFmpeg：可用性完整分析（2026-10-08）

> 触发：用户「我希望给 JXR 管线完整切 FFmpeg 上，完整分析可用性」
> 关联：`3fp/docs/15`（可行性）、`3fp/docs/16`（满血方案）、`3fp/docs/64`（根因定案）、`3fp/docs/62`（产物差异）
> 结论：**解码层已通（4/5 全链路可解），但"完整切 FFmpeg"在语义层仍有 2 个真实缺口** ——
> ① **HDR 数值范围被整数化截断**（实测 2.8%–10.7% 像素饱和）；② **颜色标签全 unknown ⇒ 内核按 SDR 处理 HDR JXR**。
> 这两条**不是** FFmpeg 的问题，是**内核像素管线**的问题，需要内核改动才能"完整"。

---

## 一、结论先行

### 1.1 分层可用性总表

| # | 层 | 状态 | 证据 |
|---|---|---|---|
| L1 | FFmpeg 依赖（`libjxr` 编入） | ✅ **已就绪** | `-decoders` 有 `V....D libjxr  JPEG XR via jxrlib (codec jpegxr)` |
| L2 | 解码器 GUID 映射 | ✅ **已修复** | 4 个真实样本全链路可解（旧 `runtime/` 版全失败，见 `docs/64`） |
| L3 | 宿主图片白名单 `.jxr/.wdp/.hdp` | ✅ **已放开** | `播放列表.vb:32,38`（`docs/16 §3.1` 已完成） |
| L4 | 内核 still-image 路由 | ✅ **正确** | `image2` demuxer 被识别为 static image，走单帧呈现 |
| L5 | 内核像素格式转换 | ⚠️ **能跑但截断** | `rgbaf16le` → `RGBA64LE`，**实测饱和 2.8–10.7%** |

| L7 | 文件关联（双击即看） | ❌ **未加** | `文件关联管理器.vb` 81 项无 `.jxr`（`docs/16 §3.2` **有意留待**） |

### 1.2 一句话结论

> **"切 FFmpeg"这件事本身已经成立且成本极低（换 DLL，零代码）。**
> 但用户要的"**完整**"若包含"HDR JXR 正确呈现"，则需要**内核像素管线改动** ——
> 因为 JXR 的 HDR 内容是 **16-bit float 全域值**（实测最高 **53.9×**、最低 **−1.22**），
> 而内核把它当 **整数 SDR** 处理，既**截断**又**误判色域**。

## 二、L5 关键新发现：HDR 数值范围被整数化截断（**本次最重要**）

### 2.1 实测数据（`_3fc_tmp/jxr_range.cpp`，直接调 FFmpeg API 读原始 float）

4 个真实样本的 `rgbaf16le` 原始值域与经内核转换后的饱和情况：

| 样本 | 分辨率 | float min | float max | >1.0 的通道数 | <0.0 的通道数 | **转换后饱和像素占比** |
|---|---|---|---|---|---|---|
| `FH4-HDR.jxr` | 3840×2160 | 0.000 | **4.559** | 2,088,981 | 0 | **2.79%** |
| `DHR-CoJ1002.jxr` | 3840×2160 | **−1.225** | **53.938** | 3,527,975 | 549,104 | **4.76%** |
| `fh2_fp16.jxr` | 1616×909 | −0.062 | **58.094** | 757,570 | 353 | **5.73%** |
| `HDColorHDRCalibration.jxr` | 320×240 | −0.121 | **17.734** | 47,023 | 106 | **10.73%** |

（"饱和" = 转换后达到 `65535` 上限的通道数占比）

### 2.2 机制（代码证据）

`VideoRenderer.cpp:5103-5145`：
```
input = DescribeInput(frame->format)        // rgbaf16le 不在表内 -> 返回 {}（layout=0）
const auto directYuv = input.layout != 0;   // false -> 走 CPU 转换
input.bitDepth = max(8, sourceDescriptor->comp[0].depth);   // rgbaf16le -> 16
const auto convertedFormat = input.bitDepth <= 8 ? AV_PIX_FMT_BGRA : AV_PIX_FMT_RGBA64LE;
//                                                            ^^^^^^^^^^^^^^^^^^^^^^^^ 整数！
sws_scale(...)   // 浮点 -> 16bit 整数，>1.0 与 <0.0 全部 clamp
```

- `DescribeInput`（`:1091-1137`）**只覆盖 YUV** 平面/半平面格式，RGB 一律落 `default: return {}`。
- 于是 RGB 帧被迫走 `sws_scale` CPU 转换到 **整数** `RGBA64LE`。
- **`RGBA64LE` 是无符号 16bit 整数 → 无法表达 >1.0（超白/HDR）与 <0.0（负值）** ⇒ 截断。

### 2.3 为什么这很重要

JXR 是**唯一**用 `rgbaf16le` 携带真实 HDR 范围的格式之一（Windows HDR 校准图、`FH4-HDR` 等）。
`DHR-CoJ1002.jxr` 同时含**负值**（549,104 个通道 <0）与**53.9× 超高值** —— 这是**场景参考的宽动态范围数据**，
不是"RGB 是 0..1 的普通图片"。整数化会：
- **高光削平**（>1.0 全变 65535）→ 高光细节丢失
- **负值抬到 0** → 超出色域的颜色信息丢失

⇒ **"能解出来" ≠ "解对了"。** 这是"完整可用"的核心缺口。

## 三、L6：HDR/广色域语义未覆盖

### 3.1 实测

| 样本 | `color_transfer` / `color_primaries` | 内核 `hdrFormat` | `outBits` |
|---|---|---|---|
| 全部 4 个 JXR | **unknown / unknown** | **0（SDR）** | **10** |

`docs/16 §6` 步骤 5 的期望是「HDR JXR ⇒ `outBits=16`(scRGB)」，**实测为 10 且 `hdrFormat=0`** ⇒ **未达成**。

### 3.2 原因（两层，都要注意）

1. **上游标签缺失**：`libjxr` 解出的帧**不填** `color_trc`/`color_primaries`（全 `unknown`）。
   内核的 HDR 分类（`HdrProcessor::ConfigureStream:182-192`）与 `ResolveSourceGamut`（`:262-264`）
   **都依赖这些标签** ⇒ 只能判为 SDR/709。
2. **`outBits=10` 的来源**：非 scRGB 路径下的常规输出位深，与 JXR 的 16bit 源无关。

⇒ 即使修好 L5 的截断，**仍需**为 JXR 建立"无标签时的合理默认"（例如按 `rgbaf16le` 推断为
线性/宽色域），否则 HDR JXR 仍按 SDR 呈现。

> ⚠ **注意 `docs/16` 步骤 5 的期望值可能本身就偏乐观**：它假设内核能识别 HDR JXR，
> 但上游不给标签这一事实**当时未被验证**。本报告实测推翻了该期望的前提。

## 五、"完整切 FFmpeg"的可行性分级

| 目标 | 需要做什么 | 成本 | 可行性 |
|---|---|---|---|
| **A. 能打开/呈现 JXR** | 换 `publish` 版 DLL 到 `runtime/` | **极低，零代码** | ✅ **已达** |
| **B. 双击即看** | A + 文件关联加 3 个扩展名 | 低（纯 VB 清单） | ✅ 可达 |
| **C. HDR 范围不截断** | B + **内核 RGB 浮点通路**（见 §5.1） | **中高，需改内核** | ⚠️ 需设计 |
| **D. HDR 语义正确** | C + **无标签时的色域/传递推断** | **高，需规范决策** | ⚠️ 需设计 |

### 5.1 C 的两个可选实现方向（**未实施，供决策**）

| 方向 | 做法 | 评价 |
|---|---|---|
| **C1. 加浮点通路** | `DescribeInput` 支持 `rgbaf16le`（新增 layout），
上传 `R16G16B16A16_FLOAT` 纹理（内核已有该 DXGI 格式与 scRGB 链路） | **最正确**。内核**已有** FP16 scRGB 呈现链路（`:2628/2723/5457` 等），
复用而非新建；但需扩 `DescribeInput` + 上传分支 + 着色器 layout 约定 |
| **C2. 保留整数但先归一** | 转换前按帧最大值做一次归一化缩放，保留相对动态 | 便宜但**有损且引入逐帧状态**，且负值/超白仍无处安放 —— **不推荐** |

> **[INFERRED·中]** C1 与内核既有架构**相容**：`InputLayout` 已是多态（`shader` 里 `InputLayout==0` 走 RGB 分支，
> `:633/650/680`），FP16 纹理路径也已存在。主要工作量在 **`DescribeInput` 表扩展 + 上传分支 + 着色器 layout 值分配**，
> 而非新建渲染管线。

### 5.2 D 的关键未知

**[UNKNOWN]** JXR 的 `rgbaf16le` 在**无标准标签**时，其数值应对应哪个传递函数/色域？
需查 JPEG XR / WDP 规范对 float 像素的解释（是否恒为 **scRGB 线性**）。
Windows 的 JXR（`HDPhoto`/HDR 校准图）惯例是 **scRGB（线性、sRGB 原色、1.0=80nits 或全域）**，
但**本报告未取得规范原文**，不应据此直接实现。
