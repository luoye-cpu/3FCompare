### T2（P0）两笔未归因的大数——归因优先于修复

**这是本规划唯一的技术 P0**，因为 T3 的修法取决于它。

- **矛盾读数（必须由实验消解，不许挑一个信）**：
  - A 案：4K APNG 整进程 **70.8ms CPU/帧**（3 次 85.1/86.5/87.0 % 单核）而 `decode_profile` 只能归因 **5.97ms/帧** ⇒ 缺口 **≈65ms/帧**，占总分量 9 倍。
  - B 案：回绕后 **40.8ms** 内快照队列深度就到 **8**（`pB_apng_4k.txt` 第 5 行起 8→7→6…递减）⇒ 解码一帧至多 ≈5ms，**与 A 案的 70ms 直接冲突**。
  - 我上一轮把"接缝=暴露的解码成本"写成机制，B 案一票把它降级为**假设**。T2 的存在理由就是这个。
- **最小改法（不动内核，只用现成计数器）**：`loop_stutter_probe` 增加**逐秒增量表**，打印 API 已有的累计计数：`decodedVideoFrames / presentedVideoFrames / droppedVideoFrames / queuedVideoFrames / coalescedVideoFrames / swapChainPresents / presentWait100ns / softwareConvert100ns / hardwareTransfer100ns`（`FFF.Player.Api.h:192-195, 219-225`；仅 `DoClose` 复位，`PlayerSession.cpp:4462-4471`）。每帧 65ms 的缺口一旦落到 `softwareConvert100ns` 或 `presentWait100ns` 上，机制就自己报出来了。
  - 若计数器分不完，第二票才动内核：在 `PresentVideoFrame`/`Render` 两端加一个 `perf_counter` 段并按 1s 汇总（这一改会动出货件，须先点头）。
- **判据**：归因报告必须把 4K 那 70.8ms/帧 拆到**逐项相加≈70.8±10%**，每项指到日志行；拆不出来的部分显式写"未归因 X ms"。**禁止用"PNG 解压很慢"这类未量的话填坑**。
- **附带一条内存账**：4K 私有内存 670MB，而声明的解码队列预算是 **128MB**（`PlayerSession.cpp:50`），按 `VideoFrameQueueLimit`（`:114-119`）33.2MB/帧应夹到 **3 帧**，实测却是 **8 帧**。归因方法（不用改内核）：造 RGBA / YUV 两种像素的等尺寸动图各跑 30s，看私有内存随 `bytesPerFrame` 的斜率——斜率≈队列深度 ⇒ 预算未生效；斜率≈0 ⇒ 670MB 在队列之外。

### T3（P1）高分辨率回绕接缝（4K 每轮 +81ms，肉眼可辨）

- **前置**：T2 归因结论落地后才开这张片。**机制未定时不许改**（否则就是把 §12 的"宁可红着"变成猜）。
- **候选（按爆炸半径从小到大）**：
  1. `DoSeek` 增加一个仅供 wrap 使用的 `keepQueue` 变体：只 `ResetClock(0)` + 重定位 demuxer，不清 `videoFrameQueue_`（`PlayerSession.cpp:4244` 是清队列那一行）。
  2. EOF 时**先预取下一轮首帧**再 `DoSeek(0)`，把关键路径上的那一次解码挪到空闲窗里。
  3. 让 APNG/AVIF/HEIC 也走 demuxer 自回绕（WebP 今天就是这条，实测接缝 0）——**先复现再改**：`docs/14` §3 定案是 apng demuxer 每轮吐一个 `send=-22` 的标记包丢一帧，而本机链的是 LIBAVFORMAT 63 / 10-07 的 FFmpeg，**当年结论不能直接当作今天的依据**，先用 `3fp/build/apng_seek_repro.exe`（145,920 B，standalone）在新件上复跑一次，看还有没有 `-22`。
- **公共约束**：`RebuildMediaInfo()` 今天每轮回绕都跑一次（`:4193`，全量 JSON 重建）；任何方案都要回答"这一笔留不留"。
- **判据（可执行、且要求先红）**：4K APNG `长停 12/12 → 0`；`回绕帧均值 − 稳态帧均值 ≤ +5ms`；640 五格式与 GIF 1080p **零回归**（§2 表逐格比，两份日志并档）；`verify_all_samples.sh` 不新增失败。

### T4（P0，与 T2 同批）判据要有牙：探针加 PASS/FAIL token 与真实退出码【已完成 2026-10-10，见 docs/81 O4】

- **现状【读】**：`loop_stutter_probe` 是纯测量工具，**没有 exit code、没有 PASS/FAIL token**（源码只有 printf；`verify_image_mode.cpp:356-357` 才有 `LOOP RESULT: PASS|FAIL`，且**永远返回 0**）。⇒ 接进任何门禁都只能"看人读日志"，SKIP/无输出都会蒙过去。
- **改法**：给 `loop_stutter_probe` 加阈值判定与退出码——`长停次数 > 0` 或 `接缝 Δ > 25ms`（25ms 沿用 `docs/14` §2.2 已定的判据）或 `dropped+coalesced > 0` 或 `PlaybackEnded=yes` ⇒ 打 `SEAM RESULT: FAIL` 并 `return 1`。加一个 `LSP_MAX_SEAM_MS` 环境变量按分辨率调档（4K 与 640 用同一阈值会永远红）。
- **判据**：**在当前未修复的 DLL 上，4K APNG 必须判红**（现状 12/12 长停是现成的红源），640 五档必须判绿；两者都要留日志。`echo $?` 必须能区分 0/1（现在两条命令都是 exit 0）。
- **成本**：单文件 ~30 行，`py 3fp/tools/build_probe.py loop_stutter_probe` 重编即可（脚本按 `__file__` 定位，仓库根或任意 cwd 都能跑）。
- **构建链已实跑一次【实测】**：`build_probe.py` 用 MSVC 14.51.36231 / SDK 10.0.28000 编出 189,440 B，新件对 `07b_anim.gif` 6s 读数与旧件同量（均值 100.11ms、长停 0、丢帧 0、6s 内 5 次回绕，`anim-perf/rebuild_smoke.txt`）；两文件 md5 不同（重编所致），旧件留了回滚副本 `anim-perf/loop_stutter_probe.exe.bak_10-09`。改内核结构后探针必须一并重编——`FFF3FPConfiguration` 尺寸一变就是 `Create 失败`（`rebuild_probes.ps1:1-8`）。
