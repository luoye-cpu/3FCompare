### 4.1 ⚠️ 一次踩坑（必须记录）

第一版我用"正则把所有冲突块统一取上游"，结果**丢掉了 6 个我的函数**
（`SetViewRotation`/`ViewRotation`/`SetVideoSuperResolution`/`RequestedVideoSuperResolution`/
`VideoSuperResolutionActive`/`FillVideoSuperResolutionStatus`）。

发现后立即改为**逐块判定**，并写了显式的策略脚本（`build/resolve_conflicts.py`）：
**每个块都必须被打印出判定依据**，禁止一刀切。

> 教训：**冲突解决不能用"整体取一边"**。生成物可以（它有唯一真源），源码不行。

### 4.2 真正的代码集成（不只是文本冲突）

`VideoRenderer.cpp` 的 `PrepareScaledVideo` 是**双方都改写的函数**：

- **上游**引入了 `reconstructed` 扩展层通路：`layout` + `inputViews`
- **我**把它改成用 `effectiveSourceViews_` 做 VSR 源

⇒ 合并后必须**两者共存**：

```cpp
const bool reconstructed = extensionReconstructed_ && actualMode_ != FFF3FPColorMode::RawHdrAsSdr;
const auto layout = reconstructed ? 1u : sourceInputLayout_;
auto* inputViews = reconstructed ? extensionReconstructedViews_ : effectiveSourceViews_;
// VSR 只作用于普通解码面，扩展层重建面不走 VSR
const auto superResolutionPlane =
    !reconstructed && superResolutionActive && superResolutionViews_[plane] != nullptr;
```

首次构建报 `C2065: "layout" 未声明的标识符` —— 正是这个集成没做对，修好后通过。

## 7. ⚠️ `--color-regression` 失败：**已复核为取证假象**（详见 `docs/39`）

> **本节结论已被 `docs/39` 推翻并细化**：该失败源于**跑在陈旧二进制上的、上游已删除的旧测试**，
> 不是缺陷，且受影响代码路径在本机**不可达**。以下保留当时的推导过程。

失败信息：

```
测试失败：HDR 源没有采用 MaxCLL 1242 nit：1000。
```

**归因证据（决定性）**：

1. 该断言考的是**色调映射的 sourcePeak / MaxCLL 取值**。
2. 我的改动只涉及 **VSR（缩放）、旋转（采样/几何）、旋转 UI** —— **都不碰 sourcePeak/MaxCLL**。
3. **`HdrProcessor.cpp` 在合并结果里与上游逐字节相同**（`git diff upstream/master HEAD` 为空）⇒ **我没改过它**。
4. **上游确实改了这一块**：`5881872`（2026/10/5-1）改动 `HdrProcessor.cpp`（+64）与
   `PlayerSession.cpp`（+414/-…），其中一处正是：

```diff
-    if (std::isfinite(sourcePeakNits) && sourcePeakNits > 0.0f)
+    if (active && std::isfinite(sourcePeakNits) && sourcePeakNits > 0.0f)
```

即上游把"外部扩展峰值处理"的生效条件**收紧为需要 `active`**，属 Dolby Vision 扩展层重构的一部分。

⇒ **结论：这是上游自身的行为变化（或回归），本次合并没有引入它。**
需要上游确认是有意收紧还是遗漏——**建议作为独立事项跟进，不要在本次合并里顺手改上游逻辑**。
