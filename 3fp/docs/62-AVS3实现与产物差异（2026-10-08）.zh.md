## 一、结论先行

### 1.1 一句话结论

**AVS3 与 JXR 在现有产物间结构性互斥，需产品决策。**

AVS3 可以在零代码改动下被内核选中，但代价是丢掉 JXR —— 本机全部 6 个可得的 FFmpeg 产物中，没有任何一个同时具备 `libjxr` 与 `libuavs3d`，且第三方预编译产物（BtbN）**任何变体**都不含 `libjxr`（附录 B.1）。因此「换 DLL 即得 AVS3」这条路径不能按现状推荐。

**本文结论为「能力验证」（capability verification）级别，不是「AVS3 已支持」。** 见 §1.2。

### 1.1.1 当前 JXR 的真实状态（不得含糊）

> **经 3FP 内核路径，现役 `runtime/` 下 5 个 JXR 样本（4 真实 + 1 自编码）目前 0/5 能成功打开。**

因此**任何文档都不得声称 3FP 当前可显示 JXR**。但「不能打开」的原因在两层是**不同性质**的（§4.3）：
- 现役产物：**能力在位**，受阻于解码器侧一个**已知的、原则上可修**的 GUID 映射缺陷（`docs/15`/`docs/16` 为可行性/规划文档，**并非已排期的修复承诺**）；
- BtbN 产物：**能力整体移除**，不更换构建则无法恢复。

### 1.2 ⚠️ 能力验证 vs 真实解码（必须首先明确）

> ### 「本任务未做真实 AVS3 码流解码，仅证明解码器已注册且可被内核选中」

**AVS3 的结论只有一句话，且仅为能力级：**

> **`avcodec_find_decoder(193)` 由 NULL → NON-NULL，且 `avcodec_find_decoder_by_name("libuavs3d")` 由 ABSENT → PRESENT。这是「能力验证」（capability verification），不是「AVS3 已支持」。**

本任务**降级为「能力验证」**。具体含义：

| 已验证（VERIFIED） | 未验证（NOT verified） |
|---|---|
| 隔离目录内 `avcodec_find_decoder(193)` 返回非空（NULL→NON-NULL） | **没有**解码过任何一帧真实 AVS3 码流 |
| 解码器名 `libuavs3d` 可被 `avcodec_find_decoder_by_name` 选中（ABSENT→PRESENT） | 未验证 AVS3 码流的画面正确性 / 色彩 / HDR 元数据 |
| 该查找路径与内核 `PlayerSession.cpp:2245` 完全相同 | 未验证 seek / 播放 / 音视频同步 / 硬件解码回退 |
| 现役 `runtime/` 内同一调用返回 NULL | 未验证长片稳定性、内存、崩溃率 |

**不得把本文读作「AVS3 已支持」。** 真实码流不可得的原因见 §6：FFmpeg 无 AVS3 编码器（无法自制），上游 FATE **根本没有 AVS3 测试**（`tests/fate/avs3.mak` 不存在），公开样本站点亦无 AVS3 目录。

### 1.3 三条可选路径（决策收敛）

| 方案 | 动作 | 得到 | 失去 | 成本 |
|---|---|---|---|---|
| **① 维持现状** | 不动 | JXR 解码器**能力在位**（受阻于已知、原则上可修的解码器侧 GUID 缺陷，见 §4.3；**非已排期承诺**） | 无 AVS3 | 0 |
| **② 换 BtbN LGPL** | 替换 FFmpeg 产物 | AVS3（**能力验证级**） | **JXR 解码器能力整体移除**（不换构建无法恢复）；另失 51 项组件（§2） | 低，但功能净损失 |
| **③ 自行构建 FFmpeg** | 同时 `--enable-libuavs3d --enable-libjxr` | 两者兼得 | — | **高**：需新建并长期维护构建流水线 |

**③ 无法通过换第三方预编译产物达成**（附录 B.1 已证：BtbN 全部变体都不含 jxr）。本机现役产物是**无仓内构建配方的第三方不透明产物**（Lead 已 grep 全仓 `enable-libuavs3d|enable-libjxr|dominic` → 零命中），故 ③ 意味着**从零建立并维护一条 FFmpeg 构建流水线**，成本远高于「换一个缓存 DLL」的设想。

**建议**：若 AVS3 非硬需求，选 ①；若 AVS3 是硬需求，必须走 ③，且需为 FFmpeg 构建流水线**单独立项**。**不建议 ②**（功能净损失 51 项 vs 新增 25 项，且含不可逆的 JXR 能力移除）。

### 2.6 一个必须记录的假阳性陷阱

`avcodec_find_decoder(192)`（AV_CODEC_ID_AVS2）在两套产物中**都返回非空**，但解析出的解码器名是 **`pgx`**（PGX / JPEG2000 Test Format），**不是 AVS2**。这是按 id 空间扫描时的错误命中。

> ⇒ **「`avcodec_find_decoder(id) != NULL` 就说明该 id 被支持」这一判据对 id 192 是不成立的。** 任何用该方法审计 AVS2 的结论都会得到**假阳性**。本任务对 id 193 的判定是用 name + long_name + 全量枚举三重确认的，不受此影响。

### 2.7 AVS2 不可达（补充结论）

`libdavs2` 在本机全部 6 个产物中**均不存在**（BtbN 显式 `--disable-libdavs2`）。**换产物只能得到 AVS3，得不到 AVS2。**

### 4.3 JXR 回归 —— 本任务最重要的功能影响

**必须分层表述，两层结论不同**（此点纠正「4/5 今天可用」的单一说法）：

**第一层 · FFmpeg CLI（各产物自带 ffmpeg.exe）**

| 采样 | 现役（有 libjxr） | BtbN（无 libjxr） |
|---|---|---|
| `fh2_fp16.jxr` | **OK** → 实际映射出 `Video: jpegxr (libjxr), rgbaf16le, 1616x909` | **FAIL** `Invalid data found` |
| `HDColorHDRCalibration.jxr` | **OK** → `rgbaf16le, 320x240` | **FAIL** |
| `12a_srgb_1920x1080.jxr` | FAIL（自编码，`jxrlib ... error=-1`，`docs/15` 已知） | **FAIL** |

⇒ 现役构建的 `libjxr` **确实能解出真实 JXR 帧**；BtbN **连打开都不能**（打开即败，因为没有解码器）。

**第二层 · 3FP 内核路径（`read_pixel_probe`，隔离目录）**

| 采样 | 现役 | BtbN |
|---|---|---|
| 全部 5 个 JXR | **FAIL** —— `Unsupported JPEG XR pixel format GUID` + `Could not find codec parameters for stream 0 (Video: jpegxr (libjxr), none): unspecified size` → open 超时 | **FAIL** —— 无任何解码器报错，仅 open 超时 |

⇒ **经内核，两层都是 0/5。** 现役在核内的失败是 `docs/15` 已记录的**内核侧 codecpar/unspecified-size 与 GUID 映射**问题，**不是解码器缺失**，且**早于并独立于本次换 DLL**。

**失败模式差异（关键 —— 这是本决策最重要的不对称）**：

| | 现役 | BtbN |
|---|---|---|
| 失败位于 | **解码器内部**（GUID 映射，诊断明确） | **打开阶段**（无解码器存在） |
| 能力状态 | **能力在位**，受阻于解码器侧一个**已知、原则上可修**的 GUID 映射缺陷 | **能力整体移除**，不更换构建则**无法恢复** |

**对本决策的意义**：这不削弱 JXR 损失结论，而是**重述**它 —— 换产物把「JXR 能力在位、只差一个已知且原则上可修的缺陷」变成「JXR 能力归零」。

**这是一个条件性（conditional）论证，不是修复承诺**：`docs/15`/`docs/16` 是**可行性分析与规划**文档，**不是已排期的修复**。因此准确表述是 —— 现役产物**保留**该能力且阻断点性质**在原则上可修**；BtbN 产物**移除**该能力。**若**该缺陷将来被修复，则 ① 之下的 JXR **有可能**恢复可用，而 ② 之下**不可能**（除非另换构建）。此不对称性**加强了对方案 ① 的偏好**。

> ⚠️ 不得据此文档声称「3FP 当前可显示 JXR」——**经内核路径现役亦为 0/5 成功**（§4.3 第二层），且本环境未能端到端复现 JXR 呈现（§4.1）。

### 4.4 「4/5 JXR 可用」的口径校准

Lead 的表格（以各产物自带 `ffmpeg.exe` 判定）经我独立复现：**在 FFmpeg CLI 层成立**。但该层成功不传递到内核层（§4.3 第二层）。统一口径应为：

> **「现役产物的 `libjxr` 在 FFmpeg CLI 层可成功解码 5 个样本中的 4 个」（`docs/15:5`：4 个真实样本 + 8 路自编码往返，但仅部分可用）；**经 3FP 内核路径，现役亦为 0/5 成功**，受阻于 `docs/15` 已记录的内核侧 GUID/`unspecified size` 问题。BtbN 产物在两层均 0/5，且原因是**无解码器**。**

以上口径已与 `docs/15` 交叉核对一致（Lead 独立确认：`docs/15:5` 结论摘要为「❌ 仍不能跑通」、`:50` 记录 `HDColorHDRCalibration.jxr` 报 `Unsupported JPEG XR pixel format GUID`、`:113` 记录**内核路径**同样报该错）。

真实视频样张（`testmedia/media/real/`）：**本会话未覆盖**。该目录 7 个样本合计约 1.8 GB（221 MB–553 MB 各一个），在剩余预算内全量打开+播放+seek 不可行。作为部分替代，HDR `.hevc` 小样本（§4.2）已做完整 open+play+像素读取，覆盖 HEVC 解码路径。**`real/` 全量矩阵是明确的未覆盖项**（§7）。

## 七、风险与未覆盖项

### 7.1 未覆盖（明确列出）

1. **真实 AVS3 码流解码** —— 无素材（§6）。**本任务最大的空白。**
2. **`testmedia/media/real/` 全量视频矩阵** —— 7 个样本约 1.8 GB，本会话预算内不可行；未做打开/播放/seek 全矩阵。
3. **seek 行为** —— 未覆盖（所有配置均只做了 open + 短时播放）。
4. **音视频同步 / 音频路径** —— 未覆盖。注意 §2.2 显示 BtbN 丢失 28 个音频解码器 + 11 个音频编码器；**本任务未验证音频回归**。
5. **硬件解码 / GPU 路径** —— 未覆盖。`_cuvid` 新增与 `vaapi` 差异未做实机验证。
6. **长时间稳定性 / 崩溃率 / 内存** —— 未覆盖。
7. **`astc`/`ktx` 容器** —— 仅确认组件消失（§2.2），未验证 3FP 是否对外承诺这两种格式（若承诺则直接影响用户）。
8. **`verify_image_mode.exe` 图像模式矩阵** —— 本环境不可用（§4.1），未能运行该工具的完整断言集。
9. **像素级回归** —— 有意不做（非确定性，§4.1）。

### 7.2 方法学风险

- **假绿风险（已规避 2 次）**：
  1. 首版矩阵脚本因数组/字符串比较语义把**完全相同的输出**判为 DIFF（虚假红）；改用 `TrimEnd` + 显式数组后修正。
  2. `verify_image_mode.exe` 的 `Create: -1` 会让任何基于它的矩阵**两边同样失败 ⇒ 全部 SAME ⇒ 虚假绿**。已识别并放弃该工具，改用 `read_pixel_probe`。
  > 两者均说明：**「两侧输出相同」必须先证明两侧都真的跑成功了**，否则只是「两侧以相同方式失败」。
- **`avcodec_find_decoder(id) != NULL` 判据不健全**（§2.6，id 192 → `pgx`）。审计 AVS 系必须用 name + long_name 复核。
- **component diff 用 descriptor 偏移读取**（`AVCodec` +0/+8/+16/+20）。偏移若随 FFmpeg 版本变化会误读；本任务用「已知组件名（png/hevc/mjpeg 等）出现在预期类别」做了合理性校验，且两套产物用同一脚本读取，**内部一致**，不影响双向 diff 结论。
- **hwaccels 结论**基于 DLL 字符串计数（`runtime/` 不随包 ffmpeg.exe）；属取证性证据，非 `av_hwdevice` 运行期枚举。

### 7.3 对决策的关键风险

1. **方案 ② 的功能净损失是确定的**（51 项丢失 vs 25 项新增），且包含 **JXR 解码器整体消失**这一不可逆项。
2. **AVS3 集成上游无测试**（§6.2）⇒ 采用 AVS3 等于引入一个未被上游回归覆盖的能力。
3. **方案 ③ 的成本被此前的「换缓存 DLL」设想严重低估**：需自建 FFmpeg 构建流水线（现役产物无仓内配方），且需同时满足 jxrlib + uavs3d 的许可与依赖。**建议单独立项。**
4. **AVS2 不可达**（§2.7）——若产品目标是「AVS 系全覆盖」，换产物达不到。

### 附录 B.1：为何第三方预编译产物无法同时提供两者（BtbN 构建系统取证）

- BtbN `scripts.d` 完整清单含 **`50-uavs3d.sh`**，但**不存在任何 jxr 脚本**（对完整清单检索 `jxr|jpegxr` → 零命中）。

- `variants/defaults-gpl.sh` 仅设置 `FF_CONFIGURE="--enable-gpl --enable-version3 --disable-debug"`，变体不增删组件。

⇒ **BtbN 全部变体（含 `gpl-shared`）都不含 `libjxr`。** 故「换 `gpl-shared` 即可两者兼得」**不成立**，方案 ③ 无法通过换 BtbN 资产达成。

> 置信度说明：`scripts.d` 无 jxr 脚本为 **VERIFIED**（完整清单检索）；「所有变体都得到 libuavs3d」为 **INFERRED**（由 `defaults-gpl.sh` + 变体命名推得；`variants/win64-gpl-shared.sh` 本体取回失败）。该推断不影响结论 —— 因为 jxr 在任何变体中都不存在。
