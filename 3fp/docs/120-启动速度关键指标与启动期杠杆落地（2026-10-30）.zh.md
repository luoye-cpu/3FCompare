## 二、本轮落地（宿主单侧，默认开启，环境开关可退出）

| 项 | 实现 | 开关 |
|---|---|---|
| 启动预取 | `MyApplication_Startup` 起 BelowNormal 后台线程，把 exe 目录（与 `AppContext.BaseDirectory`，去重）的 FFmpeg 六件 + libshaderc（合计 ~113 MB）顺序读进文件缓存。内核 +1.1s 才映射它们，此后映射即缓存命中。首跑收益≈0（解包刚写完，本就在缓存） | `FFF_NO_PREFETCH=1` |
| 启动期优先级 | `Startup` 拉到 `HIGH_PRIORITY_CLASS`；`Form1_Shown` 后 600 ms 由后台线程降回 `Normal`（T2 通常在 Shown 后 ~100 ms）。空闲机收益≈0，负载机把排队的启动时间抢回来 | `FFF_NO_STARTUP_PRIORITY=1` |

与内核 `PlacementPolicy` 的关系：内核播放期 Boost（`ABOVE_NORMAL`，`PlacementPolicy.cpp:581`）最早在播放泵启动后触发且恢复彼时基线；本处在它之前拉、之后降，互不踩踏。

**生命周期实测**：High@0.3s → 窗口@1.8s → Normal@2.6s（覆盖 T2）。

### 落地：后台预热设备（提交 `cc545d2`）

开关：`FFF_NO_GPU_WARMUP=1`。

## 八、Attach 细化拆解（第二轮打点，结论：**全部是一个 SetWindowPos**）

在 GPU 预热已落地的基础上，用 `a0..a7` 逐段打点（均已还原，LakeUI 仓干净）：

| 段 | 覆盖的代码 | 耗时 |
|---|---|---:|
| `a0_enter → a1_style` | 第一步透明度 + 第二步窗口样式 | 0 ms |
| `a1_style → a2_dwm` | 第三步 DWM 属性 | 0 ms |
| `a2_dwm → a3_reg` | 第四步拦截器 + `_forms(hWnd)` | 0 ms |
| `a3_reg → a3b_kbd` | `注册键盘过滤器()` | 0 ms |
| `a3b_kbd → a3c_preSetpos` | `SyncLock` + `_attachedForms` 赋值 | 0 ms |
| **`a3c_preSetpos → a4_setpos`** | **`SetWindowPos(..., SWP_FRAMECHANGED \| NOMOVE \| NOSIZE \| NOZORDER)`** | **234 ms** |
| `a4_setpos → a5_overlays` | `CreateChromeOverlays`（5 个 overlay） | 0 ms |
| `a5_overlays → a6_upd` | `RecalculateButtonBounds` + `更新窗口内边距` + `更新ChromeOverlays` | 0 ms |
| `a6_upd → a7_gpu` | 尾部 `请求GPU渲染(immediate)` | 16 ms |

**结论一（推翻旧猜测）**：`CreateChromeOverlays` 创建 5 个 overlay 只要 **≤16 ms**，它不是 282 ms 的主人。

**结论二**：那 282 ms 里 **234 ms 是单个 `SetWindowPos(SWP_FRAMECHANGED)`**。该标志强制
重算非客户区（`WM_NCCALCSIZE` + DWM 重排帧），而此时窗口**还没显示**——这笔钱很可能
花在了会反复重算的工作上。

### 下一步方案（待实测，未动）

候选：窗口不可见时省掉 `SWP_FRAMECHANGED`，改在首次 `VisibleChanged` 时补一次。
代价与风险：非客户区可能晚一帧到位，出现 chrome 闪烁；必须像素闸门 + 人工看截图。
预期上限：**−200~234 ms**。

### 实测结果：两条路都走不通（结论：234 ms 是固有成本）

**实验一：条件化推迟（不可见时省掉、`VisibleChanged` 补做）**
结果：Δ = **+12.2 ms（p=0.866）**，无任何收益。
原因（打点查明）：**`Form1_Load` 里 `targetForm.Visible` 已经是 True**，
条件分支一次都没走到“省掉”那一侧——那次 A/B 实际是“无改动 vs 无改动”。
顺带地：这个空改动测出来是 +12 ms，正好给我们一个噪声水位的参照。

**实验二：完全去掉这次 `SetWindowPos(SWP_FRAMECHANGED)`**
结果：Δ = **−26.4 ms（p=0.715）**，仍然无收益。
含义：那 234 ms **不是这个调用造成的**，而是“建立自定义边框窗口时必做的那次非客户区重算”
本身的时间；`SWP_FRAMECHANGED` 只是把它**提前触发**，去掉它这笔钱会落到首次显示时再付。
⇒ **这条不是可优化项，从候选表删除。** 真要拿掉它，得改窗口策略（例如换成
`WS_POPUP` 无边框窗口 + 完全自绘 chrome，不再触发自定义边框重算），那是架构级改动，
需单独的视觉/行为验收（伪最大化、任务栏交互、DWM 阴影都得重建）。

两个实验均已回退：LakeUI 仓工作树干净，`LakeUI.dll` 回到 2,375,168 B（与基线字节数一致）。

## 十二、O3-B（探测后台预载）实测：无收益，已回退

调研（`3fp/build/imgperf/o3b_analysis.md`）结论：O3-A 已把探测从“试载后卸载”变成“预载”
（`Form1.vb:109` 一行、UI 线程；`NativeLibrary.TryLoad` 七个模块并保留句柄），所以 O3-B
不需要再造预载，只需把这次预载从 UI 线程挪到启动早期；剩余上限 ≈ 36–41 ms（推断）。

实现：`Form1.启动期后台预载核心文件()` 在 `MyApplication_Startup` 最早处起后台线程算缺失集，
`Form1_Load` 改为 `核心文件预载完成.Wait(3000)` 取结果，失败/超时/开关关闭时回退到同步计算
（`FFF_NO_PROBE_PRELOAD=1`）。失败语义、文案、`Return` 位置逐字未动。

**实测（24 轮交替，fast 档 48/48，负载 73.5%）**：

| 臂 | T1 中位 | T2 中位 |
|---|---:|---:|
| base | 1,188.5 | 1,282.4 |
| o3b | 1,182.5 | 1,298.0 |

Δ(T2) = **+15.6 ms（U=270, p=0.711）**；逐轮配对中位 −15.3、均值 +23.5、**13/24**。
解读：七个模块的首映射是**固有成本**，只是从 UI 线程换到了另一条线程上与 UI 初始化抢 CPU
（当时负载 73.5%）；负载高时重叠反而变慢。**已回退，未提交。**

## 十四、P1 可行性调研（只读，未实施）

详见 `3fp/docs/121-P1会话提交提前-可行性与边界（2026-10-30）.zh.md`。关键结论：

1. 内核不设线程约束：`FFF3FP_*` 只是把命令塞进会话队列（`Enqueue`），真正干活在会话 worker；
   今天的会话创建已在 `Task.Run` 里，HWND 恒传 `IntPtr.Zero`，绑窗走 `SetOutputWindow` 且已在 worker 上。
2. **台账原改法（把“打开”提到 Load）几乎拿不到收益**：`打开Async` 的 enqueue 在 `Await Task.Run(...)`
   的续体里，续体回 UI，Open 仍要等消息泵（≈T1 之后）。只挪调用点 ≈ 3–6 ms。
3. 要兑现 −45~55 ms，必须把 `FFF3FP_Open` 的提交点搬进 worker 闭包（`播放器控制器.vb:1338-1342`
   附近 3 行）+ 宿主 3 处门控/去重；内核零改动。风险中（不碰视频、不给 Create 传 HWND、
   不用 `ConfigureAwait(False)` 三条红线任一放松即升高风险）。
4. 建议先花少量成本做一次纯打点，确认 `Load` 剩余是否 ≥ 60 ms（决定收益是 45–55 还是 10–20）。

## 十五、P1（Open 提交提前）实测：前提成立，但收益被“续体回 UI”吃掉，已回退

本节是对 §十四 的兑现与**否定**。§十四 第 4 点的“45–55 ms”估算偏乐观，实测后修正为
“上限 ≈ 32 ms”，并且这笔上限也没拿到。

### 15.1 前提验证：`Load` 剩余确实 ≥ 60 ms（结论：立）

临时以 `Console.Error.WriteLine("[LT] <tag> " & Environment.TickCount64)` 在三处插桩
（`Form1.vb` / `Core/播放器控制器.vb` / `Core/播放器会话.vb`），`arm_lt1` 臂 10 轮采集，
相对 `load_begin` 的中位偏移：

| 打点 | 偏移 | 段 |
|---|---:|---|
| `load_begin` | 0 | — |
| `post_probe` | 438 | 核心文件探测 |
| `trig_pt` | 532 | 控件 + 控制器树 |
| `renderer_started` | 626 | 呈现器 |
| `load_end` | 673 | 收尾 |
| `shown_begin` | 798 | Load → Shown |
| `sess_enqueued` | 829 | Shown 里跑 `打开外部文件` |
| `ctl_open_done` | 861 | **demux（worker）32 ms** |
| `ctl_bind` | 877 | 绑窗 16 ms |
| `ctl_opened_event` | 956 | **事件前 79 ms** |

关键读数是 **`load_end − trig_pt` = 141 ms（中位，最小 125）**，远超 60 ms 门槛，
所以“把 Open 提前”在窗口上是可行的。

### 15.2 真正的上限只有 32 ms（这是本次否定的一半原因）

上表把 Open 全链（`sess_enqueued → ctl_opened_event` = 140 ms）拆开后，**只有 32 ms 在 worker 上**：

- `enqueue → open_done` = 32 ms → 跑在会话 worker，**可隐藏**；
- `open_done → bind` = 16 ms → `重绑输出窗口()`，要 UI 线程和 `画面控件.输出窗口句柄`；
- `bind → opened_event` = 79 ms → 媒体信息/快照获取后 `RaiseEvent 媒体已打开`，处理器全在 UI 线程；
- `load_end → Shown` = 125 ms → 消息泵与首次布局，本就在关键路径上。

也就是说 §十四 把整段 140 ms 当成可隐藏量，实际可隐藏量是它的 23%。

### 15.3 实现（M1–M5）与第二个否定原因

按 §5 方案实现，全部 opt-in（`FFF_EARLY_OPEN=1`），内核零改动：

1. `播放器控制器.vb`：`创建会话` 与 `候选.打开Async(...)` 一起搬进 `Task.Run` 闭包，
   `Await` 放到外面；音量改在 UI 线程取快照再传值（不让 worker 读控制器的 `当前音量`）。
2. 控制器新增 `提前打开媒体 / 正在提前打开 / 放行延迟宿主事件` 与 `延迟宿主事件` 缓冲。
   必要性已验证：宿主的事件处理器挂在 `Form1.vb:218-257`，**晚于** `trig_pt`（149 行），
   提前打开期间触发的事件必须攒着，否则静默丢失。
3. `Form1.vb`：`trig_pt` 后调 `尝试启动期提前打开(...)`，白名单仅限静态单帧扩展名
   （排除 gif/apng/webp/avifs），开关不满足或路径不支持则静默退回原路径。
4. `ApplicationEvents.vb`：新增 `预览待处理启动文件()`（只读不清空），把原文件留给 Shown 去重。
5. `Form1_Shown`：先消费 `正在提前打开(请求文件)`，再 `放行延迟宿主事件()`，已被预打开的文件
   不再 `BeginInvoke(打开外部文件)`——否则命中“原位重开”分支把刚解码的帧重解一遍，收益归零。

单跑打点显示 M1 确实生效（`sess_enqueued` 从 `shown+31` 前移到 `trig_pt+32`），
**但 `ctl_open_done` 从 32 ms 膨胀到 297 ms**：`Await` 的续体要回 UI 线程，
而 UI 线程正被 `Load` 剩下的 141 ms 独占，续体只能排队。于是这笔“提前”被大量回吐：
`ctl_open_done` 最终只落在 `load_end+172`，而 baseline 是 `load_end+188`——
**只提前了 16 ms，而不是那 32 ms 上限，更不是 140 ms 全链**。

### 15.4 实测：零收益（20 轮配对，同一 exe 仅开关不同）

为排除臂间差异，A/B **用同一个 `arm_p1` 产物**，只靠 `FFF_EARLY_OPEN` 区分
（`quiet_ab.ps1` 为此新增 `-EnvA/-EnvB`）。20 轮交替、fast 档 40/40、负载 51.3%：

| 臂 | T1 中位 | T2 中位 |
|---|---:|---:|
| P1off | 955.5 | 1,048.7 |
| P1on | 962.5 | 1,067.7 |

Δ(T2) = **+19.0 ms（U=179, p=0.57）**；逐轮配对 **中位 +2.6 ms**、均值 +42.3、**10/20**。
配对差分布 −493 ~ +892 ms，说明窗口仍有噪声，但**中位贴着 0 且胜负对半**，
结合“上限 32 ms < 30 ms 分辨门槛”，结论是**无可测收益**，不是“测不出来所以保留”。

### 15.5 处置与教训

**已 `git checkout -- .` 回退，kernel 干净 @ `cc545d2`**；插桩、P1 代码、`预览待处理启动文件`
全部消失（`rg -c '\[LT\]'` 四文件均为 0，`git status --porcelain` 为空）。

两条可复用的判断：

1. **“`Load` 还剩多少”不是充分条件**。真正的判据是**关键路径上跑在 worker 上的那一段有多长**，
   而不是“Load 剩余窗口有多大”。本次窗口 141 ms，可隐藏段只有 32 ms。
2. **把活挪进一个已被 UI 线程占满的窗口，等于让它的续体排队**。只要 `Await` 之后还要回
   UI（必须回，红线 R4 禁止 `ConfigureAwait(False)`），提前提交就只是把耗时从左移到右，
   并发抢 CPU 时净效果为负。要让这类改动成立，前提是**整条链都不需要回 UI**，
   而本次 `bind` 与事件分发都在 UI 上，做不到。

剩下的可动目标已经很少：`load_end → Shown` 125 ms 与 `bind → opened_event` 79 ms 都在 UI 线程上，
要压只能改这两个处理器本身的工作量，而不是改它们的调度位置。
