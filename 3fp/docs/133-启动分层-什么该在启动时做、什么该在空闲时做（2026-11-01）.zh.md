# 133 · 启动分层：什么该在启动时做、什么该在空闲时做（2026-11-01）

## 〇、问题与结论

用户问：**"很多东西是不是没必要在启动时候一起自动？在启动后四五秒再进行是不是更合适一点"**

实测后的回答分三层：

1. **方向对，机制错。** "固定 4–5 秒后再做"不可验收（慢机器不够、快机器白等、用户可能 1 秒就点剪辑按钮）。正确的机制只有两种：**内容驱动**（首次用到才建）与**事件驱动**（状态变化时唤醒）。
2. **真正的常驻开销不在启动路径上。** 本轮用消融矩阵定位到：三台图层泵（字幕/弹幕/歌词）各占一条 PrecisionTimer 调度线程，调度线程设计为每刻度最后 0.5 ms 用 `SpinWait` 忙等精磨——**没有内容时也照样忙等**，合计 51 ms/s 常驻 CPU（占当时地板 66 ms/s 的 77%）。这既拖慢启动（线程 + JIT + 锁），也让播放器挂着不动时持续吃 CPU。已修（8eaa472）。
3. **看起来该延后的几项，实测都不是成本。** 光盘 1 Hz、解锁 1 Hz 的消融 Δ 均为正（无贡献）；文件关联"后台同步"在出货形态下延后仅 −21.4 ms 且 p=0.163（不显著）；SP 三项受 `SP_UnLock` 门控，普通用户直接 return。**延后它们只会增加状态机复杂度，没有收益。**

## 一、启动分层账（出货形态实测）

### Tier 0：必须留在首帧前（动不得）

| 项 | 实测成本 | 为什么动不得 |
|---|---:|---|
| `Attach`（SWP_FRAMECHANGED） | 294.5 ms | LakeUI 固有架构成本，其中 258.5 ms 是那一帧必须付的（docs/120 §八） |
| 框架起窗 01→10 | 251–355 ms | WinForms 内部，不可动 |
| 设置加载（含 JSON 反序列化） | — | 解码方式/音量/初始尺寸都从这来 |
| 核心文件探测 | — | 是**门禁**：失败要 `Return` 弹错误框，提前它等于吞掉错误 |
| 画面控件 + 播放控制器 | — | 开图需要句柄 |
| 界面呈现器 | — | 状态栏布局依赖它的量宽（docs/123 §2-B 已证不可延后） |
| 窗口布局 + 应用初始尺寸 | — | 首帧尺寸 |

### Tier 1：已在首帧后（43a7f90 已做）

- 四个图层呈现器延后至 `Shown` 之后：**−88.6 ms（R2R 出货同形，同批 20 轮交替配对）**。
- 已知代价：信息图层的操作提示 toast 在窗口刚出现的短窗内会静默丢失（字段 null、`?.` 守卫变空操作）——按"罕见退化"接受，见 docs/123 §2-B。

### Tier 2：**不该延后**——实测为伪成本或已达标（本轮判死，不要回头做）

| 候选 | 实测 | 判决 |
|---|---|---|
| 文件关联"后台同步"延后 | −21.4 ms，p=0.163（同 exe 切环境变量，16 轮） | **不做**。机制上 UI 线程同步部分仅微秒级（选项构造 + 信号量 + `Task.Run` 排队），注册表写在线程池。JIT 插桩臂上 13→14 段的 43.8 ms 是**首次调用 JIT 编译的伪影**，不可外推到出货形态 |
| 光盘 1 Hz 原生读延后 | 消融 Δ=+2.7（无效应） | 不做 |
| 解锁轮询 1 Hz 延后 | 消融 Δ=+5.2（无效应） | 不做 |
| SP 加载 / 个性化 / 自定义图标 | 受 `SP_UnLock` 门控，普通用户直接 return | 非成本 |
| 字体全树替换 | 天花板实验 −0.2 ms | 非成本 |

### Tier 3：真正的常驻税（本轮已修，8eaa472）

**三台图层泵空闲降频**——判定条件取"有没有内容源"（轨道是否存在），不取"当前时刻有没有要画的"：

| 泵 | 空闲判据 | 恢复通路 |
|---|---|---|
| 字幕 | `字幕提供器() Is Nothing` | 轨道加载/卸载/seek → `使图层失效()`（仅置签名标志）；下一拍 tick 自行判定切回 16 ms |
| 歌词 | `歌词 Is Nothing OrElse 条目.Count = 0` | 同上 |
| 弹幕 | 沿用已有「非播放 ⇒ 跳过」分支，跳过时降频 | 强制提交标志 + `退出空闲档()` 清累积基准 |

三条设计约束（都踩过坑，写进代码注释防回退）：

1. **只调频率、不改提交条件。** 不自己记"屏幕上是不是空的"——`提交当前帧()` 内部已有图层签名去重，无内容那一拍只是几次整数运算。第一版写了个 `图层已清空标志`，复查发现"无→有→无"迁移会漏重置、把残影永久留在屏幕上，**已删除**。
2. **间隔只由 tick 线程写（单写者原则）。** `使图层失效()` 从 UI 线程写会与 tick 的写交错，末态可以是"守卫字段=16、真实 Interval=200"，此后守卫恒相等 ⇒ 泵在有内容时**永久停在 5 Hz**。且它想省的延迟也省不掉：调度线程当前这一拍已按旧间隔武装，改字段不缩短在途的 wait。
3. 弹幕泵恢复时把 `下次刷新时间戳` 归零，不依赖 `更新下一节拍()` 里那条"|现在−下次| > 2×周期 ⇒ 重设基准"的兜底。

**实测**（出货同形：散装 41 件 / 同一无插桩内核 5,623,296 B / R2R A2）：

| 场景 | 无降频 | 有降频 | Δ | 备注 |
|---|---:|---:|---:|---|
| 地板·空载 | 64.1 | 29.1 | **−35.0（−54.6%）** | 5/5 轮全部更低，区间不重叠 |
| 地板·播放视频 | 129.3 | 91.9 | **−37.4（−28.9%）** | 5/5 轮全部更低，区间不重叠 |
| T2 回归 | 1218.2 | 1236.2 | +17.9，p=0.927 | 噪声内；**本笔对启动无贡献**（泵在图层群构造时才建，而图层群已延后） |

**已知代价**：轨道到达后最坏等一个空闲拍（200 ms）才恢复 60 Hz，只影响"加载后第一行字幕"的出场时机。

**功能验收**（两臂各 26 帧 PrintWindow 抓图 + 帧间差分自动定位字幕带，夹具 clip.mkv 10.02 s + clip.srt 覆盖 0.6–9.5 s）：

- ✓ 两臂字幕都正常渲染（峰值差 104,835 像素，两臂完全相同）
- ✓ 播放结束后两臂尾部 4 帧差值均为 0 ⇒ **无残影**
- ✓ 两臂逐帧字幕差中位 = 0 像素；唯一偏差 15,457 出现在字幕间隙（两臂抓帧起点相差 139 ms），不是内容差异

## 二、视角转换：T2 之外还有"什么时候真正闲下来"

T2 回答"首帧什么时候上屏"；本轮引入了一个此前从未测过的指标：**time-to-idle**——首帧之后，这台机器什么时候真正闲下来。两者差别很大：

- T2 ≈ 858.7 ms（出货形态，132）
- time-to-idle ≈ **7.7 s**（idle_probe，含启动爆发 + 线程池膨胀至 128 条后缓慢退役）

**线程数 127–136** 曾被怀疑是泄漏，实测是线程池膨胀后回收（40 秒内 128→121），不是泄漏——130 条等待线程的代价是内存不是 CPU。

用户问的"四五秒后做"其实指向的就是这个指标：启动爆发 0–2 s 内 2.0–2.7 核全忙，之后进入稳态地板。**把启动项延后 4 秒不改变地板**（那些 1 Hz 计时器是永久轮询），要压地板只能逐个加内容门控——这正是 8eaa472 做的事。

## 四、对 1000 ms 目标的诚实交代

- **132 批次**（负载 41%）：`arm_ls_opt_r2r` T2 = **858.7 ms** ⇒ 达标。
- **本轮批次**（负载 51–59%）：同一臂 T2 = **1218–1290 ms**。

同一份二进制跨批漂移 360–430 ms，远超此前记录的 69–175 ms。**结论：T2 绝对值只在批内可比，"是否达标"取决于负载窗口。** 858.7 是安静窗口的读数；机器繁忙时同一份二进制也会超 1000。验收应以批内配对 Δ 为准，绝对目标值需注明负载窗口。

## 五、遗留（明确不做 + 下一步）

- **明确不做**：文件关联延后、光盘/解锁轮询延后、SP 三项延后（均为伪成本，见 Tier 2）。
- **下一步候选**（按收益排序）：
  1. LakeUI 侧 PrecisionTimer 的 0.5 ms SpinWait 阈值——三台泵降到 200 ms 后仍各占一条调度线程；若在"没有刻度任务"时完全 Stop 并由事件重启，可再省 ~10 ms/s 并释放 `timeBeginPeriod(1)`（系统级功耗）。风险：漏启动即图层冻结，需事件完备性清单。
  2. `timeBeginPeriod(1)` 是进程级引用计数，只要任一 PrecisionTimer 在跑就抬着全系统时钟精度（docs/123 §7.3）——这是**跨进程**的功耗代价，值得单独立项。
  3. 360 控制器 `Application.AddMessageFilter` 的守卫顺序（每条消息先读别的控件属性再查自己的 bool）——全进程常驻税，改守卫顺序是零风险纯赢，未做。
