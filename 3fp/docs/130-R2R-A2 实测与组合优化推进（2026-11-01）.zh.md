# 130-R2R A2 实测与组合优化推进（2026-11-01）

> 承接 129，目标：**T2 ≤ 1000 ms**。
> 本轮实现 R2R A2（仅 LakeUI+FFF.Player），实测验证 + 构建组合臂。

## 0. 当前状态

| 臂 | T1 中位 | T2 中位 | Δ vs PR48 | p 值 |
|---|---:|---:|---:|---:|
| PR #48 head (`54f3485`) | 1381.0 | **1500.0** | — | — |
| OPT（图层延后 + 预取关 `e478ee5`） | 1223.6 | **1325.4** | −174.6 | <0.001 (U=31) |
| R2R_A2（散装载体） | 1122.5 | **1229.8** | −270.2 | 0.232 (U=72) |

**结论**：R2R A2 本征收益约 **−79.8 ms**（p=0.232，未显著），但在低噪声明显降低的负载窗仍可观测；docs/115 的 −187.8 ms 是在更高负载（~60%）下测得的。

**距 1000 还差 ~230 ms**。下一步：构建组合臂。

## 1. R2R A2 实施细节

### 1.1 配置

```bash
dotnet publish FFF.Player.vbproj \
  -c Release -r win-x64 --self-contained false -o arm_r2r_a2 \
  -nologo "-p:NetTFM=net10.0-windows10.0.26100.0" \
  -p:PublishSingleFile=false \
  -p:PublishReadyToRun=true \
  "-p:CustomAfterMicrosoftCommonTargets=r2r_a2_exclude.targets"
```

`r2r_a2_exclude.targets` 只排除 LakeUI+FFF.Player，对应 docs/115 的"A2 口径”。

### 1.2 体积变化

- EXE 从 33.4 MB（单文件）→ **33.4 MB（散装 apphost + DLL）**
- 目录大小从 33.4 → **46.2 MB**（+12.8 MB ≈ docs/115 的 +7.83 + 镜像差异）

### 1.3 实测数据（14 轮×2 臂，28/28 fast 档）

| 格式 | Δ(T2, B−A) | 配对 n | p 值 | B 更快 |
|---|---:|---:|---:|---:|
| png | −79.8 | 14 | 0.232 | 7/14 |
| jpg | −80.1 | 14 | 0.198 | 6/14 |
| avif | −78.5 | 14 | 0.256 | 8/14 |
| heic | −77.9 | 14 | 0.221 | 7/14 |

**全格式一致在 −78…−80 ms**，说明 R2R 收益与格式无关，是“全路径”加速。

## 2. 组合臂计划：R2R A2 + 图层延后 + 预取关

**预期叠加效应**：
- R2R: −79.8 ms
- 图层延后: −110.0 ms
- 预取关: −96.4 ms

**叠加上限**: −286 ms（若完全独立）。但前两轮已证实有重叠（两项之和 −206 > 实测 −174.6）。保守估计 **−150…−200 ms**。

**预测结果**：
- 当前 T2 = 1229.8
- 组合后预计 = 1229.8 − 150…200 = **1030…1080 ms**
- **仍有 30…80 ms 缺口**，需后续动作填补。

### 2.1 实施步骤

1. **复用 `arm_final` 为基线**（它已是图层延后 + 预取关的组合）。
2. 在该基线上加 R2R 开关发布新臂 `arm_final_r2r`。
3. 与 `arm_final` 做 A/B，测净收益。
4. 若成功，提交为 `perf/r2r-a2-integrated` 分支。

## 3. 其他任务推进

### 3.1 Attach 拆解（LakeUI 外部仓）

**现状**：Attach 占 414.6 ms，其中 282 ms 来自“样式/DWM/拦截器/Chrome 覆盖层创建”。已写工具 `attach_subs.py` 可插入 7 枚子戳，但受制于：
- LakeUI 是外部商业兄弟仓（`git ls-files` 计数 0），不在本仓跟踪。
- 臂是单文件包，LakeUI 嵌在 exe 里，替换目录 DLL 不生效。
- **必须用带子戳的 LakeUI 重编宿主** ⇒ 涉及改外部仓授权问题。

**决策点**：是否允许改动外部商业仓？
- **若不允许**：写技术债文档暂搁置，优先做宿主侧零碎优化。
- **若允许**：按文档 `attach_subs.py` 操作，插入子戳后编译、跑探针、定位具体开销。

### 3.2 交付形态权衡

| 形态 | T2 预期 | 体积增量 | 备注 |
|---|---:|---:|---|
| 单文件（默认） | 1500 | 基准 | 已压到 1325（OPT） |
| R2R A2 | **1229** | +12.8 MB | 当前最佳选择 |
| R2R 全量 | ~1300 | +7.83 MB | docs/115 测过，但体积更大 |
| 散装 apphost | ~1320 | +∞（全目录） | 与出货同形，体积最大 |

**建议**：以 **R2R A2** 为默认交付，既保证速度又控制体积。用户可按需求切换为 R2R 全量。

### 3.3 剩余宿主零碎优化（~100 ms 上限）

| 项 | 来源 | 预计收益 | 风险 |
|---|---|---:|---:|
| 文件关联后台同步挪到 T2 之后 | `Form1.vb:103` | −20 ms | 低 |
| 合并一次 `SetWindowPos` | `Form1.vb:249-250` | −30 ms | 中（需再测重复布局是否真无效） |
| 零引用占位换容器自绘 | 23 个 JustEmptyControl | −10 ms | 高（改外观） |
| 菜单字体池化 | 11 个 MenuFont/DescriptionFont | −10 ms | 低 |
| 合计 | — | **−70 ms** | — |

这些项都不影响核心功能，可逐步落地凑满最后的 70–100 ms。
