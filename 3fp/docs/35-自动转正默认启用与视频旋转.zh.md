## 1. 关键设计决策：默认启用放在**内核**，而不是宿主

上一版我把自动转正做成宿主的 `自动转正图片()` 函数，**需要宿主记得调用**。这不叫"默认启用"——只要打开流程改动、或新增一条打开路径，旋转就会**静默丢失**。

**本次改为：内核在 `DoOpen` 里读源旋转并直接调用 `SetViewRotation`。**

```cpp
// PlayerSession.cpp，紧跟 staticImage_ 判定之后
sourceRotation_ = SourceRotationQuarterTurns(format_, videoStream_);
(void)videoRenderer_.SetViewRotation(sourceRotation_);
```

⇒ **默认路径下宿主一行都不用写**，任何打开路径（拖拽、命令行、文件关联、切换上一张）**自动**带上旋转。

宿主侧只保留两件事：用户的开关偏好、手动旋转（R / Shift+R）。

## 2. 视频分析：**确实有问题，而且比图片更隐蔽**

### 2.1 问题一：视频路径**完全不读**旋转信息

逐行核实：`AV_FRAME_DATA_DISPLAYMATRIX` 在 3FP 里**只出现在 `GetImageInfo`**（图片专用 API，`PlayerSession.cpp:3249`）。
视频路径**从不读**。而 `GetImageInfo` 对视频返回 `-2 (NotSupported)`：

```
vprobe 对旋转视频的实测输出（修复前）：
  GetImageInfo(视频)=-2 (图片专用)
  snapshot: 1280x720          ← 横躺
  MediaInfo 中无任何旋转相关字段 ← 没有任何渠道可查
```

⇒ **竖拍/旋转过的视频会横躺着播，而且 API 层面完全查不到原因。**

### 2.2 问题二（更隐蔽）：视频旋转有**两套并行机制**，只认一套会漏

这是本次分析最有价值的发现。真实文件用**两种互不相同**的载体：

| # | 机制 | 载体 | ffmpeg 暴露方式 |
|---|---|---|---|
| 1 | **容器 rotate 标签** | Matroska `ProjectionPoseRoll` / ffmpeg muxer 写的 `rotate` | `av_dict_get(stream->metadata, "rotate")` |
| 2 | **display matrix** | MP4 `tkhd` 矩阵 / MOV | `AV_PKT_DATA_DISPLAYMATRIX` side data |

**只查 display matrix 会漏掉机制 1**——实测：`-metadata:s:v rotate=90` 生成的 MKV 里，
`ROTATE: 90` 只是**流元数据标签**，**不会**变成 display matrix：

```powershell
# 实测：MKV 里只有标签，没有矩阵
ffmpeg -i m90.mkv          →  Metadata: ROTATE : 90
字节扫描 'displaymatrix'    →  未找到
```

⇒ 只读侧数据（`AV_FRAME_DATA_DISPLAYMATRIX`）的实现，对这类文件**完全失明**。

### 2.3 问题三：EXIF 与容器标签的**方向定义相反**

| 输入 | ffmpeg 报的角 | 语义 |
|---|---|---|
| EXIF Orientation=6 | `-90°` | 需顺时针转 90° 才正 |
| 容器 `rotate=90` | `+90°`（CCW 约定） | 需逆时针转 90° 才正 |

**两者含义相同**（都是"躺着，要转 90°"），但**符号相反**。
所以归一化时必须**分别处理**：矩阵走 `av_display_rotation_get` 的符号，标签走 `4 - n` 反转。

### 2.4 问题四：图片的 EXIF 只在**帧级**，打开时读不到

修复过程中实测发现的坑：`SourceRotationQuarterTurns` 在**打开时**运行，而此时**还没有任何帧**。
对图片，EXIF 只作为**帧侧数据**存在 ⇒ 打开时查流级 `coded_side_data` **查不到**，
实测表现为"视频好了、图片反而变成 0"。

**修复**：帧解码后再补一次（`ApplyRotationFromDecodedFrame()`），帧级数据优先：

```cpp
// DecodeInitialFrame() 末尾
ApplyRotationFromDecodedFrame();   // 图片的唯一来源；视频则更具体
```

⇒ 图片**以转正姿态首帧呈现**，不会先闪一下横躺。

## 3. 实现

### 3.1 内核：统一读源旋转（两条机制）

```cpp
std::uint32_t SourceRotationQuarterTurns(AVFormatContext* format,
    const std::int32_t streamIndex) noexcept {
    // 1) 容器元数据标签（CCW 正向，故 4-n 反转成顺时针四分一转）
    for (const char* key : { "rotate", "ROTATE" }) {
        const auto* entry = av_dict_get(stream->metadata, key, nullptr, 0);
        ... return (4 - turns) % 4;
    }
    // 2) display matrix（已是顺时针语义，直接用）
    const auto* matrix = av_packet_side_data_get(stream->codecpar->coded_side_data,
        stream->codecpar->nb_coded_side_data, AV_PKT_DATA_DISPLAYMATRIX);
    ... return normalized / 90 % 4;
}
```

**永不抛异常**：畸形矩阵降级为"不旋转"，不能因为一个坏矩阵打不开文件。

### 3.2 内核：帧级补读（覆盖图片）

`ApplyRotationFromDecodedFrame()`：读 `stillImageFrame_`/`videoDecodeFrame_` 的帧侧矩阵，与打开时的值不同才更新（避免每帧重复调用）。

### 3.3 宿主：默认启用的开关 + 手动旋转

```vb
Private 自动转正偏好 As Boolean = True          ' 默认启用

Public Property 自动转正已启用 As Boolean       ' 关闭时把旋转归零
Public Sub 手动旋转(顺时针 As Boolean)          ' R / Shift+R
```

> **注意**：开关默认 `True`，但**内核无条件套用源旋转**——
> 因为"默认启用"是产品默认值，而内核行为不该依赖宿主的开关状态。
> 宿主关闭时显式调用 `设置视图旋转(0)` 归零即可。

## 5. 测试素材的构造（可复现）

本次为验证视频旋转，构造了**两套机制**的样本。⚠ 过程有坑，记录下来：

```powershell
# ❌ 无效：新 ffmpeg 对 MP4/MKV 不再把 -metadata rotate 写成矩阵
ffmpeg -i in.mp4 -c copy -metadata:s:v:0 rotate=90 out.mp4

# ✅ 机制 1：MKV 标签（-metadata 会写入 Matroska 的 rotate 标签）
ffmpeg -i in.mp4 -c:v libx264 -metadata:s:v:0 rotate=90 out.mkv

# ✅ 机制 2：真实 MP4 tkhd 矩阵 —— ffmpeg 不再支持写入，需直接改字节
#   关键：tkhd 矩阵偏移 = 'tkhd' 类型字段 + 4(ver/flags) + 20 + 16
#        且最后一个元素（w）是 2.30 定点 0x40000000，**不是** 16.16 的 0x00010000！
#        写错会得到 "rotation of nan degrees"（矩阵不可逆）。
#   90° 顺时针: a=0 b=1 c=-1 d=0
```

> **踩坑记录**：我最初把 `w` 写成 `0x00010000`，ffmpeg 报 `rotation of nan degrees`；
> 又把偏移算早 4 字节，毁掉了 width 字段。两处都靠"读回矩阵并与单位矩阵比对"定位。
