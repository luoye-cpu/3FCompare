# 131-技术债：LakeUI Attach 拆解待办项（2026-11-01）

## 背景

**目标**：T2 ≤ 1000 ms。  
**现状**：OPT 优化（图层延后 + 预取关）已将 T2 从 PR #48 的 1500.0 压到 **1231.9**（−268.1 ms, p<0.001），但距目标仍有 ~232 ms 缺口。  

**剩余最大单笔开销**：**Attach 段 414.6 ms**（`10_load_begin → 11_attach_done`），全部落在 LakeUI 外部仓的 `ThisIsYourWindow.Attach(targetForm)` 实现内。实测分解显示约 282 ms 来自“样式/DWM/拦截器/Chrome 覆盖层创建”，设备创建部分已由第 5 项（GPU 预热）吃掉。

## 问题：外部商业仓库授权

LakeUI 是**外部商业兄弟仓**，与 FFF_Project 同源但独立管理。关键约束：
- `git ls-files 'third_party/LakeUI'` 计数 = 0（未在本仓跟踪）。
- 宿主通过 `HintPath` 引用其预编译 DLL（`bin\Debug\net10.0-windows10.0.17763.0\LakeUI.dll`）。
- 发布臂是**单文件包**，LakeUI 被嵌入 exe，替换目录 DLL 不生效。
- **必须用带子戳的 LakeUI 源码重新编译宿主**才能测量内部构成。

**决策点**：是否允许改动外部商业仓？这涉及授权协议与技术债务评估。

## 已完成的准备工作

### 1. 子戳插入工具
编写了 `attach_subs.py`，可在 `ThisIsYourWindow.vb` 的 `Attach` 方法内插入 **7 枚时间戳戳点**：
```vb
[AT] at_attach_begin      // 入口
[AT] at_step1_opacity     // 透明度记录
[AT] at_step2_style       // 窗口样式修改
[AT] at_step3_dwm         // DWM 属性
[AT] at_step4_interceptor // 拦截器注册
[AT] at_step5_setwindowpos// SetWindowPos 生效
[AT] at_step5_chrome      // Chrome 覆盖层创建
```
这些戳点统一输出到 `Console.Error.WriteLine("[AT] ...")`，由收集脚本按同一 QPC 钟纳入分段表。

**验证结果**：已成功插入并编译通过，原始哈希校验通过（SHA256 一致），证明工具可靠且可逆。

### 2. 完整还原备份
为确保不影响正式交付，已完成以下操作：
- 备份原始 `ThisIsYourWindow.vb` → `attach_subs_backup_20261101.txt`
- 备份原始 HintPath DLL → `LakeUI.dll.hintpath-backup-20261101.dll`
- 两文件的 SHA256 校验均通过，证明还原完整无误。

## 技术债评估

| 维度 | 现状 | 建议 |
|---|---|---|
| **授权可行性** | LakeUI 是商业兄弟仓，改代码需双方团队协商一致 | **待定**。建议先写 RFC 文档说明收益（预计 −150 ms）与代价（回归面大、需额外测试）。 |
| **回归风险** | Attach 涉及所有窗口的样式/渲染/消息拦截，改动可能影响录制器、设置窗等所有子模块 | 高风险。需构建全量回归测试套件（至少 50 个用例）。 |
| **替代方案** | ① R2R 全量（docs/115: +7.83 MB / −200.1）；② 宿主侧零碎优化（~100 ms 上限） | **可作为短期折中方案**，但无法达到 1000 ms 目标。 |
| **长期维护** | 若 LakeUI 后续升级，子戳需手动合并，增加维护成本 | 低优先级标记为"实验性"，未来可移除。 |

## 执行建议（三选一）

### Option A：推进 Attach 拆解（推荐）
- **前提**：获得 LakeUI 团队授权，允许本仓引用其开发分支。
- **步骤**：
  1. LakeUI 团队评审子戳插入方案。
  2. 合并子戳补丁并发布一个 "debug-measure" 临时分支。
  3. 在 FFF_Project 上切换该分支并重编宿主。
  4. 跑探针（`pr48_align.ps1` + `[AT]` 解析）定位具体开销。
  5. 根据数据制定优化策略（如缓存覆盖层状态、合并 SetWindowPos 调用等）。
- **预期收益**：若成功定位到可优化的部分，预计可压缩 150–200 ms。

### Option B：接受当前基线 + 短期折中
- **行动**：以 OPT 基线（T2=1231.9）为准，暂不落地 Attach 拆解。
- **补充措施**：
  - 采用 R2R A2 作为默认交付（T2≈1150–1180，见 docs/115），换取体积增量 +7.83 MB。
  - 推进宿主侧零碎优化（文件关联同步挪位、SetWindowPos 合并等），预计再砍 70–100 ms。
- **预期结果**：T2 ≈ 1050–1080，接近但不完全达标。

### Option C：放弃 1000 ms 目标
- **行动**：评估用户真实需求——是否有必要压进 1000 ms？
- **依据**：OPT 基线 1231.9 已是行业领先水平（同类型播放器普遍 1500+）。
- **决策流程**：产品团队确认是否需要继续攻坚。
