## 二、O4 启动收益（安静窗 A/B，分档口径）

两臂同形态（均带 6 件 FFmpeg 侧载件 + libomp/libshaderc + settings），**唯一差别是 exe**：
base `rel_norm_iamf`（17,737,018 B）/ O4（16,683,170 B）。逐轮交替 20 轮，样片 `sample_1920.png`。

| 项 | base | O4 | Δ |
|---|---:|---:|---:|
| T2 中位（Mann-Whitney） | 2,165.8 | 2,009.0 | **−156.8 ms**（U=109, p=0.014） |
| T1 中位 | 2,067.6 | 1,902.0 | −165.6 ms |
| openGap（T2−T1） | 97.1 | 100.0 | **+2.9 ms（不变）** |
| 逐轮配对差（同轮消除漂移） | — | — | 中位 **−153.0 ms**，均值 −185.8，**16/20 轮 O4 更快** |

**归因**：`openGap` 未变而 T1/T2 同步下移 → 收益全部发生在"窗口出现在标题栏之前"，
即 **Svg/ExCSS 两个装配体的加载 + SVG 光栅化被移除**，与静图解码路径无关。这条同时说明
O4 的收益是"少加载两条装配体"，不是"图标画得更快"。

**口径约束（按 docs/117-118）**：40 轮全部落在 slow 档（spawn 201.6–264.1 ms，中位约 213–222），
平均 CPU 负载 69.8%（机器上有挖矿进程在跑）。故上表只作**相对比较**，绝对值带系统噪声，
不可当产品性能；fast 档 0 样本，无法给绝对基线。

## 三、测量前提的一个坑（本轮新发现，必须写下来）

单文件（single-file bundle）产物在本 Agent shell 里**一律 early-exit**，退出码 `0x800080A0`：

```
Failure processing application bundle.
Failed to create directory [C:\Users\<user>\AppData\Local\Temp\.net\FFF.Player\<hash>]
for extracting bundled files. Error code: 5
```

根因不是权限，也不是 360：**本 shell 的 `LOCALAPPDATA` 为空**，bundle 解包基准路径算错。
手工在该真实路径建目录是成功的，可作为排除证据。

解法（两条一起给，缺一不可）：

```powershell
$env:LOCALAPPDATA          = 'C:\Users\<user>\AppData\Local'
$env:DOTNET_BUNDLE_EXTRACT_BASE_DIR = '<工作区>\3fp\build\imgperf\bundle_extract'
$env:DOTNET_ROOT           = 'C:\Program Files\dotnet'
```

此前 `rel_loose_iamf`（散装布局，不解包）能跑，正是因为它不走 bundle 解包，所以这个坑长期没暴露。

## 四、JXL 内嵌尝试：已完整撤回

### 4.1 做过什么

静态编译 libjxl（VS18 x64，`jxl_dec` + `jxl_threads` + brotli + hwy），照 libiamf 的模式接进
`FFF.Native.vcxproj`（`HaveLibjxl` 属性 + 条件 `ItemGroup` + `FailIfLibjxlMissing` 门禁 +
`#error` 兜底），新增 `JxlImageDecoder`（`ReadHeader` / `DecodeFile` / `ToFrame`），并在
`PlayerSession` 里改成：`.jxl` 静图**跳过 `avformat_find_stream_info`**、**不开 FFmpeg 解码器**、
由 libjxl 直接出 rgb24 帧，失败走 `open-image` 真实报错（无回退）。

### 4.2 为什么撤回

| 判据 | 实测 | 结论 |
|---|---|---|
| 链接增量 | 674,816 B（只拉实际引用的对象） | 体积不是问题 |
| FFmpeg 路径成本 | `find_stream_info` **496 ms（自己解了一帧）** + 真正解码 **491 ms** = **双解码单线程** | 内部路径确有优势 |
| libjxl 路径成本 | 1 线程 529 ms；4 线程 139；8 线程 ~99；20 线程 ~105 | 线程收益真实 |
| 像素一致性 | FFmpeg 与 libjxl 输出**逐字节一致** | 正确性 OK |
| **应用内收益** | 两臂 5 轮：旧 2,073.6 / 新 2,271.9（噪声 ±200 ms） | **拿不到有统计力的结论** |

即：组件级优势确定，但**在产品启动时间上未能证明**；而它要新增一条 P/Invoke 式解码通路、
一个构建门禁和一套新的失败面。收益无法证实时，不引入复杂度是对的。

### 4.3 附带结论：图标不该换 JXL（已量化）

| 路径 | 单图标 | 11 个合计 |
|---|---:|---:|
| 现状 GDI+ 解 PNG（内存流） | 22–29 µs | **284 µs** |
| libjxl 1 线程 + GDI+ 包装 | 408 + 5.6 µs | 4,548 µs（慢 16×） |
| libjxl 8 线程 + GDI+ 包装 | 1,174 + 5.6 µs | 12,978 µs（慢 46×） |

48×48 下 libjxl 的固定开销（decoder 创建 + 头解析 + brotli + 线程池启动）就占满全部时间；
而换 JXL 只省 **3,294 B（占包 0.019%）**。**结论：图标继续用 PNG，此项到此为止。**

> 测量教训：用 PowerShell 循环调 `Bitmap.FromFile` 会把每张放大到约 850 µs（脚本引擎开销），
> 必须用真正的 .NET 代码计时。第一版数字因此把结论方向搞反过一次。

## 六、O4 × A2 可加性尝试（本轮，结论：**未能判定**）

### 6.1 先撞上两个工具链事实（均已验证，值得记下）

1. **台账里的历史产物体积无法从仓内复刻。** `rel_o4`（16,683,170 B）/ `rel_a2`（21,964,602 B）都是
   单文件，但当前仓内 `dotnet publish -p:PublishSingleFile=true` 的框架依赖产物是 **33.5 MB**；
   想用 `-p:EnableCompressionInSingleFile=true` 解释差值时被 SDK 挡住：`NETSDK1176`（压缩只支持自包含），
   而自包含档是 77 MB 级。**结论：当初的发布参数没有留存，记录值不可复刻**。
2. **`PublishReadyToRunExclude` 是 Item，不是 Property。** 用 `-p:` 传：
   - 带 `;` 会被 MSBuild 当成多属性分隔而报 `MSB1006`（须转义为 `%3B`）；
   - 即使转义成功也**不生效**（实测 `Vortice.DXGI.dll` 仍被 R2R 编译，91,648 → 225,280 B）。
   唯一有效的做法是用 `-p:CustomAfterMicrosoftCommonTargets=<targets>` 注入真正的 ItemGroup，
   注入后 LakeUI（+2.97 MB）与 FFF.Player（+1.26 MB）变大、其余全部不变 = A2 口径复现。

### 6.2 四臂（同一条发布管线重造，单文件 / 框架依赖 / A2 口径 R2R）

|---|---:|
| `arm_svg_jit`（O4 前，JIT） | 33,513,507 B |
| `arm_svg_a2`（O4 前，A2 R2R） | 39,543,331 B |
| `arm_png_a2`（O4 后，A2 R2R） | 36,687,319 B |

### 6.3 测量结果：无效窗格，不作结论

`arm_svg_a2` vs `arm_png_a2`，20 轮交替：Δ 中位 **−344.0 ms**，但 **U=86, p=0.272**；
40 轮里废 10，平均负载 **77.9%**；T2 极值 4,380 / 6,512 ms，单轮配对差从 **−1,379 到 +3,106 ms**。
配对中位 −141.8 ms、13/20 轮 O4 更快，方向与 O4 单独收益一致，但**噪声完全泛没效应**。

⇒ 按 docs/117 口径记为：**可加性未判定**，不得写成任何数字。需要安静窗（或换测量机）后重跑。
