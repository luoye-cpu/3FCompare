## 四、同步现状（关键风险）

```
2026-08-17  fork/master                        ← 停在这里
   │              （落后 54 个提交）
   ▼
2026-09-23  上游 master 2acd96d（tag 2026.9.23）← 上游当前
```

| 对比 | 结果 |
|---|---|
| `fork/master` vs `origin/master` | fork 独有 **0**，上游独有 **54** ⇒ 纯落后，可 fast-forward 同步 |
| 本地基线 `3fc/integrate-issue7`（b765a1f） vs 上游 master | 本地独有 **31**，上游独有 **8** |
| fork 上的 `3fc/integrate-issue7` | `0d5856e`，**落后本地基线**（本地已推进到 `b765a1f`） |
| 上游发布节奏 | 近 36 天 54 个提交，**tag 打到 2026.9.23** ⇒ 近乎日更 |

⚠ **含义**：

- 提 PR 前必须把 fork/master 同步到上游最新，否则 PR 会带着 54 个提交的陈旧基线
- 上游日更 ⇒ PR 从开发到合并期间要**频繁 rebase**；**小步快跑**（先提 PR-A 纯行为修正）比攒大 PR 稳
- 3FC 本地基线也**落后上游 8 个提交**

## 六、PR 工作流（照 `upstream/pr-b-adapter` 的既有范式）

### 6.1 分支策略：双基线

| 分支 | 基于 | 用途 |
|---|---|---|
| `feature/image-mode` | 本地基线 `b765a1f` | **实验与 3FC 侧验证**（可构建、有 runtime/ 的 ffmpeg） |
| `upstream/image-mode` | **上游 master `2acd96d`** | **提 PR 用**（纯净，不含 3FC 的 31 个本地提交） |

⚠ 提上游的 PR **绝不能**基于 `3fc/integrate-issue7`（含单 presenter 管线等 3FC 私有改动）。

### 6.2 提交纪律：**上游 PR 只能有一个提交**（决策 D10）

> ⚠ 这一条**偏离** PR #9 的既有范式（那个是 `Native:` / `Player:` 两个提交分开）。
> 仓库所有者明确要求：**给上游的 PR 最终只做一次提交**。

理由与好处：

- 本次改动横跨内核与外壳，一次提交**不可能出现"合了内核没合外壳"的半截状态**
  （PR #9 当年必须靠"两者一起合并"的约定来规避，单提交则结构上就不会发生）
- 上游 master 近乎日更，单提交 rebase 与冲突解决都最省事
- 本方案**不改动 ABI**（D9），不存在 breaking change 需要单独提示

代价与补偿：单提交丢失过程可读性 ⇒ 用**分节的提交信息**补偿（见 §6.4），
并在本地保留完整开发历史分支（见 §6.3）。

### 6.3 分支布局：开发历史与 PR 分支分离

| 分支 | 内容 | 用途 |
|---|---|---|
| `upstream/image-mode` | **多个提交**，完整开发过程 | 本地开发、回溯、已推送到 fork 作备份 |
| `upstream/image-mode-pr`（最终建） | **单个提交** | 提给上游的 PR |

这样既满足"上游只看到一个提交"，又不丢本地过程。

### 6.4 产出单提交的操作步骤（最终执行）

```powershell
cd 3fp/kernel
git fetch upstream --prune

# 1) 基于上游**最新** master 建 PR 分支（上游日更，务必先 fetch）
git switch -c upstream/image-mode-pr upstream/master

# 2) 把开发分支的全部改动压成工作区变更（不带来提交历史）
git merge --squash upstream/image-mode
# 若上游已推进导致冲突：逐个解决后继续（冲突文件就是图片模式动过的那几个）

# 3) 单一提交，信息按内核/外壳分节写（草稿见 §6.5）
git commit -F <提交信息文件>

# 4) 压缩后代码内容不变，但仍需重新编译验证（内核 + 宿主各一次）
msbuild FFF.Native\FFF.Native.vcxproj -p:Configuration=Release -p:Platform=x64
dotnet build FFF.Player\FFF.Player.vbproj -c Release

# 5) 推送并开 PR（目标 Lake1059/FFF_Project:master）
git push -u origin upstream/image-mode-pr
```

```

<为什么需要它：图片在 3FP 里的现状问题>

Native:
- <内核改动 1>
- <内核改动 2>

<行为不变性说明：视频路径未改动 / 无 ABI 变更>

```

> 提交前用 `git log --oneline upstream/master..upstream/image-mode` 核对改动范围，
> 用 `git diff --stat upstream/master...upstream/image-mode` 核对文件清单。

### 6.6 命令（在 `3fp/kernel/` 执行）

```powershell
cd c:/PLAN/3FCompare/3fp/kernel

# 1) 当前 origin 指向本地 bundle，补两个 remote
git remote add upstream https://github.com/Lake1059/FFF_Project.git
git remote add fork     https://github.com/luoye-cpu/FFF_Project.git
git fetch upstream --prune
git fetch fork --prune

# 2) 建提 PR 用的分支（基于上游最新 master）
git switch -c upstream/image-mode upstream/master

# 3) 同步 fork/master 到上游最新（纯 fast-forward，fork 独有 0 提交，安全）
git push fork upstream/master:master

# 4) 开发完成后推到 fork 并开 PR（目标 Lake1059/FFF_Project:master）
git push -u fork upstream/image-mode
```

### 6.3 提交纪律

- 内核与外壳**同一 PR**，提交分开（`Native:` / `Player:` 前缀）—— PR #9 的既有范式
- 改 ABI 时在 PR 正文**顶部显式警告** breaking change 与版本递增
- 上游日更 ⇒ 每次 rebase 后重新自测，不要盲推

### 6.4 沟通渠道

- fork 无 issues ⇒ **去上游 `Lake1059/FFF_Project` 发 issue**（它有 issues，41 stars）
- 建议顺序：issue 探路（附 `01-可行性分析` 的 M1 部分）→ 取得意向 → 再提 PR
