# 49 · 3FP 视频播放再审查（修复后复评）

> 问题：「回头重新分析 3FP 的视频播放还有没有可以优化的部分」
> 方法：**先用足够长的测量窗口重做基线**，再定位真正的瓶颈
> 日期：2026-10-06

---

## 0. 最重要的结论：**只有 8K 软解有问题，其余已达源帧率**

| 场景 | fps | 丢帧 | 状态 |
|---|---|---|---|
| 1080p HDR10 软解 | 51.2 | — | ✅ 达标 |
| 4K HEVC10 软解 | 56.0 | 0 | ✅ 达标 |
| 4K AV1 软解 | 57.0 | 0 | ✅ 达标 |
| 4K H264 软解 | 56.6 | 0 | ✅ 达标 |
| 8K HEVC **硬解** | **58.7** | **0** | ✅ 达标 |
| 8K AV1 **硬解** | **58.8** | **0** | ✅ 达标 |
| **8K HEVC 软解** | **11.5** | **253** | ❌ **唯一瓶颈** |
| **8K AV1 软解** | **15.8** | **238** | ❌ **唯一瓶颈** |

⇒ **除 8K 软解外，视频播放已经没有可优化的空间**（都贴着 60 fps 源帧率）。

---

## 1. ⚠️ 先修正我自己的一个测量错误

初测时我用 **3 秒**窗口，得到"HDR10 4K 软解只有 23–27 fps、Present 28ms"，
一度以为发现了一个新的普遍性问题。

**用 5 秒重测后，同一文件是 51–56 fps、Present 3.7ms、零丢帧。**

原因：**3 秒窗口被启动开销主导**（avformat 打开 + 解码器初始化 + 首帧 + preroll ≈ 1 秒）。
3 秒里约 1/3 是启动，把稳态帧率拉低了一半以上。

> **教训：测量窗口必须显著大于启动开销。** 本机启动约 1 秒，所以至少用 5 秒。
> 之前 8K 的部分结论也受此影响（方向不变，但绝对值偏低）。

## 2. 8K 软解的精确分解

| 8K HEVC 软解 | fps |
|---|---|
| **仅解码**（无窗口） | **51.2** |
| **完整链路**（带窗口） | **11.8** |

**解码有 51 fps 的余量，却只呈现 11.8 fps。**

每帧构成：

```
上传   13.25 ms   (99.6 MB => 7.5 GB/s)
Present 28.88 ms
合计   42.13 ms  => 23.7 fps
实测 11.8 fps    => 实际帧时间 84.7 ms
```

**差额 42.6 ms 说明存在串行化**：上传与 Present 并非并行，且 Present 中
还包含等待 GPU 完成上一次上传的时间。

**硬解对照**：同一文件 Present 仅 **0.76 ms** —— 因为硬解的源纹理由 GPU 填充
（`CopySubresourceRegion`），完全没有 CPU→GPU 的等待。

### 为什么之前测的带宽不同

| 测量 | 带宽 |
|---|---|
| 早期微基准 | 4.2 GB/s |
| 当前实测 | 7.5–8.2 GB/s |

⇒ 微基准（紧密循环、同一纹理）**低估了**真实播放的带宽。以实测为准。

## 3. 可优化项评估

### ★ P1：CPU 预缩放后再上传（**唯一有量级收益的方向**）

**原理**：8K 源 7680×4320，窗口仅 2560×1440（或更小）。当前上传**完整 8K 帧**（99.6 MB），
而 GPU 上传后再下采样。若先 CPU 缩放到窗口尺寸再传：

| 项 | 值 |
|---|---|
| 传输量 | 99.6 MB → **5.3 MB**（18×） |
| 省下 | ~13.25 ms → ~0.7 ms，**省 12.5 ms/帧** |
| CPU 成本 | **~1 ms/帧**（纯缩放，实测；多线程可摊薄） |
| **净收益** | **~11.5 ms/帧** |
| 预期 | 11.8 fps → **~15 fps**（受解码 51 fps 与 Present 限制） |

**⚠️ 真实约束（必须承认）**：

1. **解码上限 51 fps** —— 即使上传降到 0，也到不了 60 fps；
2. **只在"源 ≫ 窗口"时有效** —— 全屏 8K 时窗口≈源，收益消失；
3. **画质** —— GPU Lanczos3 换成 CPU sws，需目视/PSNR 比对；
4. **影响面** —— VSR、360、旋转、截图等路径都以全帧为源，改动是**架构级**的；
5. **Present 的 28.88 ms 不会因此消失** —— 它含同步等待，需一并处理才有效果。

⇒ **收益真实但有限（11.8 → ~15 fps），风险是架构级。** 建议**先做原型验证**再决定。

### ❌ 已排除（本轮复查确认无收益）

| 项 | 结论 |
|---|---|
| 软解线程数（非 AV1）| 8K HEVC 软解已达 **51.2 fps** 解码能力，不是瓶颈 |
| 4K/1080p 任何优化 | **全部已达源帧率**，无空间 |
| 硬解路径 | 58.7–58.8 fps、**零丢帧**，无空间 |
| Lanczos 下采样改动 | 严格 A/B（6 轮交错）中位 **170 vs 171**，**无回归** |
| 上传并行化（多平面并发） | 同走一条 PCIe 上行，总线受限，无益 |
| 逐帧重复计算 | 抽查 `UpdateBitRateForPosition` 等均有秒级/代次缓存，无发现 |

### ⚠️ 结构性观察（非缺陷，但值得知道）

`PresentTimedText` 在 Present 期间释放 `deviceMutex_`（docs/45 §5）。
上传可在此期间提交，但**跨线程命令顺序不确定** —— 这很可能是
8K 软解中"上传 13.25 + Present 28.88 却不等于实测帧时间"的原因之一。

**若要彻底解决 8K 软解，正确做法是让上传与呈现真正流水线化**，
而不是继续微调上传本身（P2 已证明单纯双缓冲无效，见 docs/46）。

## 4. 建议

| 优先级 | 项 | 收益 | 风险 | 建议 |
|---|---|---|---|---|
| **1** | **明确提示用户 8K 请用硬解** | 直接 11.8→58.7 fps | 无 | **优先做** |
| 2 | CPU 预缩放（可选开关） | 11.8→~15 fps | 架构级 | 先原型验证 |
| 3 | 其余 | 无 | — | **不做** |

**核心理由**：8K 软解是**降级路径**（丢 238–253 帧/5 秒），
而硬解在同一机器上跑满 58.7 fps 且零丢帧。
**把 11.8 优化到 15 的价值，远低于让用户知道"切硬解能到 58.8"。**
