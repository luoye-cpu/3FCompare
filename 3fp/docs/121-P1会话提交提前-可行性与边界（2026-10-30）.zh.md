## 0. 结论摘要（整体置信：高）

1. **技术上可行，且内核侧没有任何"必须同一宿主线程"的约束**：所有 `FFF3FP_*` 入口只是把命令塞进会话自己的队列（`Enqueue`），真正干活在会话 worker 线程。今天的"会话创建"已经跑在线程池上（`Task.Run`）。
2. **但台账写的改法（把 `打开媒体` 提到 `Form1_Load`）几乎拿不到收益**——这是本轮最关键的发现：`打开Async` 的 enqueue 发生在 `Await Task.Run(创建会话)` 的续体里，续体回到 UI 线程，所以 Open 实际仍要等 `Load` 返回、消息泵转起来（≈T1 之后）才提交。只挪调用点 ≈ 省 3–6 ms，不是 45–55 ms。
3. **要兑现 −45~55 ms，必须把 `FFF3FP_Open` 的提交点搬进 worker 闭包**（3 行改动），再在 `Load` 中段触发。改动集中在 `播放器控制器.vb:1338-1342` 一处 + 宿主 3 处门控/去重，内核零改动。
4. **HWND 在 `FFF3FPConfiguration.outputWindow` 里，但宿主恒传 `IntPtr.Zero`**；绑窗走 `FFF3FP_SetOutputWindow`，其"设置窗口 + 首帧重绘"本来就在内核 worker 上执行 ⇒ **不存在"必须 UI 线程绑窗"的内核约束**；真正必须在 UI 线程的只有"取控件句柄"和"重绘之后的宿主 UI 事件"。
5. **风险等级：中**（严格按 §5 的方案、不碰视频、不给 Create 传 HWND、不用 `ConfigureAwait(False)`）。放宽到任意一条 §8 红线条目即升为**高**。
6. **建议现在就做**，但先花半天做一次纯打点验证（`Load` 剩余时长是否 ≥60 ms），它决定收益是 45–55 还是 10–20。像素闸门是硬门槛，且闸门工具目前**尚不存在**（需新建/编译）。

| 证据 | 内容 | 等级 |

## 3. 可行性判定与线程亲和点清单

### 3.1 判定

- **能在 worker 创建会话并 Open**：能。创建已经是池线程；Open 只需把 enqueue 点搬进 worker。
- **HWND 在哪一步绑定**：`FFF3FP_Create` 的 `configuration.outputWindow`（`播放器会话.vb:79`）**可以**带，但宿主传 `IntPtr.Zero`（`播放器控制器.vb:1497`）。真正的绑定是 `FFF3FP_SetOutputWindow`（`:369`），在 `重绑输出窗口()`（`:1138-1140`）里调。
- **必须先 Open 后绑窗吗**：是，且这正是现状。必须保持：Create 带真窗口 = **带窗 Create ≈398 ms**（`t1t2_decompose.md` §二.1、`docs/104` §二.1，实测 n=7），因为 `PlayerSession.cpp:908` 的 `WarmDevice()` 会在构造函数里同步建全套渲染管线。无窗 Create ≈0.1 ms（探针实测）。
- **绑窗可以不在 UI 线程**：可以（见 §2），但**取句柄**必须在 UI 线程。

### 3.2 线程亲和点（施工红线表）

| 步骤 | 位置 | 归属 | 依据 |
|---|---|---|---|

## 4. 关键反证：只把「打开媒体」提前，收益≈0

推演（逐行可查）：

1. `Load:155` 调 `打开媒体` → `打开媒体Async` → `切换媒体会话Async`，同步跑到 `:1338`；
2. `:1338` 的 `Await Task.Run(创建会话)` 让出，创建在池线程跑（headless 0.1 ms）**并立刻完成**；
3. 续体（`:1341 设置音量` + `:1342 Await 候选会话.打开Async`）被 Post 回 **UI 线程**的同步上下文（WinForms 同步上下文 = `Control.BeginInvoke` 投递的消息）；
4. UI 线程此刻正停在 `Form1_Load` 里，**不跑消息泵** ⇒ 续体不会执行，`FFF3FP_Open` 也就没被提交；
5. `Load` 返回 → 窗口显形（≈T1）→ 消息泵转起来 → 续体才执行 → **Open 才入队 → DoOpen 才开始**。

⇒ 若只在 Load 里调 `打开媒体`，只省掉 `Shown → BeginInvoke → 打开外部文件` 那 3–6 ms（`t1t2_decompose.md` §四 #1），与台账的 −45~55 相差一个量级。

**因此 P1 的真身不是"提前调用"，而是"提前提交"**：把 `打开Async`（= `FFF3FP_Open` 的 enqueue）搬进 `Task.Run` 的闭包。这一步之后，`DoOpen`（demux 12–15 + PNG 解码 ~40 + 尾部 1–5；P2 已消掉无窗那遍 sws，见 `VideoRenderer.cpp:7219`）全部落在 Load 期，与控件树/JIT 重叠。

**另一个必须同时处理的坑（否则收益清零）**：`Shown` 时 `打开外部文件` 会再走一遍 `打开或替换单个文件:755` → `打开媒体`。此时 `会话` 非空且解码器/性能选项相同 ⇒ 命中 `:1240` 的"原位重开"分支（`原会话.打开Async(同一路径)`），等于把刚预解码的图**再解一遍**。必须在 `:755` 去重。

## 5. 最小改动方案

开关建议：`FFF_EARLY_OPEN=1`（opt-in，验收期）；通过后默认开、留 `FFF_NO_EARLY_OPEN=1` 作退路，与 `FFF_NO_GPU_WARMUP` / `FFF_NO_PREFETCH`（`ApplicationEvents.vb:34,71`）同构。

### M1（核心，3 行）`3fp/kernel/FFF.Player/Core/播放器控制器.vb:1338-1342`

现状：

```vb
候选会话 = Await Task.Run(
    Function() 创建会话(解码器, 候选色彩输出, 性能选项),
    此次取消.Token)
候选会话.设置音量(当前音量, 已静音)
Await 候选会话.打开Async(路径, 此次取消.Token)
```

改成（Open 的提交点在闭包内）：

```vb
Dim 打开任务 As Task = Nothing
候选会话 = Await Task.Run(
    Function()
        Dim 候选 = 创建会话(解码器, 候选色彩输出, 性能选项)
        候选.设置音量(当前音量, 已静音)
        ' Open 只入队；必须在 worker 上提交，否则解码仍被 UI 消息泵卡在 T1 之后。
        打开任务 = 候选.打开Async(路径, 此次取消.Token)
        Return 候选
    End Function, 此次取消.Token)
Await 打开任务
```

要点：
- **不要**改成 `ConfigureAwait(False)`——那会把 `:1385 重绑输出窗口`、`:1391 媒体已打开` 之后的整段静默搬到池线程（见 §8 R4）。
- 此改动对所有调用方（拖拽/播放列表/相邻项目）等价：只换了"谁把命令塞进队列"，队列顺序不变。
- 原位重开分支（`:1240-1300`）不动。

## 6. 为什么只对图片模式门控

1. **静图没有时间线/音频/播放泵**：`DoOpen` 的静图分支只到 `DecodeInitialFrame`（`PlayerSession.cpp:3671`），无窗时 `Render` 直接返回（`VideoRenderer.cpp:7219`），不建设备、不上传、不 present。
2. **绑窗路径是专为静图写的**：`SetOutputWindow` 里 `staticImage_ && stillImageFrame_ != nullptr` → `Render(stillImageFrame_, ..., imageMode=true, ...)`（`PlayerSession.cpp:1751`）。这就是 `2867d8a` 一族的无窗→绑窗首帧路径。
3. **视频语义面完全不同**：视频 Open 会起音频渲染器（WASAPI）、`newlyVisibleVideo`/`ArmAudioUntilVideoFrame` 的"首帧前静音"边界（`PlayerSession.cpp:1735-1745`）、硬解能力预检与首包解码、播放泵节奏。无窗期先跑会与"音频不能先于画面"的既有不变量打架，且 T1→T2 的构成（hw 试解为主）与静图不同，收益无实测依据。
4. **动图也是另一条路**：`animatedImage_` 在绑窗时落到 `PresentAfterBind()`（`PlayerSession.cpp:1756`）而不是静图分支，动画泵/循环语义都要重新验收 ⇒ v1 用扩展名排除 `.gif/.apng/.webp`（少赚一点，换掉一整类风险）。

## 7. 验收方案

### A. 结构闸（先做，不依赖安静窗，半天）

临时 `Stopwatch` 打点（**注意：`-TraceDir` 当前不产出任何计时**，`docs/114` §五.1；`FFFPROF`/`FPT_OPEN_TRACE` 全树 0 命中）：`LoadStart / EarlyTrigger / OpenEnqueued / OpenCompleted / BindEnqueued / LoadEnd / T1 / T2`。

判据：
- `OpenEnqueued` 必须落在 `LoadEnd` 之前（证明 §4 的坑真的被绕过）；
- `LoadEnd - EarlyTrigger ≥ 60 ms`（决定收益是否满额；不足则把触发点前移到 `:137` 之后并补 `应用音量()`）。

### B. quiet_ab A/B（安静窗，≥20 轮交替）

- `3fp/tools/quiet_ab.ps1` 判据沿用（`SpawnMs>50` 废、分 fast/slow 档，`docs/117`）。
- **主判据用逐轮配对的 `T2−T1` 中位差**，不是 T2 单看：P1 会把工作搬进 T1 前的窗口，T1 预计 +3~15 ms（`t1t2_decompose.md` §五 P1 风险 1），T2 单看会被稀释。CSV 里 T1/T2 都在，事后配对。
- 预期：`T2−T1` 89 → 25–35；净 T2 −45~55。
- **工具缺口**：`quiet_ab.ps1` 只能换 exe（`-ExeA/-ExeB`），不能按臂换环境变量。需加 `-EnvA/-EnvB`（在两臂 spawn 前设/清 `$env:FFF_EARLY_OPEN`；探针继承父进程环境）。这是唯一必须动 `tools` 的地方。
- 两臂必须同目录同 DLL 集合：单文件产物不含 FFmpeg 六件与 `FFF.Native.dll`，缺了会走 `Form1.vb:114` 的"核心文件缺失"提前 Return，A/B 测的是错误框。

### C. 像素闸门（PrintWindow，硬门槛）

- 抓手：`PrintWindow(hwnd, dc, PW_RENDERFULLCONTENT)`，本仓已验证可行且是唯一可行路线（`3fp/tools/WinUi.cs:201-208`；`docs/07 §2` 证 gdigrab 抓 D3D 窗口全黑；`CopyFromScreen` 会抓错窗口）。
- **现状**：`WinUi.cs` 只有源码、仓内无编译产物（`WinUi.exe` 全树 0 命中）⇒ 闸门工具需要新建/编译，属验收前置工作量。
- 采样：到达 T2 后 **T2+0 与 T2+300 ms 各抓一次**（防"先黑一帧再正确"与"永久黑"两种失败）。抓 `画面控件` 的子面板（视频输出窗口）客户区。
- 判据：与 A 臂参考帧**逐像素零差**（样张 `sample_1920.png` 是渐变+4 万噪声点，灰度 stddev 53.7，任何错位/黑屏/色偏/缩放差异都会爆）。
- 样张矩阵（每张 A/B 各跑）：`sample_1920.png`、48×48 图标、EXIF 旋转 JPEG、10-bit/HDR 静图（scRGB 分支）、AVIF 平铺（`AvifIlocShim`/tile grid 路径）、4K PNG、以及**一张 gif 作负对照**（必须与非门控臂逐像素一致）。

### D. 行为回归（人工 + 脚本各半）

| 场景 | 期望 |

| # | 风险 | 为什么不可接受 |

| R1 | **视频/音频/光盘也走 worker 预打开** | 音频先于画面（`PlayerSession.cpp:1735-1745` 的首帧静音边界被绕开）、WASAPI 独占、硬解试解、播放泵全在新语义下；无实测收益。必须扩展名门控 |

## 10. 建议

1. **现在就做，分两步**：
   - 第一步（半天，无产品改动）：§9 #1 打点 + §7.A 结构闸。若 `Load` 剩余 < 60 ms，先解决"更早触发"或直接放弃该项（收益降到与噪声水位同量级：`docs/120` §十记到本机真空改动 +12 ms、<30 ms 单项 20 轮分辨不出）。
   - 第二步：M1–M5 + `FFF_EARLY_OPEN=1`，然后 A/B + 像素闸。
2. **风险等级：中**。这是宿主侧对"打开管线"最敏感的一处改动（`切换媒体会话Async` 是所有打开方式的公共路径，且 `FFF.Player.Tests` 目前只有 `Program.vb`，对打开链**零覆盖**），验收成本必须按"无回归网"来估。
3. **与台账的两处修正**：
   - `docs/114` P1 的名字应为「**Open 提交提前**」而非「会话创建提前」：headless 创建实测 ≈0.1 ms（`t1t2_decompose.md` §3），移走的是 demux+解码+尾部 ≈55–60 ms；
   - P1 的施工前提不是"把 `打开媒体` 挪到 Load"，而是 **M1（把 `打开Async` 搬进 `Task.Run` 闭包）**，否则收益不成立。
4. **不建议同批做**的相邻项：提前绑窗/设备预热（P1b，受 `EnsureDevice` 未测 + 隐藏窗口 present 双重不确定）、视频模式（R1）、O3-B/M2/M3（不同桶，可加性未验）。

## 11. 实测结果（2026-10-30 当日完成，结论：否决，已回退）

§5 的 M1–M5 已按方案实现并通过 §7.A 结构闸。**结论是否决。** 完整数据见 `docs/120` §十五。

1. **§9 待证 #1 成立**：`Load` 剩余（触发点 → `Load` 返回）实测中位 **141 ms**（10 轮，最小 125），
   远超 60 ms 门槛，所以“有时间窗”这个前提是真的。
2. **但收益上限不是 140 ms，而是 32 ms。** §1 的 `enqueue → opened` 全链里，只有
   `enqueue → open_done`（32 ms）跑在 worker 上；`open_done → bind`（16 ms）要 `画面控件.输出窗口句柄`，
   `bind → opened_event`（79 ms）的处理器全在 UI 线程。§4 只排除了“挪调用点”，
   没有排除“链上大部分时间本来就不在 worker 上”。
3. **实测零收益**：20 轮配对（同一产物，仅 `FFF_EARLY_OPEN` 不同），Δ(T2) = **+19.0 ms**
   （U=179, p=0.57），逐轮配对中位 **+2.6 ms**、均值 +42.3、**10/20**。
4. **机制**：把 32 ms 挪进一个已被 `Load` 占满的窗口，`Await` 续体回 UI 只能排队——
   `open_done` 相对 `enqueue` 从 32 ms 膨胀到 297 ms，净效果只提前 16 ms。

本篇不再作为待施工方案，保留作为线程模型实测事实的参考（§2、§3.2 仍然有效）。
真正的剩余目标在 `load_end → Shown`（125 ms）与 `bind → opened_event`（79 ms）
两个处理器**内部的工作量**，而不是它们的调度位置。
