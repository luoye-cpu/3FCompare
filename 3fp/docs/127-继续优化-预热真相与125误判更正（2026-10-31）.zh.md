# 127-继续优化：预热真相、125 误判更正、以及"还剩哪里有钱"（2026-10-31）

> 承接 [`125-PR48之上的剩余优化空间`](125-PR48之上的剩余优化空间（实机分段账，2026-10-31）.zh.md) 与

## 0. 三条判词（先行，第一条是更正）

1. **125 的"头号候选"判错，原因是跨窗比较。** 同一台机器、同一对 `[LT]` 戳，同一段
   `32_load_end → 40_shown_begin` 在三批里的中位是 **993.9 / 309.6 / 281.2 ms** —— **3.4 倍的窗漂移**。
   125 把最先那批的 993.9 当成了结构性成本，并据此推出"关预热后降到 309.6 ⇒ 预热把钱挪进了这段"。
   **配对实测（同臂、只切 `FFF_NO_GPU_WARMUP`、14 轮交替）显示该段 Δ=+0.5 ms、两条条件两臂都是
   281.2 vs 227.3** ⇒ **预热根本不在这段里**，它在 Attach（`10_load_begin→11_attach_done`，
   379.3 vs 662.4，Δ=+283.2）。
2. **预热线程降优先级：无收益。** 把预热线程设成 `BelowNormal`（必须在 `Start()` 之前设，
   设在线程体内时工作已经开始）后，配对 14 轮：Attach **+47.9**（更慢）、布局 −11.7、
   `32_load_end→40_shown_begin` −0.1、终点 −56/−51/−27/−42 但 **p10–p90 跨零、符号不一致**
   ⇒ 落在该窗分辨水位内，**不能算收益**（该窗负载中位 56.5%，噪声明显偏大）。
3. **真正还剩的钱在 Attach 内部，而现在没人拆过它。** `10_load_begin → 11_attach_done`
   是本账里**唯一一个既大（379 ms）又在关键路径上、且内部一个子戳都没有的段**
   ——`ThisIsYourWindow1.Attach(Me)` 一行吃掉全部。要动它，先补子戳（§3）。

### 1.1 三批同段的窗漂移（这是 125 判错的直接原因）

| 批次 | n | 该段中位 | 范围 |
|---|---:|---:|---|
| `pr48_lm_png.csv`（125 用的那批） | 10 | **993.9** | 729.6–1,060.8 |
| `pr48_lm_nwarm.csv`（关预热，另一批） | 8 | **309.6** | 253.0–374.6 |
| `ab_warmup_paired.csv`（本轮配对） | 14+14 | **281.2 / 227.3** | 158.1–373.3 |

三批都在同一台机器上。**这说明该段的绝对值随窗口剧烈漂移（3.4 倍）**，
任何"先跑一批 A、再跑一批 B，然后比中位"的做法都会把它读成结构性差异。
⇒ 判据补一条：**跨批比较中位，在本机上等于随机**；必须同批交替配对（125 §7.1b 本来就写了这条，
我自己在 §2.1 又犯了，本轮已按此更正）。

## 2. 预热线程优先级实验（无收益，但排除了一个假设）

假设：预热线程目前是默认 `Normal`，与 UI 线程同档；Attach 是它的落点（+283.2）⇒
降到 `BelowNormal` 应让 UI 线程先跑，从而缩短 Attach。

实现要点（**踩了一次坑**）：优先级必须在 `预热线程.Start()` **之前**用 `.Priority` 设置。
第一版写在线程体内（`Thread.CurrentThread.Priority = ...`），那时 `GetD2DDevice()` 已经开始，
测到的不是"让让"而是"跑到一半才降"。

结果（同 exe，`FFF_WARMUP_PRIO=none` vs 默认 BelowNormal，14 轮交替，负载中位 56.5%）：

| 段 | Δ(B−A) 中位 | p10–p90 | B 更快 |
|---|---:|---|---:|
| Attach | **+47.9** | −51.9 … +132.6 | 5/14 |
| `30_renderer_started→31_layout_done` | −11.7 | −31.3 … +17.9 | 12/14 |
| `32_load_end→40_shown_begin` | −0.1 | −20.4 … +16.3 | 7/14 |
| 终点 `80_event_returned` | −42.6 | −315.9 … +221.7 | 10/14 |

⇒ **区间跨零、符号不一致 ⇒ 不可声称。** 该窗负载 56.5% 明显偏吵，属分辨水位内。
登记为"试过、无收益"，补丁留档 `perf_warmup_prio.patch`（未采纳）。

## 3. 下一个该拆的地方：Attach 内部（本账唯一的大黑盒）

| 段 | 绝对中位 | 内部子戳 |
|---|---:|---|
| `01_startup_end→10_load_begin`（框架起窗） | 245.6 | 无（框架内部） |
| **`10_load_begin→11_attach_done`（Attach）** | **379.3** | **无 ← 最大可拆项** |
| `20_post_probe→25_layers_done`（图层群） | 190.9 | 有 5 个子戳（24/25 之间可再拆） |
| `30_renderer_started→31_layout_done`（布局） | 77.4 | 无 |
| `32_load_end→40_shown_begin` | 281.2 | 无（框架显示序列） |

Attach 全部落在一行：`ThisIsYourWindow1.Attach(Me)`（`Form1.vb:97`）。
124 引用的 PR 自测分解是：**样式/DWM/拦截器/Chrome 覆盖层 282 ms + 首次渲染 328 ms
（其中 D3D/D2D/DXGI/DWrite 设备创建 266 ms）+ 尾部 GPU 请求 31 ms**。
而 PR 第 5 项（GPU 预热）已经把设备创建挪出这条栈——本轮实测 Attach 剩 **379.3 ms**，
与"282 + 62 + 31 ≈ 375"吻合 ⇒ **剩下的钱在"样式/DWM/拦截器/Chrome 覆盖层创建"那 282 ms 里**，
不在设备创建。

建议唯一动作：**在 Attach 内部补 4 枚子戳**（样式 / DWM / 拦截器 / Chrome 覆盖层），
用 `pr48_lm_ab.ps1 -EnvA/-EnvB` 先证"该段稳定可拆"，再谈怎么减。
`LakeUI` 侧改动（§126 已确认 `D3D_DeviceGlobals`/`ModernButton` 都在这里）属外部依赖，
需要独立分支与更大回归面。
