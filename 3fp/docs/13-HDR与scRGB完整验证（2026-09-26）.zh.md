# 3FP 图片模式 · HDR / scRGB 完整验证（2026-09-26）

> **本文档的定位**：补上 `docs/04` 标注为「本机不可验」的 **scRGB / HDR 输出路径**验证。
> 触发条件：用户于 2026-09-26 声明「**本机有 HDR 输出，进行完整验证处理**」。
>
> **结果一句话**：scRGB 输出路径**首次实机跑通**（`outBits=16`），并在验证过程中
> **发现并修复了一个真实的上游缺陷** —— **Display P3 等广色域源没能走 scRGB，而是被错误地落到 8-bit Rec.709 交换链上**。

> 超出 709 的颜色**无处可放** ⇒ 被静默裁掉。**"装不下"的是 Rec.709，不是 scRGB。**

## 4. 发现并修复的上游缺陷：广色域源被错误落到 SDR 交换链（没能走 scRGB）

> ⚠ **标题读法**：不是"scRGB 收不了 P3"，而是**"P3 没被送进 scRGB，反而落在了装不下它的 Rec.709 交换链上"**。
> 详见 §4.6 的方向澄清。

### 4.1 现象

Display P3 PNG 请求 `MapToHdr`，实测被**静默降级**为 `MapToSdr`（⇒ 落到 8-bit Rec.709 交换链）：

```
# 修复前（../build/hdr_verify/P3_before_fix.txt）
  [open] state=Ready requested=MapToHdr actual=MapToSdr isHdrSource=0
  [open] 1920x1080 outBits=8 ...
  primaries=BT.2020(9) transfer=IEC61966-2-1 (sRGB)(13) WIDE_GAMUT=1
```

`isHdrSource=0`（P3 的传递函数是 sRGB，**不是** HDR）但对 `WIDE_GAMUT=1`。

### 4.2 根因：同一功能**三处**实现，**两处错**（元发现 1）

三处色彩门禁，**全部只判 `IsHdrSource()`，全部漏判 `IsWideGamutSource()`**：

| # | 位置 | 时机 | 问题 |
|---|---|---|---|
| **1** | `PlayerSession.cpp` 公开 `SetColorMode` | **最早**（会话层） | `const auto forceSdr = mode == MapToHdr && snapshot_.isHdrSource == 0;` ⇒ **直接改写用户意图**为 `MapToSdr` ⇒ **短路在渲染器之前** |
| 2 | `VideoRenderer::SetWindow` | `Create` 时 | 只判 `IsHdrSource()` |
| 3 | `VideoRenderer::EnsureSwapChain` | 交换链创建 | 只判 `IsHdrSource()` —— **最终裁决点** |

**⚠ 关键陷阱 —— 时序**：

```
SetColorMode（常由宿主在打开前调用）
        ↓  ← 此时流尚未配置
ConfigureHdrStream（Open 走到这里才写 sourceWideGamut_）
```

`SetColorMode` 早于 `ConfigureHdrStream` 执行 ⇒ 此刻 `sourceWideGamut_` 仍是默认 `false`
⇒ 门禁读到的是**假值**。**"在读到假值的时刻改写用户意图"必然出错**。

> 佐证（探针）：`SetColorMode: wideGamut=0`（源未配置）→ 随后
> `ConfigureHdrStream: primaries=12 wideGamut=1`（P3 的 `SMPTE432`）。
>
> 另注：`GetImageInfo` 报 `primaries=BT.2020(9)` 而 `ConfigureHdrStream` 读到 `SMPTE432(12)`，
> 二者**不矛盾** —— 前者读**帧**（`PlayerSession.cpp:3102` 已把 P3 无损转到 BT.2020 容器），
> 后者读 `codecpar` 的**原始** primaries。

### 4.3 修复（4 处改动）

**改动 A / B —— `VideoRenderer.cpp`（`SetWindow` + `EnsureSwapChain`）**：

```cpp
// 统一判据：HDR 传递函数 **或** 宽色域 primaries
const auto sourceHdr = hdrProcessor_.IsHdrSource();
const auto wideGamut = IsWideGamutSource();
const auto wantsHdrPath = sourceHdr || wideGamut;
const auto nextMode = wantsHdrPath && OutputSupportsHdr() ?
    FFF3FPColorMode::MapToHdr : FFF3FPColorMode::MapToSdr;
const auto reason = wantsHdrPath ?
    "The target display or Windows Advanced Color mode does not support true HDR output." :
    "True HDR output is only available for HDR or wide-gamut sources.";
```

```cpp
// SetWindow
if (requestedMode_ == FFF3FPColorMode::MapToHdr) {
    const auto sourceHdr = hdrProcessor_.IsHdrSource();
    const auto wideGamut = IsWideGamutSource();
    actualMode_ = (sourceHdr || wideGamut) ? MapToHdr : MapToSdr;
    fallbackReason_ = (sourceHdr || wideGamut) ? std::string{} :
        "True HDR output is only available for HDR or wide-gamut sources.";
}
```

**改动 D —— `PlayerSession.cpp` 公开 `SetColorMode`：不再在会话层裁定**：

```cpp
// The gate is deliberately *not* applied here. At this point the stream may
// not be configured yet (SetColorMode commonly runs before Open reaches
// ConfigureHdrStream), so IsHdrSource()/IsWideGamutSource() can both read
// false for a source that is in fact HDR or wide gamut. Deciding now would
// silently rewrite the user's request — which is exactly how Display P3
// photos lost scRGB. Record the user's intent verbatim…
snapshot_.requestedColorMode = mode;          // ← 原样保留用户意图
const auto result = videoRenderer_.SetColorMode(mode, sdr, hdr, paper, forceHdrOutput);
```

**改动 E —— `PlayerSession.cpp:2224`（`Open` 收尾的 `ColorModeChanged`）文案改读渲染器（单一真源）**：

```cpp
Emit(FFF3FPEvent::ColorModeChanged,
    "{\"requested\":0,\"actual\":0,\"reason\":\"" +
    EscapeJson(videoRenderer_.FallbackReason().empty()
        ? std::string("True HDR output is only available for HDR or wide-gamut sources.")
        : videoRenderer_.FallbackReason()) + "\"}");
```

**改动 C —— `VideoRenderer::SetColorMode`**：原文本**已含**宽色域分支（`docs/04` 时代的改动），本轮**仅核对未改**。

### 4.4 ⚠ 我引入又移除的缺陷（反面记录）

第一版修复中我**多加了**一个 `ReevaluateColorMode()` 与 `promotedWideGamut` 分支（想在 `Open` 收尾时再评估一次）。
**A/B 实测证明它是错的**：HDR10 视频**默认 `MapToSdr`** 时被**误提升**为 `MapToHdr`（`SetColorMode: requested=2`）。

⇒ **已移除**（`ReevaluateColorMode` 声明与实现对、`Open` 收尾的 `promotedWideGamut` 分支）。
A/B 证实 **`EnsureSwapChain` 单独足够**：移除后 P3 仍 `outBits=16`、HDR10 默认模式不再被误提升。

> **教训**：「多点再评估」看似更保险，实际制造了**新的不对称缺陷**。
> **裁决点应当唯一** —— 收敛到 `EnsureSwapChain`（唯一知道交换链最终形态的地方）。

### 4.5 修复验证

| 用例 | 修复前 | 修复后 |
|---|---|---|
| Display P3 PNG `--hdr` | `actual=MapToSdr`、`outBits=8` | **`actual=MapToHdr`、`outBits=16`** ✅ |
| HDR10 视频**默认模式** | — | `[open] requested=MapToSdr actual=MapToSdr`（**未被误提升**）✅ |

### 4.6 ⚠ 产品含义（这不是优化，是正确性）

**色域容量的方向必须说清楚，别读反**：

| 路径 | 能否装下 P3 | 说明 |
|---|---|---|
| **scRGB 交换链**（16 位浮点） | ✅ **装得下，且远有余量** | scRGB 自有色域远超 Rec.2020，P3 ⊂ Rec.2020 ⇒ **P3 完整无损** |
| **8-bit Rec.709 交换链** | ❌ **装不下** | Rec.709 是最窄的 SDR 色域，P3 的红/绿超出它 ⇒ 超出部分**无处可放** |

缺陷的因果链是：**P3 源被错误落到了 Rec.709 交换链上** ⇒ 超出 709 的颜色**静默裁剪**
（用户看到的颜色是错的，**且没有任何提示**）。⇒ 属**正确性缺陷**，写 PR 时不要写成"画质增强"。

> ⚠ 反过来说：**"scRGB 表达不了 P3"是错的**。恰恰相反 —— **正因 scRGB 装得下 P3，才必须让 P3 走 scRGB**。

### 5.3 🔴 本轮遗漏并已修复：内核 DLL **双镜像未同步**（教训）

**脚本按设计只输出到 `x64/Release_anim/`**：

```
tools/build_kernel_manual.py:12-14
  输出重定向到 Release_anim（全新目录）……
  · 产物落在 x64/Release_anim/FFF.Native.dll，验证通过后再决定是否替换 Release。
```

⇒ **同步到 `x64/Release/` 与 `build/` 是人工步骤**。本轮我**漏了 `x64/Release/`**，直到收尾核对时才发现：

| 路径 | 收尾核对时 | 判定 |
|---|---|---|
| `build/FFF.Native.dll` | 766464 B @ 01:00:47 | ✅ 晚于源码，验证用的就是它 |
| `kernel/FFF.Native/x64/Release/FFF.Native.dll` | **765952 B @ 09-24 20:46** | ❌ **旧版，不含本轮修复** |

**⚠ 为什么危险**：`docs/10` §150 明确记载**两份 DLL 必须镜像同步**（项目纪律）。
若不修，后续任何人从 `x64/Release/` 取 DLL，拿到的都是**没有 P3 修复的旧版** —— 而**只在 `build/` 上跑的验证会全部通过**（假绿）。

**已修**：`cp build/FFF.Native.dll kernel/FFF.Native/x64/Release/FFF.Native.dll` ⇒ `cmp` **逐字节一致**（766464 B）。

⇒ **新增硬校验（必须做）**：每次重编后 **`cmp` 两份镜像**，不能只看 `mtime`。
`mtime` 只能证明"某一份是新的"，**证明不了"两份是同一份"**。
（与元发现 7「工具层陷阱会伪造整个结论」同类：**校验必须覆盖全部产物副本**。）

### 5.4 ✅ 验证有效性确认：探针确实加载了新版 DLL
