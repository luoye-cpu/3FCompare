# 82 · 动图管线机制剖析（2026-10-10）

> 问题：动图的性能异常，是不是**管线机制缺少优化**造成的？
> 答：**一部分是（三条断链，可修）；最大的一笔不是**——它是"回绕清空解码流水线"的固有代价，再加一档优化救不到它。
> 取证：`3fp/build/anim-perf/`（`v2_*` 全量、`v4_*` 判据复核、`v5_*`/`v6_*` 线程对照、`v7_*` 降采样与硬解对照）。
> ⚠ **同轮比同轮**：10-10 当天同机有负载，同一份 4K 素材的每秒 CPU 从昨晚 86–92% 漂到 140%（`v5_4k_15s.txt` 复跑仍是 140.6% ⇒ 不是窗口长度）。本文所有百分比只在**同一轮内**成立。

---

## 1. 一条帧在动图路里走的完整链（带"谁在把关"）

```
av_read_frame → 包队列(64 包/16MB) → [闸门 A] DecodePendingPacket
   → 解码器（FF_THREAD_FRAME|FF_THREAD_SLICE，线程数=闸门 B 选的）
   → receiveFrames() 排空循环（一次可推 N 帧）        ← ★ 这里没有逐帧闸门
   → QueueVideoFrame → videoFrameQueue_（预算 128MB）  ← ★ 预算只在"解一个包之前"判一次
   → [闸门 C] PumpVideoPresentation：position ≤ now+2ms 才呈现
   → PresentVideoFrame：（可选 P3→2020，仅静图）→ sws_scale 转换 → UpdateSubresource 上传
   → Present(1,0) 等 vsync（`VideoRenderer.cpp:6181`；节拍 `presentationFrameRate_` = 实测刷新率
     `:2046`，由呈现线程 `TimedTextThread` 驱动 `VideoRenderer.h:441,689`）
   → EOF：FlushAtEnd → 若 sessionWrapLoop_ → DoSeek(0)
            = ClearVideoQueue + avcodec_flush_buffers + ResetClock + RebuildMediaInfo   ← ★ 接缝在这里
```

**实测到每一环的分量**（4K APNG，`decode_profile --render` 与 audit 的内核计数器）：内核自己计得了的墙钟段只有 **转换 3.68 + PresentWait 2.62 = 6.31ms/帧**，而整进程 **89–140ms/帧** ⇒ **九成以上在未计量的解码段**。8K 更极端：39.33 / 897.92 = 4%。

## 2. 三条"确实缺的优化"（都能当场指认断在哪）

### 断链① 【10-10 由 lane-R4 更正】降采样在宿主**有**接线，只是默认值为 0
我原来写"两棵树的宿主都没写这个字段 ⇒ 产品里这条路恒关"——**那是假缺席**：我用英文字段名 grep，而 VB 侧标识符是中文。
实况：`3fp/kernel/FFF.Player/Core/播放器会话.vb:81` 有 `.自适应CPU预缩放 = 0UI`；interop 配置结构体 22 字段 / 112B，已过内核尺寸门（`PlayerSession.cpp:618-626`）。
⇒ 内核侧默认 `configuration.adaptiveDownscaleBeforeUpload != 0` 不成立（值为 0）+ 断链② 的传感器失配 + 断链③ 的作用阶段，才是这条优化的真实断点。**A7 的宿主工作从"接线"降级为"给一个设值/设置项"。**
（教训归位：负断言前必须回看命中行——命中的语言不对，等于没搜。）

### 断链② 它的传感器对动图失效（接上也不触发）
- 触发条件是 **30 帧窗口内丢帧率 ≥ 阈值**（`VideoRenderer.cpp:3931-3946`）。
- 实测：4K APNG 每轮长停 12 次、节奏被拉长到 106ms，**打开 `ACA_DOWNSCALE_PCT=5` 后日志里没有 `engaged` 行**（`v7_4k_ds5.txt`）⇒ 动图的失效形式是**拉长接缝而不是丢帧**，丢帧率传感器看不见它。
- 反面对照成立：6K APNG（真在丢帧，净增 13）打开后 **`[adaptive] downscale-before-upload engaged (drops 6%)`**（`v7_6k_ds5.txt`）⇒ 传感器本身没坏，是**没覆盖动图这种形状**。

### 断链③ 降采样插错级——它在解码之后，救不到瓶颈
- `PrepareAdaptiveDownscale` 用 `sws_scale(全尺寸源帧 → 输出尺寸)`（`:3963-3964`、`:3986`），省的是**上传字节与 GPU 填充**，源帧照旧全尺寸解压、照旧整帧读。
- 实测 6K 打开后：私有 **1495 → 1068 MB（−427MB）** ✅ 内存有效；但 **fps 8.48 → 8.35、CPU 233.8% → 247.4%** ❌ 算力瓶颈无效甚至略亏（多一级 scaler）。
- ⇒ 结论要写死：**"上传前降采样"对动图是内存药，不是 CPU 药**。真要治 CPU，得在**解码前**决定尺寸（`AVCodecContext.width/height` 对 PNG 无解、`apply_cropping`/缩放解码器也不适用），或者**换掉"每轮全量重解"这件事本身**。

### 附带：动图拿不到硬件解码（实测确认，不是推测）
- 请求 `Gpu` 跑 4K APNG：首行与末行 `解码路=1`（枚举 `Cpu=1`，`FFF.Player.Api.h:9`），CPU 141.9% ≈ 默认档 140.5%（`v7_4k_gpu.txt`）⇒ **零收益，落回 CPU**。GIF/APNG/WebP 没有硬件解码器，这是源格式决定的，不是接线问题。

## 3. 最大的一笔不是"缺优化"：回绕 = 解码流水线重灌

**闸门 B（线程选择）与队列深度的耦合，被线程扫描量到了：**

| 钉死的线程数 | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| 队列峰值（4K APNG，同轮） | **2** | **2** | **4** | **8** | **8**（上限） |
| 接缝超额 | +55.6ms | +59.1 | +64.0 | +65.1 | +80.4 |
- 代码解释：解码器带 `FF_THREAD_FRAME`（`PlayerSession.cpp:2275`）时**要先攒够 thread_count 帧才开始出帧**；`receiveFrames()` 是"一次解包、把可用帧排空推完"的循环（`:3351-3358`），而 128MB 队列预算只在"取下一个包之前"判一次（`:2849`）。**⇒ 队列深度 = 流水线深度，预算绕不过去**：4K 单帧 33.2MB、预算 128MB 只允许 4 帧，实测到 8（`v2_audit_apng_4k`、`audit/4k_thr_*`），私有内存 **670MB ≈ 20 帧的量**。
- 回绕处 `DoSeek(0)` 做 `ClearVideoQueue + avcodec_flush_buffers`（`:4244/:4246`）⇒ 流水线被倒空，下一轮**从第 0 帧重新攒满**。
- **同轮配对（LSP 接缝超额 vs 同素材 audit 每帧 CPU）**——这才是可用的等式，注意它比我上一版写的更严格：

| 素材（同一轮 v2） | 接缝超额 | 每帧 CPU | 比值 |
|---|---|---|---|
| APNG 640 | **+0.38ms** | 6.90ms | 0.06 |
| APNG 1080p | **+30.46ms** | 30.59ms | **1.00** |
| APNG 4K | **+157.30ms** | 135.91ms | 1.16 |
| APNG 6K | **+404.00ms** | 280.37ms | 1.44 |
| GIF 1080p | **+31.32ms** | 11.33ms | 2.77 |

⇒ 精确说法是：**接缝超额 ≈ 重灌 D 帧（D = 队列深度 = 解码线程数）所需的"墙钟"时间**，只有当它**超过帧周期余量**时才现形：640 时整批重灌在周期内被吸收（+0.38ms），1080p 起按超出量现形。
⇒ **GIF 1080p 是对称的反证**：它的每帧 CPU 只有 APNG 的 1/2.7，接缝却几乎相同（31.3 vs 30.5）⇒ 决定接缝的是**墙钟重灌**（GIF 解码基本不并行 ⇒ 墙钟≈CPU；APNG 8 线程并行 ⇒ 墙钟≈CPU/线程数×深度），**不是 CPU 总量**。这一条正是 O7（把深度压到 ≤4）应当验证的假设：若接缝随深度近似线性下降，机制成立；若不降，docs/81 O2 的三个候选全部作废。
- **它不随并行度下降**：更多线程让"单帧墙钟"变短，但"重灌深度"同步变深，两者反向抵消 ⇒ 这才是"接缝超额随线程数**递增**（55.6→80.4）"这个反直觉读数的来源，也是**"回绕首帧解码暴露在关键路径"那句被推翻**后的替代解释。

⇒ 治它的手段不是再加一档优化，而是三选一（爆炸半径从小到大，见 docs/81 O2）：**回绕不清队列**、**跨 EOF 预灌**、**让 APNG 也走 demuxer 自回绕**（后者要先在新 FFmpeg 上复跑 `apng_seek_repro` 确认 `-22` 是否仍在）。

## 4. 判词

| 问 | 答 | 依据 |
|---|---|---|
| 动图管线有"缺优化"吗 | **有，三条断链**：宿主没接降采样；传感器对动图失效；降采样插在读码之后救不到 CPU | §2，均有实跑日志 |
| 性能异常是它们造成的吗 | **主要不是**。4K/6K 的每帧成本九成在解码段，而这三条链都作用不到解码段；能作用到的那条（降采样）实测只把内存从 1495 砍到 1068MB，fps 反而 8.48→8.35 | §1 §2③ |
| 那异常的主因是什么 | ①intra-only 动图**必然 CPU 解压**（硬解实测零收益）；②**回绕 = 流水线重灌**，其代价 ≈ 一帧总解码 CPU，且不随线程数下降；③**线程基线是常数**（8/16）而非按 deadline 推，在动图上买并行不买延迟 | §2附带 §3 |
| 有没有"接上就治好"的便宜开关 | **没有**。降采样接上只对"真在丢帧"的档位（6K/4K-WebP）生效，且只省内存；动图专属的形状要靠**新传感器**（长停率/节奏偏移）而不是复用丢帧率 | §2①②③ |

## 5. 由此新增的优化项（并入 docs/81 的分期）

| 项 | 内容 | 出片判据 |
|---|---|---|
| **O6** | 给降采样加**动图专属触发**：以"长停率/节奏偏移"为第二传感器（复用带牙探针已定的相对阈值：>1.5× 稳态中位），与丢帧率并联 | 4K APNG 打开后必须打出 `engaged`；且 fps 不许低于关闭时（今天实测 8.48→8.35 就是反例，说明必须同时要求**不恶化**） |
| ~~O7~~ **已否决** | 队列预算逐帧判定 ——**实测否决**：帧已出 `avcodec_receive_frame`，拒绝入队＝丢帧（见 docs/83 §4②）。改为"把解码器流水线帧计入内存账" | 见 docs/83 |
| **O9′** | 回绕不重开流水线的**第一版实现**（前缀预灌）已写过并实测：4K 接缝 **+81.7 → +31.0ms**，但**净增丢帧 19、帧序重复** ⇒ 形态不安全，**已完整撤销**（撤销后复核 +82.61ms、丢帧 0、DLL 回到基线 905216 B）。§3 的"重灌是主因"因此**被部分证实** | 全过程与下一步形态（whole-loop cache，一轮 ≤ 预算则完全不碰解码器）见 **docs/83** |
| **O8** | 宿主接线：把 `adaptiveDownscaleBeforeUpload`/`DropPercent` 补进 interop 的结构体（两棵树现在都没这两行） | 结构体尺寸 ≥ `offsetof(...,adaptiveDownscaleDropPercent)+4`（否则内核按"短结构体=关"处理，`:619-622`），并有一条"字段真被内核读到"的读数 |
| **O9** | 回绕策略（=docs/81 O2）：优先级低于 O7，因为 O7 一旦把深度压到 4，接缝成本近似减半——**先用 O7 验证 2× 假设，再决定要不要动回绕** | 若 O7 后接缝随队列峰值近似线性下降 ⇒ 证实"重灌深度"是主因；若不降 ⇒ O2 的三个候选全部作废，回头再查 |

**顺序**：`O7 → O9 的判定 → O6 → O8`。O7 是最便宜的一刀（只在排空循环里加一次判定），而且它的读数（队列峰值、私有内存）现在就能量。
