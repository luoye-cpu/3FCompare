## 二、改进空间清单（按优先级）

### P0 · 防坏（门槛级，改动小）

1. **发布门禁加"bundle 必含原生库"自检**：脚本已有 `UnexpectedFiles`（防多）检查，补一条"防少"——publish 后断言 bundle 内含 `FFF.Native.dll` + libass 闭包。防两类事故：绕过脚本的裸 publish（本轮实证会产出坏 exe）、未来 SDK 升级改变捆绑行为。落点：脚本末尾（.NET HostModel 的 `ManifestReader`/解包断言）或独立 target。
2. **仓库加 `global.json` 钉 SDK**：上游仓库无 SDK pin，SDK 漂移既影响构建语义也影响交付形态；PR #40 正在做 .NET 11 readiness，pin 版本是配套动作。

### P1 · 体验/性能（有实测收益账）

3. **R2R 上车——✅ 已实施（2026-10-29，本轮）**：`发布3FP单文件.ps1` 新增参数与参数包（默认开，`-NoReadyToRun` 可退回；勿同时开 EmitSymbols，与 DebugType=None 冲突）。两臂端到端验收：rel_il **45,593,664 B** / rel_r2r **53,429,824 B**，**R2R 增量 = 7,836,160 B（与散装/单文件两个口径完全一致）**；原生库照常捆绑（ass-9/harfbuzz/FFF.Native 扫描命中）；API 版本四重校验、字段数校验、框架配对全绿。注：本地产物绝对值偏大是本机内核构建 5.6 MB vs 上游发布内核 1.02 MB（差异未归因，可能发布侧另有瘦身）；上游同款 IL 38.1 MB + 7.84 ≈ **46 MB**。脚本改动落在 `3fp/kernel/tools/发布3FP单文件.ps1`（上游 main 工作树未提交补丁，即上游 PR 的内容）。
4. **LakeUI 交付形态查证与修复**：上游 ship 的 LakeUI.dll 是 Debug-IL 还是 Release-IL **待查证**（托管件不解压，bundle 内抽取未做）；若为 Debug-IL（`DebuggableAttribute=263` 含 DisableOptimizations，本机 LakeUI 实证），则整个 UI 框架以无优化 JIT 交付——修 HintPath/发布参数用 Release 产物，方向 −57 ms（本机 A/B）+ 稳态每帧收益。
5. **FFmpeg 交付缺口**（上游"单文件"实际不开箱的最大原因）：三个子项——
   (a) 发布页给"配套 FFmpeg 构建"的精确版本/sha256/放置说明（docs/102 实测 lgpl-shared 与 nonfree-shared 功能面不同，会改变格式覆盖）；
   (b) 应用内依赖闭包探测补二阶依赖（libplacebo→libshaderc 实证落 PATH），报错给可执行指引；
   (c) 可选：官方提供 LGPL-shared 配套 zip（nonfree 不可再分发是硬约束，这正是上游不捆 FFmpeg 的合理部分——改进空间在"说清"而非"捆上"）。

### P2 · 打磨

6. **Authenticode 签名**：exe 未签名（实测）——AV/SmartScreen 摩擦的根因之一；本轮实测解压首跑 `Error code: 5` 一次（MotW），签名是标准缓解。
7. **解压目录文档化**：`DOTNET_BUNDLE_EXTRACT_BASE_DIR` 可把 %TEMP% 吐库指到稳定目录（企业/清理敏感场景）。
8. **Recorder 同标准**：`FFF.Recorder.exe` 35.8 MB 同机制，P0/P1 各项同批受益。

### 明确不建议（已论证不可行/不合算）

- 单文件压缩（NETSDK1176：框架依赖不支持；自包含捆运行时反大）。
- trimming / NativeAOT（WinForms + VB 不可行）。
- 捆 FFmpeg 进单文件（+110 MB 首跑解压 + nonfree 再分发约束）。

## 五、体积还能压吗——构成解剖与最终方向（2026-10-29）

**结论先行（2026-10-29 二次修正）：剔除 `Microsoft.Windows.SDK.NET.dll` 的尝试被引用闭包证伪（Vortice.Mathematics 引用它，§六）——38.1 MB 维持「贴近形态下限」的原判；本轮落地的可提交成果是「引用⇒随包」配对护栏（kernel main commit `d8ae827`），锁死未来的坏交付。**

构成解剖（上游 38.1 MB 单文件）：

| 成分 | 体积 | 占比 | 可压性 |
|---|---:|---:|---|
| `Microsoft.Windows.SDK.NET.dll`（WinRT/CsWinRT 投影，纯 IL） | ~27.2 MB | **~71%** | ❌ 不可剔除（Vortice.Mathematics 引用闭包，§六证伪） |
| 托管 app（FFF.Player + LakeUI + Svg/ExCSS/Vortice 系） | ~6.3 MB | ~17% | 已是纯 IL；R2R 反而 +7.84 MB（性能换体积的决策，已做开关） |
| 原生捆绑件（FFF.Native 1.02 + libass 族 + 光盘库） | ~6.3 MB | ~17%* | 功能必需；上游内核已很小 |
| apphost | ~0.3 MB | ~1% | — |

*占比按上游 38.1 口径，两项相加超 100% 系组件版本差异的近似。

剔除尝试已证伪撤回；若未来真要动它，唯一可能安全的路线是收缩投影面：TFM/`WindowsSdkPackageVersion` 钉旧版（19041）——`Windows.Foundation` 核心类型自 10240 就在，与 Vortice.Mathematics 的引用大概率兼容，但必须实测后才能落地（§五.4）。

逐条排查：
1. **压缩捆绑**：NETSDK1176——框架依赖单文件不支持压缩（实测报错）；自包含+压缩要捆整个运行时反而大几十 MB；自包含+trimming 因 WinForms 不支持走不通。⇒ **全堵**。
2. **运行时去重**（假设桌面运行时自带 SDK.NET 就能不捆）：实测 **不成立**——WindowsDesktop.App 10.0.14 的 63 个 dll 里 0 个 `Microsoft.Windows.SDK.NET.dll`，框架依赖应用必须自带——**且自身也不能剔（§六证伪）**。
3. **trimming / NativeAOT**：WinForms（+VB）不支持，维持不建议。
4. **剩余真实杠杆：收缩 SDK 投影面**——TFM/`WindowsSdkPackageVersion` 钉旧版（19041）需先做 API 审计 + **Vortice.Mathematics 引用面兼容性验证**（它引用的 `Windows.Foundation` 核心类型自 10240 就在，兼容概率高但须实测），投影预计 −5~10 MB 级（未实测）。
5. **自定义压缩捆绑**（原生库 zlib 化 + 自管解压）：技术可行但只省 ~3 MB、引入自维护解压路径，不建议。

另记录：本机构建的 FFF.Native.dll（5.62 MB）与上游发布内核（1.02 MB）差 4.6 MB，未归因（可能上游发布侧另有 strip/瘦身步骤）——若属实，这本身也是一个发布侧优化点，值得向上游问一句。

## 六、`Microsoft.Windows.SDK.NET.dll` 专项：27.2 MB 死重，可整体剔除（2026-10-29）

### 6.1 它是什么、为什么在包里

CsWinRT 生成的全量 Windows SDK 投影（覆盖 `windows10.0.26100.0` TFM 的全部 WinRT API 面）。.NET SDK 对 windows-TFM 工程**自动注入** `Microsoft.Windows.SDK.NET.Ref` 包并随 publish 复制/捆入——**与应用是否真的使用 WinRT 无关**。体积随 SDK API 面增长（26100 口径 27.2 MB，纯 IL——RTR 魔数扫描阴性，R2R publish 时 crossgen2 也未编译它）。

### 6.2 零引用实证

| 检查 | 结果 |
|---|---|
| FFF.Player.dll 引用表（`GetReferencedAssemblies`） | **无** Microsoft.Windows.SDK.NET |
| LakeUI.dll 引用表（41 个引用） | **无** |
| 宿主源码 WinRT 使用（`Windows.Graphics/Foundation/Storage/…` 全量 rg） | **0 命中**；`WinRT.`/IAsync 0 命中 |
| 其余随包托管件（Svg/ExCSS/Vortice/SharpGen） | 无 WinRT 引用（SharpGen 纯 COM 互操作） |
| 桌面运行时自带？ | WindowsDesktop.App 10.0.14：63 个 dll 中 0 个 SDK.NET ⇒ 运行时不会提供，但应用也不需要 |

> **三轮深扫补记（2026-10-29）**：对 Vortice.Mathematics（68 型）做了三轮反射扫描——①成员签名（返回/参数/字段）、②接口表与基类链、③类型与成员级特性的 `typeof()` 实参——**全部零使用**。即 SDK.NET 的 AssemblyRef 存在于元数据（字节扫描+引用表实证）却找不到任何反射可见的使用点：**大概率是休眠引用**（藏在 IL 体内联 token/泛型约束/修饰符等反射盲区）。但这不构成可剔除证明：证明休眠需要 IL 体级 token 全扫（需 SRM 小工具，未做），而「大概率不炸」不满足消费级交付标准——这正是护栏判「不可剔」的依据。正路：a) 向上游 Vortice/cswinrt 报告该休眠 AssemblyRef 请其修链；b) IL 体级 token 扫描证明休眠后带白名单剔除；c) 投影降级 19041。

### 6.3 运行时双判据实测（剔除后照常工作）

把宿主运行目录的 `Microsoft.Windows.SDK.NET.dll` 挪走后实机验证：
- startup_image_time 2 轮：正常出窗出图（ContentStdDev 48.7–72.3）；
- **6 秒窗口标题判据**：主窗口标题 = `sample_1920.png`（图片模式已打开文件），与带 SDK.NET 的对照臂**逐字符一致**。
- 验证后已恢复原位（文件在位核验 True）。

### 6.4 建议落地方式（上游 PR 内容）

1. 发布 target 剔除（散装与单文件两条路径都覆盖；**两件一起**：投影 dll + CsWinRT 编组运行时）：
   ```xml
   <Target Name="DropUnusedWindowsSdkProjections" AfterTargets="ComputeFilesToPublish"
           BeforeTargets="GenerateSingleFileBundle">
     <ItemGroup>
       <ResolvedFileToPublish Remove="@(ResolvedFileToPublish)"
         Condition="'%(Filename)%(Extension)' == 'Microsoft.Windows.SDK.NET.dll' Or
                    '%(Filename)%(Extension)' == 'WinRT.Runtime.dll'" />
     </ItemGroup>
   </Target>
   ```
2. **配套护栏（必须）**：构建期断言引用闭包中无 `Microsoft.Windows.SDK.NET` / `WinRT.Runtime` 引用（有则 error，提示重新加回包）——防将来有人引入 WinRT 使用后运行时才炸。WinRT 经字符串反射激活的面也要在审计时一并排除（本轮源码扫描 0 命中）。
3. 落地后发布冒烟必须覆盖开图 + 播放 + 字幕/弹幕等全部功能面（本轮已验开图；播放/字幕路径同样无 WinRT 引用，风险低但按流程走一遍）。

## 十、SDK.NET 本身能降体积吗——版本扫掠与裁剪可达性（2026-10-29）

问题：投影不能剔（§六），那它自己呢？三路实测。

### 10.1 消费者真实引用面（理论下限的依据）

对全部随包托管件做 Windows.* 字节扫描：真正的 WinRT 引用面只有 **Windows.Foundation 一族**（Point/Rect/Size/IClosable/IAsyncOperation 系列/IMap/IVector 等 ~30 型，全为 10240 时代核心类型）+ `WinRT.Runtime` 自身 30 个内部引用；其余 **620 个命名空间无人引用**。理论裁剪下限 ~2-4 MB（−85%+）。注意：早先正则抓到的 "Windows.Forms.*" 命中是 System.Windows.Forms（非 WinRT）。

### 10.2 官方版本扫掠（7 版实测，一行属性 `WindowsSdkPackageVersion` 即可切换）

| Ref 版本 | SDK.NET 体积 | 启动验证 |
|---|---:|---|
| 10.0.19041.7（net5 时代） | 30.5 MB（**反而最大**） | 未测（尺寸已劣） |
| 10.0.20348.87 | 25.2 MB | ❌ 启动即「Microsoft .NET」host 错误框 |
| 10.0.22000.87 | 25.7 MB | ❌ 同上 |
| 10.0.22621.87 | 26.2 MB | ❌ 同上 |
| 10.0.22621.28 | 20.7 MB | ❌ 同上（正规 publish、deps 一致仍失败） |
| **10.0.26100.86（SDK 当前默认，上游现状）** | **27.2 MB** | ✅ 唯一启动正常（历史多次冒烟） |
| 10.0.26100.1 | 21.9 MB | ❌ 同上 |

**解读**：Ref 包与 SDK/运行时代强耦合——旧版包的 deps/runtime 元数据与 GA 运行时不匹配，host 拒载（错误框正文两次抓取被进程树问题打断，判据为标题「Microsoft .NET」+ 6 秒无开图）。**27.2 MB 就是官方途径的地板**，「旧版更小」不成立（19041 反而最大）。

### 10.3 非官方途径（技术可行、不支持不建议）

- **IL 裁剪官方件保身份**：MIT 许可、.NET Core 不验强名 → 裁到消费者闭包 ~2-4 MB 技术可行；代价 = 修改微软签名件、每次 Ref 更新重做、护栏语义重写。
- **自建 cswinrt 子集投影**：破强名身份绑定（Vortice 按 token 引用），同上不支持。
- **IL 体级 token 手术**：同上。

### 10.4 结论

**SDK.NET 自身无官方支持的降体积途径，27.2 MB（Ref 10.0.26100.86）是当前 SDK 形态的地板。** 体积路线收束为两条正道：框架依赖 38.1 MB（现状，若上游接受 R2R 则 ≈46 MB）或自包含 + 压缩 77.6 MB（全打包、零前置）。

证据：`sdknet_versions.csv`、`pub_small\`(19041.7)、`pub_22621\`(22621.28)、`pub_26100_1\`、`pub_v*\`（扫掠目录）、`sdknet_parse.txt`、`parse_sdknet.ps1`。

|---|---|

### 8.2 它到底是干啥的

WinRT 组件以 `.winmd` 元数据 + OS 内 activation factory 的形式存在，.NET（Core）不能像老时代那样直接吃 `.winmd` → 微软官方机制是 **CsWinRT 生成「投影程序集」**：把整个 Windows SDK 的每个 API 翻译成 C# 可调用的类型。本 dll 就是「全量 Windows SDK 的 .NET 调用说明书」：自身零原生代码，真正实现在 OS 的 `Windows.Xxx.dll` 里，运行时经 `RoGetActivationFactory` 激活。实测样本 `Windows.Graphics.Display.DisplayInformation`（37 方法/12 属性/6 事件）完整呈现投影三件套：`GetForCurrentView()` 静态工厂、`FromAbi(IntPtr)` 原生指针包装、`As[I]()` 接口转换 + `add_/remove_` 事件对。

### 8.3 全量普查读数

| 维度 | 读数 |
|---|---|
| 类型总数 | **9,695**（classes 4,229 / interfaces 385 / structs 3,493 / enums 1,588） |
| 命名空间 | **624 个**，Top：UI.Composition 134、Media.Capture 124、Networking.NetworkOperators 120、ApplicationModel.Activation 116、Media.Core 115…（媒体/网络/设备/后台任务——与播放器实际用面无关） |
| **ABI 孪生层** | **3,868 型（≈40%）**——每个投影类型配一个 `ABI.Windows.*` COM 包装（vtable 指针接口），类型数直接翻倍 |
| 泛型 | 42 |
| 体形态 | 纯 IL（无 RTR 魔数）；27.2 MB 主体是 624 域的元数据 + 薄包装体 |

### 8.4 结论

它是「整个 Windows SDK 的 .NET 翻译层」，尺寸由 **SDK API 面**（不是应用用量）决定；对零 WinRT 使用的 3FP 而言，连同 `WinRT.Runtime.dll` 共 **~27.8 MB 全部为死重**——但引用闭包（Vortice）不可剔，落地为配对护栏（§六）。

## 九、AOT 方向专项：七步试验矩阵与结论（2026-10-29）

用户指令：试试 NativeAOT 方向。结论先行：**当前无可实现路径——四道门逐层实测，最后一道是 ILC 对中文资源名的确定性崩溃（两个 SDK 版本一致）；且这还是编译层，运行层（STJ 反射/LateBinding/LakeUI）尚未开始。**

### 9.1 试验矩阵（全部本机实测）

| # | 命令要点 | 结果 |
|---|---|---|
| A1 | 原样 + `PublishAot=true` | ❌ 「Cross-OS native compilation is not supported」——ILCompiler 包的门：TFM `windows10.0.26100.0` 被推导为 `_targetOS=windows ≠ win`（targets:63 判定条件实读） |
| A2 | + `DisableUnsupportedError=true` | 过门，下一层 ❌「Platform linker not found」——包内 `findvcvarsall.bat` 定位 MSVC 失败（vswhere 本身正常返回 VS18，bat 内部 vcvarsall/`where link` 链条退出 1，手动跑 vcvarsall 正常） |
| A3 | + 完整 MSVC PATH/INCLUDE/LIB | 同 A2（该 bat 不吃环境变量，走自己的发现链） |
| A4 | + `IlcUseEnvironmentalTools=true`（官方旁路，直接用环境 link.exe） | 过链接器发现，下一层 ❌ **NETSDK1102**「请确保你发布的是独立应用」——vbproj 写死的 `SelfContained=False` 压过了 AOT 隐含的自包含 |
| A5 | + `SelfContained=true` | **ILC 真正开始编译**，❌ 崩溃：`duplicate key: FFF_Player_FFF_Player_Form_____________`（ILC 10.0.13）——中文窗体资源名下划线化后在 ILC 资源去重字典撞键 |
| A6 | 换 SDK 10.0.403（上游当日 SDK 线，ILC 10.0.14） | ❌ 官方门 **NETSDK1175**「启用剪裁时，不支持或不推荐使用 Windows 窗体」（SDK 10 显式门禁，SDK 11-rc2 未拦） |

另实测：上游 exe 与我方同源发布均为**框架依赖**（非自包含，docs/105 §七）；NativeAOT 必然自包含（A5 已证 vbproj 的 `SelfContained=False` 需显式覆盖）。

### 9.2 崩溃本体与定位

`FFF.Player` 的嵌入资源名含中文窗体名（如 `FFF.Player.Form设置_….resources`），ILC 去重时把非 ASCII 字符下划线化 → 不同资源撞成同一 key → ILC 内部 `Dictionary.Add` 抛「An item with the same key has already been added」（两版本 ILC 一致）。这是 ILC 对 CJK WinForms 工程的确定性崩溃类，与本仓库无关的复现条件：VB/WinForms + 中文窗体名 + PublishAot。

### 9.3 若上游坚持 AOT 的前置清单（按依赖顺序）

1. **ILC 崩溃修复**：向 dotnet/runtime 报告 CJK 资源名去重崩溃（可给最小复现：VB WinForms + 中文窗体 + PublishAot），或把全部嵌入资源改 ASCII 名（改 ~15 个 resx 的 manifest 名 + 对应 ComponentResourceManager 代码串，侵入面不小）。
2. **运行时面 AOT 化**：`设置` 的 `JsonSerializer` 反射序列化（AOT 下默认禁用）→ STJ source-gen；VB LateBinding 残留点排查（`Microsoft.VisualBasic.CompilerServices.NewLateBinding`）；WinForms NativeAOT 本身仍是官方「未正式支持」状态（dotnet/runtime #127049，2026-04）。
3. **LakeUI（商业闭源件）AOT 兼容性**：反射/动态模式需供应商确认，宿主侧无法自行解决。
4. 收益盘点：AOT 唯一对应的是启动账里 ~1.25 s 的三段托管 JIT gap（docs/103）→ T2 理论可进 ~800 ms 档；代价 = 放弃框架依赖形态、交付体积可能反增（WinForms AOT 产物 ~50 MB 级）。**性价比远劣于已落地的 R2R（−74~141 ms、+7.84 MB）**。

### 9.4 建议

维持 **R2R 路线**（已上车，脚本开关已做）；把 §9.2 的 ILC 崩溃作为独立 issue 报 dotnet/runtime（惠及所有 CJK WinForms 工程）；AOT 作为远期观察项，等三件事同时成立再重启：ILC CJK 资源修复 + WinForms AOT 官方 GA + LakeUI 供应商兼容声明。

## 十二、NET.11 收益专项（2026-10-29，实测）

问题：切到 .NET 11（当前 RC2，11 月底 GA）有多少收益？宿主已具 net11 能力（PR #40 readiness + `NetTFM` 参数），本机有 SDK/桌面运行时 11.0.0-rc.2。全部实测：

## 十三、上游发布不携带 IAMF 的影响分析（2026-10-29）

背景：上游发布内核（1.02 MB）实测为 **HaveLibiamf=false 条件编译**（无 IAMF 空间音频），而 main 代码带完整的 IAMF 条件集成（`HaveLibiamf` 自动探测 + `FFF_FORCE_LIBIAMF` 门禁）。不携带会有什么问题？

### 13.1 功能面：设计内降级，不会坏

- 无 libiamf 内核有**显式回退分支**（IamfAudioDecoder.cpp 六处 `#if !FFF_WITH_LIBIAMF`）；
- 宿主有配套用户话术：播放器控制器.vb:1654「IAMF 空间音频已回退到常规解码，声场以容器声明为准」（含回退原因字段）；UI 声明（Form1.vb:745-754，产品拍板「UI 声明即可」）基于快照 IAMF 声道数，无 IAMF 时不误报。
- ⇒ 播放 IAMF 内容**不会失败到打不开**：回退常规解码，损失的是空间声场渲染（对象音频/双耳），不是崩溃。

### 13.2 真正的问题：四条（都在声明与一致性层面）

1. **声明缺位（含直接实证）**：① 2026.10.28 V2 的 GitHub release 页面**正文为空**（只有资产列表，无任何更新说明）——官方从未在更新说明里写过「内置 IAMF」；② README 把 `准备Libiamf.ps1` 列为构建必需（还强调 /MD 要求），但官方发布不带 → 「文档暗示、发布不含」；③ README 称「没跑过会链接失败」与当前条件编译行为**不符**（实测无 libiamf 构建成功 1.01 MB）。**「内置」印象的真实来源**：(a) README 把 IAMF 列为标准构建三步之一；(b) 程序界面里存在「启用空间音频」开关与「IAMF 空间音频」UI 文案（随发布交付的宿主字符串）；(c) 播放 IAMF 内容时那句「已回退」提示——它反而证明没内置；(d) 提交历史里的 IAMF 大改（full-reload/bed-render 重构）。
2. **交付分叉**：同一 main 两种交付形态——官方发布（无 IAMF，1.02 MB）vs 源码构建（有 libiamf，5.6 MB）→ 用户反馈出现「我有空间音频声道显示、你那边没有」的分叉，支持成本上升。
3. **可发现性**：`准备Libiamf.ps1` 存在但 release 通道不提供也不提及，想要 IAMF 的用户必须自行走完 absl/opus/FLAC 构建链（依赖重）。
4. **下游不对称**：本工作区 3FC 出货内核**带 IAMF**（构建机已准备 libiamf）→ 3FC 用户拥有上游官方发布用户没有的功能——「main 有代码、发布不带」造成的跨产品体验分叉。

### 13.3 上游这么选的合理性（对面的账）

### 13.4 顺带发现：本机 libiamf 构建带断言

字符串差集出现 `assertion failed: opus_custom_decoder…` 与 `C:\PLAN\3FUI\fixtures\decode-research\…` 本地源路径——本机 `准备Libiamf.ps1` 产物**未定义 NDEBUG**（断言开启、路径内嵌）。3FC 出货若保留 IAMF，建议重编 libiamf/opus 加 NDEBUG（去断言与路径泄露，小优化）。

## 十五、随包依赖必要性总审计（2026-10-29，dumpbin 导入图全量）

问题：整个软件实现的所有依赖，是否都有必要随包发布？方法：对交付目录全部 36 件建 dumpbin 导入图（静态+延迟合并），逐件映射功能，找孤儿与缺件。

### 15.1 交付内依赖图（原生件，全量实测）

### 15.3 反向发现：不是多了，是少了（未随包的硬依赖）

1. **libomp.dll / libshaderc_shared.dll**：avfilter-12 **静态导入**硬依赖，既不随包、README 的 FFmpeg 下载指引（BtbN gpl-shared zip）也不含——本机能跑纯属 PATH 上有 C:\PLAN\FFmpeg（docs/103 实证）。干净机器上 avfilter 加载失败 ⇒ 内核 Open 失败。README 的「dll 必须配套不得混用」警告实际覆盖面不足：**配套闭包还包括这三个文件**。
2. **vulkan-1.dll**：avfilter/avutil 导入——由 GPU 驱动提供，通常可接受，但无 Vulkan 运行时的机器同样是加载失败点。
3. **MSVCP140 / VCRUNTIME140(1)**：内核静态导入，**未随包、README 未提**；无 VC++ 2015-2022 x64 Redist 的干净机器 ⇒ FFF.Native TryLoad 失败 ⇒ 报因误导（提示放 DLL，实际缺 VC 运行库）。

### 15.4 结论

**随包清单没有冗余件**——每一件都对应真实功能且被引用闭包覆盖；「不必要随包」的答案是：**没有**（可调项仅 §14.4 的 IAMF 开关与理论上的字幕/光盘功能整删）。真正的改进空间在反向：**把未随包的硬依赖（libomp/libshaderc、VC 运行库）补进交付或文档**，否则官方发布在干净机器上的开箱即用率取决于运气。建议上游：① FFmpeg 指引改为「整包复制配套目录」（含 libomp/libshaderc/libunwind/libwinpthread）；② 发布物或 README 补 VC++ x64 Redist 前置；③ 体积优化至此已封顶（结构性大头 = SDK.NET 27.2 + avcodec 75 + R2R 托管 14.2，均已在前文证死）。

### 14.2 “是否已经内置”的分层答案

| 层 | 状态 |
|---|---|
| 解码（IAMF → PCM） | **条件内置**：`HaveLibiamf` 自动探测 libiamf，在则 `FFF_WITH_LIBIAMF=1` 全功能；不在则六处 `#if !FFF_WITH_LIBIAMF` 回退分支（「回退到常规解码，声场以容器声明为准」）。**官方发布二进制 = 不内置**（发布管道不跑 准备Libiamf.ps1，内核 1.02 MB，10.23 解压件实测） |
| 渲染（床渲染/双耳折叠） | **明确不内置**：6e574b2 起内置渲染器被删，函数表由外部模块经宿主注入（AudioRenderPlug ABI），未注入时由 WasapiRenderer 替代路径出声——commit 原话「binaural bed output changes on merge, not on unlock」 |
| 官方发布二进制 | 三件套（解码/床渲染/双耳）**全部缺席**：仅保留条件集成点 + 回退话术；插点（ABI + 宿主接线）已内置但无模块可插 |

### 14.3 对 3FC 的含义（修正 §十三.2.4 的表述）

- 3FC 出货内核（同源 main）**同样已删内置床渲染** → 3FC 与上游官方发布在解码层的差异（libiamf 在/不在）只是**解码/元数据层**：3FC 用户可解 IAMF 内容（空间音频声道数快照、UI 声明可用），上游发布用户回退常规解码。
- 渲染层两边一致：都需要外部模块经 AudioRenderPlug 注入；3FC 宿主是否已实现音频 plug 注入（色彩变换模块接口.vb:78 已有结构定义）**待查证**——两侧都没接模块的话，渲染层均为回退态。
- 因此 §十三.2.4 的「3FC 用户拥有上游发布用户没有的功能」应精确为：**仅解码/元数据层**；渲染层为共同的外置待插状态。

## 七、自包含判定（2026-10-29）：上游发布不是自包含 .NET，是框架依赖单文件

**判定：不是自包含（framework-dependent）。** 四重证据：

1. **构建配置**：`FFF.Player.vbproj` `<SelfContained>False</SelfContained>`；发布脚本 publish 行显式 `--self-contained false`。
2. **包内容扫描**：38.1 MB exe 里 `coreclr.dll` / `System.Private.CoreLib` / `hostpolicy.dll` / `hostfxr.dll` **全部 0 命中**（二进制扫描）——自包含必含运行时；仅有的 ×1 `Microsoft.WindowsDesktop.App` 命中是 deps.json 的框架引用串。
3. **运行时行为**：在 PATH/`DOTNET_ROOT` 指向 vendored dotnet 8 的会话里，上游 exe 两次实测直接退出并打印「You must install .NET … Framework: 'Microsoft.NETCore.App', version '10.0.0' … The following frameworks were found: 8.0.31」——这是 apphost 解析**共享框架**失败的典型输出，自包含应用不存在这条路径；我方同源单文件构建运行时 `System.Private.CoreLib.dll` 的模块路径实测为 `C:\Program Files\dotnet\shared\Microsoft.NETCore.App\10.0.14\`。
4. **体积算术**：本机共享框架实测 NETCore.App 10.0.14 = 76 MB + WindowsDesktop.App 10.0.14 = 94 MB ≈ 170 MB，38.1 MB 装不下。

### 7.1 自包含反事实实测（同源发布）

| 交付形态 | 体积 | .NET 10 前置 | 压缩 |
|---|---:|---|---|
| 框架依赖单文件（**上游现状**） | 38.1 MB | 需 Desktop Runtime x64 | 不可用（NETSDK1176） |
| 框架依赖单文件 + 剔除 SDK.NET（§六） | ≈11 MB | 需 Desktop Runtime x64 | 不可用 |
| 自包含单文件（纯 IL） | **199,099,725 B（189.9 MB）** | 无 | — |

### 7.2 含义与权衡

- 用户机必须已装 .NET 10 Desktop Runtime（x64），发布页未声明这一前置（改进项：release note 声明，或应用内启动自检给官方下载链接——apphost 的英文错误框对普通用户不友好）。
- 自包含的价值：零运行时前置、运行时版本钉死（不受用户机运行时更新影响）；代价：压缩后仍 77.6 MB（比上游现状 +39.5 MB），且放弃运行时安全补丁的自动获取。
- 「要压缩就必须自包含」（NETSDK1176）——77.6 MB > 38.1 MB，**上游选框架依赖在体积上是正确决策**；§六的 SDK.NET 剔除（→ ≈11 MB）也只在框架依赖形态下成立。
- 环境注记：开发者机上若全局 `DOTNET_ROOT` 指向旧运行时（如 vendored dotnet 8），会复现上述「框架缺失」退出——这是框架依赖解析顺序（DOTNET_ROOT_X64 > DOTNET_ROOT > 默认安装位）的固有行为，终端用户未设该变量不受影响。
