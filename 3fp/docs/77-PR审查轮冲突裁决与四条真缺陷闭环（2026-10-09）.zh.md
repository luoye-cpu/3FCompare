## 五、【未做 / 未评 / 已登记不修】

- **K1（真缺陷，本 PR 不带，PR 正文已写进 "Not claimed"）— 多窗口归一化的分母恒取 `windows[0]`**：
  `VideoRenderer.cpp` 里 `settings.sourcePeak = clamp(metadata.windows[0].signalPeakNits, 1, 10000)` 是**帧级单值**，
  着色器用它归一化再乘回；`HdrToneCurve` 建曲线时**完全不看** `maxScl` ⇒ 除窗口 0 以外，每个窗口自己的
  `signalPeakNits/maxscl` 在整条链路上无人消费。lane G 的口径哨兵实测：**只把窗口 1 自己的 maxScl 翻倍
  （444→888 nits），右区域移动 0.00000**（`[J5]`，两修复臂同值）。
  *为什么不顺手修*：改法要给 b2 增每窗口峰值（动 cbuffer 布局 + HLSL 声明 + 两处填充 + 重生成字节码），
  而**判据必须先行** —— 现存的 J2 参照把峰值钉成 `windows[0]` 的 maxScl（同源钉），内核改合规后它会对
  **更正确的实现判红 0.46945–0.48663**（lane G `own_peak_false_red.out`，tol 0.012）。
  先把期望值换成独立曲线求值，再动实现；这一手需要 ST 2094-40 关于"曲线输入分母"的规范性原句定案，
  lane G 没拿到公开逐字（`hdr10plus.com` 抓取失败、Application Document 付费墙），**所以口径归属留给上游裁决**。
- VB 侧改动**未编译验证**：克隆里没有 `LakeUI` 依赖，`FFF.Player` 整项目编不过（910 个 BC30002），只做了字段顺序/宽度与 C 头逐项对齐的静态核。
- 宿主层未跑：`--selftest` 真机、`tools/发布门禁.ps1`、`构建全部.ps1` 都不在 PR 臂上跑过（3FC 侧被叫停）。
- 无判据覆盖的面（lane E 清单）：HDR Vivid 动态元数据（`FromVivid` 零调用者）、`dynamicMetadataDegrade` 全部取值、
  `dynamicMetadataHeldFrames` 过期分支、真实码流多窗口（>1）、AV1 携带 HDR10+ side data、DV RPU/FEL 叠加本笔峰值所有权、
  GPU P010 硬解。仓库自带内核 harness `测试3FP内核.ps1` 在本机 RC=1（stderr + `ErrorActionPreference='Stop'` 第 0 例即止）。
- 出货树工作副本的 `ShaderBytecode.h` 本轮**归位成生成器版式**（值可证相同：7 数组逐个与生成输出相等），
  代价是 TP 内部 diff 有约 2.5 万行纯版式；PR 侧不受影响（上游基线本就是生成器版式，那边只差 9 行）。

  `total == 2` 的反推成立、**未做逐像素取样**。修后该带内权重之和恒为 1，接缝问题的上游一致，
  但"修后带内无亮度不连续"这句**没有实测件**。
