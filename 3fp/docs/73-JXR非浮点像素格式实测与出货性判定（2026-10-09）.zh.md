## 三、五条缺陷（B-1…B-5，每条指到盘上日志）

> 内核读数一律标注**所测 `FFF.Native.dll` 的 sha256 前 16**；`_3fc_tmp/` 路径相对 `_3fc_tmp/handoff-20261008-lanes/`。
> ⚠ 这些内核读数全部来自**实验树构建** `69599183F6A10CFD`，**不是出货件** —— 见 §五纠正 ①。

### B-1 【实测】解码侧丢 alpha：所有带 alpha 格式的 A 通道恒 0

- **丢在 FFmpeg 封装侧，不在文件**：用 jxrlib 自家 `JxrDecApp` 读同一个 FFmpeg 写出的 `rgba.jxr`，第一像素 = `11 55 aa cc`（A=0xCC 完好）；FFmpeg 解码给的是 `aa 55 11 00`。证据：`laneB-jxr/logs/probe2_summary.txt`、产物 `laneB-jxr/samples/jxrdecapp/rt2rgba.bmp`。
- **真实 fp16 夹具同样丢**：4 个真实 `rgbaf16le` 夹具经 FFmpeg 解出的 A 平面 64×64 采样 `A_min = A_max = 0x0000`（`laneB-jxr/logs/fx_alpha.txt`，本轮逐行核对：4/4 夹具 `A_uniq 1`）。
- 交叉验证的边界：这 4 个夹具 jxrlib 自家 app **全部**报 `Unsupported format in JPEG XR`（`logs/jxrdecapp_matrix.txt`，本轮抽查 c=0/2/3/9/10/12 各 ext=tif/bmp 均 size=0）⇒ 真实文件**无法**用 jxrlib app 交叉验证，B-1 在真实夹具上是「FFmpeg 单侧读数 + 往返件双侧对照」的组合证据，等级低于往返件本身。
- 影响面：**对当前 fp16 通路也是活的缺陷**。短期处置是把「A 恒 0」写进验收集判据，勿做预乘/抠像。

### B-2 【实测】`gray16le` 被误做 limited→full 拉伸（两树共有）

- 现象：16bppGray 源值 `0x1234`（=4660，4660/65535 = **0.0711**）经内核输出 **0.00978**；`(4660−4112)×255/219/65535 = 0.00978` —— 正好是 **16..235 limited→full 拉伸公式**，偏暗 ~7.3×，且 `<0.0625` 一律削到黑。
- 读数：`laneB-jxr/logs/read_pixel_probe.txt` 与 `logs/read_pixel_probe_rgb24_bgra.txt` 两份独立记录同一值（本轮复算：`### rt2/gray16le.jxr → play: … peak=100 outBits=10 presented=1`，`(480,250) R=G=B=0.00978`）；同轮 `rgb24/bgr24/gray8/rgb48le/rgba64le` **全部保真**。
- 不在 FFmpeg：纯 sws 直测 `gray16le→rgba64le` 是**逐位无损**的（`logs/sws_gray16_and_bitdepth.txt`：`34 12 34 12 34 12 ff ff`）。
- **根因位 = 内核给 sws 设的 range**，`sws_setColorspaceDetails(..., IsFullRange(frame) ? 1 : 0, ...)`，JXR 无 `color_range` ⇒ `IsFullRange()=false`。**两树共有**：
  - `3fp/kernel/FFF.Native/3FP/Render/VideoRenderer.cpp:5173`（本轮实读该行即此调用）；
  - **出货树同样存在**：`third_party/fff_project/FFF.Native/3FP/Render/VideoRenderer.cpp:4821`（本轮实读）。
  > ⚠ **纠正交接账本的行号**：源材料（`_3fc_tmp/review-20261008/laneR-D/README.md`【未评】第 7 条）把 TP 侧写成 `:4771`。盘上 `:4771` 是 `const auto directYuv = input.layout != 0;`，**不是** colorspace 调用；正确行号原为 **`:4787`**，2026-10-10 因该文件内新增诊断计数整体下移 34 行，现为 **`:4821`**（`grep -n sws_setColorspaceDetails` 在 TP 全文只命中这一处帧路径调用）。kernel `:5173` 之外还有 `:3971-3972`（自适应降采样 scaler）同形调用，本轮未测。
- 修法成本：**分钟级～小时级**（RGB/gray 族强制 range=1，或整段跳过 colorspace 设置）。这是 lane B 判定里**唯一能让 16bppGray 从 7.3× 偏暗变正常**且最便宜的改动。

### B-3 【实测】`rgbaf32le`（128bppRGBAFloat，GUID `0x19`）在内核里开不出来

`[swscaler] rgbaf32le is not supported as input pixel format` → **`Open timed out`**（`laneB-jxr/logs/read_pixel_probe.txt` 与 `logs/read_pixel_probe_real_and_grayf32.txt` 两份独立记录同一行）。解码器支持（表第 10 条能解出 `rgbaf32le`）、内核不支持 ⇒ **硬失败，不是画质问题**。最省修法：CPU pass 做 `rgbaf32le→rgbaf16le` 后走 layout 3。

### B-4 【实测】非 `rgbaf16le` 的浮点格式全落 `default` 被钳位 + 吃错曲线

`rgbf16le`(48bppRGBHalf) / `grayf16le`(16bppGrayHalf) / `grayf32le`(32bppGrayFloat) 落 `DescribeInput` 的 `default`（`3fp/kernel/.../VideoRenderer.cpp:1109-1162`，本轮确认**只有 `:1157 AV_PIX_FMT_RGBAF16LE` 一个 RGB case**）⇒ layout 0 ⇒ 被 sws 量化进整数 `RGBA64LE`：哨兵 `1/2/4/8/−1` → **>1.0 全钳到 1.0、负值全削**（sws 独立直测 `logs/sws_clamp_measured.txt`：`rgbaf16le` 得 `65532/65535/65531/65535/~0`，`bgra` 得 `255 255 255 / 255 / 0`；内核探针 `logs/read_pixel_probe.txt` 三条浮点件中心像素均读回 `R=G=B=1.00000`）。再叠 `transfer=0` 的 sRGB 解码曲线 —— 而 `JXRGlue.h:136` 把这一族归在 `scRGB formats. Gamma is 1.0` 块下 ⇒ **曲线也错**。

### B-5 【实测】CMYK / YCC / n-channel 等 GUID 打不开；`32bppPRGBA` 预乘未还原

见 §二 第 15 条与 §2.1。`3cc4a650` 32bppPRGBA **表命中→`rgba`，但预乘没还原**（`logs/patchprobe_fullguid.txt` 第 3 行；本轮复读该行确认 `rc=0 OK`）⇒ 与 B-1 的 A 恒 0 叠成双重错。CMYK 族则**到不了内核**（`avcodec_open`/demux 阶段就 `Unsupported JPEG XR pixel format GUID`）。
CMYK 的「打不开」结论来自 **GUID 补丁法，不是真 CMYK 码流**（现役编码器根本产不出：`-pix_fmt cmyk` ⇒ `Unknown pixel format requested: cmyk`，`logs/roundtrip_summary.txt` §02）；且 jxrlib 的 glue **没有 CMYK→RGB 转换**（`grep -i cmyk jxrgluelib/JXRGluePFC.c` 零命中，CMYK 只在仓外 `jxrgluelib/JXRGlue.c` 第 171–175 行的 `pixelInfo[]` 表里作为 4/5 通道存在）。

### 纠正 ②：JXR 浮点通路**不在出货树**


实验树那 7 处是：`VideoRenderer.cpp:1157`（`case AV_PIX_FMT_RGBAF16LE:`）、`:4042`（缩放链 `layout == 0 || layout == 3`）、`:5147`（`floatRgb`）、`:5148`（`directYuv`）、`:5149`（`if (!directYuv && !floatRgb)`）、`:5343`（`else if (floatRgb)` 直传）、`:5396`（`transfer=3`/`gamut=0`）。出货树**一处都没有**。

## 七、修法清单与推荐顺序（成本口径照搬源账，产品取舍留给用户）

**推荐顺序（成本/确定性优先）**：① **G2** gray 族 range 强制 full（分钟～小时级，B-2 缺陷明确且最便宜）→ ② **G3** alpha 恒 0 **提单给封装补丁方**（不改代码也能推进；同时把「A 恒 0」写进验收集判据）→ ③ **G1-rgbf16le**（48bppRGBHalf 接 layout 3；注意是 3 通道交错 half，**不能**直接复用 4 通道 `R16G16B16A16_FLOAT`，纹理格式与着色器 swizzle 要按通道数分派，约半天）→ ④ **G5①** `rgbaf32le→rgbaf16le` CPU pass（把「打不开」变「能看」，收益 0→1）→ ⑤ **G6** 16-bit 整数曲线（**先取证**：需 T.832/WIC 原文）→ ⑥ **G1-grayf16le / G7 CMYK / G8 高级档**（等真样本或需求；CMYK 是天级 ×2 且第②③段不归内核）。

**G4（alpha 的内核侧本来也不消费）**：HLSL `:748`/`:755` 恒写 `float4(rgb,1)` ⇒ **只做 G3 不做 G4 也没有可见收益**（图像模式透明背景需求未定）。

> 出货性提示：G2 的落点在**出货树 `:4821`**（2026-10-09 记为 `:4787`，本轮因该文件新增诊断计数下移 34 行；见 §二 注），改它属 PR 面；G1/G5 的落点在实验树 layout-3 体系内，而出货树根本没有该体系（§五纠正 ②）⇒ 这两类改动的**落地树不同**，别混成一笔。
