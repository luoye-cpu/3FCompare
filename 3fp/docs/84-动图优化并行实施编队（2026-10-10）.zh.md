## 0. 决定编队形状的三条硬约束（都是实测/实读，不是偏好）

1. **内核不能在 worktree 里构建**：`3fp/kernel` 的 `third_party/`（FFmpeg 头与库）与 `obj/`、`x64/` **全部未跟踪且被 .gitignore 忽略**（`git ls-files` 空、`.gitignore:46`），且 `tools/build_kernel_3fp.py:50` 把 `NAT` 写死成 `<repo>/3fp/kernel/FFF.Native` ⇒ 新 worktree 里没有依赖、脚本也不指向它。
   ⇒ **并行编写、串行落地**：同一时刻只允许一个写者碰同一个内核文件；补丁由 lane 起草、主循环按序应用并构建。
2. **构建目录按 `--config` 隔离**（`obj/x64/<cfg>`、`x64/<cfg>`）：一次只能有一个 `Release_sdr` 的读者；集成期给每次落地用**独立 config 名**（`lane-a1`、`lane-b1`…），永不覆盖别人的产物；`3fp/build/FFF.Native.dll`（10-09 件 `38d44decce9837d7`）全程只读。
3. **计时读数不能被并行污染**：本机跨会话绝对值会漂（4K 每秒 CPU 86–92% → 140%，`v5_4k_15s.txt`），任何 lane **不得产出性能结论**；所有 A/B/A/B 计时批由主循环在屏障后串行跑。lane 可以跑"对不对"（帧序/丢帧/错误码），不可以跑"快不快"。

## 2½ W0 普查结论（5 路已回，改写了三条落点）

- **A1 的形状被 R1 收窄**：解码输出格式**按素材不同**（R1 用 ffprobe 量到 webp_anim=`argb`、gif=`bgra`、apng=`rgba`，而 07c 这类无 alpha 的 APNG 是 `rgb24`）。DXGI 只有 `B8G8R8A8`（内存序 B,G,R,A）与 `R8G8B8A8` 两种可用 ⇒ `bgra` 源可逐字直传、`rgba` 源换一个纹理格式即可直传，而 **`argb` 与 `rgb24` 仍需一次重排**（要么着色器 swizzle，要么保留 sws）。⇒ **A1 的天花板不是"消掉全部转换"，是"消掉 4 字节且顺序匹配的那部分"**；我原先把 WebP 4K 的 23.72ms/帧当成 A1 的主要靶子，按 R1 它是 `argb`，直传路拿不到它。
  现成可延用的臂：保持 layout 0、在 `floatRgb` 旁加一个 `verbatimRgb` 谓词、纹理格式由 pixdesc 分量序决定（而不是现在 `:3091` 只按位深二选一）、复用 `:5369-5375` 的逐字上传体。
- **A4/A5 落点由 R2 定死**：唯一干净的位置是"分类处算一个会话深度上限 + `VideoFrameQueueLimit()` 消费它"（两个闸门 `:753/:3448` 都走这里，视频路不受影响）；A5 的账 = `depthCap = clamp(budget/bytesPerFrame − pipelineFrames, 2, 8)`，`pipelineFrames` 取 `videoDecoder_->thread_count`（CPU 路）。**不需要改 API/结构体**。⚠ 三条连带风险：深度到 2 时饱和变成"1 帧即饱和"、1.5s 前瞻子句永久不可达；空队列更容易触发 late-drop，从而**在动图上意外启动降采样**（画质变化）；`MaxQueuedVideoFrames` 还被 `:2902-2903/:3009` 当包数/`extra_hw_frames` 上限用，**不能跟着动**。
- **门禁真相（R3）**：`verify_all_samples.sh`、`verify_animated.sh`、`ab_baseline_vs_patched.sh`、`bench_ab.ps1`、`frame_pool_probe`、`decode_profile`、`create_cost_probe`、`rebuild_probes.ps1` **全部恒退 0**，不能当门禁；`anim_cost_audit` 半有牙（**0 次呈现也判 PASS**）；PR 树 `FFF.Player.Tests/Program.vb:29-32` 把**任何未知旗标**路由进 `ImageZoomRegression` 再 `return 0` ⇒ 那 23 条旗标在这棵树里是集体空判；`check_kernel_config_abi.py` 只数字段数且**无调用者**，同宽字段换序抓不到；出货树是 API 17/15 字段，其 `--static-image-open-regression` 等**跑不到我们的 API 19 DLL 上**。
- **R5 直接作废了我引用过的一批读数**（已写进 docs/83 §3½）：`v9_*` 两臂其实都是旧路径。
- **A7 更正**：宿主其实接了线（`播放器会话.vb:81 .自适应CPU预缩放 = 0UI`），断链①改为"默认值为 0"。

## 3½ W1 验收结果（主循环实读 diff + 实跑；两处前提被推翻）

**已验（真跑过，命令与读数在 `anim-perf/i_*.txt`）**
- `anim_cost_audit`：**over16k 素材现在退 3 并打 `NOT-JUDGED(OpenCompleted 未到达)`**——修掉了我自己那枚"0 呈现也报 PASS"的假绿；5fps HEIC 在 poll20 下 **PASS/rc=0**（旧版按 150ms 绝对阈判它 58/58 长停），poll200 下**主动拒绝判**（"阈差 90.54ms 落在 ±400ms 带内"）⇒ 不放宽、只认测得准的。
- `loop_stutter_probe --replay`（W1b 新增的回放入口）：**对 `ab_new/arm_4k_on.txt` 判红 rc=1，红因含"帧序完整性：重复 4 / 跳号 3 / 起点漂移"**——这正是我上一轮靠肉眼才发现的缺陷，现在判据能自己抓；对 `teeth_07b_anim_gif.txt` 判绿 rc=0；扫全部历史日志：**帧序 红 8 / 绿 83 / 不可辨 29 / 无该行 4，"当年 PASS 如今 FAIL"= 0 条** ⇒ 无假红引入。副发现：`fix_4k_on.txt` 每圈起点漂到 fIdx 1 而丢帧计数为 0 ⇒ 旧六条判据漏网的第二类（整帧蒸发）。
- 两探针均**主循环重建通过**（`loop_stutter_probe.exe` 239,104 B / `anim_cost_audit.exe` 202,240 B，0 warning）。

**被推翻的两条前提**
1. **A1 的靶子要换**（W1e 实测解码帧格式，不是看声明）：`webp_anim` 声明 `argb` 但**解码出 `yuva420p`**；`07c` 这类无 alpha 的 APNG 解码是 `rgb24`，而我造的 4K APNG 是 `rgba` ⇒ **格式随内容变**。按"解码帧字节序"分类：可逐字直传只有 `bgra` 1/10；加 `R8G8B8A8` 后升到 5/10。**两个 4K 成本大户里只有 APNG(rgba) 在 A1 射程内，WebP(yuva420p) 不在** ——它属于"YUV 平面直传"那条 `directYuv` 路，而四平面 YUV+alpha 能否绑成 D3D11 纹理**尚未证**（无对应 DXGI 格式）。⇒ A1 拆成 A1a(4 字节 RGB 直传，射程明确) 与 A1b(YUV+alpha 平面，先做一次绑定可行性实验)。
2. **B1 的假设死了**（W1d 实测）：`07d_anim.avif`/`07e_anim.heic` 的像素都是 **8-bit**（`frac_Y_not_multiple_of_4` = 0.000000），所以 `VideoRenderer.cpp:5166` 的 10-bit→RGBA64 分支**解释不了** HEIC 那 20.57ms/帧。B1 换方向：同一 AVIF 内容做 8bit/10bit 对（10g/10h 已生成）只能问"位深代价"，问不出 HEIC 的账；HEIC 的 20.57 要先归"哪个阶段"，不是先假设位深。

**夹具与现实修正**：8 张新夹具在盘（脏矩形实测变化占比 **1.04–1.17%**、脏框 80×60/220×165/440×330；AVIF 8/10bit 对可成，动图 HEIC/JXL 在本机**做不出来**：`Requested output format 'heif'/'jxl' is not known.`）。两个坑已记进生成器：gif 默认管线会抖动（实测 66–67% ⇒ 必须 `palettegen+paletteuse=dither=none` 才到 1.x%）；**"我们的样张每像素都在变"这个前提是我错的**——既有素材变化 4.6–17.3%，但脏框横跨全宽 ⇒ 判据必须是"占比 + 框紧致度"两条。
⚠ `3fp/samples/media/` **整目录被 .gitignore 忽略** ⇒ 夹具不进仓，可复现性只来自 `3fp/samples/tools/gen_dirty_rect_anim.py` + `lane-W1d/manifest.md` 的 sha256；`verify_all_samples.sh:38` 的 17 条硬编码名单也不会自动收它们。

**并发写者实锤（同一文件）**：`FFF.Player.Tests/Program.vb` 的 diff 里混着两笔改动——W1c 的"未知旗标 ⇒ 点名 + `Return 3`"（:31-46，已确认在位，且保留了 `:21/:26` 两个 `ImageZoom*` 入口）与另一路 agent 8 分钟前的"工程此前引用了树里不存在的例程 ⇒ 清到可编译 + `--image-zoom-regression` 入口"。⇒ 我按规矩**只认自己读到的最终状态**，且 **W1c 的守卫未编译未运行**（构建 `FFF.Player.Tests` 会写别人正在用的 bin，本轮不碰）；收口时随宿主构建一起验，命令已记在任务 #6。

## 4. 波次 2：内核实现（串行落地，切片到"一次一个函数"）

顺序与理由：

1. **A4+A5（队列深度与内存账，`PlayerSession.cpp:114-120`）**——最便宜，且 A2 的预算口径必须先正确才有意义。
   判据：4K 私有 ≤350MB 且**接缝、丢帧、长停都不变差**（A/B 用同轮 env 或 config 开关）。
2. **A6（节奏精度：`wait_for` clamp[1,20] 与 `Sleep(1)/Sleep(2)` 各点，`:3464`、`:4174`、`:2858/2867`）**——只碰等待语义，判据靠 F1。
   判据：640 GIF `p90−中位 ≤5ms`，且 CPU/帧不升（主循环量）。
3. **A2（whole-loop cache）**——需要 1 的账本正确；判据：4K/1080p 接缝 → ≈0.4ms 量级、**长停 0、丢帧 0、帧序完整**；超预算档必须逐字节退回旧路径（用 `--config` 两枚 DLL 对照）。
4. **A1（RGB 免 sws 直传，`VideoRenderer.cpp:5152-5215`）**——风险最高（色彩语义），且必须先有 R1 的清单；判据：逐像素对旧路（外部参照解码，不用产出它的二进制读回），4K WebP 转换列 → ≈0。
5. **A7（降采样第二传感器：长停率）**——依赖 A6 的抖动读数定义；预期结论可能是"它是内存药"（docs/83 已证一次），所以排最后。

每条内核片都带**同一枚 DLL 内的 env/config 闸**做 A/B（先例 `FFF_ANIM_NOSEEK`、本轮 `FFF_ANIM_PRIME_DISABLE`），避免跨会话漂移进结论。
