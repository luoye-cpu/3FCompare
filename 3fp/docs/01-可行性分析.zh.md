## 一、结论

| 判定项 | 结论 |
|---|---|
| 技术可行性 | ✅ **可行**，且不需要引入新解码库 |
| 起点 | 3FP **已经内建静态图通路**（内核 `staticImage_` 全链路），不是从零做 |
| 主要工作量 | 在**交互层**，不在解码层 |
| 建议形态 | 分两期：M1「能看图」（导航 + 适应窗口 + 目录打开）、M2「看得准」（EXIF / 多页 / 色彩） |
| 工作量 | M1 约 1.5–2 周（1 人）；M2 约 1.5–2.5 周 |
| 是否破坏 ABI | M1 **可以不破坏**（纯行为修正 + 外壳改动）；M2 若新增 API 需递增 `PlayerApiVersion` |
| 主要风险 | 上游产品定位（"极简播放器"）是否接受看图形态；每改一次内核，下游 fork 要重移植 |

**一句话结论**：这不是"让 3FP 支持图片"（它早支持了），而是"把已有的单帧渲染能力包装成一套看图交互 + 补齐图像特有的语义缺陷"。

**色彩能力三条结论**（复审新增，详见 §4.6）

| 能力 | 结论 | 归属 |
|---|---|---|
| HDR 静态图（PQ / HLG 的 AVIF、HEIC、JXL） | ✅ **可行**，无需改内核；前提是 ffmpeg 为该格式填充了 `color_trc` | M1 顺带获得，需实测确认 |
| 广色域 SDR（Display P3 的 PNG / HEIC / JXL） | ❌ **当前不支持**，且修它要动**全局**渲染管线，影响所有视频 | **剥离为 M3，独立提案** |
| GainMap（Apple Gain Map / Google Ultra HDR） | ❌ **短中期不可行**，ffmpeg 无通用通道，依赖上游 ffmpeg | 明确列为不支持 |

## 二、范围界定（先说清做什么、不做什么）

3FP 是「独特路线的本地视频播放器，也支持单独的音频和图片」（上游 README）。图片目前只是"能被打开"，因此本提案的范围是：

- **做**：打开单张图片后的**浏览体验** —— 上一张/下一张、适应窗口/1:1、缩放平移、旋转、幻灯片、目录内连续浏览、文件关联。
- **不做**：缩略图网格图库、壁纸管理器、批处理/格式转换、编辑标注 —— 这些属于独立产品，与 3FP 定位冲突，不建议纳入。

## 四、差距分析（要做什么）

### G1 · 没有"上一张/下一张" —— 最核心缺口

静态图不产生时间轴推进，**不会触发 `PlaybackEnded`**，因此播放列表的"播放结束自动下一项"（`Form1.vb:455` → `移动到播放结束后的项目()`）**对图片根本不生效**。

→ 必须由图片浏览控制器**显式驱动**导航（手动切换 or 幻灯片定时器）。这是本次改造的主要工作量。

### G2 · 不能打开文件夹

`规范本地文件` 要求 `File.Exists`，命令行也只取第一个文件（`参数.FirstOrDefault`）。看图的第一诉求是"打开一个目录然后翻"，需新增目录枚举 + 图片过滤。

### G3 · 交互被视频语义占用

| 现有绑定 | 看图期望 | 冲突等级 |
|---|---|---|
| ←/→ = ±5 秒跳转 | 上一张/下一张 | 高 |
| ↑/↓ = 音量 | 缩放/翻页 | 中 |
| 滚轮 = 音量 | 缩放 | 高 |
| 左键拖 = 移动窗口 | 平移画面 | 高 |
| 进度条/播放按钮 | 无意义 | 中（UI 需切换态） |

→ `播放器360视角控制器` 已经给出了成熟范式：`IMessageFilter` + 模式开关（`全景交互已启用`）。图片模式照抄即可，**不需要新造机制**。

### G4 · 内核语义缺陷（3FC 侧实测到的既有行为）

| # | 行为 | 证据 | 影响 |
|---|---|---|---|
| K1 | 一旦 `Play()` 立刻 `Ended` | `:2910-2915`，`if (!staticImage_ && ClockPosition() < endPosition)` 跳过等待 | 图片"播完"语义错误，触发下游结束/循环逻辑 |
| K2 | `Seek` 对静态图报错 | `DoSeek` 无静态图短路（`:2926-2954`），`av_seek_frame` 对 image2 失败 → 字节 seek 兜底也失败 → `ReportError` | 任何自动同步/循环都会刷错误 |
| K3 | 图像序列被误判为单图 | `img%03d.png` 走 `image2` ⇒ `staticImage_` ⇒ **只显示首帧** | 序列图只能看第一张 |
| K4 | 静态图强制 CPU 解码 | `:2044-2056` | AVIF/JXL 大图首帧数百 ms～数 s，阻塞 Open |

### G5 · 图像特有的正确性问题（M2）

| # | 问题 | 现状 | 建议 |
|---|---|---|---|
| P1 | **EXIF 方向** | 未知：需实测 ffmpeg 是否导出 displaymatrix、3FP 是否应用 | 手机照片横竖倒是最高频投诉点，必须处理 |
| P2 | **广色域/ICC** | ❌ 内核**无 primaries 参数化**、无 ICC 处理（全仓库未见 SMPTE431/432 与 ICC 代码），Display P3 一律按 BT.709 解 | **剥离为 M3，独立提案**（见 §4.6.2）；M1/M2 内仅在信息面板提示"未做色彩管理" |
| P3 | **多页 TIFF / 多尺寸 ICO / PSD 图层** | ffmpeg 通常只取首页/首尺寸 | 明确声明"仅显示第一页"，不要假装支持 |
| P4 | **动画图** | 已当定时视频 ⇒ 会"播放" | 看图模式下默认停首帧，右键菜单提供"播放动画" |
| P5 | **超大图** | D3D11 纹理上限 16384；8K+ 图 staging 回读内存大 | Open 前预检尺寸，超限给明确提示而非渲染失败 |
| P6 | **HDR 静态图**（PQ/HLG 的 AVIF、HEIC、JXL） | ✅ 静态图走**同一** `IsHdrSource()` 判定与同一 `Render()` 入口；条件是 ffmpeg 填了 `color_trc` | 见 §4.6.1；**是本功能的差异化卖点**（多数看图器不支持 HDR） |
| P7 | **GainMap**（Apple Gain Map / Ultra HDR JPEG） | ❌ ffmpeg 无 gain map 侧数据通道，3FP 无相关代码 | 见 §4.6.3，明确列为不支持 |

### 4.6 色彩专项审查：广色域 / HDR / GainMap（复审新增）

> 审查方式：逐行核对 `Render/VideoRenderer.cpp`、`Hdr/HdrProcessor.cpp`、`Render/ShaderBytecode.h`
> + ffmpeg 头文件 API 面。**⚠ 局限：HLSL 源码不在仓库**（`ShaderBytecode.h` 只有编译后的 DXBC），
> 因此 shader 内部的 EOTF / 色调映射实现**无法审查**，以下结论限于 CPU 侧可见逻辑。

#### 4.6.1 HDR 静态图 —— ✅ 可行（条件性）

已核对的事实：

- `IsHdrSource()` 只依据 **`color_trc` == PQ(SMPTE2084) / HLG(ARIB_STD_B67)**（`HdrProcessor.cpp:194/199` 流级、`:235/240` 帧级），**不依赖 primaries**
- 静态图走**同一判定**、**同一 `Render()` 入口**（`PlayerSession.cpp:1376` 设备恢复、`:2062` 配置、`:2645+` 解码路径），色彩处理**未被跳过或降级**
- 输出：HDR ⇒ `R16G16B16A16_FLOAT`（`VideoRenderer.cpp:91-99`、`:2400`、`:2483`）；交换链强制 `DXGI_COLOR_SPACE_RGB_FULL_G10_NONE_P709`（scRGB 线性，1.0=80nits，`:2422`）+ `SetHDRMetaData(HDR10)`（`:4171-4176`）
- mDCV / MaxCLL 会被读取并转发给 DWM（`HdrProcessor.cpp:121-148`）

**唯一的成立条件**：ffmpeg 解码器是否为静态图填充 `color_trc`。

若某格式解码后 trc 为空 ⇒ `IsHdrSource() == false` ⇒ `ForceSdrOutputForSdrSource()` 强制回落 SDR（`VideoRenderer.cpp:2113`），
**HDR 图会被当 SDR 显示**。且 `forceHdrOutput` **不能**绕过这道门禁（`:2083-2087`、`:2326-2333`）——它只跳过显示器能力探测。

⇒ 结论：**若 ffmpeg 填了 trc，HDR 静态图直接可用、无需改内核**；若没填，需要在打开时按容器元数据（AVIF/HEIC 的 `colr` box、JXL 的 CICP）补填。
是否要补填取决于实测（Q5）。

⚠ **2026-09-23 补充 —— HDR 静态图还有一个格式相关的坑**：
实测确认 AVIF / HEIC 由 `mov` 解复用器承载，**不会被判为静态图**（见 §5），
因此这两类文件**不走** `DecodeInitialStillImage()` / `stillImageFrame_` 常驻路径，而是走视频解码分支。

- HDR 判定本身（`IsHdrSource()` 只看 `color_trc`）**不受影响** ⇒ HDR AVIF/HEIC 仍可能正常显示高亮
- 但会连带出现"单帧视频"的既有问题：极可能立即 `Ended`、设备丢失后无帧可重建
- ⇒ HDR 静态图的**完整**体验（常驻 + 不跳 Ended）依赖 **K3** 落地；
  在 K3 之前，HDR AVIF/HEIC 属于"能亮但状态机不对"

#### 4.6.2 广色域 SDR（Display P3 等）—— ❌ 当前不支持，且不属于本功能范围

已核对的事实：

- 内核的色域处理只有**一个布尔** `source2020`（`VideoRenderer.cpp:164 IsRec2020()`）+ **三组硬编码** YUV 矩阵 BT.2020 / BT.709 / BT.601（`YuvCoefficients()` `:1002-1013`）
- 全仓库**未见** `AVCOL_PRI_SMPTE431/432`（Display P3 / DCI-P3）；**未见**任何 ICC / cICP 代码
- `forceHdrOutput` 不覆盖 `IsHdrSource()` ⇒ P3 SDR 内容永远走 MapToSdr + BT.709 矩阵

后果：Display P3 的 PNG / HEIC / JXL 会被按 BT.709 解 ⇒ **欠饱和、颜色偏淡**。这与 HDR 无关，是**"SDR 广色域"这一整类内容的系统性缺失**。

⚠ **这是本次复审最重要的修正**：原报告把它当作"图片功能的子项"，实际上 ——
**改动点（primaries 参数化矩阵 / 3D LUT）位于全局渲染管线，会影响所有视频播放**，
风险等级与"看图功能"完全不在一个量级，**必须与本提案剥离**。

可行路径（按侵入性递增，供 M3 选型）：

| 路径 | 做法 | 影响面 | 精度 | 新增依赖 |
|---|---|---|---|---|
| A | 仅在图片模式的 swscale 阶段按 primaries 做一次色域转换 | 仅图片 | 一般 | 无 |
| B | Windows ICM（`mscms.dll` `CreateColorTransform`）：显示器 ICC + 图片 ICC → 变换/3D LUT | 仅图片 | 好 | **无**（优于引 LittleCMS） |
| C | 全局 primaries 参数化：shader 增加色域矩阵常量 | **全部视频** | 最好 | 无（但需全量 A/B 回归） |

⇒ 建议 M3 走 **B**（Windows 原生 ICM，不引第三方库，符合 3FP 轻量定位），并**单独发 issue 取得上游同意后再动手**。

#### 4.6.3 GainMap —— ❌ 短中期不可行

已核对的事实：

- 3FP 内核：**代码中未见**任何 gain map 处理
- ffmpeg API 面：`libavutil/frame.h` 的 side data 枚举已含 `AV_FRAME_DATA_DISPLAYMATRIX`(:85)、`AV_FRAME_DATA_ICC_PROFILE`(:144)、`AV_FRAME_DATA_DYNAMIC_HDR_PLUS`(:159)、HDR Vivid(:215)、SMPTE2094-40 App5(:270) —— **唯独没有任何 gain map 类型**；对 `third_party/ffmpeg/include` 全目录 grep `gainmap` **零命中**
- 3FP 只取一路视频流（`FindTimedVideoStream`），即便容器把 gain map 暴露为第二路 image item 也不会用

即：**ffmpeg 主线没有把 gain map 交给调用方的通用通道**，Apple Gain Map（HEIC/AVIF）、Google Ultra HDR（JPEG + MPF）、ISO 21496-1 同理。

要在 3FP 支持需同时满足：

1. ffmpeg 先把 gain map 解出来（新增 side data，或作为第二路流暴露）—— **依赖上游 ffmpeg，非 3FP 可控**
2. 3FP 自实现 ISO 21496-1 合成（SDR base + gain map → HDR），并新增 shader 路径

代价高、外部依赖不可控 ⇒ **建议明确列为"不支持"**；如有可能，对检测到 gain map 的文件在信息面板提示"按 SDR 基图显示"（能否可靠检测待定，可能只能靠容器 brand 猜测）。

#### 4.6.4 附带确认：HDR10+ / Dolby Vision / HDR Vivid

- **HDR10+**：`AV_FRAME_DATA_DYNAMIC_HDR_PLUS` **有读取**（`HdrProcessor.cpp:299-317`），但仅取 `window[0].MaxScl` 参与峰值计算，**没有逐场景/逐帧色调映射**
- **Dolby Vision**：识别但**不应用 RPU**，一律降级为 Rec.2020 / PQ HDR10（`:262-298`，注释明确需单独授权实现）
- **HDR Vivid**：同上（`:248-262`）

⇒ 静态图即使携带这些元数据（HEIC/AVIF 可能带 HDR10+），也只会用到其峰值，不做动态映射。对看图场景影响有限，但应在信息面板如实标注。

#### 4.6.5 输入像素格式对色彩的硬约束（复审新增）

`DescribeInput()`（`VideoRenderer.cpp:902-948`）白名单内的 YUV（420/422/444 的 8/10/12/16LE、NV12/P010/P210…）**直传 GPU**；
**其余（含全部 RGB）走 CPU swscale**，目标 `bitDepth<=8 ? BGRA : RGBA64LE`，目标矩阵**硬编码 `SWS_CS_ITU709`**（`:4209`、`:4216-4219`）。

| 静态图常见格式 | 路径 | 色彩后果 |
|---|---|---|
| `yuv420p10le`（AVIF / HEIC 常见） | 直传 GPU | ✅ HDR 链路完整可用 |
| `rgb24` / `gbrp`（PNG / JXL SDR） | swscale → BGRA8 | SDR 无碍，但色域在 swscale 阶段已按 709 定型 |
| `rgb48le` / `gbrp16` | swscale → RGBA64LE | 同上 |
| `gbrpf32`（JXL / EXR float HDR） | swscale → RGBA64LE | ⚠ 可行性与精度**需实测**；`maximum = (1u << bitDepth) - 1`（`:4304`）在位深推导异常时存在溢出风险 |

⇒ 新增内核待办 **K7**：验证并加固 RGB / float 输入的色彩路径（见 §6.1）。

## 五、ffmpeg 侧依赖与验证清单

3FP 允许**用户自行更换 FFmpeg 核心**（项目最大特色），因此图片格式覆盖**不取决于 3FP，而取决于用户放的 DLL**。这一点必须写进设计：能力必须**运行时探测**，不能硬编码格式清单。

```
ffmpeg -hide_banner -decoders | findstr /i "png mjpeg bmp gif webp apng tiff ico jpegxl hevc av1 rawvideo"
```

| 格式 | 预期 | 备注 |
|---|---|---|
> **2026-09-23 实测回填**（原表为"预期"，现已用真机 DLL 实测替换）。

**实测环境**：本机 `runtime/` 的 Shared FFmpeg —— `N-126168-gb16b5f2a01-20260815`（2026-08-15 master）。

| 格式 | 实测结论 | 承载方式（实测到的组件名） |
|---|---|---|
| PNG / APNG | ✅ 支持 | 解码器 `png` + 解复用器 `image2` / `png_pipe` |
| JPEG | ✅ 支持 | `mjpeg` + `image2` / `jpeg_pipe` |
| WebP（静/动） | ✅ 支持 | `webp` / `webp_anim` + `webp_pipe` / `webp_anim` |
| GIF | ✅ 支持 | `gif` + `gif` |
| TIFF | ✅ 支持（`tiff` + `image2` / `tiff_pipe`） | **多页只解首页仍待样张确认**（Q4） |
| BMP / ICO | ✅ 支持 | `bmp` + `ico` |
| JPEG XL | ✅ 支持 | 解码器 **`libjxl`**（⚠ 不是 `jpegxl`）；解复用器 `jpegxl_pipe` / `jpegxl_anim` |
| JPEG XL 动画 | ✅ 支持 | `libjxl_anim` + `jpegxl_anim` ⇒ 命中 3FP 的 `IsLoopAwareImageDemuxer`，按定时视频处理 |
| **AVIF** | ✅ 可解码 | `av1` 解码器 + **`mov` 解复用器**（本构建**无**独立 `avif` 解复用器） |
| **HEIC** | ✅ 可解码 | `hevc` 解码器 + **`mov` 解复用器**（本构建**无**独立 `heic` 解复用器） |
| EXR（HDR 扫描图） | ✅ 支持 | `exr` |
| 相机 RAW | ❌ **不支持** | 无 `dcraw` 解复用器 |
| SVG | ❌ **不支持** | 只有 `svg_pipe`，**无** `svg` 解码器（缺 librsvg） |

⚠ **实测发现的重要副作用：AVIF / HEIC 不会被 3FP 判为静态图**

`IsStaticImageDemuxer()`（`PlayerSession.cpp:322-329`）只认 demuxer 名 == `image2` 或 `*_pipe`。
而 AVIF/HEIC 由 **`mov`**（注册名 `mov,mp4,m4a,3gp,3g2,mj2`）承载 ⇒ **匹配不上** ⇒ `staticImage_ = false`。

后果（AVIF/HEIC 图片会走"视频"分支）：

- 不走 `DecodeInitialStillImage()`，**无 `stillImageFrame_` 常驻** ⇒ 设备丢失后可能白屏
- 会尝试 D3D11VA 硬件解码（静态图本该强制 CPU）
- 单帧媒体 ⇒ 极可能立即 `Ended`（§4 G4-K1）
- 对 HDR 卖点的影响见 §4.6.1

⇒ 这正是 **K3**（改用 `nb_frames <= 1` 判定静态图）要一并解决的问题 —— **K3 的优先级应上调**：
它不只是"修序列图"，而是"让 AVIF/HEIC/JXL 这类新格式正确进入静态图语义"。

**本次实测未覆盖**：解码后是否填充 `color_trc` / `color_primaries`（需样张跑解码流程，Q5）、
gain map 是否作为第二路流暴露（Q8）。本脚本只枚举组件注册情况，不做解码。

### 5.1 色彩相关元数据通道（复审新增）

原报告写"ffmpeg 不解析 ICC"**不够准确**，修正如下：

| 元数据 | ffmpeg 是否提供通道 | 3FP 是否使用 |

## 九、验收标准（建议）

**M1 通过条件**

1. 双击/拖放/命令行打开 `.png .jpg .webp .jxl .bmp .tif .gif` 均能正常显示；不支持的格式给出明确错误而非崩溃。
2. ←/→ 切换同目录上一张/下一张，状态栏显示"第 n/N 张"。
3. 适应窗口 / 1:1 / 百分比缩放正确；滚轮缩放、左键拖拽平移生效，且**不影响视频模式下的原有绑定**。
4. 打开图片后不出现 seek 错误、不自动跳 Ended。
5. 序列图（`img%03d.png`）可作为时间序列正常播放（K3 生效后）。
5b. **AVIF / HEIC 图片打开后进入静态图语义**：不立即跳 Ended、设备丢失后可重绘（K3 生效后，R12）。
6. 显卡设备丢失/驱动重置后图片仍可重绘（复用 `stillImageFrame_`）。

**M2 附加**

7. 带 `Orientation=6` 的 JPEG 竖拍照片显示方向正确。
8. 8K+ 大图给出明确提示，不出现渲染失败或 OOM。
9. **HDR 静态图**（PQ/HLG 的 AVIF、HEIC、JXL）在 HDR 屏上：快照 `isHdrSource == true`、输出位深 16（R16F）、
   三挡色彩模式行为与 HDR 视频一致。**若实测发现被降级为 SDR，则 R9 成立，需先补 `color_trc` 才能宣称支持。**
10. RGB / float 输入（PNG `rgb24`、JXL `gbrpf32`）不出现色彩错乱或溢出（K7）。

**明确的"不支持"声明（须写进帮助/信息面板，避免误判）**

- Display P3 等 SDR 广色域：按 BT.709 呈现（M3 之前）
- GainMap（Apple / Ultra HDR）：按 SDR 基图呈现
- 多页 TIFF / 多尺寸 ICO / PSD 图层：仅显示第一页/首尺寸
- HDR10+ / Dolby Vision / HDR Vivid 动态元数据：仅用于峰值，不做逐帧映射

消除静态图 seek 报错与立即 Ended，是 3FC 支持"图片 vs 视频帧对比"的前置条件。
若上游接受，3FC 随基线升级自动获得；若上游不接受，可先在 3FC 归档分支落地（按 `PATCHES.md` 重移植流程）。
