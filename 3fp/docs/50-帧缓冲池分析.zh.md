# 50 · 帧缓冲池分析

> 问题：「分析帧缓冲池的情况」
> 方法：读所有权路径 + 实测内存曲线（`tools/frame_pool_probe.cpp`）
> 日期：2026-10-06

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 有帧池吗？ | ✅ **有**（`videoFramePool_`），设计正确 |
| 稳态会反复分配吗？ | ❌ **不会** —— 池非空即复用，稳态零 `av_frame_alloc` |
| 会泄漏吗？ | ❌ **不会** —— 归还时 `av_frame_unref` 释放像素缓冲，六个场景实测后半段增长 **≈0** |
| 队列有内存上限吗？ | ✅ **有** —— 按 128 MB 预算动态压到 2–8 帧 |
| 内存主因是什么？ | ⚠️ **解码器内部**，不是我们的池（8K 软解 3.97 GB vs 硬解 600 MB） |

## 1. 帧所有权与复用机制

### 1.1 解码器复用帧（每流一个）

```
DecodePacket:
    AVFrame*& reusableFrame = video ? videoDecodeFrame_ : audioDecodeFrame_;
    if (reusableFrame == nullptr) reusableFrame = av_frame_alloc();   // 仅首次
    av_frame_unref(frame);                                            // 复用前清空
    while (avcodec_receive_frame(decoder, frame) >= 0) {
        handleFrame(frame);
        av_frame_unref(frame);                                        // 每帧后清空
    }
```

**每个流只分配一个 `AVFrame` 结构体**，循环内 `unref` 后重用 ⇒ 这是正确的写法。

### 1.2 视频帧池（队列用）

| 操作 | 位置 | 行为 |
|---|---|---|
| 取用 | `QueueVideoFrame` | 池非空 → `pop_back`；空 → `av_frame_alloc` |
| 归还 | 呈现后 / `ClearVideoQueue` | `av_frame_unref` → `push_back` |
| 释放 | `ReleaseMedia` | 遍历 `av_frame_free` + `clear` |

**关键**：`av_frame_unref` 释放的是**底层缓冲引用**（`AVBufferRef` 计数减一），
所以池里保留的只是**空的 `AVFrame` 结构体**（约 500 字节），**像素内存已归还系统**。

⇒ 池无上限增长**不构成内存问题**（最多 8 个结构体 ≈ 4 KB）。

## 2. 实测：内存全部稳定（无泄漏）

各场景跑 12 秒，观察"后半段增长"（后 6 秒的净变化）：

| 场景 | 结束内存 | 后半段增长 |
|---|---|---|
| 720p 软解 | 173.7 MB | +1.0 MB |
| 4K H.264 软解 | 674.0 MB | **+0.0 MB** |
| 4K HEVC 软解 | 1165.5 MB | **+0.0 MB** |
| 4K HEVC 硬解 | 252.3 MB | **+0.0 MB** |
| **8K HEVC 软解** | **3975.4 MB** | **−4.6 MB** |
| 8K HEVC 硬解 | 599.5 MB | +47.9 MB |

**全部接近 0 增长** ⇒ 池稳定复用，**无泄漏**。

（8K 硬解 +47.9 MB 属分配器碎片/驱动侧波动，非单调增长，见下节复核。）

队列深度实测**恒为 3**，不随分辨率变化 —— 说明内存预算约束**确实生效**。

## 3. 队列的内存上限（我们可控的部分）

```cpp
constexpr std::size_t MaxQueuedVideoFrames   = 8;
constexpr std::size_t MinimumQueuedVideoFrames = 3;
constexpr std::size_t MinimumMemoryBoundVideoFrames = 2;
constexpr std::size_t DecodedVideoQueueBudgetBytes = 128 * 1024 * 1024;

std::size_t VideoFrameQueueLimit(queue) {
    bytesPerFrame = EstimateDecodedFrameBytes(queue.back());
    memoryBound = 128MB / bytesPerFrame;
    return clamp(memoryBound, 2, 8);
}
```

各分辨率下的推导与实测：

| 分辨率 | 单帧 | 预算算出 | clamp 后 | 实测队列 |
|---|---|---|---|---|
| 720p P010 | 2.8 MB | 46 | **8** | 3 |
| 4K P010 | 24.9 MB | 5 | **5** | 3 |
| **8K P010** | **99.6 MB** | **1** | **2** | **3** |

⇒ **内存约束正常工作**：8K 时队列被压到 2–3 帧（约 200–300 MB），
不会因为"8 帧 × 99.6 MB = 797 MB"而失控。

**这是一个设计得不错的地方**：用字节预算而非固定帧数，天然适配分辨率差异。

## 4. ⚠️ 真正的内存主因：解码器内部（不是我们的池）

**决定性对照**（同一 8K 文件）：

| 8K HEVC | 内存 |
|---|---|
| **硬解** | **599.5 MB** |
| **软解** | **3975.4 MB** |
| **差额** | **约 3.4 GB** |

**归属分解**：

| 项 | 估算 |
|---|---|
| 我们的队列（3 帧引用） | ~300 MB |
| **解码器内部（参考帧 + 线程缓冲）** | **~3.4 GB** |
| D3D 纹理等 | ~250 MB |

⇒ **队列不是内存主因**。3.4 GB 来自 libavcodec 自身：
HEVC 软解 8K 需持有大量参考帧，且 `FF_THREAD_FRAME` 下**每个线程各持一帧**。

### 与线程数分级的关系（docs/49 的后续）

`FF_THREAD_FRAME` 每个线程持有一帧 ⇒ **线程数直接放大内存**。
8K 单帧 99.6 MB，8→16 线程理论上增加约 800 MB。

**这给"线程数只升不降"策略带来一个未被考虑的副作用**：
升档在缓解 CPU 压力的同时，**会显著增加内存占用**。
在内存紧张的机器上，这可能把"掉帧"换成"换页"，反而更糟。

**建议**：升档决策除 CPU 负载外，**应同时考虑可用物理内存**。
本轮未实现（需要新的内存探测与策略），但值得记录。

## 5. 观察到的次要点（均非缺陷）

| 项 | 说明 | 影响 |
|---|---|---|
| 池不收缩 | 曾达 8 帧则保留 8 个结构体 | ~4 KB，可忽略 |
| 每帧一次 `av_frame_ref` | 浅拷贝 + 引用计数，O(1) | 对硬解会 retain 纹理，已由 `extra_hw_frames = 10` 覆盖 |
| 队列饱和时主动 sleep | 不轮询，等待队首到期 | 省 CPU，设计良好 |
| `EstimateDecodedFrameBytes` | 硬解时用 `sw_format` 估算 | 与实际纹理一致，估算正确 |
