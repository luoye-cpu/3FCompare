# 145 · 启动期把进程提到 HIGH、启动后降回，能否改善启动与"启动瞬间打开"？（2026-11-11）

> **问题**：软件启动时把自己 `SetPriorityClass(HIGH)`，启动完成后降回正常档位，能不能提高启动性能和"启动瞬间打开（双击文件直接开）"的性能？
>
> **结论**：
> 1. **这套机制上游代码里已经有了，而且默认开启**（`ApplicationEvents.vb` 启动时拉到 HIGH，`Form1_Shown` 后 1500 ms 降回启动前保存的原始 class；`FFF_NO_STARTUP_PRIORITY=1` 可关）。它不是 PR #57 新增，属于 PR #48 时代落地、已在基线 `72af915` 里。
> 2. **已有的两次实测都不支持它有效**：唯一一次支持性读数（−111.7 ms）是"预取+优先级"**合测**，拆开后优先级单独测 **Δ +4.4 ms、p=0.783（14 轮交替、负载 57.4%）**，落在噪声内且符号对 ON 不利（docs/124 §2.3）。
> 3. **不建议新增或再加热**。现实现还带三处实打实的代价：与内核 `PlacementPolicy` 的优先级基线耦合（docs/124 判"真缺陷、本机未复现"）、固定 1500 ms 降档与"打开大文件"的实际时长不匹配、HIGH 覆盖全进程所有线程（含预取侧车/图层泵）。
> 4. 如果目标真的是"负载机/最坏情况"，**先做受控争抢实验再谈**（§五.3）；更值钱的方向是把启动关键线程钉到 P-core（CPU Sets）和继续减同步等待。

## 一、现状（代码事实，3689f77 树）

| 位置 | 行为 |
|---|---|
| `FFF.Player/ApplicationEvents.vb:20-24` | `MyApplication_Startup` 里依次调 `启动期拉高优先级()` / `启动期预取大件()` / `启动期预热GPU设备()` |
| `ApplicationEvents.vb:62-76` | 读当前 `Process.PriorityClass` 存进 `启动期原始优先级`，然后 `PriorityClass = High`；`FFF_NO_STARTUP_PRIORITY=1` 退出；读/写失败静默（优先级不是启动前提） |

- 生命周期（旧构建实测，docs/120 §二）：`High@0.3s → 窗口@1.8s → Normal@2.6s`；当时降回延时是 600 ms，现码是 **1500 ms**。

## 三、为什么理论上也只有很小的空间

1. **优先级只重排"就绪"线程**。它不改变 I/O 优先级、GPU 驱动排队、DWM 合成、vblank 等待。而启动关键路径的大头恰好是同步等待与一次性成本：docs/133 的启动分层——`Attach` 294.5 ms（其中 258.5 ms 是那一帧必须付的）、框架起窗 251–355 ms（WinForms 内部不可动）、设备创建 150–170 ms（在等驱动/GPU）、首帧等 vblank。
2. **空闲机上它是恒等操作**：没有就绪竞争者时，调度器本来就把 CPU 给它；文档自己写"空闲机收益≈0"。
3. **负载机上通常也没有"排队"可抢**：这台是 i7-13650HX（20 逻辑核）。后台负载 50–60% 意味着大约 10–12 条就绪线程，**远少于 20 条 CPU**——启动的 UI 线程几乎不会被排在队里等。优先级要产生收益，需要"就绪线程数 > 逻辑核数"的极端争抢；那种场景下整机体验本来就已经崩了。
4. **前台提升已经覆盖大半窗口**：窗口出现后应用就是前台进程，Windows 对前台进程有调度提升（更大的时间片/优先级分离），更高级别的系统线程（DWM/音频/驱动）本来就在普通进程之上，HIGH 压不动它们。
5. **进程级 class 不区分自身线程**：真正的"首帧关键线程优先"是线程级 `SetThreadPriority` 的事，进程 class 一拉，预取侧车解码、图层泵、后台线程全都跟着高——它们和首帧路径抢 CPU 时并不比别的进程更"讲道理"。

## 四、现实现的风险与缺陷（比收益更值得处理）

1. **与内核 `PlacementPolicy` 的基线耦合（真缺陷、本机未复现，docs/124 §4.1）**：内核在首次播放 `OnPlaybackStart` 采样 `baselinePriorityClass_`（`PlacementPolicy.cpp:476-480`），tier 从 `Boosted` 释放时按该基线恢复（`:589-591`）。若播放泵在 `Shown+1500ms` 之前启动（**"启动即打开/自动播放"正是本问题关注的场景**），基线记成 `HIGH`；此后内核 Boost 释放会把进程恢复成 HIGH ⇒ 进程长期停在 HIGH。host 侧后来改成了"恢复原始值"（`daf7142`），但内核侧的"取当前值当基线"没有对应修正，缺口仍在。
2. **固定 1500 ms 与真实打开时长不匹配**：T2 通常只在 Shown 后约 100 ms，但冷启动打开大图/大视频、慢盘、杀软扫描时远超 1500 ms——**恰好在最需要的时候降档**；反之如果启动很快，HIGH 白挂 1.5 s 压着其它应用。
3. **全进程线程继承 HIGH**：预取侧车（本仓库确实存在"无线程预算的自解码线程"，见 docs/144 PF-1）与 LakeUI 图层泵一起被拉高；启动期它们与首帧路径抢 CPU 时，进程 class 拉高只是让它们更狠地挤别人，不改善自己内部的次序。
4. **用户观感风险**：HIGH 窗口内磁盘/GPU 重活会让别的应用短暂卡顿；只按自己的 T2 记账会低估这项成本。
5. **测量学污染**：每次启动 A/B 都要控制这个 env，否则就是隐性混淆项——PR #48 的 −111.7 ms 误归因就是先例。

## 五、建议

**5.1 首选：删掉启动期 HIGH**（保留 `FFF_NO_STARTUP_PRIORITY` 兼容一段时间）。理由：无收益证据 + 消除与内核 `PlacementPolicy` 的隐式耦合 + 少一个启动期混淆项。删除的验证成本很低：`FFF_NO_STARTUP_PRIORITY=1` 就是现成的"无此功能"臂，20 轮交替确认 T2 无退化即可。

**5.2 若坚持保留，至少改成：**
- 降档**事件驱动**：首帧 presented / 首图 opened / 播放器 Preroll 完成，取"先到者"，上限 3 s；不要用 `Shown+固定延时`。
- 只对启动关键线程 `SetThreadPriority(HIGHEST)`（UI 线程 + 内核 create 线程），**不动进程 class**；预取/图层泵保持低档。
- 修内核基线：`PlacementPolicy` 不把 `HIGH` 当基线（或由宿主显式传入"原始 class"）。

**5.3 若目标真是"负载机最坏情况"，先做受控实验（约 10–15 分钟）：**
- 造争抢：8–12 条 NORMAL 优先级 CPU 忙线程 + 并发磁盘读，目标"就绪线程数 > 20"。
- A/B：同一 exe，`quiet_ab.ps1 -ExeA/-ExeB ... -EnvA "FFF_NO_STARTUP_PRIORITY=1"`，20 轮逐轮交替，判据 T2 中位差 ≥5%、p<0.05。
- 同时测"CPU 时间占墙钟比"：启动到 T2 期间 `GetProcessTimes` 的 CPU 秒 / T2 秒。**若 <30%，说明启动不是 CPU 排队瓶颈，这条路直接判死**；若 >70%，才值得继续做线程级提升。

**5.4 更值钱的方向（都有既有实测或明确机制）：**
- 继续减同步等待/延后非关键工作：四图层延后 −88.6 ms（docs/133）、GPU 预热消融 −446.6 ms（docs/124 §2.2）、R2R/O3-A/O4 已落地部分——这些是启动路径的真实结构，不是"抢 CPU"。
- **CPU Sets 而非 priority**：本机是 6P+8E 混合架构，把启动关键线程显式钉到 P-core 的 CPU set（`SetThreadSelectedCpuSets`），比进程 class 更对症——内核 `PlacementPolicy` 已有 tier0 P-core 偏好机制，但**只用于播放期，启动期未用**。这条同样要先测（启动期线程多且分散，限制 CPU set 有反效果风险）。

## 六、边界

- 本轮**未跑新基准**：当前窗格负载 ~65%（360tray / DeepSeek Harness / codearts-agent / Intel 显卡服务等），不满足 docs/132 的安静窗纪律；本文直接引用 docs/120/124 的同窗 A/B，不制造跨窗数字。
- 代码事实取自 `3689f77` 树；运行时优先级轨迹未在本轮重测（docs/120 §二给了旧构建轨迹，现码降回延时已从 600 ms 改为 1500 ms）。
- 若用户要求"现在就验证"，最小实验即 §5.3，产出两个数：T2 中位差、启动期 CPU 占墙钟比。
