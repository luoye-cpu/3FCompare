## 3. 执行过程（**全程未用 `git stash`**）

未提交的 P1/P2/P3 改动（3 个文件）先存为补丁，rebase 后再 3-way 应用回去 —— 绕开 `git stash`
（项目明令禁用：曾丢 28 提交）。

```bash
cd 3fp/kernel
git branch -f backup/pre-upstream-a87046e upstream/image-mode   # ① 安全备份（本地，可随时回退）
git diff > 3fp/build/pending-p1p2p3.patch                       # ② 存下未提交改动
git checkout -- <3 个文件>                                       # ③ 退回，得到干净工作区
git rebase upstream/master                                      # ④ 7 提交 rebase（无冲突）
git apply -3 3fp/build/pending-p1p2p3.patch                     # ⑤ 3-way 应用回去
git reset                                                       # ⑥ 回到未暂存（与 rebase 前状态一致）
```

## 4. 更新后的验证

### 4.1 构建

`dotnet build FFF.Player.Tests.vbproj -c Release` ⇒ **0 错误 0 警告**（同时产出宿主与测试）。

### 4.2 宿主测试全扫描（21 个单参数开关）

⚠ 宿主测试共 **51 个** `String.Equals(参数(0), "--…")` 分支、**没有全量模式**，故写了
`3fp/tools/run_host_tests.sh` 逐个跑。**⚠ 覆盖率须如实标注**：脚本只提取 `参数.Length = 1` 的开关
（**21 / 51**）；其余 30 个需要媒体/图片路径等额外参数，脚本未覆盖。
其中与图片模式最直接相关的 `--static-image-open-regression <图片>` 已**单独**用 6 种格式跑过（见 §4.4）。

**首轮：12 通过 / 9 失败** ⇒ 但 9 个失败里 **8 个是同一个临时目录症状**
（`The directory … does not exist` / `Cannot create … because a file or directory with the same name already exists`）。

**⚠ 根因是环境而非代码**：Git Bash 把 `TEMP`/`TMP` 设成 **POSIX 路径 `/tmp`**，
Windows 原生进程按 `C:\tmp` 之类解释 ⇒ 测试里 `Path.GetTempPath()` 拿到的目录不存在/不可建。
把 `TEMP` 归一为 Windows 路径后重跑，**第二遍只剩 3 个失败**（6 个转绿 ⇒ 属偶发/环境性）。

### 4.3 剩余 3 个失败 —— **全部为更新前既有，非本次更新引入**

用「切到更新前基线 `88526b5` 跑同一组」做 A/B：

### 4.4 与图片模式最直接相关的那个开关：`--static-image-open-regression <图片>`

（该开关需要图片路径，故不在 §4.2 的 21 个之内，单独跑。）

| 输入 | 更新后 `83a775c` | 更新前 `88526b5` | 判定 |
|---|---|---|---|
| `basic\01b_srgb_1920x1080.png` | **PASS** | **PASS** | ✅ 正常 |
| `basic\01c_srgb_1920x1080.jpg` | **PASS** | — | ✅ |
| `hdr\04_pq_10bit.avif` | **PASS** | — | ✅ |
| `edge\08a_multipage.tiff` | **PASS** | — | ✅ |
| `edge\08b_single_256.ico` | **PASS** | — | ✅ |
| `anim\07a_anim.webp`（动画） | **FAIL**（等待首帧超时） | **FAIL（同样超时）** | **既有** |

> 动画 WebP 那条属**输入选择不当**：该测试的断言里写着"静态图片没有使用稳定的软件首帧解码路径"，
> **前提就是静态图**；动画 WebP 在改动前后都走**视频路径**，不适用。A/B 已确认两版同样失败。

**顺带读到的一条重要信息**：该测试 `Program.vb:3320-3328` 断言
「小尺寸图片按**原始尺寸居中**（输出左上角为黑）」——
这正是 `limitToNativeSize` 的预期语义，也说明 `docs/07` §4 记的"640×480 图呈 525×394 且锚定右下"
**确实偏离上游设计意图**（不是"上游本来就长这样"）。
不过该断言只在「图 ≤ 输出窗口」时生效，测试用的输出窗口是 640×360，
而 640×480 的图**高于**窗口 ⇒ 这条断言对那个输入**不触发**，所以它没被测试覆盖到。
