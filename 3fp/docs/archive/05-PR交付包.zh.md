## 1. 单提交信息（`git commit -F` 的输入）

```
Add a picture mode for still images

3FP currently treats every opened file as a video. A picture therefore
inherits a timeline it does not have: the session reports it as finished
playback as soon as its single frame lands, seeking along that non-existent
timeline fails, and a few formats are not even recognised as pictures at
all. This change keeps the existing video path untouched and adds a
picture mode on top of it, together with the small behavioural fixes that
make a picture usable.

Native:
- Report still images as Paused instead of Ended once their frame has been
  presented, so a freshly opened picture is not treated as finished
  playback (no auto-advance, no meaningless PlaybackEnded).
- Treat a seek on a still image as a successful no-op. Single-image
  demuxers are not seekable, so the previous path reported an error for
  every attempt; image2-based demuxers instead silently clamped the
  position to the media duration and re-rendered.
- Decide still images by frame count (nb_frames <= 1) instead of by
  demuxer name. Formats carried by the mov demuxer (AVIF, HEIC) were
  missed entirely and fell back to the video path.
- Reject images larger than the D3D11 texture limit during open with an
  explicit message, instead of failing later with a texture-creation error.
- Add FFF3FP_GetImageInfo: frame count, loop count, rotation (from the
  EXIF display matrix), source pixel format and bit depth, ICC profile
  size, alpha, and colour primaries/space/transfer, plus a wide-gamut flag.
- Let a wide-gamut SDR source use the scRGB output path. An SDR swap chain
  cannot hold colours outside Rec.709, so a Display P3 picture was being
  clipped back silently. Wide-gamut pictures are converted to BT.2020 (a
  lossless carrier, since Display P3 is a subset) before rendering.

Player:
- Add a picture mode: opening a picture shows it fitted, the wheel zooms
  around the cursor, dragging pans, left/right move to the previous/next
  picture in the same folder, and the timeline, play button and timecode
  are hidden. The mode can also be toggled from the menu.
- Build the picture list from the file's own folder and hide the timeline
  while the mode is active.
- Let picture mode step aside for 360-degree mode when the two disagree.
  The existing 360 detection also treats any frame twice as wide as it is
  tall as a panorama, so such a picture turned both modes on at once: the
  wheel went to picture zoom while the arrow keys never reached picture
  mode, because the 360 message filter consumes them first. Auto-entry now
  shares the 360 predicate instead of deciding on its own.

Behaviour is unchanged for video, audio, subtitles, disc navigation and
360-degree playback: the picture logic is gated behind a mode flag and the
video branches are not modified. The single exception is one guard clause in
the clip-range arrow handler, which now returns early when a handler
registered before it has already taken the key - picture mode is that
handler, and without the guard one press could both change picture and step
a frame. No handler set that flag earlier, so configurations without picture
mode behave exactly as before. There is no ABI change - PlayerApiVersion
stays at 15 and the snapshot layout is unchanged; FFF3FP_GetImageInfo is a
new export, so a host running against an older library simply receives
NotSupported and falls back to showing no picture details.

Verified by building the library and the player on Windows and running a
probe against a real window with real FFmpeg DLLs, comparing a baseline
build with the changed build on the same inputs. The video path was
exercised alongside the picture cases and behaved identically.
```

## 2. PR 正文（目标 `Lake1059/FFF_Project:master`）

### 标题

```
Add a picture mode for still images
```

### 正文

```markdown
### 概要

3FP 目前把打开的每个文件都当作视频处理。图片因此背上了一条它并不拥有的时间轴：
单帧一落地，会话就把它报成"播放结束"；沿这条不存在的时间轴 seek 会失败；
还有少数格式（由 `mov` 解复用器承载的 AVIF / HEIC）根本没被认成图片。

本 PR **不改动视频路径**，在其之上新增**图片模式**，并顺带修掉让图片不可用的几处行为问题。

### 一、内核侧改动（`FFF.Native`）

| # | 位置 | 改动 |
|---|---|---|
| 1 | `PlayerSession::FlushAtEnd` | 静态图不再进入 `Ended`，改为保持可交互（`Paused`）。此前一张刚打开的图片会被宿主当成"播放完毕"，触发自动续播/循环，并发出对图片毫无意义的 `PlaybackEnded` |
| 2 | `PlayerSession::DoSeek` | 静态图的 seek 变成**成功的 no-op**。单图解复用器不可 seek，旧路径每次都会报错；而 image2 系解复用器则是把位置静默夹到媒体时长并重渲染 |
| 3 | `IsStillImage` | 判定改为**按帧数**（`nb_frames <= 1`）而非解复用器名。原按名字枚举的写法永远追不上 FFmpeg，实测由 `mov` 承载的 AVIF/HEIC 会被漏判并回落到视频路径 |
| 4 | Open 阶段 | 超过 D3D11 纹理上限的图片**在打开时**以明确文案拒绝，而不是稍后以"纹理创建失败"这种模糊错误收场 |
| 5 | 新增 `FFF3FP_GetImageInfo` | 提供帧数、循环次数、旋转（取自 EXIF display matrix）、源像素格式与位深、ICC 大小、alpha，以及色彩 primaries / space / transfer 与广色域标志 |
| 6 | `VideoRenderer` | 允许**广色域 SDR 源**进入 scRGB 输出路径。SDR 交换链装不下 Rec.709 之外的颜色，Display P3 图片此前会被静默裁回 709；现改为先无损转换到 BT.2020（Display P3 ⊂ BT.2020）再渲染 |

### 二、宿主侧改动（`FFF.Player`）

新增**图片模式**：打开图片按适应窗口显示，滚轮以光标为锚点缩放，左键拖动平移，
←/→ 切换同目录的上一张/下一张，隐藏进度条、播放按钮与时间码；菜单可手动开关该模式。
图片列表由**文件所在目录**构建。
**自动进入图片模式让位给 360° 模式**：360 的识别里有一条"宽 == 高×2"的启发式，任何 2:1 素材都会命中，
两模式同时启用时滚轮归图片缩放、方向键却被 360 的消息过滤器吃掉 ⇒ 自动启用改为与 360 共用同一判据。

### 三、行为不变性

- 视频、音频、字幕、弹幕、光盘导航与 360° 播放**行为不变**：图片逻辑由模式开关门控，视频分支未被修改
- ⚠ **唯一例外是一行守卫**：剪辑区间的方向键处理器改为"若已有更早注册的处理器接管本次按键则直接返回"。
  图片模式正是那个更早的处理器；没有这行，一次按键会**既切图又逐帧**。
  在本 PR 之前没有任何处理器会置该标志 ⇒ **不含图片模式的配置行为逐字节不变**
- **无 ABI 变更**：`PlayerApiVersion` 仍为 15，快照结构不变
- 新导出 `FFF3FP_GetImageInfo` 遵循"未实现返回 `NotSupported`"的既有约定 ⇒ 新宿主 + 旧库的组合会安全降级，只是不显示图片扩展信息

### 四、如何验证

- 在 Windows 上编译内核（MSVC Release x64）与宿主（`dotnet build`），均通过
- 用一个独立探针在**真实窗口 + 真实 FFmpeg DLL** 下跑内核，对**同一组输入**交替比较
  「基线构建」与「本次改动构建」的可观测差异（图片不再进入 Ended、seek 不再报错、
  AVIF 被正确判为图片、超大图给出明确错误文案）
- 同时跑了视频与动画图片用例：视频路径行为与基线一致
```

### English summary

```markdown
### English summary

3FP currently opens every file as a video, so a still image inherits a
timeline it does not have: it is reported as finished playback as soon as
its frame lands, seeking along that timeline fails, and formats carried by
the mov demuxer (AVIF, HEIC) are not recognised as pictures at all.

This PR leaves the video path untouched and adds a picture mode on top of
it, plus the behavioural fixes that make a picture usable:

- still images stay interactive instead of entering Ended;
- a seek on a still image becomes a successful no-op;
- still images are detected by frame count rather than by demuxer name;
- oversized images are rejected during open with an explicit message;
- a new FFF3FP_GetImageInfo export reports frame count, loop count, EXIF
  rotation, source pixel format and bit depth, ICC size, alpha, and colour
  primaries/space/transfer with a wide-gamut flag;
- wide-gamut SDR sources may use the scRGB output path, converted to
  BT.2020 first (a lossless carrier), instead of being clipped to Rec.709.

On the player side, a picture mode is added: fitted display, cursor-anchored
wheel zoom, drag to pan, previous/next picture in the same folder, hidden
timeline, and a menu toggle. Auto-entry shares the existing 360 detection
instead of deciding on its own, so a frame that 360 already claims as a
panorama no longer turns both modes on at once.

One guard clause touches a video-side handler: the clip-range arrow handler
now returns early when a handler registered before it has taken the key. No
handler set that flag before this change, so configurations without picture
mode are unaffected.

No ABI change: PlayerApiVersion stays at 15 and the snapshot layout is
unchanged. FFF3FP_GetImageInfo is a new export, so a host paired with an
older library receives NotSupported and degrades gracefully.
```

## 3. 执行步骤

在 `3fp/kernel/` 下执行（**前 4 步全部本地，第 5 步才涉及远端**）：

```bash
cd /c/PLAN/3FCompare/3fp/kernel

# 0) 前置：P1/P2/P3 目前**只在工作区**。`merge --squash` 只压提交、不含未提交改动，
#    跳过这步会产出一个**不含这三个修复**的 PR。必须先提交到工作分支（需用户授权）。
git status --porcelain          # 期望：空。非空 ⇒ 先提交，别往下走
git log --oneline -1            # 期望：`83a775c` 之后、且包含 P1/P2/P3 的那个提交

# 1) 先抓上游（2026-09-24 上游已推进 3 个提交，别再假设"未动"），再基于最新 master 建 PR 分支
git fetch upstream master
git switch -c upstream/image-mode-pr upstream/master

# 2) 把 7 个提交压成工作区变更（零冲突：a87046e 是 83a775c 的祖先）
git merge --squash upstream/image-mode

# 3) 单一提交（提交信息见 §1，存为文件后 -F 传入）
git commit -F /c/PLAN/3FCompare/3fp/patches/commit-message.txt

# 4) 核验：提交后的树内容必须与工作分支**逐字节一致**
git diff upstream/image-mode upstream/image-mode-pr      # 期望：无输出
git diff --stat upstream/master upstream/image-mode-pr   # 期望：16 files, +751 -16（含 P1/P2/P3）

# 5) 推送并开 PR（**目标必须是上游 Lake1059/FFF_Project:master**）
git push -u origin upstream/image-mode-pr
```

> ⚠ 第 4 步的 `--stat` 若少了 `播放器图片浏览控制器.vb`、`播放器剪辑区间控制器.vb`、
> `FFF.Player.Tests/Program.vb` 三个文件 ⇒ 是**第 0 步没做**，不是数字写错，回去提交再压。
> 这三个文件是 P1/P2/P3 的全部落点（`docs/06` §5.1）。

> **为什么压扁后不必重新编译**：`docs/03` §6.4 第 4 步要求重编译，前提是"压缩可能改变内容"。
> 但第 4 步的 `git diff` 若为空，即证明**内容逐字节未变** ⇒ 无需重编译。
> （若第 4 步有输出，说明压缩过程引入了差异，**必须停下来查**，不要直接推。）
>
> ⚠ 本机 `git push` 的凭据机制有坑：`credential.helper` 是多值配置，直接 `push` 会弹 GUI 并挂死。
> 可用 `git -c credential.helper= -c credential.helper=wincred push …`（先清空列表再指定）。
> 详细见 `.workbuddy-ai/memory/MEMORY.md`（用户级）。
