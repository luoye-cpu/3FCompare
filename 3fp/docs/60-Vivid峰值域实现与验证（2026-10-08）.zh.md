## 一、方案选择与理由

依据 `3fp\docs\61-Vivid峰值域规范依据（2026-10-08）.zh.md`（P2 规范依据）与 Lead 的更正指令，
采用**方案 B 的保守落地**（仅改峰值派生），**未触碰** `VideoRenderer.cpp`。

### 1.1 为什么门控不是 `frame->color_trc`

task-4 原始规范写的门控是 `frame->color_trc == AVCOL_TRC_ARIB_STD_B67`。
**实测证明该判据在本样本上恒假**，按字面实现会得到"零行为变化"（详见 `_3fc_tmp\task4-prep-门控阻塞.md`）：

```
ffprobe -select_streams v:0 -show_entries stream=color_transfer -of default=nw=1 hdr_vivid_h265_sample.hevc
→ color_transfer=arib-std-b67          # 流级：有值（HLG）
ffprobe -read_intervals "%+#3" -show_entries frame=color_trc -of csv hdr_vivid_h265_sample.hevc
→ frame,I,bt2020,                       # 帧级：空（AVCOL_TRC_UNSPECIFIED）
```

⇒ **流级 `color_transfer` 有值，帧级 `frame->color_trc` 为空**（两个样本皆然）。
内核读的是帧级，因此帧级 trc 不可用作门控。

### 1.2 真正的机制（Lead 定位，本机复核确认）

| 步骤 | 位置 | 行为 |
|---|---|---|
| ① | `ConfigureStream:182-186` | 读**流级** `parameters->color_trc == ARYL_STD_B67` → `format=Hlg(3)`、`sourcePeakNits=1000.0f` |
| ② | `ConfigureStream:204` | `streamState_ = next`（分类被正确保存） |
| ③ | `ProcessFrame:213` | `auto next = streamState_`（正确分类随帧带入） |
| ④ | `ProcessFrame:239` | **无条件** `next.format = HdrVivid(5)` —— 覆盖了正确分类 |
| ⑤ | `ProcessFrame:245`(原) | `sourcePeakNits = 1.0 × 10000 = 10000` —— 覆盖了正确的 1000 |

⇒ **缺陷本质：分类本来是对的，但 Vivid 分支把它丢掉，并把正确的 1000-nit 峰值替换为物理上无意义的 10000。**
探针逐字印证：`open: hdrFormat=3 hdrPath=3`（HLG 正确）→ `play: hdrFormat=5 hdrPath=6 peak=10000`。

### 1.3 采用的门控（非粘性）

```cpp
const bool vividBaselineIsHlg = streamState_.format == FFF3FPHdrFormat::Hlg;
```

**为何用 `streamState_.format` 而不是 `compatibility` 位**（Lead 指出的粘性风险，已按构造规避）：

- `compatibility` 在多处用 `|=` 累加（Vivid 分支 `:240-241`；`ClassifyDolbyVision:53-54` 在
  DV profile 7 / BL compat id 4 时会置 Hlg 位），且 `next` 继承自 `streamState_`。
  ⇒ 用 `& Hlg` 判据**可能把一个真正 PQ 基线的流永久钉在 HLG 分支上**。
- `format` 是**赋值**语义，从不 `|=`，因此**不可能粘滞**。
- `ConfigureStream` 起始于 `HdrFrameState next{}`（`:169`，零值）并**无条件** `streamState_ = next`（`:204`），
  故 `streamState_.format` 每个流都被完整重新推导，无跨流残留。

⇒ **结论：门控为非粘性，无 PQ 误分类缺口。** 这一点由构造保证，非默认假设。

### 3.3 修复后峰值是 4000（非 1000）——**已裁定：接受，保留；但"域正确性"论证已撤回**

Lead 初版预期 HLG 路径应得 **1000**；实测为 **4000**。**经 Lead 独立复核后裁定：接受 4000，不改为 1000。**

#### 3.3.1 修复的语义主张（必须准确表述）

> **修复的语义是"停止用 HLG 相对域字段断言一个物理无意义的 10000 nits"，而**不是**"把峰值设为 1000"。**

具体：**Vivid 动态峰值不再被应用于 HLG 基线**，该流于是回退到**自身声明的静态峰值**。
4000 来自静态元数据路径，**不是**从 `maximum_maxrgb` 推出来的。

#### 3.3.2 链条（本机逐项实测复核，VERIFIED）

1. HLG 基线下不再覆写 `sourcePeakNits` ⇒ `dynamicSourcePeak` 保持 `false`；

#### 3.3.3 为何接受 4000 ——**但不主张它是"域上正确"的值**（经对抗复核更正）

> ⚠ **本节曾主张"4000 是更正确的结果"、"用 1000 属语义错位"。该论证已被 task-5 对抗复核推翻，Lead 已承认并撤回。以下为更正后的表述。**

**更正后的定性**：

> 4000 是**量级更合理、来源可追溯、并与既有静态回退设计一致的保守值**；
> 它**并非域上正确的值** —— 它同样源自**绝对域**元数据。mastering display 描述的是**母版显示器（mastering monitor）的亮度框**，
> 而非纯粹"内容有多亮"的断言；`min_luminance = 0.005 nits` 表明这是 **PQ/HDR10 时代的绝对域母版框**。
> 把它的绝对 nits 用于 **HLG 相对域**内容，**仍属同一类错误（绝对域值用于相对域）**，
> 只是**量级从 10× 降到 4×**。

**为何"用 1000 属语义错位"这一原始论证不成立**：

- 原论证称 4000 是"内容属性"、1000 是"显示器属性"，故 4000 更正确 —— **这个不对称性不成立**：
  mastering display 元数据同样是在描述**显示器**（母版显示器）的亮度，两者都是"显示器有多亮"类别的声明。
- 因此**不能**以"域正确性"为由选择 4000。

**那么为何仍然接受 4000（决策不变，理由收窄）**：

| 理由 | 说明 |
|---|---|
| 量级更合理 | 4× 偏差显著优于 10× 偏差 |
| 来源可追溯 | 是流**自身显式声明**的元数据，非内核自造约定 |
| 与既有设计一致 | 沿用 `:322-327` 既有的静态元数据回退路径，不新增特例 |
| 改动最小 | 无需越过静态回退去覆写流声明的值 |

⇒ **决策（接受 4000、否决覆写为 1000）保持不变且仍受支持；仅其"域正确性"论证被撤回。**
**遗留的诚实结论：本修复消除了 10× 的无依据断言，但未消除"绝对域元数据用于相对域"这一问题类别本身。**
彻底的解决需按 UWA FAQ Q24 做 HLG→PQ 显式转码（`docs/61` §4.3.2），**属独立任务，未在本次范围内**。

#### 3.3.4 被考虑并**明确否决**的替代方案

| 方案 | 否决理由 |
|---|---|
| 显式覆写为 HLG nominal `1000.0f` | 需**越过静态元数据回退**去改写流自身声明的峰值，是**更大的语义改动**，超出"最小 diff"约束，且与 `:322-327` 既有设计冲突 |

#### 3.3.5 诚实的局限（HLG 且**无**静态元数据时）

若某 HLG 内容的**静态元数据缺失**（无 MaxCLL、无 mastering display），`StaticSourcePeak` 返回 0，
峰值将保持 `ConfigureStream`/帧级 HLG 分支设定的 **1000.0f** —— **这正是相对域所期望的默认值**。

即：**有**静态元数据 → 用其声明值；**无** → 回落到 HLG 相对域默认 1000。
两条路径都不再产生物理无意义的 10000。
⚠ **本仓库现有样本未覆盖"HLG 且无静态元数据"这一分支（未实测）。**
