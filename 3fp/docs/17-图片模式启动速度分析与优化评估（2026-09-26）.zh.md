## 3. 关键归因：**首触 JIT**，不是算法浪费

### 3.1 决定性证据：同进程二次调用

在 `按钮图标资源.加载()` 之后**立刻再调一次**并单独计时：

| | 耗时 (ms) |
|---|---:|
| 首次 `加载()` | **74.0** |
| **同进程第二次 `加载()`** | **2.4** |

**30× 差距** ⇒ 74 ms 里几乎全是**代码首次执行**的开销（`Svg` 程序集加载 + SVG/XML 解析栈 JIT + GDI+ 初始化），
**不是**「11 个 SVG 解析慢」。同理 `播放器界面呈现器` 的 54 ms（首触 `LakeUI.PrecisionTimer`）、
`信息图层呈现器.应用全局字体` 的 78 ms（首触字体反射）**都是首触型**。

⇒ **这解释了为什么 `PublishReadyToRun` 这一条就有效**（见 §4）。

**旁证**：启动期间该进程**加载了 154 个模块**（WinForms + WPF + Vortice + Svg + LakeUI + 全部传递依赖），
与「大量程序集首次加载/JIT」的判断一致。

### 3.2 FFmpeg 核心文件探测（30.8 ms）—— ⚠ 首版归因错误，已实测修正

`Form1.vb:86-99` 对 6 个前缀逐个走 `枚举可加载核心文件()`；
候选目录 = `AppContext.BaseDirectory` + 程序集目录 + **`PATH` 的每一项**（本机 **64 项**）。

> 🔴 **首版报告曾断言「PATH 扫描是纯浪费」——那是推理，不是实测，现予撤回。**
> 补做裁决实验（`tools/startup_path_ab.ps1`）：同批次交替对比「完整 PATH」vs「极简 PATH（3 项）」，9 轮：
>
> | | 完整 PATH | 极简 PATH |
> |---|---:|---:|
> | 中位数 | 1131.5 ms | 1108.1 ms |
> | 轮间 delta 范围 | — | **+18.5 ~ −59.8 ms** |
>
> **中位数差 −23.4 ms，但抖动幅度（≈±60 ms）远大于差值** ⇒ **落在噪声带内，不足以归因**。
> 且缩短 PATH 本身也会加速 `LoadLibrary` 的依赖搜索（这是**应用改不了**的）。

**修正后的结论**：`可以加载核心文件` 用 `For Each` 遍历迭代器且**首次命中即 `Return`**（VB 迭代器惰性），
因此只要 exe 同目录有 FFmpeg，**PATH 目录根本不会被枚举**。30.8 ms 的主体是
**6 个 FFmpeg DLL（合计 >100 MB）的 `NativeLibrary.TryLoad` 本身**（映射 PE + 解析导入表），不是扫目录。

## 5. 其余候选：❌ 经实测后**全部否决**（附理由）

> 这几项在首版报告里曾被列为「次级建议」。补做实测后**均不成立**，特此记录以免重复投入。

### 5.1 ❌ FFmpeg 探测窄化 —— **否决**

- **实测**：完整 PATH(64 项) vs 极简 PATH(3 项)，中位数差 **−23.4 ms**，轮间抖动 **±60 ms** ⇒ **噪声内**（§3.2）。
- **原理**：`For Each` + 迭代器惰性 ⇒ 同目录命中即短路，**PATH 根本不会被枚举**；30.8 ms 主体是
  6 个 >100 MB DLL 的 `TryLoad` 本身，**不是扫目录** —— 窄化探测范围**动不了它**。
- **风险**：若真把 PATH 从候选里删掉，会**破坏**「用户自装 Shared FFmpeg + 设环境变量」这一真实场景
  （`核心文件名称` 的报错文案本身就写着「放到程序目录**或环境变量**后重新启动」）。
- ⇒ **收益 ≈0 且功能有损，不做。**

### 5.2 ❌ 按钮图标懒加载 —— **否决**

- 首版归因「11 个 SVG 解析慢」是**错的**：`ICON_LOAD_2ND = 2.4 ms` vs 首次 `74.0 ms` ⇒ 74 ms 是
  **`Svg` 程序集首触 JIT + GDI+ 初始化**，不是解析工作量。
- **关键**：`按钮图标 = 播放器按钮图标资源.加载()` 的**下一行就是 `配置播放器按钮图标()`**，
  立刻就要用到图标 ⇒ 懒加载只是把同一份 JIT 成本**挪后几毫秒**，窗口并不会更早出现。
- 真正能消掉它的就是 **R2R（已做）**；若要彻底移除 `Svg` 程序集，需构建期预光栅化为 PNG，
  但会**丢失 DPI 自适应**（现为运行时按 48×48 绘制）⇒ 权衡后不做。

### 5.3 `设定.启动时加载设置()`（43 ms）

读取 `FFF.Player.Settings.json` + 可能的**磁盘写探针**（可写性检测）。**不建议动**（涉及可移植部署语义）。

### 5.4 `PerformLayout` + 应用初始尺寸（62 ms）

WinForms 布局固有成本。**不建议动**（改布局引擎风险远大于收益）。

### 5.5 ⚠ 一个「不推荐」的选项：AOT

主项目 `src/3FCompare` 用 `PublishAot=true`，但**宿主 `FFF.Player` 不宜照搬**：

- 宿主依赖 `LakeUI`（指向 **`bin\Debug`** 的引用！见 vbproj `HintPath`）、`Svg`（反射式）、`WinForms`（大量反射/序列化）。
- AOT 需要完整 trim 兼容性；WinForms + `Svg` 的反射路径极易被 trim 掉 ⇒ 风险极高。
- R2R 是**渐进式收益、零 trim 风险**的安全选择。

> ⚠ **顺带发现（预存、未改）**：`FFF.Player.vbproj` 的 `<Reference Include="LakeUI">` 指向
> **`..\..\LakeUI\LakeUI\bin\Debug\...`** ⇒ Release 宿主引用 **Debug 版 UI 库**。
> ⚠ **但本轮核实：LakeUI 目录里只存在 Debug 构建，没有 Release 产物**（`3fp/LakeUI/LakeUI/bin/` 下只有 `Debug/`）
> ⇒ 这不是「忘了切」，而是**当前无 Release 可用**。要改需先构建 LakeUI Release，属**独立任务**，不在本轮范围。

### 5.6 ❌ 去掉 `<UseWPF>True</UseWPF>` —— **否决（零收益）**

- 全仓 grep：宿主**无任何文件**引用 WPF 命名空间；**无 `.xaml`**；`LakeUI.dll` 的 assembly 引用里
  `PresentationCore`/`WindowsBase`/`System.Xaml`/`WindowsFormsIntegration` **计数全 0**。
- **决定性判据**：`FFF.Player.deps.json` 里 **WPF 相关库 = 0 个**（共 13 个库）；输出目录也**没有**这些 DLL。
- ⇒ `UseWPF=True` 未产生任何 WPF 产物，**去掉它不会减少任何加载**，反而是无谓的改动风险。**不做。**

### 5.8 ⚠ 体积问题：单文件 exe 为什么这么大（40.5 MB）

用户提问「我记得以前只有几 MB」。**实测构成**（非单文件发布目录，剔除未打包的 FFmpeg 后 = 38.8 MB）：

| 文件 | 大小 | 占打包内容 |
|---|---:|---:|
| **`Microsoft.Windows.SDK.NET.dll`** | **25.99 MB** | **67.1%** ⭐ |
| `LakeUI.dll` | 2.15 MB | 5.5% |
| `harfbuzz.dll` / `libxml2.dll` / `iconv-2.dll`（libass + 光盘库） | 3.37 MB | 8.7% |
| `FFF.Player.dll` + `FFF.Native.dll` | 1.66 MB | 4.3% |
| `Svg.dll` + `ExCSS.dll` + `Vortice.*`(6) | 2.52 MB | 6.5% |
| `WinRT.Runtime.dll` + `freetype`/`bluray`/`udfread` 等 | ~3.1 MB | 8.0% |

**⭐ 真凶 = `Microsoft.Windows.SDK.NET.dll`（26 MB，67%）**：
这是 **WinRT API 投影程序集**，由 TFM **`net10.0-windows10.0.26100.0`**（带 Windows SDK 版本号）自动引入
（deps.json 里 `runtimepack.Microsoft.Windows.SDK.NET.Ref/10.0.26100.87`）。
⚠ **宿主一行 WinRT 代码都没用**：全仓 grep `Windows.(Foundation|Graphics|Storage|Media|UI|System|…)` **0 命中**，无 `.xaml`。

**与「以前几 MB」的对比**：主项目 `3FCompare.exe` = **72 KB** —— 它是 **AOT** 且 **FFmpeg 外置**（`ffmpeg-full/` 单独分发，
共 17 项发布包）。`FFF.Player` 走的是**单文件自带全家桶**（含 libass / 光盘库 / Vortice / LakeUI / Svg），且**反而没打包 FFmpeg**（109 MB）。

**试过两条瘦身路，都被 SDK 硬性拒绝**：

| 手段 | 结果 |
|---|---|
| `-p:PublishTrimmed=true` | ❌ `NETSDK1175`：**启用剪裁时不支持 Windows 窗体** |
| `-p:EnableCompressionInSingleFile=true` | ❌ `NETSDK1176`：**仅 self-contained 单文件支持压缩** |

**唯一可行（未做，风险较大）**：把 TFM 从 `net10.0-windows10.0.26100.0` 改成不带 SDK 版本的形式（如 `net10.0-windows`），
去掉 26 MB 的 WinRT 投影 ⇒ 单文件 exe 预计 **40.5 MB → ~14 MB**。
⚠ 但代价明显，**故未擅自改动**：

1. 输出路径从 `bin/Release/net10.0-windows10.0.26100.0/` 变为 `bin/Release/net10.0-windows/` ⇒
   **所有脚本、测试、门禁的路径都要跟着改**。
2. 实测会撞 `NETSDK1135`：`SupportedOSPlatformVersion 10.0.19041.0` 高于 `net10.0-windows` 的默认
   `TargetPlatformVersion 7.0` ⇒ 需一并调整该属性。
3. 需验证 `LakeUI`（目标 `net10.0-windows10.0.17763.0`）在降级 TFM 下的引用兼容性。
4. 这是**上游项目**代码，改 TFM 会与上游同步/PR 产生冲突面。

> **取舍提示**：本轮 R2R 让体积 **+7.5 MB**（40.5 → 48.0 MB）。若体积优先于启动速度，回退 `PublishReadyToRun`
> 即可省回这 7.5 MB，代价是冷启动慢约 13%。

### 5.7 ⚠ 新发现（非本轮范围）：单文件发布**不含 FFmpeg**

- vbproj 的 `DevelopmentRuntime`（FFmpeg 六件套）只被 `CopyNativeRuntime` 拷到 `$(OutDir)`，
  **不在发布项图里** ⇒ `CopyProductNativeToPublish` 只拷 `ProductNative`(FFF.Native) + `LibassRuntime`。
- **实测**：单文件 exe **40.5 MB**，而 FFmpeg 六件套合计 >100 MB ⇒ 确实没打包进去。
- ⇒ 单文件形态启动时 `可以加载核心文件` 找不到 FFmpeg ⇒ 走「核心文件缺失」早退路径
  （§4.2 ② 的 836 ms 就是这个**降级路径**的耗时，**不代表完整启动**）。
- **属打包问题，不是启动速度问题**，未改动；建议单独确认发布包是否另有 `ffmpeg-full` 目录或依赖 PATH。

## 7. 结论

1. **唯一划算且零代码风险的杠杆是 `PublishReadyToRun`，已落地**：
   发布产物对照 **−141.4 ms（−13.0%）/ 11 轮全胜**；真实单文件交付 **−74.1 ms（−8.9%）/ 9 胜 11**，
   代价 **+7.5 MB**。改动仅 `FFF.Player.vbproj` 一处，**未动任何 .vb 代码**。
2. **根因是首触 JIT**，不是算法浪费（`ICON_LOAD_2ND` 2.4 ms vs 首次 74 ms 是决定性证据）——
   这也解释了为什么其余「算法侧」优化都不成立。
3. ⚠ **首版报告的两条建议已被实测否决**：FFmpeg 探测窄化（噪声内 + 有功能风险，§5.1）、
   图标懒加载（首触 JIT 且立即被用到，懒加载只是挪后，§5.2）。另新增否决项：去掉 `UseWPF`（§5.6，零收益）。
4. **若干怀疑点已被证伪**：DLL 自解压、DXGI 枚举、`播放器控制器` 构造（0.2 ms）、文件关联同步 —— **都不在启动路径**。
5. ⚠ **新发现（未处理）**：单文件发布**不含 FFmpeg**（§5.7）⇒ 该形态实际走早退路径，属打包问题。
5b. **体积 40.5 MB 的真凶是 `Microsoft.Windows.SDK.NET.dll`（26 MB / 67%）**——WinRT 投影，宿主一行都没用（§5.8）。
    Trimming 与单文件压缩**均被 SDK 拒绝**；唯一出路是改 TFM，但会改变输出路径且属上游代码，**未擅自改动**。
    ⚠ 本轮 R2R **+7.5 MB**，体积优先时可回退（代价：启动慢约 13%）。
6. ⚠ **仍未动的建议**：`LakeUI` 引用的是 Debug 构建，但**当前没有 Release 产物可切**（§5.5），需先构建 LakeUI Release。
7. **git**：本轮只在工作区改了 `FFF.Player.vbproj`（未提交）；**未做任何 git 写操作**，是否提交请用户定夺。
