## 1. 重新取证的实测读数（最新基线）

```
===== SDR（源 1280x720，窗口 900x520）=====
渲染目标: swap=884x481 client=884x481 dest=(14,0) 855x481 outBits=8
CopySdrFrame 尺寸查询 -> 884x481          ⚠ 期望 1280x720
CopySdrFrame 拷贝     -> result=0（成功，但只有窗口尺寸）

===== HDR（源 1920x1080，MapToHdr）=====
渲染目标: swap=884x481 outBits=16 hdr=1
CopySdrFrame 尺寸查询 -> 884x481
CopySdrFrame 拷贝     -> result=-7        ⚠ 失败（NotSupported）
ReadVideoPixelRegion  -> result=-2        ⚠ 失败
```

**两条 GPU 回读路径在 HDR 下都不可用**；SDR 下也只有窗口尺寸。

## 2. 关键新发现：**不需要新增 ABI 也能修**

`docs/37` 提的方案 A 是"新增 `FFF3FP_CopySourceFrame` 导出"。重新读代码后发现**有更好的办法**：

### 2.1 `DrawCachedVideo` 已经能渲染到任意目标

```cpp
FFFResult PlayerVideoRenderer::DrawCachedVideo(ID3D11RenderTargetView* target) noexcept {
    ...
    destination = CalculateVideoDestination(layoutWidth, layoutHeight,
        swapWidth_, swapHeight_, ...);      // ← 唯一与"窗口尺寸"绑定的地方
    ...
    DrawWithShader(target, destination.x, destination.y, destination.w, destination.h, 0, views);
}
```

它接收**任意 `ID3D11RenderTargetView`**，只是**目标矩形按交换链尺寸算**。
⇒ 只要让它按**传入的尺寸**算目标矩形，就能渲染到一张**源分辨率**的离屏纹理。

**⇒ 修复的本质是把 `swapWidth_/swapHeight_` 参数化，而不是新造一条渲染路径。**

### 2.2 推荐方案：`FFF3FP_CopyFrame`（帧回读，走既有渲染路径）

```cpp
// 新增导出（追加在 v16 之后，与 VSR/旋转同一约定：不动 PlayerApiVersion）
FFF3FP_API FFFResult FFF3FP_CopyFrame(FFF3FPHandle player,
    void* pixels, std::uint32_t capacity,
    std::uint32_t* width, std::uint32_t* height,
    std::uint32_t layout /*0=源分辨率, 1=当前窗口*/, 
    std::uint32_t format /*0=BGRA8, 1=RGBA16F*/) noexcept;
```

内核侧流程：

```
1. 取源分辨率（含旋转后的宽高交换）
2. 建一张 DEFAULT 纹理 + RTV：
      layout=0 → 源分辨率，format: BGRA8 或 R16G16B16A16_FLOAT
      layout=1 → swapWidth_ x swapHeight_
3. 调用参数化后的 DrawCachedVideo(rtv, 目标尺寸)   ← 复用既有渲染
4. 需要时叠加字幕/弹幕层（与 Present 同序）
5. CopyResource 到 STAGING → Map → 逐行 memcpy 到 pixels
```

**为什么这条路对**：

| 需求 | 如何满足 |
|---|---|
| 源分辨率（不是窗口尺寸） | 目标尺寸传源分辨率 |
| **不受遮挡/最小化影响** | 全程离屏，**完全不碰屏幕** |
| **HDR 可用** | 目标纹理按所需格式创建：SDR→BGRA8，HDR→RGBA16F（scRGB 线性） |
| 与画面一致（含旋转） | 复用 `DrawCachedVideo`，旋转/缩放/色调映射**自然一致** |
| 不破坏 ABI | 追加导出，`PlayerApiVersion` 保持 16 |

### 2.3 需要改的既有代码（最小集）

| 位置 | 改动 |
|---|---|
| `DrawCachedVideo(target)` | 增加一个"输出尺寸"参数（默认 `swapWidth_/swapHeight_`），把 3 处引用换成它 |
| 新增 `EnsureReadbackTexture(w,h,format)` | 缓存一张离屏纹理，尺寸/格式不变则复用 |
| 新增 `CopyFrame(...)` | 上面的流程 |
| `PlayerApi.cpp` | 追加导出 |
| `FFF.Player.Api.h` | 追加声明 |
| 宿主 `播放器画面菜单控制器.vb` | 三个菜单项改走 `CopyFrame`；"原始画面"用 `layout=0` |
| 宿主 `播放器会话.vb` | 把零调用的 `读取SDR合成帧` 替换为 `读取帧(layout, format)` |

**改动量估计：内核约 150 行，宿主约 60 行。** 无需新渲染路径。

## 3. 分阶段实施建议

### P1（最小可用，先解决"HDR 失败"与"遮挡"）
- 实现 `CopyFrame` 的 **`layout=1`（窗口尺寸）+ BGRA8/RGBA16F**
- 宿主截图菜单切到它 ⇒ **立刻消除"被遮挡抓错"与"HDR 抓不到"**
- 验收：HDR 素材截图不失败；遮挡场景内容正确

### P2（真正的"原始画面"）
- 加 **`layout=0`（源分辨率）** ⇒ 截图尺寸 = 源尺寸
- 验收：源 1280×720 ⇒ 输出 1280×720

### P3（HDR 色彩正确）
- `format=1`（RGBA16F 线性）⇒ 由宿主决定：
  - 写 16-bit PNG（保留 HDR），或
  - 先做 SDR 映射再写 8-bit PNG
- 验收：HDR 截图像素值可解释，不再是 DWM 映射后的 8-bit

### P4（与旋转一致）
- 复用 `DrawCachedVideo` 即自动带上旋转；但**"原始画面"的尺寸也要按旋转交换宽高**
- 验收：EXIF=6 图片截"原始画面"应为竖图

## 5. 顺带发现的既有风险（仍未修）

| 风险 | 位置 | 说明 |
|---|---|---|
| 尺寸守卫过紧 | `播放器会话.vb` `CULng(宽)*高 > 16777216` | ≈4096²；**8K 素材会被拒**（本机有 8K 样本） |
| 保存路径不可控 | `生成截图路径()` 用 `Environment.CurrentDirectory` | 从快捷方式启动时可能是 `System32` ⇒ 保存失败或写到意外位置 |
| 无失败回落 | 屏幕抓取失败直接抛给用户 | 没有降级路径 |

**P1 顺带修掉"保存路径"**（改用媒体所在目录或用户图片目录）成本很低、收益明确。

## 6. 验收判据（可直接自动化）

| # | 判据 | 方法 |
|---|---|---|
| V1 | 源 1280×720 ⇒ 截图 **1280×720** | 探针对比 `width/height` |
| V2 | HDR 素材截图**不失败** | `format=1` 跑通，`result=0` |
| V3 | **窗口被完全遮挡**时内容仍正确 | 置顶窗口覆盖后截图并与未遮挡逐像素比对 |
| V4 | **窗口最小化**时仍可截图 | 最小化后调用 |
| V5 | 旋转 90° 素材方向与画面一致 | 配合 `docs/35` 用例 |
| V6 | 8K 素材不被尺寸守卫误拒 | 用 `testmedia` 8K 样本 |
| V7 | 截图**不改变**当前播放状态/交换链 | 截图前后 `GetRenderTargetInfo` 一致 |

> ⚠ **V7 很重要**：`CopySdrFrame` 现在会**在真实后缓冲上重绘**（`DrawCachedVideo(target)` 直接画进 back buffer），
> 截图会**污染正在显示的帧**。新方案渲染到**离屏纹理**，天然避免这一点——这也是新方案优于"直接接 `CopySdrFrame`"的原因之一。
