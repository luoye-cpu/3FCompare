## 1. ★ seek：两个叠加的缺陷

### 1.1 缺陷一：seek 被完全忽略

`DoSeek` 只 flush `audioDecoder_`，但 **IAMF 根本不用它** —— libiamf 通过自己的文件句柄读原始 OBU 流。
⇒ 音频位置完全不动，继续从原处播放。
`RestartFile` 早已实现，**却没有任何调用点**。

### 1.2 缺陷二：仅调用 RestartFile 会让音频**静音**

修复 ① 后看似正常，但**测出来的数字全是 seek 自己写进去的**（`position100ns`、`audioPosition100ns`
都由 seek 赋值），所以测不出差别 —— 与未修复版本 A/B **输出完全相同**，这才暴露了问题。

真正的证据来自**插桩解码器交付批次的 PTS**：

```
修复前:  frames=16  firstPts=0.000s    seekTarget=180.000s
```

libiamf 无随机访问，重启后**从字节 0 重放并从 0 编号**。
而 `QueueAudioFrame` 会丢弃 `位置 < seekTarget100ns_` 的音频（这个过滤本身是正确的）
⇒ 未锚定的 0.000s 全部早于 180s 目标 ⇒ **每一帧都被丢弃，音轨静音**。

**修复**：`RestartFileAt` 记录"重放流的 0 对应文件的哪个位置"，
`nextPosition100ns_` 从该基准开始：

```
修复后:  frames=16  firstPts=180.000s  seekTarget=180.000s
```

### 1.3 验证

在 4分59秒 / 328 MB 素材上测三个位置：

| seek 目标 | 实际位置 | seek 后产出 | 判定 |
|---|---|---|---|
| 60 s | 60.00 s | 16 帧 | PASS |
| 180 s | 180.00 s | 16 帧 | PASS |
| 240 s | 240.00 s | 16 帧 | PASS |

## 2. 长时间稳定性（#3）

328 MB / 4分59秒素材，seek 到 250 秒后连续播放：

```
内存采样: 72, 72, 72, ... MB（恒定）
seek 后位置: 250.00 秒
续播产出: 16 帧
```

⇒ **无泄漏、无累积**。增量式读取（按块读原始 OBU）设计正确 —— 328 MB 文件不会整体载入。

## 3. 与视频轨共存（#5）：**该场景目前不存在**

`TryOpenIamfAudioDecoder` 的启用条件：

```cpp
if (!IsIamfFormat(format_)) return false;   // iformat->name 含 "iamf"
```

⇒ 要求容器**本身就是 raw IAMF 解复用器**，而不是"含有 IAMF 音轨的容器"。

**实测**：用 ffmpeg 把 IAMF 与视频合入 MKV：

```
Stream #0:1: Audio: pcm_s24le, 48000 Hz, stereo
```

⇒ **ffmpeg 的 mkv muxer 不支持 IAMF 直通**，直接转成了 stereo PCM。
MP4 侧的 IAMF 支持只存在于**纯音频**（`p_A.mp4` 无视频轨）。

**结论**：当前不存在"IAMF + 视频"的容器形态，因此
**没有可测场景，也没有需要修复的缺陷**。若将来出现（如 MP4 支持 IAMF 音轨 + 视频），
需要重新评估：`PumpIamfAudio` 由 `PumpPlayback` 驱动，与视频共用同一 worker，
时钟与队列机制已经就位，预期可直接工作。

## 5. 本轮发现但**未修复**的问题

### 5.1 `bufferedAudio100ns` 对 IAMF 报出荒谬数值

| 素材 | 内容时长 | 报告缓冲 |
|---|---|---|
| live_7_1_4.iamf | 1.02 s | **365 s** |
| p_A.iamf | 299 s | **46747 s** |

比值（358 与 156）**不成比例** ⇒ 不像"内容时长 × 常量"。
更像该字段**累计**而非反映当前队列。

**重要**：这**早于**本轮改动（未 seek 时同样异常），**不是** seek 修复引入的。
需要在音频渲染器的缓冲统计里单独排查。

### 5.2 容器声明序 vs 解码器输出序（易错点，已写进代码注释）

`ffprobe` 报告 IAMF layer 为：

```
FL+FR+SL+SR+BL+BR+TFL+TFR+TBL+TBR+FC+LFE
```

这**不是**解码器吐出的顺序。若照它推导，会得出一个远比实际更大的置换。
判据是 `-s9 SOURCE`（解码器输出），即 3FP 真正收到的顺序：

```
[0,1,2,3,6,7,4,5,8,9,10,11]   # 仅 4/5 与 6/7 对调
```

且 FFmpeg 自己把该文件解成 **stereo**，说明其元数据不能作为解码序的依据。
