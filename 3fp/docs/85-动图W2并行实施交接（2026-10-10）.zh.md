## 1. 现场快照

### 1.1 代码改动（A5 机制一句话）

`PlayerSession` 的队列深度上限（原 `VideoFrameQueueLimit(queue)`，128MB 预算 ÷ 单帧字节）改为
扣除**解码器自身在飞行帧数** `pipelineFrames` 后再算：

- 新私有成员 `VideoQueuePipelineReservation()`：仅当 `animatedImage_` 且
  `videoDecoder_->active_thread_type & FF_THREAD_FRAME` 时返回
  `max(0, videoDecoder_->thread_count)`，否则 0。**用 `active_thread_type` 判"真的在跑帧线程"，
  不用 open 时写入的 `thread_type`（那只是请求）**；PNG 是否真跑 frame threads 由实测裁决，不凭记忆。
- 新私有成员 `VideoQueueLimit()`：包装上述两步，并在动图路径打一行一次性 stderr
  `[queue] animated bytesPerFrame=%llu pipeline=%lld limit=%lld`（值变化才打）。
- 两个消费点 `VideoQueueSaturated()`（cpp 原 :753）与 `PumpVideoPresentation()`（原 :3448）改调
  `VideoQueueLimit()`。**视频路径行为不变**（保留值 0 ⇒ 预算不减）。
- 单 DLL A/B 门：`FFF_ANIM_QUEUE_RESERVE=0` 还原旧记账，免重建。

## 3. 下一步：A/B 批次（未跑，接手即跑）

串行、交错跑 4 用例 × 2 臂，臂 A=不动环境变量（记账生效），臂 B=`FFF_ANIM_QUEUE_RESERVE=0`（旧记账）：

```
# 每行先 set/清 FFF_ANIM_QUEUE_RESERVE，再跑两个探针，落盘到 3fp/build/anim-perf/lane-a5/
#   loop_stutter_probe <媒体> --loops N ...   （接缝/丢帧/帧序/meanGap）
#   anim_cost_audit    <媒体> ...             （CPU ms/s、私有 WS、直方图）
# 用例：anim_640_apng.png / anim_1080p_apng.png / anim_4k_apng.png / anim_6k_apng.png
# 顺序 A4K,B4K,A640,B640,A1080,B1080,A6K,B6K 再反序一轮（A/B/A/B，防漂移）
```

判据（W1 时已定，不新造）：

1. **生效判据**：日志里出现 `[queue] animated bytesPerFrame=… pipeline=N limit=M`，且
   探针的 queued 峰值 ≤ `limit-1`、不再触发 queue-overshoot 警告行；`pipeline=N` 就是本机实测的
   活跃帧线程数（PNG 若判 0 ⇒ 整条 A5 对动图是 no-op，如实记，下一步转查真实内存大头）。
2. **收益判据**：4K 私有 WS 显著下降（目标 ≤350MB，原实测 ~670MB）；
   640/1080p 不应变化（预算本来就够）。
3. **代价判据**：接缝、丢帧、帧序完整性、meanGap 四项与臂 B 比**不劣化**
   （落在探针的 ±2×轮询量化带内算不变）。若 depth=2（4K）导致节奏变差 ⇒ 结论写
   **"128MB 预算对 4K 动图不足"**，不是"公式错"；处置转 A6/预算上调提案，不许放宽判据换绿。
4. 每行读数必须指到落盘日志文件名；跑不了的项记"未判"，不许记绿。
