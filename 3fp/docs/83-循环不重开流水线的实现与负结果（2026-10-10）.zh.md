# 83 · 循环不重开流水线：一次实现与一次负结果（2026-10-10）

> 用户指令：「重新调整 CPU 流水线等，调整后视频/动图在反复循环的情况下应该**不完全重开**流水线实现，其他优化根据真实测试结果进行。」
> 做了：内核里实现"回绕预灌缓存"（loop-priming cache），实测**方向对、实现不安全**，已完整撤销并验证撤销。
> 结论一句话：**接缝确实来自解码器流水线重灌（去掉它，4K 接缝 +81.7ms → +31.0ms），但"前缀重放"这个做法会在高分辨率造成丢帧与帧序重复（净增丢帧 19、fIdx 2 连续两次）⇒ 不能要。真正安全的形态是"整轮不再解码"（whole-loop cache），不是"先放几帧顶住"。**

---

## 1. 实现的形态（已撤销，留作下一次的地基）

```
第一遍正常解码 → QueueVideoFrame 里把一轮开头 K 帧 av_frame_ref 进 animPrimeCache_
                （K 由 DecodedVideoQueueBudgetBytes=128MB 与 MaxQueuedVideoFrames=8 共同夹住）
EOF/FlushAtEnd → DoSeek(0) 之后，先把缓存的 K 帧压回 videoFrameQueue_（预灌）
              → 置 animPrimeDiscarding_：解码器重灌期间重新吐出的同一批前缀**不入队列**
              → 清空缓存、重新武装，采集**这一轮**的头几帧给下一轮用
非回绕的 DoSeek（拖动、切流、阶梯换解码器）→ 缓存作废并解除武装
DoClose → 释放缓存
```
谓词：`animatedImage_ && sessionWrapLoop_ && !disc_ && 解码器是 intra-only`；闸：`FFF_ANIM_PRIME_DISABLE`（同枚 DLL 上做 A/B，先例是 `docs/14` §4 的 `FFF_ANIM_NOSEEK` 与本文件的 `FFF_DISC_TRACE`）。

**为什么加环境变量而不是"改了直接比两轮"**：这台机器跨会话的绝对值会漂（同一份 4K 素材每秒 CPU 从 86–92% 漂到 140%，`v5_4k_15s.txt`），只有同一次运行内的 A/B/A/B 才把"开关的效应"和"时间的漂移"分开。

## 2. 被实测打回来的两处（都不是"想法"问题，是实现前的必修课）

**① 白名单里的 codec id 猜错了 —— 而且是权威源级别的错**
第一版放行 `{AV_CODEC_ID_GIF, AV_CODEC_ID_PNG}`，跑起来毫无效果：`[animprime] 未生效：缓存 0 帧 / animated=1 wrap=1 **解码器=207**`。
按 `3fp/kernel/third_party/ffmpeg/include/libavcodec/codec_id.h` 逐个枚举算出来（`AV_CODEC_ID_PNG` 在头里是**隐式序号**，不能靠记忆取值）：

| 名字 | 本构建的值 |
|---|---|
| `AV_CODEC_ID_PNG` | 61 |
| `AV_CODEC_ID_GIF` | 97 |
| `AV_CODEC_ID_WEBP` | 170 |
| **`AV_CODEC_ID_APNG`** | **207** |

⇒ **这个 FFmpeg 分支自带原生 APNG 解码器，APNG 是独立 codec id**（上游是 `PNG` + apng demuxer）。只列 PNG/GIF 会让整条路径静默失效——没有报错、没有崩溃，只是"缓存 0 帧"。加 `AV_CODEC_ID_APNG` 后预灌立刻生效（`回绕预灌 4 帧（缓存 132710400 B）`）。

**② 第一遍的"头几帧"根本不经过 `QueueVideoFrame`**
`DecodePacket` 的 `handleFrame` 有个分叉（`PlayerSession.cpp:3345-3347`）：`state==Playing && !seeking` 才走 `QueueVideoFrame`，否则**直接** `PresentVideoFrame`。探针/宿主打开后是 `Seek(0)+Play`，首帧正落在 seeking 窗口里 ⇒ 若在回绕之前采集，缓存存的是**一轮中段**的帧，回绕时把它们当头部放出去＝画面乱序 + 时间戳错位。
修法：只在**回绕之后**武装采集（第二轮提供头部，第三轮起才享受预灌）。

## 3. 负结果（为什么这个形态不能要）

4K APNG，`ab_new/`（同一枚 DLL，只差 `FFF_ANIM_PRIME_DISABLE`），1ms…实际 20ms 轮询，8–12s：

| 臂 | 接缝超额 | 长停 | 解码侧丢帧 | 帧序完整性 |
|---|---|---|---|---|
| 关（旧路径） | **+81.70ms**（`fix`/`arm` 前）；+82.61（撤销后复核） | 8/8 | **0** | 完整 |
| 开（前缀预灌） | **+31.02ms** | 8/8 | **净增 19** | ⚠ `fIdx 2` 连现两次 |

机制解释（为什么"顶几帧"不够）：呈现端被 `Present(1,0)` 锁在 vsync 上（`VideoRenderer.cpp:6181`），每帧最快 100ms 消费一次。4K 解码器重灌 `thread_count` 帧的墙钟 ≈ 一整帧总解码量（≈136ms），比缓存能顶住的 K=3~4 帧（300–400ms）……实测却仍长停 8 次并丢 19 帧 ⇒ 说明**丢弃窗与真实重灌不同步**：被丢弃的前缀帧数（按 PTS ≤ cacheLastPts 判）与实际重灌出来的帧数不匹配时，队列会在缓存耗尽、解码器仍未吐帧的间隙**空一次**，随后按 `lateTolerance = max(2×duration, 50ms)`（`:3629`）把赶不上的帧判成丢帧。也就是说：**要安全，必须"整轮都不重新解码"，不能"先放几帧再指望时序刚好对齐"。**

## 4. 由此改掉的三条判断（写进 docs/81/82 的对应位置）

1. **docs/82 §3 的假设被部分证实**：去掉重灌确实把接缝从 81.7 压到 31.0 ⇒ "接缝主要来自流水线重灌"成立；但**幅度不到 100%** 且伴随丢帧 ⇒ 不能作为实现收口。
2. **O7（在排空循环里逐帧判队列饱和）现在判定为不成立**：帧已经从 `avcodec_receive_frame` 取出，拒绝入队＝**丢帧**，不是"少灌一帧"。压深度的合法手段只剩两条：动图降低解码线程数（但今天实测：负载机上 1 线程会在 4K 崩到 3.74fps），或把 `MaxQueuedVideoFrames`/预算按 `bytesPerFrame` 与 `thread_count` 一起算（**声明的 128MB 从没把解码器内部的流水线帧算进账**，这才是 670MB 的成分）。
3. **下一条可实现的形态**：`whole-loop cache` —— 一轮总字节 ≤ 预算时整轮缓存，回绕**完全不碰解码器**（不 seek、不 flush、不重灌），预期接缝 → 固定开销 ≈ 0.4ms（640 实测值）；超预算就退回今天的路径。按 10 帧算：640→13MB ✅、1080p→83MB ✅、4K→332MB ❌、6K/8K ❌ ⇒ 覆盖面恰好是"动图最常见的尺寸"，4K 以上交给降采样/门槛那条路（docs/79 轨道 D）。
