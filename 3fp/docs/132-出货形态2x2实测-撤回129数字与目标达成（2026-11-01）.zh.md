# 132-出货形态 2×2 实测：撤回 129/130 的数字，目标已达成（2026-11-01）

> 本文**撤回** 129/130 里"两项优化 −174.6 ms"与"R2R 组合失败 +23.9 ms"两个数字。
> 两者都是实验缺陷造成的，本轮用出货同形的四臂 2×2 重做，给出可信结论。

## 0. 判词

1. **目标达成**：出货形态（散装 + R2R A2）+ 两项宿主优化 ⇒ **T2 = 858.7 ms**，低于 1000。
   对照 PR #48 同形态 1016.4 ms、PR #48 的 JIT 形态 1239.2 ms。
2. **两项优化的真实效应是 −86…−89 ms，不是我上轮报的 −174.6 ms。**
   上轮跨了内核血统（`arm_pr` 干净 5622784 B vs `arm_final` 带 `[KT]` 插桩 5624320 B），
   把插桩开销记进了收益。
3. **R2R 没有"组合失败"。** 上轮那个 "+23.9 ms (p=0.713)" 是**同一份二进制自己跟自己比**：
   publish 因反引号转义失败，`arm_final_r2r` 的 exe 与 `arm_final` 字节数完全相同
   （33,439,093 B 单文件）。该结论作废。

## 2. 两个实验缺陷是怎么造成的（方法教训）

### 缺陷 A：跨内核血统比较

`arm_pr48_lm`（插桩臂）建好后，源树 `FFF.Native.dll` 停在带 `[KT]` 的那份（10/31 20:06，
5624320 B）。后续 `dotnet publish` 建的臂默认侧载它，而对照组 `arm_pr` 是 10/30 的干净件
（5622784 B）。**两臂差的不仅是宿主改动，还差一份插桩内核** ⇒ 收益被高估约一倍。

**判据补一条**：每次建对照臂，必须打印**两臂 `FFF.Native.dll` 的字节数与 SHA**，
不一致就直接中止。本轮四臂校验全部一致（5623296 B / `[KT]=False`）。

### 缺陷 B：构建静默失败后拿旧产物继续测

上轮我用 `& dotnet publish ... `-p:PublishReadyToRun=true`` 这种反引号续行写法，
参数被吞、publish 实际没跑，而 `arm_final_r2r` 目录里还留着先前 `Copy-Item` 复制进去的
单文件 exe ⇒ 脚本"成功"结束，我拿同一份二进制跟自己比，读出 +23.9 ms 并据此推断"互斥"。

**判据补一条**：臂构建后必须验**产物指纹随开关变化**（R2R 判据 = 托管 DLL 尺寸，
本轮 2,355,200 vs 1,089,536；散装判据 = apphost 299,520 B）。
`arm_build.ps1` 里本来就有 apphost 尺寸闸（`-Loose` 而 exe>5MB ⇒ throw），
**该脚本可用，不该手写 publish 命令行绕过它**。
