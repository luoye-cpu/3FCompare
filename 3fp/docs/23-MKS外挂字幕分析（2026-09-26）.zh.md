## 2. 内核现状：早就按「容器 + 流索引」实现的

`FFF.Native/3FP/Subtitle/AssSubtitleRenderer.cpp:258` 起的 `Open()` 就是分水岭：

```cpp
if (requestedStream >= 0) {
    track_ = ReadContainerTrack(path, requestedStream);   // ← 容器路径：任意格式
} else {
    auto script = NormalizeAssScriptEncoding(ReadFile(widePath));  // ← 纯文本直读
    track_ = ass_read_memory(library_, script.data(), script.size(), nullptr);
}
```

`ReadContainerTrack()`（同文件 :360）做的事：
`avformat_open_input`（**不看扩展名**）→ `find_stream_info` → 校验
`streams[requestedStream]->codecpar->codec_type == AVMEDIA_TYPE_SUBTITLE` → `avcodec` 解码 →
ASS/SSA 取 `extradata`（Matroska 里就是 `[Script Info]`+`Styles`）喂 `ass_process_codec_private`，
**其它编码（subrip/mov_text/…）走内置 `DefaultHeader` 兜底** → `ass_process_data`。

位图路径 `BitmapSubtitleDecoder.cpp:32-67` 同理：要求**显式流索引**，只接受
`HDMV_PGS_SUBTITLE / DVB_SUBTITLE / XSUB`。

⇒ **MKS 只是 Matroska 容器**，对这两条实现来说和「MKV 里的内嵌字幕流」没有区别。
内核侧唯一的前提是：**必须传流索引，且必须 ≥ 0**。

## 3. 宿主现状：永远传 -1，所以 MKS 必失败

`FFF.Player/Core/外部字幕自动加载器.vb`：

- 白名单 `候选项` = **`.srt / .ass / .ssa / .sup`**（:95），`加载字幕` 里不匹配就抛
  `「仅支持 SRT、ASS、SSA 和 SUP 外部字幕。」`
- 加载是**按扩展名直读文本**：SRT→自研解析器、ASS/SSA→`ASS特效字幕帧生成器(路径, 媒体路径)`、
  SUP→`SUP字幕帧生成器(路径)`，**流索引参数全程保持默认 -1**
- 容器语义只在 `加载内嵌字幕(媒体路径, 流)`（:187）里用——按 `流.编码` 分派：
  位图编码 → `SUP字幕帧生成器(路径, 流.索引)`，其余 → `ASS特效字幕帧生成器(路径, 路径, 流.索引)`

⇒ **改造的正确姿势是把 .mks 走「内嵌字幕」那条路**（容器 + 流索引），
而不是走「外部字幕」那条路（纯文本 -1）。

## 4. 实测：内核零改动即可吃 MKS

探针：`3fp/tools/mks_subtitle_probe.cpp` → `3fp/build/mks_subtitle_probe.exe`
（对每个文件遍历流索引 -1..2；渲染画布 640x360，采样 1s/4s/7s/11s；
判据不是「返回 Success」，而是**位图里真的有非透明像素** `opaque>0`）

| 样本 | 流索引 | 结果 |
|---|---|---|
| `sample_ass.mks`（ass） | **-1** | ❌ `NativeFailure(-4)` "Could not parse the ASS subtitle." ← **反向对照，宿主今天的用法必失败** |
| `sample_ass.mks` | **0** | ✅ Success，opaque = 7605 / 4662 / 6178（1/4/7s），11s `flags=0x1`(Clear) |
| `sample_srt.mks`（subrip） | **0** | ✅ Success，opaque = 4774 / 2782 / 2201 ← DefaultHeader 兜底生效 |
| `sample_multi.mks` 双轨 | **0**（ass） | ✅ opaque 7605…（与单轨一致） |
| `sample_multi.mks` 双轨 | **1**（subrip） | ✅ opaque 4774… ⇒ **两条轨内容不同，多语言可选** |
| 任意文本轨 + `OpenBitmapSubtitle` | 0 | `NotSupported(-7)` ⇒ **可用来区分「这条轨是位图还是文本」** |
| 越界流索引 1/2（单轨文件） | — | "The requested embedded subtitle stream does not exist."（报错正确） |
| 纯 `.srt` 文件 | -1 | ❌ "Could not parse"（宿主对 .srt 走自研解析器，不走 libass，不影响现状） |

**结论**：解码、渲染、时间轴、结束语义、多轨——内核全部现成。

## 5. 唯一硬缺口：宿主无从知道 .mks 里有哪几条流

宿主枚举字幕流靠已打开媒体的 `FFF3FP_GetMediaInfo`。那就试试让播放器直接打开 .mks：

探针 `3fp/tools/mks_open_probe.cpp`，实测输出：

```
=== sample_multi.mks ===
  Open -> 0
    event=Error {"result":-7,"message":"The file contains no playable video or audio stream.","operation":"open"}
  OpenCompleted=no Error=yes
  GetMediaInfo -> 0 (required=1)      ← 空

=== sample_video.mkv ===              ← 对照组，证明探针本身可用
  Open -> 0
    event=OpenCompleted {"success":true}
  GetMediaInfo -> 0 (required=2417)   ← 正常返回流信息
```

⇒ **播放器不接受纯字幕容器**（这是合理的：它没有可呈现的视频/音频）。
⇒ 宿主**没有任何现成途径**拿到 `.mks` 的「流索引 + 编码名 + 语言标签」。

**因此内核必须加的只有一处**：一个按路径探测字幕流的 API。建议形状：

```cpp
// 返回 JSON：[{index, codecName, language, title, forced, default}]
FFF3FP_API FFFResult FFF3FP_ProbeSubtitleStreams(const char* localPathUtf8,
    char* outputUtf8, std::uint32_t outputSize, std::uint32_t* requiredSize) noexcept;
```

⚠ 别用「依次试流索引 0..N 直到成功」来省这个 API：那样拿不到**语言/标题标签**，
多语言 MKS（MKS 的典型用途就是多语言）在选择 UI 上会退化成「轨 0/轨 1」。

## 4b. 官方样本实测（samples.ffmpeg.org）

**先说一个事实：网上没有现成的官方 `.mks`。** 已核实两处最权威的来源都没有：

- **Matroska 官方 test suite**（matroska.org/downloads/test_suite.html，SourceForge）：8 个文件 `test1..test8.mkv`，**全是 .mkv**，含多字幕的 `test5.mkv`
- **FFmpeg `samples.ffmpeg.org`**：`Matroska/`（25 个文件，只有 .mkv/.mka）与 `Matroska/subtitles/`（只有 .mkv/.ass/.txt）**均无 .mks**

⇒ 改用**官方素材重封装**（`ffmpeg -map 0:s -c copy -f matroska`，轨道零转码），得到合法且内容真实的 .mks。
素材与生成命令见 `3fp/samples/media/mks/official/README.md`。

| 官方素材 | 生成的 MKS | 实测结果 |
|---|---|---|
| `sub/PGS/supsample.mkv`（h264 + **hdmv_pgs_subtitle**） | `pgs_official.mks` 单轨 PGS | ✅ **`OpenBitmapSubtitle` 成功**，渲染出 **689×56 位图、`opaque=22291`**；`start=1.001s` 与源视频包时间**逐位一致**（1.001000 / 9.009000）⇒ 重封装零漂移 |
| `Matroska/subtitles/multiple_sub_sample.mkv`（**7 条 subrip**：chi/eng/fre/ger/ita/jpn/spa） | `multi_sub_official.mks` 7 轨 | ✅ **流 0..6 全部 Success**，且内容各不相同（box 宽 174/169/161/173/156/191/175，`opaque` 各异）；流 7+ 正确报错 |

🔴 **实测撞出一个不对称（实现时必须注意）**：

```cpp
// BitmapSubtitleDecoder.cpp:45-47 —— 位图路径：-1 = 自动选最佳字幕流
streamIndex_ = requestedStream;
if (streamIndex_ < 0) streamIndex_ = av_find_best_stream(format_, AVMEDIA_TYPE_SUBTITLE, -1, -1, nullptr, 0);

// AssSubtitleRenderer.cpp:276-282 —— ASS 路径：-1 = 纯文本直读（对容器必失败）
if (requestedStream >= 0) track_ = ReadContainerTrack(path, requestedStream);
else { ... ass_read_memory(...); }
```

⇒ 同一个 `-1`，位图路径**碰巧能用**（只拿第一条，无法选轨），ASS/文本路径**必失败**。
**宿主实现 MKS 时必须显式传流索引**，否则会出现「PGS 的 mks 能用、ASS 的 mks 用不了」的怪现象。
（另：越界索引两路径报错也不一致——位图 `InvalidArgument(-1)`，ASS `NativeFailure(-4)`。）

★ **语言标签是硬需求**：官方样本 7 条轨带真实 `chi/eng/fre/ger/ita/jpn/spa`。
这正是 §5 那个探测 API 必须返回 `language` 的原因——否则选择 UI 只能显示「轨 0/轨 1」。

## 8. 附带发现：libass 依赖链在开发运行时是断的（既有问题，非本次引入）

跑探针时踩到 `EXIT=127`，异常码 **`0xC06D007E`(STATUS_MODULE_NOT_FOUND)**，逐个 `LoadLibrary` 定位到：

```
FFF.Native.dll → ass-9.dll → freetype.dll → z.dll   ← 这一层缺
                           → harfbuzz.dll / fribidi-0.dll
```

- `3fp/build/` 与 `3fp/kernel/runtime/` 都**只有 av* / sw* / lib*，**没有 ass-9.dll 及其依赖**
- 完整的一套在宿主运行目录 `FFF.Player/bin/Release/net10.0-windows10.0.26100.0/`（含 `ass-9.dll freetype.dll fribidi-0.dll harfbuzz.dll z.dll`）
- 发布包副本 `publish/PLAN/ffmpeg-full/` 里**有 `ass-9.dll` 但没有 freetype/fribidi/harfbuzz/z.dll ⇒ 那份 libass 是残的**

⇒ 任何**不含完整 libass 链**的运行形态，ASS 字幕（外挂与内嵌都是）会以「模块未找到」形式失败，
而不是优雅报错。与 `docs/19` 记录的单文件裁剪问题同族，但更精确：**不是缺 libass，是缺 libass 的依赖**。

（本次为跑探针，已把缺失的 13 个 DLL 补进 `3fp/build/`，属**新增**、未覆盖任何既有文件。）

## 9. 给 issue 的回复草稿

> 样本来了（zip 159 KB，含生成命令）：一个 10s 视频 + 单轨 ass / 单轨 srt / 双轨 ass+srt 三个 .mks，
> 另外两个是**用 FFmpeg 官方素材重封装**的（轨道零转码）：一个**真实 PGS 位图轨** .mks，
> 一个**7 语言轨**（chi/eng/fre/ger/ita/jpn/spa）.mks。
> 顺带一提：Matroska 官方 test suite 和 FFmpeg samples 库里都**没有现成的 .mks**，所以只能重封装。
>
> 顺手先替你验证了一件事：**内核不用改就能解 .mks**——
> `FFF3FP_OpenAssSubtitle` 传显式流索引（≥0）时，ass 轨和 subrip 轨都能解能画，
> 双轨的两条轨可以分别打开（流 0 = ass、流 1 = subrip）。
> 前提是**不能传 -1**：-1 走的是"纯文本直读"分支，对 .mks 必然失败。
>
> 真正缺的是**探测**：播放器打开 .mks 会返回 `-7 NotSupported`
> （"The file contains no playable video or audio stream."），`GetMediaInfo` 是空的，
> 所以宿主没办法知道一个 .mks 里有几条字幕流、各是什么编码/语言。
> ⇒ 建议加一个 `FFF3FP_ProbeSubtitleStreams(path)` 之类按路径返回字幕流列表（含 language/title）的 API，
> 宿主侧再把 .mks 加进白名单并按流索引加载（走内嵌字幕那条分派），多轨选择 UI 才能有语言标签。
>
> 位图轨也测了：用 FFmpeg 官方 PGS 素材重封装出的 .mks，`OpenBitmapSubtitle` 能渲染出 689×56 的图形，
> 时间戳和源视频逐位一致。
>
> ⚠ 一个坑提醒你：同一个流索引 **-1，两条路径语义不一样**——
> 位图路径是"自动选最佳字幕流"（`BitmapSubtitleDecoder.cpp:45`），ASS/文本路径是"纯文本直读"（必失败）。
> 所以加载 .mks **必须显式传流索引**，不然会出现"PGS 的能用、ASS 的用不了"。
> 另外外挂音轨 mka 那边传 -1 是合法的，别把那个习惯带过来。
