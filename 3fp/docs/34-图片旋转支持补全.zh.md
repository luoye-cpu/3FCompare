# 34 · 图片旋转支持补全（2026-10-05）

> 需求：「3FP 缺少图片旋转信息支持，补全一下」
> **结论：已补全并实机验证。** 检测（已有）→ 渲染（新增）→ API（新增）→ 宿主自动转正（新增）四级打通。

---

## 1. 补全前的缺口（逐级核实）

| 级 | 能力 | 补全前 |
|---|---|---|
| 1 | **检测** EXIF 方向 → `GetImageInfo.rotationQuarterTurns` | ✅ **已有**（K5，`PlayerSession.cpp:3225`） |
| 2 | **渲染** 旋转（着色器/几何） | ❌ **完全没有** |
| 3 | **API** `SetViewRotation`（K6） | ❌ **未实现**（`docs/02` 规划过，从未落地） |
| 4 | **宿主** 应用旋转 / 自动转正 | ❌ **完全没有**（`GetImageInfo` 被调用但旋转字段无人使用） |

⇒ 也就是说：**内核能"报告"照片需要转正，但没有任何东西会去转它**。这就是"缺少旋转支持"的实际形态。

---

## 2. 实现（四层）

### 2.1 渲染层：旋转采样坐标（核心决策）

**做法**：在像素着色器里旋转 **UV**，而不是旋转几何。

```hlsl
float2 sampleUv=uv;
if(ViewRotation>0.5){
    if(ViewRotation<1.5)      sampleUv=float2(1.0-uv.y,uv.x);      // 90 cw
    else if(ViewRotation<2.5) sampleUv=float2(1.0-uv.x,1.0-uv.y);  // 180
    else                      sampleUv=float2(uv.y,1.0-uv.x);      // 270 cw
}
```

**为什么选这个方案**（而不是旋转四边形）：
- 下游所有阶段（色度偏移、360 投影、色调映射、scRGB）**仍然只看到正常的 0..1 UV**，无需各自适配；
- 目标矩形与色度布局**不动**，改动面最小。

> **⚠️ 一个 HLSL 陷阱（实测踩到）**：像素着色器的输入参数**不可写**。
> 最初写 `inout float2 uv:TEXCOORD0` 会被 fxc 拒绝：
> `error X4502: invalid ps_5_0 output semantic 'TEXCOORD0'`——
> `inout` 让它变成输出语义，而像素着色器不允许。必须用**局部变量**。

### 2.2 几何层：适配盒按旋转后的宽高比

只转 UV 不换盒子，竖图会被塞进横盒子 → 压成细条。所以 `DrawCachedVideo` 里：

```cpp
const auto rotation = viewRotation_.load(std::memory_order_acquire);
const auto swapAxes = (rotation & 1u) != 0;      // 90/270 交换宽高
const auto layoutWidth  = swapAxes ? sourceHeight_ : sourceWidth_;
const auto layoutHeight = swapAxes ? sourceWidth_  : sourceHeight_;
```

### 2.3 常量缓冲：复用 padding，布局不变

`ShaderSettings` 原本有 `padding3`，直接**改名为 `viewRotation`**：

```cpp
float viewAspect, viewRotation, padding4, padding5;
```

⇒ 结构体**大小不变**，HLSL cbuffer 布局不变 ⇒ **不会因常量缓冲错位而静默改变画面**。

### 2.4 API 层：不改 `PlayerApiVersion`

```cpp
FFF3FP_SetViewRotation(player, quarterTurns)   // 0..3，越界 InvalidArgument
FFF3FP_GetViewRotation(player, &quarterTurns)
```

沿用 VSR 的同一原则：**`PlayerApiVersion` 保持 16**，只追加导出。
理由（`PlayerApi.cpp:12-14`）：`FFF3FP_Create` **硬拒版本号不符**，升版会让 3FC 立刻无法创建实例。

### 2.5 宿主层：动态解析 + EXIF 自动转正

`播放器原生接口.vb` 用既有的 `NativeLibrary.GetExport` 模式（与字幕流探测同款）**动态解析**：

> ⚠ **为什么不静态导入**：旋转是"**同版本号内的新增导出**"（版本仍是 16）。
> 若静态导入，一个"16 版但尚无旋转"的内核会在调用时抛
> `EntryPointNotFoundException`，把"旧内核无此能力"变成"**宿主崩溃**"。

`播放器会话.vb` 新增 `自动转正图片()`：读 `GetImageInfo`，仅对**静态图**施加。

## 3. ⚠️ 一个必须写清楚的语义陷阱（EXIF=6 → 内核报 3，不是 1）

实测：`03_exif_orientation6.jpg`（EXIF **Orientation=6**）→ `GetImageInfo.rotationQuarterTurns = **3**`。

**看起来矛盾，其实不是。** 原因：

| 环节 | 值 |
|---|---|
| EXIF Orientation 标签 | `6` = "需顺时针转 90° 才正" |
| ffmpeg 的 display matrix | `rotation = **-90°**`（`docs/04` §194 实测） |
| `av_display_rotation_get` | 返回 `-90` |
| 内核归一化到 `[0,360)` | `270°` ⇒ `270/90 = **3**` |

⇒ 内核报的是「**需要施加的顺时针四分一转数**」，而 EXIF 标签的方向定义相反。
两者关系：`内核值 = 4 - (EXIF 校正角)/90`。

**实践结论**：宿主**必须直接用内核的值**，不要按 EXIF 标签自行换算，否则会**转反 180°**。
这一条已写进 `播放器会话.vb` 的注释。

## 4. 实机验证（全部实测）

### 4.1 几何：适配盒正确交换宽高

| 旋转 | dest 矩形 | 宽高比 | 判定 |
|---|---|---|---|
| 0° | 1211×681 | **1.7783**（16:9） | ✅ 横 |
| 90° | 383×681 | **0.5624**（9:16） | ✅ **竖——轴已交换** |
| 180° | 1211×681 | 1.7783 | ✅ 同 0° |
| 270° | 383×681 | 0.5624 | ✅ 同 90° |
| 回到 0° | 1211×681 | 1.7783 | ✅ 复原 |
| 4（越界） | — | 被拒，读回仍 0 | ✅ `InvalidArgument` |

### 4.2 像素：**内容确实被旋转**（决定性证据）

在**同一个屏幕坐标** `(631,85)` 上采样，只改变旋转：

| 旋转 | RGB | 颜色 |
|---|---|---|
| 0° | `(0.498, 0.502, 0.498)` | 灰 |
| 90° | `(0.000, 1.000, 1.000)` | **青** |
| 180° | `(0.498, 0.502, 0.498)` | 灰（中心对称，合理） |
| 270° | `(0.996, 0.000, 0.000)` | **红** |

⇒ 同一像素随旋转**变色** ⇒ **UV 查找真的在旋转**，不是只有盒子在动。
（若只换了几何，重叠区域的像素应当完全不变。）

### 4.3 零回归

| 项 | 结果 |
|---|---|
| 未旋转的普通图 | `aspect=1.7783`、`1211×681`，**与改动前完全一致** |
| 无旋转信息的图 | `rotationQuarterTurns=0xFFFFFFFF`、`ROTATION=0` ⇒ 不动 |
| 视频路径 | `videoScalingMode=Shader`、无异常 |
| 内核编译 | ✅ EXIT=0，791552 B |
| 宿主编译 | ✅ **0 警告 0 错误** |

## 5. 宿主测试结果与归因（**如实记录**）

`run_host_tests.sh`：**通过 12 / 失败 11（共 23）**。
文档基线为 **12 通过 / 9 失败（共 21）**——**数目不同**，故逐条归因：

| 失败项 | 原因 | 是否与本次改动有关 |
|---|---|---|
| 8× `Access to the path ...Temp... is denied` | ⚠ 环境 | ❌ 无关 |
| 1× `Panel`→`ModernPanel` 类型错配 | 既有缺陷（`docs/08`/`docs/11` 已记录） | ❌ 无关 |
| 2× `A generic error occurred in GDI+`（`--360-projection-regression`、`--scaling-frequency-regression`） | ⚠ **同源环境**（见下） | ❌ 无关 |

**两条 GDI+ 失败的归因证据**：

```
引导：重定向设置文件失败，内存清除仍生效：
      Access to the path '...\Temp\FFF.Player.Tests.Settings.40380.json' is denied.
测试失败：A generic error occurred in GDI+.
```

⇒ 它们**同样先撞上 Temp 拒绝**（GDI+ 报错是其下游表现），与上面 8 条**同根**。

**根因定位**：本机运行 **360 安全卫士**（`360DesktopService64` / `360QuickPreview` / 多个 `360se`）。
其实时防护阻止**测试进程**写 `%TEMP%`，而 PowerShell（已受信任）写入正常——
这解释了"为什么 PowerShell 能建文件、测试进程却被拒"。

> ⚠ 因此这 11 项**不是**本次旋转改动引入的回归。
> 但也**不能**说"全绿"——它们是本机环境的**既有红**，且数目随安全软件行为漂移
> （这也是基线 9 项与本次 11 项差异的来源）。
> **要确认旋转无回归，请以 §4.3 的三条直接证据为准**（几何一致、像素探针、视频路径）。
