# 37 · 截图链路缺陷分析（2026-10-05）

> 需求：「分析一下 3FP 的截图相关实现有什么问题？疑似在很多播放情况下截图输出有问题」
> **结论：怀疑成立。** 截图走的是**屏幕抓取**（`Graphics.CopyFromScreen`），不是帧回读。
> 独立验证的 **5 类缺陷**，其中 2 类在实机上**已复现**（含 HDR 下彻底失败）。

---

## 0. 结论速览

| # | 缺陷 | 严重度 | 实测证据 |
|---|---|---|---|
| **1** | "原始画面"是**把屏幕抓图放大回去**，不是原始像素 | 🔴 高 | 源 1280×720 → 实际只能抓到 884×481 再拉伸 |
| **2** | **HDR 下内核唯一的 GPU 回读直接失败** | 🔴 高 | `CopySdrFrame` 返回 **-7 (NotSupported)** |
| **3** | 屏幕抓取**受遮挡/最小化/后台影响** | 🔴 高 | 架构性（见 §3） |
| **4** | 截图链路**完全不知道旋转** | 🟡 中 | 全文搜 `旋转` **0 命中** |
| **5** | 正确的回读函数**存在但零调用** | 🟡 中 | `读取SDR合成帧` 仅 1 处定义、**无调用者** |

## 1. 现状：截图到底怎么实现的

截图菜单（`播放器画面菜单控制器.vb`）提供三项：

| 菜单项 | 实现 |
|---|---|
| 剪贴板：原始画面 | `截取原始画面()` |
| 剪贴板：实际渲染 | `截取客户区(画面控件.ClientRectangle)` |
| 原始画面保存到当前目录 | `截取原始画面()` + `Save(Png)` |

**三者最终都落到同一个函数**：

```vb
Private Function 截取客户区(客户区范围 As Rectangle) As Bitmap
    Dim 屏幕原点 = 画面控件.PointToScreen(客户区范围.Location)
    Dim 图像 As New Bitmap(客户区范围.Width, 客户区范围.Height, ...)
    Using 图形 = Graphics.FromImage(图像)
        图形.CopyFromScreen(屏幕原点, Point.Empty, 客户区范围.Size, SourceCopy)   ' ← 屏幕抓取
    End Using
    Return 图像
End Function
```

而"原始画面"在此基础上**再多一步放大**：

```vb
Private Function 截取原始画面() As Bitmap
    Dim 原始尺寸 = 取得原始画面尺寸(快照)                 ' 快照里的源分辨率
    Using 当前画面 = 截取客户区(视频区域)                  ' ← 实际是屏幕抓的窗口大小图
        Dim 原始画面 As New Bitmap(原始尺寸.Width, 原始尺寸.Height, ...)
        图形.InterpolationMode = HighQualityBicubic
        图形.DrawImage(当前画面, New Rectangle(Point.Empty, 原始尺寸))   ' ← 拉回源分辨率
        Return 原始画面
    End Using
End Function
```

> **⇒ 所谓"原始画面"，实际是「屏幕像素 → 放大到源分辨率」。**
> 它既不是源像素，也不是无损的：窗口内每像素先被 DWM 缩放/合成一次，再被双三次插值一次。

## 2. 实测复现（`tools/shot_probe.cpp`）

新增探针 `shot_probe`，把主观感受变成读数。刻意把窗口设成 **900×520**，
与被测视频尺寸明显不同 —— 这样"回来的尺寸"能直接指认是谁。

### 2.1 SDR 视频（源 1280×720）

```
渲染目标: swap=884x481 client=884x481 dest=(14,0) 855x481 outBits=8
=== CopySdrFrame ===
  尺寸查询 result=-3  ->  884x481          ⚠ 期望 1280x720
  拷贝 result=0  中心像素 BGRA=(248,0,0,255) 左上=(0,0,0,255)
```

**缺陷 1 已复现**：源是 **1280×720**，回读只给 **884×481**（= 窗口/交换链尺寸）。
内核里**根本没有"取源分辨率帧"的接口**。

### 2.2 HDR 视频（源 1920×1080，MapToHdr）

```
渲染目标: swap=884x481 outBits=16 hdr=1
=== CopySdrFrame ===
  尺寸查询 result=-3  ->  884x481
  拷贝 result=-7   ⚠ 失败
```

**缺陷 2 已复现**：`CopySdrFrame` **在 HDR 下彻底失败**（`-7 = NotSupported`）。

源码原因（`VideoRenderer.cpp:5840`）：

```cpp
if (description.Format != DXGI_FORMAT_B8G8R8A8_UNORM) return FFFResult::NotSupported;
```

而 HDR 走 **16-bit scRGB（`R16G16B16A16_FLOAT`）** 交换链（`docs/13`/`docs/20` 既定契约）
⇒ **只要用户开了 HDR 或源是 HDR，这条路径必然失败**。
同一探针里 `ReadVideoPixelRegion` 在 HDR 下也返回 `-2`，**两条 GPU 回读路径在 HDR 下都不可用**。

## 3. 为什么"很多播放情况"下会出问题（架构性根因）

因为截图 = **屏幕抓取**，它天然依赖"窗口正在屏幕上、且没被挡住"：

| 播放情况 | 屏幕抓取的结果 |
|---|---|
| 窗口被其他窗口**部分遮挡** | ❌ **抓到遮挡物的像素** |
| 窗口**最小化** | ❌ 抓到桌面/黑块 |
| 被**全屏游戏/独占应用**覆盖 | ❌ 抓不到 |
| 在**另一个虚拟桌面** | ❌ 抓不到 |
| 窗口移出屏幕（负坐标） | ❌ 区域无效 |
| 双屏 DPI 不同 | ⚠ 可能取到错误缩放 |
| 开着 **HDR** | ❌ 抓到的 scRGB 合成结果，Save 成 PNG 后**颜色明显不对**（见 §4） |

而它**本可以**用 GPU 回读（内核已有该能力），完全不受上述影响。

> 这正是用户感知到的"很多播放情况下截图有问题"——不是偶发 bug，是**方法选错**。

## 4. 附带缺陷

### 4.1 HDR 截图颜色错误

即便屏幕抓取"成功"，HDR 窗口的呈现内容由 DWM 做 SDR 映射，
抓到的 BGRA 是**映射后**的结果；而"原始画面"又把它当 8-bit sRGB 拉回原尺寸。
⇒ HDR 素材截图**必然偏色**，且无处校正。

### 4.2 截图不知道旋转（缺陷 4）

全文搜索 `播放器画面菜单控制器.vb`：`旋转` / `Rotation` / `DestWidth` —— **0 命中**。

后果：接入旋转功能（`docs/35`）后：
- **"实际渲染"**：屏幕抓取 ⇒ 抓到的是**已旋转**的画面（歪打正着，正确）
- **"原始画面"**：抓屏幕 → 按 `原始尺寸`（**未交换宽高**）拉回去 ⇒ **竖图被拉成横图并再次变形**

⇒ 旋转过的素材截"原始画面"会得到**双重错误**（变形 + 方向错）。

### 4.3 正确的函数就在旁边，但没人调用（缺陷 5）

```vb
Public Function 读取SDR合成帧(Optional 仅光盘层 As Boolean = False) As Bitmap
    ' 两次调用 FFF3FP_CopySdrFrame：第一次问尺寸，第二次取像素
    ' 用 Format32bppPArgb 直接包裹，避免逐像素转换
End Function
```

**全工程仅 1 处匹配（就是定义本身），零调用者。**
—— 但它内部的 `CopySdrFrame` 恰好有 §2 的两个缺陷（窗口尺寸 + HDR 不支持），
所以**即使接上去也解决不了问题**。这解释了为什么它被搁置。

## 5. 修复方案（按代价排序）

### 方案 A（推荐）：内核新增「源分辨率帧回读」

现有 `CopySdrFrame` 的两个限制都要在**内核**修，宿主改不了：

```
新增 FFF3FP_CopySourceFrame(player, void* pixels, uint32 capacity,
                             uint32* width, uint32* height,
                             uint32 format /*0=BGRA8, 1=RGBA16F*/)
```

要点：
1. **尺寸 = 源分辨率**（`sourceWidth_ × sourceHeight_`），不是 `swapWidth_`；
2. **不依赖交换链**：从解码面/中间面回读，窗口最小化也能用；
3. **支持 HDR**：`format=1` 时回读 `R16G16B16A16_FLOAT`（scRGB 线性），
   由宿主决定是写 16-bit PNG 还是先色调映射；
4. **不受遮挡影响**：纯 GPU→CPU 回读，与窗口可见性无关；
5. **应用旋转**：按 `viewRotation_` 决定是否交换宽高，或原样给出并让宿主转。

> ⚠ 这条路径的正确性要**与现有 `ReadVideoPixelRegion` 对齐**（后者已是底缓冲回读），
> 但后者在 HDR 下也返回 `-2`，需一并查因。

### 方案 B（中间态）：把截图切到 `CopySdrFrame`

比现状好（不受遮挡影响），但仍：
- ❌ 只有窗口尺寸（不是原图）
- ❌ HDR 下失败
- ⇒ **只解决"遮挡"一类问题**，需明确标注"截取的是渲染结果，非原始帧"。

### 方案 C（最小）：明确区分命名

把"原始画面"改名为"**当前画面（窗口尺寸）**"，
避免用户以为拿到的是源像素。**不修问题，只消除误解。**

## 6. 已识别的相关风险

| 风险 | 说明 |
|---|---|
| `读取SDR合成帧` 的守卫 | `CULng(宽) * 高 > 16777216`（约 4096×4096）⇒ **8K 素材会被拒**（`docs/04` 有 8K 样本） |
| 路径用 `Environment.CurrentDirectory` | `生成截图路径()` 写当前工作目录；从快捷方式启动时可能是 `System32` ⇒ **保存失败或写到意外位置** |
| 文件名碰撞 | 用 `_fff` 毫秒时间戳，快速连点可能覆盖（并发下极小概率） |
| 无失败重试 | 屏幕抓取失败直接抛异常给用户，没有回落路径 |
