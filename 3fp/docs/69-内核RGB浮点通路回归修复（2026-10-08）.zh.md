## 一、回归现象（sync-impl 发现，Lead 复现）

新内核 `0962A76E9BE9027A` 下 JXR **解码成功但 G/B 通道全为 0**：

```
( 480, 250) R=1.00000 G=0.00000 B=0.00000    ← 回归态
( 240, 250) R=0.22190 G=0.00000 B=0.00000
```

改动前基线（同一 `FFF.Native.dll` + 新 FFmpeg）：
```
( 240, 250) R=0.22190 G=0.06256 B=0.01955    ← 正确
```

⇒ **解码成功 ≠ 颜色正确**。sync-impl 没有让"4/4 通过"掩盖此问题，是本次能及时止损的关键。

---

## 二、根因（Lead 读码定位，3 处缺陷）

vivid-impl 完成了 4 项改动中的 3 项（`DescribeInput` layout 3、`EnsurePipeline` → `R16G16B16A16_FLOAT`、
着色器 `InputLayout==3`），但**喂给该纹理的数据仍是整数**：

| # | 位置 | 缺陷 |
|---|---|---|
| 1 | `:5123` `const auto directYuv = input.layout != 0;` | layout 3 被当成**平面 YUV** ⇒ 仍走 `sws_scale` 转**整数** `RGBA64LE` |
| 2 | `:5286` `planeCount = layout==1 ? 3 : 2` | layout 3 被当成 **2 平面**（实际是**交错 RGBA，1 平面**） |
| 3 | `:5313` 上传无条件用 `convertedRgb_` | **整数缓冲被当作 FP16 位模式重解释** ⇒ G/B 落到 0 |

**根因链**：纹理声明为 FP16，但填充的是整数 `RGBA64LE`（每通道 16 位无符号整数）；
其位模式被 D3D 当作 half-float 解释，产生垃圾值，G/B 恰好归零。

---

## 三、修复（Lead 实施，3 处外科式改动）

全部位于 `VideoRenderer.cpp`，**未动着色器**。

### 3.1 `directYuv` 排除 layout 3
```cpp
// Layout 3 is interleaved half-float RGBA (JPEG XR's rgbaf16le): like layout 0 it
// is sampled directly as RGB, so it must NOT take the planar/semi-planar upload
// path. Unlike layout 0 it needs no CPU conversion at all -- the decoded buffer is
// already half-float, which is bit-compatible with DXGI_FORMAT_R16G16B16A16_FLOAT,
// so sws_scale would only re-quantise it into an integer range that cannot hold the
// negatives and super-whites float RGB legitimately carries (see docs/65, docs/70).
const auto floatRgb = input.layout == 3;
const auto directYuv = input.layout != 0 && !floatRgb;
if (!directYuv && !floatRgb) {
```

### 3.2 新增浮点上传分支（逐字节拷贝，零量化）
```cpp
} else if (floatRgb) {
    // Half-float RGBA is interleaved, one plane, 8 bytes per pixel -- the same
    // shape as the RGBA64LE path below, so it reuses the same single-plane upload.
    // The bytes are copied verbatim: no quantisation, so components outside [0,1]
    // survive into the FP16 texture.
    context_->UpdateSubresource(sourceTextures_[0], 0, nullptr, frame->data[0],
        frame->linesize[0], 0);
}
```

### 3.3 `planeCount` 无需改动
`:5286` 的守卫是 `input.layout == 1 || input.layout == 2` —— `directYuv` 修正后 layout 3 自然不进入该分支。
（**二次确认**：仅修 `directYuv` 不足以修好，因为上传点是独立的 `else` 分支；两者都要改。）

## 五、⚠ 仍待完成：改动 4（transfer/gamut 语义）—— **这是"完整"的必要条件**

### 5.1 为什么还没"完整"
数据现在**正确送达**且是真浮点，但**语义仍错**，Lead 已定位：

1. JXR 帧 `color_trc = UNSPECIFIED` ⇒ `frameDeclaresTrc == false`（`VideoRenderer.cpp:5337-5338`）
2. ⇒ `settings.transfer` 落回 `hdrState.format == Sdr ? 0 : ...` ⇒ **transfer = 0**
3. ⇒ 着色器执行 `ToLinear709(rgb)`，即 `LinearOne(v)`：
   ```hlsl
   float LinearOne(float v) { v=saturate(v); return v<0.081 ? v/4.5 : pow((v+0.099)/1.099,1.0/0.45); }
   ```
4. **但 `docs/70` 已用一手证据确立：`rgbaf16le` 是 scRGB 线性光**（`JXRGlue.h:136`「scRGB formats. Gamma is 1.0」）：
   - **曲线错**：对已线性数据再做 **sRGB→线性解码**
   - **钳位回潮**：`saturate(v)` **把刚保留的负值与超白又夹掉**

⇒ **V1（饱和→0）与 V2（负值/超白存活）在改动 4 落地前不可能通过。**

### 5.2 改动 4 的要求（依据已具备，见 `docs/70`）
- layout 3 的 `transfer` 须表示**"已是线性"**，**不得**跑 `LinearOne`/`ToLinear709`
- `Gamut` = **709**（scRGB 原色）；range = full
- **不得用值域启发式**（"max>1 ⇒ 线性"）：WIC 的规则只看**格式的数值类型**，不看实测动态范围
  （`FH4-HDR` max 仅 4.56，阈值法会误判）；应按 `layout == 3` / `AV_PIX_FMT_RGBAF16LE` 判定
- 需同时兼顾 `:733-737`（SDR/`MapToSdr` 路径）与 `:739`（`Transfer==1?PqToNits(...)`）
- 改 HLSL 后**必须**跑 `tools/generate_shader_bytecode.py` 重生成 `ShaderBytecode.h`

### 5.3 测量方法上的诚实提醒
`read_pixel_probe` 是**显示参考、[0,1]** 的读数，**它本身无法直接证明"负值/超白存活"**（V2）。
若 V2 无法经该探针观察到，应**如实说明并改为仪表化纹理/上传路径**，
**不得在没有证据的情况下声称 V2 通过**。
