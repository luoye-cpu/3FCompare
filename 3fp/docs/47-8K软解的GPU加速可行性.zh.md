# 47 · 8K 软解：能否用 GPU 加速（但不走 GPU 解码）

> 问题：「8K 软解的情况下有没有一些用 GPU 等加速但不是 GPU 解码的加速办法？」
> 方法：先分解"什么必须过 PCIe"，再逐项量化收益与代价
> 日期：2026-10-06

---

## 0. 结论速览

| 问题 | 回答 |
|---|---|
| 上传**之后**的步骤还能用 GPU 加速吗？ | ❌ **已经在 GPU 上了** —— 缩放、色彩转换、合成全是 GPU 着色器，没有剩余空间 |
| 上传**之前**能做什么？ | ✅ 只能**减少要传的字节数**（用 CPU 换 PCIe 带宽） |
| 最划算的方案？ | ✅ **CPU 预缩放到窗口尺寸**：净省 **~21.4 ms/帧**（20 → ~35 fps，**+75%**），CPU 成本仅 ~1 ms/帧 |
| 无损方案？ | **10bit 紧凑打包**：净省 ~6.3 ms/帧，但实现复杂且只在 10bit 源有效 |
| 最该做的其实是？ | ⚠️ **让用户用硬解** —— 同一文件硬解 58.8 fps 零丢帧，软解 20 fps 丢 2/3 |

## 1. 先厘清：上传前后各是谁在干

3FP 的渲染链路：

```
[CPU] 解码 ──► [CPU] 上传 ──► [GPU] 缩放 ──► [GPU] 色彩转换 ──► [GPU] 合成 ──► Present
                 ↑ 99.6 MB/帧        ↑ 已是 GPU        ↑ 已是 GPU      ↑ 已是 GPU
                 唯一瓶颈
```

**上传之后的每一步都已经是 GPU 着色器**：

| 步骤 | 实现 |
|---|---|
| 缩放 | `PrepareScaledVideo` + `DrawWithShader`（Lanczos3） |
| 色彩转换 | 着色器内 `To2020`/`To709`/`ToBt709`/PQ/HLG |
| 合成 | `DrawTimedText` + `CompositeTimedText` |

⇒ **"用 GPU 加速"这件事已经做到位了**，上传是唯一还在 CPU 侧的环节。

---

## 2. 上传为什么是瓶颈（实测数据）

```
8K P010 每帧 = Y 66.4 MB + UV 33.2 MB = 99.6 MB
实测带宽 4.2 GB/s  =>  23.7 ms/帧  =>  上限 42 fps
```

对照：**硬解同文件 58.8 fps、Present 0.34 ms、零丢帧** —— 因为解码器**直接产出 GPU 纹理**，不经 PCIe。

## 3. 候选方案量化（`tools/pcie_payload.cpp`）

以 8K 源、2560×1440 窗口为例：

| 方案 | MB/帧 | 相对 | 无损 | 理论上限 |
|---|---|---|---|---|
| P010 原样（现状） | 94.9 | 1.00× | 是 | 42 fps |
| **10bit 紧凑打包** | 59.3 | **1.60×** | **是** | 68 fps |
| NV12 8bit（降色深） | 47.5 | 2.00× | **否** | 84 fps |
| **CPU 缩放到窗口 + NV12** | 5.3 | **18.0×** | **否** | 760 fps |

## 4. 逐项评估

### ★ 方案 A：CPU 预缩放到窗口尺寸（**修正后：最值得做**）

**⚠️ 修正说明**：初稿把 CPU 缩放成本估为 ~5 ms/帧，那是**解码+缩放的总时间**。
分离后实测纯缩放只有 **~1 ms/帧**（同样线程数下对比"有/无缩放"）：

```
threads=1: 仅解码 5.35s  解码+缩放 5.52s  差值 ~1 ms/帧
threads=8: 仅解码 1.54s  解码+缩放 1.61s  差值 ~1 ms/帧
```

**修正后的账**：

| 项 | 值 |
|---|---|
| 现状 | 上传 99.6 MB = **23.7 ms** |
| 提案 | CPU 缩放 **1.0 ms** + 上传 5.3 MB = **1.3 ms** = 2.3 ms |
| **净收益** | **~21.4 ms/帧** |
| **预期帧率** | 50 ms → 28.6 ms ⇒ **20 → ~35 fps（+75%）** |

**⚠️ 仍需注意**：

1. **画质**：sws 可用 lanczos/bicubic，但与 GPU 侧 Lanczos3 仍有差异，需目视/PSNR 验证；
2. **窗口变化**：目标尺寸随窗口变 ⇒ 需重建 sws 上下文（有缓存机制可用）；
3. **收益只在"源 ≫ 窗口"**：全屏 8K 时几乎无收益；
4. **本质是"CPU 换 PCIe"**：占一个核约 1 ms/帧，多核下可接受。

#### ★ 端到端验证（决定性）

直接测「8K 解码 + 缩放到 1440p」的吞吐：

| sws 质量 | 2 秒素材耗时 | 吞吐（含解码） |
|---|---|---|
| fast_bilinear | 1.29 s | **93.1 fps** |
| bilinear | 1.44 s | **83.5 fps** |
| bicubic | 1.54 s | **78.0 fps** |
| **lanczos**（最高质量） | 1.70 s | **70.4 fps** |

**即使选最高质量的 lanczos，也能到 70.4 fps** —— 对比现状 **20 fps**，以及硬解的 58.8 fps。

> **诚实前提**：这是 ffmpeg CLI 的"解码+缩放"吞吐，**不含** 3FP 的上传/合成/呈现。
> 3FP 还要加上传 1.3 ms + 合成/Present；且 3FP 目前**不做 CPU 缩放**（缩放全在 GPU），
> 方案 A 是一条**新路径**。即便按一半估算，也显著优于现状。

### ★ 方案 B：10bit 紧凑打包（无损）

P010 把 10 位存在 16 位容器里 ⇒ **37.5% 是填充位**。

| 项 | 值 |
|---|---|
| 省下 | 99.6 → 59.3 MB = **9.6 ms/帧** |
| CPU 打包成本 | 33.2 Mpx × 3.25 B ≈ 108 MB 内存流量 ≈ **3.3 ms** |
| **净收益** | **~6.3 ms/帧** ⇒ 20 → ~23 fps |

**⚠️ 复杂度高**：

1. GPU 侧要写**解包着色器**；
2. 紧凑格式**不能直接用硬件线性插值** ⇒ Lanczos3 采样需手工实现，代价可能抵消收益；
3. **只在 10bit 源有效**（8bit 源无填充位可省）。

### ❌ 方案 C：降色深到 8bit

省一半传输，但**有损**：HDR/10bit 内容不可接受。不推荐。

### ❌ 方案 D：GPU 参与解码的一部分（环内滤波 / 变换）

理论上"熵解码在 CPU、残差+变换+预测在 GPU"存在，但：

- FFmpeg **没有**提供这种分离接口；
- 需要自研混合解码器，工程量与风险远超收益；
- **不可行**。

## 5. 最重要的结论：这本质上是"降级路径"

| 8K AV1 | fps | 丢帧 |
|---|---|---|
| **硬解** | **58.8** | **0** |
| 软解 | 20 | 2/3 |

**8K 软解只在以下情况发生**：

1. 用户**主动选择** CPU 解码；
2. 显卡**不支持**该编码（老卡解 AV1）；
3. 硬解实例数**超限**；
4. 硬解初始化**失败**（已有回退）。

⇒ **优先做的是让用户知道"硬解可用"**，而不是把软解从 20 优化到 30 fps。

## 6. 建议（按性价比）

| # | 建议 | 收益 | 代价 | 建议 |
|---|---|---|---|---|
| 1 | **硬解不可用时明确提示用户**（而非静默降级） | 高（直接解决根因） | 无 | **优先** |
| 2 | **CPU 预缩放到窗口尺寸**（可选开关） | 20 → **35~70 fps** | 画质需比对；新增路径 | **值得做** |
| 3 | 10bit 紧凑打包 | 20→23 fps | 高复杂度 | 暂不建议 |
| 4 | 降色深 8bit | 2× | 有损 | 不做 |
| 5 | GPU 参与解码 | — | 不可行 | 不做 |
