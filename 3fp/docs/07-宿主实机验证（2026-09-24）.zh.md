## 2. 抓屏手段（三条路，只有一条能用）

| 手段 | 结果 |
|---|---|
| `ffmpeg -f gdigrab -i title=<标题>` | ❌ **全黑** —— 3FP 是 D3D/DirectComposition 窗口，窗口 DC 抓不到合成内容（airspace） |
| `SetWindowPos(HWND_TOP)` 提到最前 + 抓全桌面 | ❌ 无效 —— 本会话的宿主/IDE 以**提升权限**运行，低完整性进程无法把窗口置于其上方（UIPI） |
| **`PrintWindow(hwnd, dc, PW_RENDERFULLCONTENT)`** | ✅ **可用** —— 由 DWM 侧渲染到内存 DC，**与 z 序、与焦点都无关** |

⇒ 工具：`3fp/build/capwin.c`（抓窗→BGRA raw）+ `ffmpeg -f rawvideo -pix_fmt bgra` 转 PNG。
另附 `3fp/build/sendkey.c`（`PostMessage` 投键，不依赖焦点）、`3fp/build/focuswin.c`（诊断窗口状态）。

## 3. 验证结果

### 3.1 ✅ 图片模式确实被调用（**决定性判据：窗口标题变化**）

图片模式下 ←/→ 切换同目录的上一张/下一张；视频模式下 ←/→ 只是 ±5 秒跳转 ⇒ **标题不会变**。
故"标题变了"即证明图片模式的抢键路径真的生效。

```
打开  C:\...\samples\media\seq\img001.png   （同目录共 10 张图）
→ 窗口标题 = img001.png
投递 VK_RIGHT(0x27) 到该窗口
→ 窗口标题 = img002.png          ✅ 切图成功
```

⇒ 一次性证明了四件事：**① 打开图片后自动进入图片模式**（`图片模式已启用=True`，否则抢键处理器会 early-return）；
**② 同目录图片列表已建立**（否则没有"下一张"）；**③ ←/→ 抢键生效**；**④ 宿主→内核的打开链路正常**。

### 3.2 ✅ 图片被正确解码与呈现

抓窗结果：`testsrc2` 图案完整显示（色条 + 对角彩线 + 点阵），窗口标题为文件名。
⇒ 内核解码 → 渲染 → 呈现 → 宿主显示，整条链路通。

### 3.3 ✅ 视频无回归

用 `small.mp4` 跑同一流程：正常播放，帧号从 0 递增到 `71`（时间码 `00:00:02.958`），窗口 `Responding=True`。
⇒ 视频模式基本播放未受影响。

### 3.4 ✅ 图片模式下时间轴控件被隐藏

对照两态抓窗（同一窗口尺寸 857×591）：

| 元素 | 视频态 | 图片态 |
|---|---|---|
| 进度条 / 播放暂停按钮 | （见下注） | **不可见** |
| 时间码 | 大号 OSD（`00:00:02.958` + 帧号 `71`） | 仅左上角**小号标签**（`00:00:00.000` + `0`） |

> ⚠ **一处未定**：图片态左上角仍有一个小号"时间码 + 数字"标签。
> `播放器界面呈现器.设置图片模式` 会置 `时间标签.Visible = False` 并把文本重置为 `TimeSpan.Zero`，
> 但实测该标签**仍可见**且显示 `00:00:00.100`（非零）。
> ⇒ 它**可能不是** `时间标签`，而是信息图层（`播放器信息图层呈现器`，其 `:230` 会格式化播放位置）的另一个元素。
> **未定案**，需在宿主侧加一次控件级读数才能确认。

## 4. ⚠ 新发现：图片的适配尺寸不对（与图片模式无关）

### 4.1 客观测量（抓窗 + 像素级外接矩形）

| 样张 | 可绘区 | 画面外接矩形 | 左/右留黑 | 上/下留黑 | 画面宽高比 |
|---|---|---|---|---|---|
| **640×480（4:3）** | 837×514 | (322,187)-(846,580) = **525×394** | **312 / 0** ← 不对称 | **120 / 0** ← 不对称 | 1.3325 ✅ 保持 |
| 1920×1080（16:9） | 837×514 | (10,67)-(846,580) = 837×514 | 0 / 0 | 0 / 0 | 1.6284 ⚠ 与源 1.7778 不符 |

- 4:3 图**宽高比正确**（1.3325 ≈ 4/3），但**被锚定到右下角**，不是居中。
- 4:3 图的偏移量**恰好是居中值的 2 倍**（312 = 2×156，120 = 2×60）。
- **直接打开**与**按 ← 切过来**结果**完全一致**（525×394 @ (322,187)）⇒ **与切图路径无关**。

### 4.2 反解：内核实际使用的输出高度是 **394**，而非客户区高度（≈534）

用内核的 `CalculateVideoDestination`（`VideoRenderer.cpp:791-812`）逐值反解：

```
CalculateVideoDestination(源 640×480, 输出 851×394, limitToNative=true)  →  size 525×394   ← 与实测尺寸完全吻合
CalculateVideoDestination(源 640×480, 输出 851×534, limitToNative=true)  →  size 640×480   ← 与实测不符
```

⇒ 内核按 **输出高度 394** 做适配，而窗口客户区高度约 **534**，**相差 140 px**。
`limitToNative`（静态图会传 `true`，见 `PlayerSession.cpp:2708`）本意是"小图不放大"，
但因为输出高度(394) < 源高(480)，代码落进了**缩小**分支 ⇒ 图片被缩到 525×394。

**候选根因（未定案）**：输出区域（交换链）高度比客户区小 140 px，很可能是
「按'扣掉控制条'的尺寸建交换链」，而图片模式把控制条隐藏后**没有让输出区域随之变大**。

### 4.3 未能定案的原因（如实记录）

- 想用「基线内核 + 同一宿主」做对照，但 **3FC 基线内核与 3FP 宿主不兼容**：
  换上去后宿主停在默认标题 `FFF.Player`、**根本没打开媒体**（未查明具体原因，可能是加载期依赖或配置差异）。
- 要定案需**内核侧插桩**（打印 `swapWidth_/swapHeight_` 与 `destination`）⇒ 需要重编译内核，
  而**本会话的内核重编译不可用**（`MSB6001` 环境缺陷 + `dotnet build` 不支持 `.vcxproj`）。

⇒ 建议下一步：换一个允许 `MSBuild` 的终端重编译内核并插桩，或先查宿主的窗口/交换链尺寸同步逻辑。

## 5. 复现命令

```bash

cp 3fp/kernel/FFF.Native/x64/Release/FFF.Native.dll "$D/"

# 启动宿主（注意：变量要先设好，且启动要放进子shell，否则 & 会吞掉后续命令）
( "$D/FFF.Player.exe" "C:\PLAN\3FCompare\3fp\samples\media\seq\img001.png" & )
sleep 13
3fp/build/capwin.exe "img001.png" "C:\PLAN\3FCompare\3fp\build\hostshots\a.raw"
3fp/build/sendkey.exe "img001.png" 27          # VK_RIGHT
sleep 5
# 再读标题：应变成 img002.png
```
