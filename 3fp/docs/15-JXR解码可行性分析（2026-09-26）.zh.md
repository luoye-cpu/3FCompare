# JXR（JPEG XR）解码可行性分析

- 日期：2026-09-26
- 触发：用户更新了 `publish/PLAN/ffmpeg-full/` 的 FFmpeg 依赖（Sep 25 03:15），要求确认 **JXR 解码现在能否跑通**
- 结论摘要：**❌ 仍不能跑通。** 新依赖**确实**带上了 `libjxr` 解码器（旧依赖完全没有），失败点也从"打不开文件"推进到"解码器拒绝包"——但 **4 个真实 JXR 样本 + 8 路自编码往返，只有 `gray` 一种能解出**，其余全部 `Unsupported JPEG XR pixel format GUID`。根因是 **FFmpeg `libjxr` 封装层的像素格式 GUID 映射表只覆盖 8bpp Gray**；此外内核/宿主**双层扩展名白名单都不含 `.jxr`**，即使 FFmpeg 能解也进不来。

## 2. CLI 层实测（`ffmpeg.exe` 直连）

### 2.1 真实样本（Windows HDR Calibration 资源）

素材来源：`C:\Program Files\WindowsApps\MicrosoftCorporationII.WindowsHDRCalibration_1.0.152.0_x64__8wekyb3d8bbwe\Assets\`
（⚠ WindowsApps 受保护目录不可直读 ⇒ 已 `cp` 到 `3fp/samples/media/jxr/`）

| 样本 | 体积 | 新 FFmpeg 解码结果 |
|---|---|---|
| `HDColorHDRCalibration.jxr` | 24.5 KB | ❌ `Unsupported JPEG XR pixel format GUID` → `Function not implemented` |
| `fh2_fp16.jxr` | 1.9 MB | ❌ 同上 |
| `FH4-HDR.jxr` | 8.3 MB | ❌ 同上 |
| `DHR-CoJ1002.jxr` | 7.8 MB | ❌ 同上 |

### 2.2 编码器→解码器往返（决定性实验）

用**新 FFmpeg 自己的编码器**写出 8 种像素格式，再用**同一个解码器**读回 —— 这条路径排除了"真实样本写法特殊"的干扰，直接测量解码器的 GUID 表覆盖度：

| `-pix_fmt` | 编码 | 解码 | 写入的嵌入 GUID | 说明 |
|---|---|---|---|---|
| `gray` | ✅ | **✅** | `6fddc324-4e03-4bfe-b185-3d77768dc908` | **8bppGray —— 唯一能解的** |
| `gray16le` | ✅ | ❌ | `...c90b` | 16bppGray |
| `rgb24` | ✅ | ❌ | `...c90d` | 24bppRGB |
| `bgr24` | ✅ | ❌ | `...c90c` | 24bppBGR |
| `rgba` | ✅ | ❌ | `f5c7ad2d-6a8d-43dd-a7a8-a29935261ae9` | 32bppRGBA |
| `bgra` | ✅ | ❌ | `...c90f` | 32bppBGRA |
| `rgb48le` | ✅ | ❌ | `...c915` | 48bppRGB |
| `rgba64le` | ✅ | ❌ | `...c916` | 64bppRGBA |

⇒ **编码器 8 种全写出成功，解码器 8 种只认 1 种。** 失败全部是 `jxrlib JPEG XR decode failed (error=-1)`（自产文件用 GUID 路径），与真实样本的 `Unsupported ... GUID` 是同一层问题的两种表现。

`gray` 的**真解码**已交叉确认（非空转）：

```

ffprobe: codec_name=jpegxr  width=64  height=64  pix_fmt=gray
```

## 3. JXR 头部结构（区分两类文件）

JXR 文件头 = `IMAGE_HEADER{ magic(4) + headerSize(u32) }`，其后接若干 tag。**`headerSize` 决定内不内嵌 GUID**：

| 文件 | magic | `headerSize` | offset 8 处的字段 | `pixelFormat`/GUID |
|---|---|---|---|---|
| 4 个**真实样本**（`HDColorHDRCalibration`/`fh2_fp16`/`DHR-CoJ1002`） | `49 49 BC 01` | **8** | 1 字节像素格式码 = **`0x0B`(11)** | 无 GUID，**扩展格式码**（超出 jxrlib 经典 0–10 枚举） |
| `FH4-HDR.jxr`（真实） | `49 49 BC 01` | **8** | 像素格式码 = **`0x0C`(12)** | 同上 |
| 新 FFmpeg **自编码**产物 | `49 49 BC 01` | **32** | 128-bit WIC GUID | 标准 `WICPixelFormat*` GUID |

**jxrlib 经典 `PIXEL_FORMAT` 枚举**（`JXRGlue.h`）只到 10：

```
0 32bppRGB  1 32bppRGBA  2 32bppPRGBA  3 24bppRGB  4 48bppRGB
5 32bppBGR  6 32bppBGRA  7 32bppPBGRA  8 8bppGray  9 16bppGray  10 32bppCMYK
```

⇒ 真实样本用的 **11 / 12 是枚举外的扩展码**（HDR/WGC 相关编码），FFmpeg 封装的 GUID 映射表**两头都不覆盖**（既没覆盖 11/12，也没覆盖标准彩色 GUID）。这解释了为什么 **4 个真实样本和 8 路自编码往返一起失败**——不是样本"写法特殊"，而是**封装层只映射了 gray**。

## 5. 第二层阻塞：扩展名白名单不含 `.jxr`

即使 FFmpeg 修好 GUID 表，还有一道**宿主/内核层的格式清单**挡着：

| 位置 | 内容 | 含 `.jxr`? |
|---|---|---|
| `FFF.Player/Core/播放列表.vb:31,37`（`图片扩展名`） | `.png .jpg .jpeg .jpe .gif .apng .webp .jxl .bmp .tif .tiff .ico .avif .heic .heif` | ❌ |
| `FFF.Player/文件关联管理器.vb:503-545` | 常见图片 15 项 / 不常见图片 13 项 / 老旧图片 14 项 | ❌（`.jxr/.wdp/.hdp` 全无） |
| 内核路径校验 `PlayerSession.cpp:3920-3931` | `GetFullPathNameW` + `GetFileAttributesW`，拒 reparse point | —（探针已绕过，直接传绝对路径） |

⇒ 在真实宿主里，`.jxr` **既不会被当作图片纳入播放列表，也不会出现在文件关联里**。要真正跑通，需**同时**改这两处（或至少 `图片扩展名`）。

## 6. 结论

**❌ JXR 解码仍不能跑通。**

分三层：

1. **依赖层** ✅ **已到位**——新 FFmpeg 编入 `libjxr`，`-decoders` 有、字符串有、字节计数有；失败点从 `open` 推进到 `decode`，证明接线正确。
2. **解码器层** ❌ **阻断点**——FFmpeg `libjxr` 封装的像素格式 GUID 映射**只支持 8bpp Gray**。真实样本用的扩展码 11/12、以及全部标准彩色 GUID（24/32/48/64bpp、RGBA）**全不认**。
3. **宿主/内核层** ❌ **第二道门**——`图片扩展名` 与 `文件关联管理器` **均不含 `.jxr/.wdp/.hdp`**。

## 7. 可选后续（供决策，**未实施**）

| 选项 | 内容 | 代价/收益 |
|---|---|---|
| **A. 等上游** | jxrlib 上游补齐 FFmpeg 封装的 GUID 表（或换 `jxrlib` 分支） | 零成本，但**不可控、无时间表** |
| **B. 本地打补丁** | 给 FFmpeg 的 `libjxr.c` 补 GUID 映射后自行重编 `avcodec-63.dll` | 需维护 FFmpeg 分支，与"用预编译 full build"策略冲突 |
| **C. 只管白名单** | 先给 `图片扩展名`/文件关联加 `.jxr/.wdp/.hdp` | ❌ **无效**——FFmpeg 仍解不出，只会得到"能选中但打开失败" |
| **D. 换解码后端** | 走 Windows 原生 WIC（`IWICImagingFactory` 支持 JXR）绕过 FFmpeg | 需新增 WIC 解码路径，与现有 FFmpeg 单链路架构冲突，改动大 |
| **E. 判定为"暂不支持"** | 文档标注 `.jxr` 不在支持范围 | 成本最低；但若用户有 JXR 需求则需回到 B/D |

⚠ **不建议先做 C** —— 白名单放开而没有可用解码器，只会把"格式不支持"变成"支持但打不开"的坏体验。

## 9. 本轮踩坑（工具层）

1. **WindowsApps 受保护目录不可直读**：`GetFileAttributesW` 失败 ⇒ 探针报 `"The path must identify an existing regular local file."`（**误导性**，会被当成"路径不合法"）。**修法**：先 `cp` 到工作区。
2. **Git Bash 传 Windows 路径给原生 exe 必须单引号**：`"C:\\PLAN\\...\\$f"` 里 `$f` 前的 `\\` 会与变量展开交互，折叠成单反斜杠+变量丢失 ⇒ `No such file or directory`。**统一用单引号完整路径**。
3. **新 FFmpeg 是 clang/llvm-mingw 交叉编译** ⇒ 缺 6 个运行期 DLL 时**探针静默无输出**（不是崩溃）。**修法**：把 `libc++.dll` 等一并拷入。
4. **`/tmp` 与 Windows Python 的路径鸿沟**：MSYS `/tmp` 对 Windows Python 不可见，须 `cygpath -w` 解析（实测 `/tmp/jxrrt` → `C:/Users/.../Temp/jxrrt`）。
5. **换 DLL 试验后必须还原并 `cmp` 校验**：本轮已在 `3fp/build/` 用新 DLL 覆盖（备份在 `/tmp/oledll/`），**收尾已完整还原**（三个 DLL `cmp` = IDENTICAL，6 个额外依赖已删），避免污染后续动图/图片基线。
6. 🔴 **`ffmpeg -frames:v 1 -f null -` 解码失败仍返回 exit 0** ⇒ 用退出码当判据会得到**假绿**。实测：脚本初版据此判"8 种 pix_fmt 全 DEC-OK"，与本节 §2.2 的手工结论（只 `gray` 能解）**直接矛盾**。**正确判据 = `-v error` 下 stderr 为空**（已修入 `docs/16` §5 / `tools/verify_jxr.sh`）。⇒ **元发现 2（判据特异性）的又一实例：ffmpeg 的退出码不携带解码器层面的失败**。
7. **宿主测试输出目录有独立的 FFmpeg DLL 副本**：`FFF.Player.Tests/bin/Release/.../` 下另有一套 `avcodec-63.dll` 等，只换 `3fp/build/` **不影响宿主端到端** ⇒ 两处都要换（见 `docs/16` §7.4）。
