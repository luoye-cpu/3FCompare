# 3FP 图片模式 与 主流图片查看器 启动速度对比分析

- 日期：2026-10-07
- 触发：用户指令「分析一下 3fp 图片模式的启动速度和大部分图片查看器的启动速度」
- 对象：3FP 图片模式宿主 `FFF.Player.exe`（散装非单文件发布，Release x64） vs 本机主流图片查看器
- 本机环境：Intel i7-13650HX（14C/20T）· 31.6 GB RAM · Windows 11 build 26300 · .NET 10.0.12 · PowerShell 7.6.6
- 组织方式：Lead + 2 名 Team 成员（`threepfmeasure` 负责 3FP 侧，`viewermeasure` 负责查看器侧）并行实测

> ⚠ **全部绝对数字均在「重载环境」下采集**：采集期间本机有**其它 agent 会话**并发占用 CPU
> （`VBCSCompiler` 一度累计 157 s CPU、`FFmpegFreeUI` GUI 在跑），实测负载 18%–37%。
> 因此本报告的数值**只适合作横向相对比较**，不代表空闲机器上的绝对值。
> 唯一在**较低负载窗口**采集的是 §2 的「Lead 干净锚点」，其 `SpawnMs` 中位数仅 6.3 ms（重载时为 100+ ms），可作绝对基线。

## 0. 结论摘要（先看这个）

**在同一口径（T0 = 起进程之前；T1 = 该进程首个「可见且有标题」的顶层窗口出现）下，带图启动中位数：**

| 排名 | 对象 | 中位数 | 3FP 是其几倍 | 样本 | 口径说明 |
|---|---|---:|---:|---:|---|
| 1 | **WPS 图片** | **468 ms** | **2.6×** | 11 | Win32 真冷启动 |
| 2 | **Windows 照片查看器** | **499–515 ms** | **2.4×** | 11+11 | Win32（rundll32 薄宿主） |
| 3 | **Adobe Photoshop 2026** | **731–759 ms** | **1.6×** | 5+7 | ⚠ 重型编辑器，参照上限 |
| 4 | **3FP 图片模式** | **1212 ms**（干净）/ 1604 ms（重载） | 1× | 5 / 7 | Win32 冷启动，完整路径 |
| 5 | Windows 照片（UWP） | 2032 ms | ⚠ **不可比** | 9 | 含 shell 激活层，且无法传图 |
| 参照 | .NET10+WinForms 地板（自建最小空窗体） | **≈203–219 ms** | 0.18× | 7+9 | 运行时下限 |

> 「3FP 是其几倍」= 1212 ms ÷ 该对象中位数。UWP 因口径不等价**不参与倍数计算**。

**三句话结论：**

1. **3FP 图片模式启动 ≈1.2 s，比 WPV / WPS 图片慢约 2.4–2.6 倍**（Photoshop 也快 1.6 倍）。这不是"演示模式"或"缺 DLL 早退"造成的——该形态 FFmpeg 六件套与 `FFF.Native.dll` 齐全，走的是**完整启动路径**。
2. **慢的不是 .NET 运行时，而是应用自身**：一个功能等价的最小 WinForms 空窗体只要 **≈210 ms**（60 个模块），3FP 要 1212 ms（154 个模块）⇒ **约 1000 ms（≈82%）是 3FP 自己的启动工作量**。
3. **最大单项开销是 LakeUI 的 D3D/Direct2D 初始化，它会拉起 NVIDIA 驱动着色器编译器**（实测 `nvgpucomp64.dll` 在 **≈735 ms** 才进内存）。这比"首触 JIT"更接近根因；R2R 只能回收其中约 **−142 ms（−10.6%）**。

**并且有一个直接可用的杠杆**：`PublishReadyToRun` 当前**是关闭的**（`FFF.Player.vbproj:11-12` 注释态），开启后实测 **−141.9 ms（−10.6%）**，代价是托管体积 **+7.5 MB**。

## 1. 测量口径（两个任务严格一致，否则不可比）

| 项 | 定义 |
|---|---|
| T0 | 调用 `Process.Start` **之前** |
| T1 | **目标 pid** 首个「`IsWindowVisible` 为真 **且** `GetWindowTextLengthW > 0`」的顶层窗口出现 |
| 判据实现 | `EnumWindows` + `IsWindowVisible` + `GetWindowTextLengthW` + `GetWindowTextW`（自包含 P/Invoke） |
| 预热 | 2 次，不计入 |
| 正式 | ≥9 次（部分 5–7 次，见各表） |
| 轮间隔 | Kill + 等 1.0–1.2 s |
| 启动 API | `[System.Diagnostics.Process]::Start(...)`（**`Start-Process -PassThru` 在本机会挂住不返回**） |
| 证据 | **每轮记录窗口标题**，作为「确实打开了」的凭据 |
| 作废规则 | `SpawnMs > 50 ms`（说明调度器被抢占）⇒ 该轮重跑（Lead 侧脚本已实现） |

> ⚠ **为什么不复用 `3fp/tools/WinUi.cs`**：本机 PowerShell 是 7.6.6 / .NET 10，`Add-Type -Path WinUi.cs`
> 会因 `System.Drawing` 变成 facade 而编译失败。故计时工具**自包含 P/Invoke**（沿 `startup_time.ps1` 的做法）。

### 1.1 ⚠ 口径的一个重要局限（本次实测发现）

「有标题窗口」这个判据**会被假窗口骗到**。实测踩坑：

- **rundll32 的参数写法只要稍有出入，就会弹出一个类名 `RunDLL` 的「找不到指定的模块」错误框**；
  该错误框**可见且有标题**，完全满足判据 ⇒ 被误判为「查看器窗口已出现」。
- **Lead 自己就中招了**：`lead_final_compare.ps1` 对 WPV 测出 **140.8 ms**，7/7 轮标题全是 `RunDLL`——
  **该数字是假的**。加类名白名单（排除 `RunDLL`/`GDI+`/`IME`/`tooltips_class32`/输入法皮肤）重测后为 **499.4 ms**，
  与 viewermeasure 独立测得的 **515.2 ms** 吻合。
- 真正的查看器窗口类名是 **`Photo_Lightweight_Viewer`**，标题 `Windows 照片查看器`。
- ⇒ **凡是用「窗口出现」做判据的启动计时，都必须校验窗口身份（类名/子控件），不能只看"有标题"。**
  这条已写入 §7 陷阱表。

### 1.2 ⚠ 另一个口径陷阱：`$args` 是 PowerShell 自动变量

脚本里用 `$args` 存 rundll32 的参数串，在**函数内**会解析成该函数的「未绑定参数数组」（空），
导致 `Arguments` 为空 ⇒ rundll32 立刻 `exit=0`、11/11 全失败。**改名 `$wpvArgs` 后正常。**
（与 docs/17 §4.4 记录的 `$A`/`$a` 自我污染同族：PowerShell 的变量解析陷阱。）

## 2. 3FP 图片模式（本报告主角）

### 2.1 被测形态（必须先讲清，否则数字无意义）

| 项 | 值 |
|---|---|
| 主交付形态 | `3fp\publish\Release-win-x64\`（**非单文件**散装发布） |
| 文件数 / 体积 | 38 个文件 / **159,620,108 B（152.1 MB）** |
| 关键依赖 | FFmpeg 六件套（`avcodec-63` 71.75 MB / `avfilter-12` 28.66 MB / `avformat-63` 8.03 MB / `avutil-61` / `swscale-10` / `swresample-7`）+ `FFF.Native.dll` 1.26 MB —— **全部齐全** |
| ⇒ 路径判定 | **走完整启动路径**。⚠ **不是** docs/17 §4.2② 那个「单文件发布不含 FFmpeg ⇒ 核心文件缺失早退」的 836 ms 降级路径 |
| 托管 DLL | `FFF.Player.dll` **995,328 B，纯 IL（R2R=False）** |

> ⭐ **重要**：「3FP 图片模式」**不是一个独立 exe**。同一个 `FFF.Player.exe` 启动后，打开图片才自动进入图片模式
> （`播放器图片浏览控制器.自动进入图片模式`）。所以「图片模式的启动速度」= **宿主进程启动到窗口可用**的速度；
> 图片模式的额外开销发生在**打开图片之后**，不在进程启动路径上。

### 2.2 基线读数（三个独立来源互相印证）

| 来源 | 环境 | 中位数 | 样本 | 备注 |
|---|---|---:|---:|---|
| **Lead 干净锚点** | 低负载（SpawnMs 中位 6.3 ms） | **1212.4 ms** | 5 | 1060.2 / 1193.6 / **1212.4** / 1259.1 / 1263.3 |
| **docs/17**（2026-09-26 前序） | 当时 | **1205.9 ms** | 9 | 与 Lead 仅差 0.5% |
| threepfmeasure | 重载 | 1539.0 ms | 11（2 作废） | ⚠ **重载伪影，不作基线**（见 §2.3） |
| Lead 最终对比 | 重载（18% 负载） | 1604.2 ms | 7 | 与 1539 同向，佐证负载抬高量 |

**⇒ 采信绝对基线 = 1212 ms。** 两个独立会话在相隔 11 天、不同代码状态下测出 1212 / 1206 ms，
差异 0.5%，说明该数字**稳定可复现**。

### 2.3 ⚠ 为什么否定 threepfmeasure 的 1539 ms（方法论诚实性）

该轮两个异常使 Lead 判定为伪影，**不采信**（团队主动否定自己的第一轮数据）：

1. **2/9 样本撞单实例**：`提前退出 exit=0` —— 撞上 `IsSingleInstance=True` 的既存实例。
2. **旁证污染**：`SpawnMs`（`Process.Start` 到返回）在 **4.7 ~ 168.4 ms** 乱跳；正常应 ≈6 ms。
   `Process.Start` 都要花 168 ms ⇒ **是调度器被抢占，不是宿主变慢**。

**污染源（Lead 独立核实）**：本机有**其它 agent 会话**在 `C:\PLAN\ffmpegPictureUI` 里构建，
`VBCSCompiler` PID 27500 累计 **157.2 s CPU**、`FFmpegFreeUI` GUI 在跑、多个 `pwsh` 在跑验证脚本；
CPU 负载 37%。⇒ 属真实跨会话争用，**不是被测软件的属性**。

> ⚠ 更严重的：存在**互相杀 `FFF.Player` 的冲突**（有会话在跑 `Get-Process FFF.Player | Stop-Process`）。
> 这会**同时破坏双方数据**。建议后续涉及 GUI 计时的任务先做**进程级互斥约定**（见 §8）。

### 2.4 启动阶段时间线（Lead 独立实测，3 次重复高度一致）

用「模块首次进内存时刻」外部观测（不插桩、不改源码）：

| 时刻 | 事件 | 说明 |
|---:|---|---|
| 0–6 ms | `Process.Start` 返回 | 进程已创建 |
| ~55 ms | `FFF.Player.dll` | 托管入口程序集装载 |
| ~58 ms | `System.Windows.Forms.dll` | WinForms 栈 |
| ~121 ms | `LakeUI.dll` | ★ 第三方 UI 库（2.15 MB，含完整 D3D11 引擎） |
| ~213 ms | `icu.dll` | 全球化 |
| **~368 ms** | **首个「可见」窗口（尚无标题）** | 窗口已存在，但 UI 线程还没跑完 `Form1_Load` |
| **~460 ms** | **`d2d1.dll`** | ★ **Direct2D 初始化开始**（LakeUI 自绘标题栏/毛玻璃/阴影） |
| **~735 ms** | **`nvgpucomp64.dll`** | ★★★ **NVIDIA 驱动着色器编译器** —— 单项最大开销 |
| ~855 ms | `nvwgf2umx.dll` | NVIDIA 用户态驱动（UMD） |
| ~950 ms | `d3dcompiler_47.dll` | D3D 着色器编译器 |
| ~1120 ms | `System.Private.Xml.dll`(7.42 MB) + `Svg.dll` | ★ 图标 SVG 解析（首触 JIT + XML 栈） |
| **~1212 ms** | **窗口获得标题 `FFF.Player`** | = 本报告的 T1 |

三次重复的到达时刻（ms）：`nvgpucomp64` = **806 / 650 / 751**；`d2d1` = **437 / 520 / 434**；
`System.Private.Xml` = **1306 / 1054 / 1225** ⇒ **顺序与量级稳定，归因可信**。

**启动期间共加载 154 个模块 / ~70 个托管程序集**，其中重量级：
`System.Private.CoreLib` 15.28 MB、`System.Windows.Forms` 13.07 MB、`System.Private.Xml` 7.42 MB、
`coreclr` 4.48 MB、`System.Windows.Forms.Primitives` 3.45 MB、`System.Security.Cryptography` 2.42 MB、
`clrjit` 2.01 MB、`System.Text.Json` 1.79 MB、`System.Net.Http` 1.66 MB、`LakeUI` 2.17 MB。

### 2.5 ⭐ 决定性归因实验：真正的瓶颈是什么

**(a) 运行时地板实验（Lead 自建最小 WinForms 应用）**

自建一个「只有运行时 + 一个空窗体」的 VB.NET WinForms 应用（`net10.0-windows`，同 SDK 同 Release）：

| | 地板应用 | 3FP | 差 |
|---|---:|---:|---:|
| 中位数 | **219 ms**（n=9，样本 108–294） | 1212 ms | **≈993 ms** |
| 加载模块数 | **60** | **154** | **+94** |

⇒ **.NET 10 + WinForms 的冷启动地板只有 ~220 ms；3FP 自己的启动工作量约 1000 ms（占总时长 ≈82%）。**
⇒ 结论明确：**慢的不是运行时，是应用自身**（LakeUI 的 D3D/D2D 引擎 + 大型依赖栈）。

**(b) 运行时开关对照（验证「首触 JIT」论断，不改代码，n=7）**

| 场景 | 中位数 | 相对默认 |
|---|---:|---:|
| A 默认 | **1147.2 ms** | — |
| B 关分层编译 `DOTNET_TieredCompilation=0` | 1394.4 ms | **+247.2 ms（+21.5%）** |
| C 关 R2R `DOTNET_ReadyToRun=0`（纯 IL 无影响，对照） | 1806.9 ms | +659.7 ms（+57.5%） |
| D `TC=0` + `QuickJitForLoops=0` | 1523.0 ms | +375.8 ms（+32.8%） |

⇒ **关掉分层编译/JIT 优化后启动显著变慢（+21.5% ~ +32.8%）**，**支持** docs/17「首触 JIT 是重要成本」的论断。
⇒ 但注意：**JIT 不是唯一成本**——§2.4 显示 D3D/驱动初始化（~460→950 ms 段）**在时间上占了绝大部分**，
而 R2R 只能优化 JIT 那一部分（实测 −10.6%）。**两者是并列而非互斥的结论。**

## 3. ⭐ 唯一「一行配置、零代码风险」的杠杆：`PublishReadyToRun`

### 3.1 ⚠ 首先纠正一个现状误判（本轮独立核实）

**`docs/17` 声称 R2R 已于 2026-09-26 落地 —— 该结论对当前产物已不成立。**

三条硬证据（`threepfmeasure` 独立核实）：

| # | 证据 |
|---|---|
| 1 | `3fp/kernel/FFF.Player/FFF.Player.vbproj:11-12` 的 `<PublishReadyToRun>True</PublishReadyToRun>` **处于注释态** |
| 2 | 出货产物 `3fp\publish\Release-win-x64\FFF.Player.dll` = **995,328 B**（R2R 后应 ≈2.05–2.11 MB） |
| 3 | COR20 头：**`Flags=0x1`（ILONLY）+ `ManagedNativeHeader RVA=0`** ⇒ 纯 IL，未编译为本机码 |

**根因比预判更确定**：`git log -S "<PublishReadyToRun>True</PublishReadyToRun>"` 全仓**只命中 2026-07-25 两个提交，
且引入的是注释形式** ⇒ **「取消注释」这个动作从未进入任何提交**（当时的"已落地"只是**未提交的工作区状态**）。

**决定性证据**：提交 `6d5cdb2`（**2026-09-26 15:57**，恰是 docs/17 记「13:30 已落地」的同日晚）
diff 明确写「R2R 已按体积优先口径关闭」。且该提交属 `upstream/image-mode` 分支，
`merge-base --is-ancestor` **exit=1** ⇒ **不在当前 HEAD（`feature/vsr-and-rotation`）上**。
两条分支殊途同归：**R2R 都是关的**。

⇒ **行动项：若启动速度优先，需重新开启 R2R 并提交。**

### 3.2 R2R A/B 实测（同批次交替，Lead 执行，n=9）

用 `threepfmeasure` 构建的 R2R 副本（原工程零改动）做**同批次交替**对照：

| | A 纯 IL | B R2R |
|---|---:|---:|
| `FFF.Player.dll` | 995,328 B | **2,113,536 B** |
| COR20 Flags | `0x1` ILONLY, MNH RVA=0 | **`0x4` ILLIBRARY, MNH RVA=142768** |
| **中位数** | **1341.0 ms** | **1199.1 ms** |
| Min / Max | 1186.3 / 1554.0 | 1045.0 / 1275.5 |
| 有效样本 | 7 | 8（共 9 轮，2 轮作废） |

**⇒ 差值 −141.9 ms（−10.6%）；B 胜 6 轮 / A 胜 1 轮 / 2 轮作废。**

⚠ **诚实标注（重要）**：**Δ 范围（−278.5 ~ +0.7 ms）大于中位数差（−141.9 ms）**，
且 2 轮因 `SpawnMs>50` 作废 ⇒ **该结论「方向一致但落在噪声带内，不足以单独定量」**。
它与 docs/17 记录的 **−141.4 ms 数值上几乎完全吻合**，可作**旁证**，但**不能当成独立复现的硬证据**
（同机、同法、同样受负载影响）。

**代价**：托管 DLL 合计约 **+7.5 MB**（`FFF.Player.dll` +1.09 MB、`LakeUI.dll` +2.82 MB、`Svg.dll` +1.06 MB、`Vortice.*` +1.47 MB、`ExCSS` +0.74 MB）。

**注意事项**（沿 docs/17 §4.4，本轮复核仍然成立）：
1. 只对 **`dotnet publish`（且带 `-r <RID>`）** 生效，`dotnet build` 不受影响 ⇒ 日常 `bin/Release` 仍是纯 IL。
2. **不要**同时开 `PublishReadyToRunEmitSymbols`（与发布脚本的 `-p:DebugType=None` 冲突）。
3. 发布后必须确认 FFmpeg/`FFF.Native.dll` 在位 ⇒ 否则「启动变快但打不开文件」。

## 4. 主流图片查看器实测

### 4.1 结果（`viewermeasure`，与 §2 同口径）

| 查看器 | 冷/暖 | 带图 | N | Min | **中位数** | Max |
|---|---|---|---:|---:|---:|---:|
| **WPS 图片** | **真冷** | ✅ 241 KB | 11 | 390.1 | **468.1** | 625.5 |
| WPS 图片 | 真冷 | ✅ 8.3 MB | 5 | 436.6 | 438.7 | 526.8 |
| **Windows 照片查看器** | 冷（每轮干净重启） | ✅ 241 KB | 11 | 466.9 | **515.2** | 729.4 |
| Windows 照片查看器 | 冷 | ✅ 8.3 MB | 9 | 497.7 | 623.5 | 761.4 |
| **Adobe Photoshop 2026** | 冷（参照上限） | ✅ 241 KB | 5 | 744.4 | **758.5** | 772.8 |
| **Windows 照片（UWP）** | ⚠ shell 激活 | ❌ 无法传图 | 9 | 1968.2 | **2032.2** | 2170.2 |

窗口标题证据（全部轮次一致）：`WPS图片` / `Windows 照片查看器` / `Adobe Photoshop 2026` / `照片`。
**6 个正式 CSV 零失败。**

Lead 独立复测 WPV（加类名白名单，n=11）：**499.4 ms**（467.2–655.4）⇒ 与 515.2 ms 一致。

### 4.2 冷 / 暖判定 —— 推翻一个假设

任务书曾假设「`photolaunch.exe` 可能只是唤醒常驻进程 ⇒ 属暖启动」。**实测相反**：

- 它**确实拉起一整套常驻子树**：`photolaunch` ×1–2、`wps` ×4–6、`wpscloudsvr` ×1、`ksomisc` ×1。
- **但常驻进程并不加速**。对照实验（各 4 轮）：真冷 ≈**505 ms** vs 保留常驻 ≈**454 ms** ⇒ **无显著差异**。
- **反向发现（更重要）**：**不清理会污染下一轮**。未清理的连续测试中，常驻进程数 1→3→8→13→18，
  耗时同步 489→688→967→1058 ms **单调恶化**。⇒ 正式数据因此**每轮前彻底清理 WPS 全家族进程**。

**⇒ WPS 图片记为「Win32 真冷启动，468 ms」。**

### 4.3 ⚠ 公平性局限（本报告最重要的部分之一）

1. **Windows 照片（UWP）的 2032 ms 不可与其余并列。**
   - `Start(Photos.exe)` ⇒ **拒绝访问**（`WindowsApps` ACL + AppX 不允许直接起 exe）；
     `ms-photos:viewer?fileName=...` ⇒ `explorer` **exit=1**；仅 `shell:AppsFolder\...` 可用。
   - `explorer.exe` 只是**激活器**（自身立刻退出），真正承载窗口的是**新出现的 `Photos.exe`**。
     ⇒ 测到的是「**shell 激活 + UWP 冷启动**」的**合成时间**，比 Win32 查看器多一整个 shell/RuntimeBroker 层。
   - 且 `shell:AppsFolder` **无法传入图片**，故 UWP 只测到**不带图**，与其它对象的「带图」口径**不一致**。
   - 旁证：**Photoshop（编辑器）758 ms 反而快于 UWP 照片** ⇒ 正说明 UWP 那个数被 shell 层拖累。
2. **WPV 的 `PhotoViewer.dll` 属系统组件，可能已被预热/驻留**，不像第三方软件那样"冷"。
   `rundll32` 是**共享宿主**，故每轮前确认相关进程为 0，排除「换图」被误计为「启动」。
3. **Photoshop 是编辑器而非查看器**，其功能集与资源开销远超查看类 ⇒ 标注为**参照上限，不与查看器同台比较**。
4. **大图差异有限**：WPV 241 KB→515 ms、8.3 MB→624 ms（+108 ms）；WPS 几乎无差异。
   ⇒ 因为 **T1 只到「窗口出现」，不覆盖完整解码**。
5. **单实例风险**：WPS / Photoshop 均有单实例倾向，已用每轮前后进程快照确认每轮均为**新进程**。
6. **本机未安装** IrfanView / Honeyview / XnView / JPEGView / FastStone / ImageGlass 等，故未纳入
   （已全盘扫描 `Program Files` 与 `Program Files (x86)`）。

## 5. 为什么 3FP 比查看器慢 —— 差距拆解

以 Lead 干净锚点 1212 ms 为基准，与地板 219 ms、WPV 499 ms 对比：

| 分段 | 估算耗时 | 内容 | 可优化性 |
|---|---:|---|---|
| .NET 10 + WinForms 运行时地板 | **≈220 ms** | CLR 启动 + WinForms 初始化（60 模块） | ❌ 结构性，AOT 才能显著砍（但 WinForms+AOT 需 trim 兼容，风险高） |
| LakeUI + D3D/Direct2D 初始化 | **≈600–700 ms** | `d2d1`(~460) → `nvgpucomp64`(~735) → `nvgwf2umx`(~855) → `d3dcompiler_47`(~950) | ⚠ **最大单项**；需评估是否启动即建 D3D 设备（懒初始化/延迟到首帧） |
| SVG 图标加载 + XML 栈 | **≈90–160 ms** | `System.Private.Xml`(7.42 MB) + `Svg.dll`（首触 JIT） | ⚠ 中等；构建期预光栅化会丢 DPI 自适应（docs/17 §5.2 已否决懒加载） |
| 其它（设置/字体/文件关联/布局） | **≈100–150 ms** | 读 JSON + 反射设字体 + `PerformLayout` | ⚠ 低收益，风险高于回报 |

**关键对比**：WPV 只需「起一个薄宿主 + 载 DLL + 建一个 GDI 窗口」；
3FP 要「起 .NET 宿主 + 载 154 模块 + **建完整 D3D11/2D 设备与交换链** + 解析 SVG 皮肤」。
**差距的本质是架构选择，不是代码写得差。**

## 7. 已知陷阱（本轮新增，供后续复用）

| 陷阱 | 说明 |
|---|---|
| ⚠ **「有标题窗口」判据会被假窗口骗到** | rundll32 参数稍有出入会弹**类名 `RunDLL`** 的错误框，**可见且有标题** ⇒ 满足判据被误判成功。**Lead 自己就测出过假的 140.8 ms**（7/7 轮标题均为 `RunDLL`）。⇒ 必须校验**窗口类名**（真查看器 = `Photo_Lightweight_Viewer`）或 dump 子控件 |
| ⚠ **`$args` 是 PowerShell 自动变量** | 脚本里用 `$args` 存参数串，在**函数内**解析成「未绑定参数数组」（空）⇒ rundll32 立刻 `exit=0`、11/11 全失败。改名 `$wpvArgs` 即正常（同族：docs/17 的 `$A`/`$a`） |
| ⚠ **rundll32 参数写法只有一种正确形式** | `rundll32.exe /d "<DLL全路径>",<入口名> <图>` —— `/d` 必须有；**逗号紧跟右引号**（不能加空格）；**图片路径不能加引号**（加了立刻 `exit=0`）；DLL 路径不加引号会弹 `RunDLL` 错误框 |
| ⚠ **必须用 `ProcessStartInfo.Arguments`（字符串）** | `Process.Start(exe, args)` 会破坏引号 ⇒ rundll32 失效。`ArgumentList`（集合形式）同样失效 |
| ⚠ **UWP 应用不能直接 `Start(Photos.exe)`** | `拒绝访问`（`WindowsApps` ACL）。唯一可用：`explorer.exe "shell:AppsFolder\<PFN>!App"`；且不能用 explorer 的 pid 判窗口（它立刻退出） |
| ⚠ **多 agent 共享同一台机器会互相破坏测量** | 本次实测：其它会话在跑构建（`VBCSCompiler` 157 s CPU）+ **有进程在 `Stop-Process FFF.Player`**，既抬高绝对值又造成真实冲突。判据：`SpawnMs` 从正常的 ~6 ms 漂到 100+ ms ⇒ 该轮作废 |
| ✅ **`Copy-Item -Force` 保留时间戳致假对照** | 已在 docs/STATUS 记录；本轮 A/B 用「副本工程独立发布」而非换文件，天然规避 |

## 8. 结论与建议

### 8.1 直接回答用户的问题

1. **3FP 图片模式启动 ≈1.2 s**（干净环境，n=5，与 docs/17 的 1205.9 ms 吻合）。
2. **主流查看器带图启动**：
   - **WPS 图片 468 ms**（3FP 的 2.6 倍耗时）
   - **Windows 照片查看器 499–515 ms**（2.4 倍）
   - **Adobe Photoshop 2026 758 ms**（1.6 倍，但它是编辑器，作参照上限）
   - Windows 照片（UWP）2032 ms —— **口径不可比**，不能算「更慢」
   - 参照：**.NET10+WinForms 空窗体地板 ≈210 ms**
3. **⇒ 3FP 图片模式耗时约为主流查看器的 2.4–2.6 倍**，绝对差距约 **700–740 ms**。

### 8.2 差距的本质

- **不是**因为缺 DLL 走了降级路径（已确认走完整路径）。
- **不是**因为包体大（26 MB 的 WinRT 投影启动时根本没加载）。
- **主要是**因为 3FP 要在启动路径上**建完整 D3D11/Direct2D 渲染栈**（LakeUI 自绘窗口/毛玻璃/阴影），
  这会拉起 **NVIDIA 驱动着色器编译器**（实测 `nvgpucomp64.dll` 在 **≈735 ms** 才进内存）；
  其次是大型托管依赖栈的首触 JIT（154 模块 / 70 程序集）。
- **本质是架构选择**：3FP 用 GPU 合成换取了自绘 UI 与 HDR/广色域能力，代价就是启动要付 GPU 初始化成本。

### 8.3 建议（按优先级）

1. ⭐ **立即做**：重新开启 `PublishReadyToRun` 并**提交**（`FFF.Player.vbproj:11`），
   实测 **−141.9 ms（−10.6%）**、代价 +7.5 MB。这是唯一「一行配置、零代码风险」的杠杆。
   ⚠ 提交前须确认该分支与 `6d5cdb2`（曾因体积优先关闭 R2R）的产品口径一致。
2. ⚠ **值得立项评估**：LakeUI 的 **D3D/D2D 设备懒初始化**（延迟到首帧真正绘制）。
   从模块时间线看，~460→950 ms 这一段是最大单项，但属**跨仓（LakeUI）改动**，
   且可能影响首帧观感，须单独验证后再动。
3. ❌ **不要再投入**：FFmpeg 探测窄化、图标懒加载、去掉 `UseWPF`、改 TFM 瘦身 —— 均已实测为零收益或已被否决。
4. 📌 **产品口径建议**：若用户对「双击图片秒开」敏感，可在**图片模式**下考虑
   「先出窗口/缩略图，再异步完成 D3D 栈初始化」的两段式呈现 —— 需先做用户感知验证。

### 8.4 本次测量的可信度自评

**可信（多来源交叉验证）**：
- 3FP 绝对基线 1212 ms（Lead n=5 + docs/17 n=9，差 0.5%）
- WPV 499–515 ms（Lead n=11 + viewermeasure n=11，独立一致）
- 运行时地板 ≈210 ms（Lead n=9 自建对照）
- 模块时间线与瓶颈归因（3 次重复，顺序与量级稳定）

**方向可信但不可定量**：
- R2R 收益 −141.9 ms（Δ 范围 > 中位数差，落在噪声带内）

**不可信 / 已作废（明确标注，避免被误用）**：
- Lead 首次 WPV 结果 **140.8 ms** —— **假数据**（命中 `RunDLL` 错误框），已由 499.4 ms 取代
- threepfmeasure 首轮 IL 基线 **1539 ms** —— 重载伪影，不作基线
- 所有重载环境下采集的**绝对值**均只可用于相对比较
