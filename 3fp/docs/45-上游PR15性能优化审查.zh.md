## 2. 逐项核实

### 2.1 ✅ `SetMaximumFrameLatency` 的判断是对的

PR 注释称原调用在"无 `FRAME_LATENCY_WAITABLE_OBJECT` 标志的链上无效"。

**核实**：原代码是 `swapChain_->SetMaximumFrameLatency(1)`，即 **`IDXGISwapChain2`** 版本；
该 API **要求**链带 `DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT`（值 64，
见 `dxgi.h`），而 `CreateSwapChain` 从未设置该标志
（全仓搜索 `FRAME_LATENCY_WAITABLE` **0 命中**）。

⇒ **原调用静默失败，延迟限制实际从未生效**。PR 改用 `IDXGIDevice1::SetMaximumFrameLatency`
（设备级、无标志要求）是**正确的修复**，不是在调参。

> 但注意：这是**行为变更** —— 从"DXGI 默认 3"变成"显式 2"。
> 数值 2 是新引入的选择，**缺少依据说明**（见 §4.4）。

### 2.2 ✅ BufferCount 2 → 3

`ResizeBuffers(0, ...)` 传 0 表示**保持现有 buffer 数**，因此两条 resize 路径
不需要跟着改（PR 也确实没改，正确）。

3 buffer 与 `SetMaximumFrameLatency(2)` 配合合理：2 帧在飞 + 1 帧在显示。

### 2.3 ✅ 着色器资源释放

`ReleaseDeviceObjects()` 里新增 `for (auto*& shader : sdrPixelShaders_) ReleaseCom(shader);`
—— 惰性创建的 3 个特化 shader 有正确回收，无泄漏。

## 3. 实测数据

### 3.1 ✅ dav1d 8 → 16 线程：**真实有效**

先怀疑"16 被 `min(hardware_concurrency, 16)` 截掉"，实测本机 **20 逻辑核**，未被截断。
再用探针直接对比线程数：

```
请求 1  线程 -> thread_count=1   30 帧  1112.7 ms (37.09 ms/帧)
请求 4  线程 -> thread_count=4   32 帧   568.3 ms (17.76 ms/帧)
请求 8  线程 -> thread_count=8   33 帧   399.4 ms (12.10 ms/帧)
请求 16 线程 -> thread_count=16  34 帧   364.9 ms (10.73 ms/帧)   ← −11.3%
```

⇒ **改动确实生效且有益**（8K AV1 解码快 11%）。

> 补充：`libdav1d` 的 capability 报 `Threading capabilities: other`（非 frame/slice），
> 一度让我怀疑 `thread_type` 会被忽略 —— **实测证明会生效**，怀疑不成立。

### 3.2 ⚠️ "SDR 上传跳过 present 锁"：收益与风险不成比例

PR 的核心叙事是让 SDR 上传不再等阻塞式 Present。**但实测设备锁等待极小**：

| 场景 | 设备锁等待 | Present 等待 |
|---|---|---|
| 8K HEVC 硬解 | **0.02–0.03 ms** | 872–1049 ms |
| 720p 软解 | 0.01 ms | 388 ms |
| 8K AV1 软解 | 0.02 ms | 1312 ms |

⇒ **锁竞争本来就几乎不存在**（0.02 ms vs 数千 ms 的 Present）。
该改动的**期望收益很低**，却引入了 §5 的并发风险。

### 3.3 ★ 真正的瓶颈：sws 色彩转换（PR 未覆盖）

8K 软解下分解各阶段：

```
纯解码 3 秒素材         1.92 s
解码 + sws 转 BGRA     3.59 s      ← 转换让耗时 +87%
```

而 vsync 侧：8K 硬解能跑到 **58.8 fps**（贴 60Hz），软解只有 **3.7 fps**。
⇒ 8K 软解的瓶颈是**解码 + sws 转换 + 合成**的整条 CPU 链路，
**不是** PR 优化的上传调度。

### 3.4 A/B 的方法学教训

用 `Present 等待` 做 A/B 时，**组内波动（2.1–5.9 ms）大于组间差异**，
两组平均都是 3.75 ms —— 该指标被 vsync 主导，**不适合衡量这类优化**。
改用"固定时长内的呈现帧数"后稳定（229.6 vs 224.8），差异在噪声内。

> 记录此点，避免后续再拿被 vsync 主导的指标下结论。

## 4. 可以改进的地方

### 4.1 着色器特化条件偏窄

```cpp
if (!extensionShader_ && effect == 0 && projection360 == 0 &&
    cachedVideoSettings_.colorMode == 0 && cachedVideoSettings_.transfer == 0 &&
    cachedVideoSettings_.gamut == 0 && cachedVideoSettings_.inputLayout < 3)
```

特化只覆盖 **SDR + 无 360 + 无色彩扩展**。而 3FP 的常见场景里：

- `effect != 0`（缩放/滤镜链）会直接跳过特化；
- `ResizeVideoConversionBuffer` / 缩放路径同样受益于特化但拿不到。

**建议**：把特化维度从"整组参数全等 0"放宽为**按 `inputLayout` 单独判定**，
即只要 `inputLayout` 已知就选对应特化 shader，其余参数仍走常量缓冲。
这样 `effect != 0` 的场景也能命中，覆盖面显著扩大。

### 4.2 WRITE_DISCARD 只覆盖 `layout == 1`（planar）

```cpp
if (input.layout == 1) { /* DYNAMIC + Map(WRITE_DISCARD) */ }
else { /* UpdateSubresource */ }       // layout 2 = NV12 semi-planar
```

而 **`layout == 2`（NV12）恰恰是最常见的**：
- 硬件解码器的共享纹理是 semi-planar（代码里 `input.layout != 2` 直接报错）；
- 多数软解输出在 4:2:0 下也是 NV12。

⇒ **优化命中的是少数路径**。

**建议**：对 `layout == 2` 同样启用 DYNAMIC + `WRITE_DISCARD`（两平面各自 Map）。
注意 `DYNAMIC` 纹理不能作 `D3D11_BIND_RENDER_TARGET`，本例只作 SRV，**可以安全扩展**。

### 4.3 `UpdateSubresource` 在 layout 0 分支仍被使用

```cpp
} else {   // layout == 2
    context_->UpdateSubresource(sourceTextures_[0], ..., frame->data[0], ...);
    context_->UpdateSubresource(sourceTextures_[1], ..., frame->data[1], ...);
}
```

这两次 `UpdateSubresource` 是**每帧两次完整平面拷贝**，8K 下每次约 33 MB。
与 4.2 合并处理即可一并消除。

### 4.4 `SetMaximumFrameLatency(2)` 的数值缺少依据

从"默认 3"改为"2"是**行为变更**（更低的延迟、更少的缓冲余量），
但注释只解释了 API 用法，**没有说明为什么是 2**。
在低端 GPU 或 8K 下，2 帧可能不足以覆盖合成耗时，反而增加卡顿。

**建议**：要么保留默认（不调用即 3），要么把选择依据写进注释并给出测量。

### 4.5 `PresentTimedText` 的锁重构有并发风险（§5 详述）

### 4.6 缺少对"优化是否有效"的可回归度量

PR 自带 `kernel-probe` / `compare-kernel-pixels.py` / `test-kernel-equivalence.ps1`，
但都是**像素等价性**，**没有性能回归门槛**。

**建议**：把 §3 的指标（固定时长内的呈现帧数、sws 增量、设备锁等待）
纳入一个可在 CI 跑的基线，至少能发现"优化后反而变慢"。

## 5. ⚠️ 并发风险：`PresentTimedText` 中释放 `deviceMutex_`

PR 把 `PresentTimedText` 改成：

```cpp
ComPtr<IDXGISwapChain4> retainedChain = swapChain_;
deviceLock.unlock();                                   // ← 释放 deviceMutex_
const auto result = PresentCurrentFrame(retainedChain.Get(), generation);
...
presentLock.unlock();
deviceLock.lock();                                     // ← 重新获取
```

**风险点**：`deviceMutex_` 是保护 D3D 设备与即时上下文的锁。在 Present 等待期间
释放它，意味着**另一个线程可以在此期间向同一 immediate context 提交命令**。

注释称这是为了让播放线程"上传下一帧而不改变这个合成"，但：

- **`presentMutex_` 仍然持有** —— 重配置路径（ResizeBuffers / 换链）确实进不来；
- 但**上传路径只用 `deviceMutex_`**，所以它**确实能**在此期间向 context 提交命令。

在多线程 D3D11 里，**同一 immediate context 从不同线程并发提交**是合法的（runtime 会串行化），
所以这不是数据竞争；但它会让 Present 的等待时间与下一帧的上传**互相干扰**，
且**命令提交顺序变得不可预测**。

**这解释了我们实测的现象**：Present 等待在 A/B 中波动很大（2.1–5.9 ms，组内方差大于组间差异）。

**建议**：
1. 若目的是让上传不被 Present 阻塞，**更清晰的做法**是用**独立的 deferred context**
   做上传，或
2. 保留 `deviceMutex_`，仅让 `presentMutex_` 覆盖 Present（语义更明确），
   并在注释里写明"上传会插入到 Present 的等待窗口内"这一事实与代价。

当前实现**能工作**，但把"锁的语义"和"性能意图"混在一起，后续维护容易出错。

## 6. 建议的改进优先级

| # | 改进 | 收益 | 风险 | 建议 |
|---|---|---|---|---|
| 1 | **`layout == 2`(NV12) 也启用 `WRITE_DISCARD`** | 高（覆盖最常见路径） | 低 | **优先做** |
| 2 | **放宽着色器特化条件**（按 inputLayout 单独判定） | 中高 | 低 | 优先做 |
| 3 | 补性能回归基线 | 中（防退化） | 无 | 建议做 |
| 4 | `SetMaximumFrameLatency` 数值补依据或回退默认 | 低 | 低 | 建议做 |
| 5 | 澄清 `PresentTimedText` 的锁语义 | 中（可维护性） | 中 | 需讨论 |
| 6 | 8K 软解的 sws 转换优化 | **最高** | 高（涉及色彩正确性） | 单独立项 |

**第 6 项最重要但风险也最高**：8K 软解 3.7 fps 的主因是 sws 转换（+87%）。
可能的优化方向（**需谨慎，涉及色彩正确性**）：
- 用 `sws_scale` 的**多线程**（`SWS_CPU_CAPS` / 按行分片并行）；
- 或改走 **GPU 色彩转换**（把 YUV→RGB 放进着色器，彻底省掉 CPU 转换）；
- 后者与 PR 已有的"特化着色器"方向一致，且能**同时**消除 sws 与上传两份开销。

> 这三条都**未实测**，属建议方向，落地前需单独评估与验证。
