## 1. 判词（先给结论）

1. **4K 动图那笔"每帧 89ms CPU"不是解码慢，是解码并行度买出来的**【实测】。同一素材同一节奏要求，线程从策略默认(8+)钉到 1：**CPU/帧 89.29→67.44ms（−24.5%）、私有内存 670.4→447.7MB（−33%）、接缝超额 81.8→55.6ms（−32%），而帧率一格没掉**（9.87→9.90fps，10fps 素材）。1080p 同向：21.35→16.41ms/帧（−23%）、256.1→206.0MB（−20%）、接缝不变、9.98fps。
2. **但纯按尺寸钉线程会翻车**【实测】：6K APNG 钉 1 线程后节奏从 9.30fps 崩到 **5.46fps**，最大间隔 733ms、10 次长停。⇒ 优化必须是"动图起始低档 + 既有负载阶梯按需上爬"，不是新常数表。
3. **视频不能跟着降**【实测】：1080p24 H.264 钉 1 线程 CPU/帧 **5.50 vs 4.39ms（+25%）更差**。⇒ 改法的适用范围必须写死成 `animatedImage_`。
4. **接缝超额随分辨率急剧放大，但"谁的回绕更贵"要分分辨率说**【实测，含两条自纠】：4K 超额 81.8ms(8线程) → 55.6(1线程)——线程越多墙钟解码越短而超额反而越大，"首帧解码暴露在关键路径"这个解释被**否掉**（我在 docs/80 里把它写成机制，现撤回为假设）；6K 复核到 **385ms**（`v4_apng6k_poll20.txt`）。~~反向证据是 WebP 自回绕不吃接缝成本~~ **该句已作废**：4K WebP 实测是**算力不足**（3.4fps、丢 68 帧、长停 10~13 次/轮，只有 53% 落在循环边界），640 WebP 则无回绕帧可判 ⇒ 详见 O4-补。
5. **一个仍未裁的矛盾**【未定】：4K 探针报队列峰值 **8**，而 128MB 预算（`PlayerSession.cpp:50` + `:114-119`）对 33.2MB/帧只允许 **4**；8K 报 **3**（预算暗示 2）——同一公式在 4K/6K 不约束、在 8K 约束。不裁清就不许写"预算失效"。

## 3. 优化项（每条：改法→预期→判据→边界）

### O1 动图起始线程低档 + 复用既有负载阶梯【主力，收益最大】

- **改法 A（零内核改动，先做这个）**：宿主在动图上用现成配置字段——`FFF.Player.Api.h:160-163` 的 `adaptiveDecoderThreads=1`、`minSoftwareDecoderThreads=1`、`maxSoftwareDecoderThreads=8`。今天默认 `adaptiveDecoderThreads=0` ⇒ 走 `:2649-2651` 的固定 8。
- **改法 B（内核，A 生效后第二刀）**：`SelectSoftwareDecoderThreads`（`:2644-2672`）在 `animatedImage_` 时把 baseline 从 `min(hw,16,ceiling)` 改成 **1**，其余不变——上爬由既有 `EvaluateDecoderLoad`（`:2675`）安全网负责。
- **预期**【实测】：4K −24.5% CPU、−33% 内存、−32% 接缝；1080p −23%/−20%；640 −29%/−5%。节奏全档不掉。
- **判据**：4K APNG `CPU/帧 ≤70ms 且 私有 ≤470MB 且 长停=0 且 ≥9.8fps`；6K **必须靠阶梯爬回去**（≥9.0fps 且长停 < 默认档的 11 次，即不许比 A 案更差）；静图/视频逐格零回归（拿 §2 表的视频行当基线）。
  **10-10 追加一条硬判据**（见 §5½①）：必须再加**"同机加负载"臂**——低起点在 4K 于负载下实测会崩到 3.74fps（无负载时 9.90fps），所以验收不能只在安静机器上跑；带牙门禁已能自己抓住它（`LSP_DEC_THREADS=1` 打 4K → rc=1 且红因含"节奏 270.44ms vs 期望 100ms"）。
- **边界（写死）**：只对 `animatedImage_` 生效；不改 `MaximumSoftwareDecoderThreads`、不动 AV1 那条 `largeAv1Frame?16:8` 规则。

### O7 【10-10 判定为不成立，见 docs/83 §4②】队列预算逐帧判定

原文：把 `VideoQueueSaturated()` 的判定点放进 `receiveFrames()` 排空循环里。
**否决理由（实测）**：帧已经从 `avcodec_receive_frame` 取出，在循环里拒绝入队**等于丢帧**，不是"少灌一帧"。
合法的两个替代：① 按 `bytesPerFrame × thread_count` 把**解码器内部的流水线帧**计入内存账（今天 `DecodedVideoQueueBudgetBytes=128MB` 只算队列，这就是 4K 实测 670MB 的成分）；② 动图降线程起点——但必须与 deadline 绑（docs/81 O1 追加条、docs/83 §5）。

### O2 削会话回绕的接缝成本【第二主力】

> **10-10 机制更新（见 docs/82 §3）**：接缝超额 = **重灌 D 帧所需的墙钟**（D = 队列深度 = 解码线程数），
> 同轮配对 APNG 1080p/4K/6K 的比值是 1.00 / 1.16 / 1.44，而 640 是 0.06（被周期余量吸收）；
> GIF 1080p 每帧 CPU 只有 APNG 的 1/2.7 而接缝几乎相同 ⇒ 决定量是**墙钟**不是 CPU 总量。
> ⇒ 新增 **O7（队列预算逐帧判定，把深度压下来）**应先于 O2 实施，并用它验证"接缝随深度线性下降"这一预测；
> 若该预测不成立，O2 的三个候选（不清队列 / 预灌 / 改走 demuxer 自回绕）**全部作废**。

- **先复现再改**：WebP 走 demuxer 自回绕时 excess≈0【实测】，说明代价在会话那套，不在"要不要重解"。开刀前必须用 `3fp/build/apng_seek_repro.exe` 在**当前** FFmpeg（LIBAVFORMAT 63 / 10-07 件）上复跑一次，确认 docs/14 §3 的"每轮 `send=-22` 标记包"是否仍在——在，才不能把 APNG 改回 demuxer 回绕。
- **候选按爆炸半径排序**：
  1. wrap 专用不清队列：`DoSeek`（`:4244` 的 `ClearVideoQueue`）加 `keepQueue` 变体，仅 `FlushAtEnd`（`:4185`）调用；
  2. wrap 前预取下一轮首帧，把那次解码挪进空闲窗；
  3. wrap 时跳过 `RebuildMediaInfo()`（`:4193`，每轮一次全量 JSON 重建）——单独一刀，先看它值几毫秒。
- **预期**：excess 由 81.8ms(4K/默认) 降到 ≤20ms（1080p 的超额已是 17ms 量级，说明"每帧管线量级"就是天花板）。
- **判据**：4K APNG `长停 11/11 → 0`；640/1080p 的 excess **不上升**；`verify_all_samples.sh` 17/17 不新增失败；静图支路逐字节不变（`staticImage_` 分支不许被顺手改到）。

### O3 裁掉那条未定的内存矛盾，再谈预算【前置，别跳过】

- **矛盾**【未定】：4K/6K 队列峰值 8 vs 预算暗示 4；8K 峰值 3 vs 暗示 2。若实现真是"按预算"，4K 不该到 8。
- **不改件的裁断法**：O1 的 670→448MB（Δ222MB ≈ 6.7 帧 33.2MB）已是"深度主导"的一票；但**深度读数本身被 §3-③ 的探针噪声质疑不了**（队列峰不是计时量），所以这一票可用。
- **要改件的那一行**：在 `VideoFrameQueueLimit` 返回处打一条 `queueLimit / bytesPerFrame / size` 日志——**这会动出货 DLL，须先点头**。拿到它才能写"预算在 X 情形不约束"。
- **判据**：要么实测私有内存 ≤ 声明预算 ×1.2，要么把声明值改成与实测一致并在 `:50` 注释写明依据。**不许留"声明 128MB、实测 670MB"这种并存**。

### O4 判据有牙【已完成，2026-10-10】

- **两支探针现在都能判红并给出可区分的退出码**：
  - `loop_stutter_probe`（原 `:286` 永远 `return 0`）补了六条判据 + `SEAM RESULT: PASS|FAIL|NOT-JUDGED（判 N / 红 M / 未判 K）`：接缝超额≤`LSP_MAX_SEAM_MS`（默认 25ms，沿用 docs/14 §2.2）/ 长停(>**1.5× 稳态中位**，探针本来就用相对阈值 `:204-213`，比我 audit 里写死的 150ms 对) / 解码侧丢帧 / 渲染侧合并帧 / 未提前结束 / 节奏（需 `LSP_EXPECT_FPS`，不设就记**未判**）。退出码 **0=全判且绿 · 1=有红 · 2=对象没起来（用法/建窗/Create/Open 失败）· 3=判据一条都没成立**。
  - `anim_cost_audit`（本轮新建）：`AUDIT RESULT` + 0/1/2。
- **有牙实测（`anim-perf/teeth_*.txt`）**：4K APNG **rc=1**（红因 接缝超额 83.3ms、长停 12）；640 GIF **rc=0**；4K WebP **rc=1**（红因只有长停，接缝记**未判**——它 0 回绕）；**17000×64 rc=3「判 0 / 未判 6」**（打不开首帧时不许冒充绿）；不存在路径 **rc=2**。
- **两档变异实测（证明判据不是恒真）**：`LSP_MAX_SEAM_MS=0.01` 打在 640 GIF 上 → **rc=1 红因 接缝超额**；`LSP_EXPECT_FPS=30` 打在 10fps 素材上 → **rc=1 红因 节奏（判 6 / 红 1 / 未判 0）**。
- **自纠一条（我的命令行坑，不是探针的）**：第一次跑判据时用 `echo "### $(basename $f) EXIT=$?"`，**命令替换先执行并把 `$?` 覆盖成 basename 的 0** ⇒ 4K 那条明明 FAIL 却被我记成 EXIT=0。改成"紧接一条 `rc=$?` 存进变量再打印"后同一命令给 **rc=1**。⇒ 凡是取退出码，`$?` 之前不许在同一行里出现别的命令替换。

#### O4-补：整轮重跑（v2/v3/v4）暴露判据自己的两条校准错——都已修，且不是放宽

第一轮 13 档全跑（`v2_lsp_*.txt`，poll=20ms）里，**三条假红来自判据而非产品**（`v4_*.txt` 是修好后的复核）：

| 1080p24 视频判"长停 红"（4 次） | 阈值 61.8ms 与中位 41.7ms 只差 20.8ms < 带 40ms | 同上 | 同上 |

**同时撤回一条上一轮的结论**：v2 见 webp_640 在 10.008s（fIdx=99）出现 165.9ms 长停，我据此准备写"WebP 内部回绕也掉停顿"。**5 次重复批一次都没复现（`v3_*`：0/0/0/0/0）**，同批 gif_640 也只有 1/5 且不在循环边界 ⇒ 记**未复现的偶发**，不写成机制（n<5 的偶发没有资格当因果）。

**新成立的一条**：**4K 动画 WebP 是算力不足，不是接缝问题**【实测 v2/v3】——5 轮长停 **10~13 次/轮**、呈现 41/12s ≈ **3.4fps**、解码侧丢帧净增 **68**、转换 **23.72ms/帧**（APNG 同尺寸 7.81ms）；长停里只有 **41/78 = 53%** 落在循环边界（fIdx ≡ 0 mod 帧数），其余散布全片 ⇒ 主导是每帧管线成本超过帧周期，"回绕方式"只解释一半不到。**对照：4K APNG 能守住 10fps（9.87–9.92）且丢帧 0。**
⇒ 由此修正 §1 判词第 4 条：**不要再说"WebP 自回绕不吃接缝成本"**。两种回绕在 640 都近似无感（会话回绕 +4ms；WebP 无回绕帧），差别要到高分辨率才显现，且届时**两边都掉**（APNG 接缝 +86.7ms；WebP 全程散布 + 边界 53%）。

### O5 高分辨率能力门槛（把 U3 从猜测变成有数）

【实测】本机 10fps 动图守得住的上界：**4K 可以（9.87–9.92fps，代价 0.67–0.89 核）**；**6K 开始掉速（9.30fps）**；**8K 只有 3.01fps、898ms/帧、2.4GB 私有**。⇒ 若要做"动图能力门槛"，档位应按 **bytesPerFrame** 而不是像素数定（WebP 4K 的 YUV 解码输出是 APNG 同尺寸的 1/2.7，代价差一倍以上：转换 11.64 vs 3.68ms/帧）。
本条只登记数字，**不替用户决定要不要设门槛**。

## 5½. 10-10 重跑一轮之后的三条结论修正（都带日志）

**① O1 的"起始低档"不能拍成常数——今天它把 4K 打崩了**【实测 `v5_4k_t1.txt`、`v6_4k_thr1.txt`】

| 4K APNG 默认档 | 9.87fps · 接缝超额 +81.8ms · 1.42→0.93 核 | 9.32fps · +155ms · **1.45 核** |

⇒ 带牙门禁这次自己抓住了：`LSP_DEC_THREADS=1` 打在 4K 上 → **rc=1，红因 接缝超额 901.8ms / 长停 9（最大 1028.96ms）/ 丢帧 49 / 节奏（整窗均值 270.44ms vs 期望 100ms）**；同旋钮打在 640 上 → **rc=0**。

**② 撤回一条**：上一轮"WebP 640 在内部回绕边界掉一次 165.9ms 长停"→ **5 次重复 0/5 未复现**（`summary_v3.json`：webp_640 `[0,0,0,0,0]`；gif_640 `[0,1,0,0,0]` 且那条不在循环边界）。记**偶发未复现**，不写成机制。
