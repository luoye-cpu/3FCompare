逐条 `sed -n 'Np'` 回读源码核过（含 §六 四个 TP 锚点 `:4768`/`:4780-4782`/`:4792-4795`/`:4878-4881`，
四行内容与本账描述逐字符相符）。
文件：实验树 `3fp/kernel/FFF.Native/3FP/Render/VideoRenderer.cpp`，函数 `PlayerVideoRenderer::Render`。

| 事实 | 锚点（改前源码里的原文；改前全文 = `_3fp-fix/laneM/patch/VideoRenderer.before.cpp`） |
|---|---|
| CPU 转换写死「入=出尺寸」 | `scaler_ = sws_getCachedContext(scaler_, frame->width, frame->height, static_cast<AVPixelFormat>(frame->format), frame->width, frame->height, convertedFormat,` |
| 缓冲容量与输出行距同样写死整帧 | `ResizeVideoConversionBuffer(convertedRgb_, static_cast<std::size_t>(width) * height * bytesPerPixel);` 与 `int outputLines[] = { static_cast<int>(width * bytesPerPixel), 0, 0, 0 };` |
| 自适应判定与小尺寸上传指针（只有 directYuv/floatRgb 用得上） | `if (PrepareAdaptiveDownscale(frame, width, height, destWidth, destHeight)) {` 那一段（`uploadPlanes = AdaptivePlanes();`） |
| 纹理按**自适应尺寸**创建 | `const auto pipelineResult = EnsurePipeline(uploadWidth, uploadHeight, input.layout, input.bitDepth,` → `CreateTexture2D` |
| **缺陷**：`else`（layout 0）上传 `convertedRgb_.data()` 且 `SrcPitch` 用**解码宽** | `context_->UpdateSubresource(sourceTextures_[0], 0, nullptr, convertedRgb_.data(), width * bytesPerPixel, 0);` |
| 着色器按上传尺寸采样 ⇒ 「尺寸口径」是对的，只有源缓冲没跟 | `settings.sourceWidth = static_cast<float>(uploadWidth);` |

**为什么 lane L1 对浮点臂的改法（`uploadPlanes[0]/uploadLines[0]`）套不过来**：
`PrepareAdaptiveDownscale` 产出的自适应平面是**解码格式**（rgb24 一类），而 layout-0 纹理是
BGRA / `R16G16B16A16_UNORM`（`EnsurePipeline` 里按 `bitDepth <= 8` 选 `DXGI_FORMAT_B8G8R8A8_UNORM`
与 `DXGI_FORMAT_R16G16B16A16_UNORM` 那两行）——把解码格式平面塞进 BGRA 纹理本身就是错的。
所以这一条只能走「**把缩小折进那次已有的格式转换**」，一次 sws 同时做 rgb24→BGRA 与缩小。

## 四·五、10-bit layout-0（`bitDepth>8` ⇒ RGBA64LE / `outBits=10`）—— 本轮补量

**这条原先记在【未做】里，现已实测**（夹具 `3fp/build/vidtest/photo_4k_16b.png`，

⚠ **读表口径**：判决件的"变了"门限是 `1e-4`，而 **10-bit 的 1 LSB = 1/1023 ≈ 9.8e-4** ⇒

## 六、若自适应政策将来进出货树：必须同带的四刀
