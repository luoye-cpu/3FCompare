## 0. 三条判词

1. **最大的一笔仍在宿主"布局后 → Shown"这段：实测 993.9 ms（n=10，范围 729–1061），且它是
   PR 与 docs/123 都没定位的一段。** 关掉 GPU 预热后同一段降到 **309.6 ms**（n=8），
   而 Attach 段从 415.4 升到 617.3 ⇒ **这笔钱不是新出现的回归，是"预热的设备创建"从 Attach
   挪进了这段**，总量守恒。要把它拿回来，只能让预热**更早**（现在它在 `01_startup_end`
   之后才开始，见 §2），而不是再换一个线程。
2. **静图硬件路的可扩展面只有两个格式：HEIC(HEVC) 与 AVIF(AV1)**；JXR/JXL/WebP/PNG/TIFF/BMP
   在 DLL 里根本没有硬件配置，**它们本来就不付这笔 200 ms**（实测 `k_hwtry_none` 0.3 ms 佐证）。
   本轮我实测 HEIC/AVIF 的配对差 **+135/+32 ms（n=14，p=0.82/0.71）——不显著**，
   与 JPEG 的 −207 ms(p=0.0019,n=10) 不在同一证据等级，**不能照抄 JPEG 那笔的收益预期**。
3. **控件树里"不需要先量就该做"的是纯浪费的三项**：17 个 `New Font` 能并成 2 组、
   字体全树替换走反射又造一遍、量宽不接现成的 `TextFormatCache`。
   **零引用占位（23 个）不能直接删**——它们是可见分隔线，删了改外观（详见 §4.1 更正）。

> **本版相对上一版的两处更正（均由只读盘点证伪，我已抽查到行号）**：
> ① 零引用占位是 **23 个**（JEC2–JEC24），不是 22；且"无风险"是错的，它们全是可见分隔线。
> ② "每个 ModernButton 建 2 Timer + 11 订阅"**一半是假的**：按钮自身构造期建 0 个 Timer；
>    52 个 Timer / 286 条订阅全部来自构造时必调的 `FloatingToolTipController`
>    （`D3D11GpuEngine/FloatingToolTipController.vb:19-20`、`:34-44`）。

## 2. 头号候选：`32_load_end → 40_shown_begin` 的 993.9 ms

### 2.1 它是什么（两条否定已实测）

- **不是我们的语句**：`Form1_Load` 最后一句是 `核心文件检查通过 = True`（`Form1.vb:276`），
  `Form1_Shown` 第一句是 `If Not 核心文件检查通过`（`:412`），两者之间没有应用的代码。
- **不是"预热的钱落在别的段"**：同臂只切 `FFF_NO_GPU_WARMUP=1`（n=8）：

| 段 | 预热开 | 预热关 | Δ |
|---|---:|---:|---:|
| `10_load_begin → 11_attach_done` | 415.4 | **617.3** | **+201.9** |
| `01_startup_end → 10_load_begin` | 355.0 | 224.1 | −130.9 |
| **`32_load_end → 40_shown_begin`** | **993.9** | **309.6** | **−684.3** |
| `30_renderer_started → 31_layout_done` | 153.1 | 75.0 | −78.1 |
| `20_post_probe → 25_layers_done` | 224.1 | 176.0 | −48.1 |
| `73_open_done → 80_event_returned` | 151.6 | 114.9 | −36.7 |

⇒ **预热的设备创建并没有消失，它在两个臂之间换了位置**：关预热时它回到 Attach（+201.9），
开预热时它把 684.3 ms 挪进了"布局后→Shown"。这与 docs/123 §13.1 在 `cc545d2` 上测到的
"关预热 Attach +292.6、该段只 +16.5"**方向相反**。
诚实结论：**两台窗给出了相反的位移方向**，可能的解释是 docs/123 那次负载 ~48% 而本轮 26%、
以及预热线程与 UI 线程的调度关系随负载翻转。**这不是回归，但也不该当成已解决**——
无论钱在哪一段，它都在关键路径上。

### 2.2 为什么值得立项

- 量级 **729–1,061 ms**（10/10 轮都出现），是本 PR 六项累计实测（−309.8）的 **3 倍**。
- 它排在开图之前（§1.2 已用同钟证实），所以**整段都在 T2 关键路径上**。
- 现有的两个解释都已被否定（§2.1），剩下的是"框架显示序列 + 预热线程竞争"这个复合体。

### 2.3 建议的下一步（三选一，按成本排序）

1. **最便宜、无需改产品码**：把预热线程的**起点**提前到 `01_startup_end` 之前
   （现在它在 `MyApplication_Startup` 里，实测 `00→01` 只花 7.2 ms，但由此起的线程
   要等 `10_load_begin` 之后才有 CPU 可用）。判据：该段应随"预热更早"而单调缩短。
2. **需要一次插桩**：在 `D3D_DeviceGlobals.GetD2DDevice` 与 `D3D_DeviceManager.EnsureCreated`
   各贴一对戳，判定 UI 线程是否**真的等**预热线程的锁（这是 docs/123 §13.2 留的
   (a)/(b) 未定问题，本轮仍未定）。
3. **最贵**：WinProc 消息计数或 ETW，拆"框架显示序列"本身。不建议先做。

## 3. 静图硬件路：还能扩展，但收益不可照抄

### 3.1 格式面（代码级判定，证据行号见来源）

| 格式 | 是否进硬件路 | 软件解码器可用 | 夹具 |
|---|---|---|---|
| **HEIC/HEIF = HEVC** | **是**（`PlayerSession.cpp:3570-3573` 无豁免；DLL 有 `hevc_d3d11va`/`hevc_nvdec`） | 是（native hevc） | ✓ `basic/01d_heic_1280x720.heic` 1280×720 8bit 4:2:0 |
| **AVIF = AV1** | **是**（同上；DLL 有 `av1_d3d11va`/`av1_nvdec`） | 是（libdav1d/libaom，支持 10bit） | ✓ `hdr/04_pq_10bit.avif` 1920×1080 10bit 4:2:0 |
| JXR / JXL / WebP / PNG / TIFF / BMP | **否**（DLL 无对应 hw config，循环在 `:3249` skip） | 是 | 多数 ✓ |

**两笔钱必须分开**（这是最容易混的一处）：
- **打开硬件解码会话**（每次 Open 都付 ~200 ms）：`OpenDecoder(...true)` 调用 `:3279` →
  硬件块 `:3107-3142`（`av_hwdevice_ctx_init` + `avcodec_open2`），门控在 `tryHardware :3572-3573`。
- **硬件试解 trial**（近乎免费）：`HardwareDecoderProducesFrame :3334-3464`，只由
  `FFF3FP_HWCAP_TRIAL` 门控；docs/123 §11.1 已证关掉它分布不动。

**豁免只在 DoOpen 生效**——另外两个入口会重新缴费，立项时必须把豁免收成一处：
- 设备重建 `:2068-2072`
- `DoSelectStream :6610-6614`（**不检查** `staticImage_`，也不检查 `stillJpegCpuPolicy`）

### 3.2 实测：HEIC/AVIF 的硬件路**不显著**（如实报告）

`arm_pp_head`（同 exe，只切设置文件 `解码方式` 1=CPU / 2=GPU），n=14 逐轮交替：

| 格式 | 配对 Δ(GPU−CPU) 中位 | CPU 更快 | p |
|---|---:|---:|---:|
| heic | **−60.7**（符号与 JPEG 相反） | 9/14 | 0.7132 |
| avif | +32.2 | 5/14 | 0.8183 |

**分叉证据成立**（`[hwcap] trial` 中位：两格式 `A=0 / B=2`，非零轮 `0/14` vs `14/14`）——
硬件路确实进了，**但那笔钱在 n=14 上没被量成收益**，分布 −611…+637（双峰）。
对比 JPEG（n=10，−207.4，p=0.0019，0/10 反例）——**A/B 级证据，不能等同**。
n=6 那轮曾给 +135/+136，样本一大就掉回噪声（与 docs/123 §11.2"份额是分布不是中位数"吻合）。

⇒ **立项建议**：把 `IsJpegCodec` 扩成 `IsStillHwBypassCodec`（含 HEVC/AV1）**是成立的代码机会**，
但要**先补 ≥20 轮配对**证明收益，并**先补像素闸门**（4:2:0 档），再谈落不落。
**不要拿 JPEG 那笔的 207 ms 当这两格式的预期。**

### 4.1 控件树：计数、可动性、以及一条新线索（已抽查到行号）

`Form1.Designer.vb` 的 `InitializeComponent`（24–1356 行，全文 1432）里：

- **`New` 共 328**：其中控件 67 个（`ModernButton` 26、`JustEmptyControl` 29、`ModernMenuItem` 27、
  `ModernPanel` 9、`ModernContextMenu` 5、`TrackBar` 2、`HtmlColorLabel` 1、`ThisIsYourWindow` 1），
  其余是 `Padding/Size/Point` 等值类型（73/68/67 等）。
- **属性赋值 886 条**（`Me.` 出现 **0** 次，全是无限定名写法）：`MB_` 按钮 **409**、
  编号 `JEC_` **144**、`MCM_` 96、`ModernPanel` 73、`MenuItem` 57、`TrackBar` 46、命名 JEC 26、标签 10、其它 25。
  另有 `Controls.Add` 64、`Items.Add` 27、`Suspend/ResumeLayout` 9/9。

**新线索（这才是 212 ms/73 ms 的候选解释，但份额未量）**：
- `ModernPanel.SetValue` 每改一条属性就 `Me.PerformLayout()`（`ModernPanel.vb:80-85`）
  ⇒ 73 条面板赋值 = **73 次 `PerformLayout`**。
- `ModernButton.SetValue` 每改一条就 `请求GPU渲染()`（`ModernButton.vb:717-722`）
  ⇒ 409 条按钮赋值 = **409 次 `D3D_InvalidationRouter.RequestRender` 入队**。
  已抽查 `:732-734` 确认为**入队**（`RequestRender`），不是同步绘制——所以它是"失效路由开销"，
  不是 409 次重绘。**这条不给数字不能立项。**
- 26 个按钮构造时必调 `FloatingToolTipController`（`ModernButton.vb:49`），
  它建 **2 个 Timer**（`:19-20`）+ **11 条 AddHandler**（`:34-44`）⇒ 合计 **52 Timer / 286 订阅**。
  按钮自身构造期建 **0 个 Timer**（另两个计时器在点击/助记键路径内 new-dispose）。

**可动性分级**：

| 改动 | 可独立回退 | 风险 |
|---|---|---|
| 17 Font → 2 组 | 是 | 低，但**按用途分池**：`ModernContextMenu.Dispose` 会 Dispose `MenuFont/DescriptionFont`（`:1657-1664`），共享会让第二个菜单用到已释放 Font |
| 量宽接 `TextFormatCache` | 是 | **无**。类已存在（`D3D_D2DInterop.vb:918`），先例 `AgentRoom.vb:424`；只改 `播放器界面呈现器.vb:427` 一处 |
| 字体全树替换改直赋 + 共享 Font | 是 | 低（现逻辑 `Catch` 吞异常） |
| 剪辑区间子树（20 控件/205 赋值）延后 | 是 | **高 NPE**：`播放器剪辑区间控制器.vb:33-39` 对 7 控件 `ThrowIfNull`、`:47-48` ctor 内 new 进度条并 `Controls.Add`、`Form1.vb:261-269` 另 10 条 Click 订阅 ⇒ 必须连带改 ctor |
| ModernButton/ToolTip 的 52 Timer/286 订阅懒建 | 是 | 中，**全局**（影响所有窗体含录制器），回归面大 |

**零引用占位更正**：全树（排除所有 `*.Designer.vb`）零引用的是 **23 个**（`JustEmptyControl2`…`24`），
不是 22。但**它们不是"无风险可删"**——全部是可见分隔线（`886×1`/`886×2`/`2×40`/`2×32`，
`BackColor 80/0/0/0` 或 40/220/220），各带 6 条赋值 + 1 `New` + 1 `Controls.Add` + 1 个 `Container`。
直接删 = **掉 1–2 px 分割线，改产品外观**。正确做法是换成容器自绘/单个便宜分隔件（属"减"不属"删"）。
必须保留：`JustEmptyControl1`（`设置.vb:315-317` 直接读写，删则 NullReference）+ 5 个命名 `JEC_*`
（`Form1.vb:391/392/1052`）。注意 `Form设置_*` 里的同名控件是**各自窗体**的，不构成对 Form1 的引用。

## 5. 排序建议（若下一批只动三处）

1. **`32_load_end → 40_shown_begin` 的 993.9 ms**（本轮最大，占 T2 的 40%）；第一步只做
   "预热起点提前"这一个零风险改动，用同臂 `[LT]` 复测该段是否缩短。
2. **三项纯浪费（低风险、可独立回退）**：17 Font→2 组分池、字体控制改直赋/共享、
   量宽接 `TextFormatCache`。这三条语义不变，不需要先量。
3. **HEIC/AVIF 静图豁免**：先补 ≥20 轮配对与 4:2:0 像素闸门，再决定；顺手把豁免从
   `DoOpen` 收成一处（否则 `:2068` / `:6610` 两个入口会重新缴费）。

**需要先量才能立项**（份额未量，别先动）：剪辑区间子树延后（20 控件/205 赋值）、
ModernButton 的 52 Timer/286 订阅、面板 73 次 `PerformLayout` 与按钮 409 次失效路由。
