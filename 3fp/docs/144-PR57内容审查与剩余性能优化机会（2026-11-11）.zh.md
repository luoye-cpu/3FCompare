## 一、总判词

- **稳态解码/呈现已无大头**：docs/136 #15 的实测（1080p60 GPU 硬解 decode 2.8% 单核、4K10bit scalePass 3.2 ms、软解 0.14%）在 PR 后依然成立；PR 的 seek/预取改动动的是**打开与跳转的延迟**，不是稳态吞吐。**不要**再立项"省解码/省上传时间"（上传重头是字节数 4K 24.9 MB/帧，不是时间）。
- **本 PR 自身最值钱的机会在预取子系统**：它新引入了一条自解码侧车（静图）、一条小助手进程（WARM/PROBE）和一套缓存，但**侧车解码不受主链路线程预算约束**、**helper 的 PROBE 产出零消费者**、**静图浏览时 helper 通道整段是白付 I/O**。这三条是"确定性浪费 + 契约违约"，不是调参。
- **打开路径的存量区间仍可用**：静图尾部 `av_seek_frame`+flush 仍在首像素路径上（HEIC/AVIF 硬件路 ~100 ms 级，docs/136 #5）；`WarmDevice` 仍在 `FFF3FP_Create` 里同步付 150–170 ms（docs/136 #9）；JXL `find_stream_info` 378.9 ms 从未定因（docs/136 #10）。
- **交互残量里有一处"中"**：逐帧步进 `FFF3FP_StepFrame` 的 **+1 帧仍走完整 seek + 重解 GOP 前缀**（剪辑区间方向键的常见路径，单步 ~60–170 ms），而顺序前进本不需要回卷关键帧（KR-11）。其余内核项是每帧/每事件级小钱（`GetBuffer`+RTV、叠加层拆建、Auto-HDR 每帧 `SetHDRMetaData`、跨卡回读兜底等，§4.3）。
- **宿主侧没有可观的每帧浪费**：UI 100 ms 刷新只做"变了才写"、快照是 608 B 结构体 P/Invoke、双耳状态回读在内核侧全是原子读（实测无锁无分配）。宿主侧真正值得动的是三件"设置页/管道"项：**清理缓存档在 UI 线程强制全代 GC**（HS-2）、**为一个动画帧率旋钮跑完整字体管道**（HS-3）、**常驻 UI 计时器**（HS-7）。
- **LakeUI 九旋钮不许诺收益，且有 4 个旋钮效力与文案不符**：3689f77 只是把 3FUI 的引擎旋钮**设置化**，默认档逐位等于旧行为（文字渲染 Outline 等）；更实际的问题是 `SsaaBucketSize` 在宿主引用的 LakeUI 树里**没有读取方**（分桶是硬编码），`Brush/TextFormat/FontResolveCacheLimit` 降档**不回收已有缓存**（见 HS-1）。这不影响"默认无收益"的结论，但影响设置页的可信度。

## 四、仍可用的优化（按 预期收益 × 成本 排序）

### 4.1 预取子系统（本 PR 新引入，机会最集中）

> 发行形态差异：散装发布携带 `FFF.PrefetchHost.exe`（`发布3FP.ps1` 的 `$Required` 已列入）；**单文件发布形态不带**（`发布3FP单文件.ps1` 白名单只有 `FFF.Player.exe`），此时 helper 通道缺失、只剩进程内静图解码线——PF-2/PF-3/PF-7/PF-8/PF-9/PF-10 只对散装形态有意义，PF-1/PF-5/PF-6 两种形态都适用。

**PF-1 · 静图侧车解码完全绕过线程预算（高收益 / 低风险）**
`FFF.Native/3FP/Prefetch/PrefetchService.cpp:221-231`：`avcodec_alloc_context3` 后**没有** `thread_count`/`thread_type`，FFmpeg 取 `av_cpu_count()` 自动值（AV1 走 libdav1d 同理）；`worker_` 线程（`:317`）也未降优先级。主链路 `PlayerSession.cpp` 的 `DecoderThreadBudget()` 特意留 4 个线程余量（`ReservedPlaybackThreads=3`+`SchedulerHeadroomThreads=1`），侧车把这条不变量整条绕过：首次打开静图会连发 6 次解码（`前后预取控制器.vb:60-64` 的 `{1,-1,2,-2,3,-3}`），在 20 线程机上拉起约 20 个 worker，正压在开图入场动画/缩放帧率上。修法：`thread_count = min(4, budget)` + `thread_type = SLICE`（小帧可分档）+ worker 线程 `BELOW_NORMAL`。验证：E1 `--chain` 臂 + 进程线程峰值 + 呈现计数间隔分布。
（`STATUS.md:486` 已记「`FFF3FP_PREFETCH_HIT=0` 不等于没有预加载（worker 仍在解码邻居抢 CPU）」——本条就是把它落地。）

**PF-2 · helper 通道在静图浏览时是死重：`TakeProbe` 零消费者 + WARM 与侧车解码重复（高收益 / 低风险）**
`PrefetchService.cpp:673-697`：helper 车道对 plan 内**每个**路径（含 `i=0` 当前文件）同步发 WARM→PROBE。但全仓 `TakeProbe` 只有定义（`:820`）与写入端，**没有任何读取者**（`STATUS.md:483` 自认「`TakeProbe` 仍只有写入端」）；静图浏览时 WARM 也与 `DecodeFirstStill`（`:178`）重复读同一文件。代价确定：每条 plan 最多 7×8 MiB WARM（`PrefetchHostMain.cpp:39`）+ 7 次 `avformat_open_input` PROBE（`:223`）+ 14 次同步管道往返，全部**排在**真正有收益的静图解码（`:697` 起）之前。修法：`STILL_BROWSING` 时跳过 helper 车道（或只对视频邻项 WARM）、helper 从 `i=1` 起、PROBE 要么接消费要么删。验证：`FFF3FP_PREFETCH_TRACE=1` 数 warm/probe 行；`FFF3FP_PREFETCH_HOST=0` 对照 `[prefetch-hit] presented` 时间差。

**PF-3 · `probes_` 每代次清空，丢弃仍在新 plan 内的结果（中收益 / 低风险）**
`PrefetchService.cpp:764`：`probes_.clear()` 的理由是"stale POD 不能跨代次"，但 `PruneToPlanLocked` 已按路径剪枝、POD 自带指纹，`routes_` 就是"有意不剪"的先例（`:440-442`）。若保留 PROBE，应改为按路径保留（否则向前一步就全量重开容器）。

**PF-4 · 单次 3 s 超时 = 整会话永久降级（中收益 / 低风险）**
`PrefetchService.cpp:465-470`：`ReadResult` 失败 ⇒ `MarkHelperFailure()` 置 `helperDisabled_ = true` 单向闩（`:468`），`EnsureHelper`（`:559`）从此直接 return。8 MiB 顺序读在 `IoPriorityHintVeryLow`+后台模式+Job 25% CPU 硬顶下，HDD/网络盘/杀软扫描场景一次就可能超 3 s；降级后"预热下一个视频"通道整会话静默消失，用户只感到变慢。修法：连续 N 次失败才禁用、按任务类型分档超时、指数退避重启。

**PF-5 · 内存预算用压缩字节判定，单帧可越界（中收益 / 中风险）**
`PrefetchService.cpp:703-726`：门槛是 `fingerprint.sizeBytes > budgetBytes_/2`（压缩后字节），预算吃的是**解码后**字节；108 MP 静图解码后 162–324 MB > 默认 256 MB 预算，而 `EnforceBudgetLocked`（`:402`）的 `while` 在缓存空时不驱逐 ⇒ 插入后 `cachedBytes_ > budgetBytes_` 成为合法状态，下一张再把刚解好的巨帧驱逐，形成"解了又扔"。修法：用 `codecpar` 的 `w×h×4` 先估上限，超预算跳过或只留最邻近一张；验证 `FFF3FP_PREFETCH_TRACE=1` 的 `action=still bytes=` 与 `GetStatus().cachedBytes/budgetBytes`。

**PF-6 · 取消粒度 = 一个完整任务，快速连按时有效预取被旧任务挡住（中低收益 / 中风险）**
`PrefetchService.cpp:674`：`Cancelled()` 只在任务边界检查；进入 `WriteTask`+`ReadResult` 后无法中断，helper 的 `DoWarm`（`PrefetchHostMain.cpp:186-193`）读满 8 MiB 或 EOF 才返回，`ReadResult` 的 3 s 读循环也不看 `cancel_`（`:496-513`）。修法：把 WARM 拆成 1 MiB 子任务（协议已按 task 粒度）+ 共享 generation 原子字。

**PF-7 · `FFF3FP_PREFETCH_FASTFORMAT` 默认关，且 probesize 8 MB 是"放宽"不是"收窄"（中收益 / 待实测）**
`PlayerSession.cpp:3446-3449`：命中后设 `probesize = 8 MiB`、`max_analyze_duration = 2 s`。FFmpeg 默认 `probesize` 约 5 MB、`max_analyze_duration` 5 s ⇒ 8 MB 实际是**放宽**，只有 2 s 是真收窄；注释与代码语义不一致。该臂 opt-in 的原因（媒体信息 JSON 对拍未做）正是兑现前必须补的：E1 已有"16 配对行×18 字段 0 差异"的对拍基建。验证：先 `av_opt_get_int("probesize")/("max_analyze_duration")` 打真默认，再按 `--chain` 臂 A/B + JSON 逐字节 diff。

**PF-8 · Critical 档的 `helperStopRequested_` 无人消费（低中收益 / 低风险）**
`PrefetchService.cpp:447-452`：`EvaluatePressure()` 在 `Critical` 置 `helperStopRequested_=true`，但不 `cv_.notify_all()`；唯一消费者是 worker 被唤醒后的 `ShouldStopHelper()`（`:661`）⇒ 小助手要等**下一次 SetPlan** 才退场，而内存压力的典型场景恰恰是"用户不动了、正在播"。修法：Critical 分支末尾 `cv_.notify_all()`（`StopHelper` 已 noexcept 且可重入）。

**PF-9 · `ReadResult` 用 `PeekNamedPipe`+`Sleep(2)` 轮询（低中收益 / 低风险）**
`PrefetchService.cpp:487-513`（`:501-504`）：管道是阻塞模式，直接 `ReadFile` 即可阻塞等待；`Peek`+`Sleep(2)` 只换来最多 2 ms/结果的额外延迟与固定唤醒，且 `WriteTask`/`ReadResult` 各取一次 `mutex_` 只为读 HANDLE。与 PF-2 叠加时 14→0，单独改收益上限几十 ms/plan。

**PF-10 · WARM 窗口/邻居深度硬编码，与码率无关（待实测 / 中风险）**
`PrefetchHostMain.cpp:38-39` 固定 8 MiB；`前后预取控制器.vb:60-64` 固定图片 6 层、视频 2 层。8 MiB 对 60 Mbps 是 1.1 s 内容、对 3 Mbps 是 21 s；协议里没有 `bit_rate`（`PrefetchProtocol.h` 只有 codecId/width/height），**自适应在当前协议下不可表达**。属设计缺口，先做 PF-1/PF-2 再谈。

**PF-11 · 路由读取在"服务已关"时也照付一次文件 stat（低收益 / 极低风险）**
`PlayerSession.cpp:4272-4277`：每次 `DoOpen` 调 `TakeUnsupportedRoute`；`PrefetchService.cpp:851-860` 的 `StatFile`（`GetFileAttributesExW` + UTF8 转换）排在 `disabled_` 判定**之前** ⇒ 预取被宿主关掉/未启动时照样付一次冗余 I/O 再必然 miss。修法：先查 `Enabled()/disabled_` 再 stat（断言命中语义不变）。验证：`FFF3FP_PREFETCH_ROUTE=0/1` 下同夹具打开耗时 A/B（µs 级，属清理项）。

### 4.2 音频直通 / 渲染

**AU-1 · 暂停恢复/设备恢复先建 PCM 渲染器、随即被直通替换（中高收益 / 低中风险）**
`PlayerSession.cpp:2232`、`:2261-2264`（`ResumeAudioRenderer`）、`:2284`、`:2304`（`RecoverAudioDevice`）：先用 PCM 格式独占打开一次端点，随后因 lane 仍 `Engaged` 而 `RearmForReopen()`，下一个音频包触发 `RecreateAudioRendererWithBitstream` 把刚建好的渲染器 reset 掉，再用 IEC SubFormat 打开一次（含最多 4 次 `IsFormatSupported`）。**每次 pause→play / 设备热切换付 2 次独占 Initialize + 1 次销毁 + 一整轮格式探测**，且驱动刚释放就重开最易撞 `AUDCLNT_E_DEVICE_IN_USE`，把正常恢复误判成回退。修法：恢复前先取 `ptLane_.Format()`，Engaged 时直接走 bitstream 重建（失败再退回现路径）。验证：`RecreateAudioRenderer`/`EngagePassthrough` 加计数 trace，一次 pause→play 目标 2→1；或 WPR 数 `IAudioClient::Initialize`。

**AU-2 · 直通接管在 worker 包循环里同步打开独占端点（中收益 / 中高成本）**
`WasapiRenderer.cpp:291-296` 等待 `initializedCondition_` 无超时；调用方 `PlayerSession.cpp:6020/6032` 在包分派路径内先 `audioRenderer_.reset()`（Stop 会 join 渲染线程）再同步等新渲染器枚举+探测+Initialize。等待期间 session worker 停摆，**视频呈现同一线程一起卡住**——播放中切音轨会现形为一次可见停顿。修法：打开移出 worker，或保留旧渲染器直到新渲染器 ready（独占语义要求先关后开，需状态机配合）。

**AU-3 · burst 队列不吃缓冲池，分配发生在队列锁内（低中收益 / 低风险）**
`WasapiRenderer.cpp:231-244`：PCM 路径有 `reusableBuffers_` 池（注释明说是为了避免每帧堆分配），直通路径每 burst 新 `vector` + 全量拷贝，且在 `mutex_`（填充线程每设备周期都抢）内做。TrueHD ≈3.05 MB/s（~50 次分配/s）、DTS-HD ≈3.08 MB/s（~94 次/s）。拷贝本身 ~0.3 ms/s，收益主要在填充线程尾延迟确定性。修法：照 PCM 池化，或生产侧双缓冲直接 move。

**AU-4 · 每呈现帧 3 次 lane 锁、每音频包 2 次（低收益 / 低风险）**
`PlayerSession.cpp:7650-7654`（每帧调用点 `:7519`）：`UpdateAudioDiagnostics` 里 `ptLane_.Engaged()` 两次 + `EngagedCodec()` 一次，24–120 fps 即 72–360 次/s；`HandlePassthroughPacket`（`:5556-5560`、`:6826-6829`）每包再 2 次。同一把锁在打包侧被 `Pack()`（`AudioPassthrough.cpp:143-151/244-256`）横跨模块回调持有 ⇒ API 线程的 `GetAudioPassthroughState`（4 次锁）理论上可被一次 pack 阻塞。CPU 可忽略（<10 µs/s），属**抖动**项。修法：`Arm/Disarm/Engage/Fallback/Rearm` 处同步一个 `laneEngaged_` bool/atomic，热路径零锁；验证跑 `--360-identification-regression` + `audio_binaural_probe` 防读数漂移。

**AU-5 · 直通沿用 PCM 的 600 ms/2.4 s 缓冲目标（低中收益 / 中风险）**
`PlaybackPerformancePolicy.h:22-27`（默认 `AudioInitial=600000`、`AudioMaximum=2400000`）；`WasapiRenderer.cpp:1073-1076` 把 burst 字节按 link 帧折算成时间 ⇒ TrueHD 队列可堆到 ~1.8 MB/~30 个 burst，seek/结束整批丢弃。修法：直通单独目标（如 250 ms）；**前提**是用 `audio_buffer_probe.exe` 验 underrun 不退化（直通 underrun 是往 burst 中间灌零，比 PCM 静音更糟，不能盲降）。

**AU-6 · 时钟锚点每个回调多拿 2 次数据锁（低收益 / 低风险）**
`WasapiRenderer.cpp:1432-1437`、`:1681-1689`：锚点只在"重置后第一个 burst"变一次，但 `updateMediaClock` 与 `ReleaseBuffer` 后每回调都无条件拿一次 `mutex_`（未启用直通时也付）。修法：发布成原子对，或只在 `bitstreamPtsAnchored_` 翻转时抄进 clock 状态。

**AU-7 · 每个 burst 都 `SetEvent` + `PublishRuntimeDiagnostics`（低收益 / 低风险）**
`WasapiRenderer.cpp:249-250` 每 burst 唤醒一次；独占且 client 已启动时消费端到 `:1513-1529` 只 `continue`，白付一次 `GetPosition` + 诊断（含再拿锁）。修法：只在未启动或队列 0→正时唤醒；诊断节流。

**AU-8 · 帧界归一化对"容器已帧对齐"的路径是每包一次整帧复制（低收益 / 低中风险）**
`PlayerSession.cpp:6072-6084`：`av_parser_parse2` 每音频包整帧写一遍 parser 缓冲；代码自认只对病态 splitter 必要（`:5841-5849`）。TrueHD/DTS-HD 3 MB/s 时是 3 MB/s 纯冗余写。修法：按 demuxer 名短路（matroska/mov 直通），保留 mpegts 等走 parser；必须有帧界证据。

**AU-9 · （宿主）调试图层每帧 `AllocCoTaskMem(256)` + P/Invoke（低收益 / 低风险）**：`播放器会话.vb:862-864` ← `播放器信息图层呈现器.vb:423`（仅调试可见）；复用会话级缓冲即可。

### 4.3 内核视频 / 呈现（按"触发概率 × 量级"排序）

**KR-1 · 多适配器回退可能把解码器放到异卡 ⇒ 每帧 4K P010 跨卡回读（高·若触发 / 低风险，本 PR 新引入）**
`VideoRenderer.cpp:7532-7552`（本 PR 新增）：`frame->format == AV_PIX_FMT_D3D11 && !OwnsD3D11Texture(...)` 时走 `av_hwframe_transfer_data` 同步回读——每帧 4K P010 ≈25 MB **GPU→CPU**，随后再 CPU 上传。它是跨设备 `CopySubresourceRegion` 非法的正确性兜底（不能删）；问题是它与本 PR 默认开的"多适配器回退"（`PlayerSession.cpp:484-492`、`DecodeDeviceSelection.cpp:59-95` 会把 renderer 以外所有硬件适配器追加为候选）**叠加后完全静默**：一旦异卡 D3D11VA 建成功，稳态从 0.1 ms/帧级变成 8–15 ms/帧，用户只看到"多卡机器 4K 掉帧"。修法：加一次性 trace（同 `FFF_CUDA_INTEROP_TRACE` 家族），多适配器回退时优先选与 renderer 同卡的 D3D11VA 设备；不改回读语义。验证：强制 `preferredAdapterIndex` 指向第二张卡 + 4K10bit 夹具，用 `3fp/tools/cuda_interop_probe` 的每帧 `uploadCopy100ns/videoUpload100ns` 对比"同卡"臂。

**KR-2 · 字幕/歌词"全空即拆"把 D2D 设备 + atlas + 精灵管线一起拆掉（中 / 中风险）**
`VideoRenderer.cpp:9389-9403`：`if (allEmpty && timedTextAtlasTexture_ != nullptr) ReleaseTimedTextResources(false);`；该函数（`:6938-6976`）除 5 个 slot 的全尺寸纹理外，还 `ReleaseCom(d2dContext_/d2dDevice_)`、`timedTextLayouts_`（≤512 个 `IDWriteTextLayout`）、`timedTextBrushes_`、精灵 atlas+Lru、精灵 VS/PS、instance buffer；`:3636-3640` 的 `ResizeBuffers` 成功后也整拆。⇒ **字幕/弹幕/歌词每出现一次、以及窗口拖动 resize 的每一帧，都付一次 D2D 设备+全尺寸画布+atlas 重建**（单次 ms 级，且发生在 `presentMutex_`/`deviceMutex_` 临界区内，直接推迟本次 flip）。稳态播放不付，只在 overlay 边界付。修法：`allEmpty` 只释放 slot 纹理，保留 D2D/atlas/精灵管线，加"空闲 N 秒/设备重建/分辨率变化"才整拆（`timedTextAtlasHdr_/timedTextResourcesHdr_` 失效条件改成显式比较 HDR 档）。验证：`GetTimedTextStatus` 的 `spriteCacheHits/Misses`+`backBufferAcquisitionCount` 配合 `lyrics_probe`/`mks_subtitle_probe` A/B。

**KR-3 · Auto-HDR 的 SDR-on-scRGB 档：每帧 `SetHDRMetaData(NONE)` + 每帧 `EnsureSwapChain`/`OutputSupportsHdr`（中 / 低风险）**
`VideoRenderer.cpp:7013-7022`：SDR 分支在 `HdrMetadataChanged` 变更闸**之前**就 `SetHDRMetaData(DXGI_HDR_METADATA_TYPE_NONE)` 并 return ⇒ 每帧一次显示配置类调用、且无"上次已声明 NONE"的记忆；`:3255-3268` 的 `previousCapabilities = hdrProcessor_.State().display` 在 750 ms 缓存判断**之前**执行；`:7694-7699` 的 `stableSdrChain` 快路只覆盖纯 SDR 链，scRGB(HDR) 档每帧走 `EnsureSwapChain`。⇒ 10-bit SDR 在 HDR 屏 + `sdrScRgbMode=1` 时，每帧 1 次 `SetHDRMetaData` + 1 次 `GetClientRect` + 3 次 `HdrProcessor::State()` 加锁拷贝。修法：给 SDR-NONE 分支加 `hdrMetadataValid_ + 全零` 短路（换链/`InvalidateHdrMetadataCache` 清），`EnsureSwapChain` 加 `(actualMode_, 输出位数, 显示器, displayCaps 世代)` 快照短路。验证：现成的 `setHdrMetaDataCalls/setHdrMetaDataSuppressed`（`:7303-7304`）——改前 `calls≈帧数`，改后 ≈1；画面用 `hdrpeak_probe`/`display_grid_probe` 确认不变。

**KR-4 · 每 present 一次 `GetBuffer`+`CreateRenderTargetView`（待实测 低中 / 中风险）**
`VideoRenderer.cpp:3816-3832` 的注释断言"flip 模型下不可跨 present 缓存 RTV"——**结论过强**：链 `BufferCount=3`（`:3672`），`GetBuffer(0)` 在两次 Present 间身份稳定，以 `ID3D11Texture2D*` 为键的 3 项 RTV 缓存可有 (N-1)/N 命中率。调用点：`:8129`（视频帧）、`:9335`（图层呈现）、`:9066/:9148/:9413`（回读/清屏）。单次若 5–20 µs，60 fps 下 0.03–0.12% CPU；240 Hz + 双 present 路径 ×4。修法风险：缓存必须持有背缓冲引用，并在 `ResizeBuffers`/`CreateSwapChain`/`ReconfigureSwapChain`/`ReleaseDeviceObjects` 之前显式清空（否则 `ResizeBuffers` 报 `DXGI_ERROR_INVALID_CALL`），键带"链世代"。验证：先按 `counter_cost_microbench` 形状在真链上量 `CreateRenderTargetView`；频率用 `backBufferAcquisitionCount` 对齐 `swapChainPresents`。

**KR-5 · CUDA→D3D11 Import：三平面各自 `streamSynchronize`，可合并为一次（低中 / 低风险）**
`CudaD3D11Interop.cpp:384-424`：`for plane` 循环里每个平面 `memcpy2DAsync` 后立刻 `streamSynchronize`，把本可在同一 stream 背靠背排队的拷贝串行化，并多付两次 `cuStreamSynchronize` 驱动往返（4K 10bit 每帧）。正确形态：先 map 全部（已是）→ 三次 async copy 全下发 → **一次**同步 → unmap 全部；`state_->stream == nullptr` 的同步分支（`:410-412`）保持原样。验证：`3fp/tools/cuda_interop_probe` 的 `uploadCopy100ns` 改前/后同夹具同秒数对比（判带宽，不判端到端 fps）。

**KR-6 · `WarmDevice` 只建设备：链 + 全套管线仍在首帧（低中 / 中风险，存量项）**
`VideoRenderer.cpp:2859-2864` 的 `WarmDevice()` 实际只有 `EnsureDevice()`（`:3145-3234` 的 `D3D11CreateDevice`+适配器日志）；**docs/121"WarmDevice 建全套渲染管线"的表述应更正**。链（`CreateSwapChainForHwnd`+3 back buffer+`SetColorSpace1`）在首次 present 才建（`:3652-3687`），5 shader+3 sampler+3 CB+动态曲线纹理+33³ LUT 在 `EnsurePipeline` 首调才建（`:4007-4100`）。带窗 `FFF3FP_Create ≈398 ms` 的 150–170 ms 只是设备创建，剩下的首帧成本仍可前移：窗口在 Create 时已知（`SetWindow` 先行），链可按 client rect 预建；shader/CB/LUT 与源尺寸无关可预建。风险：此时 HDR 档/源位深未知会先建 SDR 链（首帧判 HDR 会多一次 reconfigure，现有重建路径可覆盖）；`WarmDevice` 持 `deviceMutex_` 且 `noexcept`，拉长持锁需确认 Open 线程无等锁。验证：`startup_profile.ps1`/`probe_startup_path.ps1` 的 `k_bind_render_done`/`k_first_present` 戳位。

**KR-7 · 每帧 3 次无条件 `UpdateSubresource`（SDR 下内容恒定）（低 / 低风险）**
`VideoRenderer.cpp:7978-7986`：动态曲线纹理 + 两个常量缓冲每帧上传；无动态元数据/无辅助层时三者是同一全零结构（`:7938-7939`、`:7957-7963`）⇒ 60 fps 下 ~180 KB/s 无效写 + 3 次驱动拷贝。修法：`dynamicUploadDirty_` 脏标记（`SetInjectedMetadata`/`RefreshHdrShaderInputs`/HDR 状态变化时置位，与 `:7363-7371` 共用）。风险：漏置位会卡曲线。验证：`upload_bench`（headless，隔离 Present）量 `UpdateSubresource` 单次成本；SDR 与 HDR10+ 两夹具都跑。

**KR-8 · 每帧微项：`FFF_EL_TRACE` 的 `GetEnvironmentVariableW` + 重复 `HdrProcessor::State()` 拷贝（极低 / 极低）**
`VideoRenderer.cpp:7974-7977` 每帧一次 Win32 环境查询（同函数 `:7724-7728` 的 `FFF_CUDA_INTEROP_TRACE` 已用 `static const bool` 缓存，风格不一致）；一帧内 `HdrFrameState` 按值拷贝约 4 次、各过一次 `HdrProcessor::mutex_`（`:7932`/`:7013`/`:7553` 等，`hdrState` 就在手里）。收益 <1 µs/帧，但零风险、减少呈现线程跨模块加锁点。

**KR-9 · 每帧诊断/快照发布无节流（低）**
`PlayerSession.cpp:7511-7522`：每次 `PresentVideoFrame` 都写快照字段并 `PublishSnapshot()`（608 B 拷贝 + `snapshotMutex_`），叠加 AU-4 的 3 次 lane 锁；24–120 fps 属可接受，若要收做"脏才发"，不砍字段。

**KR-10 · 首帧 Present 仍走 `Present(1,0)` 等 vblank（低 / 低风险）**
`VideoRenderer.cpp:9255-9256` 稳态 `Present(1,0)`；docs/136 #7 的"首帧 `Present(0,0)` 不锁 vblank（−2~5 ms，撕裂一帧风险）"仍未做，只在打开后第一帧生效。

**KR-11 · 逐帧步进 +1 帧仍走完整 seek + 重解 GOP 前缀（中 / 成本中高，改行为）**
`PlayerSession.cpp:1613/1635-1670/8113`：`FFF3FP_StepFrame` → `SuspendAudioRenderer(true)`（独占时 Stop+销毁渲染器）→ `DoSeek(当前位置+1帧)` → `DecodeUntilSeekTarget()`，其中 `av_seek_frame(AVSEEK_FLAG_BACKWARD)` 回卷到 ≤目标的关键帧、再重解整段 GOP 前缀（NONREF 跳帧只省约一半，实测单步 62–170 ms）。**+1 帧不需要 seek**：目标帧落地后 demuxer 就停在下一帧包上，`videoFrameQueue_` 里通常还留着后续帧可直接上屏。宿主剪辑区间模式的方向键直接打到这里（`播放器剪辑区间控制器.vb:151` → `播放器控制器.vb:960` → `播放器会话.vb:396`）。修法：`DoStepFrame` 加"顺序前进"分支（读包→解码→`PresentVideoFrame`，维护 frameIndex/framePts/快照，不调 DoSeek 即不动 `timelineGeneration`/时钟，收尾复用现有 seek 收尾），可加开关。收益：每次 → 从"GOP 前缀 30–60 帧解码"降到 1 帧。验证：`FFF_SEEK_TRACE=1` 看 `packets=`（改前≈GOP 前缀帧数，改后≈1）+ `FFF_SEEK_SKIP=0/1` A/B；`seek_floor_probe --step` 校下限。

**KR-12 · 每帧 `CanPresentHardwareFrameDirectly` 跨设备 COM+锁检查，渲染器入口又做一遍（低中 / 低风险）**
`PlayerSession.cpp:7382` 每上屏帧无条件调；实现（`VideoRenderer.cpp:3353-3359`）`texture->GetDevice` + `deviceMutex_`，随后 `VideoRenderer.cpp:7536-7538` 渲染器自身的同款守卫再 `GetDevice`+再取同一把锁。240 Hz 下约 0.5–1k 次锁/s，真风险是与呈现线程争 `deviceMutex_`（`deviceLockWait100ns` 可见）。修法：open 时已知解码是否就在播放适配器上（`decodeAdapterIndex_` vs `adapterPlan.rendererIndex`），存 bool，只对非播放适配器解码的帧逐帧复查；不直接删会话侧那遍（它保护 gamut/静图保留步骤）。

**KR-13 · 播放态三处 `Sleep(1)/Sleep(2)` 忙轮询，每次唤醒跑完整 tick 前导（低中 / 低风险）**
`PlayerSession.cpp:5418/5436/5441`（另 `:5269/:5355`）早退在 `:5308-5337` 整套前导（pump 计数、`TryReleaseAudioAfterVideoPresentation`、`DrainInternalAudio`、`TryCompletePlaybackPreroll`、`UpdateDrainedAudioClock`、`UpdateBitRateForPosition`、`EvaluateDecoderLoad/EvaluateVideoSkipRung`）与 `:5413` 的 `PumpVideoPresentation` **之后**；4K 稳态队列饱和是常态 ⇒ worker 以 ~500–1000 次/s 唤醒跑完前导再睡 1 ms。同文件 demux 饱和路径已有正确写法（`:6434-6442` 的 `commandCondition_.wait_for(...)`，注释原文"instead of polling every millisecond and spending an idle core on look-ahead"）。修法：三处 Sleep 换同一把 `mutex_`+`commandCondition_.wait_for(到队列头到点)`，先只改 `:5436`；**必须同时校准** `pumpIterations_` 等按 tick 计的窗口口径（`:5308-5318`）。收益：0.3–1% 单核 + 1000 次/s 上下文切换。

**KR-14 · seek 链上每帧先做完整节拍记账、最后才判"未到目标即丢"（低 / 低-中风险）**
`PlayerSession.cpp:7043-7100`（内容周期 `av_rescale_q`、cadence min/max、`SetContentFramePeriod100ns`、`RaiseMediaFrameRateCeilingHz`）在 `:7132-7134` 的丢弃判据**之前**执行；4K HEVC GOP 60–120 帧都白做。修法：判据提到 cadence 段之前（索引维护 `:7101-7125` 必需，只能重排不能搬走；丢弃帧不再喂 `lastVideoFrameDuration100ns_` 需确认正常帧路径不受影响）。收益 ~0.1 ms/次 seek，价值更在"以后往这段加 per-frame 诊断不会再落在丢弃路径上"。

**KR-15 · trace 开关每帧/每包/每次 seek 都查环境变量（极低 / 零风险）**
`PlayerSession.cpp:5453`（每包）、`:7091/:7475`（每上屏帧）、`:8525/:8553`（每次 `DecodeUntilSeekTarget`）、`:5295`（seek 期间每 tick）的 `GetEnvironmentVariableW` 未缓存；`:7475` 还排在 `(elCompositionRequested || auxiliaryFrame)` 之前 ⇒ 无辅层也每帧付。同文件本 PR 已示范正确写法（`PrefetchHitEnabled/PrefetchRouteEnabled` 的 `static const bool`，`:510-545`）。修法：全部改 `static const bool`；**注意** `FFF_SEEK_PREVIEW/BATCH/SKIP` 的"以 '0' 开头即关"解析语义必须原样保留（docs/143 P3 边界），静态缓存后进程内改 env 不再生效（探针惯例是子进程带 env 启动，需在 `tools/README` 注明）。

**KR-16 · 多适配器解码计划每次硬件解码器打开都重建（待实测 / 低-中风险）**
`PlayerSession.cpp:3903` 每次 `OpenHardwareVideoDecoder` 都 `BuildDecodeAdapterPlan`：`CreateDXGIFactory1` + 最多 16 次 `EnumAdapters1/GetDesc1`（`DecodeDeviceSelection.cpp:59-95`），而该清单只在"播放适配器 + 全后端 + 全 codec 都拒绝"时才用得上；默认多适配器回退开（`PlayerSession.cpp:484-492`）⇒ 开文件/视频换轨/硬件回退重试都付。**读数分歧**：A1 结构推断 0.5–2 ms/次，A2 判 µs 级（`DeviceAdapterIndex()` 在 `device_==nullptr` 时提前返回 -1）⇒ 属**待实测**项，先量再决定"推迟到首适配器失败后"或"每会话缓存"。

**KR-17 · 图片缩放降采样链键含目标尺寸（决策项；docs/79 §5 已立账、未实施）**
当前树 `PrepareScaledVideo` 的复用判据仍含 `scaledOutputWidth_ == outputWidth`（`VideoRenderer.cpp:5705-5721`），而目标 = 缩放后的框 ⇒ `zoomedWidth < 源宽` 区间内每格滚轮整链重建；85af3fa 只调节拍，没动键。docs/79 §5 给的是 C0（加计数证明）→C1（目标量化到 2 的幂/半尺寸阶梯 + 末级自由比）。**注意分歧**：视频侧同代码路径，C1 有"末级精度"与视频缩放铁律 2 的门控风险，必须先 C0 拿到"每格重建"的读数再决策；A2 审查认为"重开属决策项而非新机会"，与本文"可用区间"不冲突。

**KR-18 · 精确 seek 的剩余量只能靠"改行为"换（决策项，非纯优化）**
`STATUS.md:559-564`：4K 长 GOP 单次 seek 已降到 63–173 ms（−55~63%），连点 6 次 1677→905 ms；**物理下限 = GOP 内参考帧数 × 单包成本**，再快只能牺牲精确性：落关键帧（10–30 ms）或"先出关键帧画面、后台精确到位"两段式——两者都改行为，未实施。另：seek 期间解码量对 `decodedVideoFrames` 不可见（`seekDecodedFrames_` 只进 `FFF_SEEK_TRACE`，`PlayerSession.h:824-827`），属**度量债**（P3），影响后续任何 seek 优化的验收。

### 4.4 宿主（无每帧路径；机会在"旋钮效力"与 UI 线程同步阻塞）

> 宿主侧没有"每帧"：画面由内核交换链线程绘制，host 只有 8 / 100 / 200 ms 三条定时器链。PR 新增的 per-tick 工作（双耳状态、直通文本、呈现计数）单项都在 µs 级，找不到高收益项。
> 3FUI 纪律落实情况：引擎旋钮设置化**已落**（9 组 GlobalOptions + 帧率字体管道）；但"上层使用纪律"只搬了一半——脏标记合并刷新/节流/BeginUpdate/反射热路径查找表在宿主侧仍是零散既有实现（媒体信息/播放列表有 BeginUpdate、图片浏览 32 ms 节流、AI 字幕 10 s 采样），`字体控制.vb:66/77/84` 的每控件实时 `GetProperty` 就是反例。这不产生大钱，但说明"移植完成"只对引擎旋钮那一半成立。

**HS-1 · LakeUI 九旋钮中 1 个完全无效、3 个"降档不回收"（PR 内容审查发现，中收益：可感知落差 / 低风险）**
- `设置.vb:486-495` 写入 `GlobalOptions.SsaaBucketSize`，但宿主引用的 LakeUI 树里 `SsaaBucketSize` **只有声明**（`third_party/LakeUI/LakeUI/D3D11GpuEngine/GlobalOptions.vb:142`），真正的离屏尺寸取整是硬编码：`D3D_WindowCompositor.vb:266-270` 的 `Dim bucket = If(value <= 256, 16, If(value <= 1024, 32, 64))` ⇒ **分桶档 8 个档位零效果**。
- `BrushCacheLimit / TextFormatCacheLimit / FontResolveCacheLimit` 是纯自动属性（`GlobalOptions.vb:182/186/190`，无 setter 逻辑）；`TrimToCurrentLimit`（`D3D_D2DInterop.vb:866/1049`）全树**零调用点** ⇒ 把画刷档 256→8、字体档 128→0 **不会释放任何已有条目**，直到下一次新建。相对地 `GpuCacheBudgetBytes/CpuCacheBudgetBytes` 的 setter 会立即 `TrimToBudget(immediate:=True)`（`GlobalOptions.vb:156-177`）——九旋钮里只有这两项"写下去就立刻见效"，而它们同时在 **UI 线程同步回收**。
- 结论：默认档逐位等于移植前（无默认收益，符合预期）；但设置页文案暗示这些是性能/内存开关，其中 4 项实际无效或延迟生效。**要么补 LakeUI 侧 setter/接入 SsaaBucketSize（跨仓），要么在文案上标"仅影响后续分配"**。
- 验证：画刷档 8↔256 后观察缓存条目数不降；SSAA 分桶 32↔1024 用 RenderDoc/ETW 看 SSAA RT 尺寸不变。

**HS-2 · "清理缓存"两档在 UI 线程强制全代 GC + 等终结器 + `EmptyWorkingSet`（中收益 / 低中风险）**
`Form设置_设备与性能.vb:133-145`：`SelectedIndexChanged` 里同步 `GC.Collect(GC.MaxGeneration, GCCollectionMode.Forced, True, True)` + `GC.WaitForPendingFinalizers()`（+ 档 1 的 `EmptyWorkingSet`）。本进程有 Vortice/D2D COM、pinned 载荷表与大对象堆，强制 blocking+compacting 全代 GC 通常几十~几百 ms，且要与 finalizer 线程上的 COM 释放串行 ⇒ 用户点"清理缓存"时设置页可见冻结。修法：GC/EmptyWorkingSet 挪线程池、完成后 `BeginInvoke` 回 UI 提示；D3D 资源清理（档 2-4，`CleanupD2DResources`）必须留 UI 线程。验证：Stopwatch 包 handler 量 UI 阻塞，改后对比。

**HS-3 · 为一个"动画帧率"旋钮跑完整字体管道（低中收益 / 低风险）**
`字体控制.vb:64-84`：逐控件 3 次 `GetProperty`（Font / AnimationFPS / DropDownAnimationFPS，带 NonPublic 还会走基类链）+ `AnimationFPS` 的 `GetValue` 装箱，无按 Type 的 `PropertyInfo` 缓存；`DropDownAnimationFPS` 是无同值守卫的 `?.SetValue`（与"值没变就不写"注释自相矛盾）；`New Font(...)` 每控件每次新建（**已实测**：把 `Control.Font` 设成等值新实例会短路，不触发 FontChanged/重排，所以只是白分配）。改帧率（8 档）每次都触发 `更新所有控件字体属性()` 全树遍历。修法：`Dictionary(Of Type, PropertyInfo())` 缓存；只推 FPS 时跳过 `New Font`；DropDown 加同值守卫。验证：Stopwatch + `GC.GetAllocatedBytesForCurrentThread` + 控件计数。

**HS-4 · 信息图层新增直通行：每次重建都 P/Invoke + 256 B 非托管分配（低收益 / 低风险）**
`播放器信息图层呈现器.vb:423-426` → `播放器控制器.vb:1223-1237` → `播放器会话.vb:856-876`：`Marshal.AllocCoTaskMem(256)` + `FFF3FP_GetAudioPassthroughState`，即使"未接管"也照分配照调用；`显示操作信息` 每次调用都会立刻重建整层，图片缩放期间提示可到 ~10 Hz。修法：先看 `快照.音频直通已接管`（快照已带该字段），False 直接空串；名称按（编解码, 突发数）缓存；缓冲复用。验证：`音频直通图层文本` 计数 / PerfView 分配。

**HS-5 · 信息图层与媒体信息窗"先全量重建、后比较签名"（低收益 / 低风险）**
`播放器信息图层呈现器.vb:256-273`：每 tick 新建行表/文本段/字符串、`CreateGraphics()`、逐段测量、逐命令**逐字符**哈希，最后才比较签名并可能 `Return` ⇒ "内容没变"时该省的一样没省（5–10 Hz × 20–30 行）。`Form媒体信息.vb:76-107,141` 的 200 ms 刷新同形（9 个标签重拼 + 每条流 24 字段 LINQ 签名，本 PR 把签名加宽了 6 个字段）。修法：值提供器加脏标记（关键字段元组比较）再决定重建；签名先比便宜标量。

**HS-6 · 图片缩放动画 8 ms 定时器与呈现门叠加（低收益 / 低风险）**
`播放器图片浏览控制器.vb:152-157`：`Interval=8`（125 次/s），而 P0-2 呈现门在 60 Hz 屏上会丢掉约一半下发；提示串却每 tick 都插值分配（真正下发受 0.1 s 门控）。弹簧按真实经过时间推进（`:374-377`），降低定时器频率不改手感。修法：间隔按显示器节拍取（`显示器节拍.vb`）；提示串挪到门控通过之后。

**HS-7 · 常驻计时器与时基未做空闲全停（低收益 / 低风险）**
`播放器界面呈现器.vb` 的 100 ms `PrecisionTimer` 在 `启动()` 后常驻；`PrecisionTimer` 只要在跑就持有进程级 `timeBeginPeriod(1)`（`third_party/LakeUI/LakeUI/无界面组件/PrecisionTimer.vb:56-61,75-87`）。docs/136 #2 的"空闲全停 + 时基释放"仍未做 ⇒ ~10 ms/s 唤醒 + 全系统时钟精度——**功耗项，不是吞吐项**。修法：暂停/最小化/图片静止时停 UI 计时器。

**HS-8 · 前后预取控制器每次列表事件整表拷贝（低收益 / 低风险）**
`Core/前后预取控制器.vb:48-85` 每次事件都 `播放列表.取得项目()`（= `项目.ToArray()`，`播放列表.vb:84-88`）再 `String.Join`+`StringToCoTaskMemUTF8`。事件驱动非热路径；1000 项约 8 KB/次。修法：播放列表暴露"计数 + 按索引取项"，只用当前索引 ±3 窗口。

**HS-9 · 其余宿主项判无收益（不做）**：快照 608 B P/Invoke（100 ms 一次，内核只锁 `snapshotMutex_` 拷一份）；`GetPresentationCounter`（静态解析一次 + 内核原子读）；双耳状态每 tick 读两次（内核 4 个原子读，~20 次/s，可忽略）；360 元数据归一化（每次打开一次）；`色彩表述`（纯 Select Case 零分配）；`设置.实例对象`（静态属性）；100 ms tick 里的控件写入（WinForms/LakeUI 有同值短路）。
