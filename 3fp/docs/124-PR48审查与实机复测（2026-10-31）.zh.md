### 3.1 第 6 项 JPEG 策略的像素：**不是"逐位相同"，是 ≤5/255**

PR §17.3 写"两臂 `max|d|=0.000000`、端点值逐位相同"。本机用同一件 exe、只切策略，JPEG 夹具：

| 层 | 不同像素 | max |

| 画面区（掩 UI） | 122,955 / 1,139,795 = 13.05% | **5/255** |
| 舍入级 1–2/255 | 117,413 | — |
| 3–4/255 | 5,520 | — |
| 5/255 | 22 | — |
| ≥6/255 | **0** | — |
| α 通道 | 全等 | 0 |

**这必须说清楚归因，不能直接判"PR 错了"**：PR 的"逐位相同"读数来自

两者是不同仪器，量到不同层是合理现象。
⇒ **结论**：解码出来的帧确实一致（PR 探针口径可信），但**呈交到屏幕的 CSS 颜色换算路径

量级相近（本机 5/255 略大）。**建议 PR 把措辞从"逐位相同"改成"解码帧逐位相同、
上屏后画面区 ≤5/255 舍入级"**，否则读起来像是"用户看到画质零变化"，而实测是"零可见变化"
——后者需要用户裁决的那条闸门才真正关上。

JPEG 夹具下 base(head 前五项做硬件路) vs 策略臂的整窗差异里，最大那团

## 4. 代码面审查：发现与结论

### 4.1 启动期优先级与内核 `PlacementPolicy` 的时序（PR 自述"未实测"，本次实测了）

**代码事实（成立）**：`PlacementPolicy.cpp:476-480` 在**首次** `OnPlaybackStart` 采样
`baselinePriorityClass_`；`ApplyTier` 降级时（`:586-591`）按该基线恢复。
宿主 `Form1.vb` Shown 后 600 ms 无条件设 `NORMAL`（常量，不是"恢复进入前的值"）。
⇒ **若首次播放启动落在 Shown+600 ms 之前，基线被记成 HIGH，此后 Boost 释放会把进程恢复成 HIGH。**

**实测（`arm_pr`，视频/静图两条路径各测 8 秒）**：

| 路径 | PriorityClass 轨迹 |
|---|---|
| 视频（进播放泵） | `Normal@11ms → High@173ms → …High… → Normal@2983ms → 一直 Normal 到 8s` |
| PNG 静图（不进泵） | `Normal@0 → High@720 → High@1424 → High@2140 → Normal@2848 → 一直 Normal` |

⇒ 两次都**正常降回 Normal 并保持**。原因：本次负载下 tier 未升到 Boosted，
内核的"恢复基线"分支没被触发，所以陈旧基线没有机会发作。
⇒ **判词：PR 说的缺口是真的（代码路径成立），但需要"基线=C(HIGH) + 触发 Boost + 释放"
三个条件同时成立才发作，本机未复现。** 属**真缺陷、可按 PR 计划独立修**（PR 已声明"保存进入前的值
并据此恢复"是后续独立改动），**不阻塞本次合并**。

另注意一个 PR 未提的细节：降回是**常量 NORMAL**，故用户以 `start /high` 启动会被无条件改回
Normal——PR 已列在风险第 1 条，与上述同源，同一笔修。

### 4.2 GPU 预热的 LakeUI 弱双检（PR 风险第 2 条）

PR 说 `_initialized` 非 Volatile、且 `factory1.CreateDevice` 只持 `_lock` 不持 `_factoryLock`，
与 UI 线程经 `GetRoundStrokeStyle` 走 `_factoryLock` 操作同一个 SingleThreaded factory 可并发。

**本次独立复核的结论：表述不准确，当前实现不构成可复现的并发违规。**
- `D3D_DeviceGlobals.GetD2DDevice` 的双检第一判在锁外、第二判在锁内，`_initialized` 置 True 在锁内；
  缺 `Volatile` 属**规范瑕疵**，不是本次引入（此前也有读者，只是都在 UI 线程）。
- `GetD2DFactory1` 走 `_factoryLock`，UI 线程的 `GetRoundStrokeStyle` 也走 `_factoryLock`
  ⇒ **factory 本身的访问是被同一把锁串行的**；
- `CreateDevice` 在 `_lock` 内调 factory，此时若 UI 线程也在动 factory 会各自串行在 `_factoryLock` 上。
⇒ 风险从"可并发违反 SingleThreaded"降级为"跨线程缺乏显式内存屏障（弱 DCL），规范瑕疵"。
**建议 PR 改写这条风险的措辞**（现在这段会让评审以为有硬并发缺陷），并把它降为"建议后续加
`Volatile.Read/Write`"，不阻塞合并。

### 4.3 P2（无窗时不做 sws）的正确性复核

我把"提前返回会不会改变 headless/像素读回语义"这条查了：
`VideoRenderer.cpp:7219-7222` 提前返回处只 `++presentedVideoFrames_` 就 return，
**不进 sws、不取设备锁**；而 `PlayerSession.cpp:3790/3812/3828/3836/3854` 那五处判据
全部以 `presentedVideoFrames_` 的**前后增量**衡量解码是否推进 ⇒ 语义等价，不会把正常路径误判成失败。
`ReadVideoPixelRegion` 走的是**纹理读回**（`videoRenderer_.ReadPixelRegion`），不读 `convertedRgb_`
⇒ 无窗会话本来就读不到像素，提前返回不改变这条。**P2 安全。**

PR 列的"无窗路径不再暴露 sws 失败"属实（`scaler_==nullptr` 的错误推迟到有窗首帧），
属可接受的诊断信息后移，不影响正确性。

### 4.4 O3-A 保留句柄

- 实测分叉确认：base 的 exe 里完全没有那三个 `FFF_NO_*` 字面量，head 有 ⇒ 血统无误。
- `属于内核搜索目录` 对裸文件名直接返回 True，与内核 delay-load 的实际搜索序
  （`FfmpegRuntime.cpp:95-112`：FFF.Native 目录 → exe 目录）**一致**，不是"不校验"的漏洞——
  裸文件名经程序集解析落在程序目录，与内核同址。
- 候选排序改 `ThenByDescending`，与内核 `LoadMatchingModule:75-87` 的
  `CompareStringOrdinal(...) CSTR_GREATER_THAN` 取字典序最大**一致**，属对齐而非新增语义。

  `DllNotFoundException` 两条仍 Catch ⇒ 实际漏的是更罕见的第三方异常，影响一个句柄，可接受。
