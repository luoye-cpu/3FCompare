# 53 · 音频缓冲池分析

> 问题：「分析一下音频缓冲池的情况」
> 方法：读所有权路径 + 拆解 `Buffered100ns` 的两个分量 + 实测（`tools/audio_buffer_probe.cpp`）
> 日期：2026-10-07

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 有缓冲池吗？ | ✅ **有**，且是**两级**：应用侧 PCM 队列 + WASAPI 已提交样本 |
| PCM 队列会反复分配吗？ | ❌ **不会** —— `reusableBuffers_` 复用，稳态零分配 |
| 有容量上限吗？ | ✅ **有** —— `MaximumReusableAudioBufferBytes` / `MaximumReusableAudioBuffers` |

| 内存会泄漏吗？ | ❌ **不会** —— 复用池 + 队列出队即归还 |
| **发现的问题** | ✅ **IAMF 时间戳 208 倍误差**导致排队 **207 秒静音**（已修复，见 §3） |

## 1. 两级结构

### 1.1 应用侧队列（`PlayerWasapiRenderer::queue_`）

```cpp
std::deque<AudioChunk> queue_;                          // 待提交的 PCM
std::deque<std::vector<std::uint8_t>> reusableBuffers_; // 复用池
std::size_t queuedBytes_;
```

- **分块 SPSC 队列**，避免 vector 反复搬迁；
- 长编辑间隙用 `AudioChunk::silenceBytes` 表示**逻辑静音**，而不是分配几秒的零填充 PCM
  —— 这是正确的设计，静音不占内存；
- 出队时若容量在阈值内则**归还复用池**（`MaximumReusableAudioBufferBytes` / `MaximumReusableAudioBuffers`）。

### 1.2 设备侧（WASAPI）

`pendingMediaFrames_` = 已提交给端点、但尚未播放的样本数，由设备时钟位置推算。

### 1.3 `Buffered100ns` 的定义

```cpp
frames = queuedBytes_ / outputBlockAlign_ + pendingMediaFrames_;
return frames * 10^7 / outputSampleRate_;
```

⇒ 语义是**"解码 PCM 领先端点的时长"**，不是硬件固定输出延迟。两边都是**帧**，单位一致 ✓。

---

## 2. 生产端节流

`PumpPlayback` 中的门控：

```cpp
if (iamfDecoder_ != nullptr && !delayAudioUntilVideo &&
    audioBuffered < TargetAudioBuffer100ns) {   // 1.2 秒
    PumpIamfAudio();
}
```

⇒ 队列**没有硬上限**，但生产端在缓冲 ≥1.2 秒时停止灌入。
**正常情况下这就够了** —— 设备每 10ms 左右消费一次，生产者永远追不上。

> ⚠️ 这个假设在 §3 的缺陷下**失效**：单帧就能注入 17.7 秒静音，
> 一次性把队列顶到 207 秒，远超 1.2 秒的目标。

## 3. ★ 发现并修复：IAMF 时间戳 208 倍误差

### 3.1 现象

`bufferedAudio100ns` 对 IAMF 报出荒谬数值：1.02 秒素材报 **207 秒**。

### 3.2 定位过程（**前两次测量无效**）

| 步骤 | 做法 | 结果 |
|---|---|---|
| ① | 看 `position100ns` / `audioPosition100ns` | ❌ 两者都由 seek 写入，测不出差别 |
| ② | 拆分 `Buffered100ns` 两个分量 | ✅ `pendingMediaFrames=2379`（正常）、`queuedBytes=79,575,008`（≈9.9M 帧 = **207 秒**） |
| ③ | 插桩 `Enqueue` | ✅ 每帧注入 **17.7 秒静音** |
| ④ | 插桩解码器 | ✅ 解码器**完全正确**：`sampleRate=48000`，每帧推进 0.0853 秒 |

### 3.3 根因

`QueueAudioFrame` 按**流的 time_base** 解释帧 PTS 并重采样：

```cpp
av_rescale_q(timestamp, stream->time_base, {1, 10'000'000})
```

而 raw IAMF 解复用器的 `time_base = 1/48000`。

**IAMF 解码器交出的 PTS 已经是 100 纳秒单位** ⇒ 被**二次换算**：

```
0.085 秒 × (48000 / 10^7)^-1 = 0.085 × 208 = 17.7 秒/帧
```

渲染器把这种前向跳变当作**编辑点**并合成静音补齐（这个逻辑本身是正确的）。

### 3.4 影响

- 207 秒**真实静音 PCM** 被推给端点；
- 播放停在文件末尾**等它排空**；
- 12 声道音轨全程背着一个 200 倍大的队列；
- **在立体声端点上完全听不出来** —— 静音就是静音。

### 3.5 修复（`9df3783`）

在入队前换算到流的 time_base，使**所有编解码器共用一套约定**：
AVFrame 上 PTS 用流 time_base，100 纳秒只在 `StreamTimestampPosition100ns` 之后出现。

| | 修复前 | 修复后 |
|---|---|---|
| 缓冲 | **207.27 秒** | **0.04 ~ 1.36 秒** |
| 每帧静音注入 | 17.7 秒 | **无** |

## 4. 实测

| 场景 | 缓冲 | 说明 |
|---|---|---|
| 720p 视频（普通路径） | **0.13 秒** 稳定 | 正常 |
| IAMF 7.1.4（1.02s）修复后 | **0.04 秒** | 正常 |
| IAMF 5 分钟素材修复后 | **0.15 ~ 1.14 秒** | 在 1.2s 目标内波动 ✓ |
| IAMF seek 到 180s 后 | **1.36 秒** | 正常 |

⇒ 修复后各级都在 `TargetAudioBuffer100ns`(1.2s) 附近，符合设计。

## 5. 与视频侧帧池的对比

| | 视频帧池 | 音频缓冲池 |
|---|---|---|
| 结构 | `videoFramePool_`（frames） | `reusableBuffers_`（byte buffers）+ `queue_` |
| 上限 | **有**：128 MB 预算 → 2~8 帧 | **无硬上限**，靠 1.2s 目标节流 |
| 长间隙表示 | 不适用 | `silenceBytes`（逻辑静音，不占内存）✓ |
| 复用 | 出队归还池 | 出队归还池 ✓ |
| 显存 | 硬件解码 surface（docs/50） | 不涉及 |

**一个可考虑的改进**（低优先级）：给 `queue_` 加一个**硬上限**（如 4 秒），
超限时丢弃最旧的块。当前 1.2 秒的生产端节流在正常情况下够用，
但 §3 表明**一旦时间戳异常，队列可以被瞬间顶到几分钟** —— 硬上限是这种故障的兜底。

**未实施的原因**：修复 §3 后已无触发路径，而硬上限在正常路径上引入丢帧风险，
需要先证明它不会在重负载下误伤。属"防御性改进"，非当前缺陷。
