## 2. 事件与现象

### 2.1 发现背景

2026-10-31 将 upstream/main（75efcf8，含 PR #49）合并进启动性能分支（PR #48，九笔提交，合并提交 05152d1）后，按推送纪律做启动冒烟：宿主加载样例图片后 ~417 ms 进程退出。

### 2.2 崩溃形态（"三无"）

- 退出码：`0xC0000602`（有符号 -1073740286，STATUS_FAIL_FAST_EXCEPTION；注意与 `0xC0000409` STATUS_STACK_BUFFER_OVERRUN 相区分）
- stdout / stderr：**全空**（无托管异常文本、无 CLR fatal error 横幅）
- Windows 事件日志（Application，含 .NET Runtime / Application Error 来源）：**无记录**
- WER（ReportArchive / ReportQueue）：**无报告**
- 确定性：8/8 轮全部早退，时刻稳定在 ~417 ms（Form1_Load 尾段～Shown 早期）
- 抓栈尝试全部失败：CoreCLR `DOTNET_DbgEnableMiniDump=1` + `DOTNET_DbgMiniDumpType=2` 实测对 fastfail 路径**不生效**（fastfail 不走 SEH/Vectored 分派）；WER LocalDumps 注册后亦未产出（WER 未收到请求）

> 该形态是典型的 **native/CLR 层显式 fastfail**（`RaiseFailFastException` 系），且被静默吞掉——排查上几乎不留下任何软件层痕迹，最终只能依靠**产物血统对照**定位。

### 2.3 影响面

- 仅影响**本机合并构建**（2026-10-31 之后用坏产物建出的宿主臂）；不影响 PR 合入 upstream 后的上游构建（上游以各自干净状态重建 LakeUI）
- 崩溃窗口极早（~417 ms），任何启动性能测量（PR #48 的全部 T1/T2 数据）在坏产物上**不可采信**

## 3. 根因结论

### 3.1 三个产物的血统档案（唯一可靠事实）

LakeUI.dll 全部产物均产自**同一源码提交** `2be4a02`（2026-10-12，此后仓内零提交、工作树干净）：

| 产物 | 字节数 | SHA-256 前 12 位 | 产生方式 | 行为 |
|---|---|---|---|---|
| 旧产物 | 5,345,280 | `cc7c27cb62a1` | 10/29 前后干净构建 | ✅ 正常（a8934a2 系全部实验臂在用） |
| **坏产物** | **2,383,872** | **`fdf72b52205b`** | **10/31 合并期间增量编译**（体积骤降 ~2.96 MB 且无任何源码变更） | ❌ **启动 fastfail** |
| 新产物 | 2,375,168 | `b692def599f4` | 11/1 12:41 前后干净重编 | ✅ 正常（arm_final 在用） |

- 坏产物体积比旧/新正常产物**小约 2.96 MB**，与另外两个产物差异巨大——高度疑似增量编译时**部分类型/方法未正确编译进映像**（不一致 IL），运行期首次触及缺失成员时 CLR 内部一致性检查 failfast
- 三产物 **AssemblyVersion 均为 5.113.0.0**：文件版本比对、程序集绑定日志全部失效，字节级血统核对是唯一区分手段

### 3.2 坏产物进入实验链的路径

宿主工程对 LakeUI 的引用为固定 HintPath：`<3FP仓根>\..\..\LakeUI\LakeUI\bin\Debug\<LakeUITfm>\LakeUI.dll`（符号链接指向兄弟仓 `3fp/LakeUI`）。因此：

- 10/31 起兄弟仓 `bin\Debug` 内的增量产物（坏）被此后**每一次主仓建臂**原样带入（arm_merged、arm_reviewfix、arm_e2、E1/E2/E3r1 全部中招）
- 建臂血统核对惯例只覆盖 `FFF.Native.dll`（内核），**LakeUI.dll 从未被核对**——坏产物因此畅通无阻地混入全部"05152d1 系"实验臂

### 3.3 判定性证据（因果闭合）

| 实验 | 臂配置 | LakeUI | 结果 |
|---|---|---|---|
| E3r2 | 宿主 05152d1+9项修复，revert b0f1bd6（worktree 建臂） | 旧好 `cc7c27cb62a1`（5,345,280） | ✅ 5/5 存活 |
| E3r3 | 同 E3r2，**臂内覆盖坏产物** | 坏 `fdf72b52205b` | ❌ 2/2 崩（同码） |
| **E3r4** | **upstream 原版宿主 75efcf8（无 PR #48 任何代码）** | **坏 `fdf72b52205b`** | ❌ **2/2 崩（同码）** |
| E3r5 | 同 E3r4，换新产物 | 新好 `b692def599f4` | ✅ 2/2 存活 |
| FINAL | 05152d1+9项修复 + 合格内核（5,690,368 B/EEAECA58958A） | 新好 `b692def599f4` | ✅ **5/5 存活** |
| **NEGCTL** | 同 FINAL，**唯一变量换回坏产物** | 坏 `fdf72b52205b` | ❌ **2/2 精确复现 0xC0000602** |

- E3r4 是"宿主代码嫌疑"的终结者：**崩溃不需要 PR #48 的任何代码在场**
- NEGCTL 是因果闭合：同臂唯一变量翻转，结果精确翻转
- 各臂 LakeUI.dll 血统已逐一实测归档（见 §8 附录 A），链路无断点

## 4. 排查历程复盘（两轮误判的方法论剖析）

### 4.1 为什么所有二分证据都"指向宿主"——共线伪影

时间线上：a8934a2 系臂（10/29-30 建）恰好全用**旧好产物**，05152d1 系臂（10/31 后建）恰好全用**坏产物**。于是：

| 表面事实 | 实际解释 |
|---|---|
| 旧宿主 + 新内核 ✅ / 新宿主 + 旧内核 ❌ | 宿主臂建时点与 LakeUI 产物更替**完全共线**，"内核无关、宿主决定"的结论是伪影 |
| arm_picfirst（9 笔 vs 旧 main）✅ | 该臂用旧好产物，9 笔自然洗不白也冤枉不了 |
| arm_merged / arm_reviewfix ❌ | 与 9 笔无关，坏产物在场即崩 |
| "合并 upstream 后崩" | 合并动作本身无罪——它只是恰好在 10/31 触发了一次 LakeUI 增量重编 |

### 4.2 第一轮误判：GPU 预热线程（审查 high 项 VBS.001）

审查报告指出第 5 笔 GPU 预热线程首次把 LakeUI 弱双检/双锁分裂的 D3D 全局暴露给非 UI 线程，与崩溃时刻吻合——方向合理、证据扎实，但 `FFF_NO_GPU_WARMUP=1 + FFF_NO_STARTUP_PRIORITY=1` 消融后 3/3 仍崩 ⇒ 洗清。随之实施的方案 J（预热线程字段化 + UI 线程 Join 串行化）作为**独立成立的审查修复**保留（它修的是真实的线程安全隐患，只是不是本崩溃的根因）。

### 4.3 第二轮误判：Svg 包引用（时序伪相关）

- E3r2（revert b0f1bd6 图标烘焙，worktree 建臂）存活 → 误读为"Svg 引用恢复"的功劳
- r4（仅恢复 Svg PackageReference）存活 → 强化误判并推送 510ed74
- **血统复核揭穿**：E3r2/r4 臂内 LakeUI.dll 实为旧好产物 `cc7c27cb62a1`（worktree 建臂的依赖解析与主仓不同），而 E2PLUS（崩溃臂事后拷回 Svg.dll/ExCSS.dll）3/3 仍崩早已暗示"非文件在场层面"
- 教训：**任何"修复后存活"的结论，必须回查存活臂的全量产物血统**——否则修复归因可能是产物更替的时序伪相关

### 4.4 正确路径的还原

崩溃二分工程师在 E3r3 做出"r2 形态 + 覆盖坏产物 → 崩"的对照后锁定 LakeUI，随后用 E3r4（upstream 原版宿主 + 坏产物）一锤定音。此前二分矩阵的每一条"宿主决定"证据都被"产物共线"统一解释——**旧结论无一例外兼容新事实，这是正确根因的标志**。

## 5. 机制分析（坏 IL 为何 fastfail 且"三无"）

以下为基于证据的机制推断（指令级栈不可得，无法逐条实证）：

1. **不一致构建的产生**：增量编译（Incremental Build）在源码零变更时产出与先前干净构建差异巨大的映像（体积 −2.96 MB），常见诱因：MSBuild 增量标记（*.obj/IntermediateOutputPath 时间戳错乱）、跨 TFM 混合编译残留（宿主已 TFM 护栏提示 LakeUI 为 `net10.0-windows10.0.17763.0` 混血状态）、并行构建竞争导致部分编译单元被跳过。**具体诱因未逐项溯源**——LakeUI 仓 11/1 的干净重编已治愈，若复现建议在 LakeUI 仓开 Clean+Rebuild 对照留档。
2. **运行期表现形式**：坏映像缺少/错置部分类型或方法体，宿主启动 ~417 ms（Form1_Load 尾段～Shown 早期）首次触及对应成员 → CLR 加载器/一致性检查触发内部 `FAIL_FAST`（`RaiseFailFastException` → 0xC0000602）。三无现象与 CLR 内部 fastfail 被静默吞掉一致（未走 WER 常规管线）。
3. **为何秒级复现却无任何日志**：fastfail 不产生托管异常，`Environment.FailFast` 的常规事件日志路径同样未走——三无形态本身即可作为"怀疑产物不一致"的启发式信号。

### 5.4 定位深化（2026-11-02 追加）：坏 IL 精确到 R2R 预编译本机码层

诊断脚本（`diag_lakeui_diff.ps1` / `diag_lakeui_il.ps1`，输出 `lakeui_diff.txt` / `lakeui_il_diff.txt`）对坏产物（`fdf72b52205b`）与新好产物（`b692def599f4`）做了三层对比：

| 对比层 | 方法 | 结果 |
|---|---|---|
| 托管元数据 | 双 ALC 隔离加载 + `GetTypes()` + 逐类型成员枚举 | **完全一致**：737 类型、9945 方法、类型/成员签名**零差集** |
| 方法体 IL | `System.Reflection.Metadata`（PEReader/MetadataReader）逐方法 IL 字节 SHA1 | **完全一致**：9945 个方法 IL 字节逐一相同（含方法体长度） |
| 全文件字节 | `cmp -l` 全量对比 | **94% 字节不同**（2,239,902 / 2,383,872，差异均匀分布于全文件） |

**判别实验**：崩溃臂加环境变量 `DOTNET_ReadyToRun=0`（禁用 ReadyToRun 预编译映像、强制 JIT）→ **3/3 全部存活**（`NOR2R` 轮，smoke_e1.ps1）。

**定位结论**：坏产物的问题**不在源码、不在托管 IL、不在元数据表**，而在 **R2R（ReadyToRun）预编译本机码层**：

- 两份产物 IL/元数据完全等价 ⇒ 托管语义无差异；94% 字节不同 ⇒ 差异集中在**本机码/映像布局**（R2R publish 每次构建的本机码/函数表布局天然不同，故两份"好"产物彼此也 94% 不同但都健康——**健康的标准是产物自身自洽，不是与另一份逐字节相同**）
- 坏产物 = **自身不自洽**：10/31 增量构建只重编了部分编译单元，R2R 本机码/函数表与映像元数据脱节 → 宿主启动 ~417 ms 执行到 LakeUI 某 R2R 入口时命中不一致点 → CLR 内部 fastfail
- `DOTNET_ReadyToRun=0` 强制 JIT 完全绕开本机码层 → 存活，方向性实锤

**附加价值**：`DOTNET_ReadyToRun=0` 是免费的"本机码层 vs 托管层"判别杠杆——今后遇三无 fastfail，先禁 R2R 复测一轮即可把嫌疑面砍半。据此可将 §5.2 的机制表述修正为：坏映像的**托管元数据并无缺失/错置**（实测一致），failfast 源于 **R2R 本机码与元数据的脱节**。

## 7. 处理与防护建议

### 7.1 给 LakeUI 仓的反馈要点（建议随本报告提出）

1. 2026-10-31 增量编译产出了与源码状态不一致的坏映像（2,383,872 B / `fdf72b52205b`），运行期触发 CLR fastfast（0xC0000602，三无）；同源干净重编（2,375,168 B / `b692def599f4`）即愈
2. 建议排查该时段的增量编译环境（MSBuild 增量标记、TFM 混血 `net10.0-windows10.0.17763.0` vs 宿主 `net10.0-windows10.0.26100.0`、并行构建竞争）
3. 建议构建脚本加"产物自述"：每次构建输出 字节数 + SHA-256 到清单文件，供下游血统核对

### 7.2 宿主/kernel 侧的长期防护（建议纳入惯例）

1. **血统核对清单扩容**：建臂前核对 `FFF.Native.dll` **与 `LakeUI.dll`** 的字节数 + SHA 前 12 位，与已知-good 值比对（如同内核 5,690,368 B / `EEAECA58958A` 的既有惯例）；不匹配即拒建
2. **兄弟仓产物更替须显式记录**：任何重建 LakeUI 的动作在实验日志中留产物血统行，避免再次形成共线
3. **"修复后存活"必须回查全量产物血统**再下归因结论（§4.3 教训）
4. **二分矩阵把兄弟仓产物列为独立控制变量**：宿主 × LakeUI（好/坏）至少 2×2，而非默认兄弟仓恒定
5. 推送前验证臂冒烟 ≥5 轮保持既有纪律（本轮 arm_final 即该纪律的产物）

### 7.3 对 510ed74 的处置建议

保留（不强推撤回）：对 upstream 中性、用户工作线（fff5d2b）已收编、撤回收益仅是去掉一个中性提交而代价是历史重写+再次分叉。仅需在 PR 描述更正其提交说明中"规避 FailFast"的表述（可引用本报告 §3.3/§6）。
