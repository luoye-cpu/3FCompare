## 2.1 基线 A/B 对照（K1–K4 的**决定性**证据）

单看改动内核"行为正确"不足以证明修复必要；必须有**同一份探针、同批次交替**跑出的基线对照。
做法见 `../tools/ab_baseline_vs_patched.sh`，原始输出 `../build/ab/ab_result.txt`，汇总 `../build/ab/ab_summary.txt`。

**方法论要点**（三处都是踩过坑才成立的）：

1. **一份 exe 跑两版内核**：把 `FFF3FP_GetImageInfo` 由静态导入改为 **`GetProcAddress` 动态解析**
   （`tools/verify_image_mode.cpp`）。基线内核没有该导出，静态导入会让 exe 直接加载失败。
2. **探针必须能读到 `staticImage`**：`GetMediaInfo` 的 `"staticImage"` 字段**两版内核都有**，
   这是 K3 唯一可对照的读数。
3. **`Seek(0)` 不能证明 K2**：`av_seek_frame` 到起点天然可满足 ⇒ 两版都返回成功。
   必须补**非零 Seek**，K2 的证据才出现（见下表 ICO 行）。

> ⚠ **对照基线的口径（必须如实标注）**：本轮用的是 **3FC 基线内核产物**
> （`third_party/fff_project/FFF.Native/x64/Release/FFF.Native.dll`，2026-09-21 构建），
> 即「上游 `2acd96d` + 3FC 的 31 个本地提交」——**不含** K1–K4 与 `GetImageInfo`，
> 但不是纯上游。之所以没重新构建纯上游：本机 MSBuild 命中
> `MSB6001`（环境里 `Path`/`PATH` 大小写重复，.NET Framework 版 MSBuild 的已知缺陷），
> `dotnet build` 又不支持 `.vcxproj`（缺 `VCTargetsPath`）。
> ⇒ 该基线与上游在 K1–K4 落点（`FlushAtEnd` / `DoSeek` / `IsStillImage`）上一致（已核对源码），
> 但**严格意义的"纯上游对照"仍未做**，若要写进 PR 正文，建议补一次纯上游构建。

| 用例 | 基线内核 | 改动内核 | 结论 |
|---|---|---|---|
| PNG 静态图 | `staticImage=true`、**`PlaybackEnded=yes`**、seek 落点 `400000` | `staticImage=true`、`PlaybackEnded=no`、seek 落点 `0` | **K1 ✅** |
| JPG 静态图 | 同上 | 同上 | **K1 ✅** |
| **AVIF（PQ）** | **`staticImage=false`** ← K3 缺陷；seek 落点 `10000000`（**真的移动了**） | **`staticImage=true`**；seek 落点 `0` | **K3 ✅ 决定性** |
| 多页 TIFF | `staticImage=true`、`PlaybackEnded=yes` | `staticImage=true`、`PlaybackEnded=no` | K1 ✅ |
| **ICO** | `PlaybackEnded=yes` + **`event=Error{result:-5,"FFmpeg could not seek to the requested position; playback remained active."}`**，`swapPresents` 239→281 | 无错误事件，`swapPresents` 恒为 3 | **K2 ✅ 决定性** |
| PNG 17000×64（超限） | `event=Error{result:-6,"Could not create the decoded frame textures."}` + `"Could not decode or render the still image during open."`（**模糊**） | `event=Error{result:-7,"The still image is too large to display: 17000x64 exceeds the limit of 16384 pixels per side."}`（**明确**） | **K4 ✅ 决定性** |
| PNG 16384×64（边界） | `PlaybackEnded=yes` | `PlaybackEnded=no`，正常呈现 | K4 边界精确 ✅ |
| WebP 动画 | `staticImage=false`、seek 落点 `50000000` | `staticImage=false`、seek 落点 `50000000` | **两版一致 ⇒ 动画路径无回归** ✅ |

**读法要点（K2 的触发条件具格式特异性）**：

- **ICO** 的解复用器**真的不可 seek** ⇒ 基线走 `av_seek_frame` 失败 → 字节回退也失败 → `ReportError(-5)`。
- **image2 系**（PNG/JPG/TIFF）基线**不报错**，而是把落点**静默夹到媒体时长**（`400000` = 0.04 s）
  并执行一次完整 seek + 重渲染。⇒ 所以 **`Seek(0)` 那一轮看不到 K2**，必须在 ICO 上用非零 Seek 才能复现。
- 这条修正很重要：`PlayerSession.cpp` 里 K2 的注释写的是"every attempt ends in ReportError"，
  **实测只对不可 seek 的解复用器成立**，对 image2 系是"静默夹值 + 多余重渲染"。PR 描述应按实测口径写。

## 4. 广色域（D12）：检出正确，**scRGB 输出已于 2026-09-26 验证**（初版记为"无法验证"，已作废）

**正确部分**：
- Display P3 PNG（cICP `smpte432`）被正确识别：`WIDE_GAMUT=1`、`flags=0x41`。
- `GetImageInfo` 报 `primaries=BT.2020` —— 这是**设计预期**：`ConvertPrimariesToBt2020` 已把 P3 无损转成 BT.2020，
  帧级参数随之更新（P3 ⊂ BT.2020，色域只扩不缩）。

**⛔ 初版"无法验证部分"已作废，替换为以下已实测结论（2026-09-26）**：

对 PQ AVIF / HLG JXL / **Display P3 PNG** 请求 `SetColorMode(MapToHdr)`，在 HDR 已开启的显示器上实测：

| 源 | 实测 `actualColorMode` | `videoOutputBitDepth` | `sourcePeakNits` |
|---|---|---|---|
| PQ AVIF 静态图 | `MapToHdr` | **`16`（scRGB 真 HDR）** | 1000 |
| HLG JXL 静态图 | `MapToHdr` | **`16`** | 1000 |
| **Display P3 PNG** | **`MapToHdr`** | **`16`** | 100 |
| sRGB PNG / JPG | `MapToSdr`（正确回落） | `8` | 100 |

⇒ 初版"回落机制确实生效且正确"的结论**维持**，但现在**两侧都验证过了**：HDR/广色域源进 scRGB、SDR 源正确回落。

**🔴 本轮（2026-09-26）发现并修复的真实缺陷 —— 广色域源无法进 scRGB**：

- **现象**：Display P3 PNG 请求 `MapToHdr` 时被静默降级为 `MapToSdr`（`outBits=8`），`reason="…for HDR source video."`。
- **根因（同一功能三份实现、两份错 ⇒ 元发现 1 的又一实例）**：
  1. `PlayerSession.cpp` 公开 `SetColorMode` 在**会话层**先判 `snapshot_.isHdrSource == 0` ⇒ 直接把 `MapToHdr` 改写成 `MapToSdr`，**短路在渲染器之前**（真正的元凶）；
  2. `VideoRenderer::SetWindow`（Create 时）只判 `IsHdrSource()`；
  3. `VideoRenderer::EnsureSwapChain`（最终裁决点）只判 `IsHdrSource()`。
  三者都漏了 `IsWideGamutSource()`。**为什么"早于流配置"是关键**：`SetColorMode` 常在 `Open` 走到 `ConfigureHdrStream` **之前**被调用，
  此刻 `sourceWideGamut_` 尚为默认 `false` ⇒ 门禁读到的是**假值**，据此改写用户意图必然出错。
- **修复**：
  - 会话层**不再裁定**（`snapshot_.requestedColorMode = mode`，原样保留用户意图），裁决统一交给 `EnsureSwapChain`；
  - `SetWindow` / `EnsureSwapChain` 的门禁改为 `sourceHdr || wideGamut`；
  - 回落文案统一为 **`"True HDR output is only available for HDR or wide-gamut sources."`**，且 `PlayerSession.cpp` 改为读取渲染器的 `FallbackReason()`（单一真源）。
- **验证**：修复后 P3 PNG `--hdr` ⇒ **`outBits=16`**（修复前 `8`）；15 用例矩阵（含 HDR10 4K/8K 视频、动图、多页 TIFF、HEIC、16bit PNG）全部符合预期，**无回归**。
  宿主回归门 `run_host_tests.sh` ⇒ **12 通过 / 9 失败**，与基线**逐条同形**（9 个失败均为 `Temp` 目录冲突等环境固有项，无一落在色彩/HDR 路径）。
- **⚠ 产品含义**：这不是"P3 图片更好看一点"的优化，而是**正确性问题** —— P3 源被错误落到 8-bit Rec.709 交换链上，
  而 **Rec.709 是 SDR 最窄的色域、装不下 P3**（⚠ **注意方向**：装不下的是 **Rec.709**，**不是 scRGB** —— scRGB 色域远超 Rec.2020，P3 走 scRGB 是**完整无损**的），
  旧行为会把 P3 色彩**静默裁剪**（用户看到的颜色是错的，且无任何提示）。

## 6. 发现的缺陷 / 风险（供 PR 与后续决策）

| # | 项 | 证据 | 严重度 |
|---|---|---|---|
| **A** | **EXR/float 输入触发位深溢出路径** | EXR 实测 `sourceBitDepth=32`；代码 `input.bitDepth = max(8, comp[0].depth)`（`VideoRenderer.cpp:4003`）⇒ `bitDepth=32`；随后 `maximum = (1u << 32) - 1u`（`:4123`）与 `FullRangeChromaOffset(32)`（`:4132` ⇒ `(1u<<31)/((1u<<32)-1)`）均为 **UB**，后者分母为 0 ⇒ `cOffset = +inf` | 中（**实测渲染未崩**，`presented` 递增 ⇒ 当前 RGB 布局下该值未被 shader 使用；但属真实 UB，K7 应加固） |
| **B** | **float HDR 精度损失** | `gbrpf32le` → `convertedFormat = RGBA64LE`（`:4008`，因 `bitDepth>8`）⇒ 32 位浮点降为 16 位整数，**超 [0,1] 的值被裁** | 中（EXR/JXL float HDR 的高动态范围丢失；需产品侧确认是否可接受） |
| **C** | **`MULTI_FRAME` 标志对多页 TIFF 不可用** | 判定为 `stream->nb_frames > 1`（`PlayerSession.cpp:2974`）；而 ffmpeg 的 image2 解复用器对多页 TIFF 只暴露第 1 页且 `nb_frames` 未知 ⇒ 3 页 TIFF 实测 `MULTI_FRAME=0` | 低（M2「仅显示第一页」标注无法靠该标志实现） |
| **D** | **EXIF 旋转符号方向未视觉确认** | Orientation=6 报 `rotationQuarterTurns=3`；ffmpeg 对同一文件报 `displaymatrix rotation=-90`。需确认「3」是否对应"顺时针 90° 校正" | 低-中（方向反了会转错 180° 的观感；须真机看图确认） |
| **E** | 序列图（`img%03d.png`）经 3FP 打开路径不可达 | 内核路径校验要求真实常规文件（`PlayerSession.cpp:3767`，**上游 `2acd96d:3511` 同样存在** ⇒ 非本次回归）；而 ffmpeg 只在**显式模式串**下才识别 10 帧序列 | 低（样张 #10 的用途在当前宿主下不成立，K3 的序列顾虑实为 moot） |
| **F** | P3 转换触发 ffmpeg 警告 | 打开 P3 PNG 时 stderr：*"Changing video frame properties on the fly is not supported by all filters."*（`zscale` 输入 csp 由 unknown→gbr） | 低（实测未影响结果：`WIDE_GAMUT=1`、`presented` 递增） |
| **G** | 🔴 **广色域源被错误落到 SDR 交换链（本轮发现并已修复）** | Display P3 PNG 请求 `MapToHdr` ⇒ 被静默降级 `MapToSdr`/`outBits=8`。根因：三处色彩门禁（`PlayerSession::SetColorMode`、`VideoRenderer::SetWindow`、`VideoRenderer::EnsureSwapChain`）**只判 `IsHdrSource()`，漏判 `IsWideGamutSource()`**；会话层还先于 `ConfigureHdrStream` 执行 ⇒ 读到 `wideGamut=0` 假值 | **高（正确性）**：**Rec.709 是 SDR 最窄色域、装不下 P3**（⚠ 装不下的是 Rec.709，**不是 scRGB**）⇒ 旧行为把 P3 **静默裁剪色域**。**已修复并验证** `outBits=16`（P3 走 scRGB ⇒ 完整无损）；详见 §4 与 `docs/13` |

| **Q3** | EXIF 方向是否被 ffmpeg 应用 | ✅ **定案（正向）** | **是**：mjpeg 解码器导出**帧级** `AV_FRAME_DATA_DISPLAYMATRIX`（注入 Orientation=6 ⇒ `rotation=-90`）⇒ M2 自动旋转可实施。注意 ffmpeg 只**暴露**矩阵，**不自动旋转**像素（解码后仍 1920×1080） |

| **Q9** | RGB/float 输入的色彩与精度 | 🟡 **部分定案** | 色彩：RGB→RGB 不过 YUV 矩阵 ⇒ 硬编码 `SWS_CS_ITU709` 对 RGB 源**无影响**（与 `00-设计规格` §9.2 一致），P3 primaries 得以保全。精度：见 §6 A/B（float 有 UB 与精度损失） |
| **Q8** | gain map 是否被 ffmpeg 暴露 | ✅ **定案（不支持，读取侧）** | 见 §9。D4 结论**维持**，但**依据需修订** |
| **Q1** | 基线打开 PNG 的实际行为 | ✅ **定案** | 见 §2.1。基线：PNG/JPG/TIFF 打开即 `PlaybackEnded=yes`、seek 落点被静默夹到媒体时长；**AVIF 被判为非静态图**（`staticImage=false`）；**ICO 的 seek 直接报错**；17000px 大图报模糊的"纹理创建失败" ⇒ **四项修正的必要性全部由实测支撑** |
| Q4 | 多页 TIFF 只解首页 | ✅ 顺带定案 | 是（image2 解复用器只给第 1 页） |
| **Q10** | P3 量化偏色 | ✅ **定案（2026-09-26）** | 初版记"暂不可测（HDR 关闭）"**已作废**。HDR 开启后实测：**修复前** P3 源 `MapToHdr` 被静默降级 ⇒ `outBits=8`（Rec.709 交换链**必然裁剪 P3 色域** ⇒ 偏色）；**修复后** `outBits=16`（scRGB，P3 色彩完整保留）。⇒ **P3 量化偏色是真实存在的缺陷，已修复**（详见 §4 与 `docs/13`） |

## 9. Q8 定案：ffmpeg 无 gain map **读取**通道（D4 维持，依据修订）

> 本机二进制取证 + 上游调研（2026-09-24）。

**本机取证（`ffmpeg git-2026-09-01-c27482a18d`）**：

| 手段 | 结果 |
|---|---|
| `avcodec-63.dll` / `avformat-63.dll` / `ffmpeg.exe` 串扫描 `gainmap` / `gain_map` / `GainMap` / `hdrgm` / `21496` / `urn:iso` | **0 命中** |
| `gmap` / `tmap` | 仅有假阳性（`pixlet`/`tmpm` 等无关符号） |
| `mov` 解复用器对 HEIF 静态图的支持面 | ✅ 支持 `iref`(dimg/thmb/cdsc)、`iloc`/`iinf`/`infe`/`iprp`、`grid`/`iovl`；**派生项 switch 只处理 `grid`/`iovl`** ⇒ **`tmap` 不被识别** |
| 容器能力 | **无** `heif`/`heic` muxer（只有 `avif`）⇒ 本机无法自造样张 |

**上游现状**：
- 存在 PR **#24264 "Implement JPEG Ultra HDR"**（作者 haasn，2026-08-25 提交，状态 **New / 未合并**）——
  但该 PR 只做**编码 / 封装侧**（写 gain map 到 JPEG），**不含 decoder / demuxer 读取路径**。
- ⇒ 上游**没有**可用的 gain map 读取实现；`tmap` 派生项在 demuxer 侧未被处理。

**结论**：
- **Q8 = 不支持（读取侧）**。`docs/00` 的决策 **D4「GainMap 明确不做」维持不变**。
- ⚠ 但 **D4 的表述应修订**：原文写"ffmpeg **无 gain map 侧数据通道**"过于笼统。
  准确表述应为：**"ffmpeg 当前无 gain map 的读取通道（demuxer 不解析 `tmap`、无对应 side data）；
  上游仅有一个未合并的写侧提案（PR #24264）"**。
- **若要做**的最小路径与代价：需先在 ffmpeg 侧补 `tmap` 派生项解析 + 增益图解码 + side data 暴露，
  3FP 才能消费 ⇒ **属上游级改动，代价远超本项目范围**。建议维持"不做"，并在设计文档里留一句
  "等上游 demuxer 支持后再评估"。
