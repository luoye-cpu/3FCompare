**一句话**：`rgbaf16le` 的规范语义是 **scRGB 线性光**（gamma=1.0、sRGB/709 原色、1.0=参考白、负值=色域外、>1.0=超白）；
4 个样本无 ICC ⇒ 走 WIC 兜底规则 ⇒ **默认按线性处理**；内核当前把它当 **SDR 编码域**并转整数，是**双重错误**（既丢数值又用错曲线）。

## 二、float 像素数值语义（含出处与置信度）

### 2.1 scRGB —— 来自 jxrlib 官方头文件（主要证据）

`jxrlib` 的 `jxrgluelib/JXRGlue.h`（本机副本：`_3fc_tmp/jxr_spec_evidence/JXRGlue.h`，29502 字节，
取自 `https://raw.githubusercontent.com/4creators/jxrlib/master/jxrgluelib/JXRGlue.h`）第 136–159 行**原文**：

```c
/* scRGB formats. Gamma is 1.0 */
/* For a full definition, see the scRGB spec */

/* 16bpp format */
DEFINE_GUID(GUID_PKPixelFormat16bppGrayFixedPoint, ...c913);
...
/* 96bpp format */
DEFINE_GUID(GUID_PKPixelFormat96bppRGBFixedPoint, ...c918);
DEFINE_GUID(GUID_PKPixelFormat96bppRGBFloat, 0xe3fed78f,...);

 /* Floating point scRGB formats */
DEFINE_GUID(GUID_PKPixelFormat128bppRGBAFloat,  ...c919);
DEFINE_GUID(GUID_PKPixelFormat128bppPRGBAFloat, ...c91a);
DEFINE_GUID(GUID_PKPixelFormat128bppRGBFloat,   ...c91b);
```

**[VERIFIED·高]** `gamma = 1.0` ⇒ 浮点像素承载的是**线性光**，不是编码域码值。
这是"**已是线性**"主张最直接的原始出处。

> ⚠ 注意：该注释在 jxrlib 中是**分组标题**，其下同时包含 FixedPoint 与 Float 两类；
> 但第 156 行另有更窄的标题 **"Floating point scRGB formats"** 单独管辖 128bpp 浮点三兄弟。
> ⇒ **浮点 = scRGB 是明确的**；灰阶/定点是否也严格属 scRGB，本文不主张（见 §七 U2）。

**[VERIFIED·高]** 同一头文件还存在 **`GUID_PKPixelFormat32bppRGBE`（…c93d）**，即 Radiance RGBE 编码，
说明 JXR 的浮点/HDR 家族**不止一种**，`rgbaf16le` 只是其中一族（见 §七 U1 关于 11/12 码的归属）。

### 2.2 定点 vs 浮点：两套数值解释

**[VERIFIED·高]** Microsoft WIC 文档《Native pixel formats overview》
（https://learn.microsoft.com/en-us/windows/win32/wic/-wic-codec-native-pixel-formats ）原文：

> 16-bit fixed-point values are interpreted as **s2.13**: sign bit, two integer bits, and thirteen fractional bits.
> Using this interpretation, a numerical range of **−4.0 to +3.999...** can be represented, with the value of **1.0
> represented by the signed integer value 8192 (0x2000)**.
>
> 32-bit fixed-point values are interpreted as **s7.24** … a numerical range of **−128.0 to +127.999...** … with the
> value of **1.0 represented by the signed integer value 16777216 (0x01000000)**.

**[VERIFIED·高]** 同文档对浮点/定点存在的理由：

> In addition, WIC supports fixed-point and floating-point formats. These formats support **larger dynamic ranges,
> because the entire numerical range of each color channel is larger than the visible range**. As a result, **colors
> can be adjusted above or below the visible range**, during the intermediate steps of image processing, without loss
> of image information.

⇒ **负值与 >1.0 是被规范预期的**，不是损坏数据。**置信度 高。**

### 2.3 负值 = 色域外，>1.0 = 超白

- **[INFERRED·中高]** 负分量语义：scRGB 以 sRGB/Rec.709 原色为基准的三刺激值域；三原色坐标之外的色（如
  P3/2020 的饱和色）在该基下会出现**负分量**。这与本仓既有设计注释一致 ——
  `VideoRenderer.cpp:744` 已写明"**negative components FP16 carries as-is**"（`docs/68 §二`）。
- **[INFERRED·中高]** >1.0 语义：线性域中 1.0 = 参考白，>1.0 = 超白高光。
  实测 `DHR-CoJ1002` max=**53.94**、`fh2_fp16` max=**58.09**，即参考白的 ~54–58 倍，典型 HDR 内容特征。

> ⚠ **未能**从 T.832 条文中确认"负值/超白"的确切合法区间（见 §七 U3）。
> scRGB 常引用的 **[−0.5, 7.5]** 范围**本文未取得原始规范文本**，故不作为结论。

### 2.4 本机实测：样本的头部与颜色标签

**[VERIFIED·高]** 头部解析（`_3fc_tmp/jxr_hdr_parse.ps1`，逐字节读文件）：

| 样本 | magic | `headerSize` | offset 8 处像素格式码 | JXR 内颜色 tag |
|---|---|---|---|---|
| `HDColorHDRCalibration.jxr` | `49 49 BC 01` | 8 | **`0x0B` (11)** | 无 |
| `fh2_fp16.jxr` | `49 49 BC 01` | 8 | **`0x0B` (11)** | 无 |
| `DHR-CoJ1002.jxr` | `49 49 BC 01` | 8 | **`0x0B` (11)** | 无 |
| `FH4-HDR.jxr` | `49 49 BC 01` | 8 | **`0x0C` (12)** | 无 |

- `headerSize=8` ⇒ **无内嵌 WIC GUID**，只有 1 字节扩展格式码（与 `docs/15 §2.2` 一致）。
- **[VERIFIED·高]** 四个样本的字节流中**均不含** `PROF`/`ICC` 标记（≤200 KB 前缀扫描），
  即 **JXR 层未携带 ICC / ColorContext** ⇒ §三 兜底规则适用。

**[VERIFIED·高]** 内核侧实际读到的 `AVFrame` 颜色字段（本机只读解码探针 `jxr_semantics.exe`）：

```
HDColorHDRCalibration.jxr  color_trc=2 primaries=2 space=2 range=0
fh2_fp16.jxr               color_trc=2 primaries=2 space=2 range=0
DHR-CoJ1002.jxr            color_trc=2 primaries=2 space=2 range=0
FH4-HDR.jxr                color_trc=2 primaries=2 space=2 range=0
```

对照 `libavutil/pixfmt.h`：**`2` = `AVCOL_TRC_UNSPECIFIED` / `AVCOL_PRI_UNSPECIFIED` / `AVCOL_SPC_UNSPECIFIED`，
`0` = `AVCOL_RANGE_UNSPECIFIED`**。⇒ 与任务描述的"全部 unknown"**一致**（`2` 就是 FFmpeg 的"未指定"）。

> ⚠ **重要修正**（对 `docs/61` 的教训的延伸）：`ffprobe` 把这些**打印为 `unknown`**，
> 而内核读到的是**数值 `2`（UNSPECIFIED）**。二者语义相同，但**不要**把"打印为 unknown"当作"字段为空"——
> 这里 `color_trc` 确实是"规范意义上的未指定"，**不是**"libjxr 填了但被丢弃"。

### 2.5 是否有实测证据区分"线性 vs 编码"？

**[VERIFIED·高]** 有，且结论指向"**数据本身已是显示域**"，这一点与 §2.1 的 scRGB 结论**存在张力**，必须如实记录。

探针 `jxr_final.exe` 对同一帧做两件事：(a) 把 float **按原值**统计；(c) 用 `sws_scale` 把同一帧转 8-bit BGRA 统计。

| 样本 | (a) float 原值均值 | (b) 把 float 当线性→sRGB 编码 | (c) swscale 转 8-bit 均值 |
|---|---|---|---|
| `HDColorHDRCalibration` | **0.4195** | 0.5856 | **0.4203** |
| `FH4-HDR` | **0.2111** | 0.2833 | **0.2116** |
| `fh2_fp16` | **0.3236** | 0.4851 | **0.3242** |
| `DHR-CoJ1002` | **0.2454** | 0.3717 | **0.2457** |

**(a) ≈ (c)**（差 <0.001）⇒ **`swscale` 的 float→8-bit 是恒等映射（截断），不是线性→sRGB 编码**。
若 float 真按 scRGB 线性语义处理，(c) 必须显著高于 (a)（应接近 (b)），实测**没有发生**。

**[VERIFIED·高]** 另一独立判据：把值域限制在 [0,1] 的通道单独统计（`jxr_lintest.exe`）：

| 样本 | [0,1] 内通道均值 | 天然线性光图像的期望 |
|---|---|---|
| `HDColorHDRCalibration` | **0.2708** | 0.10–0.30 |
| `fh2_fp16` | **0.1832** | 0.10–0.30 |
| `DHR-CoJ1002` | **0.1239** | 0.10–0.30 |
| `FH4-HDR` | **0.1388** | 0.10–0.30 |

⇒ **完全落在"线性光"的预期区间**。

**综合判断 [INFERRED·中高]**：
- **数值语义（§2.1）**：scRGB 线性，gamma=1.0 —— 有原始出处，**高**。
- **FFmpeg 封装行为（§四）**：`libjxr` 把反 gamma 后的线性值直接交给 FFmpeg，标签却是 UNSPECIFIED；
  下游 `swscale` 因为**看不到"这是线性"的标签**而走了恒等路径。
  ⇒ 这正是**内核判 SDR 并整数化的根因**，也说明"**我们必须在封装/内核侧补上 transfer=linear 标签**"。

## 三、无色彩标签时的默认假设

**[VERIFIED·高]** Microsoft WIC 文档《Native pixel formats overview》"Color space" 一节**逐字原文**：

> **Color space**
> Pixel formats in themselves do not have a color space. Generally, color space is a semantic interpretation of the
> pixel values that depends on the context of the bitmap. Some images identify a color context that defines the color
> space of the image. **Only in the absence of a color context should the color space be inferred.**
>
> Color context information is defined by the **IWICColorContext** interface for WIC. To retrieve the color context
> information for an image frame, use the **GetColorContext** method.
>
> In the absence of color space information for an image, the general rule for color space inference is that
> **UINT RGB and grayscale formats use the standard RGB color space (sRGB)**, while **fixed-point and floating-point
> RGB and grayscale formats use the extended RGB color space (scRGB)**. The CMYK color model uses an RWOP color space.

**三层优先级（本条是本任务最重要的可执行结论）**：

| 优先级 | 来源 | 对未标记 JXR 的含义 |
|---|---|---|
| 1 | 容器 **ICC / `IWICColorContext`** | 若存在，**必须**用它，不得推断 |
| 2 | WIC 兜底规则（上引） | float/fixed ⇒ **scRGB（线性）**；UINT ⇒ sRGB |
| 3 | （无） | — |

**[VERIFIED·高]** 4 个样本按 §2.4 均**无 ICC** ⇒ **命中优先级 2** ⇒
**`rgbaf16le` 应默认解释为 scRGB 线性光，即 transfer = linear，primaries = sRGB/Rec.709。**

> ⚠ **口径澄清**：以上出自 **Microsoft WIC 文档**（HD Photo/JXR 的官方实现方文档），
> **不是** ITU-T T.832 条文。WIC 文档把 JXR 视为其编解码器之一，该推断规则对 JXR **适用**，
> 但**本文不声称 T.832 原文有同样措辞**（见 §七 U4）。

### 4.2 为什么只输出 `rgbaf16le`

**[VERIFIED·高]** DLL 字符串取证（`avcodec-63.dll`，本机）：

```
libjxr / JPEG XR via jxrlib
Unsupported JPEG XR pixel format GUID\n      <-- GUID 路径（headerSize=32 的自产文件）
Unsupported JPEG XR pixel format: %s\n       <-- 扩展码路径（headerSize=8 的真实样本）
jxrlib JPEG XR decode failed (error=%d)\n
Invalid JPEG XR image extent\n
Invalid JPEG XR alpha extent\n
jxrlib JPEG XR encode failed (error=%d)\n
```

**[VERIFIED·高]** 实测证据链（`ffprobe` + 我方探针）：

| 文件 | 内部格式码 | 结果 |
|---|---|---|
| 4 个 HDR 样本 | 11 / 12（`headerSize=8`） | ✅ 解出 `rgbaf16le` |
| `12a_srgb_1920x1080.jxr` | （`headerSize=32`，GUID 路径） | ❌ `jxrlib JPEG XR decode failed (error=-1)`；但 `ffprobe` 仍报 `rgb24` 且 `bits_per_raw_sample=8` |

> ⚠ **该行取自本任务执行前半段的实测**（当时文件存在，命令与输出见 §八 记录）。
> 该文件在**本任务执行后半段已被并发会话移除**，`ffprobe` 现报 `No such file or directory`，
> **因此本条当前不可复现**；结论强度降级为 **[VERIFIED·中]**。核心结论（封装层不读颜色信息）
> 由 `12a_srgb` **之外**的证据独立支撑：DLL 字符串（本节上方）+ 四个 HDR 样本的颜色字段全为 `UNSPECIFIED(2)`（§2.4）。

⇒ **封装层只把 float/HDR 那一族映射到 `rgbaf16le`**；GUID 路径覆盖不全（`docs/15 §2.2` 已记录）。
**该封装完全不读取、也不设置任何 JXR 颜色信息** —— 这正是 §2.4 中四个字段全为 `UNSPECIFIED(2)` 的原因。

> **[VERIFIED·中]** 另需注意：`12a_srgb_1920x1080.jxr` 走的是 GUID 路径，
> 其 `ffprobe` 报的 `rgb24` **不是真实解码结果**（同一命令带 `-v info` 会打印 decode failed）。
> **不要把"元数据能报出 pix_fmt"当作"解码成功"。**
> ⚠ 该文件**已被并发会话移除**（见上方注记），本条当前不可复现；方法论要点仍然有效。

### 4.3 对内核的直接后果

- `DescribeInput(AV_PIX_FMT_RGBAF16LE)` 落 `default: return {}`（`VideoRenderer.cpp:1134-1135`）⇒ layout=0。
- layout=0 走"编码域 + UNORM"分支 ⇒ 转 `RGBA64LE` 时 **clamp** ⇒ 饱和 2.79%–10.73%。
- 且 `hdrFormat=0`（SDR）⇒ **即使不 clamp，曲线也是错的**。

**[INFERRED·高]** 两个缺陷**互相独立**：
① 数值截断（`docs/68` 改动 1–3 解决，可独立验证）；
② 语义误判（本任务，需改动 4）。**不要用一个改动同时修两者**。

### 4.4 构建来源旁证

**[VERIFIED·高]** DLL 内嵌构建命令行含 `--enable-libjxr`，且 `Lavc63.18.100`（FFmpeg 8.x 时代 SONAME），
与上游 master/n7.1 **均无** libjxr 的事实共同证明其为**下游/第三方补丁构建**。

```c
DEFINE_GUID(GUID_WICPixelFormat64bppRGBAHalf, 0x6fddc324,0x4e03,0x4bfe,0xb1,0x85,0x3d,0x77,0x76,0x8d,0xc9,0x3a);
DEFINE_GUID(GUID_WICPixelFormat128bppRGBFloat,0x6fddc324,0x4e03,0x4bfe,0xb1,0x85,0x3d,0x77,0x76,0x8d,0xc9,0x1b);
DEFINE_GUID(GUID_WICPixelFormat32bppRGBE,    0x6fddc324,0x4e03,0x4bfe,0xb1,0x85,0x3d,0x77,0x76,0x8d,0xc9,0x3d);
```

**[VERIFIED·高]** `GUID_WICPixelFormat*Half` 即 IEEE-754 **半精度**，**与 FFmpeg `rgbaf16le` 逐位同构**
（`pixfmt.h:403-404` 亦如此描述 RGBAF16）⇒ 内核方案 a（直接上传 F16）在表示上是**无损且位兼容**的。

### 5.2 与 jxrlib 输出的一一对应

`jxrlib` 的 `GUID_PKPixelFormat64bppRGBAHalf` = `…c93a`，与 WIC 的 `GUID_WICPixelFormat64bppRGBAHalf` **同一 GUID**。
并且 `GUID_PKPixelFormat128bppRGBAFloat`(…c919) 等**与 wincodec.h 完全一致** ⇒
**jxrlib 直接复用 WIC 像素格式 GUID 空间**（`GUID_PKPixelFormat` ↔ `GUID_WICPixelFormat` 前缀不同、值相同）。

**[INFERRED·高]** 因此：`headerSize=32` 的 JXR 内嵌 GUID 直接从该空间取值。
而 4 个真实样本用 **`headerSize=8` + 1 字节码 11/12**，**不带 GUID** ⇒ **WIC 无法据 GUID 推断**，
只能靠内部格式码 → 这正是"扩展码"路径存在的意义。

### 5.3 Windows HDR 惯例（谨慎表述）

- **[VERIFIED·高]** WIC 文档明确：`GUID_WICPixelFormat32bppR10G10B10A2HDR10` 是"**10 bit pixel format for HDR10
  (BT.2020 color space and SMPTE ST.2084 EOTF)**" ⇒ Windows 确实在 WIC 层区分 HDR10 语义。
- **[VERIFIED·高]** 但 **JPEG XR 原生编解码器的格式表中并不含该 HDR10 格式** ⇒
  **JXR 的 HDR 承载方式是浮点/定点 scRGB，而不是 HDR10 的 PQ/BT.2020 整数格式**。
- **[UNKNOWN·低]** "HDColorHDRCalibration" 这一**具体文件名的业界惯例**（是否 HDR 校准图、期望如何显示）
  **未找到任何权威说明**。该样本解码为 **320×240**，用户行指出 `HDColorHDRCalibration` 是 **文件名**并无标准含义；
  **本文不对其做任何惯例性断言**。若需确认，应向样本提供方索取（见 §七 U6）。

## 六、实现建议

### 6.1 核心结论：**默认必须取"线性"，不是 sRGB**

**[INFERRED·高，基于 §三 的 VERIFIED 规则]**
`rgbaf16le` + 无 ICC ⇒ 按 WIC 兜底规则 ⇒ **scRGB（线性）**。
因此 `docs/68` 改动 4 的正确默认是：

| 设置 | 取值 | 依据 |
|---|---|---|
| `settings.transfer` | **"已是线性"（不要再做 PQ/HLG/sRGB 编码）** | §2.1 `Gamma is 1.0` |
| `Gamut` | **709（sRGB 原色）** | WIC：scRGB 基于 sRGB 原色；jxrlib 同 |
| `color_range` | full / PC | RGB，§三 |

> ⚠ **这是对 `docs/68 §三 改动 4` 措辞的强化**：那里已写"必须同时把 `settings.transfer` 设为
> **"已是线性"**"。本文**确认该判断正确**，并给出规范出处。

### 6.2 推荐实施顺序（分两步，可独立验证/回滚）

| 步骤 | 内容 | 依赖 | 风险 |
|---|---|---|---|
| **步骤 1** | `docs/68` **改动 1+2+3**：`DescribeInput` 加 FP16 RGB layout、跳过整数化、纹理用 `DXGI_FORMAT_R16G16B16A16_FLOAT`。**先不改 Transfer/Gamut** | 无 | 低 |
| **步骤 2** | **改动 4**：按本文件 §6.1 设 transfer=linear、Gamut=709 | 本文 | 中 |

**理由**：步骤 1 只恢复**数值完整性**（负值/超白不再丢），呈现曲线仍走现状；
把"数值截断"与"语义判定"**解耦**，各自可独立验证与回滚（与 `docs/68 §五` 一致）。

### 6.3 安全选项设计（若不想无条件改语义）

**[INFERRED·中]** 建议**不要**用"值域 >1 ⇒ 线性，否则 sRGB"这类**启发式**，因为：

- 该启发式**没有规范依据**（WIC 规则只看**格式的数值类型**，不看**测得的动态范围**）；
- 实测 `FH4-HDR` 最大仅 4.56，若按某一阈值可能被误判为 SDR；
- 更稳妥的是**按格式判定**（正是 WIC 的规则）：**只要像素格式是 float/fixed-point RGB ⇒ 线性 scRGB**。

**[INFERRED·中高]** 若必须保守，可采用"**格式优先 + 用户可覆盖**"：
默认按 §6.1；同时提供显式覆盖入口（供将来带 ICC 或带 HDR 标签的文件）。

### 6.4 明确的"不要做"

- **不要**在未获得 T.832 原文前，声称"T.832 规定 X"（§七 U4）。
- **不要**把 `GUID_WICPixelFormat32bppR10G10B10A2HDR10`（PQ/BT.2020）路径应用到 JXR 浮点（§5.3）。
- **不要**用 `12a_srgb_1920x1080.jxr` 的 `ffprobe` 元数据当作解码成功证据（§4.2）。
- **不要**为"负值"单独做 clamp —— 负分量是 scRGB 的**合法**承载（`docs/68 §二` 已注意到）。
