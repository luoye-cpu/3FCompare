# 54 · 音频管线完整分析：视频模式 vs 纯音频

> 问题：「完整分析 3FP 的音频管线，视频模式下音频输出和音乐模式下的音频输出有什么区别」
> 方法：读整条链路 + 实测对比（`tools/audio_path_probe.cpp`）
> 日期：2026-10-07

---

## 0. 首要结论：**3FP 里没有"音乐模式"**

全仓搜索 `音乐模式` / `MusicMode` / `IsMusic`：**零命中**。
`音乐` 只出现在两处，且都与音频输出无关：

| 位置 | 用途 |
|---|---|
| `Form设置_音乐与歌词.vb` | 设置页（歌词、封面） |
| `播放器控制器.当前音乐有封面` | 封面图显示判断 |

**3FP 的模式只有**：视频（默认）、图片模式（`播放器图片浏览控制器`）、360°、光盘。
**音频输出路径不区分"音乐/视频"** —— 只有一条管线，按**流的构成**分叉。

## 1. 完整管线

```
┌─ 解复用 ────────────────────────────────────────────────┐
│  av_read_frame(format_)                                 │
│    ↓ 按 stream_index 分流                                │
│  ┌─ 视频流 → pendingVideoPackets_ ─┐                    │
│  └─ 音频流 → pendingAudioPackets_ ─┤                    │
└────────────────────────────────────┼────────────────────┘
                                     ↓
┌─ 解码（PlaybackWorker 单线程）─────────────────────────┐
│  DecodePacket() → avcodec_send/receive                  │
│    ↓                                                    │
│  QueueAudioFrame(frame, owner, streamIndex)             │
│    · 算位置 = StreamTimestampPosition100ns(pts)          │
│    · **丢弃 < seekTarget100ns_ 的帧**                    │
│    · 峰值电平统计                                        │
│    ↓                                                    │
│  audioRenderer_->Enqueue(frame, position)               │
└─────────────────────────────────────┬───────────────────┘
                                      ↓
┌─ 重采样 / 队列（PlayerWasapiRenderer）─────────────────┐
│  swr_convert → 设备格式（采样率/声道/位深）             │
│    ↓                                                    │
│  queue_ (分块 SPSC)  + reusableBuffers_ (复用池)        │
│    · 长间隙用 silenceBytes 表示**逻辑静音**（不占内存）  │
│    · 时间戳跳变：<100ms 计抖动，>=100ms 计不连续并补静音 │
└─────────────────────────────────────┬───────────────────┘
                                      ↓
┌─ WASAPI（独立事件线程）─────────────────────────────────┐
│  IAudioRenderClient::GetBuffer/ReleaseBuffer            │
│    ↓ shared 或 exclusive                                │
│  端点设备                                                │
└─────────────────────────────────────────────────────────┘
```

## 2. ★ 唯一的实质差异：**音频起播闸门**

### 2.1 机制

```cpp
bool ShouldGateAudioAtVideoStart() const noexcept {
    if (format_ == nullptr || videoStream_ < 0 || ...) return false;   // ← 纯音频直接返回 false
    ...
    return start - TimelineOrigin100ns(format_) <= GateTolerance100ns; // 100µs
}
```

`ArmAudioUntilVideoFrame()` 在打开/seek 时设置：

```cpp
audioBlockedUntilVideoFrame_ = ShouldGateAudioAtVideoStart();   // 纯音频恒为 false
audioResumePendingAfterVideoFrame_ = audioBlockedUntilVideoFrame_ && Playing;
if (...) audioRenderer_->SetPaused(true);
```

放行条件（`TryReleaseAudioAfterVideoPresentation`）：**已呈现的视频帧代次 ≥ 闸门臂代次**。

### 2.2 为什么这么设计

带视频时若音频先跑，会出现"**画面还没出来声音已经响了**"。
闸门保证**先出画、再出声**，且只在两种情况下生效：

- 有视频流；
- **首个视频时间戳不晚于公共媒体原点 100µs**（若视频本身晚于音频，
  说明起播前确有有效音频，此时**不闸**）。

### 2.3 纯音频的差异

`videoStream_ < 0` ⇒ `ShouldGateAudioAtVideoStart()` **直接 false**
⇒ `audioBlockedUntilVideoFrame_ = false` ⇒ **音频立即起播，不等任何视频帧**。

## 3. 实测对比

同一音频内容，一份带视频轨、一份仅去掉视频轨：

| 项 | 带视频轨 | 纯音频 |
|---|---|---|
| 视频流 / 音频流 | 0 / 1 | **-1** / 0 |
| 首个音频帧出现 | 563 ms | 1063 ms |
| 已呈现视频帧 | 141 | **0** |
| 已解码音频帧 | 257 | 264 |
| 音频位置 vs 播放位置 | 5.86 / 5.86 **同步** | 6.54 / 6.54 **同步** |
| 缓冲 | 0.14 s | 0.12 s |
| 欠载 / 不连续 / 插入静音 | **0 / 0 / 0** | **0 / 0 / 0** |

**观察**：
- 两者都正常起播、无欠载、无静音注入；
- **纯音频并不比带视频更快**（1063ms vs 563ms）—— 说明 563ms 那次并非闸门延迟，
  而是**初始化/demux 开销**；闸门在首个视频帧到来后立即放行，本就很快；
- 位置与音频位置**始终同步**，说明时钟机制一致。

### 3.1 另一条分支：无窗口的纯音频

```cpp
if (videoStream_ < 0 && audioStream_ >= 0 && !audioRenderer_) {
    // 端点被其它进程独占时，用**墙钟**推进而不是瞬间解码整个文件
    snapshot_.position100ns = min(ClockPosition(), duration);
    ...
    Sleep(10);
}
```

⇒ 纯音频 + 无音频渲染器（设备被占）时，**不会**像视频那样停住，
而是按墙钟推进位置并正常走完。这是纯音频**独有的**分支。

## 4. ★ 顺带发现并修复：抖动计数 100% 误报

### 4.1 现象

正常素材：`已解码音频帧=257`，`抖动=257` —— **每一帧都被计为抖动**。
而 `欠载=0  不连续=0  插入静音帧=0`，即**流完全健康**。

### 4.2 根因（实测）

插桩打印 `delta`：

```
[jitter] delta=17 frames (0.354 ms) threshold=4800 producedTimeline=1098 signedStart=1115
[jitter] delta=16 frames (0.333 ms) threshold=4800 producedTimeline=8900 signedStart=8916
```

- delta 是 **恒定 16–17 帧（0.33–0.35 ms）**；
- 阈值是 **4800 帧（100 ms）**；
- 判定却用 **`delta != 0`** ⇒ **任何舍入余数都计数**。

**成因**：帧时间戳是媒体时间（100 ns），比较对象是运行中的采样计数。
48 kHz 下一个 100 ns 刻度 = 0.0048 采样，**两者永不可能恰好相等**
⇒ 每帧都有固定余数 ⇒ 计数每帧 ++。

### 4.3 影响

这不是播放缺陷（流量、同步、缓冲都正常），而是**诊断字段失效**：
一个永远显示"全在抖动"的指标，**无法报告真正的抖动**。

### 4.4 修复

引入舍入容差 `outputSampleRate_/1000`（48 帧 ≈ 1 ms），只统计**超出舍入**的偏差：

```cpp
const auto jitterFloorFrames = std::max<std::int64_t>(1, outputSampleRate_ / 1000);
if (std::abs(delta) < discontinuityThreshold) {
    if (std::abs(delta) > jitterFloorFrames) ++timestampJitterCount_;
}
```

### 4.5 验证（**双向**）

| 素材 | 修复前 | 修复后 | 期望 |
|---|---|---|---|
| 正常视频 | **257** | **0** | 0 ✓ |
| 人为注入 5ms 抖动 | — | **124** | >0 ✓ |

⇒ **误报清零，真实检出能力保留**（用 ffmpeg `asetpts` 每 0.5 秒偏 5ms 构造）。

## 5. 差异总结

| 维度 | 视频模式 | 纯音频 |
|---|---|---|
| 解码路径 | 同一 worker、同一 `DecodePacket` | **相同** |
| 队列/重采样 | `queue_` + `swr` | **相同** |
| WASAPI 输出 | 同一 `PlayerWasapiRenderer` | **相同** |
| **起播闸门** | **有**（等首个视频帧呈现） | **无** |
| 无渲染器时 | 停住等待 | **墙钟推进**（独有分支） |
| 视频队列/丢弃 | 参与 | 不参与 |
| **音频输出本身** | — | **无任何差别** |

> **回答原问题**：3FP **没有"音乐模式"**；音频输出在两种形态下**走完全相同的解码、
> 重采样、队列与 WASAPI 路径**。唯一区别是**起播时序**（视频要等首帧画面）
> 和**无音频设备时的退避策略**，两者都不改变音频数据本身。
