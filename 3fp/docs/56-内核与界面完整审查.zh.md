## 1. 🔴 致命缺陷：宿主无法创建会话（已修复）

### 1.1 现象

`FFF.Player` 把 API 版本**写死为 16**，配置结构体止于 `sdrScRgbMode`（**80 字节**）；
而内核已是 **API 18 / 112 字节**。内核同时校验**版本号**与**结构体大小**：

```cpp
if (configuration->size < sizeof(FFF3FPConfiguration) ||
    configuration->version != PlayerApiVersion || ...) return FFFResult::InvalidArgument;
```

⇒ **每次创建会话都返回 -1，播放器根本起不来。**

### 1.2 复现（不靠推断）

`tools/host_compat_probe.cpp` 用宿主**原样**的结构体调用 `FFF3FP_Create`：

```
内核 API 版本 = 18
内核 sizeof(FFF3FPConfiguration) = 112 字节
修复前宿主结构体 = 80 字节

① version=16, size= 80 : result=-1  **被拒**
② version=18, size= 80 : result=-1  **被拒（size 也校验）**
③ version=18, size=112 : result= 0  （可用）
```

**两个条件互相独立** ⇒ 只改版本号或只补字段都不够。

### 1.3 修复

1. 宿主结构体补齐 **7 个追加字段**（自适应预缩放 + 软解线程档位）；
2. 版本号 16 → **18**；
3. 顺带补上 `播放器配置.SDRscRGB模式` —— 原生结构体自 API 16 就有该字段，
   但**托管侧从未定义**，于是初始化时无处取值、一直被静默置 0。

### 1.4 为什么一直没被发现

- 两侧**始终在同一工作树里一起构建**，从没遇到过版本漂移；
- 回归套件里的探针**直接调内核 API**，不经过宿主结构体；
- ⇒ **没有任何测试覆盖"宿主自己的结构体"**。

### 1.5 防复发

新增 `host_compat_probe` 并登记进重建清单。
今后**内核新增字段而宿主未同步** ⇒ 测试失败，而不是"播放器变成哑巴"。

## 2. 🟠 结构性风险：`VideoRenderer` 职责过载

### 2.1 实测规模

| 文件 | 行数 |
|---|---|
| `VideoRenderer.cpp` | **6287** |
| `PlayerSession.cpp` | **4561** |
| 内核合计 | 48 文件 / 2.5 MB |

### 2.2 一个类里的 8 项职责

对 `VideoRenderer.cpp` 的函数名分类：

| 职责 | 函数数 |
|---|---|
| 设备/交换链/呈现 | 21 |
| 缩放/管线/上传 | 14 |
| 字幕图层 | 11 |
| 封面背景 | 7 |
| HDR/色彩 | 6 |
| VSR | 6 |
| HDR 扩展/DV | 3 |
| 其他 | 45 |

### 2.3 为什么这是风险（有实证）

本轮修 `EnsureSwapChain` 的设备创建问题时，**必须读遍 6000 多行**才能确认
"D3D11 设备在哪里创建、由谁释放"。这直接体现在：

- 我先怀疑是交换链、再怀疑是 `ResetMedia`、最后才定位到 `EnsureDevice`；
- 中途还因为批量删行**误伤了 `Worker` 函数**（已 `git checkout` 还原）。

### 2.4 建议（分阶段，不要求一次性重构）

| 阶段 | 动作 | 风险 |
|---|---|---|
| ① | **只抽头文件**：按职责拆出 `VideoSwapChain`/`VideoHdr`/`VideoSubtitleLayer` 的内部结构体，`VideoRenderer` 保留门面 | 低（不动逻辑） |
| ② | 把 `EnsureDevice`/`EnsureSwapChain` 移入独立的 `DeviceContext` | 中 |
| ③ | 字幕图层独立（它已有自己的线程与锁） | 中 |

**不建议**在没有回归覆盖的情况下做大规模搬迁 —— 当前 31 个探针覆盖的是**行为**，
不是内部结构，重构期间容易引入静默回归。

## 3. 🟢 确认无问题的项（查过，不是假设）

| 项 | 结论 | 依据 |
|---|---|---|
| **COM 所有权** | ✅ 严谨 | 62 个裸指针成员，73 处 `ReleaseCom` + 专用 `Release*` 辅助函数（`offscreenTexture_`、`superResolutionTexture_` 等用显式 `->Release()`） |
| **内核空 `catch(...)`** | ✅ 全部合法 | 18 处**全是 `noexcept` 守卫**：存错误消息、触发回调、日志。**没有一处吞掉真实失败** |
| **宿主异常处理** | ✅ 良好 | `播放器控制器.vb` 76 个 catch，**无一处空吞** —— 全部通过 `播放器错误` 事件上报；按类型区分（`ObjectDisposedException`/`OperationCanceledException` 属预期竞态） |
| **事件处理器配平** | ✅ 无泄漏 | 控制器 Add/Remove 看似不配平，但处理器挂在**菜单项**上，而 `Dispose` 里 `菜单.Items.Clear()` ⇒ 处理器随对象销毁 |
| **硬编码路径** | ✅ 无 | 内核与宿主**零** `C:\PLAN` 等绝对路径（仅构建脚本里有，属可接受） |
| **构建** | ✅ 干净 | 内核 MSBuild **0 错误 0 警告**；宿主 `dotnet build` 通过 |

## 4. 打包与部署

### 4.1 内核运行期依赖（必须随包分发）

```
系统:   d3d11 / dxgi / d2d1 / DWrite / D3DCOMPILER_47 / AVRT / ole32 / WinRT
VC 运行库: MSVCP140 / VCRUNTIME140 / VCRUNTIME140_1
FFmpeg:  avcodec-63 / avformat-63 / avutil-61 / swresample-7 / swscale-10 / avfilter-12
第三方:  ass-9 / bluray-3
```

### 4.2 ⚠️ 宿主的 DLL 会过期

本轮发现宿主输出目录里的 `FFF.Native.dll` **早于当前内核**（6:49 vs 12:49）。
⇒ **部署时必须同步拷贝内核 DLL**，否则又会出现版本失配（§1）。

**建议**：给宿主项目加一个 **post-build 步骤**自动拷贝内核 DLL，
或至少在启动时**明确提示版本不符**（现在会抛 `InvalidOperationException`，
但只在构造会话时，用户看到的是"播放失败"而非"版本不符"）。

## 5. 建议优先级（可直接排期）

### P0 —— 立即（本轮已完成）
- ✅ 修复宿主 API 合同（否则播放器不可用）
- ✅ 加 `host_compat_probe` 防复发

### P1 —— 短期
1. **宿主 post-build 自动部署内核 DLL**
   （消除 §4.2 的人工步骤；当前每次改内核都要记得手动拷贝）
2. **启动时友好提示版本不符**
   （现在是构造会话才抛异常，用户看到"播放失败"；应显示"内核版本 18，宿主期望 16"）
3. **把结构体镜像检查自动化**
   （`host_compat_probe` 是手写的；可生成一个"内核结构体字段清单"，
   在宿主构建时比对）

### P2 —— 中期
4. **拆分 `VideoRenderer`（阶段①：只抽结构）** —— 风险低、收益长期
5. **UI 显示 VSR / 光标准确缩放状态**
   （两者已有完整 API，`vsr_probe` 证明可用，但 UI 未接线）

### P3 —— 长期
6. 拆分 `PlayerSession.cpp`（4561 行，同样职责过载）
7. 补齐**非 N 卡 / 无 VSR 驱动**的拒绝路径测试（本机无此硬件）

## 6. 本轮未覆盖

- **非 NVIDIA 硬件**上的 VSR 拒绝路径；
- **独占模式 WASAPI** 行为；
- **小时级**长时间稳定性；
- **多显示器 / 热插拔**（`SetWindow` 与 HDR 重探测路径）；
- **UI 主观体验**（布局、可读性、交互手感）—— 需人工目视。

---

## 7. 一句话结论

**内核与 UI 的工程质量高于平均**（COM 所有权严谨、异常处理有章法、无硬编码），
真正的问题不在细节而在**两侧接口的同步缺乏自动化保障** ——
本轮那个"播放器完全起不来"的缺陷，本质是一次**未被测试覆盖的结构体漂移**。
