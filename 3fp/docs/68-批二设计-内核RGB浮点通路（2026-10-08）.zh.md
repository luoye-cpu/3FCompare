# 68 · 批二设计：内核 RGB 浮点通路（C1）实施方案（2026-10-08）

> 目标：让 JXR 的 `rgbaf16le`（16-bit float）**不再被整数化截断**，使 JXR 的 HDR/宽色域内容完整可用。
> 关联：`docs/65`（可用性分析，实测饱和 2.79%–10.73%）、`docs/67`（浮点语义规范依据，**D 的前置**）
> 状态：**设计定稿，未实施**。实施前需 `docs/67` 回答"无标签 float 的语义"。

---

## 一、问题重述（已实证）

`VideoRenderer.cpp:5103-5145` 的 RGB 分支：

```cpp
auto input = DescribeInput(frame->format);      // rgbaf16le 不在表中 -> {}  (layout=0, bitDepth=16)
const auto directYuv = input.layout != 0;       // false
if (!directYuv) {
    input.bitDepth = max(8, sourceDescriptor->comp[0].depth);   // 16
    const auto convertedFormat = input.bitDepth <= 8 ? AV_PIX_FMT_BGRA : AV_PIX_FMT_RGBA64LE;
    //                                                            ^^^^^^^^^^^^^^^^^^^^^ 无符号整数
    sws_scale(...);   // float -> uint16，>1.0 与 <0.0 全部 clamp
}
```

随后 `EnsurePipeline:3062-3063` 建纹理：
```cpp
if (inputLayout == 0) texture.Format = bitDepth <= 8 ?
    DXGI_FORMAT_B8G8R8A8_UNORM : DXGI_FORMAT_R16G16B16A16_UNORM;   // 无符号整数
```

**双重截断**：① `sws_scale` 到 `RGBA64LE` 时 clamp；② 纹理格式 `_UNORM` 本身也只表示 [0,1]。

实测代价（`docs/65 §2.1`）：`FH4-HDR` 2.79%、`DHR-CoJ1002` 4.76%、`fh2_fp16` 5.73%、
`HDColorHDRCalibration` **10.73%** 的像素通道被饱和。

## 二、关键可行性结论：**内核已有全部所需部件**

这是本设计最重要的发现 —— **不需要新建渲染管线**，只需把已有部件接上。

| 部件 | 现状 | 证据 |
|---|---|---|
| FP16 纹理格式 | ✅ 已在用 | `DXGI_FORMAT_R16G16B16A16_FLOAT` 在 `:2628/2723/2804/4010/4381/4455/5457` 等多处 |
| FP16 scRGB 呈现链 | ✅ 已在用 | `:2796` 注释「1 = RGBA16F (linear scRGB, for HDR and wide-gamut SDR)」 |
| 着色器 RGB 分支 | ✅ 已有 | `InputLayout==0` → `ReadSource` 直接取 `.rgb`（`:633`），**不做 YUV 反矩阵** |
| **负值**承载 | ✅ **已明确支持** | `:744` 注释「both are pure linear maps whose **negative components FP16 carries as-is**」 |
| 线性/scRGB 输出 | ✅ 已有 | `ColorMode==2` 分支（`:740-747`）→ `rec709Nits/80.0` |
| 换色域矩阵 | ✅ 已有 | `Gamut` 三态（0=709 / 1=2020 / 2=P3），`:745` |

⇒ **[VERIFIED·高] C1 = 「让 `rgbaf16le` 走 FP16 纹理 + 正确的 Transfer/Gamut 标志」，而非新建通路。**

**特别注意 `:744` 的既有注释**：内核作者**已经**为 P3 的负分量预留了 FP16 承载 —— 说明
"浮点负值"在这个渲染器里是**被设计考虑过的**，C1 与既有设计意图一致。

## 三、实施方案（4 处改动，全部集中在 `VideoRenderer.cpp`）

### 改动 1 · `DescribeInput` 增加浮点 RGB 支持（`:1091-1137`）

当前 RGB 一律落 `default: return {}`。需新增一个**浮点 RGB layout**：

```cpp
// 建议：新增 layout 值 3 = FP16 RGB（与 0=BGRA/unorm、1=YUV420、2=NV12 并列）
case AV_PIX_FMT_RGBAF16LE:
case AV_PIX_FMT_RGBAF16BE:
    return {3, 16, 1.0f, 0, 0};      // FP16：bitDepth=16 但语义是"浮点全域"
```

⚠ **注意**：`bitDepth=16` 会被下游用于选纹理格式（`bitDepth <= 8 ? BGRA : R16G16B16A16_UNORM`）。
所以**必须**用新的 `layout` 值区分，不能只改 `bitDepth`，否则仍走 UNORM。

### 改动 2 · RGB 转换分支跳过 clamp（`:5110-5145`）

新增：当源是浮点 RGB 时，**不做 sws_scale 到整数**，而是：

- 方案 a（推荐）：**直接上传 float 数据**（保持 `rgbaf16le` 布局，转成 `DXGI_FORMAT_R16G16B16A16_FLOAT` 纹理）。
  半精度 float 与 D3D `R16G16B16A16_FLOAT` **逐位兼容**，无需 swscale。
- 方案 b：若需 alpha 重排（RGBA vs BGRA），用 `sws_scale` 到 `AV_PIX_FMT_RGBAF16`（浮点目标，不 clamp）。

⇒ **方案 a 零拷贝**（除必要的行重排），且**完全保留负值与超白**。

### 改动 3 · `EnsurePipeline` 纹理格式（`:3062-3063`）

```cpp
if (inputLayout == 3)      texture.Format = DXGI_FORMAT_R16G16B16A16_FLOAT;
else if (inputLayout == 0) texture.Format = bitDepth <= 8 ?
    DXGI_FORMAT_B8G8R8A8_UNORM : DXGI_FORMAT_R16G16B16A16_UNORM;
```

⚠ 同时要检查 `bytesPerPixel` 与 `ResizeVideoConversionBuffer` 的尺寸计算（`:5120/5139-5140`）
对 layout 3 是否成立（FP16 = 8 字节/像素，与 `RGBA64LE` 相同）。

### 改动 4 · 着色器：`InputLayout==3` 的语义

因为 `:633` 已是 `if(InputLayout==0) return ...Source.rgb`，**最省的做法**是让 layout 3
在着色器里**复用 layout 0 的读取分支**：
```hlsl
if(InputLayout==0 || InputLayout==3) return SampleVideo(Source,uv).rgb;
```
需改 `:633`、`:650`、`:680`（三处 `ReadSource*` 系列）。

⚠ **但有一条更重要的语义要求**：FP16 的 JXR 数据是**线性**的（scRGB 惯例），而
`InputLayout==0` 的现有语义是**编码域**（`Transfer` 决定曲线）。所以：

- 必须同时把 `settings.transfer` 设为 **"已是线性"**（避免二次 PQ/HLG 解码），
- 并把 `Gamut` 设为正确值。

这与 `docs/67` 的结论**强耦合** ⇒ **D 必须先行**（见 §五）。

## 四、改动面与风险

| 项 | 评估 |
|---|---|
| 涉及文件 | **1 个**（`VideoRenderer.cpp`），4 处 |
| 着色器改动 | 需改 3 行 HLSL → **必须**跑 `tools/generate_shader_bytecode.py` 重生成 `ShaderBytecode.h` |
| 对现有格式影响 | **零**：layout 3 是新增值，既有 layout 0/1/2 分支不变（需以回归证明） |
| 硬解路径 | 不涉及（JXR 走软解） |
| 视频路径 | 不涉及（JXR 是 static image） |
| 主要风险 | ① `InputLayout` 新值需与着色器约定**同步**（注释 `:257-258` 明确要求）；② `bytesPerPixel` 尺寸计算需核对；③ 需真机目视确认 |

> ⚠ `:257-258` 的既有告警：「Regenerate ShaderBytecode.h with tools/generate_shader_bytecode.py
> after HLSL changes. Gamut is tri-state (709/2020/P3); source and bytecode must stay in sync.」
> ⇒ 改 HLSL 后**必须**重生成，否则运行期静默失效。

## 五、阻塞项：**D 必须先行**

**[INFERRED·高]** 改动 4 要求知道"无标签 float JXR 的传递函数与色域"，这正是 `docs/67` 的问题。
在 `docs/67` 给出结论前，**不应**实现改动 4 —— 否则会把"截断"换成"用错曲线"，问题更隐蔽。

**可选的安全中间态（推荐先做）**：
实现改动 1–3（**保留浮点、不截断**），但**暂不改 Transfer/Gamut**。
效果：数值完整性恢复（负值/超白不再丢失），呈现曲线仍按现有 SDR 逻辑。
好处：把"数值截断"与"语义判定"两个问题**解耦**，前者可独立验证、可独立回滚。
