## 〇、一句话结论

3FP 目前有 HDR10+ 的**识别能力**，没有 HDR10+ 的**映射能力**：`AV_FRAME_DATA_DYNAMIC_HDR_PLUS` 全仓库仅在一处被读，且只取 `params[0].maxscl` 的通道最大值乘 10000 当作 `sourcePeakNits`；ST 2094-40 真正定义色调映射曲线的 `knee_point`、`bezier_curve_anchors`、`distribution_maxrgb` 一个都没读，也没有任何逐帧参数通道进入着色器。对外却上报 `processingPath = Hdr10PlusDynamic`（文案 `"HDR10+ metadata-guided display mapping"`）——**名不副实**。

> ✅ **先说一处不是缺陷的地方**：`maxscl × 10000` 的换算**是正确的**（`maxscl` 是已线性化的量，1.0 = 10000 cd/m²）。本轮初稿曾误判其为缺陷，已在 §1.3 翻案并留档。真正的缺口是"曲线参数完全没读"，不是"峰值算错了"。

本规划给出把"HDR10+ 元数据真正驱动色调映射"做实的完整路径，含必须同批修掉的一项既有正确性缺陷（transfer 推断）。

### 1.3 G4 翻案：`maxscl × 10000` **是正确的**（本轮复核订正）

> ⚠ **本节是规划过程中的一次自我纠错留档。** 初稿曾把 `maxscl × 10000` 判为语义错误并列为"正确性缺陷 G4"，**该判定是错的**，现予翻案。留下过程是因为这个坑很容易再踩一次。

**头文件原文**（`libavutil/hdr_dynamic_metadata.h:150-157`）：

> The maximum of the color components of **linearized RGB** values in the processing window in the scene. The values should be in the range of **0 to 1** ... `maxscl[0..2]` correspond to R, G, B.

**关键在 "linearized"**：`maxscl` 是**已经在光域（线性域）**的量，归一化到 1.0 = PQ 峰值 10000 cd/m²。它不是 PQ 编码码值，因此**不需要**再做一次 ST 2084 反 EOTF。

⇒ 正确的换算就是朴素的线性比例：

```
nits = maxscl × 10000
```

`0.0334 × 10000 = 334 nits` —— **现实现正确**。

**数值反证**（本轮实算）：若把 `maxscl` 当作 PQ 归一化信号去反 EOTF（`PqCodeToNits(0.0334 × 4095)`），得到 **0.02 nits** —— 即"整段视频峰值是纯黑"。对一个官方测试向量而言荒谬。334 nits 才合理。

**独立第三来源**：`3fp/docs/archive/status-log-2026-09` 记录该项目实测时**与 ffprobe 对拍**（"=SEI maxscl 0.0334×10000，与 ffprobe 对拍精确吻合"），即已用独立实现验证过。⇒ `3fp/docs/20` 附录的"✅ 精确吻合"判定**成立，不应订正**（初稿要求订正该文档，撤销）。

**顺带核实**：`PqCodeToNits()`（`:39-49`）本身**也是正确的**。本轮曾误读其运算符优先级以为它把指数只作用到分母上（算出 138,901,065 nits），实际表达式是 `pow(max(...)/denominator, 1/m1)`，指数作用于**整个比值**；实算 `code=4095 → 10000.00 nits`，`code=2048 → 92.36 nits`，完全正确。**该函数无需改动**（初稿曾提议复用它替换 G4 的写法，现撤销——G4 本来就没有可替换的东西）。

**对规划的净影响**：G4 从缺陷清单移除，`sourcePeakNits` 的既有语义保留不变；§3.2、阶段 1、§十 中与之相关的条目同步订正。**这不削弱本规划**——HDR10+ 的真实缺口是 G1/G2/G3/G5（曲线参数、多窗口、逐帧通道、targeted display 亮度），它们与 G4 无关。

## 三、核心设计

### 3.1 三个数据面 + 一条门控

**关键洞察**：HDR10+（2094-40）与 HDR Vivid（2094-30）的元数据结构**形状高度同族**（都是"多窗口 + 分布百分位 + 曲线锚点"），但**曲线语义不同**（40 用 `knee_point` + bezier 锚点；30 用三样条）。⇒ **数据面统一、解释层分离**。

#### 数据面 A · 元数据快照（`HdrProcessor` 内部）

`HdrFrameState` 在多处按值传递，且 `State()`（`:361-364`）每次加锁返回副本 ⇒ 新结构必须**定长、平凡可拷贝**（禁止 `std::vector`）。

```cpp
// 新文件：3FP/Hdr/HdrDynamicMetadata.h（HdrProcessor 与 VideoRenderer 共享）
enum class HdrMetadataKind : std::uint32_t { None = 0, Hdr10Plus = 1, HdrVivid = 2 };

struct HdrDistributionPoint {          // = AVHDRPlusPercentile 一项
    std::uint8_t percentage = 0;       // ⚠ 字段名是 percentage（uint8_t，0..100）
    float linearizedMaxRgb = 0.0f;     // ⚠ 字段名是 percentile（AVRational，0..1）——命名与语义相反！
};

struct HdrProcessingWindow {
    bool valid = false;                // 该窗口是否可用（含降级判定）
    float upperLeftX = 0.0f, upperLeftY = 0.0f;      // 归一化 [0,1]
    float lowerRightX = 1.0f, lowerRightY = 1.0f;
    float maxScl[3] = {0.0f, 0.0f, 0.0f};            // 线性化 RGB（0..1），nits = ×10000
    float averageMaxRgb = 0.0f;
    float fractionBrightPixels = 0.0f;
    std::uint8_t distributionCount = 0;              // 规范上限 15
    HdrDistributionPoint distribution[15] = {};
    bool toneMappingPresent = false;                 // tone_mapping_flag == 1
    float kneePointX = 0.0f, kneePointY = 0.0f;      // [0,1]，toneMappingPresent 时有效
    std::uint8_t bezierAnchorCount = 0;              // 规范上限 15
    float bezierAnchors[15] = {};                    // [0,1]
    // 派生量（解析时算好，渲染时不再算）
    float signalPeakNits = 0.0f;                     // max(maxScl) × 10000
    float distributionPeakNits = 0.0f;               // 最高百分位 maxRgb × 10000
};

enum class HdrMetadataDegrade : std::uint32_t {
    None = 0,
    WindowCountInvalid = 1,        // num_windows ∉ [1,3]
    NonMonotonicDistribution = 2,  // 百分位/maxRgb 非单调
    AnchorsOutOfRange = 3,         // bezier 锚点越界或 knee 退化
    ToneMappingAbsent = 4,         // tone_mapping_flag == 0
    TooFewAnchors = 5,             // 锚点数不足以重建曲线
    NonFiniteValues = 6,           // av_q2d 出 NaN/Inf
};

struct HdrDynamicMetadata {
    HdrMetadataKind kind = HdrMetadataKind::None;
    std::uint8_t windowCount = 0;                    // 已校验的有效窗口数 ∈ [0,3]
    HdrProcessingWindow windows[3] = {};
    float targetedDisplayNits = 0.0f;                // av_q2d(值) × 10000 → cd/m²（见 §3.2）
    bool hasTargetedDisplay = false;
    HdrMetadataDegrade degrade = HdrMetadataDegrade::None;
    std::uint64_t serial = 0;                        // 更新计数（诊断/去重）
    std::uint64_t heldFrames = 0;                    // 已沿用多少帧（见 §5.2）
    HdrDynamicMetadata() noexcept = default;         // 平凡拷贝
};
```

挂到 `HdrFrameState`：`HdrDynamicMetadata dynamic;`

**窗口上限取 3 的依据**：`AVDynamicHDRPlus` 声明 `params[3]`，规范 `num_windows ∈ [1,3]`。`num_windows == 2` 或 `> 3` 属非规范流 ⇒ 置 `WindowCountInvalid` 并**只用窗口 0 当全帧**，同时保留诊断标记（不静默）。

#### 数据面 B · 逐帧着色器常量

**新增独立 constant buffer，不修改现有 `ShaderSettings` 布局**——这直接服务 T5：无元数据时该 buffer 全零，着色器走原分支，逐位不变即结构性保证。

### 3.2 关键数值决策（逐条给依据）

| 决策 | 依据 |
|---|---|
| `maxscl` → nits 用 **`× 10000`**（**保持不变**） | 头文件 L150-157：`maxscl` 是**已线性化**的 RGB（"linearized RGB"），1.0 = 10000 cd/m² ⇒ 朴素线性比例即可。详见 §1.3 的翻案 |
| `targeted_system_display_maximum_luminance` **× 10000** 得 cd/m² | 头文件 L265-268：*"in units of **0.0001** candelas per square metre"*。⚠ 极易漏乘 |
| `targeted_system_display_maximum_luminance` **优先**于 `maxscl` 作为 `sourcePeakNits` | 规范明确它是"targeted system display 的标称最大显示亮度"，是**权威目标**；`maxscl` 是内容统计量 |
| `distribution_maxrgb` 的两个字段**命名与语义相反**，极易写反 | `hdr_dynamic_metadata.h:39-53`：`uint8_t percentage` 是**百分比**（0..100），`AVRational percentile` 是**线性化 maxRGB 值**（0..1）。⚠ 按字段名想当然会取错量，且两者都在 [0,1]/[0,100] 内不会立刻报错 |
| 所有 `AVRational` 经 `av_q2d` + `std::isfinite` 校验 | 与现有 `ValidPeak`/`ValidLuminance`/`ValidChromaticity`（`:24-37`）风格一致 |
| 分布/锚点按**单调性**校验，违反则丢弃该字段并降级 | bezier 重建要求锚点单调；用假数据 clamp 会产出错误曲线，比降级更糟 |
| 派生量在**解析时**算好，存进快照 | 渲染热路径不做重复计算；也让探针能直接读 |

### 3.3 门控与「逐位不变」的证明义务

`DynamicHdrSettings.enabled = (metadata.kind != None && windowCount > 0 && degrade != 阻塞性) ? 1 : 0`

**着色器中原色调映射公式必须保持为 `if (enabled == 0)` 的那条分支，且该分支内部表达式一个字符都不能改。** 这样 T5 是结构性保证，而非依赖测试运气。

**关于降级是否仍置 `enabled=1`**：区分两类降级——
- **阻塞性**（`ToneMappingAbsent`、`TooFewAnchors`、`NonFiniteValues`、`WindowCountInvalid`）⇒ `enabled = 0`，退回静态 BT.2390（即当前行为）。
- **非阻塞**（`NonMonotonicDistribution`）⇒ `enabled = 1`，曲线用 knee+锚点正常重建，仅不使用分布峰值。

## 四、ST 2094-40 曲线重建算法（方案 B 主体）

> **这是本规划最容易做错的部分。** 以下按 `3fp/docs/22` 与规范语义给出可实现的完整定义。

### 4.1 规范给的是什么

ST 2094-40 对每个处理窗口给出一条**色调映射函数**：

- **线性段**：`[0, knee_point_x]` 上 `y = (knee_point_y / knee_point_x) · x`
- **曲线段**：`[knee_point_x, 1]` 上，从 `(knee_point_x, knee_point_y)` 到 `(1, 1)` 的曲线，由 `num_bezier_curve_anchors` 个**中间锚点** + 两个端点定义。

锚点在文档中表述为 *"intermediate anchor parameters of the tone mapping function"*。**规范未强制接收端的插值方法**（这是本方案最大的自由度，也是最需要论证的地方）。

### 4.2 采用的重建方法：单调三次 Hermite（PCHIP）通过锚点

**选择理由**：
- **单调性保持**：色调映射函数必须单调不减，否则画面出现反相/色带。PCHIP（Piecewise Cubic Hermite Interpolating Polynomial）**按构造保证单调**，普通三次样条不保证。
- **端点行为可控**：两端斜率可显式指定，天然满足"从 `(knee_x, knee_y)` 到 `(1,1)`"。
- **可实现**：算法约 40 行，无迭代、无需求解线性方程组。

**具体步骤**：

```
输入：knee_x, knee_y, anchors[0..n-1]（已在 [0,1]），n = num_bezier_curve_anchors
1. 若 !tone_mapping_flag 或 n < 1 → 降级（走静态 BT.2390）
2. 构造节点序列，x 坐标均匀分布（规范对锚点只给 y 值）：
     x_i = knee_x + (1 - knee_x) * (i + 1) / (n + 1),   i = 0..n-1
     y_i = anchors[i]
   端点： (x_{-1}, y_{-1}) = (knee_x, knee_y)，(x_n, y_n) = (1, 1)
3. 校验单调不减：knee_y <= y_0 <= y_1 <= ... <= 1
   违反 → 丢弃曲线段，线性段保留，置 degrade
4. 计算调和平均斜率（PCHIP 标准公式）：
     d_i = 0                     若 delta_{i-1} 与 delta_i 异号或任一为 0
     d_i = (w1 + w2) / (w1/delta_{i-1} + w2/delta_i)   否则
     其中 delta_i = (y_{i+1} - y_i) / (x_{i+1} - x_i)，w1 = 2h_i + h_{i-1}，w2 = h_i + 2h_{i-1}
5. 逐段三次 Hermite：
     t = (x - x_i) / h_i
     h00 = 2t³-3t²+1, h10 = t³-2t²+t, h01 = -2t³+3t², h11 = t³-t²
     y = h00·y_i + h10·h_i·d_i + h01·y_{i+1} + h11·h_i·d_{i+1}
```

### 4.3 定义域与值域

- 曲线作用于**归一化 PQ 信号**（`x` = `pq / sourcePq`，与现有 `Bt2390HdrToSdrPq` 的口径一致）。
- 输出乘以 `sourcePq` 回到 PQ 域，再 `×10000` 转 nits。
- 最终 targetPeak = `min(targetedDisplayNits, 显示器峰值)`；若 `targetedDisplayNits` 缺失则回退 `ResolveTargetPeak()`（`:451-460`）。

### 4.4 CPU 端参考实现 + GPU 端镜像

**关键工程决策**：曲线在 **CPU 端逐帧求值成 LUT**，而非在 shader 里跑 PCHIP。

| 方案 | 评价 |
|---|---|
| **CPU 求值 → 256 项 1D LUT → 采样** | ✅ shader 端只需一次纹理采样或线性插值求值；**CPU 实现可单测**（与方案 B 的验证需求完美契合）；避免 shader 里的分支/horner 展开 |
| shader 内联 PCHIP | ❌ 每像素算斜率与分段查找，分支发散、难验证、cbuffer 传 15+ 锚点×3 窗 |

⇒ 新 cbuffer 只传 **LUT 的少量控制信息**（或直接把 LUT 放进一张 256×1 纹理/RW 常量），**§3.1 的 `windows[3][28]` 据此可精简**。LUT 分辨率 256 对 SDR 输出（8/10bit）足够；若未来 16bit 输出需评估提升到 1024。

**这条决策同时解决了 §3.1 数据面 B 的 cbuffer 容量问题**，是最优解。

### 4.5 MapToHdr 路径（T3）

MapToHdr 下着色器不做映射（`:719-726` 直接线性转 scRGB），映射交给 DWM。故 HDR10+ 的价值在于**逐帧更新 `DXGI_HDR_METADATA_HDR10`**（`SetHdrMetadata()`，`:4433-4447`，由 `:4543` 每帧调用）：

- `MaxContentLightLevel` ← 当前帧 `distributionPeakNits`（或 `signalPeakNits`）
- `MaxFrameAverageLightLevel` ← 当前帧 `averageMaxRgb` 反变换
- `MaxMasteringLuminance` ← **保持静态母版值**（规范要求，不得逐帧变）

**必须限流**：`SetHDRMetaData` 有开销，且 DWM 对频繁变更有平滑。仅当新值与当前值差异 > 阈值（建议 2%）才提交。注意 `:4562` 已有一次"extension applied 后重调"的调用点，改造时要一并覆盖。

## 五、必须处理的工程风险

### 5.1 「只加不改」与"逐帧变化"的张力 —— 最高风险

铁律 2 要求视频路径行为不变，但 HDR10+ 动态映射**本质就是改变视频路径行为**。**已裁决 D1：按 `3fp/README.md` 铁律 2 的既有例外条款处理**（该条款原文允许"确属既有缺陷且对视频也有害的修正"，K1–K4 为先例）：

> 唯一例外：内核里确属**既有缺陷**且对视频也有害的修正（K1/K2/K3/K4），
> 但它们也必须保持"视频路径行为不变"，且单独成提交，便于上游单独评估。

⇒ 本改动必须满足：**① 拆独立提交；② 无 HDR10+ 元数据的流逐位不变**（可证明、可测的强条件：`enabled == 0` 分支即原代码）。

### 5.2 元数据抖动与缺失帧（G8）

真实 HDR10+ 流并非每帧都带 SEI。当前逻辑"本帧无 side data ⇒ `dynamicSourcePeak=false` ⇒ 回退静态元数据"会导致**峰值逐帧跳变**，观感是画面忽明忽暗。

**必须实现「保持（hold）」语义**：本帧无元数据 ⇒ 沿用上一帧的 `HdrDynamicMetadata`，直到出现新元数据或 seek/切流。用 `heldFrames` 计数。

**但必须有上界**：连续 N 帧（建议 60，约 1–2 秒）无元数据 ⇒ 判定"该流实际不携带动态元数据"，退回静态路径并置诊断标记。避免 seek 后长期持有陈旧元数据。

### 5.3 窗口边界的接缝（多窗口必现）

`num_windows == 3` 时，相邻窗口参数不同 ⇒ 边界处出现**可见竖条/横条**。必须定义过渡带（建议宽度 = 窗口跨度的 5%），带内对映射参数**线性插值**。这是实现细节但直接决定观感，不可省。

### 5.4 `HdrFrameState` 体积与冗余加锁

新 `HdrDynamicMetadata` 是定长小结构（约 700 字节），拷贝可接受。但注意：`VideoRenderer.cpp:4619` 调 `hdrProcessor_.State()` 又锁一次，而 `ProcessFrame` 刚返回 `hdrState`（`:4461`）——**这是既有冗余**。改用已返回的 `hdrState` 是安全的顺手清理，但**要单独成提交并说明**，避免混进功能改动。

### 5.5 性能

- 解析 + LUT 生成是纯 CPU、每帧几百次浮点运算 ⇒ 可忽略。
- 真正风险：① 多窗口在片元着色器的分支发散（用 LUT 后已大幅缓解）；② `SetHDRMetaData` 调用频率（限流解决）。
- 二者都要在 4K/60 高码率下实测（§7 阶段 6）。

### 5.6 生成物与 ABI

- `Render/ShaderBytecode.h` 是生成物，改 HLSL 后重新生成，diff 巨大（`PATCHES.md` §十三 先例：+13041/−13004）属预期。
- 新增快照字段 ⇒ `FFF3FPSnapshot` 布局变化。⚠ **上游有"改结构体布局但不升 `PlayerApiVersion`"的前科**（`PATCHES.md` §〇）。本改动**必须**升 `PlayerApiVersion` 并同步托管侧 `Marshal.SizeOf`/字段偏移（`Fff3FpNative.cs`）。这是 3FC 侧的硬约束。

### 11.2 ⚠ 规划初稿的一处**错误**已被实机推翻

§3.2 曾断言 `targeted_system_display_maximum_luminance` 须 × 10000（依据头文件"units of 0.0001 cd/m²"）。

**实测错误**。ffprobe 对 FATE 样本报 `targeted_system_display_maximum_luminance=400/1` ——
**libavutil 在解析 SEI 时已归一化为 cd/m²**，那个 0.0001 只属于比特流编码层。
再乘 10000 得 4,000,000，被 `clamp(...,1,10000)` **静默饱和成 10000** —— 一个"看起来合理"的错值，
没有任何报错。修正后实测 `targeted=400`，与 ffprobe 精确一致。

**教训**：头文件描述的是**比特流**语义，不等于**结构体字段**语义。凡"单位换算"类判断，
必须拿独立实现（ffprobe）对拍，不能只读文档。

### 11.3 解析层对真实内容做了两处放宽（规划初稿过严）

用真实 FATE 向量测试后，初稿的两条校验被证明会**拒绝真实元数据**：

| 初稿校验 | 真实数据 | 处置 |
|---|---|---|
| `knee_point_x` 必须 > 0（按头文件"excluding 0"） | FATE 样本编码 `knee_point_x=0/4095` | **放宽为接受 0**：knee=0 表示"无线性段"，锚点铺满全区间，是合法编码 |
| `distribution_maxrgb` 的 maxRGB 列必须随 percentage 单调 | FATE 样本在 5% 处为 0.0294，10% 处 0.00255 —— **非单调** | **取消单调性要求**，仅校验取值范围；峰值改取 `max()` 而非最后一项 |

⇒ 若不实测，这两条会让真实 HDR10+ 内容**全部降级**，功能等于没做，且不会有任何报错。

### 11.5 ABI 连锁：必须与 3FC 同步改

新增快照字段使 `FFF3FPSnapshot` 长大 32 字节。内核按 `size < sizeof(FFF3FPSnapshot)` **拒绝**过小的调用方，
而托管侧 `Fff3FpEngine.cs:378` 发送的是 `Marshal.SizeOf<Fff3FpSnapshot>()` ⇒ **两侧必须同批增长**，
否则 `GetSnapshot` 整体失效。已同批完成：

- 内核 `FFF3FPSnapshot` 尾部 +5 字段；`PlayerApiVersion` **16 → 17**
- 托管 `Fff3FpNative.cs` 同尾 +5 字段；`Fff3FpEngine.ConfigVersion` **16 → 17**
- 实测两侧 `368 B` 一致

### 11.6 ⚠ 探针 ABI 陷阱（排查过程中真实踩到）

`3fp/tools/build_probe.py` 的 `#include "FFF.Player.Api.h"` 解析自 **`3fp/kernel`**（API **19**），
而本次改的出货树是 API **17**。用 `read_pixel_probe.exe` 去读 API-17 的 DLL 会**按错误偏移解释字段**，
症状是一个**看似合理的错值**（曾据此误判 Vivid 出现 `peak=4000` 回归，实为布局错读）。

⇒ 新增 `3fp/tools/hdr10plus_kernel_probe.cpp`，**直接对 `third_party/fff_project` 头文件编译**，
读到的布局与 DLL 一致。**凡跨这两棵树读快照的探针都必须先确认 `FFF3FP_GetApiVersion()` 与探针编译期版本相符**
（该探针已把版本打印出来自证）。

### 11.6b 阶段 2（transfer 修正）**已评估后主动放弃**，理由如下

规划把 `docs/22` 的 transfer 缺陷列为阶段 2 必做项。**实施前复核发现该缺陷已被修复**：

- 出货树 `VideoRenderer.cpp` 已实现 `docs/22` 方案 A（`frameDeclaresTrc` / `transferFromFrame`），
  系早前重移植时带入。
- 残留的仅是一个**边界条件**：`... && transferFromFrame != 0u`，即"帧 trc = BT.709（值 0）但元数据把流分类为 HDR"
  才会回落到 format 推断。该组合是**畸形输入**（ST 2094-40 定义在 PQ 上）。
- 两种处置都说得通（信元数据意图 vs 信像素 trc），**且无任何失败用例或现实素材指向其一**。

⇒ **按"只加不改"原则，不值得为一个无证据的推测性行为改动背书**，已把改动**完全回退**
（`git checkout` 后 `git status` 干净，未被任何提交包含）。
该残留条件作为**开放问题**记入 §九（Q6），留待有真实素材时再定。

**教训**：规划里的"必做缺陷修复"清单**必须在实施前重新核对当前代码**——
规划基于某时点的代码状态，而缺陷可能已被上游或自己的早期重移植修掉。照单执行会改出无谓的行为变化。

## 十二、实施记录（阶段 3–5 完成）

### 11.8 着色器接线：b2 + LUT，而非规划里的 b1

规划 §3.1 写"新增独立 cbuffer（b1）"。**实测 b1 已被占用**：`extensionConstants_`（Dolby Vision 颜色扩展）在**每次 draw 都无条件绑定** b1（`VideoRenderer.cpp:3250`）。占用会与扩展路径互相覆盖。

⇒ 改用 **register(b2)**（常量缓冲）+ **register(t3)**（256×3 R32_FLOAT 曲线 LUT）。t0–t2 是 Source/ChromaU/ChromaV，t3 空闲。

### 11.9 ⚠ 我自己写错了一版组合，被实测抓出

第一版把 ST 2094 曲线**直接替换** BT.2390 映射。结果 HDR10+ 五个采样点里五个全部饱和到 `1.00000` —— 因为曲线近恒等时**没有任何压缩**，高光直接削顶。

**正确的组合是两段**：
1. ST 2094 曲线：内容信号 → 内容自己的目标显示（逐帧/逐窗变化的部分）
2. BT.2390：目标显示 → 本机 SDR 峰值（压缩）

修正后 `G/B` 从 `0.96285/0.95797` 变到 `0.95503/0.95112`（约 2 个 8bit 码），`R` 前后都是 `1.00000`（该测试图的红色本身已饱和）。方向与幅度都合理。

**教训**：曲线是"内容→目标显示"的映射，**不是**"内容→任意显示"的映射。少掉第二段就会削顶。

### 11.10 布局验证用反射，不靠人眼数行

HLSL 的 16 字节寄存器行规则会让"两个标量共用一行"的写法**静默加宽** cbuffer，使后续所有字段错位。因此：

- HLSL 侧编译后用 fxc 的 `RDEF` 块读回：`DynamicSettings size=80`、`Settings size=128`
- C++ 侧 `static_assert(sizeof(DynamicShaderSettings) == 80)`
- 两侧一致才继续

（首版我写了 `float3 DynamicPadding` 凑数，反射会显示 80 而 C++ 是 76 —— 靠反射才确认下来。）

同时验证**7 个着色器数组里只有主像素着色器变化**，其余 6 个逐字节相同。

### 11.11 Vivid：**明确不做曲线**，并让快照如实报告

规划的"架构留位"在实现时遇到硬约束：Vivid 的色调映射是**另一套曲线族**（参数化 `base_param_m_p/m_m/m_a/m_b/m_n` + 可选 three-spline），不是 HDR10+ 的 knee+bezier。而定义该公式的 **CUVA 005.1 规范原文拿不到**（UWA 官网下载有登录门禁；同仓库 `3fp/docs/61` 今日已独立确认此事）。

⇒ **不发明公式**。Vivid 保持原有"只取峰值"行为，`toneMappingPresent=false` 并上报 `ToneMappingAbsent`，快照如实说明它没有走动态路径。共享的窗口结构仍然填充，将来补真公式是**纯增量**。

### 11.12 阶段 5：MapToHdr 的逐帧元数据 + 限流

- `MaxContentLightLevel` / `MaxFrameAverageLightLevel` 改为跟随逐场景 ST 2094 值（这正是动态元数据在"显示器自己 tone map"时的价值）
- `MaxMasteringLuminance` **保持静态**（规范要求：它描述的是母版显示器）
- **限流**：亮度字段变化 >2%（或 primaries 变化）才提交 `SetHDRMetaData`，否则每帧提交会让显示器色调映射"追着跑"（hunting）

### 11.14 ⚠ 已知局限（未验证的部分，如实列出）

1. **没有真实 HDR10+ 影视素材跑过端到端**。FATE 向量是合成梯度图，其曲线**近恒等**，几乎不锻炼这条路径。已改用**离线组合映射单测**（非恒等曲线）来补偿，但那验证的是数学，不是真实片源观感。
2. **多窗口（`num_windows=3`）未在真实素材上验证**。过渡带宽度 `kDynamicWindowBlend=0.05` 是经验值，仅由代码路径覆盖，无观感确认。
3. **59.94/23.976 等帧率下的元数据 hold 上界（60 帧）** 未做长播实测（60 帧在 23.976fps 下约 2.5 秒，在 60fps 下约 1 秒，差异较大）。
4. **实机 HDR 显示器**上的逐帧元数据闪烁未人眼确认（本机是否有 HDR 屏未确认）。限流逻辑只有代码级保证。
5. `read_pixel_probe`（`build_probe.py` 产物）与出货树 **API 不同步**（前者 API 19 头文件），直接用它读出货树 DLL 会按错误偏移解释字段、给出**看似合理的错值**。我另行编译了 `3fp/build/hdr10plus-run/read_pixel_probe.exe` 对 `third_party` 头文件。**这是工具链陷阱，不是内核问题**（§11.6）。
