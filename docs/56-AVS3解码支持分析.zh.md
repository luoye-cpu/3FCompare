# 56 - AVS3 解码支持分析（AVS3-P2 / IEEE 1857.10，附 AVS2 / AVS1）

- 分析对象：3FP（上游 Lake1059/FFF_Project）内核 `3fp/kernel/FFF.Native`
- 本报告为**只读分析**，未修改任何源码
- 所有"实测"均由本机运行真实 DLL / `ffmpeg.exe` 得到，命令与输出可复现

> ⚠️ **本报告含一处对初始预设的重要纠正**：任务简报假设"运行期 FFmpeg = 构建脚本下载的 BtbN LGPL 包"。实测**该假设不成立**——`runtime/` 与 `publish/PLAN/ffmpeg-full/` 里的 DLL **都不是** BtbN LGPL 产物，而是第三方自编译的 **GPL + nonfree** 构建。而**真正含 AVS3 解码器的恰恰是被弃用的 BtbN LGPL 缓存**。详见 §2.5 与 §5。

## 一、结论先行（是否支持／能否支持）

### 1.1 核心结论

1. **当前 `runtime/avcodec-63.dll` 没有 AVS2 / AVS3 解码器。** 298 个可用解码器中 AVS 家族只有 `avs`（AVS1）与 `cavs`（AVS1-P2 基准档）；`avs2`/`avs3`/`libuavs3d`/`libdavs2` **全部不存在**（`avcodec_find_decoder_by_name` 逐名实测为 ABSENT）。
2. **容器层完整。** `avformat-63.dll` 注册了真正的 `avs`、`avs2`、`avs3`、`cavsvideo` 解复用器，能把码流正确识别为 `Video: avs3`（codec id 193）⇒ **能开、能解出流、能读宽高帧率，但解不了码**。
3. **打开 AVS3 文件的最终结果**：一路走到内核 `PlayerSession.cpp:2245` 的 `avcodec_find_decoder(193)` 拿到 nullptr → `:2248` 返回 `NotSupported` → `:2463` 报 **"Could not open a hardware or software video decoder."**。**不是"找不到视频流"，也不是"格式不支持"。**
4. **AVS3 在 FFmpeg 里从来只有外部库一条路**（`libuavs3d` 包装器）。上游**没有**、也**从未有过**原生 AVS3 解码器；AVS2 同理**没有**原生解码器（只有 `libdavs2` 包装器）。§4.1 有源码级证明。
5. **好消息：AVS3 是"零代码"可达的。** 真正带 `libuavs3d` 的 BtbN LGPL 构建就在本机缓存里（§2.5，#4），把它换进运行目录即可解码 —— 内核与宿主**一行都不用改**（§4.4）。
6. **坏消息：换了会踩许可证红线。** 当前 `publish/PLAN/ffmpeg-full/`（实际随完整版发布的产物）内嵌 **`libavcodec license: nonfree and unredistributable`**（§5.4），而 `tools\发布门禁.ps1` 与 `pack.ps1` **都没有任何 FFmpeg 许可证检查**。

### 1.2 一张表看清"支持到什么程度"

| 能力层 | AVS1 (`avs`) | AVS1-P2 (`cavs`) | AVS2 (`avs2`) | AVS3 (`avs3`) |
|---|---|---|---|---|
| 解复用器（能开容器） | ✅ | ✅ | ✅ | ✅ |
| parser（能读序列头） | ❌ | ✅ | ✅ | ✅ |
| **当前 runtime 解码器** | ✅ | ✅ | ❌ | ❌ |
| **BtbN LGPL 缓存解码器** | ✅ | ✅ | ❌ | ✅ `libuavs3d` |
| 3FP 当前能否播 | ✅ | ✅ | ❌ | ❌ |
| 硬件解码（D3D11VA） | ❌ | ❌ | ❌ | ❌ |

> **"有 parser ≠ 有 decoder"** 是理解本问题的关键，也解释了预审中"avs3 字面量只出现在描述性字符串表里"的现象（§2.4）。


### 3.3 明确回答"文件是怎么被接受的"（无白名单）

对 `3fp\kernel` 与 `src\` 做了针对性检索：

- **内核（C++）无扩展名白名单**：全树 `extension` 命中均与媒体格式无关——`AssSubtitleRenderer.cpp:54/78` 是字体（`.ttf/.otf/.ttc`），`DiscInput.cpp:42-52` 是 `.bdmv`。
- **内核无 codec 允许/拒绝清单**：`OpenFormat`（`:2115-2160`）只有协议白/黑名单与 demuxer 名 `hls`/`dash` 拦截；`codec_id` 仅出现于 `:2241`（AV1 特判 `libdav1d`）、`:2266`（MPEG2+菜单）、`:4690-4691`（H264/HEVC/AV1 的 `codecConfiguration`）。
- **宿主（C#）仅有文件选择器过滤器**：`MainWindow.axaml.cs:411`/`:794`。

⇒ **AVS3 能进入 OpenDecoder，失败点纯粹是 FFmpeg 没有解码器。** 意味着**换一个带 `libuavs3d` 的 FFmpeg 即可开播，无需改内核逻辑**。

### 4.3 (c) 硬件解码 —— **AVS3 在 Windows/D3D11VA 上无路可走**

对上游 `libavcodec/hwaccels.h` 全量检索：

```

(空)
```

| 检查点 | 结论 |
|---|---|
| 上游有 AVS3 hwaccel 吗 | ❌ 无（D3D11VA/DXVA2/D3D12VA/NVDEC/QSV/VAAPI/Vulkan 全无） |
| `libuavs3d` 支持硬解吗 | ❌ 参考解码器纯软件（README 只提 ARMv7/v8、SSE4、AVX2 优化） |
| 内核 `FindHardwareFormat`（`:288`）能救吗 | ❌ 不能。无 `hw_configs` ⇒ 返回 `AV_PIX_FMT_NONE` ⇒ `:2246` 直接 NotSupported |
| Windows 通用 API 暴露 AVS3 吗 | ❌ D3D11VA/DXVA 未向应用暴露 AVS3，FFmpeg 也无封装 |

| 方案 | 可行性 | 代码改动 | 构建改动 | 许可风险 | 性能 | 建议 |
|---|---|---|---|---|---|---|
| (a) 原生解码器 | **不可行** | — | — | — | — | **排除** |
| **(b1) 换入本机已有的 BtbN LGPL 缓存 DLL** | **✅ 立即可行** | **零** | **零** | ✅ BSD-3 兼容 | 中（软解） | **首选验证路径** |
| (b2) 自建 FFmpeg + libuavs3d | 可行 | 近零 | 高 | ✅ BSD-3 | 中 | 长期方案 |
| (c) 硬件解码 | **不可行** | — | — | — | — | **排除** |

> **(b1) 是本报告最重要的可执行结论**：本机 `%LOCALAPPDATA%\fff-ffmpeg-download\extracted\ffmpeg-master-latest-win64-lgpl-shared\bin\` 下**已经躺着一个带 `libuavs3d` 的 BSD/LGPL 干净构建**。因其同时更"干净"（无 `--enable-gpl`/`--enable-nonfree`），换入它既能**立刻获得 AVS3 解码**，又能**顺带消除 §5.4 的 `nonfree and unredistributable` 问题**。⚠️ 但须先解决版本差异（见 §5.3/§7）。

## 五、构建与依赖改动面（钉死在哪个产物／校验）

### 5.1 FFmpeg 是"下载的"，不是项目自编

**下载脚本（多处副本，内容一致）**：`3fp\kernel\tools\准备FFmpeg.ps1`（内核侧，被 `构建全部.ps1` 调用）、`tools\verify-scripts\pr_wt\准备FFmpeg.ps1`。

| 项 | 值 | 位置 |
|---|---|---|
| **下载 URL** | `https://github.com/BtbN/FFmpeg-Builds/releases/download/latest/ffmpeg-master-latest-win64-lgpl-shared.zip` | `准备FFmpeg.ps1:9` |
| 本地缓存 | `%LOCALAPPDATA%\fff-ffmpeg-download\…`（实测存在 67,696,776 B） | `:12`、`:67-74` |
| 源码克隆（仅取头文件/许可） | `git clone https://github.com/FFmpeg/FFmpeg.git` | `:90` |
| **源码 commit 钉死** | `$PinnedCommit = "7f6b35d6c804ed8d1bc517c33044f075d72852ba"` | `:24` |
| 头文件 / 导入库 / 运行 DLL 目录 | `third_party\ffmpeg\include`、`lib\x64`、`runtime` | `:20-23` |

### 5.2 ⚠️ 核心问题：**DLL 换掉了，脚本却以为用的是 BtbN 包**

- 脚本从 BtbN LGPL 包解出 DLL → 拷到 `runtime\` 与 `publish\PLAN\ffmpeg-full\`。
- 但**实际躺在这些位置的是第三方自编译的 GPL+nonfree 构建**（内嵌 `--enable-gpl --enable-nonfree`，版本号 `git-2026-09-24-c0e8b139fd` / `git-2026-10-07-e5a08f7c0e`），**与 BtbN 缓存（`N-126168-gb16b5f2a01-20260815`）完全不同**。
- 后果：**构建脚本描述的能力面与实际发布的能力面不一致**。脚本假设有 `libuavs3d`（BtbN 有），实际产物没有。

### 5.3 ⚠️ 运行期 DLL 能力**不可钉死、不可复现**

| 层 | 是否钉死 | 说明 |
|---|---|---|
| 头文件 | ✅ 钉死 | git commit `7f6b35d6…`（`:24`、`:96-99`） |
| **运行期 DLL** | ❌ **完全不钉死** | URL 用 `releases/download/latest/`（**会滚动**）；且检索 `SHA\|sha256\|Hash\|checksum` **无任何校验**（`:24`） |

⇒ 即便脚本正常工作，**同一份代码在不同时间跑 `准备FFmpeg.ps1` 也会得到能力面不同的 DLL**。这既是不确定性来源，也解释了本机为何并存四个不同 `avcodec-63.dll`（§2.5）。

**加固建议**：钉死具体 BtbN release tag（或自建产物）+ 记录 SHA256 到清单，否则"AVS3 能播"会在下次拉取时无声失效。

### 5.4 ⚠️ 发布与再分发风险（陈述事实，非法律意见）

**当前实际发布的产物** `publish\PLAN\ffmpeg-full\avcodec-63.dll`（SHA256 `C6163B23AF0CACC6…`）内嵌：

```
--enable-gpl --enable-nonfree --enable-version3 ...
libavcodec license: nonfree and unredistributable
```

- `--enable-nonfree` + `nonfree and unredistributable` 意味着**该二进制按 FFmpeg 自身声明不可再分发**。
- **门禁与打包脚本均无任何 FFmpeg 许可证检查**：
  - `tools\发布门禁.ps1`：检索 `ffmpeg|avcodec|license|nonfree` **无命中**（仅 `:567` 提到"完整版含 FFmpeg"的重试逻辑）。
  - `pack.ps1`：检索 `license|nonfree|unredistributable` **无命中**。其 `:329-332` 只校验"完整版必须有 `ffmpeg-full\avcodec-*.dll`"，`:600-608` 只校验 DLL 数量，**不检查内容或来源**。
- **`runtime\` 本身不随包发布**：`pack.ps1:591-604` 从 `publish\PLAN\ffmpeg-full\` 拷入包的 `ffmpeg-full\` 子目录（`PACKAGING_SPEC.md:50-57`）。`runtime\` 只用于开发/测试（`构建全部.ps1:211`、`deploy_ffmpeg_for_tests.sh:28`）。
- ⇒ **风险不在 `runtime\`，而在 `publish\PLAN\ffmpeg-full\`** —— 即随 `-Mode full` 发布出去的那份。

### 5.5 部署脚本的第二个来源（易踩坑）

`tools\deploy_ffmpeg_for_tests.sh:26-29` 定义两个来源，**优先级与 `publish` 不同**：

```bash
SRC_CANDIDATES=(
  "/c/PLAN/ffmpegPictureUI/publish/PLAN/ffmpeg-full"   # 优先：完整包
  "$ROOT/runtime"                                       # 兜底
)
```

⇒ 只改 `runtime\` 时，用此脚本部署的测试环境**仍会用 `ffmpeg-full`**，"有没有 AVS3"取决于走哪条路径。落地时必须**两个来源同步**。

### 5.6 用户可自行更换 FFmpeg（"支持"取决于用户放了哪个 DLL）

这是**设计内的**能力来源，`src\3FCompare.Core\Backend\NativeRuntime.cs:462-467` 定义优先级：

```
① 手动指定的 FfmpegDirectory（仅当其含 avcodec）
② exe 同目录
③ ffmpeg-full/ 子目录（发布完整版运行目录）
④ ffmpeg/ 子目录（旧版）
```

机制为 `SetDllDirectoryW`（`:11`、`:104`）+ 内核 Delay-Load（`FFF.Native.vcxproj:75`），**不复制 DLL 到应用目录**（`NativeRuntime.cs:7`）。UI 提示文案见 `LanguageManager.cs:138`：*"优先级：手动设置 > 同目录 DLL > ffmpeg-full/ 子目录"*。

⇒ **对 AVS3 的直接含义（这是回答"3FP 是否支持 AVS3"的关键限定条件）**：

| 用户放入的 FFmpeg | AVS3 结果 |
|---|---|
| 默认（当前发布的 `ffmpeg-full\`，dominic GPL/nonfree 构建） | ❌ 打不开 |
| 手动指向 BtbN LGPL 构建（含 `libuavs3d`） | **✅ 可解码播放（零代码）** |
| 手动指向其它含 `libuavs3d` 的自编译构建 | ✅ 可播放 |
| 精简版（无任何 FFmpeg） | ❌ 演示模式 |

⇒ **严谨表述：3FP 的 AVS3 支持能力不是编译期常量，而是"用户放入的 DLL 的函数"。** 内核侧 100% 就绪（会正确走 `avcodec_find_decoder(193)` 并接受 `libuavs3d`），瓶颈只在随包分发的那个 DLL 恰好没有该解码器。

### 5.7 与 ARM64 迁移的冲突

`docs\52-3FP-Windows-ARM64-可行性分析.zh.md:187-201` 已记录需把 `准备FFmpeg.ps1` 参数化。**新增约束**：BtbN 的 `50-uavs3d.sh` 有 `[[ $TARGET == winarm64 ]] && return -1`，`50-davs2.sh` 有 `[[ $TARGET == *arm64 ]] && return -1`（注释：*"davs2 aarch64 support is broken"*）⇒ **ARM64 上无法走 BtbN 获得 AVS3**，需单独解决 uavs3d 的 aarch64 构建。**AVS3 支持与 ARM64 迁移在此处冲突**，应登记为依赖项。

### 6.2 ⚠️ 无法用 FFmpeg 合成 AVS3 样本

FFmpeg 只有 AVS3 **解码器**，**没有 AVS3 编码器**（`ffmpeg -encoders` 无 AVS 项；上游只有 `libxavs`/`libxavs2` 两个 **AVS1/AVS2** 编码器）。⇒ **必须外部获取真实码流**，无法自造。

### 6.3 本分析用的合成样本（可驱动整条链，作回归门禁）

```powershell
# 00 00 01 B0 = 序列头；00 00 01 B3 = 帧内图像起始码
$bytes = [byte[]]@(
 0x00,0x00,0x01,0xB0, 0x22,0x00,0x00,0x02,0x00,0x0F,0x00,0x08,0x70,0x00,0x00,0x00,0x00,0x00,0x00,0x00,

[IO.File]::WriteAllBytes("synthetic.avs3", $bytes)
```

```powershell
ffmpeg.exe -hide_banner -f avs3 -i synthetic.avs3 -f null - 2>&1 | Select-String 'no decoder found'
```

| uavs3d 软解 4K/8K 性能 | 未测 | 未知 | **低** |
| `libuavs3d` 输出与渲染管线兼容性 | 未测 | 未知 | **低** |

### 7.2 风险项

| 风险 | 影响 | 严重度 | 缓解 |
|---|---|---|---|
| **发布产物是 `nonfree and unredistributable`** | 完整版随包分发该二进制存在许可风险 | **高** | 换用 BtbN LGPL 构建（同时白得 AVS3）；加许可证门禁 |
| **门禁无 FFmpeg 许可证检查** | 风险长期不被发现 | **高** | 在 `发布门禁.ps1`/`pack.ps1` 加 `_license` 串检查 |
| **构建脚本描述与实际 DLL 不符** | 能力面认知错误、复现困难 | **高** | 钉死来源 + 记录 SHA256 + 门禁校验 |
| 运行期 DLL 无 SHA 钉死、URL `latest` | 支持能力漂移/静默失效 | **高** | 钉死 release tag + SHA |
| **AVS 专利授权** | 商业化分发风险 | **高** | 落地前法务确认（AVS 有明确专利池） |
| 两套 FFmpeg 来源版本不一致 | 验证结果不可复现 | 中 | 统一来源或同步更新 |
| `deploy_ffmpeg_for_tests.sh` 优先级与 publish 不同 | 改了不生效 | 中 | 两来源同步 |
| **AVS2/AVS1 探测歧义** | AVS2 可能被判成 AVS1 并用错解码器 | 中 | 按扩展名提示 `-f avs2` 或调整 probe 权重 |
| ARM64 与 AVS3 冲突 | `50-uavs3d.sh` 排除 winarm64 | 中 | 登记为 ARM64 迁移附加依赖 |
| 软解性能（无 GPU） | 4K/8K 可能掉帧 | 中 | 实测；利用 uavs3d 的 AVX2 优化 |
| 色彩/HDR 衔接 | AVS3 色彩字段需进入既有 HdrProcessor | 中 | 用真实 HDR 样本验证 |
| `:2248` 错误文案误导 | 排障方向被带偏 | 低 | 区分"无解码器"与"无硬件格式" |

### 7.3 明确标注的**未知项**（不猜测）

1. **BtbN 何时/为何停止随包发布、以及 `runtime/` 里的 GPL 构建由谁替换**：仅能证明"实际 DLL ≠ 脚本下载的 DLL"，**替换动作的来源与原因未知**。
2. **`libuavs3d` 与 3FP 渲染管线的实际兼容性**：无样本、无解码器环境未搭建 ⇒ **未验证**。其输出 `AV_PIX_FMT_YUV420P`/`YUV420P10` 是否被 `VideoRenderer` 完整支持、色彩字段是否被 `HdrProcessor` 采用，均**未知**。
3. **uavs3d 软解吞吐（4K/8K 能否实时）**：**未测**。
4. **AVS 专利池具体授权条件与费用**：**完全未核实**。
5. **换用 BtbN 缓存 DLL 后的回归面**：其版本（`N-126168`，2026-08-15）比现用者旧/新方向不同，且解码器数多 11 个（298 vs 287）、解复用器少 4 个（364 vs 368）⇒ **可能引入其它格式的行为变化**，**未做回归**。
6. **是否存在其它现成、可直接替换且含 `libuavs3d` 的 Windows x64 shared 构建**：**未穷举**（本机四个均非理想：仅缓存那个含 AVS3，但版本与现用者不同）。

---

## 八、给决策者的一句话总结

**AVS3 在 3FP 中"差一个 DLL"**：内核路径、容器识别、codec ID 常量、用户自定义 FFmpeg 机制**全部就绪**，唯一缺口是随包分发的 `avcodec-63.dll` 恰好来自一个 `--disable-decoder=libuavs3d` 的 GPL/nonfree 自编译构建。**本机已存在一个 BSD/LGPL 干净、含 `libuavs3d` 的 BtbN 构建，换入即可零代码获得 AVS3 解码**，同时还顺手消除 `nonfree and unredistributable` 的再分发隐患——代价是必须做一轮跨格式回归（版本与组件集有差异），并补齐门禁里缺失的许可证与 SHA 校验。
