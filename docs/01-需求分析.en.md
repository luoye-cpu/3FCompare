## 1. Background & Goals

NVIDIA ICAT (Image Comparison & Analysis Tool) is a graphical tool for image-quality comparison: it loads up to 4 videos/images at once, supports alignment, frame stepping, looping, A-B sliders, pan & zoom and other region-focused comparison, and is widely used by encoding reviewers (VCB, etc.) and game graphics testers.

**3FCompare Goal**: Build the same kind of frame-by-frame video inspection software, but with the decode/playback kernel replaced by FFF_Project's 3FP. The backend capabilities (frame-level stepping, frame-accurate Seek, 100ns-granularity snapshots, pixel probe, multi-stream info) naturally fit ICAT's "frame-by-frame comparison" workflow.

**Note**: ICAT itself is developed by NVIDIA, closed-source and without a public plugin API; its code cannot be directly reused. This plan follows a "benchmark the UX + independent implementation" approach.

## 2. User Personas & Scenarios

| Persona | Needs |
| --- | --- |
| Video encoding reviewers (VCB / encode groups) | Compare source vs. encoded versions, locate degraded frames, inspect chroma / ringing / blocking artifacts |
| Game graphics / ray-tracing comparison | Differences of the same scene under different settings |
| Video processing researchers | Frame-level capture, algorithm parameter comparison |

**Core usage scenarios**:

1. Open 2~4 videos, auto-align the timeline / manually set offsets;
2. Synchronized frame-by-frame stepping (forward/backward) or jump by frame number;
3. Switch among side-by-side / single-view / A-B slider comparison views;
4. Magnifier / high-zoom pan to inspect details;
5. Pixel probe (color readout), record frame number and time;
6. Produce a report (screenshots, records).

## 3. Functional Requirements Overview

### 3.1 Video Loading & Media Management (P0)

| ID | Requirement | Description |
| --- | --- | --- |
| F1 | Multi-source loading | **1~9 streams variable** (min 1, max 9, 3x3 grid cap; supports 1x1/2x1/2x2/3x2/3x3 layouts); drag & drop and file picker |
| F2 | Image loading | Static images treated as single-frame media (3FP already plays stills as single frames) |
| F3 | Media info display | Resolution, frame rate, codec, HDR info, bitrate, etc. (from 3FP `media info` JSON) |
| F4 | Timeline | Show per-stream / overall timeline, draggable Seek (100ns precision) |
| F5 | Frame number display | Show current frame number (snapshot.frameIndex and original frame PTS/timebase) and timestamp |

### 3.2 Sync & Playback Control (P0)

| ID | Requirement | Description |
| --- | --- | --- |
| F6 | Sync play/pause | Master clock drives all sessions (see 04 Sync Model) |
| F7 | Sync frame stepping | Step aligned by PTS base; fall back to frame-index base when no precise PTS (tradeoff in 04) |
| F8 | Frame-accurate Seek | Precise frame jump (3FP `SeekFrame`) |
| F9 | Offset calibration | Per-stream manual ±time/±frame offset for aligning source video with compressed deliverables |
| F10 | Playback speed | 0.25x/0.5x/1x/2x/4x etc. (3FP native speed is "pseudo-variable-speed" oriented at high-frequency snapshot frames; see risks) |
| F11 | Loop | Interval (A/B) looping for repeatedly watching a segment |
| F12 | **Dual stepping buttons** | **Two sets of forward/backward buttons**: ① step by frame (default ±1 frame, adjustable ±N in settings); ② step by second (default ±1s, adjustable ±N in settings) |

### 3.3 Comparison Views (P1)

| ID | Requirement | Description |
| --- | --- | --- |
| F13 | Split grid | **1x1 ~ 3x3 adaptive** (1/2/3/4/6/9 streams), click to select a stream |
| F14 | Single view | View only one stream, zoom into details |
| F15 | A-B slider | Slide between two parallel timeline contents (ICAT-style interaction) |
| F16 | Sync zoom/pan | All views share one viewport (same region & zoom), or support independent-viewport mode |
| F17 | Magnifier | Follow the mouse to read local pixels of a stream |
| F18 | **Fullscreen/window mode** | **Fullscreen mode** (player surface fullscreen, hide UI frame) + **window mode** (normal window, resizable/maximizable) |

### 3.4 Pixel-level Tools (P1)

| ID | Requirement | Description |
| --- | --- | --- |
| F19 | Pixel probe | Read RGB(A) value at any coordinate of the current frame (3FP `ReadVideoPixel`), show raw BGRA8/RGB10A2 values |
| F20 | Difference overlay | (Optional) per-pixel difference heatmap between two streams — note it is affected by different scaling/color management; must compare under the same quantization path (see risks) |
| F21 | Screenshot | Output current frame as PNG (coordinate with 3FP snapshot buffer, see 03 Capability Mapping) |

### 3.5 Records & Settings (P2)

| ID | Requirement | Description |
| --- | --- | --- |
| F22 | Bookmark/marker | Record frame number + time + note, export CSV/JSON |
| F23 | Session save/restore | Save loaded-file list, offsets, layout and current frame per stream; one-click restore next time |
| F24 | Shortcut scheme | ICAT/PotPlayer-style, customizable |
| F25 | **Secondary settings window** | Open a standalone **settings dialog** from the main window menu/toolbar to centrally manage: hardware acceleration, GPU selection, stepping parameters, window/fullscreen behavior, decode/color/audio track, layout, etc. (see table below) |
| F26 | **Hardware encode/decode switch** | Toggle **hardware decode** and **hardware render** globally/per-stream in settings; GPU decode can be specified per session (multi-GPU) |

**Secondary settings window (F25) content list**:

| Group | Configurable items |
| --- | --- |
| Hardware acceleration | Hardware decode switch (global); specify decode GPU (multi-GPU: `use N-th GPU for this session` or `system default`); hardware render/composite switch |
| Stepping | **Frame step size (default 1 frame)**; **second step size (default 1 second)**; step key bindings |
| Window | Default startup mode (window/fullscreen); window size/memory; hide timeline/toolbar in fullscreen or not |
| Decode/color | Decode mode (CPU/GPU); color mode (SDR mapping / HDR / ACM-related); audio track selection |
| Layout | Default grid rows/cols; per-stream independent decode config |
| Other | Shortcut scheme, probe panel preferences, VRR presentation options (if supported) |

### 3.6 Windows Wide-Gamut / ACM (P1)

| ID | Requirement | Description |
| --- | --- | --- |
| F28 | Native wide-gamut + ACM support | Follow the Windows Advanced Color mechanism: swap chain supports **RGB10A2/BGRA8 soft-play HDR**, explicit color spaces (BT.2020/PQ / BT.709); SDR windows follow the desktop SDR contract with display-side mapping by DWM/ACM |
| F29 | Wide-gamut overlay color | The render/composite path performs wide-gamut conversion between **Rec.709 ↔ Rec.2020**, covering **drawing, probe readback, screenshots** so the color semantics reviewers see stay consistent |
| F30 | HDR/ACM display capability probe & fallback | Detect Advanced Color (HDR availability, bit depth, gamut) at startup / monitor change; auto-fallback to SDR with a notice when HDR fails (3FP reports via `color mode change` event + snapshot.actualColorMode) |

> **Key dependency**: 3FP already implements the "Microsoft Advanced Color swap-chain contract": SDR uses BGRA8/RGB10A2 (desktop contract), true HDR uses R10G10B10A2 + explicit PQ/BT.2020; **ICC, HDR calibration and SDR brightness mapping are applied once by DWM at window composition**, 3FP does no display-side compensation. The core question is whether ACM follows 3FP (known), and **reading the pre-color-management native buffer across sessions** won't cross-contaminate (known, supported).

### 3.7 VRR (G-SYNC / FreeSync) (P1)

| ID | Requirement | Description |
| --- | --- | --- |
| F31 | VRR support | In fullscreen/borderless window, output matches the display refresh-rate range (G-SYNC/FreeSync active), no tearing; implemented via both window creation (`DwmSetWindowAttribute`/`SetWindowDisplayAffinity` scenarios) and swap-chain behavior |
| F32 | Isolate in-game vs. desktop VRR | The player window is a **standalone window** (not an in-game overlay); desktop VRR depends on Windows global switches (G-SYNC desktop mode / FreeSync); we only guarantee **the window itself doesn't break VRR** |
| F33 | Sync playback under variable refresh | Playback pacing follows the master clock; under VRR the **frame base of sync stepping remains media time/frame number** — no need to calibrate to display refresh rate |

> **Key dependency & risk**: need to confirm **whether the 3FP swap chain enables VRR-related flags (`DXGI_SWAP_CHAIN_DESC1::SwapEffect/Flags` supports `DXGI_SWAP_EFFECT_FLIP_DISCARD` and `DXGI_PRESENT` parameters, and whether Present pacing follows the media frame rate rather than a fixed 60Hz)**; if 3FP uses fixed-rate Present, VRR can only be supported as the "window layer doesn't interfere" subset — full-time VRR is not guaranteed (see [06 Risks](06-风险与依赖.en.md) A8/A9). MVP acceptance: "static refresh ≤ display cap, doesn't actively block VRR".

### 3.8 Audio Track (Optional, P2)

| Feature | Description |
| --- | --- |
| Audio track selection | Pass through 3FP's `SelectAudioStream` / external audio tracks |
| Audio sync | In sync mode the master clock is still driven by video; the user can choose a single stream to output audio |

> Video review scenarios are mostly picture-oriented; audio is a low-frequency need, scheduled at P2.

## 4. Non-functional Requirements

| Category | Requirement |
| --- | --- |
| Performance | **9 streams** of 1080p sync stepping with no noticeable lag; single step feedback < 100ms (with hot decode data); reasonable GPU memory usage |
| GPU | Prefer GPU decode (CUDA/D3D11VA), auto-fallback to CPU; **evaluate VRAM for multi-stream HW decode**; support **specifying decode GPU per multi-GPU** (see F26) |
| Memory | Stable playback-session memory model (3FP has an 8-frame video queue + 128MiB budget constraint) |
| Stability | Session errors don't crash the UI; playback thread isolated from UI thread (3FP events go through SynchronizationContext) |
| Maintainability | Backend capabilities encapsulated in a standalone module (`Backend.3FP`), swappable for other implementations later |
| Compatibility | Windows 10 22H2+; .NET 11 runtime (or NativeAOT self-contained, no runtime needed); Shared FFmpeg DLL and FFF.Native shipped in the user directory |
| Color/wide-gamut | Support Windows Advanced Color: RGB10A2 HDR/wide-gamut output, explicit color spaces, DWM/ACM display-side color management; **probe/screenshot/UI overlay all work under the same color semantics** |
| Display sync | Support VRR (G-SYNC / FreeSync): swap chain doesn't break VRR, doesn't force fixed 60Hz; playback pacing independent of refresh rate |

## 5. Priority & Acceptance Criteria

| Milestone | Acceptance |
| --- | --- |
| M0 MVP | **2 streams of 1080p opened simultaneously**, synchronized PTS stepping, arrow-key **frame-step / second-step** dual forward/backward, stable frame-number/time display |
| M1 | **5~9 stream grid layout (1x1~3x3)**, independent offset calibration, selection highlight, single view |
| M2 | Sync play/pause/speed, **hardware encode/decode switch (incl. multi-GPU)**, interval loop, seek bar |
| M3 | A-B slider, sync zoom/pan, magnifier, pixel probe |
| M4 | **Secondary settings window** (hardware acceleration / GPU selection / step size / window fullscreen), session save-restore, bookmark export, shortcuts |
| M5 | Packaging & distribution (NativeAOT self-contained/single-file + external FFmpeg DLL), documentation, performance regression; **ACM/wide-gamut and VRR acceptance** (see table below) |

### 5.1 ACM / VRR Special Acceptance

| Item | Acceptance method |
| --- | --- |
| ACM SDR | SDR window displays correctly on an ACM-enabled display; probe readback values match 3FP color mode (independent of DWM post-processing) |
| ACM HDR | HDR source renders correctly on a true HDR display (R10G10B10A2/PQ·BT.2020); auto-degrade to SDR with notice when HDR is unavailable (`color mode change` / snapshot.actualColorMode) |
| Overlay color | Magnifier / probe annotation / A-B divider and other GDI+ overlays show no obvious color cast on HDR/wide-gamut windows (SDR overlay compositing semantics; must be verified on an ACM display) |
| VRR frame refresh | Fullscreen playback of a 60fps source doesn't force a fixed 60Hz cadence (if 3FP exposes Present pacing params, VRR takes effect); when not yet verifiable, "doesn't actively block VRR + no tearing" is the pass line |

## 6. Out of Scope

- No network protocol (3FP itself doesn't support network input);
- No screen recording, transcoding, or editing;
- No true "per-pixel comparison engine" (P-frame difference semantics); only pixel probe and optional per-point absolute-difference view;
- No "in-game overlay / injection VRR tools" (e.g. RTSS layers); this software is a standalone window, VRR support is limited to **window/swap-chain not breaking desktop VRR**;
- No self-implemented display-side color correction (ICC / calibration / SDR brightness mapping) — delegated to DWM/ACM, consistent with the 3FP contract.
