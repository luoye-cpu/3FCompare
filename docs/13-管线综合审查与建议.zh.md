## 2. 代码层：本轮新发现的缺陷（docs/11、12 未覆盖）

### 2.1 🔴 P0-C1 · `PAINTSTRUCT` 声明缺尾部字段 → 每次 WM_PAINT 栈上越界写 32 字节

**位置**：`src/3FCompare/Controls/PlayerSurface.cs:523`（调用点 `:269`、`:379`）

```csharp
private struct PAINTSTRUCT {
    public nint HDC; public bool fErase; public RECT rcPaint;
    public bool fRestore; public bool fIncUpdate;
}                                   // ← 缺 rgbReserved[32]
```

| | 布局 | 大小 |
|---|---|---|
| 托管声明 | HDC(8) + BOOL(4) + RECT(16) + BOOL(4) + BOOL(4) → 对齐 8 | **40 字节** |
| 原生 `tagPAINTSTRUCT` (x64) | … + `BYTE rgbReserved[32]` | **72 字节** |

结构体是 blittable，`ref ps` 直接把**托管栈上局部变量的地址**交给 `BeginPaint`，
原生侧按 72 字节写 → **多写 32 字节**，覆盖 `SubclassedWndProc` / `PaintSelf` 栈帧的相邻局部变量。

**为什么危险**：每次重绘都触发，但多数时候踩到的是无关变量 → 表现为"偶发随机崩溃"，
极难归因。这与已知的"多路播放 SIGILL/SIGSEGV"在现象上无法区分，
**在修掉这条之前，无法断定那些原生崩溃里有多少其实是这里造成的**。

**修法**（二选一）：
```csharp
[MarshalAs(UnmanagedType.ByValArray, SizeConst = 32)] public byte[] rgbReserved;
// 或
public unsafe struct PAINTSTRUCT { ... public fixed byte rgbReserved[32]; }
```
建议顺手用 `Marshal.SizeOf<PAINTSTRUCT>()` 加一条启动期断言，防止将来再漏。

### 2.2 🟠 P1-C2 · 伪变速首次生效会把播放位置跳到当前位置的 N 倍

**位置**：`src/3FCompare/MainWindow.axaml.cs:660-663`

```csharp
var mediaElapsed = pos - _speedBasePos;      // _speedBasePos 初值 0，全仓库仅在 663 行赋值
if (_playbackSpeed > 1.0 && mediaElapsed > 0)
    SafeSeek(pos + (long)(mediaElapsed * (_playbackSpeed - 1.0)));
```

`_speedBasePos` 只在每次 seek 后更新，**从不随倍速切换复位**。
稳态下 `mediaElapsed ≈ 1s` 语义正确，但**首次**进入时 `mediaElapsed = pos`：

> 播放到 30s 时切 2× → 下一次轮询（≤250ms 内）直接 Seek 到 **60s**；4× 则跳到 120s（被 clamp 到片尾）。
> 切回 1× 再切 2× 会**再跳一次**。

**修法**：在 `_transport.SpeedChanged`（现仅 `:287` 赋值 `_playbackSpeed`）与 `_sync.Play()`
两条路径上补：
```csharp
_speedBasePos = _sync.GetMasterPosition100ns();
_lastSpeedSeekTicks = Environment.TickCount64;
```
并把首 tick 的 `mediaElapsed` 钳到 `<= 2s` 作为兜底。

### 2.3 🟠 P1-C3 · 放大镜一旦失败就永久只剩空框（自锁死）

**位置**：`src/3FCompare/Controls/MagnifierOverlay.cs:55-60`

```csharp
if (_session is null || !_session.ReadRenderTargetInfo(out var rt) ||
    rt.SwapWidth == 0 || rt.SwapHeight == 0 || _pixelGrid is null)
{ _pixelGrid = null; return; }        // ← 判据里含 _pixelGrid is null
```

只要有一次失败（`TryReadPixelRegion` 返回 false、引擎刚打开 RTInfo 还为 0、会话切换），
`_pixelGrid` 被置 null，此后**每次**都因同一判据提前 return，再也进不去重建分支。
`AttachSession` 也不重置它。

**现象**：放大镜开关正常、边框十字线正常，但内容永远不出现——用户只会以为"功能没做"。

**修法**：判据移除 `|| _pixelGrid is null`；`AttachSession` 里补
`_pixelGrid ??= new float[ZoomGrid * ZoomGrid * 4];`

### 2.4 🟠 P1-C4 · 探针坐标回退分支数学错误（演示模式/旧内核必中）

**位置**：`src/3FCompare/MainWindow.axaml.cs:1092-1093`

```csharp
return ((int)(physX / Math.Max(1, rt.SwapWidth == 0 ? physX : rt.SwapWidth) * media.VideoWidth), ...);
```

`ReadRenderTargetInfo` 返回 false 时（**`SimulatedEngine.cs:200-204` 恒 false**，
即演示模式必然命中）`rt` 全 0，分母退化成 `physX` 自身
→ 结果恒为 `(VideoWidth, VideoHeight)`，且未做 `-1` 钳位。

**现象**：演示模式下探针读数恒为右下角越界像素 → `TryReadPixel` 失败 → 面板显示"读取失败"。

**修法**：分母改用表面物理尺寸 `surface.Bounds.Width * scale`，并 `Math.Clamp(…, 0, VideoWidth - 1)`。

### 2.5 🟠 P1-C5 · 重建次数是「累计」而非「连续」，达 3 次后进程内永久放弃

**位置**：`src/3FCompare/MainWindow.axaml.cs:558-563`、`:811`、`:1574`

注释写"连续失败计数，≥3 放弃"，但 `_recoveryAttempts` **只在 1574 行成功路径清零**。
实际语义是进程内累计：

- 用户暂停中触发过恢复（确认循环要求 `State == Playing` 才算 stable，暂停时必然拿不到 stable）→ 白烧计数
- 累计 3 次后，即使 SwapChain 已恢复健康，再遇 `Failed` 也**永不重建** → 永久黑屏，只能重启

**附带**：`attempts` 每 250ms 递增且无上限，放弃后每个 tick 打一行 stderr，日志无限增长。

**修法**：用户重新 `OpenFiles` 时清零；放弃后加一次性标志避免重复打日志；
"连续"语义改为"距上次成功恢复的时间窗口"。

### 2.6 🟡 P1-C6 · 会话快照存了 `GridLayout` 但加载时不还原

**位置**：保存 `MainWindow.axaml.cs:1010`；加载 `LoadSessionSnapshot`（`:1053-1075`）

```csharp
GridLayout = Grid.SingleView ? 1 : (_sync.Count <= 4 ? 2 : 3),   // 1010：存了
```
`LoadSessionSnapshot` 只读 `Items / Position100ns / Loop*`，**从不读 `GridLayout`**。

**现象**：保存单屏或 3×3 布局后重载，布局回到默认 → "保存会话"只恢复了一半。

**修法**：`LoadSessionSnapshot` 中按值还原：`Grid.SingleView = (v == 1)` /
`Grid.SetGridLayout("2x2" | "3x3")`。

## 3. 构建与发布脚本

### 3.1 🟠 P0-S1 · 门禁在英文 SDK 下恒定误报（CI 一接就红）

**位置**：`tools/发布门禁.ps1:123-128`

```powershell
$realWarnings = @($buildOut | Where-Object { $_ -match 'warning' } | ...)
```

MSBuild **英文**摘要行 `    1 Warning(s)` 会被 `-match 'warning'`（大小写不敏感）命中，
而该行不含 `AVLN3001` → 判定为非白名单告警 → `$buildOk = $false`。

本机摘要是中文「1 个警告」，不含 `warning`，**所以本机不暴露、一上 CI 必炸**。
这正是"门禁在最需要它的地方失效"，讽刺的是它拦的是白名单内的告警。

**修法**：先排除摘要行 `-notmatch '^\s*\d+\s+Warning\(s\)'`，
或按 `warning\s+([A-Z]+\d+)` 提取 code 再做白名单比对（后者更严谨）。

## 9. 多路崩溃归因：实证排除 C1 关联（2026-09-14 11:58–12:05）

C1 修复前曾推测：`PAINTSTRUCT` 栈溢出的现象（偶发随机崩溃）与"多路播放 SIGSEGV/SIGILL"
无法区分，那些被归因为"内核缺陷"的崩溃里可能有一部分其实源自这里。
**C1 修复后重测，该推测已被证伪。**

### 9.1 测试

`--multitest <真实 4K HEVC 10bit 60Mbps> 2 15`，**连跑 5 次**：

| 轮次 | 退出码 | 信号 | 崩溃时所在阶段 |
|:--:|:--:|---|---|
| 1 | 139 | SIGSEGV | "并行扇出后" 之后（即 `SetViewTransform(1,0,0)` 复位与后续检查之间） |
| 2 | 139 | SIGSEGV | 静置播放 5s |
| 3 | 139 | SIGSEGV | 并行扇出 20 次循环 |
| 4 | 139 | SIGSEGV | 静置播放 5s |
| 5 | 132 | SIGILL | 静置播放 5s |

**5/5 全崩**，与修复前"近乎必现"的基线一致，未见改善。

### 9.2 结论

1. **多路崩溃与 C1 无关**——栈溢出已消除，崩溃率没有变化。
   之前"内核缺陷"的归因成立，本次实证把它从推测变成了结论。
2. **崩溃与视图变换无强相关**：3 次发生在**无任何交互**的静置播放期，
   说明是播放/解码路径本身的并发问题，不是 UI 触发的。
3. **单路稳定、2 路必崩**：`--selftest`（单路，含 20 次快速变换压力测试）连续多轮 exit=0。
   分界点明确落在"多路并发"，指向 FFF.Native 侧的多路 D3D 设备 / 解码线程竞态。
4. C1 的修复价值**不受影响**——它消除的是一个真实的内存破坏缺陷，
   只是恰好不是这个崩溃的原因。

### 9.3 后续定位建议（需原生侧）

- 抓 dump：对 `3FCompare.exe` 配 WER LocalDumps（`DumpType=2` 全量），
  崩溃后看 SIGILL 现场的指令地址属于哪个模块（`FFF.Native` / `avcodec` / D3D11）。
- 优先怀疑多路**共享/重复创建**的资源：D3D11 device、解码器上下文、或内核内部的全局单例。
- 可做的低成本对照实验：2 路同文件 vs 2 路不同文件；关闭硬件解码；
  强制单路复用同一 `FFF.Native` 会话句柄。这些能快速区分"设备竞态"与"解码器竞态"。

> 注：应用侧暂无可规避手段（多路是核心功能）。建议先把该结论同步到
> `docs/09-测试素材与实机验证.zh.md` 的"未修复"一节，避免后续重复排查。

1. **`Format-FailDetail`**：`exit=-1` 时 Detail 统一写成
   "命令未能启动（exit=-1）：本会话无法启动原生进程，请在真实终端运行门禁"，
   覆盖编译 / 单测 / 会话往返 / 帧导出 / 打包五处，不再给出似是而非的计数。
2. **`-LogPath`**：结果逐项落盘，非交互调用不再只能拿到一个退出码。

### 12.3 环境限制（重要，避免重复排查）

**WorkBuddy 沙箱的 PowerShell 会话无法启动原生子进程**：

```
& "C:\Program Files\dotnet\dotnet.exe" --version
→ 无法在管道中间运行文档: C:\Program Files\dotnet\dotnet.exe
```

`3FCompare.exe` 同样如此。因此**门禁在本沙箱里必然全项 `exit=-1`**，
这不是脚本缺陷（同一脚本在真实终端可跑）。
本轮的有效验证是在 **Bash 工具**里逐项跑出来的：

| 项目 | 结果 |
|---|---|
| Release 构建 | 0 错误 / 1 警告（AVLN3001，白名单内） |
| 单元测试 | 80/80 |
| `--sessiontest`（真实 4K ×2） | exit=0（`布局=2x2`） |
| `--screentest`（真实 4K AV1 10bit，门禁默认取的首个素材） | exit=0，PNG 895,486 字节（1995×1122） |

> 后续如需在 CI 里跑门禁，须确认 runner 能启动原生进程；
> 沙箱内请直接用 Bash 逐项跑，不要用门禁的退出码下结论。

### 12.4 改 ps1 必须实跑（本次连犯两次）

`[System.Management.Automation.Language.Parser]::ParseFile` **只能查语法**，
以下两类错误它查不出来，而且本次各犯一次：

| 错误 | 现象 |
|---|---|
| 函数调用括号内换行续参（`(Format-FailDetail $x` ⏎ `"...") `） | `Missing closing ')' in expression` |
| 写成 C# 的 `///` 注释 | 解析通过（当作命令调用），运行时 `The term '///' is not recognized` |

两者都只有**实际跑一遍**才暴露。所以：改完 ps1 → 语法检查只是第一步 → 必须真跑一次。
沙箱里无法启动原生进程时，至少要让脚本跑到能写出日志、并确认没有异常。
