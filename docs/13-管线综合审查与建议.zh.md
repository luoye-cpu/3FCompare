## 2. 代码层：本轮新发现的缺陷（docs/11、12 未覆盖）

### 2.1 🔴 P0-C1 · `PAINTSTRUCT` 声明缺尾部字段 → 每次 WM_PAINT 栈上越界写 32 字节

**位置**：`src/3FCompare/Controls/PlayerSurface.cs:523`（调用点 `:269`、`:379`）

```csharp
private struct PAINTSTRUCT {
    public nint HDC; public bool fErase; public RECT rcPaint;
    public bool fRestore; public bool fIncUpdate;
}                                   // ← 缺 rgbReserved[32]
```

| | 布局 | 大小 |
|---|---|---|
| 托管声明 | HDC(8) + BOOL(4) + RECT(16) + BOOL(4) + BOOL(4) → 对齐 8 | **40 字节** |
| 原生 `tagPAINTSTRUCT` (x64) | … + `BYTE rgbReserved[32]` | **72 字节** |

结构体是 blittable，`ref ps` 直接把**托管栈上局部变量的地址**交给 `BeginPaint`，
原生侧按 72 字节写 → **多写 32 字节**，覆盖 `SubclassedWndProc` / `PaintSelf` 栈帧的相邻局部变量。

**为什么危险**：每次重绘都触发，但多数时候踩到的是无关变量 → 表现为"偶发随机崩溃"，
极难归因。这与已知的"多路播放 SIGILL/SIGSEGV"在现象上无法区分，
**在修掉这条之前，无法断定那些原生崩溃里有多少其实是这里造成的**。

**修法**（二选一）：
```csharp
[MarshalAs(UnmanagedType.ByValArray, SizeConst = 32)] public byte[] rgbReserved;
// 或
public unsafe struct PAINTSTRUCT { ... public fixed byte rgbReserved[32]; }
```
建议顺手用 `Marshal.SizeOf<PAINTSTRUCT>()` 加一条启动期断言，防止将来再漏。

### 2.2 🟠 P1-C2 · 伪变速首次生效会把播放位置跳到当前位置的 N 倍

**位置**：`src/3FCompare/MainWindow.axaml.cs:660-663`

```csharp
var mediaElapsed = pos - _speedBasePos;      // _speedBasePos 初值 0，全仓库仅在 663 行赋值
if (_playbackSpeed > 1.0 && mediaElapsed > 0)
    SafeSeek(pos + (long)(mediaElapsed * (_playbackSpeed - 1.0)));
```

`_speedBasePos` 只在每次 seek 后更新，**从不随倍速切换复位**。
稳态下 `mediaElapsed ≈ 1s` 语义正确，但**首次**进入时 `mediaElapsed = pos`：

> 播放到 30s 时切 2× → 下一次轮询（≤250ms 内）直接 Seek 到 **60s**；4× 则跳到 120s（被 clamp 到片尾）。
> 切回 1× 再切 2× 会**再跳一次**。

**修法**：在 `_transport.SpeedChanged`（现仅 `:287` 赋值 `_playbackSpeed`）与 `_sync.Play()`
两条路径上补：
```csharp
_speedBasePos = _sync.GetMasterPosition100ns();
_lastSpeedSeekTicks = Environment.TickCount64;
```
并把首 tick 的 `mediaElapsed` 钳到 `<= 2s` 作为兜底。

### 2.3 🟠 P1-C3 · 放大镜一旦失败就永久只剩空框（自锁死）

**位置**：`src/3FCompare/Controls/MagnifierOverlay.cs:55-60`

```csharp
if (_session is null || !_session.ReadRenderTargetInfo(out var rt) ||
    rt.SwapWidth == 0 || rt.SwapHeight == 0 || _pixelGrid is null)
{ _pixelGrid = null; return; }        // ← 判据里含 _pixelGrid is null
```

只要有一次失败（`TryReadPixelRegion` 返回 false、引擎刚打开 RTInfo 还为 0、会话切换），
`_pixelGrid` 被置 null，此后**每次**都因同一判据提前 return，再也进不去重建分支。
`AttachSession` 也不重置它。

**现象**：放大镜开关正常、边框十字线正常，但内容永远不出现——用户只会以为"功能没做"。

**修法**：判据移除 `|| _pixelGrid is null`；`AttachSession` 里补
`_pixelGrid ??= new float[ZoomGrid * ZoomGrid * 4];`

### 2.4 🟠 P1-C4 · 探针坐标回退分支数学错误（演示模式/旧内核必中）

**位置**：`src/3FCompare/MainWindow.axaml.cs:1092-1093`

```csharp
return ((int)(physX / Math.Max(1, rt.SwapWidth == 0 ? physX : rt.SwapWidth) * media.VideoWidth), ...);
```

`ReadRenderTargetInfo` 返回 false 时（**`SimulatedEngine.cs:200-204` 恒 false**，
即演示模式必然命中）`rt` 全 0，分母退化成 `physX` 自身
→ 结果恒为 `(VideoWidth, VideoHeight)`，且未做 `-1` 钳位。

**现象**：演示模式下探针读数恒为右下角越界像素 → `TryReadPixel` 失败 → 面板显示"读取失败"。

**修法**：分母改用表面物理尺寸 `surface.Bounds.Width * scale`，并 `Math.Clamp(…, 0, VideoWidth - 1)`。

### 2.5 🟠 P1-C5 · 重建次数是「累计」而非「连续」，达 3 次后进程内永久放弃

**位置**：`src/3FCompare/MainWindow.axaml.cs:558-563`、`:811`、`:1574`

注释写"连续失败计数，≥3 放弃"，但 `_recoveryAttempts` **只在 1574 行成功路径清零**。
实际语义是进程内累计：

- 用户暂停中触发过恢复（确认循环要求 `State == Playing` 才算 stable，暂停时必然拿不到 stable）→ 白烧计数
- 累计 3 次后，即使 SwapChain 已恢复健康，再遇 `Failed` 也**永不重建** → 永久黑屏，只能重启

**附带**：`attempts` 每 250ms 递增且无上限，放弃后每个 tick 打一行 stderr，日志无限增长。

**修法**：用户重新 `OpenFiles` 时清零；放弃后加一次性标志避免重复打日志；
"连续"语义改为"距上次成功恢复的时间窗口"。

### 2.6 🟡 P1-C6 · 会话快照存了 `GridLayout` 但加载时不还原

**位置**：保存 `MainWindow.axaml.cs:1010`；加载 `LoadSessionSnapshot`（`:1053-1075`）

```csharp
GridLayout = Grid.SingleView ? 1 : (_sync.Count <= 4 ? 2 : 3),   // 1010：存了
```
`LoadSessionSnapshot` 只读 `Items / Position100ns / Loop*`，**从不读 `GridLayout`**。

**现象**：保存单屏或 3×3 布局后重载，布局回到默认 → "保存会话"只恢复了一半。

**修法**：`LoadSessionSnapshot` 中按值还原：`Grid.SingleView = (v == 1)` /
`Grid.SetGridLayout("2x2" | "3x3")`。

## 3. 构建与发布脚本

### 3.1 🟠 P0-S1 · 门禁在英文 SDK 下恒定误报（CI 一接就红）

**位置**：`tools/发布门禁.ps1:123-128`

```powershell
$realWarnings = @($buildOut | Where-Object { $_ -match 'warning' } | ...)
```

MSBuild **英文**摘要行 `    1 Warning(s)` 会被 `-match 'warning'`（大小写不敏感）命中，
而该行不含 `AVLN3001` → 判定为非白名单告警 → `$buildOk = $false`。

本机摘要是中文「1 个警告」，不含 `warning`，**所以本机不暴露、一上 CI 必炸**。
这正是"门禁在最需要它的地方失效"，讽刺的是它拦的是白名单内的告警。

**修法**：先排除摘要行 `-notmatch '^\s*\d+\s+Warning\(s\)'`，
或按 `warning\s+([A-Z]+\d+)` 提取 code 再做白名单比对（后者更严谨）。

## 9. 多路崩溃归因：实证排除 C1 关联（2026-09-14 11:58–12:05）

C1 修复前曾推测：`PAINTSTRUCT` 栈溢出的现象（偶发随机崩溃）与"多路播放 SIGSEGV/SIGILL"
无法区分，那些被归因为"内核缺陷"的崩溃里可能有一部分其实源自这里。
**C1 修复后重测，该推测已被证伪。**

### 9.1 测试

`--multitest <真实 4K HEVC 10bit 60Mbps> 2 15`，**连跑 5 次**：

| 轮次 | 退出码 | 信号 | 崩溃时所在阶段 |
|:--:|:--:|---|---|
| 1 | 139 | SIGSEGV | "并行扇出后" 之后（即 `SetViewTransform(1,0,0)` 复位与后续检查之间） |
| 2 | 139 | SIGSEGV | 静置播放 5s |
| 3 | 139 | SIGSEGV | 并行扇出 20 次循环 |
| 4 | 139 | SIGSEGV | 静置播放 5s |
| 5 | 132 | SIGILL | 静置播放 5s |

**5/5 全崩**，与修复前"近乎必现"的基线一致，未见改善。

### 9.2 结论

1. **多路崩溃与 C1 无关**——栈溢出已消除，崩溃率没有变化。
   之前"内核缺陷"的归因成立，本次实证把它从推测变成了结论。
2. **崩溃与视图变换无强相关**：3 次发生在**无任何交互**的静置播放期，
   说明是播放/解码路径本身的并发问题，不是 UI 触发的。
3. **单路稳定、2 路必崩**：`--selftest`（单路，含 20 次快速变换压力测试）连续多轮 exit=0。
   分界点明确落在"多路并发"，指向 FFF.Native 侧的多路 D3D 设备 / 解码线程竞态。
4. C1 的修复价值**不受影响**——它消除的是一个真实的内存破坏缺陷，
   只是恰好不是这个崩溃的原因。

### 9.3 后续定位：已于 §18 闭环（函数名级）

本节原列的"抓 dump / 怀疑共享资源"等建议**已经做完**，结论见 **§18**：

- 崩溃点是 `dxgi.dll`（不是 `avcodec`，也不是 D3D11 自身的稳定路径），
  由 `PlayerVideoRenderer::TimedTextThread → PresentTimedText → PresentCurrentFrame

  **交换链的"改写"与"呈现"由 `deviceMutex_` / `presentMutex_` 两把不同的锁保护**（§18.4）。

## 14. 第 3 批（续）：C7–C10 清理项收尾

### 14.1 C9 · 时间码「秒内帧号」（原结论方向对、修法错，已纠正）

**原判断**：`FrameIndex % round(fps)` 在 23.976/29.97 下会漂 —— **方向成立**。
**原给的修法** `FrameIndex - (long)(Position100ns / TicksPerSecond * fps)` —— **是错的**。

数值验证（帧 0..3000）：

| 帧率 | 现有实现 vs 真实秒边界 最大偏差 | 原建议修法的取值集合 |
|---|---|---|
| 29.97 | **29 帧** | `{0, 1}` —— 几乎恒为 0 |
| 23.976 | **23 帧** | `{0, 1}` |
| 25.0 | 1 帧 | `{0, 1}` |
| 60.0 | 1 帧 | `{0, 1}` |

原修法为何退化：`Position100ns` 与 `FrameIndex` 是同一事实的两种表示，
`(Position100ns / 1e7) * fps ≈ FrameIndex`，相减自然恒为 0——**它算的是"帧号与自身之差"**。

**真正的问题**：时间码的 `HH:MM:SS` 来自 `Position100ns`（墙上时间），而帧号来自
标称帧网格（29.97 按 30 计）。两套网格每秒相对滑移 0.03 帧，
**约 1000 s（16.7 分钟）后错开整整一个周期** —— 表现为「秒刚跳过去，帧号却是 29」。

**修法**：帧号与秒**同源**，都由 `Position100ns` 推出。实现下沉到
`Core/Display/Timecode.cs`（UI 纯计算必须下沉才可单测，见 §10），
`MainWindow.FrameInSecond` 只做一次转发，原有两条不一致的分支合并为一条。

代价（如实记录）：非整数帧率下某些秒会显示 29 帧而非 30 帧。这是"与墙上时间对齐"的
必然结果——既然秒已经是墙上时间，帧号就不能另起一套网格。

**回归断言**（新增 17 条，单测 80 → **97**）：整秒处帧号必为 0（0..2000 s 每 7 s 取样）、
半秒处取中间帧、秒内单调不越界、秒末取到最后一帧、无效输入返回 0。

**反向验证**：把实现换回旧公式 → 只有 29.97 / 23.976 两组 FAIL，
25/60/30 整数帧率仍通过 —— 与"问题只在非整数帧率"的预期完全吻合。

### 14.2 C7 · 抓帧失败路径对已释放 Bitmap 二次解锁

`MainWindow.Capture.cs`：失败分支先 `UnlockBits` + `Dispose`，`finally` 又 `UnlockBits` 一次
→ 对已释放的 Bitmap 再解锁必然抛异常，被外层 `catch { return null; }` 吞掉。
**结果"碰巧正确"，但每次回读失败都在抛异常**，异常路径常态化会掩盖真实问题。

改法：`readOk` 标志 + 解锁与释放的职责统一收进 `finally`
（`try { UnlockBits } finally { if (!readOk) Dispose }`），失败分支只 `return null`。

### 14.3 C8 · 缓存清理绕过 Dispose

`PlayerSurface.cs` 超限清理时 `_gradCache.Clear()` / `_bigFontCache.Clear()` 只清字典不释放
GDI 句柄，与同文件 `:371-385` 注释的自定规则矛盾（时间字体缓存 `:457` 本来就用对了）。
两处改为 `ClearGradCache()` / `ClearFontCache(_bigFontCache)`；
`ClearGradCache()` 此前全仓库无调用者，现在不再是死代码。

### 14.4 C10 · `_pendingAutoPlay` 改用 Interlocked

原用 `+=` / `--` / `= 0` 裸读写。当前各路续体都回到 Avalonia 同步上下文、实际串行，
**暂不构成数据竞争**——但这是对上下文的隐式依赖，换线程池续体就会静默出错，
而配额收支错乱的表现是"文件都打开了但就是不动"，极难定位。

改法：新增 `TryConsumePendingAutoPlay()`（CAS 循环，只在 >0 时递减，返回是否归零），
所有写入走 `Interlocked.Add` / `Interlocked.Exchange`，读走 `Volatile.Read`。
语义与原来逐条等价（含"配额已为 0 时不触发"这一条）。

## 16. S5 · 内核 DLL 与 SHA 绑定

**问题**：`Assert-KernelExtensions` 只校验**头文件文本**（PlayerApi 导出面），
证明不了 `FFF.Native/x64/<配置>/FFF.Native.dll` 就是这个内核 HEAD 编出来的。
而 `x64/` 被 `.gitignore` 且从不清空——内核切过分支或回退过后，
**陈旧 DLL 会被继续复用并部署出去**，现象是「构建全绿，但运行行为与基线对不上」。

**修法（戳记绑定）**：

1. 内核 msbuild **成功后**，在 DLL 旁写戳记 `FFF.Native.dll.3fcbuild`：
   第 1 行 = 内核 HEAD SHA，第 2 行 = DLL 的 SHA256。
2. **下次构建前**比对戳记第 1 行与当前 HEAD：不一致、或压根没有戳记 → 追加 `/t:Rebuild` 强制重建。
3. `Deploy-To` 里新增**部署后校验**：落地副本的 SHA256 必须与源一致，不一致即 `throw`
   （堵住"复制被占用/跳过 → 部署了旧 DLL"）。

**验证**（无法端到端跑，脚本需要 VS 工具链；这里验证的是判定逻辑本身）：

| 场景 | 期望 | 实测 |
|---|---|---|

## 18. 多路崩溃：转储级归因（2026-09-14 15:00–16:10）

§9 已用统计方法把"多路崩溃"定位到 FFF.Native 侧，但**崩溃点究竟在哪个模块的哪个函数**
一直没答案（§9.3 列为"需原生侧"）。本轮用 10 个历史崩溃转储把它做实了：
崩溃不在我们的托管代码里，也不在 FFF.Native 自己的逻辑里，
而在 **`PlayerVideoRenderer::TimedTextThread` 调用 `IDXGISwapChain::Present` 时的 DXGI 内部**。

|---|---|---|

### 18.2 崩溃聚类（10 个转储，来自 `%LOCALAPPDATA%\CrashDumps`）

| 簇 | 次数 | 异常 | 崩溃点 | 现场特征 |
|:--:|:--:|---|---|---|
| A | 3 | `0xC0000005` 读 | `dxgi.dll +0x19530` | 被读地址 = **`0xFFFFFFFFFFFFFFFF`** |
| B | 2 | `0xC000001D` 非法指令 | `dxgi.dll +0x33AF3` | 与簇 C 的故障点相距 3 字节 |
| C | 1 | `0xC0000005` 写 | `dxgi.dll +0x33AF0` | 被写地址 `0x00000A75F6A882D7`，不在任何模块内 |
| D | 1 | `0xC0000005` 执行/DEP | `0x00007FFD8EB00000` | **不属于任何已加载模块**，页对齐、不可执行 |
| E | 3 | `0xC0000602` FailFast | `coreclr.dll +0x21D34D` | RIP 在 `KERNELBASE!RaiseFailFastException`，是**主动**失败快退 |

读 `0xFFFFFFFFFFFFFFFF`、读到非法指令、跳转到不可执行的页对齐地址——
这三类是**同一件事的不同表现：通过一个已失效/被破坏的指针进入 DXGI**。
簇 E 是另一回事（托管侧主动 FailFast，见 18.6）。

### 18.3 符号化的崩溃调用链

两个栈可用的转储（簇 A 与簇 D）给出**完全一致**的线程身份：

```
PlayerVideoRenderer::TimedTextThread + 0x2F7          ← 线程入口（_beginthreadex 创建）
  std::condition_variable::wait_until<...>
    PlayerVideoRenderer::PresentTimedText + 0x542
      PlayerVideoRenderer::PresentCurrentFrame + 0x7E
        [d3d11.dll] → dxgi.dll                        ← 崩溃在这里
```

即：**崩溃线程是内核为每个渲染器起的字幕/定时文本线程**，
它在 `PresentTimedText` 里走到 `PresentCurrentFrame`，调用 `IDXGISwapChain::Present` 后死在 DXGI 内部。

崩溃时刻的线程构成（两个独立转储完全一致）：

- 进程共 **106** 个线程，其中含 `coreclr` 帧的 **15** 个（托管线程）
- 含 `FFF.Native` 帧的恰好 **4** 个，其中 **3 个同时触碰 D3D11/DXGI**
- 而本次会话只有 **2 路** ⇒ 每路不止一个原生线程在碰 D3D

崩溃线程栈上**没有任何托管帧**——托管侧不是直接参与方。

### 18.4 源码级定位：同一个对象被两把不同的锁保护

`third_party/fff_project/FFF.Native/3FP/Render/VideoRenderer.cpp`：

```cpp
// PresentTimedText()，4701 起
std::unique_lock deviceLock(deviceMutex_);            // 4702
const auto chainResult = EnsureSwapChain(...);        // 4706  ← 此刻只持有 deviceMutex_
...
std::unique_lock presentLock(presentMutex_);          // 4722
...
ComPtr<IDXGISwapChain4> retainedChain = swapChain_;   // 4752
deviceLock.unlock();                                  // 4753  ← 交出 deviceMutex_
const auto result = PresentCurrentFrame(retainedChain.Get(), generation);  // 4754 只持有 presentMutex_
```

而 `EnsureSwapChain` 内部会**改写**交换链：`ResizeBuffers`（2128）、`CreateSwapChain`（2141）、
`ReconfigureSwapChain → 释放旧链`（2098 / 2120 → 2234-2237）。

也就是说：

- **改写**交换链的路径持 `deviceMutex_`（`PresentTimedText` 在 4706 调 `EnsureSwapChain` 时还没拿 `presentMutex_`）
- **呈现**交换链的路径持 `presentMutex_`（4753 已经把 `deviceMutex_` 放了）

**两把锁保护同一个对象，因此它们互不排斥。** 源码自己在 3937 行写明这条不变量：

```cpp
// Present and ResizeBuffers must never overlap. Dropping this render is
// safe because the following decoded frame publishes the latest state.
```

主渲染路径（3922/3933）确实是先 `deviceMutex_` 再 `presentMutex_` 两把都拿，遵守了这条不变量；
但 `PresentTimedText` 在 4706 调 `EnsureSwapChain` 时只有 `deviceMutex_`，
另一条线程完全可以持 `presentMutex_` 正在 `Present`——不变量在这里不成立。

另有 `ClearSurface()`（4781-4793）在**完全无锁**的情况下读 `swapChain_` 判空，
只在最后 `Present` 前才取 `presentMutex_`。

### 18.5 结论

1. **崩溃归属明确**：`dxgi.dll` 内部，由 `TimedTextThread → PresentTimedText → PresentCurrentFrame
   → IDXGISwapChain::Present` 触发。与 C1（PAINTSTRUCT）、与托管侧都无关——
   崩溃线程上没有任何托管帧，§9 的"内核缺陷"结论至此从统计推断升级为函数名级证据。
2. **Crash 的直接形态**是陈旧指针（读全 1、非法指令、跳到不可执行页），
   与"交换链在被 Present 的同时被改写/重建"高度吻合。
3. **建议给内核侧的修法**（应用侧无法修复）：让交换链的所有改写路径
   （`EnsureSwapChain` / `ReconfigureSwapChain` / `CreateSwapChain` / `ResizeBuffers`）
   在**整个持续期间**持有 `presentMutex_`；并且 `Present` 返回前不要交出 `deviceMutex_`。
   最稳妥是把两者合并成一把锁。同时给 `ClearSurface()` 补锁。
4. **应用侧没有可规避手段**：这是核心功能路径上的内核缺陷。

### 18.6 附带发现：簇 E 是另一个问题

3 个 `0xC0000602`（`coreclr.dll +0x21D34D`，Debug 构建、03:25–03:29）**不是**多路崩溃：
RIP 落在 `KERNELBASE!RaiseFailFastException`，是运行时/代码**主动**触发的失败快退，
且三次偏移完全相同（确定性触发）。它与 §9 记录过的
"内核线程长于托管侧，CLR 停机后反向 P/Invoke"是同一类退出期问题，
应单独跟踪，不要和多路崩溃混在一起统计。

### 18.9 补充：崩溃点的时序分布与真实 Present 执行者

上一节的锁分析还需要两条补充事实才能解释"为什么静置播放也会崩"。

**（1）主渲染路径自己不 Present。** `RenderFrame`（约 3922–4036）在两把锁之下只做
准备与发布，末尾 `videoGeneration_.fetch_add(1)`（4021）+ `++presentationGeneration_`
（4032）+ `notify_one`（4036），**然后就返回了**。真正调用
`IDXGISwapChain::Present` 的**恒为 `TimedTextThread`**（`PresentTimedText` →
`PresentCurrentFrame`）。也就是说：这个渲染器**只有一个 Present 执行者，但它和
"改写交换链"的线程不是同一批锁在保护**。

**（2）空闲轮询路径只持 `deviceMutex_`。** `TimedTextThread` 在空闲（500 ms 无更新）时走
`devicePollOnly`，调用 `RequestRecoveryIfDeviceLost()`（4820）：

```cpp
bool PlayerVideoRenderer::RequestRecoveryIfDeviceLost() noexcept {
    std::lock_guard deviceLock(deviceMutex_);      // 只有 deviceMutex_
    return RequestRecoveryIfDeviceLostLocked();    // → device_->GetDeviceRemovedReason()
}
```

而此刻另一个线程完全可能正持 `presentMutex_` 在 `Present`（4753 已放 `deviceMutex_`）。
这条 500 ms 一次的轮询**恰好对应 §9 观察到的"3/5 崩溃发生在无任何交互的静置播放期"**——
不需要任何 UI 操作就会周期性触发。

**崩溃点时序实测**（`_3FC_CRASH_TRACE=60` 逐轮保留现场，4 次崩溃）：

| 轮次 | 退出 | 崩溃时播放位置 | 当时所处阶段 |
|:--:|:--:|---|---|
| 1 | 139 SIGSEGV | 0.45 s | 刚起步（"全路就绪"之后） |
| 4 | 139 SIGSEGV | 5.54 s | 静置播放刚结束、进入并行扇出 |
| 6 | 139 SIGSEGV | 7.95 s | 并行扇出后的 2 s 等待窗口 |
| 7 | 132 SIGILL | 0 ms（线程仅 61） | 启动/打开阶段 |

**崩溃点与测试阶段无绑定关系**（0.45 s 到 7.95 s 都有，另有一次在启动期），
进一步印证这是**随时可发生的竞态**，而不是某个特定 API 调用的确定性缺陷。
单次成功的轮次崩溃时线程数 105–107，与转储里的 106 个线程一致。

**追踪工具**：`_3FC_CRASH_TRACE=<间隔ms> --multitest ...` 会高频把多路快照
（位置 / presented / swapChainPresents / 状态）与线程数、句柄数写入
`crash_trace_*.log` 并 flush。崩溃后读文件最后几行即可把范围压到一个采样间隔内——
这是在本机 WER 不再写转储、且原生崩溃无法被托管异常处理器捕获的情况下的替代手段。

3. **minidump 的 CONTEXT 寄存器偏移**：这批转储比标准 `CONTEXT_AMD64` **整体前移 16 字节**
   （`Rip` 0xF8 / `Rsp` 0x98 / `Rbp` 0xA0 / `Rax` 0x78）。
   按标准布局读会得到 `RIP=0`。两个交叉验证证据：Rip 处的取值在 7/7 个非 FailFast 转储中
   恒等于 `ExceptionAddress`；Rsp/Rbp 处的取值落在崩溃线程的栈区间内。

```cpp
std::lock_guard deviceLock(deviceMutex_);
std::lock_guard presentLock(presentMutex_);
const auto chainResult = EnsureSwapChain(...);   // ← 会 ResizeBuffers / CreateSwapChain / Reconfigure
```

即 **`Redraw()` 不是"只唤醒"，它会改写交换链**。把它从"排队串行"改成"UI 线程并发直调"，
等于把 `EnsureSwapChain`（交换链改写）与 `TimedTextThread` 的 `Present` 的并发窗口
**从受队列约束变成受调用频率约束**——而 `--multitest` 第二阶段正是 20 次
`SetViewTransform` 扇出（每 50 ms 一次）。

**但它是加剧因素，不是根因**：§18.9 的 4 次崩溃里有 2 次发生在
0.45 s 和 5.54 s（都在 `SetViewTransform` 扇出开始之前），另有 1 次在启动期。
**没有任何 UI 操作时也会崩**（500 ms 空闲轮询即可触发，见 §18.9 第 3 点）。

### 19.6 汇总与建议

| 问题 | 结论 |
|---|---|
| 上游最新版？ | `2026.9.14`（`d8b2c038`），本地落后 3 个提交 |
| 升级能修崩溃吗？ | **不能**，`VideoRenderer.cpp` 零改动 |
| 崩溃是上游的还是我们的？ | **上游原生设计**（所有相关符号在上游基线里全在） |
| 本地补丁是根因吗？ | **不是**。`VideoRenderer.cpp` 只加 4 个 API 扩展和 3 处 `lock_guard`，未放宽任何锁 |
| 本地补丁有责任吗？ | **有加剧**：`SetViewTransform` 直写补丁把 `Redraw()→EnsureSwapChain` 从串行队列改成并发直调 |

**建议（按优先级）**：

1. **向上游提 issue**，附上 §18 的完整证据链（符号化调用栈 + 源码行号 + 转储聚类）。
   核心诉求就一句话：`EnsureSwapChain`（改写）与 `Present` 必须由同一把锁保护，
   而当前由 `deviceMutex_` 与 `presentMutex_` 两把锁分别保护。
2. **修正 `SetViewTransform` 补丁的注释**，或给它加约束：注释里
   "does not contend with decode" 是错的，`Redraw()` 会 `EnsureSwapChain`。
   若平移延迟问题允许，可考虑只在 zoom/pan 变化累积到一帧时才 `Redraw()`（合并调用），
   而不是每次 `SetViewTransform` 都 `Redraw()`。
3. **暂不升级内核**：9.14 相对 9.12 无可观收益（只是版本号 + 一个尚未使用的包引用），
   升级还要付 4 个 API 的重移植税。等上游出现 `VideoRenderer.cpp`/呈现层的实质改动再动。
4. 修正 `upstream-baseline-2026.9.11` 的命名（实为上游 9.12）。
