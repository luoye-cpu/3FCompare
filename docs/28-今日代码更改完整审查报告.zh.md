## 一、🔴 必修项（6 条）

按"是否已在生产路径启用"排序——前两条**当前就会产生用户可见问题**。

### B1 · pending 兜底返回的是自己判定为"陈旧"的帧 【生产路径 · 数据正确】

`native/wgc_capture/wgc_capture.cpp:555-577`

pending 只可能装热身期内被丢弃的前 2 帧，而 `:573` `EmitFrame(pending)` 把它当**成功帧**返回并写入 cache。
会话重建后（切窗口 / 最小化还原 / 上次 NOT_CAPTURABLE）若窗口静止只出 1~2 帧，
返回的就是**旧会话内容**；头文件 `:119-121` 自己写了"第 1 帧是上一次会话的陈旧内容"。
托管侧还会把它标成可信的 `CaptureRoute.Wgc`（`FrameCapture.cs:57-60`）⇒ **静默输出错误像素且被当作可信**。

> 这正是昨天修复"静态内容必然超时"时**引入的新问题**。
> `selftest[8]` 测不到：它用全新 handle 且无历史内容。

**建议**：仅当 `discarded > kDiscardFrames` 才允许 pending 兜底；
"会话刚建 + 静态窗口"应靠**跨会话保留 cache**（同 hwnd 时 `CloseSession` 不清 cache）兜底，而非靠不可信帧。

### B2 · 可信度失败时保留上一路的值 【生产路径 · 违反 D1 硬约束】

`src/3FCompare/MainWindow.axaml.cs:622`

`_lastFidelity` 仅在读 `RenderTargetInfo` **成功时**赋值，失败则保留**上一路**的值，而 `:634` 无条件刷新
⇒ 切到读不到 RT 的路之后，状态栏仍显示上一路的"像素级 1.00×"
⇒ **等于对一条未经验证的路宣称像素级**，直接违反 D1。

**建议**：`else` 分支置 `default`（`PixelFidelityTier.Unknown`）。

### B3 · 覆盖层两个诊断量无人消费 【接线时必翻车】

`LayoutOverlayWindow.cs:55,58` + `MainWindow.axaml.cs:487`

`HitTestHookInstalled` / `AchievedTransparency` **全库无消费者**（grep 只有定义处）。
- 钩子安装失败 ⇒ `WM_NCHITTEST` 不生效 ⇒ **覆盖窗吞掉对比区全部鼠标**（选中/滚轮/平移全废）
- 透明失败 ⇒ **不透明底直接盖住视频**

注释承诺的"宿主据此降级"没有实现。

**建议**：`ShowOverlay` 后断言二者，失败即 `ExitCompareMode()` + 状态栏提示；
或退化为用已写好的 `SetWindowRgn` 把窗口裁到只剩手柄矩形。

### B4 · `Worker::Invoke` 非并发安全，与头文件承诺矛盾

`wgc_capture.cpp:128-136`

头文件 `:128` 承诺"同一 handle 的并发调用会被内部串行化"，实现却用单一 `job_/done_` 无代际区分：
两线程同时 Invoke 会互相覆盖 `job_`、清掉对方任务、`done_` 提前放行，
一方任务被丢弃（`bad_function_call` 被 `:158` catch 吞掉）却返回 INTERNAL；
`Wgc_Destroy`(`:647-652`) 与在飞 Invoke 并发即 **use-after-free**。
当前靠 C# `_gate` 掩盖，但这是 **DLL 对外契约**。

**建议**：job 加 generation，谓词用 `doneGen_ == myGen`；或删掉该承诺、明确要求调用方串行。

### B5 · 新增的 zoom/pan 重载零调用，且与 4 参契约互斥

`src/3FCompare.Core/Backend/PixelReadback.cs:38-69, 85-149`

全仓调用点（`DiffOverlayView.cs:152/171`、`MainWindow.SelfTest.cs:681`）走的都是 **4 参**重载。
两者同名只差 3 个可选参数，但：
- 4 参要求 `rt` 是 **post-zoom** dest（内核已核实：`VideoRenderer.cpp:4451` 读 `lastDest*`，`:4561` 存变换后矩形）
- 7 参要求 `rt` 是 **fit 框**

后来者把同一份实机 `rt` 配上 `zoom≠1` 传入即**重复施加变换**。
（`TryResolveDrawnRect` 本身经逐项复核是正确的，含 `uint32` 截断=floor、`max(0,·)`、pan 符号。）

**建议**：接上 UI，或整块删除——不要把未走通的生产路径带上线。

### B6 · `public new void Hide()` 遮蔽基类

`LayoutOverlayWindow.cs:145`

任何以 `Window` 引用调用 `Hide()` 的路径都**不会** `DetachHost()`，覆盖层继续强订阅主窗口 ⇒ 泄漏。

**建议**：改名 `HideOverlay()`；或把 Attach/Detach 移到 `OnOpened/OnClosed` 由生命周期驱动。

### 🔴 修复过程中新发现：teardown 永久死锁（比原 flaky 严重）

追查原生自测间歇失败时，子代理挖出一个**真实死锁**：

> **窗口在捕获会话存活期间被销毁 → `GraphicsCaptureSession::Close()`（或后续 Release）永久阻塞**
> （实测 ≥150s 不返回）。表现是抓帧永不返回、**宿主进程冻死**，违反头文件"不会死等"的契约。

修复：`CloseSession` 先判 `IsWindow`；窗口已消失则**跳过 teardown**（不 Close 不 Release），
挂入进程级 `Graveyard`（`new` 出来永不 delete，避免 DLL 卸载时静态析构再跑同一段 teardown）。
代价：该情形会滞留一份代理对象（已权衡接受）。

反向验证：把旧实现的固定 300ms 热身塞回 DLL，新断言判红 313ms ⇒ 鉴别力保留。

### 8.2 大样本统计（修复前）

### 8.5 ⚠ 仍未解决：`67/5`

380 遍未再现，拿不到现场。但做了**结构性判定**：

> 72 = 23 条独立断言 + 7×`VerifyFrame`(7)；`VerifyFrame` = 2 项几何 + 5 项内容。
> `67 通过 + 5 失败` 恰好等于「**某一个 VerifyFrame 的 5 项内容断言全错、而尺寸/stride 正确**」

> 而不是"某环节挂掉导致 5 个用例连锁失败"。

### 8.6 下次再现时的排查步骤（已写入流程）

## 九、发布前阻塞项修复（2026-09-19 第二轮）

发布前对整条管线做复核，发现 3 项阻塞 + 若干建议修项。本节记录处理方式与理由。

### 9.1 🔴 生产源里残留的故障注入（已删除）

`native/wgc_capture/wgc_capture.cpp` 的 `EmitCached()` 里有一段由环境变量 `WGC_INJECT_BLACK_CACHE=1`
门控的"把兜底帧涂黑"代码 —— 那是反向验证判据鉴别力时加的**故障注入**，注释自述"验证后必须删除"，
却残留了下来，并且**已经编译进将要嵌入 exe 的那份 DLL**。

处置：整块删除，并在 Git Bash 重跑 `native/wgc_capture/build.sh` 重建 DLL。
**必须重建**：csproj 有"DLL 比源码旧即报错"的时间戳闸门（S3），只删源码不重建会让构建直接失败。
重建后 `selftest` **76 / 76 全绿**。

> 教训：故障注入必须与被测代码**同一次提交**删除，否则"验证工具"就变成"生产缺陷"。
> 这类门控最好用编译期开关而非运行时环境变量 —— 环境变量版能悄悄进发布包，且不重建就毫无痕迹。

### 9.2 🔴 S4 抓屏降级不可恢复（已修，采用"可恢复降级"）

问题：`CaptureRouter` 在 UI 层是**进程级静态单例**，`_downgraded` 一旦置位永不自愈。
3 次瞬时 WGC 失败（驱动重置 / 锁屏 / 目标窗口被临时占用）之后，本进程余下的导出帧与缩略图
全部永久走 GDI —— 而 GDI 对 flip-model **不可靠**，用户会一直看到错内容，直到重启应用。

**为什么选"可恢复"而不是"永久降级"**：永久降级确实省掉了反复尝试失败路径的超时代价，
但代价是"一次瞬时故障 ⇒ 整段会话静默输出错内容"，而且**用户没有任何自助恢复手段**（除重启）。
抓屏结果是要被当作对比素材导出/测量的，静默错内容比多花几百毫秒严重得多。
折中：不做"每次抓帧都重试"（那正是降级要避免的），只在两个**自然恢复点**重置：

| 调用点 | 理由 |
|---|---|
| `PlaybackCoordinator.OpenFilesCore`（打开媒体） | 所有打开路径（文件对话框 / 拖放 / 会话恢复 / 自动演示）的唯一入口；此刻目标窗口是全新的，也是用户眼中"重来一次"的动作 |
| `PlaybackCoordinator.HandleEngineEvent` → `DeviceChanged` | 引擎报显卡/显示器变更 —— 抓屏环境**确实**变了，原有 WGC 会话与失败计数都失去意义；若不重置，用户在提示后"手动重试"仍会拿到 GDI 的错内容 |

**没有**挂到设置对话框，理由有二：① 该 apply 路径位于混有用户未提交改动的 `MainWindow.axaml.cs`，
能不动就不动；② 设置项（`HardwareDecode` / `PreferredAdapterIndex` / `ColorMode` / …）影响的是
内核解码器，**没有一项改变 WGC 的可用性** —— 在那里重置属于"看起来合理但没有依据"的触发点。

实现：`CaptureRouter.Reset()`（清降级标记 + 连续失败计数），门面暴露 `FrameCapture.ResetRouting()`。
**线程安全**：Reset 从 UI 线程调用，而失败/成功上报来自抓帧线程，因此把状态收进单把内部锁
（初版注释写"本类不做同步、靠调用方串行化"，在引入 Reset 后不再成立，注释已一并更正）。
刻意**不**重置 `_probe`：探测结果是不可变的系统能力（是否支持 WGC / DLL 能否加载），进程内不会变。

### 9.3 🔴 干净检出无法构建（已修）

问题：`CheckWgcCaptureDll` 在 DLL 缺失时直接 `<Error>`，但该 DLL 被 `native/wgc_capture/.gitignore`
忽略、仓库内也没有基线归档（内核有 `.3fc_kernel_baseline.bundle` 可还原，WGC **没有**）
⇒ 没有 VS C++ + cppwinrt 的机器（CI、新克隆）连 `dotnet build` / `dotnet test` 都跑不起来。

处置：
- 缺失时降级为 **Warning**，消息给出正确指引（Git Bash 跑 `native/wgc_capture/build.sh`，需 VS 的
  「使用 C++ 的桌面开发」负载含 Windows SDK 的 cppwinrt 头）与后果说明（本次不会嵌入，
  运行时会全程退回 GDI）。
  > 注意：**不是** `tools/deploy_ffmpeg_for_tests.sh` —— 那是 FFmpeg 部署脚本，与 WGC 无关。
- 新增开关 `-p:WgcCaptureRequired=true`：发布/CI 门禁用它强制"缺失即 Error"。
- **保留**"DLL 比源码旧即报错"（S3 那条）不变：它拦的是"本机源码与产物自相矛盾"，
  与有没有 C++ 工具链无关；DLL 不存在时它自然跳过。

理由：运行时 `FrameCapture.GetProbe()` 探测到缺库已有 GDI 兜底、**本就不会崩**，
不该用构建失败去拦一个运行时不崩、且多数机器上根本修不了的条件。

验证（两条都实测）：

| 场景 | 结果 |
|---|---|
| 缺 DLL，默认 | `warning` + **生成成功**（0 错误） |
| 缺 DLL + `-p:WgcCaptureRequired=true` | `error` + 生成失败 ✔ |

### 9.4 ⚠ S5 / 误导性注释 / 同义反复断言（已修）

- **S5**：`GdiFrameCapture.cs` 的 BitBlt 路径里 `GetHdc` / `ReleaseHdc` 未包 `try/finally`
  （同文件 `CaptureViaPrintWindow` 已包，不一致）。已改为 `try { BitBlt } finally { ReleaseHdc }`：
  抓屏是会被反复调用的路径，不能靠"P/Invoke 一般不会抛"来赌。
- **误导性注释**：`MainWindowFidelityTests` 声称"UI 工程未开 `InternalsVisibleTo`、本批次不允许改 csproj"，
  而 `3FCompare.csproj:42` 早已对 `3FCompare.Platform.Tests` 开放。已去掉整套反射：
  `ResolveFidelity` / `DescribeFidelity` / `WithoutPixelClaim` 由 `private static` 改为 `internal static`，
  测试直接调用（编译器从此能帮上忙：改名/改签名会在**编译期**报错，而不是运行时才炸）。
- **同义反复断言**：删掉 `两条线取值可区分`（`Assert.NotEqual(Wgc, Gdi)`）—— 它比对的是两个枚举常量
  本身，只有"有人把两条线改成同一取值"才会红，不是可信的回归信号；
  保留 `默认值落在不可信一侧`（钉的是"默认落不可信侧"这一设计取舍）与 `路径标识与IsWgc一致`
  （真的调用生产属性 `CaptureRouteDecision.IsWgc`，能抓到它被写反）。
- 新增 4 条 `Reset` 用例（含一条并发状态一致性不变量守卫）。
