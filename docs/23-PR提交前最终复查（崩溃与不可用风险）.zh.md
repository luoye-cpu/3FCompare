## 一、【阻断 1】PR 只改内核 ⇒ 合入即坏

### 事实

补丁**只含 `FFF.Native/`**，`FFF.Player/`（上游 VB.NET 播放器）**一处未改**。

而上游播放器在创建会话前有两道硬校验（基线 `ea3ce05`，已实测确认）：

```vb
' FFF.Player/Core/播放器会话.vb:41
If 播放器原生接口.FFF3FP_GetApiVersion() <> 14UI Then
    Throw New InvalidOperationException("FFF.Native 的 3FP API 版本不兼容。")
End If
...
Dim 原生配置 As New 原生播放器配置 With {
    .大小 = 原生播放器配置大小, .版本 = 14UI,   ' ← 结构体仍 72 字节 / 版本仍 14
    ...
}
```

内核侧（补丁后）：

```cpp
// FFF.Native/3FP/Api/PlayerApi.cpp:12
constexpr std::uint32_t PlayerApiVersion = 15;
// :29  创建时严格校验
configuration->version != PlayerApiVersion || ...   → InvalidArgument
//     且要求 size >= sizeof(config)（80 字节）
```

### 后果链

1. 播放器 `GetApiVersion()` 返回 15 ≠ 14 ⇒ **抛 `InvalidOperationException`**
2. 即便绕过，`.版本 = 14UI` 且结构体 72 字节 < 内核 `sizeof` 80 字节 ⇒ `FFF3FP_Create` 返回失败
3. `播放器会话` 是**唯一**的会话创建点（`播放器控制器.vb:1126`）
4. ⇒ **上游播放器打不开任何文件**；`FFF.Player.Tests` 中所有需要会话的测试同步挂掉

播放器源码注释还写明这是**故意的快速失败**：
> "光盘导航接口及此前的渲染合同从 API 14 起才完整。这里必须在创建会话前失败，不能让输出目录中的旧 DLL 继续播放出错误颜色。"

⇒ 这不是"可能有兼容问题"，是**合入瞬间必坏**。

### 修法（必须随 PR 一起提交）

已核实全仓仅此 4 处，Recorder 走 3FR（`NativeApi.cpp:21` ApiVersion=4）不受影响：

1. `FFF.Player/Interop/播放器原生接口.vb` — `原生播放器配置` 结构**末尾**追加
   `Public 首选适配器索引 As Integer`（尺寸 72 → 80）
2. `FFF.Player/Core/播放器会话.vb:41` — `14UI` → `15UI`
3. `FFF.Player/Core/播放器会话.vb:49` — `.版本 = 14UI` → `15UI`
4. `FFF.Player/Core/播放器会话.vb` 初始化器 — 追加 `.首选适配器索引 = -1`

## 二、【阻断 2】`preferredAdapterIndex` 零值 = 静默换卡

### 事实

```cpp
// FFF.Native/3FP/Api/FFF.Player.Api.h:114（最终态，已确认无默认值）
std::int32_t preferredAdapterIndex;
```

基线 `ea3ce05` 的 `EnsureDevice()`（`VideoRenderer.cpp:1937-1968`）策略是：
**按"输出窗口所在显示器"匹配适配器**；无匹配时 `D3D11CreateDevice(nullptr, HARDWARE)` 用系统默认。

补丁后：`preferredAdapterIndex >= 0` 时**优先** `EnumAdapters1(index)`，**覆盖**显示器匹配。

⇒ **VB 侧零初始化得到 0，会被当作"显式指定 0 号卡"**，而不是"保持原策略"。

### 实测（本机，`.review_pr/hdrprobe/adapters.exe`）

```
EnumAdapters1 原生顺序:           [0] RTX 5080   [1] Intel UHD   [2] RTX 4060
EnumAdapterByGpuPreference 顺序:  [0] RTX 5080   [1] RTX 4060    [2] Intel UHD
系统默认 D3D11CreateDevice:       RTX 5080
```

**两种枚举顺序不一致**（索引 1/2 恰好互换）。本机 0 号恰为系统默认卡，侥幸无害；
但在 Optimus 笔记本上 0 号完全可能是核显 ⇒ **独显→核显，硬解失败或性能暴跌，且不报错**。

### 描述文件还有错误陈述

`proposal-description.md:81` 写「`-1`（默认）保持现有行为」——**内核根本没有默认值**。
这是安全关键点上的误导。

### 修法

1. 内核：`std::int32_t preferredAdapterIndex = -1;`（对 C++ 宿主生效）
2. VB 侧：初始化器**显式** `.首选适配器索引 = -1`（对零初始化宿主生效）
3. 描述：把「`-1`（默认）」改为「**调用方必须显式设为 -1**，否则 0 会被解释为 0 号适配器」

## 三、【高危】`ReadPixelRegion` 整数溢出 → 堆越界写

```cpp
// FFF.Native/3FP/Render/VideoRenderer.cpp:4623（最终态，已确认）
if (dst == nullptr || width == 0 || height == 0 ||
    dstFloatCount < width * height * 4u)
    return FFFResult::InvalidArgument;
...
const auto copyWidth  = std::min(width,  swapWidth_  - x);
const auto copyHeight = std::min(height, swapHeight_ - y);
```

- `width * height * 4u` 是 **uint32** 运算。`width=65536, height=16384` 时
  `width*height = 2^32 ≡ 0`，`×4 = 0` ⇒ 校验恒通过，**`dstFloatCount=0` 也放行**。
- 实际写入量由 `copyWidth × copyHeight × 4` 决定（裁剪到 swap 尺寸）。
  1920×1080 即 **8,294,400 float ≈ 33 MB**，写入调用方可能只有几十字节的缓冲 ⇒ **堆越界写 / 崩溃**。
- **可达性**：宿主通常按同样的 `w*h*4` 分配缓冲，同样溢出 ⇒ 小缓冲 + 大写入，是很自然的写法。

> ⚠️ **更正 `docs/21` P2-3 的判断**：原文称"实际写入量被 copyWidth/copyHeight 限制，不会越界写"。
> 这个判断**错了**——它假设 `dstFloatCount` 校验仍然有效，而溢出恰恰**击穿了这道校验**。
> 应从 P2 提升为**提交前必修**。

修法：`static_cast<std::uint64_t>(width) * height * 4u` 参与比较。
