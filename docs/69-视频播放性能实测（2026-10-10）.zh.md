# 69 · 视频播放性能实测（2026-10-10）

> 范围：HEVC 与 AV1 的视频播放开销，SDR 8-bit 呈现路径 vs HDR 16-bit 呈现路径，
> 以及增强 HDR 格式（HDR10+ 动态元数据，附带 HDR Vivid）是否带来额外开销；
> 分辨率覆盖 1080p / 4K / 8K。
> 本文所有读数都指到 `tests/output/perf-hdr-20261010/logs/` 下的日志，
> 每条指令都是本轮实跑过的；量不了的写进 §九 未验清单，不写成结论。

> **引用口径**：本文所有 `文件名:行号` 内核引用都指**出货树** `third_party/fff_project/FFF.Native/3FP/…`；
> 另一棵 `3fp/kernel/FFF.Native/3FP/` 下有**同名文件**（行数不同，实测 `HdrProcessor.cpp` 一边 736+ 行、一边 578 行），
> 按裸文件名解析行号会指向错的那棵 —— `3fp/tools/校验文档行号引用.py` 就因此把一处引用判成越界。
## 〇、四句话答案

1. **HEVC 与 AV1 谁贵，取决于分辨率**：软解 1080p 时 AV1 贵约 60%，4K 贵 10–29%，
   到 8K 反而**便宜**（8bit 61.2 vs 67.5 ms/帧；10bit HDR 84.0 vs 99.5）。
   硬解下两者都不成问题：0.13–2.07 ms/帧。
2. **位深是软解侧真实的成本轴，"HDR 标签"不是**：8→10bit 使软解贵 15% / 41% / 25%
   （1080p/4K/8K），而把同样像素标成 PQ+静态元数据并无可测增量。
3. **SDR 8bit 与 HDR 16bit 两条呈现路径的 CPU 差，在这台机器上量不出来**
   （同批重采样漂移就有 ±15~40%，见 §七之 2）；真正看得见的代价形态是
   **"8K + HEVC Main10 的带窗呈现"塌到 3.0–19.2 fps**，而同分辨率同位深的 AV1 不塌（§七）。
4. **HDR10+ 的额外开销是每帧约 3.3 µs CPU（= 60fps 预算的 0.02%），且与分辨率无关**；
   在 16bit HDR 臂上它连这 3.3 µs 都不花（曲线按设计不建，`applied=0/refused=360`），
   那里动的是逐帧 DXGI 信令（6 秒内发 238 次、被 2% 门抑制 122 次）。
   端到端量不到它，是**方法下限**决定的，不是"测出为零"。

## 二、为什么必须新建仪器（这一段本身就是结论）

三条独立理由，每条都有行号或哈希：

1. **现成的无头基线跑的不是出货树。** `3fp/build/FFF.Native.dll` 与
   `3fp/kernel/FFF.Native/x64/Release/FFF.Native.dll` 同为 sha `4dd6a1b293e44a74`（1,319,936 B），
   而这棵树里 `2094` / `BuildDynamicToneSettings` / `dynamicCurve` / `CUVA` 的 grep 结果全是
   **none**；ST 2094-40 的解析与曲线只存在于 `third_party/fff_project`
   （`Hdr/HdrMetadataParse.cpp`、`Hdr/HdrToneCurve.cpp`、`Render/VideoRenderer.cpp`）。
   ⇒ 用 `upload_bench.exe` 量"HDR10+ 有没有开销"，量的是一台没接传感器的表。
2. **`upload_bench.cpp:62` 把 `colorMode` 钉死成 `MapToSdr`** ⇒ 历史基线里
   `1080p-hdr-cpu` 那条测的是"HDR 片源映射到 SDR"的分支，不是 HDR 呈现路径。
   本轮把 `--color sdr|hdr` 和 `--forcehdr` 变成显式变量。
3. **无头模式在渲染函数里早早返回**：`3FP/Render/VideoRenderer.cpp:4866`（`Render()` 里的 `if (window_ == nullptr)`）
   `if (window_ == nullptr) { ++presentedVideoFrames_; return Success; }`，
   而交换链创建（`EnsureSwapChain` 4870）、平面上传（4906-4916）、动态曲线
   `BuildDynamicToneSettings`（4939-4950）与像素着色器全在它之后。
   同一原因：`OutputSupportsHdr()` 在 2577 行看到 `window_ == nullptr` 就返回 false，
   所以 `swapOutputBits_`（`OutputBitDepth()` 定义在 6221 行）停在 8——
   实测：无头 + `--color hdr --forcehdr 1` 得到 `outbits=8`。
   ⇒ **16-bit 路径只在有窗口时存在**，任何"Sdr vs HDR 呈现开销"的比较都必须开窗。

新仪器：`3fp/tools/play_back_perf_bench.cpp` + `3fp/tools/build_fork_probe.py`
（不改 `build_probe.py`，那棵树并行 agent 在用；也绝不覆盖 `3fp/build/FFF.Native.dll`）。
探针自带三道守卫，任一触发就退出非 0 并把该行记为"未判"而不是绿：样本间构型不一致（3）、
要 HDR 臂但 `outbits≠16`（4）、要硬解但内核回报 `decodeMode≠2`（5）、
要 HDR 臂却是无头（6）。`SAMPLE` 行 29 个字段用单一 `sscanf` 匹配并核对命中条数，
字段错位会当场失败。

## 三、夹具与被推翻的三条夹具假设

素材全部从**真实片源**编出（`real_4k_hevc_hdr10_60m.mp4`、`real_8k_av1_hdr10_100m.mp4`，
Jellyfin 官方库），`testsrc` 系按 `docs/09` 明示不可用于结论，一处没用。
每档分辨率的角色：`sdr8` / `sdr10` / `hdr10`（静态元数据）/ `hdr10plus`（动态元数据），
HEVC 全四角色，AV1 取 `sdr8`/`hdr10`（本机工具链无法为 AV1 生成 HDR10+，见 §9）。

三条假设是被证据推翻的，留在这里是因为它们都会静默改变结论：

1. **AV1 编码参数写错**：`-svtav1-params "...:la=0"` ⇒ `Error parsing option la` ⇒
   编码器 init 失败、`rc=-22`、6 条 AV1 臂全灭。首轮日志只留了末 3 行，报错被裁掉。
   修：去掉 `la=0`。另注意 SVT-AV1 4.2 会把 `preset 12` 映射到 11，且 4K 以上强制降到 M9。
2. **容器在撒谎而码流是对的**：SDR 角色的 HEVC 文件里 VUI 是 `bt709`，但 mp4 的 `colr`
   从源片继承了 `smpte2094/bt2020`，而**内核读的是容器**——实测
   `hdrsrc=1 fmt=1 path=1`。修：`-c copy -color_trc/-color_primaries/-colorspace bt709`
   重封装，并用 packet size 序列 md5 证明载荷逐字节未变（9 个文件全等）。
   AV1 更狠：`color_config` 写在 Sequence Header OBU 里，重封装改不动，
   必须重编并在滤镜链里 `setparams=colorspace=bt709:...`；修后 `hdrsrc=0 fmt=0 path=0`。
3. **"另编一份不加 hdr10plus 滤镜的对照"不是对照**：两份的解码像素**不等**
   （1080p/4K 全流 rawvideo md5 不同），残差编码也不一样，
   于是出现了"动态臂比对照臂便宜 36%"这种不可能的读数。
   真对照：对动态臂本身做 `filter_units=remove_types=39`（去掉 PREFIX_SEI NAL）。
   三档全流/前 100 帧解码 md5 与动态臂**完全相同**，而 ffprobe 回报
   `MD=10 CLL=10 HDR10+=0`——静态元数据由容器 `mdcv/clli` box 继续供给了。
   （我先手搓 Annex-B NAL 切分时把像素改坏了：NAL 数据合法地以 `00` 结尾，
   与起始码的 `zero_byte()` 填充无法区分，裁尾部零就破坏 slice；in-tree bsf 才有边界感。）

两道夹具门都是可重跑的脚本，且都带"探针活着"的正对照：
`verify_fixtures.ps1` 先要求已知 HDR10+ 文件命中 `HDR Dynamic Metadata SMPTE2094-40` 标记
（12/12 帧命中）才允许它对别的文件断言"缺席"；`make_true_control.py` / 重封装步骤
都以 md5 等式收尾。

## 四、代码层的四个事实（决定开销该落在哪里）

1. **CPU 上没有 10→16 bit 的展开。** `sws_scale` 只在 `input.layout == 0` 时走
   （`3FP/Render/VideoRenderer.cpp:4802`（`const auto directYuv = input.layout != 0;`）），而 `DescribeInput` 给 `YUV420P`/`YUV420P10LE` 返回
   layout 1（有 `static_assert` 钉住），给 `NV12`/`P010LE` 返回 layout 2
   ⇒ 这些格式**逐平面直传**，YUV→RGB 在着色器里做。
   实测：全部 judged 行 `sws_per_frame_ms=0.0000`。
   ⇒ **撤回**：我一度把 `docs/46` 那张 1080p 0.546 / 4K 2.886 / 8K 15.213→22.266 ms 的表
   说成"当前出货路径不走的 sws 成本表"，那是**错的**——它是 `tools/upload_ab.cpp`
   严格交替 31 轮量出来的**上传路径**对比（`UpdateSubresource` vs `Map(WRITE_DISCARD)`），
   而 `docs/46:136` 本来就写着"视频不走 sws——layout 1/2 已直传 GPU，视频没有这项开销"。
   也就是说：文档没有与实现冲突，冲突是我读错了来源。
   `docs/45 §3.3` 的"sws 让耗时 +87%"是 ffmpeg 命令行独立分解实验，同样不是内核路径的读数。
   两件别混起来：`3fp/build/bench-before.txt` 里 `sws_ms_median=0.0` 是**分支未走**
   （directYuv 直传），而同一文件里 `lock_ms/present_ms` 也全是 `0.0`，那是
   `upload_bench.cpp:214` 用 `%.1f` 打印——亚 0.05 ms 一律显示成 0.0，那几列不带信息。
   本轮探针用 `%.4f`。
   ⇒ `softwareConvert100ns` 对**动画 GIF/WebP**（真走 sws）仍是有效读数，
   `anim_cost_audit.exe` 用在动图上，不是空转的闸。
2. **HDR10+ 的动态曲线只作用于"映射到 SDR"那条路——这是已声明的设计，不是缺陷。**
   `3FP/Render/VideoRenderer.cpp:4939-4941`：
   `useDynamicCurve = !prepareOnly && settings.transfer != 0 &&
   actualMode_ != MapToHdr && actualMode_ != RawHdrAsSdr && BuildDynamicToneSettings(...)`。
   `3fp/docs/58 §4.5`（任务 T3）写明理由：MapToHdr 下着色器不做映射、把画面交给 DWM/显示端，
   HDR10+ 在那条臂上的价值是**逐帧更新 `DXGI_HDR_METADATA_HDR10`**。
   实测（`3fp/tools/hdr10plus_arm_effect.ps1`，对照=同一片段只剥掉 ST 2094-40 SEI，
   解码像素已用全流 md5 证明相同；两次采样 `landedFrame` 都对齐到 120）：

   | 臂 | 像素 | srcPeak | effTarget | outbits |
   |---|---|---|---|---|
   | MapToSdr | **DIFFER**（曲线真的进了画面） | 1000 → 334 | 1000 → 1000 | 10 |
   | MapToHdr | **SAME**（渲染器不重塑形，符合 T3） | 1000 → 334 | 1015 → 1015 | 16 |

   而 `HdrProcessor::BuildDxgiHdr10Metadata`（`:713-736`）确实在动：
   `MaxContentLightLevel` 取动态窗口 `signalPeakNits`、`MaxFrameAverageLightLevel` 取
   `averageMaxRgb×10000`（低于峰值时），`MaxMasteringLuminance` 保持静态——
   注释写明"调色显示器的峰值不该逐帧变"。`effTarget` 不动也符合分工，它是**显示端**能力。
   ⇒ 我一度把这条说成"HDR10+ 在 16bit 臂上根本不生效"，那是**说过头了**：
   该臂上像素不变是设计，逐帧信令在变。真正的遗留问题只有"信令是否真的按帧发出
   `SetHDRMetaData`"无法从外部观测（见 §9）。
3. **曲线纹理与常量缓冲是无条件上传的。** 4943-4946 行注释写明"Uploaded unconditionally
   so the GPU state never keeps a previous frame's curve"，两条 `UpdateSubresource`
   每帧都发，与有没有动态元数据无关——所以这部分**不是** HDR10+ 的增量。
4. **`SetHDRMetaData` 按变更限流。** 4747 行
   `if (hdrMetadataValid_ && !HdrMetadataChanged(lastHdrMetadata_, metadata)) return;`，
   而 `HdrMetadataChanged`（1055-1062）用"相对移动 >2%"才判变。
   ⇒ `docs/58 §5.5` 点名的第二个风险（逐帧推 HDR 元数据让显示端 hunting）在实现上是关掉的。

## 五、HDR10+ 每帧 CPU 开销的确定值

仪器：`3fp/tools/hdr10plus_cost_microbench.cpp`。它把出货树的
`HdrMetadataParse.cpp` 与 `HdrToneCurve.cpp` **原文件直接编进来**（用空 `pch.h` 垫片 +
`/I` 顺序，垫片必须带 `<algorithm>`，否则 `std::min/max/clamp` 找不到），
从真实 ST 2094-40 边数据取操作数，重复 200 次清掉计时器底噪。

命令与实跑读数（`logs/microbench-hdr10plus.log`，`--frames` 见行内）：

```
py 3fp/tools/build_fork_probe.py hdr10plus_cost_microbench
cd tests/output/perf-hdr-20261010/bin
./hdr10plus_cost_microbench.exe <media> --frames N --iters 200
```

| 素材（frames） | 3 次边数据查找 | 2 次查找 | FromHdr10Plus | BuildFromWindow | 合计/帧 |
|---|---|---|---|---|---|
| `1080p-hevc-hdr10plus` (120) | 0.005 µs | 0.002 µs | 0.131 µs | 3.197 µs（1 窗口） | **3.335 µs** |
| `4k-hevc-hdr10plus` (120) | 0.005 | 0.002 | 0.129 | 3.243 | **3.379 µs** |
| `8k-hevc-hdr10plus` (40) | 0.005 | 0.002 | 0.131 | 3.283 | **3.422 µs** |
| `real_hdr10plus_rolloff` (120) | 0.005 | 0.002 | 0.125 | 3.162 | **3.295 µs** |
| FATE 向量 `hdr10_plus_h265_sample.hevc` | 0.016 | 0.008 | 0.212 | 4.801 | 5.037 µs（**只取到 1 帧，样本量不足**） |

三点解读：

* 与分辨率无关，符合预期——这是纯 CPU 数学，操作数是元数据不是像素。
* 3.3 µs/帧对 60 fps 的 16,667 µs 预算是 **0.02%**；对 8K 软解实测的单帧
  ~130 ms 是 **0.0026%**。`docs/58 §5.5` "解析 + LUT 生成……可忽略"的方向是对的，
  但它的算法账算小了：一行是 3 窗口 × 256 点 × PCHIP（每点含分段搜索与
  谐波平均斜率），量级是几万次浮点运算，不是"几百次"。
* `BuildIdentity`（同一 LUT 宽度、只填恒等表）实测 0.18 µs，
  即曲线的 3.2 µs 里 94% 是 PCHIP 求值本身，不是内存搬运。

§6 的端到端表会说明为什么 3.3 µs 在那套表里量不到。

能站住的三条：

1. **硬解把解码侧 CPU 压到 0.13–2.07 ms/帧**，比同素材软解低 3–60 倍；
   分辨率越高省得越多（8K HEVC 10bit：84–100 → 1.5–1.7 ms）。
2. **位深是软解侧真实的成本轴**：8→10bit 在 1080p/4K/8K 分别 +15% / +41% / +25%。
3. **AV1 与 HEVC 谁贵取决于分辨率**：1080p AV1 比 HEVC 贵 ~60%、4K 贵 ~10–29%，
   到 8K 反而**便宜**（8bit 61.2 vs 67.5；10bit HDR 84.0 vs 99.5）。
   同一批里 AV1 走的是 libdav1d（内核把 AV1 软解钉到 dav1d）。
4. 8K 软解**已经贴着实时线**（54.5–59.3 fps；`8k-hevc-hdr10stripped` 那次 29.83 fps/156 丢帧
   是一次明显的争用尖峰，已在 §八 按离群处理，不参与结论），4K 及以下软解仍满帧。
   与 `3fp/docs/46` 的"8K 软解 9.0 fps"差一个量级——那组是**带窗口**的旧构（含上传+Present），
   见 §八的口径说明。

真实流锚点（未改动的 Jellyfin 原件，同仪器同批）：
`real_4k_hevc_hdr10_60m` 20.83 ms、`real_4k_av1_10bit_60m` 32.94 ms、
`real_8k_av1_hdr10_100m` 84.31 ms（软解）；硬解 0.26–0.48 ms。
高码率真实流的绝对值比我合成的配对件更高若干，但**排序结论一致**。

## 七、SDR 8bit 路径 vs HDR 16bit 路径（带窗全链路）

这一维要带窗口才存在（§二第 3 条）。同一文件、同一帧，只切呈现构型
（`--color sdr` → 8/10bit 链；`--color hdr --forcehdr 1` → 16bit scRGB 链，
`outbits=16` 由守卫自证），差值即"呈现路径"的成本：

| 素材 | 呈现链 | 软解 cpu/f | 硬解 cpu/f |
|---|---|---|---|
| 1080p HEVC HDR10 | 10bit → 16bit | 11.20 → 9.12 | 3.27 → 2.72 |
| 1080p HEVC HDR10+ | 10bit → 16bit | 10.67 → 12.65 | 3.49 → 2.46 |
| 4K HEVC HDR10 | 10bit → 16bit | 36.89 → 34.99 | 2.97 → 2.57 |
| 4K HEVC HDR10+ | 10bit → 16bit | 38.36 → 39.41 | 3.79 → 2.97 |
| 8K HEVC HDR10 | 10bit → 16bit | 141.32 → 140.68 | 16.67 → 17.04 |
| 8K HEVC HDR10+ | 10bit → 16bit | 123.79 → 139.99 | 17.12 → 16.72 |

（`matrix-all.csv`，每格 3 次中位。）**没有任何一格的方向能连成一致**——同批内
10bit↔16bit 的差有正有负、幅度与重采样散布同量级（见 §七之 2）。
所以本机的诚实结论是：**在这条链上，8bit→16bit 呈现路径的额外 CPU 成本量不出来**；
它的代价形态不是 CPU，而是下面两点：

* **崩塌点是"8K + HEVC Main10 的带窗呈现路径"，不是位深、也不是 16bit 链本身**（逐条回 CSV 核实）：

  | 素材 / 构型（均为带窗硬解） | outbits | fps | 丢帧 |
  |---|---|---|---|
  | `8k-hevc-sdr8` | 8 | 58.83 | 0 |
  | `8k-hevc-sdr10` | 10 | 6.00 | 305 |
  | `8k-hevc-hdr10` | 10 / 16 | 19.17 / 15.50 | 224 / 241 |
  | `8k-hevc-hdr10plus` | 10 / 16 | 3.00 / 4.00 | 314 / 315 |
  | `8k-av1-hdr10`（同为 10bit） | 10 / 16 | **57.00 / 56.00** | 8 / 16 |
  | `real_8k_hevc10_150m`（真流 Main10） | 10 | 36.00 | 123 |

  同素材**无头**时 8K HEVC 10bit 硬解是 57.5 fps / 1.5–1.7 ms（§六）⇒ 解码不是瓶颈，
  瓶颈出现在有交换链之后；而 8K AV1 10bit 在同一构型下不崩，
  所以这不是"10bit 链"的通性。真实流锚点同方向（36.00 fps）。
  **机制未归因**（候选：该格式下拷贝/缩放走慢路径、DWM 复制、驱动快路径失效），
  判据记在 §九之 2。
* **CPU 侧不存在 10→16bit 展开**：`sws_scale` 只在 `input.layout == 0` 的兜底分支跑，
  而 `DescribeInput` 对 yuv420p/yuv420p10le 返回 layout 1、nv12/p010le 返回 2
  （头文件里有 `static_assert` 钉住）⇒ 全部 judged 行 `sws_per_frame_ms=0.0000`。

### 七之 2 · 这台机器上端到端读数的分辨率下限

同一 clip、同一臂、同一批内 7 次重复（`matrix-headline.csv` 的样本行，
`logs/matrix-headline.log`）：控制臂 7 个样本 11.94→7.83 ms **单调漂移**，
实验臂 7 个样本稳在 8.17–8.69。跨批次重跑同配置（`logs/cost-impact.txt`）最大
**|Δ| = 40.07%**。⇒ 任何小于"几毫秒/帧"量级的单点改动，端到端不可判；
本轮所有 µs 级问题一律改用直接量原语的仪器（§五、§八）。

## 八、增强 HDR 是否更贵：HDR10+ / Vivid

**真对照 A/B**（`make_true_control.py`：对动态臂自身跑
`filter_units=remove_types=39`，两臂解码像素已用全流 md5 证死相同，只差那条 SEI）：
端到端给出 −37.6% / +20.0% / −16.8% / +91.5% / −25.0% / −23.7%（`logs/an-headless.txt`），
**符号都不固定** ⇒ 按 §七之 2，这组数只能作为"量不到"的证据，不能作为成本。
（其中 8K 控制臂那次 29.83 fps/156 丢帧是一次明显的争用尖峰，已按离群处理。）

于是答案落在可确定的那层：

| 增量 | 实测 | 口径 |
|---|---|---|
| ST 2094-40 解析 → 快照 | **0.13 µs/帧** | 微基准，真实边数据 |
| 3×256 曲线烘焙（PCHIP） | **3.20 µs/帧**（1 窗口） | 同上；`BuildIdentity` 同宽度仅 0.18 µs |
| 边数据查找 3+2 次 | 0.007 µs/帧 | 同上 |
| **合计 CPU** | **≈3.3 µs/帧 = 60fps 预算的 0.02%** | 与分辨率无关（纯标量数学） |
| 16bit 呈现臂上的曲线烘焙 | **不发生**（`applied=0 / refused=360`，见 `docs/70 §五`） | 设计如此（`docs/58 §4.5` T3） |
| 该臂上真正动的东西 | 逐帧 DXGI 信令：6 s 内 **调用 238 次、被 2% 门抑制 122 次** | `hdr_signal_probe` |
| 着色器项（`DynamicEnabled!=0` 的 3 次采样+smoothstep） | **未分离**：只在映射到 SDR 的臂上存在，且被 §七之 2 的下限盖住 | 判据见 §九 |

`docs/58 §5.5` 的预测"解析 + LUT 生成……可忽略"**方向对、算错量级**：
它写作"每帧几百次浮点运算"，实际是 3 窗口 × 256 点 PCHIP（含分段搜索与谐波平均斜率），
实测 3.2 µs——仍然是可忽略，但差两个数量级不该靠感觉说。

**HDR Vivid**：本轮**没有可用读数**。仓库里两个 Vivid 向量（3840×2160、50 fps）实际只有
1 帧可解（`decoded=1`，`cpu/f 781–891 ms` 是进程启动而非播放），
分析器已按 `decoded>=30` 的下限把它们剔成未判；`hdrformat=5 path=6 windows=0` 说明
Vivid 分支被走到，但成本未量。

## 九、未验清单（本机量不了 + 闭合判据）

1. **HDR10+ 着色器项的绝对值**——需要目的像素可控且 GPU 计时。
   判据：`D3D11_QUERY` 时间戳包住 `DrawWithShader`，或同一素材在两档链尺寸下
   的 GPU 忙率差（`tools/measure_gpu_load.py`）。本轮未做，因 `--window` 改的是
   窗口而非链尺寸（链按 `EnsureSwapChain(frame->width, frame->height)` 取源尺寸），
   所以我那次"目的尺寸扫描"实测到的是合成代价，不是着色器逐像素代价——
   这条已记为仪器的口径缺陷。
2. **8K + 非 8bit 链吞吐崩塌的归因**（VRAM 带宽 / DWM 复制 / 驱动快路径失效）。
   判据：链尺寸与 `swapChainPresents` 已可取，缺 GPU 侧占用与显存曲线；
   用 `measure_gpu_load.py` 包住 8K `gpu-sdr`/`gpu-hdr` 两臂即可判。
3. **DV（Dolby Vision）**——盘上无任何 DOVI 配置记录（本轮普查 0 命中），
   `extensionEligible_` 与 `NvidiaVideoExtensions` 路径不可达，未测。
4. **AV1 + HDR10+**——本机工具链不能为 AV1 生成 ST 2094-40
   （`libsvtav1`/`libaom-av1` 无该选项，只有 `-dolbyvision` 那种别的 RPU），
   故 AV1 的动态元数据臂缺失；判据：能写出 AV1 T.35 METADATA-OBUs 的编码器。
5. **HDR 面板上的 16bit 呈现链真值**——本机面板非 HDR，`forceHdrOutput` 只能造出链。
   判据：真面板上比 `outbits=16` 与观感；信令侧已有 `hdr_signal_probe` 可跟着看。
6. **12bit / 16bit 码流源**——盘上最深 10bit；`DescribeInput` 支持 12/16bit 平面格式，
   但无素材，未测。
