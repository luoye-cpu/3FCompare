# 34 · 4 路崩溃（P1）覆盖层环境复测方案

> 目的：判定 4 路崩溃是**项目代码缺陷**还是**本机覆盖层/驱动环境**所致。
> 背景：五个代码侧假设已全部证伪（负载 / 漂移校正 / 多卡争用 / 并发 Present / 变换风暴），见 `docs/33`。
> 触发本方案的关键证据：崩溃率由「同轮第 2 个进程 + 会话累计时长」主导，**冷却 4 分钟后首个进程即恢复 exit=0**；本机今日 3 次蓝屏（`nvlddmkm` / `eaanticheat`，见 `docs/32`）。

---

## 一、环境快照（2026-09-20 07:52 实测，只检测未干预）

### 覆盖层 / 挂钩进程

| 进程 | 说明 |
|---|---|
| `RTSS` (pid 17512) + `RTSSHooksLoader64` | RivaTuner Statistics Server，**全局挂钩** |
| `MSIAfterburner` (pid 10396) | 与 RTSS 同源，硬件监控 + OSD |
| `NVIDIA Overlay` ×5 + `nvcontainer` ×4 | ShadowPlay / NVIDIA App 覆盖层 |
| `IntelGraphicsSoftware.Overlay` | Intel 核显软件覆盖层 |
| `steam` / `steamwebhelper` ×7 | Steam 覆盖层 |
| `wallpaper64` | Wallpaper Engine（动态壁纸，持续占用 GPU） |
| `eve-online` ×3 | **EVE Online 正在运行**（游戏） |
| `GHelper` / `HWiNFO64` / `ArmouryCrate*` | 华硕本厂工具 + 硬件监控 |

### ⭐ 最刺眼的一条

**`RTSSHooks64.dll` 被注入了 120+ 个进程**，且：

```
dwm (pid 2040) <- nvspcap64.dll
```

**桌面窗口管理器（合成器）里加载了 NVIDIA 的捕获钩子。** 所有窗口的呈现都要经过 DWM，而本项目的崩溃恰好发生在 Present 路径上。

---

## 二、要你做的准备（我不结束任何用户进程）

1. **退出 RTSS 与 MSI Afterburner**（托盘图标右键 → Exit；不是最小化）。
2. **退出 NVIDIA Overlay / ShadowPlay**（NVIDIA App → 设置 → 游戏内覆盖层 → 关闭）。
3. **退出 Intel Graphics Software 覆盖层**、**Wallpaper Engine**。
4. ⚠ **`dwm.exe` 里的 `nvspcap64.dll` 只靠"退出进程"清不掉，需要重启系统**。
   且 RTSS 通常随系统自启 ⇒ **重启后请先阻止其自启，或在自启后立刻退出**。
   ⇒ **建议：重启 → 不启动 RTSS/Afterburner → 立刻跑脚本**，这才是最干净的条件。

### 验证干净程度（跑测试前先确认）

```powershell
# 应返回空
Get-Process | Where-Object { $_.ProcessName -match 'RTSS|Afterburner|NVIDIA Overlay|IntelGraphicsSoftware.Overlay|wallpaper64' }
# dwm 里不应再有 nvspcap64
(Get-Process dwm).Modules | Where-Object { $_.ModuleName -match 'nvspcap|RTSSHooks' }
```

## 三、复测命令

### 第一步：在**当前**环境（覆盖层全开）跑一组基线

```bash
bash .review_pr/rtss_ab/run_batch.sh with_rtss 10
```

### 第二步：重启并退出覆盖层后，跑第二组

```bash
bash .review_pr/rtss_ab/run_batch.sh no_rtss 10
```

### 第三步：统计

```bash
python .review_pr/rtss_ab/analyze.py .review_pr/rtss_ab/runlogs/with_rtss_*.tsv
python .review_pr/rtss_ab/analyze.py .review_pr/rtss_ab/runlogs/no_rtss_*.tsv
python .review_pr/rtss_ab/analyze.py --compare \
  .review_pr/rtss_ab/runlogs/with_rtss_*.tsv \
  .review_pr/rtss_ab/runlogs/no_rtss_*.tsv
```

每组 10 轮 = 20 次运行，约 10~15 分钟。

## 四、⚠ 为什么按「位置」分组统计（否则结论不可信）

`docs/33` 已实测：崩溃率由**同轮次序**主导 —— pos1 6/17（35%） vs pos2 14/17（82%），**p = 0.0134**。
只报总崩溃率会把这个已知混杂因素混进去。曾经有一个看似显著的结果（p=0.0070）就是这么来的，次序反转后完全消失。

⇒ 脚本每轮固定跑 **pos1 + pos2 两个进程**，统计时**按位置分组再对比**。

另：**`exit=1` 是漂移断言失败，不是崩溃**，脚本已单独归类，不计入崩溃率（此前混淆过）。

## 五、判定标准

| 结果 | 判读 | 后续 |
|---|---|---|
| `no_rtss` 的 pos2 崩溃率**显著低于** `with_rtss`（Fisher **p < 0.05**） | **环境假设成立**：覆盖层/驱动是主因 | P1 **改判为环境级**，不在代码里继续找；在 `docs/33` 记录结论，发布说明里标注"建议在无覆盖层环境运行" |
| 两者**无显著差异**（p ≥ 0.05）且都高 | 排除覆盖层因素 | 回到代码，转测 `docs/33` 的线索②：**"停滞 → 轻量恢复"路径**（`SyncController` 停滞看门狗 `Pause→Play`） |
| 两者都**显著下降**（含 pos1） | 可能是重启本身 / 驱动状态复位的效果，而非覆盖层 | 补做"重启但保留覆盖层"的第三组来分离变量 |

样本量说明：每组 pos2 有 10 个样本，10 vs 10 在"8/10 vs 2/10"这种量级下 p ≈ 0.023，可检出。**若两组都在 80% 以上，说明天花板效应，需改用 2 路（基线仅 17%）重测。**

## 六、基线组结果（2026-09-20 08:03 实测，`with_rtss`）

```bash
bash .review_pr/rtss_ab/run_batch.sh with_rtss 10
```

| 项 | 结果 |
|---|---|
| 总崩溃率 | **18/20 = 90.0%**（exit=0 仅 2 次，漂移失败 0 次） |
| pos1 | 9/10 = 90.0% |
| pos2 | 9/10 = 90.0% |
| 崩溃形态 | exit 139（SIGSEGV）×19、132（SIGILL）×1 |
| 耗时 | 7 分 34 秒（单跑 4~20s，崩得很快） |

### ⚠ 一个与昨天矛盾的现象：位置效应没有复现

昨天 `docs/33` 实测 pos1 35% vs pos2 82%（p=0.0134），今天 **pos1 = pos2 = 90%**。

合理解释：今天整体已**饱和**（90%），天花板效应把位置差异压平了 ⇒ **昨天那个"位置效应"很可能也是饱和态下的伪影，而非稳定规律**。
这与昨天"变换风暴 p=0.0070 是次序伪影"是同一类陷阱。

**推论**：崩溃率更像由**机器当下整体状态**（驱动/合成器/覆盖层/会话累积）决定，任何"某个代码变量"的微弱差异都会被这个主导因素淹没。
⇒ 对照组若仍在 90%，说明天花板效应仍在，应按 §五 最后一条**改用 2 路（基线 17%）重测**。

（另：今天 90% vs 昨天 83%，也说明**跨批次比较确实不可靠**——同一配置同一台机器，隔一天就差 7 个百分点。）

## 七、安全约束

- 若发生**蓝屏**（不是进程崩溃）：**立即停止**，记录时间与已跑轮次，不重试。判断依据：重启后 `Kernel-Power 41` 事件 + `WER ReportArchive\Kernel_*`。
- 只用 4 路 + z=1，**不要放大**。
- 每组跑完让机器冷却几分钟再跑下一组。
