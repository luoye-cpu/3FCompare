## 二、P0 · 对比结果不可信

### 2.1 帧步进不暂停播放：master 停下、从路继续跑 【已验证】

`SyncController.StepFrames`（`Core/Sync/SyncController.cs:196-259`）**全程没有 `Pause()`**：

```csharp
try { master.Session.StepFrame(frames); }              // master 走 StepFrame
...
for (var i = 1; i < slots.Length; i++)
{
    var t = Math.Clamp(newPos + slot.Offset100ns, 0, long.MaxValue);
    slot.Session.Seek(t);                               // 从路走 Seek
}
```

关键在于两者对播放状态的影响**不同**（已回读内核源码确认）：

| 路径 | 内核行为 |
|---|---|
| master `StepFrame` | `PlayerSession::DoStepFrame`（`PlayerSession.cpp:899`）末尾 **`SetState(FFF3FPState::Paused, "step-frame")`**（:969） |
| 从路 `Seek` | `FFF3FP_Seek` 只改位置，**不改变播放/暂停状态** |

⇒ **播放中按帧步进，master 停在步进后的帧，而其余各路 Seek 完继续播放**，画面立刻错开。
逐帧对比的前提就是"所有路停在同一帧"，这条路径下该前提不成立。

**触发**：播放中点传输栏的"上一帧/下一帧"（`MainWindow.axaml.cs:299` 绑定 `FrameStepClicked`）。

**修法**：`StepFrames` 入口先对全部路 `Pause()`，步进后保持 Paused；
并在 UI 上明确"步进 ⇒ 进入暂停态"。

### 2.2 放大镜显示的不是光标下的内容 【已验证】

`Controls/MagnifierOverlay.cs:66-91` 的 `RefreshPixels` 把 **CenterPanel 的 DIP 坐标**
直接当成 backbuffer 物理像素坐标，三处换算全漏：

```csharp
// 注释自己承认："点 = DIP*RenderScaling (本类不知道 scaling，用 1 兜底)"
var centerX = (int)(cursor.X);          // ① 未乘 RenderScaling
var centerY = (int)(cursor.Y);
var gx = Math.Clamp(centerX - half, 0, (int)rt.SwapWidth  - ZoomGrid);
var gy = Math.Clamp(centerY - half, 0, (int)rt.SwapHeight - ZoomGrid);
```

① **未乘 `RenderScaling`** —— DPI 非 100% 时整体偏移一个缩放倍数（150% 时偏 1.5×）
② **未减去该 surface 在网格中的偏移** —— `cursor` 来自 `e.GetPosition(CenterPanel)`，
是**整个面板**的全局坐标，而 `rt.SwapWidth` 是**单路**后台缓冲 ⇒ 多格布局下
hover 右侧/下方格子时，`gx/gy` 被 `Clamp` 压到边角，显示内容与光标位置无关
③ **未用 `rt.DestX/DestY` 排除 letterbox 黑边**

**对比：探针链路是**对的。`MainWindow.axaml.cs:779` `MapPointerToVideoPixel` 做全了三件事：
`physX = local.X * RenderScaling`、坐标取自**单个 surface**、`MapToSource` 处理 letterbox、
还有 `MapFallback` 兜底。

⇒ 同一软件里"光标 → 视频像素"写了**两份实现，一份正确一份错误**。
这正是"两份 switch 迟早漂移"的又一实例（另见 docs/14 §1.1 的预设映射）。

**修法**：放大镜复用 `MapPointerToVideoPixel` 的同一条链路，并把 session 绑定为
**指针命中的那一路**（`surface.Index`）而不是当前选中路。

### 2.3 帧步进不检查帧率一致性 【代码确凿】

`StepFrames` 的 XML 注释与 `docs/04-同步模型设计.zh.md` 都承诺"帧率一致时 StepFrame、
不一致时按时间换算"，但代码中**没有任何 fps 比较分支**——从路一律 `Seek(newPos + offset)`。

多路片源帧率不同（如 24fps 与 60fps 两个编码版本）时，master 落在精确帧 N+1，
从路按时间线性映射到"时间上最接近"的帧，既非同帧号也非同内容相位。

### 2.4 并发帧步进无串行化 【代码确凿】

`MainWindow.Playback.cs:30-31` 直接 `Task.Run(StepFrames)`，而 `StepFrames` 内含
`Thread.Sleep(50)` 且全程不持锁（只在 `SnapshotSlots()` 取副本）。连按 → 键时
两个任务交错，从路可能落地在先发任务算出的**旧位置**。

## 四、P1 · 持久化与配置

### 4.1 写文件非原子，失败即损坏已有文件 【已验证】

`Core/Settings/SettingsStore.cs:86` 与 `Core/Settings/SessionSnapshot.cs:44` 都用
`File.WriteAllText(path, json)`——它会**先截断**目标文件。磁盘满 / 只读 / 被占用 /
写入途中进程被杀 ⇒ `settings.json`、`.3fcs` 变成 0 字节或半截 JSON。
下次 `Load` 抛 `JsonException` 又被 catch 吞掉 ⇒ **静默回退默认值**，
窗口几何 / 侧栏宽度 / FFmpeg 目录 / 语言全部丢失且用户无感知。

**修法**：写同目录 `*.tmp` → `Flush(true)` → `File.Move(tmp, path, overwrite: true)`。

### 4.2 没有 version 字段，`-1` 迁移每次启动都执行 【已验证】

`AppSettings` 与 `SessionSnapshot` **均无版本字段**。`SettingsStore.cs:54-55` 的
`MigrateLegacy` 每次 `Load` 都把 `WindowX/Y == -1` 置 null——而注释自己写明
"-1 在新语义下是合法坐标（副屏在主屏左侧）"。用户把窗口停在 X=-1 的副屏，
每次启动位置都被丢弃。

### 4.3 反序列化后零校验 【代码确凿】

畸形 JSON 静默整体回退默认；**合法 JSON 的越界值则直传**：
`ColorMode=99` → 直接 `(ColorMode)99` 传给内核；
`FrameStep=int.MaxValue` → `d * FrameStep` 溢出为负。

## 五、P1 · 安全

### 5.1 会话文件里的路径无校验（不可信输入）【代码确凿】

`MainWindow.axaml.cs:760` `snapshot.Items.Select(i => i.Path!)`：`string?` 用 `!` 强转，
null / 空白 / 相对路径 / **UNC** 一律直传 `OpenFiles`。
外部 `.3fcs` 可在用户无感知下让程序打开任意本地文件喂给解码器；
**UNC 路径还会外泄 NTLM 凭据**。
修法：`File.Exists` + 拒绝 UNC/相对路径 + 加载前确认。

### 5.2 `FfmpegDirectory` 可导致任意 DLL 加载 【代码确凿】

配置写在 `AppContext.BaseDirectory`（`SettingsStore.cs:12`，便携部署下常可写）。
投放一个 `settings.json` 指定任意目录 ⇒ `SetDllDirectoryW` ⇒ 内核 Delay-Load
加载该目录的 `avcodec-*.dll`。修法：配置迁至 `%APPDATA%`，或对 DLL 做签名校验。

### 本次审查的元发现

三处缺陷都源于**同一功能存在两份实现，其中一份是错的**：
探针的坐标映射是对的，放大镜的是错的；预设映射与恢复逻辑不同源。
⇒ 收敛到单一实现，比事后补测试更能防住这类问题。

> **2026-09-16 订正（重要）**：上面"探针是对的、放大镜是错的"这一**具体判断是错的**
> ——实测**两者都错了**，且错在不同层面：
>
> - 放大镜错在**几何映射**（传面板全局坐标、漏乘 RenderScaling、未排除 letterbox）；
> - 探针错在**坐标域**：内核 `FFF3FP_ReadVideoPixel` 的坐标域是**后台缓冲 / 交换链**尺寸，
>   不是片源分辨率。UI 一直把片源坐标直传 ⇒ 窗口小于片源时（常态）读到偏右下的位置甚至黑。
>   判据：4K 片源（client 1995×1122）下 x=1990 可读、x≥2500 失败；
>   换成 720p 片源后 x=1500/1920/1990 **全部可读** —— 越界边界恒等于后台缓冲尺寸，与片源无关。
>
> 之所以当时没发现，是因为**只用单点比对、且两点恰好落在同一色块里**。
> 这正是后来把断言升级为 3×3 九宫格的原因（离原点越远偏得越多，单点容易漏判）。
>
> 现已在 `Core/Backend/PixelReadback.cs` 收敛为**单一实现**：展示用片源坐标（对用户才有意义），
> 读取用缓冲坐标。
>
> ⇒ **元发现本身仍然成立，而且更强**：两份实现不仅"其中一份可能错"，
> 而是**可以各自独立地错**，且互为盲区。交叉验证 + 收敛单一实现，两者缺一不可。
