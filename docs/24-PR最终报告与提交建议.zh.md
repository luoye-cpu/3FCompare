### 5.4 本轮定位到的环境陷阱（重要，易复发）

⚠ **`FFF.Player.Tests/bin/x64/Release/` 缺全部 6 个 FFmpeg DLL**，
只有 `bin/Release/`（默认平台产物）是完整的。

- 从 `x64/Release/` 跑任何需要解码的用例 ⇒ **延迟加载失败**，
  异常码 **`0xC06D007E`**（低位 `0x007E` = `ERROR_MOD_NOT_FOUND`），
  表现为 **EXIT=127 且几乎零输出**，极易被误判成"沙箱不支持 GUI"。
- 定位手段：Windows 事件日志 `Application` 的 **事件 1026（.NET Runtime 未处理异常）**
  会写明进程名与异常码；`1000（Application Error）` 记录崩溃。
- 结论：**不要用 `bin/x64/Release/` 跑测试**；与 `docs/23` §8.4 记录的
  "必须用默认平台构建"是同一个坑的两面。

> ⚠ 更正：本文档初版曾把该现象归因为"沙箱不支持窗口创建"，**该判断错误**，已更正。

### 5.5 方法学提醒

- 本轮出现过"输出截断但 EXIT=0"的假象，根因是 **stdout 重定向到文件时为块缓冲**，
  进程异常终止会吞掉未 flush 的内容。C/C++ 探针加 `setvbuf(_IONBF)` 后结果稳定可复现。
- **EXIT=127 不等于"跑不了"**：先查事件日志拿异常码，再下结论。

## 六、需 maintainer 确认 / 提交时注意

### 6.1 语义变更（需在 PR 里明确说明）

`SetViewTransform` 从"排队到 Worker（解码）线程"改为"调用线程直写原子量 + `Redraw()`"。
这是本 PR 唯一改变既有执行语义的改动，描述中已用 ⚠ 标出。
理由：HD/HDR 播放时解码线程繁忙，排队的平移命令明显延迟甚至被下一帧覆盖。

### 6.2 合并顺序（重要）

`FFF3FP_Create` 要求 `version` 严格相等且 `size >= sizeof(config)`：

- **两个提交必须一起合并**；只合内核 → 上游播放器打不开任何文件。
- 若 maintainer 坚持拆成两个 PR：**先合并 `FFF.Player`，再合并 `FFF.Native`**；
  反过来会产生不可用的中间状态。

### 6.3 调用方义务（已写入头文件注释与描述）

- `preferredAdapterIndex` **必须显式初始化为 `-1`**。
  通过 P/Invoke 声明结构体的宿主（VB `Structure`）是零初始化的，`0` 是**合法索引**，
  会静默把播放钉死在 0 号卡并覆盖"按窗口所在显示器选卡"的默认策略。
- 索引必须来自内核使用的同一种枚举：`IDXGIFactory1::EnumAdapters1`。
  改用 `IDXGIFactory6::EnumAdapterByGpuPreference` 会因顺序不同而指向另一张卡。

### 6.4 可拆分选项

若 maintainer 希望先合并不带 ABI 变更的部分：可只取第 1、2、4、5、6、7、9 项（版本仍为 14），
第 3 项（多显卡）与第 8 项（播放器适配）单独讨论版本协调。
