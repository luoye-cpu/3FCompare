## 1. 接入形态判定

3FP 存在两层接口：

- **Native C API**：`FFF3FP_*` 系列（`FFF.Native/3FP/Api/FFF.Player.Api.h`，当前版本号 10），
  面向 C/C++/P/Invoke 调用方。
- **托管内核**：`FFF.Player` 程序集（`播放器会话`、`播放器控制器` 等，.NET 11，VB.NET），
  内部已封装 Native 调用并提供事件同步、取消、异常化错误处理。

**本项目接入方式（已决策）：直接基于 `FFF.Native` 源码开发（MIT 许可已确认）。**

核心理由：

1. `LICENSE.txt` 为 MIT（作者已确认有效），可自由修改/再分发/商用；
2. 我们需要 **VRR 交换链 / 视口子区域 / 全帧回读** 等上游当前未开放的能力，只有改内核才能拿到；
3. 与其把 `FFF.Player` 托管程序集当黑盒（受其 API 与事件语义约束），不如自带极薄互操作层，
   完全掌控 ABI 与扩展 API。

> 托管 `FFF.Player` 可作参考实现：其事件模型、错误处理、`播放器会话` 的线程纪律值得借鉴，
> 但我们不依赖其程序集。**

## 4. 互操作与数据流注意事项

1. **UTF-8 指针/位图固定地址只在同步调用期间有效**（托管互操作层会处理固定）；
   本项目如自行增加 P/Invoke 调用需遵守该契约。
2. **高频读取 `当前快照` 安全**；严禁在播放线程里直接访问 WASAPI 对象（我们不会）。
3. **播放器命令对状态敏感**：不适用命令抛 `播放器异常`；编排层需先查询快照状态再发命令。
4. **SDR/HDR 切换**：当前媒体 SDR→HDR 需要重配交换链（3FP 内部处理）；
   多路中某路 HDR、其余 SDR 时，`比较工具`（探针、差异）基于"颜色管理前缓冲"读值，
   需在相同 `色彩模式`（如都映射到 SDR 的 BT.709 码值）下对比才语义一致。
5. **每路独立 HWND**：flip-model 交换链不能同窗口并存；PlayerSurface 需保证互不嵌套。
6. **ACM/广色域**：探针回读（`ReadVideoPixel`）与截屏路径都走「颜色管理前」缓冲，
   因此**不依赖显示器是否启用 ACM**即可取得一致的视频码值；显示器侧呈现由 DWM 完成。
7. **VRR**：本软件不创建"覆盖在其他应用之上的图层窗口"（RTSS 式叠加），
   因此 VRR 只与**交换链参数 + 窗口 Present 节奏**有关；是否彻底生效取决于 3FP（见 A8/A9）。
   > **2026-09-16 实测**：已支持。`--selftest` 两条断言 `VRR 撕裂呈现: 显示器链支持 ✓`、
   > `VRR 媒体率节奏: 已启用 ✓`（对应 `SetPresentConfig` / `SetPacingConfig`）。
   > 这两项也是内核基线校验的 4 项扩展 API 中的 2 项。

**另立一条负载无关的 CFR 吞吐闸**（`content_period_probe` 的 **ⓔ**：呈现帧 == 该率 × 媒体时钟实际推进秒数，±10%）。它不替代上面那张表，它守的是"内容周期换了来源以后 CFR 会不会被掐住"这个风险面，而且不吃合成：12c 两容器实到 **91 帧**对 20fps×4.51s=90.2 ⇒ 差 0.9%，四臂 `PASS`。

**裸流缺陷（本轮发现，未修，归属已用实测排除）**：Annex-B 裸 H.264 在本播放器里**不出帧**。测了四种组合——VFR 裸流与 CFR 裸流、带窗口的 `present_pacing_probe` 与无窗口的 `content_period_probe`——全部 `呈现帧=0｜翻帧=0｜媒体时钟推进=0.00s｜两栏丢弃=0`，带窗口那趟还 `网格标定=0.00Hz、gridLocked 全程 0、bypass=2`，而 `FFF3FP_Open` 返回成功。补了快照回读以后定位到形状：**`state=5(Ended)｜duration=0.00s｜decodedVideoFrames=0｜queuedVideoFrames=0｜selectedVideoStream=0`**（对照正常件 `state=3(Playing)｜duration=6.03s｜解码 141｜队列 5`）。两条结论：
- **选流没问题**（`selectedVideoStream=0`，media info 也读得出数），坏在"一个帧都没解出来就已经判结束"；
- **本轮改动被实测排除**，不再是推理：`PresentVideoFrame` 在释放闸之后，而这件源 `decodedVideoFrames=0`，那段代码根本没被执行过。
剩下的根因（demux/decode 那侧为什么零帧、以及谁在无时长裸流上先判了 `Ended`）**本轮没继续查**——它不在本轮改动的路径上，且只有 `SetState(FFF3FPState::Ended)` 一处（`FlushAtEnd` 那条），值得单独一刀。顺带一条同形状的假阳：CFR 裸流的 `av_guess=20/1` 与 `r_frame_rate=40/1` 不等，于是 `frameRateMode` 在一条**恒定**裸流上报 `variable`——容器那条比较路会假阳，而实测那条路因无帧可测根本不介入（该件上 `⑥`/`ⓔ` 记未判，不是绿）。所以**没给裸流建判据**：那种源的节奏信息本就不存在（实测包级 PTS 输出 0 行），正确行为就是"未知⇒只剩面板那一半"，本轮已在无窗口臂量到它确实落到 60.0Hz 平台段。

该臂本轮读到的平台段是三条 `[起0.00 长1.56s @25.0Hz][起1.56 长2.02s @60.0Hz][起3.59 长0.40s @25.0Hz]` —— 最后那条不是换档，是 **EOF 之后队列空、取数退回容器那一档**（内核此时看到 `av_guess=20/1` 或 `25/1`，即流头那一段的率）。这就是 ⑥ 必须有"早段先于晚段出现"那条方向判据的原因：只问"有没有 25 的平台段"会被这条尾巴替早段作证，晚段红不红就都和早段无关了。12a 不能走无窗口臂：它晚段是 60，正等于无窗口时 `DisplayCadenceHz()` 的构造默认 60.0f，`min()` 读数分不出是哪一半赢 —— 所以本支自己把"晚段 < 60"写成了前置判据。

**CFR 那三条基线臂本轮也跑了，但取数被机器污染，只能这样读**：下午这台盒子上有游戏客户端（`DeltaForceClient-Win64-Shipping.exe`）、一个 `ffmpeg.exe` 和 `MsMpEng.exe` 在跑，于是 §A9 记录的呈现吞吐（60fps→59.7、240fps→131.5）本轮塌成 35.6–40.7 与 52.3。**归因靠消融 A/B**：同一负载下把取数退回旧两支再跑 60fps 臂 ⇒ 消融版 39.2 fps／传统丢弃 166，与修复版 35.6–40.7／153–195 同量级，而**两个构建的上限读数逐字相同**（60.00 / 24.00 / 144.0x）。所以：塌陷归机器；CFR 无回归的证据是**上限那三个数**，不是吞吐和两条计时判据（`瞄格误差`、`屏幕停留带内比例` 本轮在同一构建内部就红绿翻转 ⇒ 记未定，与 §A9 ④ 的不可重复性同向）。要正式收口得在安静机器上重跑这三臂。

⚠ 本轮还抓到一个会自己造假的仪器时刻：一次内核构建报 `C1085 … No space left on device`（磁盘瞬时耗尽，18.7s 后重试成功，事后 C: 仍有 16.2 GB），而当时构建脚本的 `tail -2` 把这个错误吞了 —— 紧接着跑的四臂里 12b.ts 判红，**跑的其实是上一轮消融留下的旧 DLL**。这条正是本仓反复踩过的"构建失败⇒陈旧二进制⇒假红/假绿"，所以 §A12 的读数一律要求同看**构建 rc=0 ＋ DLL mtime 新于源 ＋ 读数确实变**三件；补建重跑后四臂恢复全绿。
