## 十、自由拼接布局模型（取代单轴 N 带）

### 10.1 需求（用户 2026-10-07 追加确认）

- **横竖自由组合**，且允许**不对称**（一块横、一块竖混排）
- 形态是**任意自由拼接**：可含 **T 形交叉**、不等分矩形（用户明确选择"任意自由拼接"而非"嵌套切分"）
- 配一个**布局编辑器二级窗口**：用户在画布上拼出行列组合、预览后应用

### 10.2 关键结论：**绘制层已经支持自由拼接，受限的只有几何数据模型**

这是本轮最重要的发现，它把工作量从"重写渲染"降到"换布局模型"：

| 层 | 现状 | 是否支持自由拼接 |
|---|---|---|
| **线/手柄绘制** | `LayoutOverlayWindow.Render` 从 `ComputeCells()` 逐格取**右/下边界**作为线段（`Controls/LayoutOverlayWindow.cs:949-968`），用 `_segments` + `DrawLine` 画 | ✅ **天然支持**。逐格发边 ⇒ T 形交叉与断线自动正确，代码从不假设"整线贯穿" |
| **区域下发** | `WindowRegionClipper.ApplyRects` 用 `CombineRgn(OR)` 合并任意多个矩形 | ✅ **天然支持**（切片 2 已接到拉动路径） |
| **命中选择** | 需要"点落在哪个矩形" | ✅ 逐个矩形判即可（`CompareCellAtCursor` 已是这个形状） |
| **几何数据模型** | `GridPartition` = **每列/每行一个权重**的均匀网格 | ❌ **不支持**。它只能表达整行整列贯穿的 m×n；T 形交叉与非规则矩形表达不了 |
| **拖动语义** | `WithHandleDragged(k)` 按"第 k 条整线"搬运相邻两列权重 | ❌ 需要改成"第 k 条**线段**"（只影响该线段两侧的矩形） |

⇒ **结论**：需要新建一个"矩形拼接"几何模型（矩形树 / guillotine 或一般矩形划分），
并给它配一套"按线段拖动"的语义；绘制与区域下发两层可直接复用。

### 10.3 新模型：`MosaicLayout`（Core，纯逻辑，可单测）

```
// 一条拼接：若干互不重叠、并集恰好 = [0,1]² 的矩形，每个矩形带一个"槽号"
public sealed class MosaicLayout
{
    public ImmutableArray<MosaicTile> Tiles { get; }   // 每块：归一化 Rect + 槽号
    public ImmutableArray<MosaicSplit> Splits { get; } // 每条可拖线段：轴向 + 位置 + 覆盖区间
}
```

**要点**：

1. **不变式由构造保证**（与 `GridPartition` 同一哲学，不靠事后钳制）：
   ① 两两不重叠；② 并集恰好 `[0,1]²`（末边写死 1.0）；③ 每块宽高 > 0（
   0 宽块会让 `CreateRectRgn` 得到空区域、`SetWindowRgn` 失败，窗口整块不可见）。
2. **分割线是"线段"而不是"整线"**：每条 `MosaicSplit` 带一个**覆盖区间**
   （例如"竖线 x=0.5，只覆盖 y∈[0,0.4]"）。这正是 T 形交叉的表达方式，
   也是它区别于 `GridPartition.HandleCount` 的核心。
3. **拖动 = 只搬该线段相邻两块之间的边界**：拖第 k 条线段只改它两侧那两块，
   其余块纹丝不动（与 `WithHandleDragged` 的"只改相邻两权重"同一用户直觉）。
4. **构建方式**：`MosaicLayout.Split(edgeIndex, axis, position)` —— 对某块的某条边做一次切割
   （guillotine 式），因此**任意自由拼接都可由一串切割构造出来**，
   而编辑器只需提供"选一块 → 切一刀"这一个原子操作 + 撤销。
5. **相邻重复与不相邻重复**（用户决策见 §八）：槽号允许重复；
   同一槽号占多块时，区域 = 这些块的并集（`ApplyRects` 已支持）；
   **不相邻重复**需要镜像会话（§九，仍适用）。

### 10.4 与既有 `GridPartition` 的关系

- **不做替换**：网格对比（拼合）继续用 `GridPartition` —— 它是"整行整列"的高频形态，
  权重模型在那里更简单也更快，且已有大量判据钉着。硬换会无谓地动一大片已验证代码。
- **新增并列路径**：拉动 / 自由拼接走 `MosaicLayout`。
  两者共用：区域下发（`ApplyRects`）、绘制（逐格发边）、命中（逐矩形判）、
  像素预算（按块面积累加）。
- **迁移接缝**：`MosaicLayout` 提供 `FromGridPartition(GridPartition)`，
  于是"从网格切到自由拼接"时用户当前的分格被**继承**而不是重置。

### 10.5 布局编辑器二级窗口（`Views/MosaicLayoutEditorWindow`）

- **形态**：普通模态窗口（`SettingsWindow` 同款），**不是**覆盖窗口上的内嵌控件
  —— 理由见 §三 R1（覆盖窗口上的交互控件在本项目**从未实测**，`docs/30:189` 列为 P6）。
- **画布**：按当前对比区**实际宽高比**画一个矩形，里面显示当前拼接；
  每块中心标槽号；点击选中一块，工具条提供「竖切 / 横切 / 删除合并」。
- **切一刀 = 一次 `MosaicLayout.Split`**，位置由鼠标落点决定。
- **预览后应用**：确定 ⇒ 写回宿主并重排 + 重下区域；取消 ⇒ 丢弃。
- **探针前置**（§四 切片 0）：模态窗上的按钮/画布点击能否正常交互，先实测再依赖。

### 10.6 验收标准（在 §五 基础上追加）

9. **拼接不变式**：任意构造序列后，块集恒满足"不重叠 / 铺满 / 每块为正"（Core 单测，随机化构造 + 逐例断言）
10. **T 形交叉**：构造一个含 T 形交叉的拼接（如上半两块、下半一块），
    断言线段的覆盖区间正确、拖动某条线段只改它两侧两块
11. **编辑器往返**：编辑器导出 → 应用 → 再打开编辑器，拼接必须**逐字段一致**（防止序列化丢信息）
12. **区域一致性**：每块的实际 `SetWindowRgn` 回读区域 == 该块的独立复算矩形（真机逐块核对）
13. **变异验牙**：至少一条变异能让"不重叠/铺满"判据判红（例如故意让某块少 1px）

**⚠ 由验牙过程本身抓出的三个真实问题（都已修）**：

1. **判据原本没有绝对期望，是"自洽"而非"正确"**。`nobands` 变异第一次跑**没被判红**：
   逐带核对的期望值全部**从分区本身取出**，于是"分区只有 2 带"完全自洽、逐带核对照样全绿。
   ⇒ 补一条**不依赖分区**的期望：恒等映射下 `带数 == 参与路数`。
   （第一版补得也不对：写成 `WipeRoutes is null`，而 `EnterCompareOverlay` 会把
   `_wipeRoutes` 填成**非 null 的恒等表** ⇒ 条件恒不成立。改为逐项检查 `routes[i] == i` 后才真正有牙。）
2. **harness 的崩溃判定不能只看 stderr**：`Invalid Program` 那一类崩溃**可能一个字都不打**
   （不产 VEH 留痕、也可能不产 WER）⇒ 只看文本会把"跑挂了"读成"跑完了、没牙"。
   改为**以退出码为准**（合法码 0/1/2；原生异常码为负或大值）。
3. **变异臂的替换串必须能编译，锚点必须真的存在**。`mirrorsilent` 臂连续三次"编译失败"：
   第一版引用 `IPlayerSession`（`CompareOverlay.cs` 没有 `using _3FCompare.Core.Backend`）；
   第二版用条件表达式套 `default`（C# 推断不出类型，CS0173）。
   最终改为**在方法入口直接 `return false`** —— 零类型依赖、必定编译通过。

**⚠ 夹具自污染（真机判据抓出）**：镜像探针收尾时按 `routes.Length`（**带表**长度，选路后是 6）
收回 lane 数，而素材只有 5 路 ⇒ 留下 1 条多余空 lane，让后续单元判红
`网格对比入口的格数 5 ≠ lane 数 6`。正确目标是 `_sync.Count − 镜像数`。
**判据必须自己把夹具还原干净**，不能指望"下一个单元会自行收敛"。

**`noroutemap` 未取到读数的原因与处置**：镜像需要真实创建会话，而在 5 路档上
创建镜像会进一步推高 N（并发交换链数），落进 `docs/43` 的 RTSS 崩溃邻域 ⇒
该臂在跑到镜像判据前就崩了。这不是判据缺陷，是**测量环境的限制**。
⇒ 镜像的同步正确性由 **Core 单测 `SyncMirrorTests`（20 例，含 7 例段计数）**承担
（确定性、无 Win32、无 RTSS 干扰），真机侧由镜像探针覆盖"能建出来、两处都有区域、
与源路同位、撤回后释放、lane 数收回"。
**如实记账：`noroutemap` 这条真机牙本轮未取到。**

### 切片 9' · 审查轮：自查 + 对抗式复查（抓到 **2 个真实缺陷**）

**方法**：对全部新代码做对抗式复查（不重新确认"能跑"，只找反例），

#### 缺陷 A · `AddMirror` 允许"以镜像为源" ⇒ 镜像链（真实缺陷，已修）

`AddMirror` 只做了 `[0, _slots.Count)` 范围检查，而**镜像槽本身也在 `_slots` 里**
⇒ 传一个镜像槽的号**能通过检查**，造出镜像链：m2 的偏移跟随 m1，而 m1 跟随真实源路。
`ResyncMirrorOffsets` 若在中间层尚未对齐时读它，m2 就与真实源路错开 ——
**而"同一路错开"正是镜像最不能出的错**（这个功能的全部意义就是同一画面）。

- 判据：`SyncMirrorTests.拒绝把镜像当作镜像源_不允许镜像链`（判红 → 修 → 判绿）
- 修法：`AddMirror` 加 `IsMirrorIndex(sourceIndex)` 检查；是镜像则拒绝（返回 false、不追加）

⚠ **同时确认了两件"看起来可疑、实际是对的"**：镜像重建时的下标平移、移除源路时孤儿镜像的清理。
用独立探针逐槽打印验证过，逻辑正确。
**而我第一版探针把"字典键"当"列表下标"用、是探针自己错了 —— 差点据此去"修"一段正确的代码。**
这是本轮最值得记的一条：**怀疑代码之前，先怀疑自己的检查工具。**

#### 缺陷 B · `Split` 的 `Math.Min(0.5, ·)` 让最小尺寸承诺失效（真实缺陷，已修）

```csharp
var minRel = span > 0 ? Math.Min(0.5, MinSpanFraction / span) : 0.5;   // ← 错在这里
```
`span ≤ 2 × MinSpanFraction` 时这个 `Math.Min(0.5, ·)` 把下界**封顶到 0.5**
⇒ 继续切退化成"对半劈"，块一路变小、**突破文档承诺的 5%**。
实测连切 12 次可到 `0.000024`（容器的 **0.0024%**）。

**后果**：块小到 1px 以下时区域表达不出来（`PlanRegionsFor` 跳过该块）
⇒ **某一块在屏幕上彻底消失**，而用户只是多点了几下切分。

- 判据：`MosaicLayoutTests.反复切分不得把块压到最小尺寸以下`
  （判红：`第 2 次切分后出现宽度 0.025 的块，低于承诺的 0.05` → 修 → 判绿）
- 修法：父块 `span < 2 × MinSpanFraction` 时**拒绝切分**（返回 `this`），
  与"宁可这一层不跟手，也不产生坏几何"的既有取向一致。
  用户后果从"切了一下画面少一块"变成"这块太小、切不动"。

#### 缺陷 C · 区域换算"逐块各自取整"⇒ 漏一整行像素（**BLOCKER，独立 reviewer 抓出，已修**）

**这是我写的最隐蔽的一个缺陷**，也是本轮**唯一由独立复查（而非自查）发现的**：

`PlanRegionsFor` 对每块的 4 条边**各自四舍五入**。相邻块在归一化空间**数学上共享一条边**，
但两侧表达式不同（`A + B` vs `0.95`），浮点差约 `1e-16`；当 `边 × 窗口尺寸` **恰好落在 `.5` 平局**上时，
这个差会让两侧向**相反方向**取整。

确定性反例（reviewer 给出，我独立复现确认）：
```
0.8341561705991691 + 0.11584382940083071 = 0.9499999999999998   ← 块 4 的底边
而块 5 的顶边 = 0.95
在 h=2450 时：round(2327.4999999999995) = 2327   vs   round(2327.5) = 2328
⇒ 第 2327 行（整条 401px 宽）无人覆盖，露出父窗口底色
```
- 频率不低：**同一份布局在 [200,2400] 的 2201 个高度里有 110 个会露缝**（拖动窗口大小时时有时无）；
  20k 份随机布局约 1 份中招。
- **修法**：改为**共享像素边界表**（`BuildPixelCuts`）—— 先把该轴所有边界取整去重排序，
  再让每块从同一张表取端点 ⇒ 共享边必然取到同一整数，**缝与叠在构造上不可能出现**。
  这其实正是 `WipeBands.PlanRegions` 一直在用的做法（一张共享 `cuts[]`、长度取差），
  `PlanRegionsFor` 本就该照抄。

**⚠ 为什么所有既有判据都看不见它（这是最值得记的一点）**：
面积判据在**结构上**不可能发现这一级缺陷 —— 缝宽 `g` 只让面积和少 `g`，
而容差是 `1e-6`（4K 下相当于 0.0038px）。实测：`1e-6` 级缝能检出、`1e-7` 级不能。
而**我当时新加的像素级判据也是面积判据的翻版**（`AssertMosaicInvariants` 同样是面积和），
所以「Core 200 轮随机化 + 真机镜像探针」**全绿**，而屏幕上少一行像素。

⇒ **补的判据**：`区域换算后每个像素恰好被一块覆盖` —— 在多个窗口尺寸上**逐像素**扫，
断言"恰好被一块覆盖**且**不越界"。已验它**能判红旧实现**：
`401x2450：有 401 个像素无人覆盖（首个 (0,2327)）—— 会露出父窗口底色`（401 = 整行宽度）。

#### 缺陷 D · 自由拼接的线"能画、能命中、**拖不动**"（**真实功能缺口，已修**）

审查发现 `DragWipeLine` / `HitWipeLineAt` 写了却**没有任何调用者**（全树 grep 只有定义）。

### 关于"崩溃"的最终口径（本轮反复遇到，必须写清）

### 切片 7' · 路镜像（不相邻重复同时呈现）

**产物**：`SyncController.AddMirror` / `ResyncMirrorOffsets` / `Mirrors`（Core）+
宿主 `SyncWipeMirrors`（按带表按需创建/释放）+ `PlaybackCoordinator.CreateMirrorSession` +
**带→槽**解析 `SlotOfBand`。

**同步怎么保证（镜像的核心，也最容易做错）**：
镜像槽是一个**普通槽**，只是偏移恒等于源路 ⇒ 既有的漂移校正
（期望位置 = `masterPos + 槽偏移`）会把它当普通 follower 每拍拉回，
**不需要为镜像新增任何同步代码**。Core 单测 `SyncMirrorTests` **13 例**逐条钉住：
组 Seek 后同位、带偏移的源路落到相同媒体位置（而不是 master 位置）、
漂移校正把被人为拨错的镜像拉回、组播放/暂停覆盖镜像、
移除源路时镜像一并移除（不泄漏）、移除源路之前的槽时镜像源路号**跟着下标平移**。

**一个不写就会静默出错的点：判据必须是"槽"而不是"路号"**。
不相邻重复时同一路的两条带由**源槽**与**镜像槽**分别承载；若裁剪/命中仍按
`WipeRouteOfBand(b) == routeIndex` 比对，两条带会抢同一个 HWND ⇒
镜像拿不到区域（表现为"其中一处始终空白"）。故新增 `SlotOfBand`，
裁剪下发与命中测试**都改用槽号**。

### ⚠ 切片 7' 途中引入并修掉的一个崩溃回归（完整记录）

**现象**：改完镜像后，5 路 `--comparemodetest` 出现
**`baseline 3/3 不崩` vs `改后 3/3 崩`**（退出码 `0xC0000005` / `0x80131604`）。
这与既有的 RTSS 偶发问题**性质不同** —— 3/3 vs 0/3 不是概率，是确定性回归。

**根因（我自己的代码）**：为让"带表跟着 lane 数长"，我把 `GrowWipeBandsTo` 挂在
`SyncCompareModeToRouteCount` 里，而后者**由 `UpdateStatus` 调用**；而
`GrowWipeBandsTo` 会调 `ApplyCompareLayout` + `ScheduleCompareCrop`
⇒ 等于**在"刷状态栏"里改布局并连发 `SetWindowRgn`**，重入且时序危险。

**修法**：拆成两个版本，性质分开

| 版本 | 用途 | 是否做布局/下发 |
|---|---|---|
| `GrowWipeBandsTo` | 用户显式点「加路」 | ✅ 做 |
| `GrowWipeBandsDataOnly` | 路数在别处变了（`UpdateStatus` 汇聚点） | ❌ **只改数据** |

**验证**：改后 5 路跑 3 次 —— **2/3 完整跑完 30 项**；1 次崩溃且留痕为**已知 RTSS 签名**
（`ip=outside` / `state=0x10000` MEM_FREE）⇒ 确定性回归已消除，剩余为既有第三方偶发。

**教训**：`UpdateStatus` 是"全部路数变更路径的共同汇聚点"这句话很诱人（覆盖面全），
但它同时是**最高频、最靠近 UI 刷新**的路径。在它里面做"改几何 + 下发 Win32 调用"，
即便逻辑正确也是时序地雷。**"数据收敛"与"副作用收敛"必须分开考虑。**


### 切片 5' · 布局编辑器 + P6 模态交互探针（✅ 已通过）

  网格下仍是原来的"扩一条空 lane"——两者语义不同，已在代码注释与判据里写明分野。

**探针读数（真机 2/2 一致）**：

```
布局编辑器 ✓ 模态窗可建立、按钮可用态随选择变化、切分/设路/合并走生产处理器、
             确定回传往返一致、应用后 6 块 / 6 路均有区域
选择路   ✓ 窗口可建立、行数随带数、重复路不被去重、不相邻重复有说明、
             确认回传一致、应用到宿主 6 条带生效
选择路   ✓ 6 条带 / 映射 [0,1,0,3,4,4]
```

映射 `[0,1,0,3,4,4]` 恰好同时包含用户要求的两种重复形态：
**不相邻重复**（第 0 路出现在第 1、3 条带）与**相邻重复**（第 4 路出现在第 5、6 条带）。
判据逐条钉住：① 行数 == 带数；② 初始为恒等；③ 重复路**不被静默去重**；
④ 不相邻重复**必须给出说明**；⑤ 加/减带的行数边界；⑥ 确认回传与窗口内逐项一致；
⑦ 应用到宿主后带数与映射真的生效；⑧ 相邻重复时该路必须下发**两块**区域（并集可表达）。

**为什么「加路」要复用 `OpenPaths` 而不是自建会话**：打开编排涉及配额、原子闸门、
失败归还、自动播放意图、会话快照落盘一整套逻辑（`PlaybackCoordinator.OpenFilesCore`），
自己再写一份必然漂移。既有路径本身就是**追加**语义（`ComputeOpenCount` 对 `existing` 取余量），
正是这里要的。

**带表随路数收敛的落点**：放在 `SyncCompareModeToRouteCount`（"全部路数变更路径的共同汇聚点"），
而不是 `AddSlotPlaceholder` —— 因为**拖放 / 菜单打开 / 会话重载 / 崩溃重建**同样会让路数变，
只挂在加路键上会漏掉其余四条路径（漏了就是"新路没有带、加了看不到"）。

### 切片 3' 实现中由单测抓出的两个真实几何缺陷（记录以免重蹈）

随机化单测（200 轮固定种子构造序列，每步断言三条不变式）抓出两个 `DragLine` 的缺陷：

| # | 缺陷 | 症状 | 修法 |
|---|---|---|---|
| 1 | **吞并**：把"边落在 oldPos 的块"各自平移 delta | 左侧整条 + 右侧上下两块时，左条一直长到盖住右上块 ⇒ **两块重叠** | 改为按"层"配对搬运 |
| 2 | **跨线块**：某块在另一轴横跨这条线（如底部整条横带） | 它既非线左也非线右，被错配后与邻块重叠（实测重叠 0.013） | **只处理"干净层"**：要求一对块在另一轴上的区间完全一致，否则跳过该层 |

⇒ **含跨线块的线只有"干净层"部分跟手**。这是刻意的保守取舍：布局正确性优先于跟手范围。
若没有随机化判据，这两个缺陷都只会在用户拖到特定形态时才暴露，且表现是"画面缺块/串色"，极难归因。

### 切片 3''/4' 由真机判据抓出的第三个缺陷：区域坐标加了窗口原点

**症状**：真机判据报"第 0 条带在其窗口 1995x1122 内期望覆盖 `[0,698]×1122`，实际 `[2,2 698x1122]`"
—— 尺寸完全正确、**整体偏了窗口原点 (2,2)**。

**根因**：区域是**窗口相对**坐标（`SetWindowRgn` 语义，见 `WindowRegionClipper` 类型注释），
而块是**容器相对**归一化矩形。两个新函数都写成了"加窗口偏移"：

| 函数 | 错误写法 | 正确写法 |
|---|---|---|
| `WipeBands.PlanRegions` | `new Rect32(windowPx.X + start, windowPx.Y, …)` | `new Rect32(start, 0, …)` |
| `MosaicLayout.PlanRegionsFor` | `new Rect32(windowPx.X + x0, windowPx.Y + y0, …)` | `new Rect32(x0, y0, …)` |

对照既有正确样板 `CompareCropPlanner.Plan`：`region = cellPx - windowPx`（**减**窗口原点）。

**为什么危险**：偏 2px 在 4K 上肉眼几乎看不出，但它意味着**每条带都多露/少露 2px**，
且各带偏移量相同 ⇒ 带与带之间会出现**累积缝隙或重叠**（重叠会让 Z 序重新决定可见性）。
这是一个"看起来能用、实际破坏了核心不变式"的缺陷，靠单测（当时我在单测里也写成了"加偏移"的期望值）
**没有抓到**，是**真机逐带核对**抓到的。

**教训**：单测的期望值如果由我自己按同一错误理解写出来，就只是把 bug 抄了两遍。
真机判据的价值正在于它的期望值来自**另一个参考系**（Win32 回读的实际区域 + 独立复算的容器几何）。

## 一、问题定性（已核实，逐条有据）

用户读到的症状是「点加路后画面完全没变化」。上一轮曾把它定性为"设计如此"——
**技术上正确，但那个设计本身才是缺陷**：它由三处人为限制钉死，而非任何真实约束。

| # | 锁死点 | 位置 | 形态 |
|---|---|---|---|
| 1 | 拉动格表恒为 2 格 | `MainWindow.CompareOverlay.cs:58` | `static readonly CellRect[]` 长度写死 2 |
| 2 | 揭示区只表达互补两半 | `MainWindow.CompareOverlay.cs:210` | `OverlayRevealPlan(..., out regionA, out regionB)` |
| 3 | 每路只许一个矩形 | `MainWindow.CompareCrop.cs:1020` | `ApplyCropRegion(index, hwnd, Rect32)` |

**下游后果**：`CompareGridView.ArrangeOverride`（`Controls/CompareGridView.cs:447-453`）对
`cellIndex >= cells.Length` 的 lane 直接 `IsVisible = false` ⇒ 第 3 路起被静默丢弃。
于是「加路」只增空 lane（`AddSlotPlaceholder` → `Grid.SetCount`，不动 `_sync.Count`），
而空 lane 在拉动下必然落在 2 格外 ⇒ **画面零变化，仅状态栏一行字**。

### 关键结论：所需能力其实都已存在

| 能力 | 现状 | 证据 |
|---|---|---|
| 多矩形区域下发 | **已实现**（`CombineRgn` OR 合并 N 个矩形） | `Platform/WindowRegionClipper.cs:96-141` |
| N 条并列分区 + 权重 | **已实现**（`Uniform(lanes, cols, rows)` 支持 9×1） | `Core/Display/GridPartition.cs:110` |
| N-1 条独立可拖线 | **已实现**（`HandleCount` = Cols-1，`WithHandleDragged` 只搬相邻两权重） | `GridPartition.cs:235, 275-299` |
| 格→路映射 | **已实现**（互换/轮换在用） | `_compareRoute` / `NormalizeRoute` / `CellIndexOfRoute` |

⇒ 本改动**不需要碰内核**，是 UI/Platform 层对既有能力的解锁。内核保持 **API 16**，
`ConfigVersion` 与 `third_party/fff_project/FFF.Native` 一律不动。

## 二、目标语义（用户已确认）

1. **N 条并列窄带**：整幅被 N-1 条线切成 N 条，每条露出一路（与网格拼合同构）
2. **每条线可独立拖**：每线只改相邻两条带的宽度，其余带不动（`WithHandleDragged` 既有语义）

4. **拉动下「加路」= 弹选文件、新开一路**，该路直接作为新带加入
5. 底层**保留现有拉动专用路径**（不改成复用拼合）

## 三、风险与已知约束（实现前必读）

### R1 · 覆盖窗口上的交互控件**从未实测**（决定选路 UI 的形态）

`MainWindow.axaml.cs:1061-1065` 明确记录：

**对策**：选路做成**普通模态窗口**（与 `Views/SettingsWindow.cs` 同款，不是覆盖窗口上的内嵌控件），
绕开该风险面。覆盖窗口上仍只保留已实测可行的按钮/快捷键。
**并且先写探针验证模态窗交互**（见切片 0），拿到读数再决定。

### R2 · 拉动的显存代价会随路数线性增长

保留现有拉动路径 = 每路窗口都铺满整个对比区（`CompareOverlayCells` 两张 1×1 全幅）。
N 路 ⇒ 总交换链面积 = **N × 对比区**。这已是网格拼合的既有代价口径
（`MainWindow.CompareCrop.cs:67-80` 的 `CompareMagnifyPixelBudget` = 8 路 4K ≈ 66.4 Mpx），
但拉动的倍数此前"恒 2"从未进过预算核算。**必须**在 `EstimateCompareMagnifyPixels` 与
`docs` 里按 N 路重新记账，否则显存闸门失真（`CHANGELOG.md:26-27` 记过同类教训）。

### R3 · `_compareCropApplied` 是观测基准，不能只改写入端

该账本被 dragbench（`MainWindow.DragBench.cs`）与自测的 `RouteVisibleRectPx` 当作
"屏幕上真正露出的那一块"的唯一真源（`MainWindow.CompareCrop.cs:1061-1066` 写明 by construction 同源）。
把 `Region` 从单矩形改成数组时，**所有消费者必须同步**，否则读数与实际脱节。

### R4 · N 带互补性容易写错

现有 `OverlayRevealPlan` 的互补性靠"两半 + 各自 ≥1px"成立。推广到 N 带时不变式变成：
**两两不重叠、并集 = 整窗、每带宽高 > 0**。`Rect32` 要求宽高 > 0（0 尺寸区域会被
`CreateRectRgn` 解释为空区域、`SetWindowRgn` 直接失败）。三条不变式必须由构造保证，
并配单测钉死 —— 负宽矩形会让子 HWND 定位到非法尺寸（Win32 只认 16 位有符号）。

### R5 · 判据④当前会把本缺陷判绿

`MainWindow.SelfTest.cs:561-570` 的判据④只断言「新 lane **不可见**」+「状态栏有变化」，
**恰恰把"第 3 路被丢掉"当成正确结果**。这是本缺陷能长期存在的直接原因。
必须先改判据再改实现（否则改完也不知道对了没有）。

## 九、切片 5 详设 · 路镜像（支持不相邻重复）

### 为什么必须新增机制

`PlayerSurface` 是单个 `NativeControlHost`，只有**一个** `Hwnd`（`Controls/PlayerSurface.cs:20,138`）。
一个 HWND 的 `SetWindowRgn` 只能表达**一块连通区域**（或若干矩形的并集，但那些矩形必须
属于同一个窗口的同一组屏幕坐标 —— 而"不相邻的两条带"在屏幕上是分开的，任一路窗口位置
只能落在一个地方）。⇒ **同一路要同时出现在两条不相邻的带上，必须有第二个窗口。**

### 方案：每（路, 带组）一个镜像 surface，共享同一会话

- `Grid.SetCount(n)` 的 lane 数从"素材路数"解耦为**带数**（bands）
- 每条带一个 `PlayerSurface`（已有：`_surfaces[i]`）
- 带 i 与带 j 显示同一路时，两条带**各自**有 surface，但**共享同一个 `IPlayerSession`**
  - 关键前提：本项目**已经**验证过"多个子 HWND 共享一个会话"吗？—— **未验证**，见下
- 内核 `FFF3FP_Create` 每次创建**一个**会话绑定**一个**输出窗口
  （`Fff3FpEngine.CreateSession` 传 `OutputWindow = options.OutputWindow`）
  ⇒ **一个会话只能渲染到一个窗口**。这是最硬的内核约束。

### ⚠ 因此"共享同一会话"在现有内核 API 下**不成立**

`FFF3FPConfiguration.OutputWindow` 是会话级字段（`Core/Backend/Fff3FpEngine.cs:38`），
一个会话 = 一个输出窗口。要"同一路出现在两条带且共享解码"，只有两条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| **M1 · 镜像会话** | 同一文件开两个会话，各自绑一个窗口；同步层把它们当**同一路**对待（同一 offset、同一播放位置、同一 Seek） | 每镜像一份解码器 + 交换链 ⇒ 内存/GPU 开销按镜像数线性增长；同步必须成组下发，否则两带画面不同步（**这正是"对比"最不能出的错**） |
| **M2 · 改内核** | 内核支持一个会话渲染到多个窗口（多视图/多输出） | 需改 `FFF.Native` + 递增 `PlayerConfigVersion`（严格相等校验）⇒ 破坏"不动内核"前提，且随包内核必须整体重出 |

**M1 是可行且不需动内核的路线**，但它把"对比"的可靠性押在**同步成组下发**上 ——
两带若漂移一帧，用户看到的"同一画面"就是假的。本项目 `SyncController` 已有 master/offset
与漂移校正机制，可复用，但镜像组必须作为**原子单元**参与 Seek/步进/漂移校正。

### M1 可行性：**已核实可行，且同步机制已存在**（不需新建同步逻辑）

关键发现：`SyncController` 的漂移校正**已经**是"以 master 为 leader、其余路为 follower"
的通用机制，而 follower 的期望位置恒为 `masterPos + slot.Offset100ns`
（`Core/Sync/SyncController.cs:1330`，Seek 下发见 `:1359`，日志见 `:1377`）。

⇒ **一个"镜像槽"就是 `Offset100ns == 0` 的普通槽**：
- 它与 master 同位置 ⇒ 漂移校正每拍自动把它拉回 masterPos（半帧内视为已收敛，`:1354`）
- 组播放/暂停/Seek 走既有 `ForEachSlot` / `ForEachSlotIndexed`（`:465, :518`）⇒ **天然成组下发**
- 无需为镜像新增任何同步代码

这正是 M1 相比 M2 的决定性优势：**复用已验证的同步层，而不是新写一套**。

### M1 仍需处理的点

| # | 点 | 说明 |
|---|---|---|
| 1 | 镜像槽的**锚定语义** | 镜像必须锚到"被镜像的那一路"，而不是恒锚 master。若被镜像路本身有偏移（用户设过 A/B 偏移），镜像须跟随**它**的期望位置。实现：镜像槽的 `Offset100ns` 恒等于被镜像槽的 `Offset100ns`，且二者在偏移变更/主从切换（`:250-267, :318-333`）时**成组更新** |
| 2 | **不参与** master 选举 | master 恒为 `_slots[0]`。若镜像排在 0 号位会改变基准语义 ⇒ 镜像不得成为 master；`RemoveSlotAt(0)` 的重基准逻辑（`:250-267`）须跳过镜像或先解除镜像 |
| 3 | 镜像的**生命周期** | 删除一路素材时其镜像须一并 Dispose（`:223` 的 `DisposeSlotSession` 明确警告"绝不静默吞异常"，镜像泄漏同属永久泄漏） |
| 4 | 解码开销 | 每镜像一份解码器 + 交换链。9 带全镜像最坏 = 9 份 4K 解码 + 9 条交换链 ⇒ 必须进像素预算闸门与 `docs` 记账，并按实测给出可用上限（参考 `CHANGELOG.md:26-27` 的 22.2 Mpx 读数） |
| 5 | **镜像同步判据**（决定性） | 同组两条带的呈现时刻必须一致，漂移超阈值判红。**这条判据若做不出鉴别力，M1 就不该上** —— 两带漂移一帧，"同一画面"就是假的，而这正是对比模式最不能出的错 |

### 建议

- **实现 M1**，并把上面第 5 条判据作为 M1 的准入门槛（判据先写、先能判红，再实现）
- **不建议 M2**：改内核会让本次从"UI 解锁既有能力"变成"内核 ABI 变更 + 重新出内核基线"，
  与"不动内核/保持 API 16"的既定前提冲突，需单独评估与排期
