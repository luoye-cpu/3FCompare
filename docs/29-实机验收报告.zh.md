## 一、环境准备

### 1.1 为什么必须先做这一步（本次实测复现了"静默降级"陷阱）

内核 `FFF.Native` 按 **exe 同目录** 加载 FFmpeg DLL；缺 DLL 时**不报错、不退出**，
而是静默切到"演示模式"，自测照样打印 `全部通过 ✓` 且 `exit=0`。

本次做了**受控实验**（可复现，脚本见 `.review_pr/verify29/`）：

```
① 把 bin/Debug/net11.0-windows/ 下 16 个 FFmpeg 文件全部移走
   → comparemodetest: 请求打开 2 路（演示），等待就绪...
   → comparemodetest: 全部通过 ✓        EXIT=0     ← 假绿！实际没有真实解码
② 运行 tools/deploy_ffmpeg_for_tests.sh
   → 复制 : 更新 16 个，已一致跳过 0 个
   → ✓ 关键文件到位：avcodec-63.dll avformat-63.dll avutil-61.dll swscale-10.dll swresample-7.dll ffmpeg.exe
③ 复跑同一命令
   → comparemodetest: 请求打开 2 路（真实），等待就绪...   ← 恢复真实解码
   → comparemodetest: 全部通过 ✓        EXIT=0
```

⇒ **判定"是否真实模式"的唯一可靠依据是日志里的 `（真实）` / `（演示）` 字样**，
而不是退出码，也不是"全部通过"。`bin/` 被 `.gitignore` 忽略，**每次干净重建后都要重新部署**。

## 四、已知问题

### P1 · 🔴 4 路真实播放间歇崩溃（既有，与本次功能正交）

| 观察 | 数据 |
|---|---|
| 现象 | `exit=139`（SIGSEGV ⇒ `0xC0000005`，`dxgi.dll`） |
| 本次复现率 | `--magnifybench 4 路`：**5/6 崩溃（83%）** |
| 崩溃时点 | 集中在**播放阶段开始前后**（部分运行连第一个 `#BENCHPHASE` 都没打出就崩） |
| 反证（不崩的场景） | `--comparemodetest 4 路` **3/3 通过**（不长时间播放）；`--magnifybench 2 路` **4/4 通过** |

**归因（沿用 docs/26 §十六，本次数据与之一致，未新增结论）**：
主因是**路数**而非负载或漂移校正 Seek（4 路 100% vs 2 路 17%，Fisher p=0.0008；
720p 与 4K 无差异 p=1.00；`_3FC_DRIFT=off` 后崩溃率反而略升）。
根因在 `native/` 内核的**跨渲染器并发 Present 撞上交换链改写**（转储中两线程同处
`PresentCurrentFrame +0x7E → dxgi.dll+0x19530`）。

**本次未修**（`native/` 不在本次范围；且属既有缺陷，会掩盖放大相关回归）。
**建议**：用户按 docs/26 §16.5 步骤复测——退出 RTSS / MSI Afterburner / NVIDIA ShadowPlay 后，
确认新进程模块表不含 `RTSSHooks64.dll` / `nvspcap64.dll`，再同批次交错跑 4 路 8 次。
崩溃率显著下降 ⇒ 钩子是必要因素；仍高 ⇒ 可排除钩子，确认是内核并发 Present。

### P4 · ℹ `--selftest` 媒体信息帧率显示 24fps（本次新观察，仅显示层面）

三次运行**稳定**打印：


调用链：`MainWindow.SelfTest.cs:635` → `SyncController.EstimateFps(ready)`（`SyncController.cs:530`），
当 `snap.FrameRate <= 0` 时**回退 24**（该回退是为修"4K H.264 显示 15360fps"的旧 bug 而设）。

⇒ 含义是**内核未上报 `nominalFrameRate`**（`Fff3FpEngine.cs:516` 读
`nominalFrameRateNumerator/Denominator`）。**不影响播放**（presented 实测 60fps）。
**需用户决策**：是否追查内核媒体信息字段（属显示层信息缺失，优先级低）。

### P5 · ℹ `--selftest` 帧步进后打印一条运行时错误（既有，不影响判定）
