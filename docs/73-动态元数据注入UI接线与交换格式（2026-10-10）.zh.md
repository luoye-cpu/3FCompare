## 一、为什么需要一个文件格式

内核注入通道要求主机一次性提交整张表（`kMaxInjectedEntries = 4096` 条上限，整批校验、
整批替换）。真实需求是「同一素材的两个编码版本里，有一路在重编码时丢了 HDR10+ 元数据」——
此时两路会走不同的色调映射曲线，亮度不可比，而这正是本软件的核心场景。
所以需要一个**可落盘、可人工编辑、可被工具生成**的元数据载体。

实测结论（决定了格式选型）：

- 仓库现有 HDR 样片（`3fp/build/vidtest/hdr10_1080p.mp4`）里 HDR10+ 只以
  `H.26[45] User Data Unregistered SEI message` 形式存在，`ffprobe -show_frames`
  **解析不出**结构化的 `HDR10+ Metadata` side data。
- 因此**没有**可本地校验的 ffprobe/HDR10+ 工具 JSON 样本；照抄它们的字段属于无验证猜测。
- 结论：定义**自己的**交换格式（本节），并把校验规则逐条对齐内核真源，而不是对接一个
  验证不了的上游格式。将来拿到真 HDR10+ 样本后再加一个导入器即可，解析器已按"可扩"设计。

## 二、交换格式 v1

```json
{
  "format": "3fc-dynamic-metadata",
  "version": 1,
  "kind": "Hdr10Plus",
  "entries": [
    {
      "frameIndex": 0,
      "targetedDisplayNits": 1000,
      "windows": [
        {
          "upperLeft": [0.0, 0.0],
          "lowerRight": [1.0, 1.0],
          "maxScl": [0.8, 0.75, 0.7],
          "averageMaxRgb": 0.5,
          "fractionBrightPixels": 0.0,
          "toneMappingFlag": 1,
          "kneePoint": [0.65, 0.65],
          "curveAnchors": [0.65, 0.75, 0.85, 0.95, 1.0]
        }
      ]
    }
  ]
}
```

HDR Vivid 形态（窗口不带几何、不带曲线——内核 Vivid 走全幅峰值语义）：

```json
{ "format": "3fc-dynamic-metadata", "version": 1, "kind": "HdrVivid",
  "entries": [ { "frameIndex": 0, "targetedDisplayNits": 1000,
    "windows": [ { "maxRgb": [0.8, 0.75, 0.7], "averageMaxRgb": 0.5 } ] } ] }
```

约定：

- 字段名不区分大小写；`kind` 取值 `Hdr10Plus` / `HdrVivid` 不区分大小写。
- 可省略：`targetedDisplayNits`（=0）、`fractionBrightPixels`（=0）、`kneePoint`、`curveAnchors`、
  `toneMappingFlag`（省略按 0 = 无曲线块处理）。
- **不支持注释与尾逗号**（`System.Text.Json` 严格解析），手写文件请注意。
- 条目顺序**无需排序**：内核 `InstallInjectedTable`（`HdrProcessor.cpp:717`）自己按
  `frameIndex` 升序 `std::sort`，匹配规则是"取最后一条 ≤ 当前帧，低于首条则落首条"。
  解析器刻意不去重、不排序。
- ⚠ 不要写**重复 frameIndex** 的条目：内核用非稳定 `std::sort`，同帧号多条时谁生效未定义。

## 三、校验规则真源（改格式前必读）

解析器 `src/3FCompare.Core/Backend/DynamicMetadataFile.cs` 逐条镜像内核，这样"会被内核
整批拒绝的表"在**载入时**就带着带字段路径的中文错误失败，而不是静默地注入失败。

内核真源：`3fp/.../Hdr/HdrProcessor.cpp` — `BuildInjectedState`(:620)、
`BuildInjectedWindow`(:496)、`BuildInjectedStateVivid`(:572)、`SetInjectedMetadataPackets`(:671)。

| 对象 | 规则 |
|---|---|
| 文件 | `format == "3fc-dynamic-metadata"`、`version == 1`、`kind` ∈ {Hdr10Plus,HdrVivid}、`entries` 非空且 ≤ 4096 |
| 条目 | `frameIndex` 整数 ≥ 0；`targetedDisplayNits` 有限且 ≥ 0 |
| 窗口数 | `windows` 长度 ∈ [1,3]（`kHdrMaxProcessingWindows`） |
| 几何 | `upperLeft ≥ 0`、`lowerRight ≤ 1`、且 `lowerRightX > upperLeftX`、`lowerRightY > upperLeftY`（退化/倒置矩形内核直接拒） |
| 峰值 | `maxScl[3]`、`averageMaxRgb` 均有限且 ∈ [0,1] |
| 曲线开关 | `toneMappingFlag` ∈ {0,1}；为 0 时 `kneePoint`/`curveAnchors` 被忽略 |
| 拐点 | `0 ≤ kneePointX < 1`、`0 ≤ kneePointY ≤ 1`、且 `kneePointY ≤ kneePointX + 1e-4` |
| 锚点 | 长度 ≤ 15（`kHdrMaxBezierAnchors`）；每个 ∈ [0,1] 且**单调不减**；且**首锚点 ≥ kneePointY** |

最后一条极易漏：内核 `HdrProcessor.cpp:552` 的单调比较是
`float previous = source.kneePointY;` 起步的，只查"锚点之间单调"会放过
"首锚点低于拐点"的表。已由 `DynamicMetadataFileTests` 钉住。

两处**故意不拒绝**（内核也不拒，别当 bug 改）：
`fractionBrightPixels` 越界时内核只在范围内才采用（:527-529）；
`targetedDisplayNits > 10000` 内核 clamp 而不拒（:611/:638）。

| 落点 | 改动 |

| `src/3FCompare/Panels/MediaInfoPanel.cs` | 新增「动态元数据来源」行（仅 HDR 素材显示）+ `FormatDynamicMetadataSource` |
| `src/3FCompare/Localization/LanguageManager.cs` | 新增 15 个键 × 中英两表（缺键自检用例会自动判红） |

两条设计判词：

1. **扇出到所有路，而不是只作用于选中路。** 动态元数据决定色调映射曲线，只注入一路会让两路
   跑不同曲线——与 `OnColorModeChanged` 的"取并集统一色调映射"（P1-8）同理。
   逐路 `try/catch`：演示模式与旧内核都可能让某一路失败，一路失败不拖垮其余路。

2. **来源读数直接问内核，UI 不另记影子状态。** 内核
   `PlayerVideoRenderer::HdrMetadataSource()`（VideoRenderer.cpp:4741）只看
   `InjectedMetadataActive()`，是 **kind 无关**的——HDR10+ 与 Vivid 注入都会如实回 `Injected`，
   清除后自动回 `Bitstream`。所以"注入成功后默认切换过来"由内核保证；UI 侧保留的
   `_dynamicMetadataPath/_dynamicMetadataCount` 只服务于提示文案。
