#### A5 专项：文档原假设不成立

`FFF3FP_GetSnapshot` 是**状态快照**，不是画面截图 —— 它返回 `Fff3FpSnapshot`
（`State` / `Decoder` / `Position100ns` / `FrameIndex` / `VideoWidth` / `ActualColorMode` …），
**画面导出实际走的是 `FFF3FP_ReadVideoPixelRegion`**，回读的是「颜色管理前」的**已呈现帧**
（故分辨率 = 呈现分辨率，随窗口/显示器变化，不等于源分辨率，这点已在 `MainWindow.Capture.cs`
注释与 UI 文案中明确标注）。

⇒ 答案：**导出的画面不含 UI / OSD / 显卡合成内容**，因为它根本不经过合成器。
"需要处理 OSD 覆盖与否"这个问题本身不成立。

##### 缺陷分析（修复前）

链路的前半段全部就绪，但**最后一步没接到内核**，导致用户的选择**静默无效**：

| 环节 | 状态 |
| --- | --- |
| 设置窗口 GPU 下拉框 | ✅ `SettingsWindow`，选项来自 `GpuEnumeration`（Win32 `EnumDisplayDevices`） |
| `AppSettings.PreferredAdapterIndex` 持久化 | ✅ 有（−1 = 系统默认，`Normalize` 钳到 [−1,15]） |
| 会话存档 `SessionItem.AdapterIndex` | ✅ 有 |
| `EngineSessionOptions.PreferredAdapterIndex` | ✅ 有 |
| `PlaybackCoordinator` 传给 `CreateSession` | ✅ 有 |
| **`Fff3FpEngine.CreateSession` 使用它** | ❌ **完全没有** —— 构造 `Fff3FpConfiguration` 时不引用该字段 |
| **内核侧支持** | ❌ `Fff3FpConfiguration`（对照 `FFF.Player.Api.h` v14）**无任何 adapter 字段**；也不存在 `FFF3FP_SetAdapter` / `FFF3FP_EnumerateAdapters` |

⇒ **用户在设置里选第 2 张 GPU 解码，实际仍使用系统默认 GPU，且界面没有任何提示。**

另注：`IPlayerEngine.EnumerateAdapters()` 返回硬编码的 `"System Default (D3D11)"`，
**生产路径并未使用它**（只有 `SmokeTests` 打印）；真实下拉框走的是 `GpuEnumeration`。
故该方法名与实际能力不符，容易误导后来者以为"内核已提供枚举"。

##### 实现（2026-09-16）

**内核侧**（归档为 `3fcompare-kernel-2026.9.14.2` / `68e1965`）：

| 文件 | 改动 |
|---|---|
| `FFF.Player.Api.h` | `FFF3FPConfiguration` **末尾**追加 `std::int32_t preferredAdapterIndex` |
| `PlayerApi.cpp` | `PlayerApiVersion` 14→**15**；`FFF3FP_Create` 增加 `[-1,15]` 范围校验 |
| `FFF.Native.rc` | `VER_API` 与三处版本字符串同步 14→15 |
| `VideoRenderer.h/.cpp` | 成员 `preferredAdapterIndex_ = -1`；`SetPreferredAdapterIndex()`；`EnsureDevice()` 中「指定索引优先，失败回落到 monitor 匹配」 |
| `PlayerSession.cpp` | 构造期接线（设备是懒创建的，必须在首次 `EnsureDevice()` 前设置） |

**托管侧**：

| 文件 | 改动 |
|---|---|
| `Fff3FpNative.cs` | `Fff3FpConfiguration` 同步追加字段 |
| `Fff3FpEngine.cs` | `ConfigVersion` 14→**15**；`CreateSession` 传入 `options.PreferredAdapterIndex` |
| `GpuEnumeration.cs` | **数据源改为 DXGI `EnumAdapters1`**（经 `DxgiOutputInfo` 裸 vtable 调用） |
| `DxgiOutputInfo.cs` | 新增 `EnumerateAdapters()`（含 `IDXGIAdapter::GetDesc` → 描述/厂商/显存） |

**为什么必须同时改枚举源**：内核用的是 DXGI `EnumAdapters1`，而旧托管枚举用 Win32
`EnumDisplayDevices`（DISPLAY 设备）。两者**索引空间不同** —— 只接线不改枚举，
传下去的索引会指向错误甚至不存在的卡。这是 A11 的**第二层缺陷**。
实测本机 DXGI 有 5 个适配器（含 3 张 NVIDIA + Intel 集显 + Microsoft Basic Render Driver），
而 DISPLAY 枚举根本列不全。

##### 多 GPU 逐一验证（本机 5 个 DXGI 适配器，全部命中）

托管侧枚举（`GpuEnumeration` → DXGI）与内核实际建设备的适配器**逐项比对**：

| 托管 Index | 描述 | 托管枚举 LUID | 指定后内核 vendor/device | 内核 LUID | 一致 |
|---|---|---|---|---|---|
| 0 | NVIDIA GeForce RTX 5080（15 GB） | `0x148C9` | `4318` / `11266` | `0x148C9` | ✅ |
| 1 | Intel(R) UHD Graphics（128 MB） | `0x15D02` | `32902` / `42891` | `0x15D02` | ✅ |
| 2 | RTX 4060 Laptop（7 GB）**#2** | `0x133BE` | `4318` / `10464` | `0x133BE` | ✅ |
| 3 | RTX 4060 Laptop（7 GB）**#3** | `0x24174` | `4318` / `10464` | `0x24174` | ✅ |
| 4 | Microsoft Basic Render Driver（软渲染） | `0x1486C` | `5140` / `140` | `0x1486C` | ✅ |

⇒ **5 个适配器全部正确识别，索引一一对应，LUID 完全吻合。**

**同型号双卡（最难的一关）**：Index 2 与 3 的 `Description` **完全相同**
（都是 "NVIDIA GeForce RTX 4060 Laptop GPU"）、vendor/device 也相同，
只有 **LUID 不同** ⇒ 确认是两张物理卡。二者都能被独立、正确地选中，
证明"按索引指定"在同型号多卡场景下依然可靠。

> 附带修正两处显示问题：① 显存 <1GB 时旧逻辑按 GB 取整会显示成"0 GB"
> （Intel 集显实际 128 MB），现按量级自动切换 MB/GB；② 同型号重名条目
> 追加 `#<索引>` 后缀，否则用户在下拉框里看到两个一模一样的选项无从选择。

⚠ **已知副作用**：指定 Intel 集显时 selftest 以 EXIT=1 结束，失败点是
「滚轮缩放-节流补发」报 `节流用例空转：没有更新被丢弃`。根因是集显渲染变慢后，
同步连发 4 次 `OnSurfaceWheel` 的间隔超过了 16ms 节流窗口 ⇒ 没有一次被丢弃 ⇒
用例的"前置条件坐实"分支判定空转。**这是既有的测试脆弱性**（依赖真实时间），
不是 A11 引入的功能缺陷；默认 GPU 下不受影响。是否放宽该断言待定。

##### 维护要点

- ⚠ **ABI 破坏性**：`FFF3FP_Create` 校验 `version` 严格相等且 `size >= sizeof(config)`，
  内核与托管**必须同批次发布**，错开一个版本会让全部会话创建返回 `InvalidArgument`。
- 已登记为 `PATCHES.md` 类别一第 5 项，每次上游升级需重移植；
  字段**只能追加在结构体末尾**，不得移动既有字段。

## 4. 质量策略

- **自动化**：`Core.Tests`（同步换算、偏移、clamp、帧表、设置序列化）；E3 冒烟作为 CI 前置；
  可选针对 D3D/UI 的冒烟以 3FP 上游测试方式手测。
- **性能门禁**：M5 前建立基准（2/4 路 1080p 打开耗时、步进 P95、内存峰值、显存占用）。
