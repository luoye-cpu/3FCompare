| 维度 | 评级 | 一句话判断 |
|---|:--:|---|

## 1. P0 — 必现缺陷，发布前必须修

### P0-1 · 加载会话（`.3fcs`）必然失败

**位置**：`src/3FCompare/MainWindow.axaml.cs:983`

```csharp
Grid.SetCount(0, _realMode);          // ← 把所有 PlayerSurface 清空
_coordinator.OpenFiles(snapshot.Items.Select(i => i.Path!).ToList(), autoPlay: true, ...);
```

**机制**：`OpenFilesCore` 用 `_surfaceAt(_sync.Count)` 取 surface（`PlaybackCoordinator.cs:96`），
`SetCount(0)` 之后 `Grid.GetSurface(0)` 必为 null → 直接命中 100 行的
`"第 1 路没有可用的播放面板（surface 为空），已取消本次打开"` 分支并 return。
结果：`onAllOpened` 回调不执行 → **不会 Seek 到保存位置、不恢复循环区间、不自动播放**，
界面表现为"加载会话后一片空白"。

**对比**：`OpenPaths:236-241` 有显式扩容 `Grid.SetCount(needed, _realMode)`、
`AutoOpenFiles:203`、`RunSelftestAsync:187` 也有。唯独会话恢复这条路径漏了。

**修复**：在 `OpenFiles` 前补一行
`Grid.SetCount(Math.Min(9, snapshot.Items.Count), _realMode);`

**验证**：保存一个 3 路会话 → 重启 → 加载。当前必现空白，修复后应恢复到保存位置。

### P0-2 · "导出当前帧 PNG"产出的是**抓屏缩略图**，不是原生帧

**位置**：`src/3FCompare/MainWindow.axaml.cs:1021-1046`（`OnExportFrame`）+ `1056-1075`（`CapturePixelSampled`）

这是本次审查**最严重的一条**，因为它直接违背 README 的核心承诺，且对外是"功能可用"的假象。

README 第 38 行明确写：
> 探针/截屏始终读取「颜色管理前」的原生缓冲，保证跨路对比一致。

**实际行为**：

| 路径 | 真实行为 | 问题 |
|---|---|---|
| 首选 `ScreenFrameCapture.CaptureWindowFrame(surface.Hwnd)` | GDI **BitBlt 抓屏幕** | 抓的是 **DWM 合成后、已被色彩管理/色调映射处理过**的画面；窗口被别的窗口遮挡时**抓到遮挡物**；跨不同 DPI 显示器时尺寸错 |
| 退路 `CapturePixelSampled` | `targetW = Math.Min(320, srcW)` | **4K 视频导出 320px 宽**的图，作为画质对比素材毫无意义 |
| PNG 写出 | `bmp.Save(path, ImageFormat.Png)` | **无 sRGB / gAMA / cHRM / ICC 任何色彩标记**，HDR 内容导出后在其它看图软件里必然偏色 |

**讽刺的是：正确的能力已经在手，只是没接上线。**
`Fff3FpNative.cs:260` 存在 `FFF3FP_ReadVideoPixelRegion`（内核全帧/区域回读），
探针（`MainWindow.axaml.cs:1082/1102`）已经在用它，
且 `CapturePixelSampled` 的注释（1051-1053）清楚写明"内核像素读回的坐标域是后台缓冲，
可一次批量读回"——作者完全知道这条路。但导出功能把它**只用在 320px 缩略图上**，
主路径却去抓屏。

**修复建议**（按优先级）：
1. **新增全分辨率原生回读导出**：用 `FFF3FP_ReadVideoPixelRegion` 按后台缓冲尺寸整帧读回 →
   按 `RenderTargetInfo.DestX/Y/Width/Height` 裁掉 letterbox → 组装 `WriteableBitmap` → 编码 PNG。
   这条路才是"颜色管理前的原生缓冲"，且天然规避遮挡/多屏问题。
2. 若短期不做 1，至少：BitBlt 失败要检测（`ScreenFrameCapture.cs:135` 当前**忽略 BitBlt 返回值**，
   失败时返回全黑图并静默成功）、导出前检测窗口是否被遮挡并提示用户。
3. PNG 写入色彩标记（`gAMA`+`cHRM`，或嵌入 sRGB chunk），保证跨软件色准。

**验证**：导出 4K HDR 视频当前帧，检查 PNG 实际分辨率（当前 320px 宽）→ 修复后应为原生分辨率；
用两个看图软件打开导出的 PNG 比对颜色。

### P0-3 · 自动播放/会话恢复配额在异常路径泄漏（静默不播放）

**位置**：`src/3FCompare/Services/PlaybackCoordinator.cs:89` 记账 vs `143-147` catch 分支

```csharp
if (autoPlay) _pendingAutoPlay += count;        // 89：循环前一次性记账
...
catch (Exception ex)                            // 143：CreateSession 抛异常
{
    surface.IsFailed = true;
    surface.ErrorText = ex.Message;             // ← 没有 _pendingAutoPlay -= 1
}
```

**机制**：只有 `OpenSlotAsync` 的完成/失败分支会调 `TryAutoPlayAfterOpen()` 减账。
若 `_engine.CreateSession` 或 `EnsureHwndAsync` 抛异常，该路**不入 `_sync`、不减账**，
配额永远回不到 0 → `_sync.Play()` 永不触发、`_onAllOpenedCallbacks` 永不执行。

**影响**：P0-1 的调用点正是 `autoPlay: true`，两个 bug 叠加。即使先修 P0-1，
只要有一路创建失败（如某个文件路径损坏、GPU 索引无效），整个会话恢复就静默停在"已打开但不播放、不定位"。

**修复**：catch 分支内补 `_pendingAutoPlay--`（建议改为"已成功入队数"记账，在 `AddSlot` 后记）。
更彻底的做法见 P1-9（按批次记账）。

### P0-4 · 完整版可能打出"没有 FFmpeg"的坏包，且脚本报成功

**位置**：`pack.ps1:79-88`

```powershell
if (Test-Path $FfmpegSrc) {
    if ($ffDlls.Count -gt 0) { ...Copy-Item... }
} else {
    Write-Host "   ⚠️ FFmpeg 源目录不存在..."     # ← 只 warning，不 throw
}
```

**机制**：源目录缺失、或目录存在但 0 个 DLL、或 `Copy-Item` 静默失败——三种情况都**继续往下走**，
照常生成 `使用说明.txt`、照常打 7z、照常在末尾打印 `✅ 全部打包完成`。
产出的"完整版"解压后和精简版一样跑不起来（回退演示模式），而打包者毫不知情。

**修复**：
- `Test-Path` 失败或 `$ffDlls.Count -eq 0` → 直接 `throw`；
- 复制后断言 `(Get-ChildItem "$FfmpegDest\*.dll").Count -eq $ffDlls.Count`；
- 末尾加一次"产物自检"：解压 7z 到临时目录，检查 `3FCompare.exe` 存在 +（full 版）`ffmpeg-full/avcodec-*.dll` 存在 + exe 的 `ProductVersion` 等于传入版本。

同类问题：`pack.ps1:182-185` 找不到 `7z.exe` 也只 warning、退出码仍为 0 → CI 会误判成功。改为 `throw`。

### P0-5 · 缩略图预览：子窗口从不关闭 + GDI 位图持续泄漏

**位置**：`src/3FCompare/MainWindow.axaml.cs:389/427-428/443`、`Controls/ThumbnailPopup.cs`

- `_thumbnail ??= new ThumbnailPopup()` 是 **Window**，`Show()` 后**从不 `Close()`**；
  `EndScrubPreview:443` 只 `Hide()`，`OnClosed:1815-1820` 也没关它 → 关窗后残留顶层窗口，
  且 Avalonia 因仍有存活 Window 可能不退出消息循环。
- `427` 行：`if (!_scrubbing || _thumbnail is null) { preview.Dispose(); return; }`
  → **scrubbing 期间 `preview` 被传给 `ShowAt` 后从不 Dispose**。
  而 `_scrubTimer` 是 150ms/tick，拖动 5 秒 ≈ 33 个 GDI Bitmap 泄漏。GDI 句柄上限约 10K，
  长时间拖动会耗尽 → 整个进程界面绘制失败。

**修复**：`ShowAt` 内部持有 Bitmap 副本并在下次 `ShowAt` 前 Dispose 旧的；
`OnClosed` 补 `_thumbnail?.Close()`。

## 3. P2 — 清理与加固

**代码卫生**
- `src/3FCompare/Platform/HostSurface.cs` **全仓库无引用**（PoC 遗留死代码），且用 `"STATIC"` 窗口类（注释已说明会透传鼠标命中）；`DetachedFromVisualTree` 在从未 Attach 时会用 `_hwnd=0` 调 `DestroyWindow`。建议删除。
- `NativeRuntime.cs:231-258` `CopyDlls` 是 private 且**无调用者**（实际走 `SetDllDirectory`）。死代码。
- `MainWindow.axaml.cs:242-253`：`try { _coordinator.OpenFiles(...) } catch {}` 包的是 `async void`（`PlaybackCoordinator.cs:61`），**异常不会传播到这里**，catch 永不触发，误导后来者。删掉或改为状态回调。
- `ScreenFrameCapture.cs:135`：`BitBlt` 返回值被忽略 → 失败时静默返回全黑图，Path B（PrintWindow）几乎不可达。
- `MainWindow.axaml.cs:1074/1101`：`new Bitmap(...)` 之后 `TryReadPixelRegion` 返回 false 直接 `return null`，**bmp 未 Dispose**（两条路径都是）。
- `PlayerSurface.cs:348-351/410-425`：GDI 缓存 `Clear()` 前未逐个 `Dispose()` `Font`/`LinearGradientBrush`。
- `MainWindow.axaml.cs:1745-1754`：`OnClosing` 未停 `_scrubTimer`（只在 `OnClosed` 停），中间若有 tick 会对已 Dispose 的 HWND 做 BitBlt。
- `PlayerSurface.cs:326`：`Dispatcher.UIThread.Post(() => _session.Redraw())` 闭包延迟读字段，会话释放后可能 NRE —— Avalonia Dispatcher 作业里的未处理异常会**击穿进程**。改为捕获 session 引用 + null 校验 + `catch (ObjectDisposedException)`。

### 7.3 已知限制（未修，需内核侧扩展）

**帧导出分辨率 = 呈现分辨率，不是源分辨率。**
内核 `FFF3FP_ReadVideoPixelRegion` 的语义是"回读已呈现帧"（`FFF.Player.Api.h` 注释：
"samples a rectangular region of the presented frame"），因此 4K 素材在 1995×1122 的窗口里
导出就是 1995×1122（实测值），而不是 3840×2160。相对修复前（固定 320px）已是量级改善，
且颜色正确（不经过 DWM 合成）；要做到"原生分辨率导出"必须由内核新增"读取解码帧"的 API。
