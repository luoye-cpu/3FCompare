# 44 · 崩溃自愈：设计与验证

> 面向 docs/43（RTSS 钩子竞态根因定案）的**后果处理**。
> 根因在外部钩子、无法在进程内规避；本文记录"崩溃后自动重启并恢复会话"的设计与实测。

---

## 一、结论

**崩溃自愈已落地**：裸 GUI 启动时，3FCompare 会先起一个守护父进程，由它拉起真正的
UI 子进程；子进程一旦以原生崩溃码退出，守护就把它拉起来并恢复上次会话。

它**不减少崩溃**，只把"丢工作"降级为"闪一下自动恢复"。崩溃率本身仍取决于
交换链数量 N（docs/43 §四），本机制不触碰多显卡架构。

---

## 二、为什么必须是进程外方案

要自愈的崩溃是 `0xC0000005`（访问违规）与 `0xC000001D`（非法指令）。二者都是
**即时终止**：

| 处理器 | 崩溃时是否执行 |
|---|---|
| `try/finally` | ❌ |
| `AppDomain.CurrentDomain.ProcessExit` | ❌ |
| `AppDomain.UnhandledException` | ❌（只接托管异常） |
| `Window.OnClosed` | ❌ |

进程内没有任何一个时刻可以"自救"，所以只能由**另一个进程**发现它死了再拉起来。
这也决定了状态保存必须发生在崩溃**之前**——任何"退出时保存"的钩子在崩溃面前
等于不存在。

## 三、设计

### 3.1 触发条件：只在"裸 GUI 启动"时生效

```
守护 ⇔ 命令行里没有任何 "--" 前缀的参数
```

| 启动方式 | 命令行 | 守护 |
|---|---|---|
| 用户双击 | （空） | ✅ |
| 拖文件到 exe | `a.mp4` | ✅ |
| 文件关联双击 | `a.mp4` | ✅ |
| **无人值守演示/巡检** | `--autodemo <files…>` | ✅ **（唯一例外，见下）** |
| 所有门禁脚本 | `--selftest` / `--multitest` / … | ❌ |
| 守护拉起的子进程 | `--child <pid>` | ❌（天然不递归） |

**为什么用这条极简规则**：全仓 40+ 个自动化脚本**全部**带模式位，它们依赖退出码
与 stdout 文本判定成败。多一层父进程会让这些判定失真（退出码传播、输出前缀、
进程数翻倍、只杀单 PID 留下孤儿）。用"没有任何 `--`"一刀切，门禁零影响，
而真实用户路径全部受保护。

**`--autodemo` 为什么是唯一的例外**：它是无人值守的演示/巡检模式，**现场没人在**，
崩了没人重新打开 9 路 4K —— 恰恰是最需要自愈的场景。放行它的依据是 2026-09-21
全仓核查：`tools/`、`pack.ps1`、`发布门禁.ps1` 中**没有任何一处**使用 `--autodemo`，
因此不存在"判定被父进程改变"的风险。常量 `CrashGuard.AutodemoArg` 由 `Program.cs`
与守护共用，避免两处各写一份字面量。

逃生口：环境变量 `FC_NO_GUARD=1`。

### 3.2 重启与防循环

```
子进程崩溃 → 记日志 → 连续计数 +1
            → 计数 > 3 ⇒ 停止重启 + 隔离快照
            → 否则等 1.2s 重新拉起（第 2 次起带 --crash-restore）
```

- **连续计数在"存活 ≥ 60s 才崩"时归零**：否则一次偶发崩溃会被永久记账，
  用久了必然撞上上限。
- **1.2s 延迟**：给 WER 写完整转储（本机每个 55~64MB）留出时间，也让"闪一下"
  不至于快到用户察觉不到。
- **超限后隔离而非删除快照**：反复崩溃多半是"打开这组文件就必崩"，留着快照会
  自激循环（重启 → 恢复 → 再崩）。改名成 `.bad` 后下次启动是干净的，
  用户仍能手动改回来取回内容。

### 3.3 退出码判定（单独一处，避免口径打架）

`CrashExitCode.IsCrash` 的判据是位模式 `0xC0000000 ≤ code < 0xD0000000`，
而不是数值大小。三种宿主口径必须判出同一结论：

| 宿主 | `0xC0000005` 的表现 |
|---|---|
| .NET `Process.ExitCode` | `-1073741819`（有符号） |
| Python `subprocess.returncode` | `3221225477`（无符号） |
| bash `$?` | `1`（**已被压扁，不可用**） |

两个刻意排除的码：

- `0x8000FFFF`（E_UNEXPECTED）：落在 Severity=1 段，正常程序完全可能主动返回它。
  若按 `≥ 0x80000000` 判崩溃，"用户点了关闭、窗口又弹回来"会变成常态。
- `0xE0434352`（CLR 托管异常）：是**必现**的确定性错误，重启只会让用户反复看到
  同一个弹窗；本机制要防的是外部钩子导致的**偶发**竞态。

### 3.4 子进程看门狗

守护被强杀时子进程会变孤儿（窗口残留、GPU 不释放）。子进程每 2s 轮询父 PID，
父不在了就自行退出。用轮询而非 Job Object：纯托管、无 P/Invoke，代价可忽略。

## 四、状态恢复

| 环节 | 做法 |
|---|---|
| 存什么 | 复用 `SessionSnapshot`（与手动"保存会话"同一结构 ⇒ 同一条重建路径） |
| 存在哪 | 配置目录 `last-session.3fcs`（与 `settings.json` 同级，便携部署跟着 exe 走） |
| 何时写 | ① 每 5 秒定时；② 一批文件**全部打开完成**的瞬间 |
| 怎么恢复 | 仅当子进程带 `--crash-restore`（即崩溃后被拉起）时才恢复，且**暂停态** |
| 何时清 | 子进程正常退出时由守护删除；超过 24 小时的快照视为陈旧，不恢复 |

**为什么两个写入点缺一不可**：只留定时轮询的话，打开 8 路 4K 的十几秒里若崩溃，
快照还是上一批甚至不存在——而那恰恰是最贵的一次丢失。

**为什么恢复后是暂停态**：崩溃成因是偶发竞态，恢复后立刻播放可能立刻再撞上；
停在原位让用户看清"已恢复"再自行继续，比多闪一次要好。

## 五、顺带修掉的一个真实缺陷

接入时发现：`PlaybackCoordinator.OpenFilesCore` 的批次配额只在 `autoPlay` 为真时
发放，而 `onAllOpened` 回调挂在"配额归零"这个唯一触发点上：

```csharp
if (autoPlay) Volatile.Write(ref batch.Remaining, count);   // ← 修前
batch.OnAllOpened = onAllOpened;
```

⇒ **`autoPlay:false` 的批次回调永不执行**。表现是"文件都打开了但就是不动"。
崩溃恢复正是走 `autoPlay:false`（恢复后停在原地），所以必须修。

修法是把"发配额"与"要不要播"解耦：

```csharp
if (autoPlay || onAllOpened is not null) Volatile.Write(ref batch.Remaining, count);
batch.AutoPlay = autoPlay;
...
Interlocked.Exchange(ref batch.OnAllOpened, null)?.Invoke();
if (batch.AutoPlay) _sync.Play();          // ← Play 不再无条件
```

实测（2 路 4K，快照位置 30s）：修复前 `pos=0ms`，修复后 `pos=29950ms`。

### 11 · 真实崩溃的完整证据链（轮 3）

前 10 项都是**模拟**崩溃（`Environment.Exit` 带崩溃码）。第 11 项是真正的原生异常终止：

```
13:39:33.553 守护启动（--autodemo，9 路 4K）
13:39:33.557 第 1 代子进程 pid=81792
13:39:35.359 SessionReady routes=9 failed=0        ← 9 路打开成功
13:39:42.641 子进程崩溃 第 1 次 存活 9.1s  0xC000001D 非法指令
13:39:43.852 第 2 代子进程 pid=89676               ← 1.2s 后自动重启
13:39:45.013 CrashRecover routes=9 pos=56445134    ← 读回快照（9 路 / 5.64s）
13:39:45.668 SessionReady routes=9 failed=0        ← 恢复完成，9 路全部就绪
13:39:52.607 子进程崩溃 第 2 次 存活 8.8s  0xC000001D
13:39:53.822 第 3 代子进程 pid=62220
13:39:54.938 CrashRecover routes=9 pos=56445134
13:39:55.562 SessionReady routes=9 failed=0        ← 第 3 代稳定跑完全程
```

崩溃与恢复**一一对应**，且恢复的路数与快照一致。崩溃率 1/5 轮与 docs/43 的
"9 路 ~25~30%" 吻合，可作为自愈触发条件的旁证。

### ⚠ 一个验证方法上的坑（值得记）

首轮统计用"按行数切片"（`Select-Object -Skip <启动前行数>`）来隔离每轮日志，
结果**六轮显示同一批内容**——因为心跳日志每秒 1 行，启动前的那 1000+ 行里混着
更早轮次的记录。改为**按时间戳过滤**（`HH:mm:ss` 字典序比较）才正确。
教训：日志隔离要用时间锚点，不要用行号锚点。

验证脚本：`tools/verify_guard_selftest.py`（须用 Python 驱动——bash 的 `$?`
会把异常码压成 1，无法与断言失败区分）。

## 七、已知限制

1. **不降低崩溃率**。真正降崩溃的是 N→1（共用单交换链），但它与"每路独占窗口 /
   跨显示器 / 可指定不同显卡"冲突，属产品取舍，本次未动。
2. **重启后素材要重新打开**，8 路 4K 需要十几秒，不是瞬时。
3. **位置精度约 5 秒**（自动保存周期）。保住的是"不用重新打开素材"，不是逐帧位置。
4. **双击启动会多一个进程**（守护无窗口）。若第三方工具按进程数统计会看到 2 个。
5. 崩溃仍会触发 WER 写转储（每个 55~64MB），与自愈无关但会占磁盘。
