# 25 · 多路无缝放大与比例式差异对比：可行性分析（2026-09-18）

> 需求来源：外部建议。目标 = 像素级/比例式差异对比 + 无缝放大 + ABC/ABCD 多模式布局。
> 本文基于代码事实评估可行性，区分【事实】（附 `文件:行号` 证据）与【推断】。
> 基线：`main` = `76b52c8`，内核基线 `3ac124a`（上游 `ea3ce05` + 我方扩展）。

## 零、总体结论

**可以做，但不能按字面直接做。**

- ✅ **布局与交互（ABC / ABCD / 拖动交叉点 / 按路数限模式 / 交换位置）**：纯应用层新增，**中等工作量、无内核阻塞**。
- ⚠️ **"统一分辨率 → 同步放大 → 裁剪 → 分割"**：同步放大**已有现成能力**；统一分辨率可间接实现；**"任意区域裁剪"是硬阻塞**。
- 🔴 **"像素级比对"与"无缝放大"在物理上不可兼得**（放大必然引入插值），且现有差异链路**缺色彩空间归一化**、**缺帧对齐保证**。这是需求的内在矛盾，必须先与需求方对齐。

| # | 需求项 | 判定 | 阻塞级别 |
|---|---|---|---|
| ① | 统一各路分辨率 | ⚠ 有条件可行 | 中 |
| ② | 各路同步等比放大 | ✅ **已有现成能力** | 无 |
| ③ | 放大后裁剪 + 再分割 | 🔴 内核不支持任意裁剪 | **高** |
| ④ | ABC / ABCD 布局 | ⚠ 需重构布局模型 | 中 |
| ⑤ | 拖动交叉点调占比 | ⚠ 需新建覆盖层 | 中 |
| ⑥ | 按路数动态限模式 | ✅ 纯新增 | 无 |
| ⑦ | 文件自动交换位置 | ✅ 纯新增 | 无 |
| ⑧ | 像素级/比例式差异对比 | 🔴 三条前置缺失 | **高** |

## 一、内核侧能力边界

### 1.1 `SetViewTransform` —— 能放大，但**不能任意平移**

【事实】`FFF.Player.Api.h:490-494`：
> zoom scales the fitted video box (1.0 = fit, >1 = magnify), panX/panY are
> normalized offsets in [-1,1] relative to the unzoomed box.

【事实】`VideoRenderer.cpp:1876-1885`：clamp `zoom ∈ [0.05, 64]`、`pan ∈ [-1,1]`。
【事实】`VideoRenderer.cpp:4502`：**仅 `zoom > 1.0001f` 才应用** ⇒ **不能缩小**。
【事实】`VideoRenderer.cpp:4499-4517`：`zoomedWidth = destination.width * zoom`，
`maxPanX = (zoomedWidth - destination.width) / (2 * destination.width)`。

🔴 **硬阻塞**：`VideoRenderer.cpp:4509-4514` 存在 `std::max(0.0f, ...)` 下限钳制。
当视频铺满宽度时 `destination.x == 0`，该钳制使 **panX 不产生位移**，
只能看到放大画面的**左上区域**，无法平移到右下等其他子区域。
【推断】因此"放大后裁剪出画面**任意**区域"在现有内核 API 下**做不到**。

### 1.2 输出分辨率 —— 不可由 API 指定

【事实】`VideoRenderer.cpp:2161-2170` `EnsureSwapChain` 中 `GetClientRect` 后
`width = clientWidth; height = clientHeight;` —— 传入尺寸被客户区覆盖。
交换链按客户区创建（`Scaling = DXGI_SCALING_NONE`）并按客户区 `ResizeBuffers`。
【事实】`PlayerApi.cpp:104` `FFF3FP_SetOutputWindow` 仅更换 HWND。

⇒ **没有"指定呈现分辨率"的 API**。统一分辨率只能靠【推断】**给各会话相同尺寸与宽高比的窗口**，
再由内核各自 fit 出相同的 `dest`。⚠ 若各路**源宽高比不同**，letterbox 后 `dest` 仍会不同。

### 1.3 回读语义 —— 呈现帧、呈现分辨率

【事实】`FFF.Player.Api.h:511-515`：回读的是 *presented frame*。
【事实】`VideoRenderer.cpp:4632-4641` 校验用 `swapWidth_`，`:4653-4654` 按 swap 尺寸裁边。
⇒ 回读分辨率 = **呈现分辨率（= 客户区）**，**不等于源分辨率**。
【事实】`GetRenderTargetInfo`（`VideoRenderer.cpp:4422-4440`）返回
`swap`（交换链）/ `client`（客户区）/ `dest`（视频绘制矩形，含 zoom 后的值），
可用于 `u = (sx - destX) / destWidth` 的屏幕→视频映射。

### 1.4 多会话完全独立

【事实】`PlayerSession.h:221` 每会话持有独立 `PlayerVideoRenderer`；
`VideoRenderer.cpp:1987` `D3D11CreateDevice` 每会话各调一次；`swapChain_` 亦每会话独立。
【推断】无共享 device/swapchain ⇒ **同步放大只能由应用层逐路下发相同 zoom/pan**。

### 1.5 🔴 放大固定为双线性 —— 像素级比对的精度天花板

【事实】`VideoRenderer.cpp:4540` 恒走 `DrawWithShader`，`:4544` 置 `actualVideoScalingMode_ = Shader`。
【事实】sampler Filter = `D3D11_FILTER_MIN_MAG_LINEAR_MIP_POINT`（`:2387`）⇒ **放大 = 双线性**。
【事实】Lanczos-3 / 双三次只在**缩小**链路出现（`:2842-2852`）。
【事实】`DrawWithVideoProcessor` / `CanUseDirectVideoProcessor` 全树**无调用点**（遗留未启用）。

⇒ 放大后的像素是**插值结果，不是真实采样**。

### 1.6 无源裁剪 API

【事实】头文件检索 `crop / clip / sourceRect` 均无结果；
内部的 `VideoProcessorSetStreamSourceRect`（`:2914`）属于上述未启用路径。
⇒ **内核不提供"设置源裁剪矩形"的公开接口**。

## 二、应用层现状

### 2.1 ✅ 同步放大已具备

【事实】`MainWindow.axaml.cs:704-708, 749-759` `ApplyViewTransform` → 对所有路
统一调用 `SetViewTransform`。⇒ **需求②是现成能力，零成本**。

### 2.2 🔴 AB 模式目前根本不显示真实视频

【事实】`MainWindow.axaml.cs:1052-1065` `OnToggleAbSlider`：设置 `Grid.IsVisible = false`
再显示 `AbSliderView` ⇒ AB 模式下**没有真实视频画面**，只有占位渐变（`AbSliderView.cs:111-112`）。
【事实】`AbSliderView.cs:14` 是 Avalonia Control，`Slider` 0..1，
`OnPointerMoved` 用 `Slider = x / Bounds.Width`（`:98`）⇒ **只有 X 方向竖线，没有交叉点、没有 Y**。
【事实】**不存在**"分割位置 → 各路可见区域"的转换逻辑。

⇒ 需求中的"AB 切分"与现有 AB 模式**不是同一个东西**，现有实现无法直接扩展。

### 2.3 布局模型是均匀网格，不支持非等分

【事实】`GridLayout.cs:15-28` `ComputeGrid`：2→2×1、3→3×1、4→2×2、7-9→3×3。
【事实】`CompareGridView.ArrangeOverride:150-168`：`cw = finalSize.Width / cols` 等分摆放。
⇒ **无行/列权重、无跨格**。ABC（一大两小）与 ABCD（可调十字）是**新结构，不是调参**。
【事实】无占比/权重数据结构；持久化只有 `SessionSnapshot.GridLayout` 一个 int 码（`:10`）。

### 2.4 airspace：覆盖层必须走 Topmost 窗口

【事实】`PlayerSurface.cs:18` `class PlayerSurface : NativeControlHost`，
`:170-189` `CreateNativeControlCore` 用 `CreateWindowExW(WS_CHILD…)` 建**独立子 HWND**。
【事实】`docs/10-UI结构审查与布局优化.zh.md:86-101`：每路是真实子 HWND，
永远盖在父窗口之上，`MagnifierOverlay` / `AbSliderView` 会被画面盖住。
【事实】可靠绕过方案 = `ThumbnailPopup.cs:28-32`
`Window { Topmost = true, ShowActivated = false, ShowInTaskbar = false }`。

⇒ **可拖动的十字交叉点手柄只能画在独立 Topmost 覆盖窗口**。
⚠ `MagnifierOverlay` 目前只是 CenterPanel 内的普通 Control（`MainWindow.axaml:93`），
真机会被盖住，**不能作为参考实现**。

### 2.5 路数与模式

【事实】上限 9 路：`CompareGridView.cs:79` `SetCount` clamp 0..9；
`MainWindow.axaml.cs:282` `room = 9 - _sync.Count`。
【事实】"模式"只有 `SingleView` bool + 网格预设，**无 ABC/ABCD**。
【事实】**无"按路数限制可用模式"的逻辑**。
【事实】**不支持交换位置**：`SyncController` 只有 `AddSlot` / `RemoveSlotAt`（`:112-160`），
顺序 = 导入顺序，无 Swap/Move。

## 三、差异比对现状（🔴 三条前置缺失）

### 3.1 现有差异只是降采样热力图

【事实】`DiffOverlayView.cs:13-14` 注释："96×N 网格像素采样…归一化 |ΔRGB| 热力着色"；
`:61` `_cellsY = Clamp(96 * h / w / 2, 8, 256)` ⇒ 16:9 约 2592 格，**非全分辨率**。
【事实】算法 `:142-143`：`Delta = (|ΔR| + |ΔG| + |ΔB|) / 3`，阈值 `0.02`（`:106,127,266`）。
【事实】仅在点击/打开时重采样（`:41`），**非实时**。

### 3.2 🔴 无色彩空间归一化

【事实】探针 `ProbePanel.cs:112` 与放大镜 `MagnifierOverlay.cs:245` 一律 `Clamp(v * 255)`。
【事实】HDR 走 16 位**线性 scRGB（1.0 = 80 nits）**，SDR 走 **gamma 编码**（`docs/20 §1.3:58-74`）。
【事实】`docs/19 §6` 实测 HDR 单点回读可 >1（`B = 2.6641`）。

⇒ HDR 线性值 >1 会被截成 255；**HDR 与 SDR 的回读值不可直接相减**。
这是"比例式差异对比"落地前必须先补的**前置项**。

### 3.3 🔴 zoom/pan 逆变换未纳入

【事实】`PixelReadback.cs:68-70` 注释明确：
> ⚠ zoom/pan 的逆变换尚未纳入…按 Dest 矩形即最终成像区域处理，
> 在 zoom=1/pan=0 下与现有行为一致。

【事实】`VideoPixelMap.MapToSource`（`:21-33`）与 `PixelReadback.SourceToBackBuffer`
（`:25-89`）已处理**缩放 + letterbox 偏移 + 钳制**，可逆。
⇒ 现有映射**不支持"缩放+裁剪"后的逆变换**，需求③落地必须补。

### 3.4 🔴 无"多路同刻帧"保证

【事实】`SyncController.cs:6-8` 以第 0 路为 master、按**媒体时间**对齐；`Play()` 逐路广播（`:210`），无锁步。
【事实】漂移校正保守：冷却 1s（`:474`）、半帧阈值（`:606-609`）。
【事实】实测 4K 双路静置 8s 偏差 **138~195 ms**（`docs/18 §5:820-829`）⇒ 60fps 下约差 **8 帧**。
【事实】回读取的是"已呈现帧"（`Capture.cs:90`），`SyncController` **不校验呈现帧号**。

⇒ 像素级对拍**必须以"暂停 + 逐帧步进对齐"为前提**，播放中无法保证同刻。

### 3.5 性能：全画面逐像素回读是主要瓶颈

【事实】回读是**同步 P/Invoke，强制 GPU 管线同步**（`MagnifierOverlay.cs:128-130`、`ProbePanel.cs:83-85`）。
【事实】节流：探针 33 ms（`ProbePanel.cs:75`）；放大镜 33 ms + 整格未动则跳过（`:98,132,136`）；
`DiffOverlayView.cs:65-68` 改为每行一次批量读，调用数 ~2592 → ~27。
【推断】4K 全画面单次回读约 **133 MB**（`Capture.cs:23` `TilePixelBudget = 1.5M`），
乘以路数与帧率 ⇒ **实时全画面逐像素差异不可行**，只能"暂停后单次计算"或"降采样"。

## 四、三个必须解决的阻塞

### 阻塞 A：内核无法任意裁剪【高】

`SetViewTransform` 的 `max(0.0f, ...)` 钳制使 pan 在常见情况下失效，且无 source rect API。

三条出路（**按代价从低到高**）：

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A1 Win32 窗口裁剪**（推荐） | 每个会话一个 HWND，各自设相同 zoom；用 `SetWindowRgn` / `WS_CLIPSIBLINGS` 在 Win32 层裁出可见区域 | 不改内核 | 需处理 DPI、缩放时的区域重算 |
| **A2 应用层合成** | `ReadVideoPixelRegion` 回读后自行缩放/裁剪/拼合，画到一张位图 | 不改内核 | 🔴 **性能不可行**（4K × N 路同步回读） |
| **A3 扩展内核** | 新增 `source rect` / 视口裁剪 API，或修掉 pan 的 `max(0,…)` 钳制 | 需改上游内核 | 上游未必接受；且本次 PR #9 已占 API 15 |

⇒ **建议 A1**。它绕过了 pan 的限制，因为裁剪发生在 Win32 窗口层而非渲染层。

### 阻塞 B：像素级比对与放大不可兼得【需求层面】

放大恒为双线性 ⇒ 放大后的像素是插值值。**"无缝放大"状态下做的比对，不是像素级比对。**

要与需求方确认到底要哪个：
- 若要**真·像素级**：必须 **1:1 原生分辨率**比对（不放大），比对结果可信但看不到细节；
- 若要**放大后看细节**：那比的是**插值后的图像**，只能用于"视觉差异"，不能报像素级数值差异；
- 折中：**在源分辨率做差异计算，再把差异结果（热力图/掩膜）放大显示** ——
  计算在真像素上、显示是放大的。这是最合理的形态，且不改内核。

### 阻塞 C：差异数值目前不可比【前置项】

HDR 线性 scRGB 与 SDR gamma 直接相减无意义；阈值 0.02 的语义也未定义。
⇒ 必须先做**传递函数归一化 + 统一到同一色彩空间**，再谈"差异率"。

## 五、建议实施路径（分阶段）

**阶段 1 — 打地基（无外部依赖，可独立交付）**
1. 色彩/位深归一化层：把回读值统一到同一传递函数与量程（`Core/Imaging`）。
2. `PixelReadback` 补 zoom/pan 逆变换（`PixelReadback.cs:68-70` 已标注缺口）。
3. `SyncController` 增加 `SwapSlots(i, j)`，支撑"文件自动交换位置"。

**阶段 2 — 布局与交互（纯应用层）**
4. `GridLayout` 扩展非均匀模型：新增"每格 Rect 表"或"行列权重数组"，
   保留现有均匀网格作为特例（**注意 `GridLayout` 有单测，属 Core，两个测试工程只引用 Core**）。
5. 新增 `Mode` 枚举（AB / ABC / ABCD）+ 按路数限制可用模式的规则。
6. 新建 **Topmost 覆盖窗口**承载十字交叉点与拖动手柄（参照 `ThumbnailPopup.cs:28-32`）。
   ⚠ **不要**沿用 `MagnifierOverlay` 的普通 Control 写法。

**阶段 3 — 放大与裁剪**
7. 复用现成的 `ApplyViewTransform` 做同步放大（零成本）。
8. 用 **A1 方案（Win32 窗口裁剪）** 实现"裁剪后分割"。
9. AB 切分**重写**：现有 `AbSliderView` 不显示真实视频，不能扩展，需重做。

**阶段 4 — 差异对比**
10. 差异计算移到**源分辨率**（真像素），显示层再放大（见阻塞 B 折中方案）。
11. 性能形态定为"暂停后单次计算"，不做实时全画面。

## 六、需要向需求方澄清的问题

1. **"像素级比对"指的是源分辨率 1:1，还是放大后的画面像素？**
   两者在内核双线性放大下不可兼得（阻塞 B）。
2. **ABC 的确切布局**：笔记写"3行/1列/2个在左右上下"疑似笔误——
   是"左大图 + 右侧上下两小图"，还是"上大图 + 下方左右两小图"，还是三个等分？
   三种的交叉点自由度不同（前者交叉点只在右侧竖线上，自由度 = 1）。
3. **ABCD 的交叉点是自由二维还是仅比例？** 四宫格若允许自由拖动，
   需要 2 个自由度（x, y）；若只是"比例"，1 个即可。
4. **"文件自动交换位置"的触发规则**：自动按什么排序（文件名？分辨率？导入时长？），
   还是用户拖拽后自动重排？
5. **各路源分辨率/宽高比是否一致？** 若不一致，"统一分辨率"会因 letterbox
   产生黑边，`dest` 不同 ⇒ 需求①需要重新定义（是按"内容区"对齐还是按"窗口"对齐）。
6. **是否需要跨 HDR/SDR 比对？** 若是，阻塞 C 必须先解决，工作量显著上升。

## 七、与上游 PR #9 的关系

本次分析暴露的内核限制中，**只有"任意裁剪"需要改内核**；
若坚持"不改内核"，A1 方案可覆盖。因此**不建议**把裁剪能力挂到 PR #9
（该 PR 已是 breaking change，API 15，再叠加改动会拖长评审周期）。
可考虑作为后续独立 PR（届时需再递增 API 版本）。
