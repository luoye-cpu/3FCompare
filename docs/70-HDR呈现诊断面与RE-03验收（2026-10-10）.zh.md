## 二、为什么这些计数必须存在（而不是读代码就够）

`hdrProcessingPath` 在两条臂上都报 `*Dynamic`：它按**码流元数据**分类
（`third_party/fff_project/FFF.Native/3FP/Hdr/HdrProcessor.cpp:203（流级）与 :338（逐帧）`），而真正决定画面的是着色器闸门
`3FP/Render/VideoRenderer.cpp:4939-4941`——`actualMode_ != MapToHdr` 时曲线才生效。
两个东西不是一回事，读代码能看懂，读快照看不出来。本轮就把它读错过一次
（判成"HDR10+ 在 16bit 臂上失效"，见 `docs/69 §五之补` 第 3 条）。

新增的两组计数把这件事变成可读数，并且天然是回归探针：

* `dynamicCurveFramesApplied / Refused`——曲线到底有没有塑造已绘帧。
  `applied` 恒 0 而 `dyn=1` 就是 RE-03 那一类故障的形状。
  计数取自**真正进着色器的那块缓冲**（`dynamicSettings.enabled`，
  `3FP/Render/VideoRenderer.cpp:4956-4959`、`5078-5081`），不是重算一遍判定式——
  闸门和硬件不能对"报了什么"有分歧。
* `setHdrMetaDataCalls / Suppressed` + 最后一次发给 DXGI 的四个原值
  （`3FP/Render/VideoRenderer.cpp:4737,4754-4759`）——T3 承诺的逐帧信令是否真发、
  2% 变更限流（`HdrMetadataChanged`，`3FP/Render/VideoRenderer.cpp:1055`）挡住多少。

### 2. 我的改动值多少钱（以及为什么不能用端到端去问这个问题）

同一批素材、同一臂，在"计数器落地前/后"两批之间重跑（`logs/cost-impact.txt`）：
24 格里 22 格为正，最大 **+40.07%**（1080p `cpu-hdr` 8.55→11.98 ms/帧）。
**这个数字不能读成"计数器花了 40%"**，两个理由都足以否掉它：

1. 重编后的件不只含我的计数器——它还含那 13 个未提交的在飞文件（`SampleCurve` 行索引修正、
   刷新路径重建曲线、空槽逐个停放等）。批次差 = 在飞改动 + 我的改动 + 任何环境漂移，未分离。
2. 端到端读数本身的批间重复性就在几十个百分点量级（同配置同臂跨批最大 40%），
   而 4 个 relaxed 原子自增的量级是纳秒。

所以量原语，不透过噪声去看它（`3fp/tools/counter_cost_microbench.cpp`，`logs/counter-cost.txt`）：

```
./counter_cost_microbench.exe --iters 20000000   →  0.01691 us/loop = 16.9 ns / 帧
./counter_cost_microbench.exe --iters  5000000   →  0.01682 us/loop = 16.8 ns / 帧
轮询侧 4 次 relaxed load                                        0.4 µs / 次（不在帧路径上）
```

每帧上界 16.9 ns：对 60 fps 的 16,667 ns 预算是 **0.10%**，对 8K 软解实测的
~130 ms/帧是 **0.000013%**。逐帧实际只走 1–2 次自增（曲线计数按分支取一个、
信令两个只在 scRGB 链上动），所以这是**高估的上界**。

真正被这条数据支持、且值得记下来的结论是相反方向的：
**端到端 cpu_ms/帧只能批内比较，不能跨批复用**。这也是 `docs/69` 那张 HDR10+ A/B
表为什么要用"同批内剥 SEI 对照"而不是拿历史数字做减法。

### 3. 托管镜像的正确性不靠"编译过了"

`tests/3FCompare.Core.Tests/HdrSignalDiagnosticsLayoutTests.cs` 从内核头解析字段与类型、
按 C 对齐规则算偏移，再逐个对 `Marshal.OffsetOf`。验过它会咬：

```

还原 → 通过: 2/2
```
头文件找不到时该测试**判红而不是跳过**（`FindRepositoryRoot` 直接抛）。

## 九、附：把共享工具 `校验文档行号引用.py` 的解析缺陷一并修掉（带证明）

写这次的引用时，工具把我**完全正确**的一条判成越界：

```
docs/69 … third_party/fff_project/FFF.Native/3FP/Hdr/HdrProcessor.cpp:713（该文件只有 578 行）
```

出货树那份有 900+ 行，578 行的是 `3fp/kernel` 那份。根因在 `find_source()`：
它把引用**剥掉前缀逐级试**，而 `SOURCE_ROOTS[0]` 就是 `3fp/kernel` ⇒
只要两棵树有同名文件，**文档里写全了的 `third_party/...` 路径会被解析到另一棵树**。
该工具的 docstring 里已经为 `3fc-followhand` 的旧副本按顺序修过一次同一类坑，
换一对树就复现 —— 因为顺序解决不了"引用已经写明了路径"这种情况。

修法（`3fp/tools/校验文档行号引用.py` `find_source()`）：引用里写了从仓库根算起的路径时，
**先精确命中**，再退回原有的"剥前缀 + 名字索引"。
