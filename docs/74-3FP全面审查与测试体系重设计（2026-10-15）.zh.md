# 3FP 全面审查与测试体系重设计（2026-10-15）

> 本文是"全面审查 3FP、确定功能是否完全可用，并在原有测试办法基础上扩展重设计"的交付文档。
> 工作方式：主 agent 侦察 + 三路并行只读调研（A 内核仓 / B 测试设施 / C 宿主与文档）→ 主 agent 程序化实测复核 → 汇总本文 → 动手执行验证（`tests/output/gate-suite-20261015/`）。

## 0. 结论前置

1. **"完全可用"的判定词：进包形态（3FC 应用 + TP 出货内核）功能基本可用，但未达到完全可用。** 挡住"完全"的是三件事：
   - **一条确定性真缺陷**：应用级 selftest 的「放大镜-探针一致性」稳定失败（差 0.4235），10-14 与 10-15 两轮数字逐位相同，日志自判"两边不是同一代帧/同一个面"；
   - **一类间歇性致命崩溃未修**：`Fatal error. Invalid Program: attempted to call a UnmanagedCallersOnly method from managed code`（docs/50/51 与 CHANGELOG 有账，本轮 2 跑中 1 崩，崩在窗口最大化/还原步）；
   - **配对维度存在结构性分叉**：实验内核树与 TP 出货树 `PlayerApiVersion` 同为 20，但 snapshot/config 两个结构的字段数、尺寸、**中段字段顺序**全不同——误配时 `FFF3FP_Create` 安全拒绝（表现为"第一步就未就绪"），而现有门禁的"版本号相等"判据区分不出进包 DLL 来自哪棵树。
2. **本轮新增交付物 `tools/check_snapshot_pairing_matrix.py`**：五源（实验内核头 / TP 头 / VB 互操作 / C# 托管镜像 / PerfTest）× 两结构（snapshot/config）逐字段宽度+偏移+尺寸+字段集合对撞，designated pair 语义把"已知跨树分叉"与"回归"分开。实跑 **VERDICT: PASS exit 0**（三对 designated 全绿，12 个跨树对如实标红）。
3. **修复一个静默失效（PerfTest）**：其快照镜像缺 5 个 DEPRECATED 槽 ⇒ 376 B < TP 392 B ⇒ 每次 `GetSnapshot` 被尺寸门硬拒而返回值被忽略 ⇒ 此前所有"性能数据"是空快照上的计时。已补槽 + 加返回值检查，修复后 designated pair 转绿、编译 0 错误。
4. **定位一个数月历史的假红工厂**：`dotnet test` 经 schtasks 跑时，48 条 Core 测试稳定失败于 `UnauthorizedAccessException`（`%TEMP%` 建目录被拒）——**与代码无关**。本轮实证：bat 里 `set TEMP/TMP` 到工作区目录后 **877/877 全绿 exit 0**。
5. **测试体系重设计六项**（§5）：按"配对"分组统一入口、矩阵工具常驻并接门禁、schtasks 通道标准化（清代理 + TEMP 重定向 + 退出码落盘）、D9 带牙判据常驻化、DLL 归属判据（实测 sizeof + 偏移对撞，不只是版本号）补进门禁、TP 头文件补 static_assert 牙齿。

## 2. 核心发现：两棵内核树的 ABI 分叉（配对矩阵）

### 2.1 五源实测布局

`tools/check_snapshot_pairing_matrix.py` 实跑（exit 0，全文见 `_3fc_tmp/matrix_final.txt`）：

| 源 | snapshot | config |
|---|---|---|
| 内核实验树 `3fp/kernel` | **71 字段 / 408 B** | **22 字段 / 112 B** |
| 出货树 `third_party/fff_project` | **69 字段 / 392 B** | **15 字段 / 80 B** |
| VB 宿主互操作 | 71 字段 / 408 B | 22 字段 / 112 B |
| C# 托管镜像 `Fff3FpNative.cs` | 69 字段 / 392 B | 15 字段 / 80 B |
| PerfTest 镜像 | 69 字段 / 392 B | 15 字段 / 80 B |

### 2.2 分叉的形状：不只是"尾巴长短"

字段**集合**差异只有 2 个：实验树快照多 `AudioDelay100ns` + `VideoUpload100ns`（2×8 B = 16 B = 408−392）。但**顺序**在中段分叉：

- TP 树：IAMF 三字段（`iamfActive`/`iamfChannels`/`iamfSoundSystem`）位于**中段 #26-28**（偏移 152/156/160，紧跟 `decodedAudioFrames`）；
- 实验树：同样位置是 `audioPosition100ns`/`bufferedAudio100ns`/`audioUnderruns`，IAMF 三字段在**尾部**（364/368/372）。

**这决定了修法的禁忌**：当前两树尺寸不同（408 vs 392），尺寸门还能拦住误配；但任何"给镜像补两个字段凑到 408"而不重排中段的做法，会产生**过了尺寸门却整体错位**的结构——这正是"尺寸相等拦不住中段少 20、尾部多 20"那一族事故的形状。矩阵工具的逐字段偏移对撞（而不仅是尺寸）就是防这个。

### 2.3 配对矩阵四象限（designated pair 语义）

| | VB 宿主 | C# 托管镜像 / PerfTest |
|---|---|---|
| **实验内核** | ✅ GREEN（71/408 + 22/112） | ❌ RED 跨树（config 80 < 112 ⇒ `Create` 即 InvalidArgument） |
| **TP 出货内核** | ❌ RED 跨树（快照字段顺序分叉；**尺寸门反而不拦**——408 > 392 类的静默错位） | ✅ GREEN（69/392 + 15/80） |

工具口径：退出码只对 designated pair 负责（`vb-host↔kernel(exp)`、`cs-mirror↔shipped(TP)`、`perftest↔shipped(TP)`）；12 个跨树对报"RED（跨树分叉，预期内）"并给出首差位置与字段集合差集，**不计入退出码**——把"已知分叉"与"回归"分开。

### 2.4 版本号鉴别力蒸发 + 调研数字勘误

- 两树 `PlayerApiVersion` **同为 20**（实验树 `PlayerApi.cpp:35`，TP `:31`）⇒ `check_kernel_pairing.py` 的"版本恰好相等"判据已失去鉴别力（其 docstring 早有预言："那天要加的是可观测的版本内指纹"）。**本轮补的指纹就是"实测 sizeof + 逐字段偏移"**。
- 勘误（以实测为准）：recon-kernel 报"TP 400 B/69 字段 + config 80 B/12 字段"——实测 TP 快照 **392 B**、config **15 字段**（80 B 与二进制实测一致）；recon-host 报 PerfTest 镜像"约 368-372 B"——实测 **376 B**（缺 5 槽），其对 docs/69 时效性的提醒（TP 当时 API 17）有效。
- 另证伪 recon-tests 报告两条：① "check_kernel_config_abi.py 两树皆 FAIL"——本轮实测三份 DLL 全 PASS（6/6/0）；② "零调用者"——已接入 `tools/发布门禁.ps1` [2/11] 追加（J5，2026-10-14）。

## 4. 缺陷与风险清单（分级）

### P0（挡住"完全可用"）

- **P0-1 放大镜-探针一致性确定性缺陷**。症状：放大镜读 (997,280) 缓冲格得 (0.435,0.435,1.000)，探针同位置读 (0.012,0.012,1.000)，5×5 邻域内无探针值（残差 0.1137）⇒ 日志自判"两边不是同一代帧/同一个面"。**10-14 与 10-15 两轮数字逐位相同 ⇒ 确定性、可复现，不是 flaky**。它还把 selftest 退出码恒压成 1（docs/95 §4 明说这条）。修法方向：取证"同一代帧/同一个面"——放大镜与探针的取帧路径是否读了不同的交换链缓冲/不同代的帧。
- **P0-2 `UnmanagedCallersOnly` 间歇致命崩溃**。`Fatal error. Invalid Program: attempted to call a UnmanagedCallersOnly method from managed code`，崩在窗口最大化/还原后的 `DispatchMessage` 附近。**不是新回归**：docs/50 §八（Release 构型 2/4）、docs/51:104/129（2 次）、CHANGELOG:254 均有账；docs/50 的根因假设是"间接调用目标被换掉"（与"IP 落 MEM_FREE"同族），**未验证未修**。特性：不产 VEH 留痕、可能不产 WER，只认旧三条腿的脚本会读成"判红退出"（docs/50 已加第四条腿 stderr 匹配 `Fatal error.`）。流行率有据：docs/50 M12 两臂 3/18 vs 6/18（p=0.4430，未测到上升）。本轮 2 跑 1 崩，与文档区间吻合。

### P1（本轮新定位/新修复，或挡住门禁效力）

- **P1-1 PerfTest 静默失效（已修并运行时验证）**。快照镜像缺 5 个 hdrDp DEPRECATED 槽 ⇒ 376 B < TP 392 B ⇒ 每次 `GetSnapshot` 被 `PlayerSession.cpp:1918` 尺寸门硬拒，而 `:322` 忽略返回值 ⇒ 全零快照上算性能。已补槽（与 `Fff3FpNative.cs:156-163` 同形状、附事故注释）+ 返回值检查（非 0 即报错返回）。修复后 designated pair 转绿、`dotnet build` 0 错误、**schtasks 实跑 exit 0 且快照字段真实流动**（§6 [R3]）。**这是 2026-10-14 托管镜像删槽事故的同族第二现场**——本文件 10-15 重犯同一错误，教训：凡是镜像结构体，必须进矩阵工具常驻对撞。
- **P1-2 docs/99 §14.5 配对断裂根因（已定位，可关闭 U3）**。应用 config 镜像 80 B（TP 形）vs 实验内核 112 B ⇒ `FFF3FP_Create` 尺寸门（`PlayerApi.cpp:94-106`）直接 InvalidArgument ⇒ 第一步"未就绪（状态=）"；对照臂换回 80 B 发布内核即"等就绪 ✓"。**当年"已排除配置结构体尺寸"是查错了镜像**（核对的是内核树 112/22，不是应用的 80 B）。修法=从当前源码重建 AOT app（本轮已做，且与 TP 内核配对正确）。
- **P1-3 Core 测试 48 条 TEMP 假红（已定位并验证修复）**。schtasks 跑的 `dotnet test` 中，凡用 `TempDir` 夹具的用例稳定失败于 `UnauthorizedAccessException`（`%TEMP%` 建目录被拒）——**与产品代码无关**（本轮探针证明 schtasks 下的 cmd.exe 写 `%TEMP%` 正常，拒绝发生在 testhost 进程）。修复：驱动 bat 里 `set TEMP/TMP` 到工作区目录（`TempDir` 走 `Path.GetTempPath()`，尊重进程环境变量）⇒ **877/877 全绿 exit 0**。这是"假绿防护很强、假红防护缺失"的缩影——重设计 R3。

## 5. 测试体系重设计

### 5.1 原有四层资产与结构性问题

| 层 | 资产 | 状态 |
|---|---|---|
| ① 内核 C++ 探针 | ~90 支（`3fp/tools/*.cpp`，直 P/Invoke 真内核 + 真实窗口/FFmpeg） | 27/82 坏（P2-6）；口径成熟（LSP/ACA 标准批次、媒体路径铁律、TMP 重定向） |
| ② VB 宿主回归 | `FFF.Player.Tests` 4 入口 + `run_host_tests.sh` 扫描器 | 扫描清单(23)与现树入口(4)错位；现树跑它会 19×exit 3 |
| ③ 3FC 应用级自测 | `--selftest/--comparemodetest/--sessiontest/--screentest` + `发布门禁.ps1` 11 步+6 追加 | 总闸当前被 P0-1 恒压 exit 1；fail-closed 口径好 |
| ④ 判据脚本 | `tools/*.py`（ABI/导出/配对/中性/探针集/文档行号） | 本轮新增矩阵工具；D9 带牙判据已流失 |

**结构性问题**（重设计的输入）：
1. **层间不互调**：门禁绿对 3FP 管线无意义（docs/87:16）——③的门禁从不跑 ① 的行为回归；
2. **配对维度缺失**：四层资产各自隐含配对假设（VB↔实验树、3FC↔TP、PerfTest↔TP），没有统一入口表达"这套资产配哪棵树、对撞结果如何"；
3. **假红防护缺失**：TEMP 假红稳定存在数月无人管（P1-3）——假绿防护（NOT JUDGED=exit 3、演示模式退码 2、变异复验）是全仓最强主线，假红却是零防护；
4. **带牙判据会流失**：D9 的 lane G 计数探针目录已不存在，判据降级成"不计数打印"后 12/12 PASS exit 0（docs/77:86）；
5. **版本号鉴别力蒸发**（§2.4）。

### 5.2 重设计六项

- **R1 按"配对"分组统一入口**。每个测试资产显式声明 designated 配对（哪份宿主镜像 ↔ 哪棵内核树），`check_snapshot_pairing_matrix.py` 作为配对守门常驻：designated pair 漂移 ⇒ exit 1；跨树对漂移 ⇒ 如实呈现但不误伤。已有三对 designated：`vb-host↔kernel(exp)`、`cs-mirror↔shipped(TP)`、`perftest↔shipped(TP)`。
- **R2 矩阵工具接发布门禁**（新增 [2/11] 追加行，与 J5 的 config ABI 判据并列；fail-closed，源缺失=NOT JUDGED=判红）。它同时回答 J5 回答不了的问题："进包那份 DLL 的布局与托管镜像是否逐字段一致"。
- **R3 schtasks 通道标准化**。所有驱动 bat 模板（`_3fc_tmp/run_*.bat`）统一内置：`chcp 65001` + 清 10 个大小写代理变量 + `set TEMP/TMP` 到工作区可写目录 + 退出码落盘 + 结论行 grep 判据。**TEMP 重定向本轮已验证消除 48 条假红**（P1-3）。
- **R4 带牙判据常驻化**。D9 判据从 docs 记账重新落成工具集常驻探针（lane G 模式：[J1]/[J2] 区域映射断言 + failed judgements 计数 + exit 0/1），防再次"降级成不计数打印"。
- **R5 DLL 归属判据补进 J5 的输出消费**：`check_kernel_config_abi.py` 已实测 sizeof，门禁结论里明印"进包内核布局 == 托管镜像布局"（而不只是"版本号 == 20"）。
- **R6 TP 头文件补牙齿**：snapshot `static_assert(sizeof==392)` + config `sizeof==80` + 关键 offset pin（IAMF 三字段 152/156/160、公共前缀止于 `effectiveTargetPeakNits` 352 B），抄实验树 `Api.h:342-352` 现成形状。
- **R7（并列）探针修复波**：按 docs/95 §J3 四档走，先修工具链一次收 19。
