## 一、P0 · 已验证（建议立即修）

### 1.1 会话布局往返丢失，且被恒真断言掩盖 【已验证】

**现象**：保存会话再加载，**1/2/3/5/6 路的网格布局会变**（4/7/8/9 路侥幸正确）。

**根因**：`GridLayout.CodeFor` 的映射与 `GridLayout.ComputeGrid` 不一致。

| 路数 | 实际布局 `ComputeGrid` | `CodeFor` 存成 | 还原后 `ResolveGrid` | 结果 |
|:--:|---|---|---|:--:|
| 1 | (1,1) | `Code2x2` | (2,2) | ❌ |
| 2 | (2,1) | `Code2x2` | (2,2) | ❌ |
| 3 | (3,1) | `Code2x2` | (2,2) | ❌ |
| 4 | (2,2) | `Code2x2` | (2,2) | ✅ |
| 5 | (3,2) | `Code3x3` | (3,3) | ❌ |
| 6 | (3,2) | `Code3x3` | (3,3) | ❌ |
| 7–9 | (3,3) | `Code3x3` | (3,3) | ✅ |

真实保存路径 `MainWindow.axaml.cs:695`：

```csharp
GridLayout = GridLayout.CodeFor(Grid.SingleView, _sync.Count),   // ← 用"路数"推导
```

还原路径 `MainWindow.axaml.cs:750`：

```csharp
Grid.SetGridLayout(GridLayout.PresetOf(snapshot.GridLayout));
```

**保存时根本没有看用户实际选的预设**——`CompareGridView.Preset`（`CompareGridView.cs:109`）就摆在那里没用。

**为什么测试没抓到**：`PipelineRegressionTests.cs:44-56` 的
`保存与还原是同一套映射_往返不丢布局` 断言是

```csharp
Assert.Contains(GridLayout.PresetOf(code), new[] { "auto", "2x2", "3x3" });
```

而 `PresetOf` 的返回集合**恰好就是** `{"auto","2x2","3x3"}` —— 对任何输入恒真。
这条测试从未验证过任何东西。同样的自证问题在 `MainWindow.SelfTest.cs:206,281`：
sessiontest 的期望值同样由 `CodeFor` 推出，所以"用户预设丢失"这条回归**永远测不出**。

**修法（已验证可行）**：保存时记录**用户实际选择**而非推导值。

```csharp
// Core/Display/GridLayout.cs 新增
public static int CodeFromPreset(string preset, bool singleView)
    => singleView ? CodeSingle : preset switch
    {
        "2x2" => Code2x2,
        "3x3" => Code3x3,
        _     => CodeAuto,      // auto → 还原时走 ComputeGrid，与保存前一致
    };
```

`MainWindow.axaml.cs:695` 改为 `GridLayout.CodeFromPreset(Grid.Preset, Grid.SingleView)`。
`PresetOf(CodeAuto)` 已返回 `"auto"`，还原侧无需改动。

**测试要同步改**：断言应对比**还原后的实际网格**与**保存时的实际网格**：

```csharp
var (cols, rows) = GridLayout.ComputeGrid(count, singleView);   // 保存前
var code = GridLayout.CodeFromPreset("auto", singleView);
var restored = GridLayout.ResolveGrid(count, singleView, /*预设来自 PresetOf(code)*/ 0, 0);
Assert.Equal((cols, rows), restored);                            // 这才是真往返
```

### 1.2 `CreateSession` 异常路径漏 `Dispose` ⇒ 原生句柄永久泄漏 【已验证并已修】

`CreateSession` 在 `ApplyInitialColorMode` / `SetPresentConfig` / `SetPacingConfig`
抛 `EngineException` 时直接丢弃 `session`，**没有任何 `Dispose`**
（只有 `FFF3FP_Create` 失败分支 :46-50 做了清理）。

由于 session 持有**强** GCHandle（原因见下），漏 `Dispose` ⇒
原生 player 句柄 + GCHandle + 整个会话图**永久泄漏**，且没有终结器兜底。

**已修**：把 52–60 行包进 `try/catch { session.Dispose(); throw; }`。

> #### ⚠ 原报告建议的「改成 `GCHandleType.Weak`」是**错的**，已否决
>
> 这正是本项目"修法也要验证"约定要拦的那种错误。理由：
>
> 原生侧保存的是 `Marshal.GetFunctionPointerForDelegate(_callback)` 得到的**函数指针**，
> 而 `_callback` 是 session 的实例方法委托。一旦 session 被 GC，委托随之回收，
> 那个函数指针就变成**悬空指针**——原生工作线程再回调就是调用已释放的 thunk，**进程崩溃**（不可 catch）。
>
> 强 GCHandle 通过保住 session 间接保住委托，是此设计的**必要条件**，不是泄漏源。
> 真正的泄漏源是"没走 `Dispose` 的路径"，即本条。
>
> 已在 `Fff3FpEngine.cs` 构造函数处加注释说明，防止后人"优化"成 Weak。

## 二、P0 · 代码确凿（未实跑修法）

### 2.1 `Dispose` 与轮询线程竞争 ⇒ 原生 use-after-free

`Fff3FpEngine.cs:577-585`：

```csharp
public void Dispose()
{
    if (_disposed) return;          // 非 volatile、检查-置位非原子
    _disposed = true;
    EngineEvent = null;
    if (_handle != 0) Fff3FpNative.FFF3FP_Destroy(_handle);
    if (_callbackContext.IsAllocated) _callbackContext.Free();
    GC.SuppressFinalize(this);
}
```

`FFF3FP_Destroy` 与轮询线程的 `ReadSnapshot`/`Seek` 之间**没有任何同步**：
`SyncController.RemoveSlotAt:109` 刻意把 `Dispose` 放在 `_gate` 锁外，
而 16 ms 轮询 `ReadAllSnapshots:145` 已取到 slot 副本 ⇒ 可能拿着正在销毁的 `_handle`
进入 `FFF3FP_GetSnapshot`。`_handle` 销毁后也未置 0，二次 `Dispose` 会 double-free。

**修法**：`Interlocked.Exchange` 做一次性守卫；`Destroy` 与所有原生调用用同一把锁互斥；`_handle = 0`。

### 2.2 SkiaSharp / HarfBuzz 原生 DLL 版本硬编码，且无存在性校验

`src/3FCompare/3FCompare.csproj:59-60`：

```xml
<EmbeddedResource Include="...\libSkiaSharp.dll" />   <!-- 路径含硬编码 3.119.4 / 8.3.1.3 -->
```

对比 :49 的内核 DLL **有** `Exists()` 条件，这两行**没有**。Avalonia 升版导致 resolved
版本变化 ⇒ 路径不存在 ⇒ 嵌入资源**静默缺失**；而 `Program.cs:56-62` 的 `catch { }`
又吞掉解压失败 ⇒ **构建全绿、pack 自检全绿、用户启动即崩**。

**修法**：改通配路径 + `Exists()` 条件 + 缺失即 `<Error>`；`Assert-Package` 补"exe 内嵌资源清单"断言。
