### 3.3 一次错误归因（记录以免重犯）

我先跑了"合并前 0/2、合并后 2/3"就判定合并引入崩溃，并提议"关掉 RTSS 再测"。**两处都错**：

1. 拿 2~3 次样本对一个已知偶发族定生死；
2. 摘掉复现条件去求一个干净读数 —— 与"放宽断言换绿灯"是同一件事。

正确做法是环境一律不动、同批交替加样本量，也就是 §3.2 那张表。
**若某条件一摘崩溃就消失，结论要写成"该条件参与致崩"，那是新证据，不是"原来没崩"。**

### 3.7 P1-4 定案：`Owner` 不保证 Z 序；判据换了 instrument，修法带牙

这一段是 §3.6 里"既有偶发红"的收尾。它不是内核问题（两臂同一个 app 二进制），但它是**发布打包的拦路项**，
所以留档在同一份文档里。

**① 旧判据无效，先换 instrument。**
旧版拿 `WindowFromPoint` 命中视频子 HWND 当"被遮挡"的定罪证据 —— 放大镜覆盖窗带 `WS_EX_TRANSPARENT`
（鼠标穿透是硬需求），命中测试**按设计**返回下层窗口 ⇒ 该探针零分辨力，且恰好在修复生效时判红。
换成自顶向下走顶层链的 `MagnifierOverlayWindow.QueryZOrderPosition()`，三态 `Above/Below/NotInChain`
（"被压到主窗之下"与"压根不在链里"是两种病，修法不同）。
⚠ 链首必须 `GetTopWindow(0)`：`GetWindow(0, GW_HWNDFIRST)` 返回 0 ⇒ 走链一次都不执行 ⇒ 恒判负，
我据此一度以为"修复生效后仍 100% 被遮挡"。`WindowFromPoint` 降级为**读数**，不再参与判决。

**② 缺陷是真的，而且不是"采样太早"。**
能确证为"无补插 + 三态判据"的两个批次 `diag_run*`(10) 与 `tm_run*`(12)：**22 次读数里 3 次**（14%）
覆盖窗排在主窗**之下**。把时间线相邻、代码态靠推断的 `vis_run*`(6 次 1 红) 与 `final_run*`(3 次 0 红)
也算进来是 4/31 ≈ 13% —— 两个口径都给出来，因为后者的代码态我没有逐批取证。
判红的那 2 轮留了 6×30ms 的重试链，12 次采样**全部**停在 `Below`
⇒ 不是平台还没排完，"等多久"这一类修法（浮条收敛轮询那一路）被排除。

**③ 第一次尝试失败，但把 API 语义问出来了。**
无条件在 `ShowOverlay` 里 `SetWindowPos(自己, 主窗句柄, ...)` ⇒ 那一批（`zofix_run*`）**12 次读数 11 次 Below**。
机理：`hWndInsertAfter` 的语义是"插到谁**之后**（=之下）"，把 owner 传进去等于**亲手**把自己塞到主窗底下；
而"owned 窗口恒在 owner 之上"这条 Win32 说法在实测里不成立（同带、`GW_OWNER` 非空、仍被排在下面）。
正确的插入点是 `HWND_TOP`，且**不用** `HWND_TOPMOST`（那会让放大镜切到别的应用后仍浮在最上面，样式判据禁止）。
失败代码从 `rollback/` 逐字节还原，还原后 `diag`+`tm` 两批 22 次读数回到 3 次 ⇒ 与失败尝试前同一水平。

**④ 现修法与它的证据边界。**
`ReassertAboveOwner()`：只在观测到 `Below` 时补一次 `HWND_TOP` 插入（健康路径只走链、不打 `SetWindowPos`），
挂在每次呈现回调尾部（`ShowOverlay`）⇒ 与真实用户路径同源，不是自测里的特殊通路。

第一批（`ra_run*` 20 轮）**全绿且 `补插次数` 恒为 0** ⇒ 那 20 轮**不构成"修好了"的证据**：
触发条件一次都没发生，兜底可能是死代码也照样全绿。于是既做 ⑤ 的注入断言，也继续加现场样本量。
补插上线后累计（`ra`+`heal`+`heal5`+`vf`+`vf20`，50 轮、**47 次到达该步的读数**）：
- 用户可见的终态：**0 次 `Below`**（对照上线前 3/22，双侧 Fisher **p=0.029**）。
- 现实里"确实被压下去过"的证据：`vf_run2` 那一轮在 ③ 读数时 `补插次数=1` 且终态 `Above`
  ⇒ **抓到一次现行并由产品路径治好**（其余 46 次读数计数为 0）。
- ⚠ 但**不能**据此宣布"现场反转率降了"：补插把每一次 `ShowOverlay` 都变成一个采样点，
  仪表灵敏度与上线前"只在 ③ 拍一张"不同；按"该轮是否发生过反转"同口径比是 3/22 vs 1/47，
  Fisher **p=0.092，不显著**。两批又相隔 40 分钟以上、机器状态不可控。
  ⇒ 能确证的只有：**终态不再有 `Below`**，以及 ⑤ 那条"治好"的机制确实接在生产路径上。

**⑤ 于是把夹具做成断言（自测 #22 的第 ④ 步）。**
用那次**已知必然造成反转**的调用（`SetWindowPos(覆盖窗, 主窗)`）人为把覆盖窗压到主窗底下，
先自证夹具落地（读回必须是 `Below`，否则判"本断言无牙"），再只走真实产品路径
（`UpdateAt → PresentationChanged → 宿主 ShowOverlay`，**不**直接调补插），断言：
Z 序回到 `Above` **且** `补插次数` 增加（计数没动就说明是别人修的序，兜底不算生效）。
实测到达该步的 **47 轮全部** `注入后=Below 走产品路径后=Above 补插次数 0→1` ⇒ 这条是确定性的，
不依赖现场是否偶发。
**验牙**：把 `HWND_TOP` 换回主窗句柄重编，该断言判红（`走产品路径后=Below`，exit=1）⇒ 不是空转断言。
`MainWindow.SelfTest.cs` 里为此带的 `SetWindowPos` P/Invoke **只用于制造反转**，不在生产路径上。

**⑥ 顺带的读数（只记录，不改判决）**：`补插次数`、`主窗topmost`、顶层链每一项的 `top=` 位。

## 四、⚠ 上游会"改结构体布局但不升 `PlayerApiVersion`"
`a87046e` 区间内上游把 `FFF3FPAudioPeakLevels` 的 `std::uint32_t reserved` 换成
`inputChannelCount` + `float inputValues[8]`（**结构体变大 32 字节**），版本号一字未动。
它自己用 `legacySize = offsetof(..., inputValues)` + `version∈{1,2}` 做了向后兼容，且 3FC 托管侧没有这个结构
⇒ 本次无害。

**但 `PlayerApiVersion` 不能当 ABI 不变的凭据**（它只做"相等才收"，保证不了结构体没被改）。
以后每次合并的判据改成：`git diff <旧基线>..<新上游> -- FFF.Native/3FP/Api/FFF.Player.Api.h` 中

## 八、单路放大拖动：方向反了 + 量程实测为 0

用户报"左右拖动疑似有问题、鼠标上下疑似是反的，要鼠标向哪边拉画面就往哪边"。两条独立的事，都量过了。

### 8.1 量程：内核根本没地方可以平移（改前实测）
> 下面这张是**修之前**的读数，保留作为根因证据；修好后的同一条扫描见 §8.3 的对照表。

自测新增一步 `单路平移量程`：把 pan 从 −1 扫到 +1（z=2），每点**等一帧**再读内核上报的
`RenderTargetInfo.destX/destY`（不能等"读数变了"——被夹死时它恒不变，而那正是要量的东西）：

```
z=2 扫描 pan=-1.0→dest=(0,0) pan=-0.5→dest=(0,0) pan=0.0→dest=(0,0) pan=0.5→dest=(0,0) pan=1.0→dest=(0,0)
⇒ 原点可动区间 横 0px / 纵 0px
```
3 轮稳定，`--selftest` 仍 `exit=0`（这条只打 ⚠ 不判红：它是内核限制，不是托管侧回归）。

机理在 `FFF.Native/3FP/Render/VideoRenderer.cpp`：
```cpp
struct VideoDestination { std::uint32_t x, y, width, height; };          // :786 原点是无符号
destination.x = static_cast<std::uint32_t>(std::max(0.0f, … − offsetX)); // :4813 负值一律夹成 0
```
自测这台机器的后台缓冲是 1995×1122（正好 16:9）、片源 1920×1080（也 16:9）⇒ 拟合盒 `x0=y0=0`，
而放大后想"往右/往下看"必须让原点走**负**（把画盒往左上推出屏幕）⇒ 整个量程被 `max(0,·)` 吃掉 ⇒ **两轴都恒 0**。
反过来，若某个方向有 letterbox 余量（`x0>0`），该轴只能在 `[0, x0]` 里动 —— 也就是
"只动几个像素、而且方向是相机语义"，正是用户看到的"上下动一点点还是反的"。
⇒ 结论：**托管侧的 ±1 只是声称值**，单路平移在真机上一直是空的。对比模式不受影响：
`CompareCropPlanner` 早就写明"内核 `SetViewTransform` 只能放大、不能任意平移"，改用窗口层开孔做平移。

### 8.2 方向与量纲：托管侧确实错了两处（已改）
`MainWindow.OnSurfaceMove` 原来是 `_viewPan += dx·2/min(宽,高)`，而它的注释自称"内核视口同向平移"——
**那句注释是错的**：内核 `offsetX` 与 `panX` 同号、且从原点里**减**掉，所以 pan 增大是画面往**左/上**跑。
两处缺陷 + 一处量纲不一致：
1. **符号**：要"跟手"，托管侧必须做减法（对比模式的 `CommitComparePan` 一直是负号，两路现在一致了）。
2. **DPI**：`GetCursorPos` 给物理像素，分母 `Bounds` 是 DIP，**没除 `RenderScaling`**
   ⇒ 150% 屏上同样一段拖动多走 1.5 倍量程（"轻轻一拖就顶到头"）。对比模式那边一直有这一步。
3. **短边归一化**（原有性质，保留）：分母取短边，取长边会让宽屏横向灵敏度减半。

算术抽成纯函数 `src/3FCompare/Platform/ViewPan.cs`，配 6 条离线单测
（`tests/3FCompare.Platform.Tests/ViewPanTests.cs`，Platform **354/354**）：方向、DPI 无关性、短边量程、
钳位不溢出、退化输入、小步累计==一步到位。
**验牙**：把负号改回正号 ⇒ 6 条里 4 条判红（另 2 条按构造与符号无关，如实说明）；改回后复绿。

### 8.3 修法：方案 A（内核放行负原点）—— 用户 2026-09-26 授权"完整修复"，已实施

取舍当时是这两条，A 被选中并落地：

| 方案 | 动什么 | 代价 / 风险 |
|---|---|---|
| **A. 内核放行负原点（已采用）** | `VideoDestination.x/y` → `int32_t`，去掉 `max(0,·)` 换成"必须仍盖住拟合盒"的双边 clamp；`lastDestX_/Y_` → `atomic<int32_t>`；导出结构 `FFF3FPRenderTargetInfo.destX/destY` → `int32_t` 并把 `version` 1→2；托管侧 `RenderTargetInfo` 及其消费点跟着改 | 改动集中在一个 `.cpp` + 一个头；画盒原点在 `DrawWithShader` 处本就是 `float`（负值天然可用），D3D 侧零新代码。风险是"已进上游的结构改了签名性"⇒ 已在 `PATCHES.md` §十 记为本地分歧并写明下次合并的冲突点 |
| B. 3FC 侧不靠内核平移 | 单路也改成对比模式那套：子 HWND 放大 z 倍 + `WindowRegionClipper` 开孔 | 不碰内核，但要把单路布局改成"窗口大于面板"，牵动排布/DPI/探针坐标映射与显存预算，改动面比 A 大得多 |

**支持 A 的一条现场事实**：`FFF.Player` 宿主自己也调 `SetViewTransform`（`播放器会话.vb:220`），
而除 3FC 外无人读 `destX/destY` ⇒ 这不是 3FC 专用分歧，是替上游把平移修好，可直接提 PR。
`version` 因此**拒绝 v1** 而不是兼容：v1/v2 字节宽度相同、`size` 分不出双方，
放一个 v1 调用方进来只会把负原点读成巨大无符号值（静默错内容）；让它响亮地 `InvalidArgument`。
⇒ 这条在实施过程中当场演示过一次：新托管绑定（发 v2）配旧内核 ⇒ 探针步骤直接报
"真实内核未上报 RenderTargetInfo"，而不是给出一个被误标的数据。

**验收读数（同一条扫描，改前 vs 改后）**：

```
改前：pan=-1.0→(0,0) … pan=1.0→(0,0)      ⇒ 横 0px / 纵 0px
改后：pan=-1.0→(0,0)  -0.5→(-499,-281)  0.0→(-998,-561)
      0.5→(-1496,-842)  1.0→(-1995,-1122) ⇒ 横 1995px / 纵 1122px
```
期望值是**独立参照**（不是拿被测实现自己算）：z=2 时放大盒 = 2×拟合盒，
"仍盖住拟合盒"的原点合法区间 `[x0−w, x0]` 全长恰等于拟合盒宽 —— 实测 1995×1122 正是
z=1 那一拍读到的拟合盒尺寸。判据已写进自测（跨度偏离 >2px 即红），
所以哪天内核退回夹负原点的写法，这条会自己叫。

**顺带修掉的第二个真 bug**（同一处代码，改内核时才暴露）：`NativeFrameReadback` 的可见矩形原来是
`w = min(DestWidth, swapW − x0)`，`x0` 被钳到 0 ⇒ 负原点时**多数出 |DestX| 列**，把屏幕外的内容
当可见区回读。改成按有符号原点求交（右界取 `DestX + DestWidth`）。
⚠ 有一条既有契约**故意没动**：盒体整体越过**右/下**界时仍留 1 列可读（旧钳制行为，有用例钉着），
左/上界则给 `null` —— 后者意味着内核报回的盒子和缓冲根本没有交集，那已经不是"裁一点"而是数据不可信。

**签名性改动踩到的两处镜像断言**（编译器只报了一处，另一处是"恒假但还活着"的判据）：
① 两条 `NativeFrameReadbackTests` 拿 `destX/destY = uint.MaxValue` 触发"坐标溢出 ⇒ null"，

并补一条"画盒被完全推出左界 ⇒ `null`"接替坐标侧。
② `rt.DestX > int.MaxValue` 变成恒假不报错 —— 这正是"编译器不报错但语义已变"的那类，
必须手着删掉并说明它由谁接管。
