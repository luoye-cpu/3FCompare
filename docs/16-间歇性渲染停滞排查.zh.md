# 间歇性渲染停滞排查记录（2026-09-15）

> 结论先行：**根因已定位到机制层面，修复已做，但疗效未经复现验证。**
> 本文如实记录哪些是实测、哪些是推理。

## 一、现象

`--selftest` 的"窗口最大化/还原"步骤间歇性失败，报 `presented 未增长`。

首次遇到时（3 次中 1 次）的实测数据：

| 阶段 | presented | 说明 |
|---:|---:|---|
| 最大化前 | 35 | Playing |
| 最大化后 | 87 | 3 秒只涨了 52（正常为 +180 上下） |
| 还原后 | 87 | **Δ=0**，判定停滞 |

同期的正常样本：

```
最大化前: presented=58  → 最大化后: 239 (+181) → 还原后: 419 (+180) ✅
```

**关键对比**：失败时位置一直在推进（`1.66s → 4.92s → 8.34s`），时钟没停；
但 `PresentedVideoFrames` 不动。即**渲染真的停了，解码和时钟照常**。

## 二、定位过程

### 2.1 先确认不是"计数问题"

停滞时 `state=Playing`、位置推进，说明引擎在跑，只是没有 Present。
所以不是"计数不更新"，是呈现管线本身停了。

### 2.2 排除"没做布局同步"

self-test 在最大化**后**有强制布局：

```csharp
WindowState = WindowState.Maximized;
await Task.Delay(3000);
Grid.InvalidateMeasure();
Grid.InvalidateArrange();
UpdateLayout();
```

布局是同步了的，不是这个原因。

### 2.3 关键线索来自内核头文件

`FFF.Player.Api.h:546`：

```
// Redraw() re-presents the last cached frame on the presenter thread —
// the App calls it after a child HWND resize **so flips continue issuing**
// (ResizeBuffers stays on the presenter).
```

**这句话直接点明了机制**：子 HWND 尺寸变化后，如果应用不调 `Redraw()`，
flips 就会停止 —— 症状与观察到的完全一致。

### 2.4 托管侧有这个机制，但恢复路径没有

`PlayerSurface.cs:336-342` 在 `WM_SIZE` 里会 debounce 后 `Post` 一个 `Redraw`：

```csharp
Dispatcher.UIThread.Post(() => { try { redrawTarget?.Redraw(); } ... },
                         DispatcherPriority.Background);
```

两点可疑：

1. **`DispatcherPriority.Background` 只在 UI 线程空闲时执行**。
   最大化 + `UpdateLayout()` 期间 UI 线程繁忙，该作业可能被推迟，
   而呈现已经停了 —— 这解释了**间歇性**。
2. 更关键的：**停滞恢复逻辑只做 `Pause → Play`，从不调 `Redraw`**。
   按 2.3 的契约，这种情况下 `Pause→Play` 唤不醒，只有 `Redraw` 才对症。
   这与日志里"轻量恢复被触发但 Δ 仍为 0"完全吻合。

## 三、已做的修复

1. `SyncController.RedrawAll()`（新增）：逐路调用 `session.Redraw()`，幂等且成本极低。
2. 停滞的第一级恢复由 `Pause → Play` 改为 **`Pause → Play → RedrawAll`**。

未改动 `PlayerSurface` 的 `DispatcherPriority.Background`：
改动它会让 resize 期间的 Redraw 更频繁，收益不确定而风险可见，
且第一级恢复补上 Redraw 后，即便 Post 被推迟也终会被触发。

## 四、验证状态（重要）

- **改进前** 6 次 selftest：全通过（0 失败）
- **改进后** 6 次 selftest：全通过，Δpresented 143~183（正常区间）
- ⚠ **复现率远低于最初估计**：合计 12 次未再复现（最初是 3 次中 1 次）。

⇒ **本修复的疗效未经复现验证**。它依据的是内核头文件的明确契约与代码比对，
属于"对症下药"，但不是"验证有效"。

## 五、后续建议

若将来再次出现该失败，按下面顺序取证据：

1. 保留完整日志，确认三段 presented 数值与位置是否仍在推进
   （位置推进 + presented 不动 = 呈现停滞，而非解码停滞）。
2. 看是否出现 `[MainWindow] presented 停滞 … 轻量恢复 Pause→Play→Redraw`：
   - 出现了且随后恢复 → 本次修复**生效**（补一条证据）
   - 出现了但仍不恢复 → 需走第二级（完整会话重建），
     或说明是交换链层面的硬失败，应转向内核
3. 若要人为提高复现率：在最大化/还原之间插入密集 UI 工作
   （连续 `UpdateLayout` + 拖动分隔条），放大 `Background` 作业被推迟的概率。
