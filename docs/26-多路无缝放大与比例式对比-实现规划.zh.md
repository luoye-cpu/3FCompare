## 一、架构决策记录（ADR）

### D1 · 差异计算的坐标域：呈现分辨率 + 可信度标注（**关键决策**）

**背景**：内核回读只能读**呈现帧**，拿不到源分辨率帧；且任何 fit/zoom 都会引入双线性插值。
因此"在源分辨率做真像素差异"在现有内核下**做不到**。

**决策**：
- 差异计算统一在**呈现分辨率**上进行（各路窗口客户区尺寸一致时，像素位置天然对齐）。
- 引入**可信度（Confidence）**概念：由 `dest 尺寸 / 源分辨率` 推算比值 `r`。
  - `r == 1.0` → **真像素级**，差异数值可直接引用；
  - `r` 为整数且 >1 → 整数倍放大，位置仍可对齐但取样已插值，标注为"放大插值"；
  - `r != 1` 且非整数 → 标注为"非像素级，仅供视觉参考"。
- UI 必须在差异面板上显示该状态，**禁止**在非 `r==1` 时对外宣称"像素级"。

**理由**：把"能不能信"变成可计算、可展示的量，而不是含糊承诺；同时不改内核。

**回退**：若后续内核补了"读解码帧"能力，D1 可升级为源分辨率计算，上层接口不变。

**⚠ 待确认（影响 D1 的严格程度）**：需求方所说"像素级比对"是源分辨率 1:1，还是放大后画面像素。
本规划按"呈现分辨率 + 可信度标注"实现，两种诉求都能覆盖。

### D2 · 裁剪：Win32 窗口层，不改内核

**决策**：用 `SetWindowRgn` / `WS_CLIPSIBLINGS` 在窗口层裁剪各路 HWND，绕开内核 pan 的 `max(0,…)` 钳制。
**理由**：三条方案里唯一"不改内核且性能可行"的（回读合成方案 4K 单次约 133 MB，不可行）。

### D3 · 布局模型：保留均匀网格，新增"归一化格表"

**决策**：`GridLayout` 在现有"路数 → 均匀 N×M"之外，增加**归一化格表**（每格 `Rect(0..1)`）与**行列权重**；
现有 int 布局码映射为均匀表，保持向后兼容与既有单测通过。
**理由**：ABC/ABCD 是非等分结构，不是给均匀网格加参数能解决的。归一化表便于窗口缩放时重算。

### D4 · 覆盖层：新建 Topmost 覆盖窗口

**决策**：新建独立的 `LayoutOverlayWindow`（`Topmost=true, ShowActivated=false, ShowInTaskbar=false`），
承载分割线与可拖动交叉点手柄，位置随主窗口同步。
**理由**：airspace 约束。参照 `ThumbnailPopup.cs:28-32`，**不参照** `MagnifierOverlay`。

### D5 · 模式与限流：新增枚举 + 规则表

**决策**：`CompareMode { Ab, Abc, Abcd }`；可用集合由路数决定
（2→{Ab}；3→{Ab,Abc}；4+→{Ab,Abc,Abcd}）；路数变化时自动收敛到合法模式。
**理由**：需求明确，逻辑简单，纯新增。

### D6 · 帧对齐：暂停 + 逐帧步进为前提

**决策**：差异计算入口在播放态给出提示（偏差可达 8 帧），推荐"暂停 → StepFrames 对齐 → 计算"。
**理由**：静置 8s 偏差 138~195 ms（`docs/18 §5`），播放中无同刻帧保证。

#### 3.1 Core 侧：可信度计算

`PixelFidelity.FromRenderTarget(in RenderTargetInfo, int srcW, int srcH)` →
`PixelFidelityResult(Tier, RatioX, RatioY, Description)`，档位：

| 档位 | 判定 | 含义 |
|---|---|---|
| `PixelExact` | 横纵 dest 与 source 相差 ≤ 0.5 px | 1:1，像素是源原值，**可宣称像素级** |
| `IntegerScaled` | 横纵比值为同一整数 n ≥ 2 | 位置可对齐但已插值，**不可宣称像素级** |
| `Interpolated` | 其余（含非整数倍、横纵不一致、**缩小**） | 仅供视觉参考 |
| `Unknown` | 尺寸 ≤ 0 / NaN / Inf | 不可用；Ratio 记 0，杜绝 NaN 污染下游 |

容差取 0.5 px 的理由：dest 由内核从浮点布局**取整**上报，严格 `==1.0` 会把合法 1:1 误判；
而偏差 > 0.5 px 时必然已发生一次采样。
⚠ 因 `dest` 是 zoom 后的矩形，一旦用户 zoom，档位会自动降级为 `Interpolated`/`IntegerScaled`
——这正是 D1 想要的行为。

### 🔴 实验副产品：两条与项目既有代码相关的发现

1. ⚠️ **GDI 抓屏对 flip-model swapchain 不可靠**（实测）。
   用 `GetDC(nullptr)` + `BitBlt` 抓屏时，7 个采样点**只有中心 1 个**能抓到 swapchain 内容，
   其余 6 点读到的是完全不受被抓窗口影响的值。
   原因：flip-model 的内容不进 GDI 重定向表面。
   ⇒ **直接影响 `src/3FCompare/Platform/ScreenFrameCapture.cs`**——
   它是 `MainWindow.Capture.cs` 的 **GDI 抓屏回退方案**。
   若回退路径被触发且目标是 flip-model 视频窗口，**可能产出与画面无关的废图**。
   建议：① 内核区域回读已是首选路径，应确保其优先；② GDI 回退需评估是否应保留。
2. ⚠️ **设置窗口区域后再 `ResizeBuffers` 返回 `DXGI_ERROR_INVALID_CALL`**（`0x887a0001`）。
   虽可能与传参（flags=0）有关、不必然由区域引起，但**若接线后出现"裁剪 + 尺寸变化"组合**，
   需要按此排查：先清区域 → ResizeBuffers → 重设区域。

接线要点：进入裁剪模式后设置，且**每次布局变化都要重设**（缩放/网格切换/分割线拖动/DPI 变化/子 HWND 重建）

## 八、抓屏方案升级：GDI → WGC（2026-09-19 实测）

### 背景

`src/3FCompare/Platform/ScreenFrameCapture.cs` 的注释已自认"实现为 GDI 路径（无 WGC）"，
并承认"BitBlt 屏幕区路径在窗口被遮挡时会抓到遮挡物"。
`docs/26 §3.2` 的实测进一步证明：**GDI 抓屏对 flip-model swapchain 根本抓不到内容**
（7 点只有中心 1 点偶尔命中）。

### WGC 实测结论（探针 `.review_pr/wgc_probe.cpp`）

| 判据 | 结果 |
|---|---|
| 能否捕获 flip-model 内容 | ✅ **能**。无 OSD 干扰的右侧 1/4 区域像素 **100% 精确等于** `ClearRenderTargetView` 的清屏色 |
| 换清屏色是否跟随 | ✅ 红 → 蓝，证明像素确实来自我们的 flip 后缓冲 |
| **被不透明窗口完全遮挡时** | ✅ **结果与无遮挡完全一致** —— 这正是 GDI 回退做不到的 |

⇒ **WGC 能同时解决 GDI 回退的两个缺陷：flip-model 抓不到 + 被遮挡抓错。建议替换。**

### 关键 API 序列（C++/WinRT，便于移植）

```cpp
winrt::init_apartment(apartment_type::multi_threaded);   // MTA 即可，不需 STA/UI 线程
auto interop = winrt::get_activation_factory<GraphicsCaptureItem, IGraphicsCaptureItemInterop>();
interop->CreateForWindow(hwnd, winrt::guid_of<GraphicsCaptureItem>(), winrt::put_abi(item));
auto pool = Direct3D11CaptureFramePool::Create(rtDevice,
    DirectXPixelFormat::B8G8R8A8UIntNormalized, 2, item.Size());
auto session = pool.CreateCaptureSession(item);
session.IsCursorCaptureEnabled(false);
session.IsBorderRequired(false);        // Win11 可关系统黄框；旧系统会抛异常，需 try/catch
session.StartCapture();
auto frame = pool.TryGetNextFrame();    // 轮询即可，不必用 FrameArrived
auto access = frame.Surface().as<IDirect3DDxgiInterfaceAccess>();
access->GetInterface(__uuidof(ID3D11Texture2D), tex.put_void());
```

### 移植到本项目（C#）的四个坑

1. **C++/WinRT 没有 `GraphicsCaptureItem::CreateFromWindow` 投影**，
   必须走 `IGraphicsCaptureItemInterop::CreateForWindow`（`Windows.Graphics.Capture.Interop.h`）。
   C# 侧可直接用 `GraphicsCaptureItem.TryCreateFromWindowId`。
2. **第 1 帧可能是陈旧帧**：实测换色后首次 `StartCapture()` 的第 1 帧仍是旧内容，第 2 帧才正确
   ⇒ 移植时必须**丢弃前 1~2 帧**。
3. **⚠ AOT 约束（本项目特有）**：`3FCompare.csproj` 有 `PublishAot=true`，
   而 WGC 属 WinRT ⇒ 需 CsWinRT 投影并**显式保留** `GraphicsCaptureItem` 与 interop 类型，
   否则可能被 AOT 裁剪。这是替换 GDI 回退的主要成本。
4. 窗口最小化时 WGC 返回黑帧，需按状态处理。

### 意外发现：本机 OSD 会污染捕获帧

探针中心采样点始终不命中，根因是 **RTSS / MSI Afterburner 的 OSD 被注入进 swapchain**
并叠加在帧左上角（`wgc_frame_a.png` 可见 GPU 温度文字压在红色上）。
这与 `MEMORY.md §7` 记录的"第三方 D3D 钩子（RTSSHooks64.dll / nvspcap64.dll）"是同一批东西，
也解释了此前 `clip_probe` 抓屏时左上角稳定出现的异常杂色 `(0,154,78)`。

⇒ **推论：本环境任何"画面采样"类验证（含多路崩溃复现）都可能被 OSD 干扰，
结论要谨慎；涉及画面判据的实验建议关闭 RTSS/Afterburner 后重跑。**

### 9.7 裁剪已接线（2026-09-19，阶段 3.2 落地）

**新增两个文件，未改任何既有逻辑**（`MainWindow.axaml.cs` 只加 4 处单行挂钩）：

| 文件 | 职责 |
|---|---|
| `src/3FCompare/Platform/CompareCropPlanner.cs` | 纯换算：格表 + 子窗口矩形 → 区域（物理像素，窗口相对坐标） |
| `src/3FCompare/MainWindow.CompareCrop.cs` | 接线（partial）：时机、DPI、句柄重建、清除、父窗口失效 |

**换算**：`区域 = 格 - 窗口`（窗口相对坐标；DIP → 物理像素乘 `RenderScaling`，由调用方与 planner 共用同一取整函数）。
放大/平移参数**不直接进入**换算，而是通过"子窗口矩形"进入 —— 内核把放大后的画面锚在窗口左上角，
窗口相对格左上移 `d` 并向右下放大 `d`，格内就露出源画面 `(d … d+格)` 区域：这才是内核 `max(0,·)` 钳制下做不到的平移。

🔴 **能力边界（可证，且比原设想更窄）**：区域是"开孔"语义、不重排内容 ⇒
1. **裁剪不能平移画面**：swapchain 里只有窗口客户区那部分内容（内核放大后的越界部分已被渲染目标裁掉），
   任何区域都露不出窗口之外的画面；
2. **区域必须 == 格**：格要被完整覆盖要求 区域 ⊇ 格，而区域与格同尺寸 ⇒ 只能相等。
   因此"把区域相对格挪一挪来实现平移"必然在格内留洞，planner 从构造上排除了这条路
   （窗口未盖住格时直接拒绝裁剪）。

⇒ 结论：**今天的裁剪"生效但只裁 ≤1px"**。`ArrangeOverride` 把窗口钉成等于格，而 Avalonia 会把排布矩形
**向外取整到物理像素**，实测窗口比格大 ≤1px ⇒ 区域真的被下发（自测实测 3/4 路），把这 ≤1px 外扩裁掉；
"裁出任意对应区域"要真正成立，前提是**子窗口被放大到格之外**（负 Margin / 布局侧放开）。

**为什么没顺手把窗口放大**：那会改掉 §9.3 已验证的对比排版语义；且放大窗口与内核 zoom 会**相乘**
（fit box 对窗口尺寸一次齐次 ⇒ 等效放大变 `z²`），且放大后子窗口重叠，Avalonia 侧 `HitSurfaceAt`
（读 `Bounds` 而非区域）会选错路，必须一并改。这些都需要真机（真实视频）验证后才敢动。

**时机**（`WireCompareCrop`）：进入/退出对比模式（退出**同步** `Clear`，否则窗口被永久裁剪）、
分割参数变化、对比区 `Bounds` 变化（窗口缩放/侧栏折叠/全屏）、宿主 `ScalingChanged`（跨屏 DPI）、
表面重新挂载（子 HWND 重建）。非对比模式且无遗留区域时 `ScheduleCompareCrop` 直接返回 ⇒ 常规使用零成本。
刻意**不**接平移过程：任务要求不引入逐帧热路径，而 pan 在拖动中逐帧变（见 `ApplyCompareCrop` 的注释）。

**命中测试副作用**：区域会同时裁掉命中测试（区域外点击落到父窗口）。今天只裁 ≤1px ⇒ 无影响；
将来窗口被放大后，这一副作用正是"越界部分不抢鼠标"的保证，但 Avalonia 侧命中判定必须改成"按格命中"。

## 十、裁剪：决定性验证与诚实结论（2026-09-19）

### 10.1 `SetWindowRgn` 对 flip-model **生效**（此前最大的未知）

探针 `.review_pr/rgn_vs_flip_probe.cpp`（日志 `rgn_vs_flip_run.log`）。
设计要点：**WGC 捕获父窗口**而非被设区域的子窗口——因为裁剪效果体现在合成结果上
（区域外应露出下层窗口），直接捕获子窗口拿到的可能是未裁剪内容。

| 相位 | 区域外 5 点 | 区域外红覆盖率（底带/右带） |
|---|---|---|
| A 对照（无区域） | 绿 0 / **红 5** | 100% / 100% |
| B 实验（设中间矩形） | **绿 5** / 红 0 | **0% / 0%** |
| C 还原（清除） | 绿 0 / **红 5** | 100% / 100% |

补充证据：
- 边界扫描量出红↔绿交界在 y∈(50,60]、(230,240]、x∈(50,60]、(330,340]，与设定的 60/240/60/340 吻合
- Present **344 次 0 失败** ⇒ 改区域**不需要**重建 swapchain / ResizeBuffers，设备不丢
- 同帧内区域仍红（82%）⇒ 不是整个 swapchain 丢失
- OSD（RTSS/Afterburner，约 190×215px）污染子窗口左上，三相位一致，不影响区域外判据

### 10.2 ⚠ 但"开孔"语义带来一个根本限制

区域是「**窗口开孔**」——**内容不重排**，只决定露出 swapchain 的哪一部分。推论：

1. **裁剪不能实现平移**：swapchain 里没有"窗口之外"的内容，把区域挪到窗口外只会打洞。
2. 因此「格要完整显示」⇒ 必须 **区域 == 格** ⇒ 裁剪量天然只有 Avalonia 排布向外取整产生的 ≤1px 外扩。
3. **要真正"裁出对应区域"（放大后取局部），必须让子窗口放大到格之外**，再由区域/父窗口裁掉越界部分。

自测实测（已接线的现状）：
```

（0 路表示该几何下窗口恰好等于格、无需裁剪；裁掉的是 Avalonia 向外取整的 ≤1px 外扩）
缩放=1.5 / 退出后裁剪已清除 ✓ / 裁剪下发累计 3 次（>0 表示生产路径确实被走到）✓
全部通过 ✓  EXIT=0
```

- 新增 `MainWindow.CompareCrop.cs`（219 行，partial）：接线；`MainWindow.axaml.cs` 仅 4 处挂钩 +16 行

## 十一、无缝放大已实现（2026-09-19）：子窗口放大 + 偏移 + 裁剪

§10.4 的"未做"已完成。**默认关闭**（`z = 1` 等价于现状），入口是 `MainWindow.SetCompareMagnify(z, cropX, cropY)`。

### 11.1 为什么不用内核 zoom（旧方案的两个死穴）

1. `VideoRenderer.cpp:4509-4514` 的 `max(0, ·)` 钳制 ⇒ 不能任意平移；
2. 内核放大恒为双线性插值（`VideoRenderer.cpp:2387`）⇒ 放大后像素是插出来的。

新方案把"放大"交给**子窗口物理尺寸**：窗口 = 格的 `z` 倍 ⇒ 内核 `PrepareScaledVideo`
的目标尺寸就是 destination 尺寸，即**按更高分辨率真实重渲染**（`sourceLimitedToNativeSize_`
默认 false，见 `VideoRenderer.cpp:1738`，所以小源也会被放大铺满）；平移由窗口位置表达
⇒ 不受 `max(0,·)` 影响。只有一个放大源 ⇒ 不存在 z² 叠加。

### 11.2 换算（唯一正确形式）

```
格 = (cx, cy, cw, ch)，z = 放大倍数，u/v = 要露出的画面块左上角（源画面归一化坐标）
窗口尺寸 = 格尺寸 × z
画面适配 = letterbox(窗口)          ← 与内核 CalculateVideoDestination 同构
区域     = fit 内 u/v 处，尺寸 fit/z
窗口位置 = 格左上 − 区域左上
```

- **不打洞的构造性证明**：`W.pos + R = 格左上` ⇒ 区域在容器坐标下恒等于格。
- **区域不出界的构造性证明**：`u ≤ 1−1/z` ⇒ `R.x + R.w ≤ fit.x + fit.w ≤ W.w`。
- **⚠ letterbox 修正不是可选项**：内核是 letterbox 适配（不是拉伸铺满）。格与源画面宽高比
  不同时窗口内有黑边 ⇒ "窗口坐标比例" ≠ "源画面比例"。忽略它时，宽高比不同的两路
  （ABC 模式的 A 与 B/C）会露出**不同的源区间**，"无缝"名不副实。反例见
  `.review_pr/verify_magnify.py` 与 `CompareCropPlannerMagnifyTests`。
- 独立验算脚本：`.review_pr/verify_magnify.py`（含内核三条 `static_assert` 的交叉验证）。

### 11.3 性能闸门（不静默爆显存）

- **z 上限 = 4**：swapchain 面积按 `z²` 增长，z=4 已是 16 倍面积。
- **总像素预算 = 4 × 3840 × 2160 ≈ 33.2 Mpx**（≈ 4 路 4K，正是"4 路 1080p 放大 2 倍"的边界）。
  BGRA8 单缓冲 ≈127 MB，flip-model 常见 2~3 缓冲 ⇒ 约 250~380 MB，加内核中间目标面再留一倍余量。
- 两道闸门**同时**生效，且**在真正分配之前复核**（`BuildCellMagnify` 每次结构性变化都重算 ——
  否则用户拉大一次窗口就能绕过入口处的检查）。超限即拒绝 + 日志 + 状态栏提示。
- 估算上界：各格铺满对比区 ⇒ `Σ(格面积 × z²) ≤ 对比区物理面积 × z²`。

### 11.4 `HitSurfaceAt` 已改为「按格命中」

放大后各路子窗口互相重叠，按 `Bounds` 命中会命中"最后一个覆盖该点的窗口"，与用户看到的格不一致。
放大启用时改走 `HitCompareCellAt`（格互不重叠且铺满对比区，判定唯一确定）；
未启用时**完全走既有路径**，一字未改。

### 11.5 自测（`--comparemodetest <video> 4`，演示模式）

新增五组断言，期望值全部由 `CompareCropPlanner.Magnify` **独立复算**：

```

  对比区=1332x750DIP 缩放=1.5；letterbox 修正生效 4 路（格宽高比 != 源宽高比）；
  OS 窗口尺寸/位置已按 GetWindowRect 核对
```

其中"OS 窗口尺寸/位置"这一条是**必须的**：`NativeControlHost` 把 `ShowInBounds` 排在

### 11.6 已知残差

- 内核在**物理像素**域算 letterbox，本方案在 **DIP** 域算 ⇒ 取整后可能差 <1px；
  与 Avalonia 自身的"排布矩形向外取整（≤1px）"同量级，不构成误差主项。

  与本次改动无关，4 路（验收口径）不受影响。

## 十一、无缝放大：子窗口放大方案（2026-09-19，需求核心落地）

### 11.1 方案：不用内核 zoom，改放大子窗口物理尺寸

| | 旧方案（内核 `SetViewTransform`） | 新方案（放大子窗口） |
|---|---|---|
| 放大源 | 内核对已 fit 画面做**双线性插值** | swapchain 变大 ⇒ **按更高分辨率真实重渲染** |
| 画质 | 有损（插值） | **更优** |
| 平移 | 受 `VideoRenderer.cpp:4509-4514` 的 `max(0,·)` 钳制，**不能任意平移** | 靠 `MoveWindow` 移动子窗口，**不受限制** |

⇒ 恰好绕开了最初发现的内核限制（§1.1 的 pan 钳制）。

### 11.2 🔴 我在换算上给错了公式，被实现者纠正

我最初给的换算（窗口 = 格×z、位置 = 格左上 − crop×z、区域 = (crop×z, 格尺寸)）
**只在"画面铺满窗口"时成立**。

内核是 **letterbox 适配**（`CalculateVideoDestination`，`VideoRenderer.cpp:780-806` + 三条 `static_assert`），
格与画面宽高比不同时窗口内有黑边 ⇒ **"窗口比例" ≠ "源画面比例"**。
忽略这点 ⇒ **ABC 模式里通高的 A 与半高的 B/C 会露出不同的源区间**（对比直接失效）。
实现者构造了反例：8:3 vs 3:8 时，A 露出源 `x∈[0.126,0.875]`，B 只露出 `[0.25,0.75]`。

**正确形式**（`.review_pr/verify_magnify.py` 逐步验算，147 行）：
```
窗口尺寸 = 格尺寸 × z
fit      = letterbox(窗口)          // 与内核同构，已用内核 static_assert 交叉验证
区域     = (fit.x + u·fit.w, fit.y + v·fit.h, fit.w/z, fit.h/z)
窗口位置 = 格左上 − 区域左上
```
不打洞、不出界的性质均有构造性证明，并做了 144 组参数化断言。

**修法**：不再看"变没变"，而是**独立复算期望**——用 `ComputeCells(mode, oldSplit)` 与
`ComputeCells(mode, newSplit)` 各算期望矩形，断言实际 Bounds 从前者迁到后者；
并加两道前提（新旧格表必须真的不同，否则断言退化；拖动前必须等于旧期望）。
抽出 `ExpectedBounds` / `BoundsClose` 供最强那条断言复用同一换算。

**反向验证**（临时停掉 `OnCompareSplitChanged` 里的 `ApplyCompareLayout()`）：
```

4 路: 失败 ✗ Abcd 第 0 路 Bounds 664,373.33 ≠ 期望 930.4,260.5       EXIT=1
```

**主 Agent 独立核验**：
```

4 路: 分割驱动重排 ✓ 664.0x373.3 → 930.7x260.7（与 ComputeCells 复算期望一致） 全部通过 ✓ EXIT=0
```

## 十六、4 路播放崩溃归因（2026-09-19）

### 16.1 实验设计：同批次交错（关键方法学）

跨批次比较无效（机器负载会漂移），故每轮内 **4K→1080p→720p→2路 交替**运行，共 24 次/批。

### 16.2 结果

| 批次 1：负载与路数 | 崩溃率 | 崩溃均时 |
|---|---|---|
| 4 路 4K60 | **6/6 (100%)** | 11.2s |
| 4 路 1080p60（1/4 像素） | **6/6 (100%)** | 11.2s |
| 4 路 720p60（1/9 像素） | 5/6 (83%) | 18.7s |
| 2 路 4K60 | **1/6 (17%)** | 19.3s |

统计：4 路 vs 2 路 **Fisher p=0.0008**；4K vs 1080p vs 720p **p=1.00（无差异）**。

| 批次 2：漂移校正 Seek | Seek 次数 | 崩溃率 |
|---|---|---|
| 正常 | 1 次/秒 | 6/8 (75%) |
| `_3FC_DRIFT=off` | **0 次** | 7/8 (88%) |
| `_3FC_DRIFT=aggressive` | 27~159 次 | 7/8 (88%) |

两两 **p=1.00**。

### 16.3 🔴 结论：我原先的假设被证伪

我此前怀疑「解码跟不上 ⇒ 并发漂移校正 Seek ⇒ AV」（§13.4）。**该假设不成立**，三重证据：
1. 解码量差 **9 倍**（720p vs 4K），崩溃率无差异（p=1.00）
2. **完全禁用漂移校正 Seek 后崩溃率反而略升**（88% vs 75%，p=1.0）；把 Seek 加密 100 倍也不变
3. 崩溃前快照显示四路位置差 **≤6ms**（远低于半帧 8.33ms 阈值）⇒ **根本没有待触发的校正**

**真正的主因是路数，不是负载**：4 路 100% vs 2 路 17%（p=0.0008）。
与 `MEMORY.md §7` 的既有结论一致——**跨渲染器并发 Present 撞上交换链改写**。
佐证：转储中两线程同处 `PresentCurrentFrame +0x7E → dxgi.dll+0x19530`。

### 16.4 ⚠ 第三方钩子（RTSS/Afterburner）本环境无法排除

已确认 `RTSSHooks64.dll` / `nvspcap64.dll` **确实注入本进程**。
反汇编 `dxgi.dll+0x19530`：该处是**正常函数序言**（`48 89 5C 24 10 ...`，前有 8 字节 `CC` 填充），
**不是钩子跳板** ⇒ AV 是 DXGI 内部解引用被破坏的指针，而非"跳进钩子"。

但这**不能排除**"钩子与多路 Present 交互"：串行化实验也会顺带串行化钩子的 overlay 工作，二者无法区分。
