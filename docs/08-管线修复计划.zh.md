## 1. 阶段一:P0 竞态与泄漏(必须最先修)

### 1.1 OpenFiles 静默丢文件导致自动播放卡死(P0)

- 位置:`PlaybackCoordinator.OpenFiles`(L53-109)。
- 现状:`_surfaceAt` 返回 null 时 `continue`,该文件的 `_pendingAutoPlay` 配额永远不释放;`RecoverFromFailedCoreAsync` 依赖 `onAllOpened` 回调执行 SeekTo+Play,命中即整体卡死。
- 修复:
  - [ ] 循环开始前先收集所有可用 surface;不可用的文件**不消耗** `_pendingAutoPlay` 配额与回调队列。
  - [ ] `count <= 0`(9 路已满)时:不调用 `onAllOpened`(会话未就绪不得 Play),改为抛出带文件清单的异常或触发 `StateChanged` + 状态栏提示"已达 9 路上限"。
  - [ ] 每个 `_ = OpenSlotAsync(...)` 分支(含异常分支)保证 pending 计数收支平衡:开多少路,`_pendingAutoPlay` 就记多少。
- 验证:单测——模拟 9 路已满后再 OpenFiles(autoPlay=true),断言回调不触发且 UI 收到上限提示;模拟 surface 为 null 的注入场景,断言不卡死。

### 1.2 关闭窗口时进行中的打开泄漏原生会话(P0)

- 位置:`PlaybackCoordinator.OpenFiles`(不检查 `_closed`)+ `MainWindow.OnClosing`(L1649)。
- 现状:`Close()` 只置标志;循环继续 `CreateSession + AddSlot`,新 slot 加入已 Clear 的 `_sync` 后无人 Dispose,`FFF3FP_Destroy` 不执行。
- 修复:
  - [ ] `OpenFiles` 循环内每轮检查 `_closed`,为 true 时跳出且不创建会话。
  - [ ] `OpenSlotAsync` 完成时若 `_closed` 为 true(打开是在 Close 之前发起的),对该 session 补一次 `Dispose`。
  - [ ] `PlaybackCoordinator.Close()` 增加收尾:遍历 `_sync.Slots` 对尚未关闭的会话统一 Dispose(幂等,依赖 `IPlayerSession.Dispose` 已防重入)。
- 验证:打开大文件(OpenAsync 未返回)期间立即关窗,用日志确认 `FFF3FP_Destroy` 被调用;重复关窗不抛异常。

## 2. 阶段二:同步与恢复语义修正(P1)

### 2.1 StepFrames 的 generation 判定失效,帧步进恒退化为全量 Seek(P1)

- 位置:`SyncController.StepFrames`(L184-198)。
- 现状:`StepFrame` 入队后立即读快照,`TimelineGeneration`(仅在 seek 成功后递增)与 `FrameIndex` 大概率未变 → `stepApplied=false` 恒成立 → 每次帧步进都走 `av_seek_frame` + 解码器 flush。
- 修复(按优先级):
  - [ ] 方案 A(首选):短等待后复测——读不到变化时 `Task.Delay(30~50ms)` 再读一次快照再判定;若仍无变化才走时间换算回退。
  - [ ] 方案 B:原生层为 `StepFrame` 成功入队也递增 `TimelineGeneration`(需改 FFF.Native,与原生负责人确认)。
  - [ ] 附带:加一次性诊断日志(stepApplied 实际命中概率),上线一周后依据数据删除回退分支或确认保留。
- 验证:用 `testmedia/small.mp4` 逐帧步进 10 次,日志确认走 StepFrame 路径而非 Seek;`SyncControllerIntegrationTests` 增加对应用例。

### 2.2 停滞检测条件恒真 + 暂停污染恢复状态(P1)

- 位置:`MainWindow.PollSnapshotsCoreAsync`(L537-539)。
- 现状:`shouldPlay` 对 Ready/Paused 恒为 true(死逻辑);暂停期间 `_stalledPolls` 照常累加,恢复播放瞬间易触发无谓的 Pause→Play,并把 `_stalledAfterLightRecovery` 置 true,导致下一次真实停滞被跳级为全会话重建。
- 修复:
  - [ ] 删除 `shouldPlay`,停滞计数仅在 `m.State == PlayerState.Playing && _isPlaying` 时累加。
  - [ ] 状态离开 Playing(暂停/Seek/恢复)时重置 `_stalledPolls` 与 `_stalledAfterLightRecovery`。
- 验证:暂停 5 秒后恢复播放,日志确认未触发轻量恢复;人为制造 presented 停滞(断点演示模式),确认两级恢复仍生效。

### 2.3 EstimateFps 的 PTS 分支为死代码,回退帧率固定 24(P1)

- 位置:`SyncController.EstimateFps`(L267-277)。
- 现状:两个分支都返回 24.0,中间 if 无作用;快照 `FrameRate==0` 时 30/60fps 内容步长全错。
- 修复:
  - [ ] 短期:删除无效分支,`FrameRate<=0` 时直接回退 24 并打一次警告日志。
  - [ ] 中期:快照新增 `FrameRate` 缺失时的兜底来源——打开完成后用 `ReadMediaInfo().FrameRate` 回填缓存,`EstimateFps` 增加可选的 mediaInfo 参数。
- 验证:用 60fps 测试媒体(如 `test_4k_60M.mp4`)执行 ±1 秒/±N 帧步进,断言落点正确。

## 4. 阶段四:体验级优化(依赖评估)

- 任务:
