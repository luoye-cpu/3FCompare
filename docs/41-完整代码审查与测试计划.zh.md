### 13.7 方法论沉淀

1. **"找不到触发链路"不等于"无法反向验证"**：R3 无法构造"订阅者没被调用"的真实场景，但可以用
   **变异判据期望值**来证明断言有牙齿（摘掉修复 ⇒ 判红）。这比"摘掉产品代码修复"更容易构造，
   且直接回答了"这条断言会不会恒绿"这个真正要害的问题。
2. **失效路径的处置必须和成功路径一样严谨**：R1 的回收线程是为了"兜底"而加的，但它做的事
   （对死目标 `Close`）恰恰是已知会永久挂死的操作 ⇒ **兜底代码自身也要过一遍死锁审查**。
3. **不对称代价要显式写成判据**：误判"死"= 泄漏，误判"活"= 冻死 ⇒ 一律选前者。但要注意
   同一个判定函数可能同时服务"复用"与"释放"两条语义相反的调用（见 🟠4 的偏离）。
4. **改了构建/门禁脚本后，验证必须显式带 `-c Release`**（§13.4 的坑）。
5. **偶发假红比假绿更早暴露**（因为它会拦住你）：本轮 1/7 的浮条 flake 是连跑才捕获到的；
   单点"跑一次通过"不足以证明自测稳定。

### 16.3 🔴 真机打包暴露的真实缺陷：自测污染产物目录

跑 `-Mode full` 真打包才发现：`Assert-Package` 通过之后，包内自测又真跑了一次 exe，
于是产生 **6 项不属于发货内容**的副产物：

- `logs\`（内核/组件日志，**含本机绝对路径**，属信息泄露）
- `FFF.Native.dll`、`3FC.WgcCapture.dll`、`libSkiaSharp.dll`、`libHarfBuzzSharp.dll`
  —— 这四个是**运行时解压产物**（内核 DLL 是 `EmbeddedResource`；实测 7z 内 17 项不含它们）

后果：产物目录 22 项 ≠ 清单 16 项，`-ChecksOnly` 复检判红；若顺序变动日志还可能被收进包。
（7z 在自测之前生成，故压缩包本身是干净的。）

**修法**：新增 `Remove-ExtraneousArtifacts`，自测后把目录收敛回 `SHA256SUMS` 列出的发货清单，
再校验"目录 == 清单 == 压缩包内容"。
⚠ **不手工列举要删的文件名**（运行时解压清单随 Avalonia/内核版本变化，列举必然漏）
⇒ 以 SHA256SUMS 为唯一真源做差集。

### 16.4 ⚠ 我在验证时引入的严重 bug（已修）

为直接调用新函数，我给 `Remove-ExtraneousArtifacts` 传了**相对路径**，
而它用 `$f.FullName.Substring($Dir.Length)` 算相对路径 ⇒ 按相对串长度切绝对 `FullName`
⇒ **把整个产物目录清空了**（`re-v0.2.5-x64-full\3FCompare.exe` 这样的错切路径）。

修：新增 `Resolve-Dir`（`[IO.Path]::GetFullPath(...).TrimEnd('\')`），
`New-Sha256Manifest` / `Test-Sha256Manifest` / `Remove-ExtraneousArtifacts` 三处统一规范化。
反向验证（相对路径夹具）：先建清单 → 再加 `junk.tmp` 与 `logs\` → 收敛后
**只删这两类、保留 keep1/keep2**，清单错误 3 → 0。
