## 二、目标模式体系（核心设计）

### 设计原则：不是所有路数都做"可拖动分割"

拖动点在 4 路以上会指数级复杂（ICAT 单屏也只到 2 路、分屏到 4 路），故分三层：

| 模式 | 支持路数 | 交互 | 对标 |
|---|---|---|---|
| **叠加模式**（新增） | **2 路** | 两路叠加，拖动滑块揭示 / 覆盖 | **ICAT Single Screen** |
| **分屏模式** | 2~4 路 | 拖动交叉点调整各画面占比 | **ICAT Split Screen**（+ 超出部分的增强） |
| **网格模式** | **2~9 路** | 均匀网格 + 预设（2x1/1x2/3x1/1x3/2x2/3x2/2x3/3x3） | 主流多画面播放器 |

⇒ 这样 **2~9 路全覆盖**，且交互复杂度可控。

### 2.1 叠加模式（ICAT Single Screen，本次最大新增）

**为什么以前做不到**：两路视频都是真实子 HWND，无法像图像那样在托管层叠加合成 ⇒ `AbSliderView` 只能画占位渐变。

**现在可行的关键**：`SetWindowRgn` 已验证对 flip-model 生效（`docs/26 §10.1`，区域外 5/5 露出下层）。

**实现方案**：

```
A 路窗口：铺满对比区，Z 序在下，不设区域（完整显示）
B 路窗口：铺满对比区，Z 序在上，SetWindowRgn 裁出 [0, splitX]（仅左侧可见）
滑块：位于 splitX，可水平拖动；重置 B 的区域为 [0, newSplitX]
```

要点：
- 两个窗口**都铺满**，靠 Z 序 + 区域决定谁露出来 ⇒ 切换方向只需改区域（左右 / 上下）
- 支持**水平滑块**（左右揭示）与**垂直滑块**（上下揭示）两种
- 两路播放仍由 `SyncController` 同步（与分屏模式共用）
- 退出时**必须清除** B 的区域，否则窗口被永久裁剪

风险：
- 两路窗口 Z 序需稳定（Avalonia 里用 `ZIndex` 或子窗口顺序控制）
- `SetWindowRgn` 区域是**绝对像素**，DPI / 尺寸变化需重设（已有 `WindowRegionClipper` + 重设时机）
- 上层窗口会**吞掉鼠标**（区域外点击落到下层，这实际是想要的行为）

### 2.2 分屏模式扩展到 9 路

现状 `CompareLayout` 只到 Abcd(4)。扩展策略：
- **2~4 路**：保留可拖动交叉点（Ab 竖线 / Abc 十字 / Abcd 十字）
- **5~9 路**：退化为**均匀网格**（沿用 `GridLayout`），不再提供拖动点
  - 理由：5 路以上的拖动点在视觉与实现上都不可控，且 `GridLayout` 已有 5~9 路预设

> **⚠ 口径更正（2026-09-19 实施时核对）**
> 1. **`GridLayout` 没有"5~9 路预设表"**：实为 `ComputeGrid` 的自动 switch（`≤1`→1x1、`2`→2x1、`3`→3x1、`4`→2x2、`5`/`6`→3x2、`≥7`→3x3）。
>    用户可选的网格预设只有 **`2x1 / 2x2 / 3x3 / auto`**（`GridLayout.OverrideOf`），本规划 §2.2 提到的 `1x2 / 3x1 / 1x3 / 2x3 / 3x2` **不存在**。
> 2. **分屏在 ≥5 路时的实际行为：保留既有能力**（`CoerceMode` 收敛到 `Abcd`，**只显示前 4 路**，状态栏提示"显示前 N / 共 M 路"），
>    **不**改成"退化成网格全显示"。理由：§七 验收标准要求"现有特色功能全部保留"，而"9 路里挑前 4 路做十字对比"是既有能力。
>    ⇒ **网格模式**才是"2~9 路全部显示"的入口，两种模式职责不同，不互相替代。

### 2.3 模式切换入口

现状只有 `C` 键循环，发现性差。提议：
- 主区右上角或传输栏加**模式切换控件**（叠加 / 分屏 / 网格 + 路数指示）
- 保留 `C` 键快捷循环
- 菜单「视图」下同步列出

## 三、深浅主题切换

### 现状约束

- `Themes\ThemeResources.cs` **代码装配** ResourceDictionary（历史原因：.NET 11 预览期 App XAML 异常）
- 键名如 `BgBrush` / `PanelBrush` / `AccentBrush` / `TextMutedBrush` / `MarkerABrush`，且会**自动派生 `xxxBrush`**

### 改造方案

1. **令牌化**：把所有颜色抽象为**语义令牌**（`Surface.Background` / `Text.Primary` / `Accent.Default` / `Marker.A` / `Marker.B` …），
   每个令牌定义 **Light / Dark 两组值。
2. **切换机制（推荐）**：仍走 Avalonia 的 `RequestedThemeVariant`（`Dark` / `Light`），
   把两套值分别放进 `ThemeDictionaries`，控件用 `DynamicResource` 引用 ⇒ 切换时自动刷新，无需重建窗口。
   - 若 `ThemeDictionaries` 在代码装配下不可行，退路：切换时**重建 ResourceDictionary 并触发刷新**（需实测哪种可行）。

### 需要同步处理的点

- 自绘控件（`TimelineView` / `MagnifierOverlay` / `ProbePanel` / `DiffOverlayView` 等）若**硬编码了颜色**，必须改为取令牌。
  ⇒ 实施前需先审计所有硬编码颜色。
- 视频区本身是子 HWND，不参与主题；但分割线、手柄、覆盖层要跟随。
- 强调色是否也随主题微调（浅色下金黄可能太亮，需降饱和）。

#### 🔴 关键认知修正：Z 序方案被实测推翻

原方案（§2.1）是「A 不设区域、B 裁 `[0,split]`、靠 Z 序让 B 盖住 A」。**实测不成立**：

- Avalonia 给每个 `NativeControlHost` 子窗口**又套了一层容器 HWND**，两路视频窗口**父窗口不同**，是顶层窗口下的**兄弟**；
- `SetWindowPos(子窗口)` 只在容器内排序，对两路的相对可见性**毫无作用**；之前"看着对"只是因为 B 的容器恰好晚创建——**偶然，容器重建就会整块盖住**。

#### ✅ 采用方案：两路互补裁剪，彻底不依赖 Z 序

```
B（第 1 路）：裁 [0, split]      ← 靠近原点的一侧
A（第 0 路）：裁 [split, 1]      ← 另一侧
并集 = 整窗、互不重叠 ⇒ 可见结果与 Z 序无关
```

- 边界：分界点钳进 `[1, span-1]`（`Rect32` 要求宽高 >0）。`split≥1` 时**不能对 A 用 `Clear`**（A 整窗可见会盖住 B，又把可见性交回 Z 序）。
- 退出**同步** `ClearCompareCrop`（延后一拍 + 异常路径 ⇒ 窗口被永久裁剪）。
- `HitSurfaceAt` 加叠加分支：两路铺满时通用循环会恒选 A，与所见不符。
- 入口：快捷键 **`S`**（裸键未占用，语义 Single Screen）；垂直揭示为内部开关，由自测覆盖。
- `Platform/WindowZOrder.cs` 曾为 Z 序方案新建，方案变更后零引用 ⇒ **已删除**。

### 阶段 3（模式体系统一 2~9 路）· 2026-09-19 完成

**调研先行的两个结论**（决定了改动量很小）：
1. 5~9 路的均匀网格**本来就能用**（`GridLayout.ComputeGrid` 自动 switch + `CompareGridView` 均匀路径），路数上限本就是 9（`CompareGridView.cs:106`）。
2. 真缺口只有**「没有模式切换入口」**——此前只能靠 `C` 键盲循环，且没有任何地方告诉用户有"叠加"这回事。

**落点**：`MainWindow.axaml`（「视图」菜单新增「对比模式」子菜单，仿既有 `Menu_GridLayout` 的 `Click` + `Tag` 写法）、`MainWindow.axaml.cs`（`OnCompareModePreset` / `EnterSplitMode` / `EnterGridMode` / `RefreshCompareModeChecks` + `V`/`G` 键）、`Localization/LanguageManager.cs`（4 键中英）、`MainWindow.SelfTest.cs`（9 路入口验收）、`tests/3FCompare.Core.Tests/ModeSystemTests.cs`（新增 65 例）。

| 入口 | Tag | 键 | 行为 |
|---|---|---|---|
| 叠加 | `overlay` | `S` | 进叠加模式（需 ≥2 路） |
| 分屏 | `split` | `V` | `CoerceMode(Abcd, count)` ⇒ 2→AB / 3→ABC / ≥4→ABCD；已是该模式**不重进**（保住用户拖好的分割位置） |
| 网格 | `grid` | `G` | 退出叠加 + 退出对比模式 ⇒ 2~9 路**全部**恢复显示 |

**⭐ 一个非显然的坑（值得记住）**：Avalonia 12 的 `DefaultMenuInteractionHandler.Click` 是「**先翻转 `IsChecked`、后 `RaiseClick()`**」。
因此勾选刷新必须在**两处**做：父菜单 `SubmenuOpened` **和**点击处理末尾各刷一次——只靠开菜单刷新，勾选会与实际状态相反直到下次展开。
另外 `ToggleType="CheckBox"` 才画得出勾（默认 `ToggleType=None` 无勾）。

|---|---|
| 分屏模式 2~4 路可拖分割线 | 网格对比态的内部线：竖线 `列数-1` 条 + 横线 `行数-1` 条（3×3 即 4 条），整条可抓 |
| 网格模式 2~9 路全部显示 | 网格对比态的**基准**：一路一格、全部显示且全部启用（"只显示前 4 路"随之取消） |
| 5~9 路"不提供拖动点" | 不再是限制：5~9 路同样有 3~4 条可拖线，几何由 `Core/Display/GridPartition` 的权重给出 |
| §2.2 提过的 1x2 / 3x1 / 1x3 / 2x3 / 3x2 预设"不存在" | 不必再加进预设菜单：它们变成 `C` 键的朝向候选（`ShapesFor`），1×2 就是旧 AbVertical |
| 叠加模式（§2.1）| **未动**：`S` 仍是两路铺满 + 互补半区；退出后落回网格对比态而不是退回均匀网格 |

随合并取消的能力只有一项：`ABC「左大图 + 右侧上下两小图」`——它是 T 形交界的非整线形状，
整线网格表达不出来，这一点在动手前已向用户明示并获准。

入口与键位的最终口径：**菜单两项**（网格对比 / 左右拉动），**`G` 是网格对比的开关**（再按回无分割线的
均匀网格，这是唯一的退出口——旧实现把退出藏在"C 循环到末项"里），`V` 为同义进入，`C` 只换朝向。
未进入任何对比态时菜单**两处都不打勾**（均匀网格是真实存在的中性态）。

`docs/47` 里"ABC 三列受 `SplitParams` 两个自由度硬约束、成本显著高于其余各项"这条判断，
在新模型下不再是问题：`GridPartition` 用变长权重取代两自由度，三列/三行/3×3 同源。
