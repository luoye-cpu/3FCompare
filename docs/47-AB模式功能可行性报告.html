一、结论摘要

核心结论：没有任何功能「被删除」，缺的是三类「从未完成」

对照设计笔记的 10 项需求逐条核验代码与提交历史后，结论是：笔记里描述的功能在 Git 历史中从未真正存在过，因此不存在「某次提交回退导致消失」的情形。它们分属三种状态：

  • 已实现（5 项） —— AB 拖分割线、ABC「左大图+右侧上下」、ABCD 四宫格、无缝放大的内核与排版层、「放大一致」（澄清语义后确认，零成本）；
  • 有内核无入口（1 项） —— 多路同步「无缝放大」内核逻辑完整且经实测有效，但生产 UI 完全没有触发路径，只有自测 --magnifybench 会调用；
  • 从未实现（4 项） —— AB 上下分、A/B 下拉框选源、ABC 三列、按路数自动进模式。

最重要的判断：本次工作的性质不是「找回丢失的代码」，而是在既有骨架上接线与扩展。其中「无缝放大」只需补 UI 触发即可获得完整能力，性价比最高；而「ABC 三列」受 SplitParams 自由度硬约束，成本显著高于其余各项。

架构定位（已按你的说明确定）：该能力作为独立于传统模式的额外模式实现 —— 不扩展 CompareMode 枚举，改用并列的独立模式开关。这贴合「与传统模式不一样」的定位，且顺带规避了「序数前缀静默收敛」与「新增枚举无编译警告」两个陷阱，现有模式体系单测亦完全不受影响（详见 4.8）。

三、十条关键发现

1
无缝放大的内核已完成并经实测，缺的只是 UI 触发 —— 这是最高性价比的一项
docs/26:786-796 实测：z=1/2/3/4 对应 2.2 / 8.9 / 20.1 / 35.7 Mpx，显存 +10 / +146 / +169 MB，帧率稳在 59.5~60 fps；最大化 z=4 达 100.1 Mpx / +594 MB / 仍 58.1 fps。也就是说放大能力本身是可用且已验证的，本项工作纯属「接线」。
2
最大雷区：改窗口区域后再 ResizeBuffers 会返回 DXGI_ERROR_INVALID_CALL
docs/26:244-246 实测记录，建议顺序为「先清区域 → ResizeBuffers → 重设区域」。而滚轮放大同时改子窗口尺寸（触发 swapchain resize）又改裁剪区域，正好命中该组合。这是本报告中唯一被实测标记为失败的操作序列，必须专项验证。
3
好消息：CompareMode 从未被持久化 ⇒ 新增枚举值不破坏任何已保存会话/设置
SessionSnapshot.cs 全文件无 CompareMode / SplitParams（只有 GridLayout 均匀网格码）；AppSettings.cs 同样没有。未知值兜底在 CoerceMode(CompareLayout.cs:120-125)。⇒ 加 AbVertical = 3 无需任何迁移代码。
4
陷阱：CoerceMode 用「序数前缀」判定，新增枚举会被静默收敛
MaxAvailableOrdinal(CompareLayout.cs:196-202) + CoerceMode(:120-125) 的规则是 (int)mode >= 0 && (int)mode <= max，注释 :107-108 明确「可用集合必为前缀是该规则的固有性质」。若 AbVertical=3 > Abcd=2，则 3 路下 max=1，它会被收敛成 Abc。必须改为集合判定。
5
C# 编译器不会警告新增枚举值 —— 无编译期保护
三处 switch 表达式（ComputeCells:151、HandleAxis:175、HandlePosition:183）都带 _ => 兜底，新增枚举值会静默落进 default（C# 仅对无兜底且非穷尽报 CS8509）。⇒ 漏改分支不会报错，只会表现为「竖分画成了左右分」。必须靠单测覆盖。
6
AB 交换 A/B 存在「格置换」最小改动路径，无需动路↔格映射
不动 surface↔slot，只在 ApplyCompareLayout(axaml.cs:640-662) 产出格表时交换 cells[0]/cells[1] 的矩形即可实现「左右互换」。改动集中在 MainWindow 一处，不触碰 CompareGridView / PlaybackCoordinator / 命中测试。
7
覆盖窗口上放 ComboBox 理论可行，但「未实测」是明确残留项
docs/30:108/135/186-190（浮条倍速/色彩下拉「本轮未实测」）、docs/31:361-363（「理论上不受 WS_EX_NOACTIVATE 影响但未实测」）、docs/42:63 仍为待做。不过 FloatingTransportWindow 已有 ComboBox 先例，不是从零开始，属「需补实测」而非「需攻关」。
8
自动进模式可复用 onAllOpened 时机，但会重置用户已拖好的分割线
现为 OpenFiles(paths, autoPlay:false, onAllOpened: TryAutosave)(axaml.cs:438)，改成 () => { TryAutosave(); EnterSplitMode(); } 即可——此刻路数已准确（OpenFiles 是 async void，直接在 OpenPaths 末尾调会拿到旧的路数）。坑：已有 2 路再拖 1 路时 target 由 Ab 变 Abc，会命中 EnterCompareMode:601 的 _compareSplit = SplitParams.Default(...)，把用户拖好的分割位置重置。
9
加 bool 设置项不必动 Normalize，但 SettingsWindow 有「两处深拷贝」陷阱
AppSettings.cs:124-126(TimelineCollapsed) 与 :131-138(FloatingTransport) 注释均写明「bool 无越界值，故不必进 Normalize」⇒ 也不必动 CurrentVersion。但 SettingsWindow.cs 有两处深拷贝（:94 与 :340），docs/30:120 记录「漏一处则『确认设置』会静默写回默认值」。
10
SetWindowRgn × flip-model 已不再「未知」，但高频改区域仍未实测
记忆修正：该项已于 2026-09-19 实测生效（docs/26:476-492，探针 rgn_vs_flip_probe，区域外 5/5 露出下层，Present 344 次 0 失败，改区域不需重建 swapchain），不再是「高风险未知面」。但「滚轮连续缩放 → 每格高频改区域」无专项实测；既有设计约束反而是 docs/26:249「不要逐帧调用」与 :450「刻意不接平移过程」。

四、分功能可行性与改动方案

4.1

AB 竖分（AbVertical）

可行待定 A/B第三期 · ~40 行
使 AB 支持上下分栏。框架层（SplitAxis.Y、CursorY、覆盖层分支）全部就绪，缺的只是把「竖」这个概念接进去。有两条路径，推荐 A。
路径抉择
A（推荐）· 加枚举值 AbVertical —— 复用 ComputeCells，符合单一实现原则；代价是必须把 CoerceMode 改为集合判定（发现 4），并手动补单测（现有测试不覆盖新增枚举值）。
B · 在额外模式内部自持分割轴 —— 不动 CompareMode，隔离性好；代价是格表逻辑出现两份实现，正是项目元发现 1 要避免的形态。
下方「必须改 / 建议改 / 无需改」清单按路径 A列出。
必须改
① ComputeCells(CompareLayout.cs:151) 加分支 —— 否则落进 _ => 被静默画成左右分；② HandleAxis(:175) 返回 SplitAxis.Y；③ CoerceMode/MaxAvailableOrdinal(:120/196) 改为集合判定（见发现 4，否则 3 路下会被收敛）；④ EnterSplitMode(axaml.cs:870) 硬编码 CoerceMode(CompareMode.Abcd, count) 取「最大模式」，若新枚举序数最大会被解析成竖分，必须改。
建议改
HandlePosition(:183) 补 (0.5, y)，否则手柄用残留的 X 定位；NotifyCompareMode(axaml.cs:830-835) 补显示名，否则显示成「AB」。
无需改
CellCount（同为 2 格，_ => 2 天然正确）；LayoutOverlayWindow 零改动——ApplyDrag(:405-410) 与 CursorFor(:432-437) 已按 SplitAxis 分支，SplitAxis.Y 与 CursorY(:145) 已存在，只要 Core 改对即可（其 Render 与 IsOnHandle 全走 Core 的 ComputeCells/HandlePosition）。
测试影响
ModeSystemTests.cs / CompareLayoutTests.cs 无 Enum.GetValues式遍历，全为显式 InlineData ⇒ 只加枚举值不改 AvailableModes 时测试全绿（即不覆盖，需手动补例）。若把竖分加入 2 路集合，ModeSystemTests:20 与 CompareLayoutTests:18（2 路 = {Ab}）会红；ModeSystemTests:81 把 (CompareMode)3 当脏值测收敛，语义需重审。自测 RunCompareModeTestAsync(SelfTest.cs:2169-2178) 遍历 AvailableModes，数据驱动，自动覆盖。
4.2

滚轮触发多路同步无缝放大

可行中风险第二期 · ~100 行
把滚轮从「单路 _viewZoom」分流到「多路 SetCompareMagnify」，并实现光标锚点缩放与拖动平移。这是笔记的核心诉求，也是唯一需要触碰高风险路径的功能。
分流点
OnSurfaceWheel(axaml.cs:1250-1255) 现为 _viewZoom = Clamp(_viewZoom*factor, 1f, 32f); ApplyViewTransform();。_compareActive 为真时改走 SetCompareMagnify。当前 zoom 可读 Grid.CellMagnify?.Zoom（CompareGridView.cs:192 public getter）；建议仿 CompareCrop.cs:98 增加 internal double CompareZoom => _compareZoom;。
锚点换算
现成可复用：MapPointerToVideoPixel(surface, session, local)(axaml.cs:1844) → VideoPixelMap.MapToSource(:1867)，已处理 letterbox（落在黑边返回 null，:1865），无 RT 信息时走 MapFallback(:1858)。得到源像素后除以 media.VideoWidth/Height 即归一化 u/v。命中哪一路用 HitCompareCellAt(:1195-1212)，且 HitSurfaceAt(:1173) 在放大态已自动切到它。
需新写：以光标为锚点的公式 newCropX = u - (u - cropX)/z，再钳到 [0, MaxCropFraction(z)](CompareCropPlanner.cs:180)。
平移
不能复用现有 OnSurfacePress/OnSurfaceMove（:1268/:1284-1299）——它们改 _viewPanX/Y 走内核 SetViewTransform。CompareCrop.cs:344-348 注释明确「平移/裁剪参数本身是显式设置一次的量，不是拖动量」。⇒ 应改 _compareCropX/Y 后松手时提交一次 SetCompareMagnify，不逐帧。
退出
SetCompareMagnify 中 zoom <= 1.0 会 ResetCompareMagnify() 且返回 true（CompareCrop.cs:124-128）；滚轮缩到底显式传 1.0 即可。退出对比模式时 ExitCompareMode(axaml.cs:718) 已复位。
闸门刷屏
两道闸门 MaxCompareZoom=4.0(:65)、CompareMagnifyPixelBudget≈66.4 Mpx(:80)。拒绝走 RejectCompareMagnify(:278-285) 写状态栏。去重字段 _compareMagnifyBudgetNote(:95) 只服务于 BuildCellMagnify 的布局复核（:210-217，指纹 {zoom}@{Mpx}），对「滚轮每格 zoom 都变」无效 ⇒ 会刷屏，需新增针对滚轮的去重。
落地延迟
HwndMatchesPixels(:501-507) + 重试上限 8 拍（:476-490）。每次 SetCompareMagnify 把计数归零(:153) ⇒ 不会累积到放弃；ScheduleCompareCrop 有 _compareCropScheduled 合并(:327) ⇒ 同一轮只排一个任务。滚轮每格仍需 1~2 拍落地。
自测缺口
现有覆盖：闸门( SelfTest.cs:3094-3119 )、放大五项断言(:3142-3268，含 letterbox 修正)、复位(:3290-3306)、--magnifybench(:2394-2543)。需补：① 滚轮→SetCompareMagnify 链路（现有滚轮断言 :1446-1468 只验 _viewZoom）；② 光标→cropX/cropY 锚点换算；③ 连续滚轮每格收敛（Bounds/HWND/区域三一致）；④ 放大态拖动平移；⑤ 拒绝提示不刷屏。

ABC 三列

可行但重中风险第三期 · 需扩展 SplitParams
受硬约束，成本高于其表面复杂度。两种方案代价接近，都绕不开扩展 SplitParams。
硬约束
SplitParams(double X, double Y)(CompareLayout.cs:37) 只有 2 个自由度，三列需两条竖分割线（x1、x2）。

可行低风险第一期 · ~5 行（+设置项 15 行）

方案

4.7

「分辨率一致」= 放大一致

已澄清 · 零成本无需改代码
你澄清的语义是「放大倍数一致」——即各路同步放大，而不是「像素级对齐 / 同尺寸源区域」。该语义现有实现已完全满足，本项不产生任何工作量。
为什么已满足
两个机制叠加即可保证：① 所有路共用同一个 zoom / cropX / cropY —— CompareCrop.cs:103-105 注释原话「所有路共用同一个 zoom/cropX/cropY ⇒ 各路露出的是各自画面中相同的相对位置（无缝）」；② cropX/cropY 是源画面归一化坐标(CompareCrop.cs:112-113)，与源分辨率无关。
⇒ 1080p 与 4K 两路会被放大相同的倍数、露出示意相同的相对区间。这正是笔记「① 拉齐 ② 同步放大 ③ 裁切」的描述。
不需要做的
像素级对齐（以某一路为基准反算其余路 crop，使露出的源像素尺寸相同）——该语义已被排除，仓库内亦无任何实现或预留，无需投入。
仍需留意
ReadCompareMagnifySources()(CompareCrop.cs:254-275) 读不到源尺寸（演示模式/纯音频）时记 (0,0)(:265) ⇒ 按「铺满」换算 ⇒ 该路会露出不同源区间（docs/26:643-650 的 8:3 vs 3:8 反例）。且只在启用时读一次(:151)，增删路数不刷新——docs/41:119 已列为 R7 缺陷。这不阻塞本期，但会削弱「放大一致」的实际观感，建议列入二期收尾。
4.8

架构定位：作为独立于传统模式的「额外模式」

已按你的说明确定规避两个陷阱第一期 · ~30 行
你明确：这套能力应作为一个额外模式存在，与传统模式不同。据此，实现方案从「扩展 CompareMode 枚举」改为「新增并列的独立模式开关」——这不仅贴合你的定位，还顺带规避了 4.1 的两个陷阱。
传统 vs 额外
传统模式＝现有 CompareMode 体系（均匀网格 / AB·ABC·ABCD 分屏 / 叠加），语义是「各路画面完整显示在各自格子里」。
额外模式＝在既有分格之上叠加「各路同步放大到同一画面区间，再裁切出格子」——这正是 SetCompareMagnify 的现成语义（CompareCrop.cs:29-34「启用放大：子窗口被排成格的 z 倍并偏移到让目标画面块对齐到格」）。两者的区别恰在于「是否放大裁切」，与你的描述一致。
推荐形态
上层独立、底层复用：额外模式表现为一个与传统模式并列的独立开关/入口；但分格计算继续复用 CompareLayout.ComputeCells，不另写一套。
为何不另起炉灶
项目有一条已归档的教训（元发现 1）：多处缺陷源于同一功能存在两份实现、其中一份是错的 ⇒ 收敛到单一实现。若额外模式自持格表逻辑，就正好制造了两份分格实现——这是明确要避免的形态。
净收益
「与传统模式不一样」体现在上层语义（同步放大裁切 vs 各路完整显示）与UI 入口独立；而底层格表、手柄、覆盖层继续共用。直接收益：额外模式的开关与参数（zoom / crop / 方向）自成一组状态，不必挤进 CompareMode 枚举，从而规避下面两个陷阱。
规避陷阱 ①
不必改 CoerceMode —— 序数前缀判定（发现 4）只在枚举新增值时才出问题；枚举不动即不受影响。
规避陷阱 ②
不再有无编译期警告的静默失败 —— 三处 switch 兜底（发现 5）同样只在新增枚举值时才构成风险。且现有 ModeSystemTests / CompareLayoutTests 完全不受影响。
留给 4.1 的抉择
AB 上下分仍需在两条路径中选一（详见 4.1 修订）：A 加 AbVertical 枚举值（复用 ComputeCells，代价是要改 CoerceMode 为集合判定 + 手动补单测）；B 在额外模式内部自持分割轴（不动枚举，代价是格表出现两份实现）。推荐 A——单一实现原则优先，且 A 的两个代价都是可控的一次性成本。
需确认
该额外模式与现有「叠加模式（S 键）」互斥——CompareCrop.cs:203-205 BuildCellMagnify 已有守卫 _compareOverlayActive 时返回 null，注释明「放大是窗口大于格 + 裁出格，叠加是两窗铺满 + 裁出半区，语义互斥」。若额外模式要保持此互斥，无需改代码；若要允许叠加共存，则需重新设计裁剪语义（成本显著上升，不建议）。

八、已澄清项与仍需拍板项

✅ 已澄清 ①：「分辨率一致」= 放大一致
语义确认为各路放大倍数一致（同步放大），非像素级对齐。该语义由「所有路共用同一 zoom/crop」+「crop 为源画面归一化坐标」两个机制天然保证（CompareCrop.cs:103-105、:112-113）⇒ 零工作量，4.7 关闭。

✅ 已澄清 ②：作为独立于传统模式的额外模式
采纳「上层独立、底层复用」形态 —— 额外的独立开关/入口 + 继续复用 CompareLayout 格表（避免两份实现）。详见 4.8。此项使 AB 竖分不再必须挤进 CompareMode 枚举，从而规避「序数前缀收敛」与「新增枚举无编译警告」两个陷阱。

❓ 仍需拍板 ①：AB 竖分走路径 A 还是 B？（唯一的架构级抉择）
A（本报告推荐）加 AbVertical 枚举值 —— 复用 ComputeCells，符合单一实现原则；代价是必须把 CoerceMode 改为集合判定（发现 4）+ 手动补单测（现有测试不覆盖新增值）。
B 在额外模式内部自持分割轴 —— 不动 CompareMode，与传统模式代码上完全解耦；代价是格表逻辑出现两份实现，正是项目元发现 1 要避免的形态。
我推荐 A；但若你希望额外模式与传统模式在代码层面彻底解耦（而不仅是 UI 入口独立），则 B 更贴合该意图。

❓ 仍需拍板 ②：「A/B 下拉框选源」的最低可接受形态
只需「AB 两路能互换」（4.3，约 25 行、低风险、走格置换），还是完整「任意路 → 任意格」（4.4，200+ 行、横跨排版 / 裁剪下发 / 命中测试 / CellMagnify.SourceOf / 自测五处）？建议先做前者验证需求真实强度。
